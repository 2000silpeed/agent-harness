# R8 — 챗봇 서비스 평가 조사

- 조사일: 2026-11-16
- 대상: 사내 직원용 대화형 어시스턴트의 평가. 기본 기능은 사내 지식 검색(RAG)이고, 도구(MCP)를 통해 업무 시스템의 소스 코드 조회·분석·수정, 업무 데이터 추출, GUI 조작까지 한다는 전제로 썼다. 업무 시스템 고유의 절차는 다루지 않았다(다른 조사가 맡는다).
- 기준 문서: `kit/harness/METHOD.md`(S0~S8), `kit/harness/reference/eval.md`. 이 둘에 이미 있는 규칙(과제 검증, 격리, 비교 규칙, 판정 상태, 잠금)은 다시 적지 않고 "달라지는 점"만 적었다.
- 저장소의 다른 파일은 고치지 않았다. 2절은 제안이다.

## 2. 챗봇 방법론에 넣을 것

단계 이름은 가칭이다: C0 범위, C1 평가, C2 기준선, C6 개선, C8 운영. 코딩 에이전트 방법론의 공통 규칙(증거로 판정, 결과를 보기 전에 판정 규칙 기록, 실패를 숨기지 않음)과 `eval.md` 5절 비교 규칙은 그대로 쓴다고 전제했다.

### C1 평가 — 숨긴 테스트를 대신하는 것

**핵심 한 줄:** 숨긴 테스트의 자리에 "채점자만 보는 기대 결과"가 들어간다. 기대 결과는 과제 유형에 따라 ① 기록 시스템(또는 그 복사본)의 끝 상태 ② 참조 사실·근거 문서 ③ 기대 행동(답한다 / 되묻는다 / 답하지 않는다 / 사람에게 넘긴다) 가운데 하나 이상이다. 대화문에 적힌 "완료했습니다"는 결과가 아니다. [T1][A1][G1]

**고민할 것**
1. **평가 단위는 대화 한 건(시나리오)이다.** 턴 하나의 품질은 진단용이다. 한 턴씩은 괜찮아도 여러 턴에 걸쳐 정보를 받으면 성능과 일관성이 떨어진다. 표본 단위는 시도가 아니라 시나리오이고, 같은 의도·같은 문서에서 나온 시나리오는 한 묶음으로 센다. [A1][T5][H1][L2]
2. **과제 유형마다 "무엇이 결과인가"가 다르다.** 유형별 채점 근거를 먼저 표로 정한다(아래 표). 한 대화가 여러 유형을 포함하면 유형별 검사를 전부 통과해야 한다. [A2][T1]
3. **사용자 쪽을 누가 연기하나.** 셋 가운데 고른다. ① 고정 스크립트(사용자 턴을 전부 미리 적음): 재현성이 가장 높지만 어시스턴트가 다른 길로 가면 다음 턴이 어긋난다. ② 실제 대화의 앞 N−1턴을 주고 다음 응답만 봄: 실제 분포에 가깝고 싸다. ③ 모의 사용자(페르소나 + 목표): 끝까지 가는 흐름을 보지만 일관성이 낮고 시뮬레이터 자체가 틀린다. 회귀 묶음은 ①②, 능력 묶음은 ③을 기본으로 한다(배분은 [제안]). [H1][L1][T1]
4. **모의 사용자를 믿을 수 있나.** 시뮬레이터는 평가 조건의 일부이고 측정 오차의 원천이다. 공개 벤치마크에서도 시뮬레이터 오류가 대화의 16~47%에서 나왔고, 시뮬레이터 모델만 바꿔도 성공률이 최대 9%p 달라졌으며, 사람보다 협조적이라 성공률을 부풀린다는 보고가 있다. 시뮬레이션 결과만으로 출시를 판단하지 않는다. [T2][T3][T4]
5. **답하지 말아야 할 때를 어떻게 채점하나.** 근거 문서가 없는 질문, 범위 밖 질문, 틀린 전제가 든 질문, 요청자 권한 밖의 정보, 사람 전문가가 답해야 하는 질문(인사·법무·재무 판단 등은 [제안])을 따로 유형으로 둔다. "틀린 답 < 답하지 않음 < 맞는 답"의 순서를 점수에 반영하고, 거절이 지나친지도 같이 잰다. [H1][R5][R6][K2]
6. **검색과 생성을 따로 잰다.** 답이 틀렸을 때 문서를 못 찾은 것인지, 찾았는데 잘못 쓴 것인지 가려야 고칠 곳이 정해진다. [H1][R1][R2][O1]
7. **무엇을 코드로, 무엇을 모델로, 무엇을 사람이 채점하나.** 끝 상태·권한 범위·인용 위치의 존재·도구 호출 사실은 코드. 충실도·필수 사실 포함·이관 맥락의 충분함은 보정된 모델 판정. 고위험 영역의 정답성, 판정기와 갈리는 건, 어조 기준 정하기는 사람. [A1][Y1][H1]
8. **답 말고 무엇을 관문으로 두나.** 정책에 없는 약속, 다른 사람·권한 밖 데이터 노출, 확인 없는 쓰기, 운영 시스템 접근, 검색 문서·도구 결과에 심긴 지시를 따른 행동. 관문은 평균에 섞지 않고 1건이면 실패다. [S1][E1][E4][C1]
9. **정답에 닿는 길.** 시뮬레이터 지시문과 채점자 파일이 어시스턴트에 보이는가, 지식 베이스에 평가 문항과 정답이 문서로 들어가 있는가, 대화 메모리에 이전 시도가 남는가, 평가용 계정이 실제보다 넓은 권한을 갖는가. [T1][제안]

**진행**
- 유형별 채점 근거 표를 먼저 채우고, 유형마다 5건으로 파이프라인(환경 초기화 → 대화 실행 → 상태 조회 → 판정)을 끝까지 통과시킨 뒤 늘린다. 개발용은 유형을 합쳐 20건 이상에서 시작한다(제안값. `eval.md` 6절과 같은 하한). [A1][제안]
- 시나리오는 실제 문의 기록, 담당자 인터뷰, 기능 × 상황 × 페르소나 조합에서 뽑는다. 의도별 빈도를 세어 상위 의도와 드문 의도를 모두 넣고, 같은 요청의 바꿔 말하기·오타·맥락 없는 짧은 요청·한 요청에 여러 의도·중간에 주제를 바꾸는 대화를 섞는다. 한 조건만 다른 쌍(권한 있음/없음, 근거 문서 있음/없음)을 넣는다. [H3][O1][A1]

- 환경: 쓰기 과제·GUI 과제는 운영이 아닌 복사본에서 돌리고, 시도마다 스냅숏으로 되돌린다. 지식 베이스 색인과 대화 메모리도 스냅숏을 고정한다. 평가용 요청자 계정은 실제 역할과 같은 권한으로 만든다. [G1][T1][S1][제안]

**검증**
- 케이스 검증(케이스마다): 사람이 정답 경로를 따라간 실행이 3회 모두 통과(제안값), 아무것도 하지 않은 실행은 실패, 아깝게 틀린 실행(다른 품목 변경, 필터 하나 누락, 한 줄 다른 인용)은 실패, 경로만 다른 정답은 통과, 두 사람이 따로 봐도 같은 판정. [T1][G1][A1]
- 시뮬레이터 검증: 대화 표본을 두 사람이 따로 읽고 시뮬레이터 오류를 "과제를 막는 오류 / 무해한 오류"로 센다. 과제를 막는 오류가 나오는 케이스는 지시문을 고친다. 가능하면 같은 시나리오 일부를 실제 직원이 수행해 성공률과 실패 유형을 시뮬레이션과 나란히 본다. [T2][T3][T4]
- 채점기 반례: 완료를 보고했지만 상태가 안 바뀐 실행 → 실패, 기대 상태는 맞지만 다른 레코드도 바뀐 실행 → 실패, 맞는 답이지만 근거 문서에 없는 수치를 덧붙인 답 → 실패, 답할 수 없는 질문에 그럴듯한 답 → 실패, 답할 수 있는 질문에 거절 → 실패, 권한 밖 행이 한 줄 섞인 추출 → 정책 위반, 턴 상한 초과 → 실패, 환경 초기화 실패 → 환경 오류. [제안][R5][S1]
- 격리: 어시스턴트 쪽 컨텍스트·도구로 `user_sim`과 채점자 파일을 읽을 수 없다. 앞 시도의 변경·대화 메모리가 다음 시도에 보이지 않는다. 지식 베이스에서 평가 문항 원문을 검색해 나오지 않는다. [T1][제안]
- 흔들림 폭: 아무것도 바꾸지 않고 같은 조건으로 두 번 돌린 차이를 잰다. 모의 사용자 케이스와 고정 스크립트 케이스의 폭을 따로 적는다. [L1][제안]

**완료 기준 (초안)**
- [ ] 과제 유형별 채점 근거 표가 있고, 유형마다 결과를 대화문이 아닌 곳에서 확인하는 방법이 적혀 있다
- [ ] 케이스 파일이 실행기용과 채점자용으로 나뉘어 있고, 시뮬레이터 지시문과 채점자용 파일을 어시스턴트가 읽을 수 없음을 시험했다
- [ ] 케이스마다 검증 기록이 있다: 정답 경로 통과, 무동작 실패, 아깝게 틀린 실행 실패
- [ ] 답하지 않기·이관·권한 밖 요청 케이스가 답해야 하는 케이스와 짝으로 들어 있다
- [ ] 쓰기·GUI 과제가 비운영 복사본에서 돌고 시도마다 초기화됨을 확인했다
- [ ] 모의 사용자의 잠금 항목이 결과 파일에 남고, 시뮬레이터 오류율을 사람이 검수한 기록이 있다
- [ ] 모델 판정기마다 사람 라벨 대비 TPR·TNR이 있고, 채점기가 반례 시험을 통과했다
- [ ] 반복 수, 주 지표, 개선·회귀 판정 규칙, 흔들림 폭이 결과를 보기 전에 적혀 있다

**흔한 함정:** 어시스턴트의 완료 문장이나 GUI 완료 화면으로 통과시키기, 한 턴 질의응답 정확도만 재고 다중 턴을 안 보기, 시뮬레이터를 검수 없이 믿기, 시뮬레이터 모델·프롬프트를 바꾸고 이전 수치와 비교하기, 충실도와 정답성을 같은 것으로 보기(문서가 낡았으면 충실한 답이 틀린 답이다 [제안]), 답변 관련성·유사도 점수를 통과 기준으로 쓰기, 정답 도구 순서와의 일치율로 떨어뜨리기, 거절만 세고 과잉 거절을 안 세기, 평가 계정에 넓은 권한을 줘서 권한 위반이 드러나지 않게 하기, 1~5점 척도를 여러 개 추적하기, 판정기 일치율 하나만 보고 TPR·TNR을 안 나누기, 평가 문항과 정답을 지식 베이스에 올려 두기.

**순서와 병렬:** 유형별 채점 근거 표 → 환경 초기화·상태 조회 스크립트 → 케이스 작성(케이스별 병렬) → 케이스 검증 → 채점기 반례 → 시뮬레이터 검수 → 첫 전체 실행. 판정기 라벨 수집은 케이스 작성과 동시에 한다. [제안]

| 지표 | 정의 | 용도 |
|---|---|---|
| 시나리오 통과 | 한 시도에서 유효성·정책 관문·결과·응답 검사를 전부 통과 | 기본 단위 [T1][A1] |
| 매번 통과율 (pass^k) | k회 시도가 모두 통과한 시나리오 수 ÷ 전체 시나리오 수 | 주 지표 [T1] |
| 시도 성공률 | 시나리오별 (통과 시도 ÷ k)의 평균 | 보조 [T1] |
| 충실도 | 검색된 문서가 뒷받침하는 주장 수 ÷ 답의 전체 주장 수 | 지식 답변. 1 미만이면 실패로 볼지 미리 정한다 [R1][R2] |
| 필수 사실 포함 | `must_include_facts`가 전부 답에 있으면 1 | 지식 답변·완료 보고 [T1] |
| 인용 재현율 / 정밀도 | 재현율: 인용 구절이 그 주장을 뒷받침하는 주장 수 ÷ 전체 주장 수. 정밀도: 뒷받침에 기여하는 인용 수 ÷ 전체 인용 수 | 인용을 요구할 때 [R4] |
| 검색 Recall@k / MRR | Recall@k: 정답 문서 가운데 상위 k에 든 비율. MRR: 첫 정답 문서 순위의 역수 평균 | 검색 단계만 따로 [H1] |
| 맥락 재현율 / 정밀도 | 재현율: 검색된 맥락이 뒷받침하는 참조 정답의 주장 수 ÷ 참조 정답의 전체 주장 수. 정밀도: 관련 조각이 상위에 있는 정도(순위별 Precision@k의 평균) | 정답 문서 라벨이 없을 때의 대안 [R2] |
| 무응답 정확도 / 과잉 거절률 | 무응답 정확도: 답하면 안 되는 케이스 중 답하지 않거나 넘긴 비율. 과잉 거절률: 답해야 하는 케이스 중 거절·이관한 비율 | 둘을 항상 같이 보고한다 [H1][R6] |
| 진실성 점수 | (맞는 답 수 − 틀린 답 수) ÷ 전체. 답하지 않음은 0점 | 틀린 답에 벌점을 주는 요약 지표 [R5] |
| 이관 재현율 / 정밀도 | 재현율: 넘겨야 하는 케이스 중 넘긴 비율. 정밀도: 넘긴 건 중 넘겨야 했던 비율 | 사람 전문가 이관 [A2][H1] |
| 추출 정확도 | 결과 집합이 참조 집합과 같으면 1. 진단으로 행 재현율(참조 행 중 반환)·행 정밀도(반환 행 중 참조에 있음) | 데이터 추출 [D1] |
| 잘못된 실행률 | 쓰기가 일어난 시도 중 끝 상태가 기대 상태와 다르거나 범위 밖이 바뀐 시도의 비율 | 쓰기·GUI 과제 [T1][G1][제안] |
| 권한 밖 노출 건수 | 요청자 권한 밖의 행·열·객체가 응답·파일·도구 인자에 들어간 시도 수 | 0이 아니면 회귀 [S1][E1] |
| 거짓 완료율 | 완료라고 보고한 시도 중 상태 검사가 실패한 비율 | 보고의 신뢰도 [제안] |

### 다른 단계에 넣을 것

**C0 범위**
- 고민할 것: 어시스턴트가 맡을 과제 유형을 나열하고 유형마다 "결과를 대화 밖에서 확인할 수 있는가"를 적는다. 확인할 복사본이나 조회 수단이 없는 쓰기 과제는 첫 대상으로 삼지 않는다. [T1][G1][제안]
- 고민할 것: 답하지 않을 범위, 사람 전문가에게 넘길 조건과 넘길 곳, 사용자 확인이 필요한 동작, 요청자 권한을 어디서 판정하는지(모델이 아니라 하류 시스템)를 정한다. [S1][A2]
- 고민할 것: 판단 기준을 쥘 도메인 전문가 한 명과, 한국어·사내 맥락을 아는 검토자를 정한다. [H2][H1]
- 완료 기준: 성공 지표 목표가 유형별로 숫자로 있다(매번 통과율, 권한 밖 노출 0건, 잘못된 실행률 상한, 과잉 거절률 상한 — 값은 기준선을 잰 뒤 정한다). [제안]
- 흔한 함정: 자동 처리율이나 만족도 점수 하나를 성공 지표로 삼기. [P1][P3][A1]

**C2 기준선**
- 진행: 대화 기록에 턴, 검색된 문서 ID, 도구 호출과 결과, 확인 요청과 응답, 이관 결정·이유·넘긴 맥락, 종료 사유를 남긴다. 이관 뒤에도 사용자의 필요가 해결될 때까지를 한 기록으로 잇는다. [H1][L2]
- 진행: 기준선은 검색 단계 수치, 유형별 매번 통과율, 관문 위반 건수, 시뮬레이터 오류율, 흔들림 폭을 평가 조건(지식 베이스 스냅숏, 시뮬레이터 버전 포함)과 함께 적는다. [제안]
- 검증: 실패 기록을 전부 읽고 "어시스턴트 / 케이스·채점기 / 시뮬레이터 / 환경"으로 먼저 나눈다. 첫 상류 실패만 표시한다. 공개 벤치마크에서도 실패의 일부는 사용자 지시문 결함이었다. [H1][T1][T2]
- 흔한 함정: 시뮬레이터 오류로 낮게 나온 수치를 기준선으로 삼기. [T2]

**C6 개선**
- 진행: 다중 턴 실패는 한 턴 재현으로 줄여 본다. 한 턴에서도 틀리면 검색·지식 문제이고, 한 턴에서는 맞으면 대화 맥락 문제다. [H1][T5]
- 진행: 오류 분석으로 찾은 실패 유형마다 검사를 하나씩 만든다. 코드로 판정되면 코드, 아니면 판정기를 만들고 사람 라벨로 보정한다. [H1][H3]
- 검증: 고친 유형의 케이스만 보지 않는다. 반대 방향 케이스(거절을 줄였으면 답하지 않기 케이스, 확인 절차를 줄였으면 쓰기 관문)를 같이 돌린다. 기밀 지시를 강화하면 과제 성능이 떨어질 수 있다는 보고가 있다. [A1][E1]
- 흔한 함정: 시뮬레이터 프롬프트와 어시스턴트 프롬프트를 같은 비교 안에서 함께 바꾸기. [제안]

**C8 운영**
- 고민할 것: 사내 어시스턴트의 운영 지표는 소수만 둔다. 과제 성공률(대화 표본을 보정된 판정기와 사람이 판정), 사람 전문가 이관율과 이관 정밀도, 잘못된 실행(사람이 되돌리거나 고친 변경) 건수, 권한 밖 노출 건수, 같은 사용자가 같은 주제로 다시 묻는 비율(기간은 제안값 7일), 포기(되묻는 질문에 답 없이 종료) 비율, 엄지 피드백(응답률과 함께). [A1][H1][P1][P4][제안]
- 고민할 것: 자동 처리율(사람에게 안 넘긴 비율)은 참고로만 둔다. 포기하고 떠난 사용자도 "넘기지 않음"으로 세어지고, 벤더 정의에는 무응답을 해결로 추정하는 규칙이 있다. 다시 묻는 비율과 포기 비율을 반드시 옆에 둔다. [P1][P3][제안]
- 고민할 것: 절감 시간은 체감 설문으로 재지 않는다. 같은 과제의 처리 시간을 사용 집단과 미사용 집단에서 재거나, 표본 과제를 사람이 직접 수행한 시간과 비교한다. 체감과 실측이 반대 방향이었던 대조 시험이 있다. [M1]
- 진행: 운영 대화는 스레드 단위로, 일정 시간 입력이 없으면 끝난 것으로 보고 한 번 채점한다. 전수가 아니라 표본으로 한다. 표본은 무작위를 항상 남기고 부정 피드백·긴 대화·재시도·판정기 표시를 더한다. 검토량 예: 주 10~20건, 주기마다 100건 이상(출처의 예시). [L2][H1]
- 진행: 운영 실패를 케이스로 올리는 절차: 열람 근거 확인 → 비식별화(가린 뒤 사람이 확인) → 앞 N−1턴 고정 또는 페르소나·목표로 재구성 → 기대 결과 작성 → 케이스 검증 → 같은 유형의 "해야 하는 경우"와 짝으로 추가 → 데이터 버전 올림. [H1][A1][K3][K4]
- 진행: 변경의 온라인 확인은 단계적 확대를 기본으로 한다. A/B는 사용자 단위로 나누고, 결정 지표와 가드레일 지표(권한 밖 노출, 잘못된 실행, 이관 대기)를 미리 적고, 변형당 필요한 사용자 수를 n = 16σ²/Δ²로 먼저 계산한다. 성공률 50% 근처에서 5%p 차이를 보려면 변형당 약 1,600명, 10%p면 약 400명이다(직접 계산). 사내 사용자가 그보다 적으면 A/B로 판정하지 않고 오프라인 평가 + 이전 버전 유지 집단과의 비교로 본다. [X1][A1][제안]
- 진행: 새 기능은 처음 며칠 사용이 튄다. 몇 주를 보고, 신규 사용자만 따로 본다. [X1][X2]
- 진행: 지식 베이스가 바뀌면 평가 조건이 바뀐 것이다. 문서 갱신 주기에 맞춰 검색 단계 평가를 다시 돌리고, 참조 정답이 낡았는지 본다. [H1][제안]
- 검증: 운영 판정기의 판정 표본을 사람이 다시 판정해 TPR·TNR이 유지되는지 주기적으로 본다. [H1][A1]
- 흔한 함정: 피드백을 준 대화만 읽기(드물고 스스로 고른 표본이다), 배포 전후 수치만 비교하기, 비식별화 없이 대화 원문을 평가셋에 넣기, 지표 이름만 같고 분모가 다른 수치를 비교하기. [A1][P2][K3]

## 4. 확인 못 한 것

- **열지 못한 원문:** C1 판결문(403), K3 보도자료(페이지는 열렸으나 본문이 나오지 않음), K4 안내서 원문(공식 페이지를 찾지 못함). 셋 다 검색 결과 요약에만 의존했다.
- **초록만 읽은 논문:** T3, T4, R6, R7, J1, J2, J3, G2, D1, D2, E1, E2, E3, E4. 표에 적은 숫자의 실험 조건과 지표 정의는 본문으로 확인해야 한다. 특히 E1의 기밀 인식 평가 방식, D1의 실행 정확도 정의는 2절에서 근거로 쓰므로 본문 확인이 필요하다.
- **nDCG:** 정의를 실은 1차 자료(정보 검색 교재 페이지)가 연결 오류로 열리지 않았다. 2절 지표 표에는 Recall@k·MRR만 넣었다. nDCG를 넣으려면 정의의 출처를 확인한다.
- **T2의 불일치:** 본문 표에는 통신 영역 치명 오류가 6%로 적혀 있는데 표 설명문에는 치명 오류가 없었다고 적혀 있다. 어느 쪽이 맞는지 확인하지 못했다.
- **시드:** 모델 API의 시드 고정이 같은 출력을 보장하는지는 확인하지 않았다. 조사한 벤치마크는 시드가 아니라 온도와 반복 횟수로 흔들림을 다뤘다.
- **코드 분석 답변의 평가:** 저장소 코드에 대한 질의응답을 "실제 소스에 근거했는가"로 채점하는 1차 자료를 찾지 못했다. 2절의 해당 줄은 인용 평가(R4)와 근거 구절 확인(A3)에서 끌어온 제안이다.
- **데이터 추출의 권한 범위 채점:** "요청자 권한 밖 행이 섞였는가"를 지표로 정의한 1차 자료를 찾지 못했다. S1(권한 원칙)과 E1(기밀 인식)에서 끌어온 제안이다.
- **사내 어시스턴트의 운영 지표:** 다시 묻는 비율, 포기 비율, 잘못된 실행률을 사내 어시스턴트에 대해 정의하고 검증한 공개 자료를 찾지 못했다. 고객 지원 벤더 문서(P1~P4)의 정의에서 옮겨 온 제안이고 기간 7일은 근거 없는 시작값이다.

- **한국어 고유 쟁점:** 경어·문체 판정, 띄어쓰기·오타 변형, 한영 혼용 질의에 대한 판정기 신뢰도를 다룬 1차 자료는 찾지 못했다. K1·K2는 한국어 평가셋이 있다는 것과 구성만 확인했다. 사내 대화 기록을 평가에 쓰는 것의 법적 근거(동의, 가명처리)는 K3·K4를 원문으로 읽고 법무 검토를 받아야 한다.

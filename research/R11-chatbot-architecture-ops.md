# R11 — 챗봇 서비스의 범위·구조·지연·비용·운영 조사

조사일: 2026-11-16. 대상: 사내 직원용 대화형 어시스턴트(여러 턴 대화). 기본 기능은 회사 지식 검색이고, 도구(MCP)를 통해 기업 기간 시스템의 소스 코드·업무 데이터를 조회·추출하며, 일부는 코드나 시스템 상태를 바꾼다(화면 자동화 포함). 기간 시스템별 세부는 다른 조사가 맡고, 이 문서는 "기업 기간 시스템" 수준에서만 적는다.
저장소의 다른 파일은 고치지 않았다. 2절은 전부 제안 텍스트다.

읽는 법
- 확인 수준: **[직]** 은 원문(문서의 마크다운판, HTML, PDF)을 내려받아 해당 대목을 직접 읽은 것이다. **[요약경유]** 는 가져오기 도구의 요약 모델이나 검색 요약으로만 본 것이라 문자 단위로 대조하지 못했다. "[직](초록)"은 초록만 읽었다는 뜻이다.
- 숫자는 출처의 것과 우리 것을 구분했다. 출처의 숫자에는 출처 ID와 열람일(2026-11-16) 또는 발행일을 붙였다. **(제안값)** 은 출처에 없는 우리 쪽 시작값이고, 기준선을 잰 뒤 바꾼다. "직접 계산"은 출처의 배수를 넣어 우리가 계산한 예시다.
- 벤더 문서의 성능·절감 수치는 그 벤더의 주장으로만 적었다. 인용문은 넣지 않고 우리말로 요약했다.
- 2절 각 항목 끝의 `[A7]` 같은 표시는 1절의 출처 ID이고, `[제안]`은 출처 없이 우리가 낸 판단이다.

## 2. 챗봇 방법론에 넣을 것

단계 번호는 코딩 에이전트 방법론(S0~S8)과 같은 자리를 쓴다. 여기서는 C0·C2·C7·C8만 다룬다. 평가(C1), 지식·검색(C3), 도구(C4), 가드(C5)는 다른 조사가 맡는다.

### C0. 범위·유형·기반

**고민할 것**
1. **누가 어느 채널에서 쓰나.** 직군, 권한 집단, 채널(사내 메신저, 웹, 업무 화면 내장). 채널마다 스트리밍·버튼·파일·긴 작업 알림 지원이 다르다. 봇이 기존 수단(검색, 담당자 문의)보다 왕복이 적은지를 기준으로 본다. [M1][I2]
2. **요청 목록을 실제 기록에서 뽑는다.** 헬프데스크 티켓, 질문 채널, 사내 검색 로그에서 요청 유형을 뽑아 빈도와 건당 처리 시간으로 줄 세운다. 이상적인 대화를 실제 문장으로 적고 과제 단위로 쪼갠다. [A1][M2]
3. **범위를 세 칸으로 나눈다.** 한다 / 안 한다(이유와 대안을 알리고 끝냄) / 반드시 사람에게 넘긴다. 넘김 계기는 실패 한도 초과와 고위험 행동이다. [A1][O1]
4. **유형을 정한다.** 아래 표에서 고른다. 유형이 올라갈수록 필요한 통제가 더해진다. 첫 버전은 한 유형, 요청 유형 몇 개로 시작한다. [W1][O1][제안]
5. **경로를 누가 정하나.** 지식 답변은 대개 코드가 경로를 정하는 워크플로(라우팅 → 검색 → 생성)로 충분하다. 모델이 순서를 정하게 하는 것은 도구를 여러 번 써야 하는 요청 유형으로 한정한다. [A2][O1]
6. **성공 정의.** 해결률(사용자가 확인한 해결과 암묵적 해결을 구분), 넘김 정확도, 근거 제시율, 응답 정확도, 첫 가시 텍스트 시간, 해결 1건당 비용, 변경형은 승인 없는 변경 0건. 자료의 목표 수치는 예시이므로 우리 기록으로 다시 정한다. [A1][M2]
7. **고지와 책임.** AI임을, 할 수 있는 일과 한계를 첫 메시지에서 알린다. 봇이 확정·약속할 수 없는 것의 목록을 둔다. 고지 의무의 적용 여부는 법무가 확인한다. [E1][A1][O8][G2]
8. **기반(만들기 / 사기 / 플랫폼).** 판단 기준: 모델에 들어가는 요청·응답 원문을 볼 수 있는가, 사용자 신원을 도구까지 전달할 수 있는가, 도구 실행 전에 승인 단계를 끼울 수 있는가, 대화 기록을 내보낼 수 있는가, 모델 버전을 고정할 수 있는가, 채널을 지원하는가. 공급자 쪽으로는 사용 한도와 증가 속도 한도, 지출 상한, 모델 종료 통지 기간, 데이터가 회사 밖으로 나가도 되는 범위를 본다. [A2][P1][A8][O5][A12][O7][제안]

(a) 챗봇 유형과 추가로 필요한 것. 근거는 [P1][P2][W1][O1][F1][ST]이고, 환경 분리와 직무 분리의 구체 기준은 [제안]이다.

| 유형 | 하는 일 | 추가로 필요한 것 | 지연·UX에 미치는 영향 |
|---|---|---|---|
| 지식 답변형 | 회사 지식을 검색해 근거와 함께 답한다 | 검색 결과를 묻는 사람의 문서 권한으로 거른다. 근거 링크. "모른다"와 사람에게 넘기는 경로. 지식 담당자와 갱신 주기 | 첫 텍스트까지 수 초. 스트리밍으로 충분하다 |
| 조회·추출형 | 도구로 기간 시스템의 소스 코드·업무 데이터를 읽는다 | 사용자 신원 전달(공용 고권한 계정 금지, 받은 토큰을 그대로 넘기지 않고 대상이 지정된 토큰으로 교환). 읽기 전용 권한과 읽기 전용 도구만 노출. 조회 범위·건수 상한. 결과 가리기와 기록 보존 규칙. 감사 기록(누가, 어느 시스템·환경에서, 무엇을). 대상 환경(개발·QA·운영)을 대화에 명시. 도구 결과 안의 지시문을 지시로 취급하지 않기 | 도구 실행 시간이 지배한다. 진행 문구를 보내고, 10초를 넘기는 추출은 비동기 작업으로 돌려 완료를 알린다 |
| 변경형 | 코드나 시스템 상태를 바꾼다(화면 자동화 포함) | 위 전부에 더해: 건별 사람 승인(바뀔 내용 미리보기), 요청자와 승인자 분리가 필요한 범위, 멱등 키, 변경 전 상태 보관과 되돌리기 절차, 환경 분리(변경은 개발 환경, 운영 반영은 기존 이관 절차), 봇이 고칠 수 없는 감사 기록, 동시 변경 잠금, 끄는 스위치. 화면 자동화는 API가 없을 때만 쓰고 단계마다 화면 상태를 확인한다 | 분 단위가 될 수 있다. 접수 응답 → 작업 ID → 진행 알림 → 취소 수단 → 결과 확인 요청의 흐름이 필요하다 |

**진행**
- 최근 기록 N건(제안값: 200건)을 요청 유형으로 분류하고, 유형마다 세 칸 중 어디인지와 유형(지식·조회·변경)을 붙인다. [A1][제안]
- 유형별로 이상적인 대화 한 편과 실패 대화 한 편(못 알아들음, 범위 밖, 도구 실패)을 실제 문장으로 쓰고, 도구 후보마다 위험 등급(읽기/쓰기, 되돌릴 수 있는가, 필요한 권한, 영향 범위)을 매긴다. [A1][G1][O1]
- 기반 후보마다 같은 질문 세 개(지식, 조회, 범위 밖)를 넣고 요청·응답 원문과 도구 호출에 실린 신원을 덤프해 읽는다. [P1][제안]

**검증**
- 분류한 기록 가운데 "한다" 칸이 차지하는 비율과, 그중 근거 문서나 도구가 실제로 있는 비율을 센다. 두 사람이 같은 기록 50건(제안값)을 따로 분류해 세 칸 판정이 일치하는 비율도 적는다. [제안]
- 조회·변경형이면 권한이 다른 두 계정으로 같은 요청을 넣어 하위 시스템 기록에 각자의 신원이 찍히는지 본다. [P1][W1]

**완료 기준**
- [ ] 사용자 집단, 채널, 요청 유형 목록(빈도 포함)이 실제 기록을 근거로 적혀 있다
- [ ] 요청 유형마다 한다 / 안 한다 / 사람에게 넘긴다가 정해졌고 넘김 계기가 적혀 있다
- [ ] 유형(지식·조회·변경)과 그 유형이 요구하는 통제 목록이 있고, 도구 후보마다 위험 등급이 있다
- [ ] 성공 지표 목표값과 턴당 지연·대화당 비용 상한이 숫자로 있고 지표마다 확인 방법이 있다
- [ ] 기반 후보별 확인 결과(원문 덤프, 신원 전달, 승인 단계, 기록 내보내기, 모델 고정)와 선택 근거가 decisions.md에 있다
- [ ] 고지 문구와 봇이 확정할 수 없는 것의 목록을 사용자 대표와 법무·보안 담당이 확인했다

**흔한 함정:** 범위를 "무엇이든 물어보세요"로 잡기, 기록 없이 회의에서 요청 목록 만들기, 세 유형을 한 번에 출시하기, 공용 고권한 계정으로 도구를 붙이고 권한 판단을 모델에 맡기기, 자료의 예시 목표(해결률 등)를 우리 목표로 옮겨 적기, 넘김 경로 없이 출시하기.

**순서와 병렬:** 요청 목록과 세 칸 판정이 먼저다. 그다음 기반 후보 조사, 도구 위험 등급, 고지 문구 검토는 동시에 한다.

### C2. 뼈대·관측·기준선

**고민할 것**
1. **한 턴의 흐름.** 아래 (b)를 기본형으로 두고 단계 전환은 코드가 판정한다. 라우팅과 질의 재작성은 한 호출로 합칠 수 있는지 먼저 본다. [O2][A2]
2. **무엇을 병렬로 돌리나.** 입력 검사와 라우팅·검색은 동시에 돌릴 수 있다. 다만 도구가 있는 경로에서는 검사가 끝나기 전에 도구가 실행될 수 있으므로 차단 방식으로 둔다. 읽기 전용 조회는 미리 시작해도 되지만 검사 통과 전에는 보이지 않는다. [O9][O2][A2]
3. **스트리밍이 바꾸는 것.** 검사 전에 글자가 화면에 나간다. 출력 검사를 문장·구획 단위 버퍼로 할지, 끝난 뒤 회수할지 정한다. 표·버튼 같은 구조화 출력은 조각이 완성된 뒤에만 그린다(부분 JSON). 스트림 중간 오류와 거절에 대비해 받은 부분의 처리(지우기, 이어 받기, 표시)를 정한다. [O2][A4][A5][I1]
4. **지연 예산.** 첫 가시 텍스트 시간과 전체 시간을 따로 잡고 단계별로 나눈다. 사용자 동작부터 화면 표시까지 잰다. [O2][N1]
5. **긴 도구 호출.** 예산을 넘는 도구는 동기 턴에 넣지 않는다. 접수 → 작업 ID → 진행 알림 → 완료 알림으로 분리하고, 사용자가 자리를 떠도 결과가 남게 한다. [O10][P2][A1][N1]
6. **기록 구조.** 대화 ⊃ 턴 ⊃ 이벤트. 대화 ID를 모든 하위 호출(검색, 가드, 도구)에 전파해야 대화 단위 비용·지연 합계가 맞는다. 턴마다 요청 유형, 경로, 결과(답함, 되물음, 범위 밖, 넘김, 오류), 피드백을 붙인다. [L1][L2][T1]
7. **원문과 개인정보.** 대화 원문은 민감 정보다. 수집은 명시적으로 켠 경우에만, 가리기는 저장소로 보내기 전에, 열람 권한과 보존 기간을 정한다. 원문을 못 보면 사고 조사가 막히므로 신고된 대화에 한해 열람하는 절차를 둔다. [T1][L1][A14]
8. **피드백 수집.** 답변마다 버튼(해결됨, 도움 됨, 도움 안 됨, 관련 없음 등)과 의견란, 그리고 암묵 신호(되묻기, 같은 질문 반복, 넘김 요청, 이탈)를 턴 ID에 잇는다. 명시적 피드백은 적고 불만 쪽으로 치우친다. [L1][M2][I2]
9. **대화 설계·접근성·언어.** 첫 메시지에 할 수 있는 일 제시, 받은 정보 되짚기, 되묻기는 짧게·두 번째는 선택지와 함께, 연속 실패 상한 뒤 넘김, 넘길 때 대화 요약 전달, 대화 종료 확인. 대화 영역을 보조 기술이 읽을 수 있게 표시하고, 스트리밍 조각마다 낭독되지 않게 한다. 지원 언어와 지원하지 않는 언어의 응답을 정한다. [G1][G2][M1][M2][X1][제안]

(b) 한 턴의 흐름과 지연 예산

```
사용자 메시지
  ① 접수: 인증·세션·권한 집단 확인, "입력 중" 표시                      (코드)
  ② 입력 검사: 길이·금칙·주입·범위 ─┐ 도구 없는 경로에서는 병렬,          (코드+작은 모델)
  ③ 라우팅 + 질의 재작성(한 호출)  ─┘ 도구 경로에서는 ②가 먼저 끝나야 한다 (작은 모델)
       ├─ 범위 밖·넘김 ──► 고정 문구 또는 사람 (모델 호출 없음)
       ├─ 지식 ──► ④ 검색(권한 필터) ──► ⑤ 생성(스트리밍) ──► ⑥ 출력 검사(구획 단위) ──► 화면
       └─ 도구 ──► ④' 도구 계획 ──► [변경형: 사람 승인] ──► 실행(진행 알림 / 비동기) ──► ⑤ ⑥
  ⑦ 턴 종료: 대화 저장, 턴 요약 기록, 피드백 버튼에 턴 ID 연결              (코드)
```

|---|---|---|
| 접수 표시(전송됨, 입력 중) | 0.1초 | 즉각으로 느끼는 한계 [N1] |

| 긴 추출·변경 | 접수 응답 2초 이하, 이후 비동기 | 완료 알림과 취소 수단 [O10][P2][N1] |

**진행**
- 기록기를 먼저 만든다. 턴 시작·끝, 모델 호출, 검색, 가드 판정, 도구 호출, 승인, 피드백을 이벤트로 남기고 전부 대화 ID·턴 ID를 갖게 한다. [L2][T1]
- 가장 단순한 경로(지식형: 재작성 → 검색 → 생성)를 끝까지 돌린 뒤 가드와 도구 경로를 붙인다. [A2]
- 단계별 시간 필드를 넣는다: 접수, 검사, 라우팅, 검색, 첫 토큰, 첫 가시 텍스트(클라이언트 측정), 완결, 도구 실행. [O2]
- 실패용 고정 응답을 먼저 만든다: 범위 밖, 못 알아들음, 시스템 오류, 넘김, 작업 접수. 긴 작업용 작업 저장소(작업 ID, 상태, 진행값, 결과 위치, 소유자)를 대화와 분리해 둔다. [G1][G2][P2][O10]
- 기준선을 잰다: 평가용 대화 묶음과 과거 기록 재생으로 유형별 품질, 단계별 지연 p50/p95, 대화당·해결 1건당 비용, 경로 분포를 조건과 함께 남긴다. 같은 조건으로 한 번 더 돌려 흔들림 폭을 적는다. [O2][제안]

**검증**
- 대화 한 건의 기록만 보고 어느 단계에서 틀렸는지(라우팅, 검색, 생성, 가드, 도구)를 사람이 찾는다. [L2]
- 대화 단위 토큰·비용 합계를 이벤트에서 직접 더해 대시보드 값과 맞춘다. 하위 호출에 대화 ID가 빠진 건수는 0이어야 한다. [L2]
- 일부러 만든 실행: 스트림 중간 오류, 거절로 끝난 응답, 검사에 걸린 입력(도구 경로에서 도구가 실행되지 않았는지), 도구 시간 초과, 가짜 개인정보가 든 메시지(기록에 원문 0건). [A4][A5][O9][L1]
- 긴 작업을 시작한 뒤 창을 닫고 돌아와 결과와 진행 상태가 보이는지 본다. 클라이언트에서 잰 첫 가시 텍스트 시간과 서버의 첫 토큰 시간의 차이를 적는다. [A1][O10][O2]

**완료 기준**
- [ ] 한 턴의 흐름, 단계 전환을 판정하는 코드, 병렬로 도는 구간과 차단으로 도는 구간이 적혀 있다
- [ ] 대화·턴·이벤트 세 층으로 기록되고 모든 하위 호출에 대화 ID와 턴 ID가 있다
- [ ] 턴마다 요청 유형, 경로, 결과, 단계별 시간, 토큰(캐시 읽기·쓰기 포함)이 남고, 피드백(버튼, 의견, 암묵 신호)이 턴 ID에 이어져 조회된다
- [ ] 스트림 중간 오류, 거절, 검사 차단, 도구 시간 초과에서 사용자에게 보이는 응답이 정해져 있고 시험했다
- [ ] 가리기 시험에서 원문이 0건이고, 원문 열람 권한과 보존 기간이 적혀 있다
- [ ] 예산을 넘는 도구는 비동기 작업으로 분리됐고 자리를 떴다 돌아와도 결과가 보인다
- [ ] 유형별 기준선(품질, 지연 p50/p95, 대화당·해결 1건당 비용)이 조건·흔들림 폭과 함께 있다

**흔한 함정:** 서버의 첫 토큰 시간만 재고 화면 표시 시간을 안 재기, 도구 경로에서 검사를 병렬로 돌려 걸리기 전에 도구가 실행되기, 스트리밍한 글자를 회수할 방법 없이 출력 검사를 끝에 두기, 대화 ID를 최상위 호출에만 붙이기, 싫어요 수만 세고 암묵 신호를 안 보기, 긴 도구 호출을 동기 턴에 넣어 시간 초과를 재시도로 덮기, 원문을 전부 남기거나 전혀 못 보게 하기.

**순서와 병렬:** 기록기와 지식형 경로는 동시에 만든다. 고정 응답과 작업 저장소는 그 사이에 만든다. 기준선은 평가용 대화 묶음이 준비되고 구성을 동결한 뒤 잰다.

### C7. 지연·비용 최적화

**고민할 것**
1. **단위.** 호출당이 아니라 대화당, 해결 1건당 비용이다. 넘김으로 끝난 대화, 가드·재작성·임베딩·채점 호출, 재시도가 전부 분자에 들어간다. 변경형은 성공한 작업 1건당으로 따로 잰다. [제안][O4]
2. **입력 비용은 턴마다 는다.** 매 턴 이전 대화를 다시 보내므로 캐시가 없으면 대화당 입력 토큰은 턴 수의 제곱에 비례해 는다. 아래 (c). [A7][직접 계산]
3. **프롬프트 캐싱이 대화에 맞는 조건.** 고정 접두(도구 정의, 시스템 지침)가 최소 길이를 넘는가, 턴 사이 간격이 캐시 수명 안인가, 접두가 바이트 단위로 같은가. 수명·배수·최소 길이·한도 계산 방식은 공급자와 모델마다 다르므로 쓰는 모델의 문서로 확인한다. [A7][O3][A8]
4. **검색 결과를 어디에 넣나.** 턴마다 달라지는 검색 결과를 시스템 프롬프트에 넣으면 그 뒤의 대화 캐시가 매 턴 깨진다. 마지막 사용자 턴 쪽에 두고, 이전 턴의 검색 결과를 대화에 남길지 정한다(남기면 입력이 늘고, 빼면 접두가 바뀔 수 있다). [A7][제안]
5. **긴 대화.** 턴 상한, 요약(압축), 새 대화 권유 가운데 무엇을 쓸지 정한다. 압축은 접두를 바꿔 한 번은 캐시를 잃는다. [A16][O3]
6. **모델 라우팅·캐스케이드.** 쉬운 요청 유형을 작은 모델로 보내면 싸지지만 라우터의 오분류가 품질을 깎고, 모델이 갈리면 캐시도 갈린다. 캐스케이드(작은 모델 먼저, 부족하면 큰 모델)는 올라간 요청의 지연과 비용이 더해진다. 논문의 절감 수치는 벤치마크 결과다. [A2][D1][D2][I1]
7. **응답 캐시(의미 유사 캐시).** 질문이 비슷하면 저장된 답을 돌려주는 방식은 권한·개인·시점에 따라 답이 달라지는 요청에서 위험하다. 다른 권한 집단의 답이 새거나 낡은 답이 나간다. 쓴다면 공개 범위가 같은 지식형 질문으로 한정하고 캐시 키에 권한 집단·지식 버전을 넣고 만료를 둔다. [D3][제안]
8. **일괄 처리와 속도 등급.** 일괄 처리는 대화 턴에 맞지 않는다(결과가 수십 분~24시간 뒤). 야간 평가, 기록 채점, 문서 색인처럼 아무도 기다리지 않는 일에만 쓴다. 추가 요금으로 속도를 올리는 등급은 출력 속도 쪽 이득이라(A11 기준) 첫 토큰 시간이 문제면 효과가 없다. 어느 구간이 느린지 먼저 본다. [A13][A11][O6]

(c) 대화 한 건의 입력 비용 (직접 계산, 배수는 [A7] 기준)

```
기호: S 고정 접두(도구+시스템), u 사용자 메시지, o 응답, R 턴별 검색 결과, T 턴 수,
      p 입력 단가, w 캐시 쓰기 배수, r 캐시 읽기 배수
캐시 없음:  입력 토큰 합 = T·(S + R + u) + (u + o)·T·(T−1)/2          ← T²에 비례
캐시 있음:  턴 t 입력 비용 ≈ p·[ r·(S + 이전 대화) + w·(o_{t−1} + u_t) + R_t ]
            (검색 결과 R_t는 캐시 지점 뒤에 두고 다음 턴에 빼는 배치 기준)
            답이 수명보다 늦게 오면 그 턴은 접두 전체를 w로 다시 쓴다
예시(제안값): S=3,000  u=50  o=300  R=1,500  T=8,  w=1.25  r=0.1, 전부 수명 안에 적중
  캐시 없음: 8·4,550 + 350·28 = 46,200 토큰분
  캐시 있음: 0.1·(24,000 + 9,800) + 1.25·2,500 + 12,000 = 18,505 토큰분 (약 40%)
  → 캐시를 켠 뒤에는 캐시되지 않는 검색 결과(12,000)가 입력 비용의 대부분이다
대화당 비용 = 입력 비용 + 출력 토큰 × 출력 단가 + 가드·재작성·임베딩·채점 호출 + 재시도
해결 1건당 비용 = 전체 대화 비용 합 ÷ 해결된 대화 수
```

**진행**
- 기준선 기록에서 단계별 시간과 토큰을 줄 세워 큰 항부터 본다. [O2]
- 품질을 걸지 않는 것부터 한 번에 하나씩 적용한다: ① 접두 고정과 캐시(변동값을 뒤로, 수명 선택, 필요하면 미리 데우기) ② 호출 수 줄이기(재작성+라우팅 합치기, 코드로 답할 수 있는 것은 모델 없이) ③ 병렬화(독립 조회) ④ 검색 결과 개수·길이 줄이기 ⑤ 출력 길이 지침. [A7][O2][A3]
- 품질을 거는 것은 평가로 정한다: ⑥ 추론 강도 ⑦ 요청 유형별 작은 모델 ⑧ 응답 캐시. 라우터는 요청 유형별 오분류율을 따로 잰다. [A2][D1][제안]
- 캐시 수명은 턴 사이 간격 분포로 정한다. 간격의 중앙값과 p90을 기록에서 뽑아 수명 안에 드는 비율을 계산한다. 변경마다 켜고 끌 수 있게 만들고 전후 수치와 유지 기준 통과 여부를 남긴다. [A7][제안]

**검증**
- 캐시 적중을 사용량 필드(읽기·쓰기 토큰)로 턴별로 확인하고, 2턴째부터 읽기가 0이면 연속 두 요청의 접두를 비교한다. [A7][O3]
- 전후 비교는 같은 대화 묶음, 같은 동시성, 캐시가 찬 상태와 식은 상태를 구분해 잰다. 첫 가시 텍스트와 완결 시간을 둘 다 적는다. 응답에 찍힌 모델·등급 필드가 설정과 같은지도 본다(조용한 내려감 확인). [O2][I1][O6]
- 라우팅·캐스케이드는 요청 유형별 품질이 흔들림 폭 안인지와 올라간 요청의 비율·추가 지연을 같이 적는다. [제안]
- 응답 캐시를 켰다면 권한이 다른 두 계정으로 같은 질문을 넣어 답이 섞이지 않는지, 지식을 바꾼 뒤 낡은 답이 나오지 않는지 본다. [D3][제안]

**완료 기준**
- [ ] 유지 기준(유형별 품질, 정책 위반 0건, 넘김 정확도)이 변경 전에 적혀 있고 유형별 기준선(대화당·해결 1건당 비용, 첫 가시 텍스트·완결 시간 p50/p95)이 있다
- [ ] 캐시 적중률이 턴별 사용량 필드로 확인됐고, 수명 선택의 근거(턴 간격 분포)가 있다
- [ ] 변경마다 끄고 켜는 방법, 전후 수치, 유지 기준 통과 여부가 있다 (변경이 없으면 "변경 없음"과 근거)
- [ ] 라우팅·응답 캐시처럼 품질을 거는 변경은 유형별 평가 결과를 근거로 채택했다 (없으면 "없음")
- [ ] C0의 지연·비용 목표에 도달했거나 더 줄이지 않는 근거가 있다

**흔한 함정:** 호출당 단가로 비교하기, 날짜·사용자 이름·검색 결과를 시스템 프롬프트 앞쪽에 넣어 캐시를 매 턴 깨기, 수명보다 긴 턴 간격인데 캐시 효과를 가정하기, 평가 없이 작은 모델로 내리기, 권한이 걸린 답을 응답 캐시에 넣기, 첫 토큰 시간만 줄이고 사고 토큰·토큰 간 시간으로 전체가 느려진 것을 놓치기, 대화 턴에 일괄 처리 할인을 기대하기, 벤더가 밝힌 절감 수치를 우리 수치로 쓰기.

**순서와 병렬:** 기준선과 낭비 분석은 다른 단계와 동시에 할 수 있다. 적용은 위 번호 순서로 하나씩이다. 프롬프트·도구 정의가 바뀌면 기준선을 다시 잰다.

### C8. 배포·운영

**고민할 것**
1. **무엇을 한 버전으로 묶나.** 프롬프트, 라우팅 규칙, 가드 설정, 도구 정의와 권한, 모델 ID·추론 설정, 지식 색인 버전, 평가 묶음 버전. 하나만 바뀌어도 새 버전이고 턴 기록에 버전이 찍힌다. 모델은 별칭이 아니라 고정 ID로 적는다. [A12][제안]
2. **어떻게 넓히나.** 내부 시험 사용 → 그림자 방식(봇은 초안만 쓰고 사람이 답하거나, 변경형은 실행 없이 계획만 낸다) → 일부 사용자·일부 채널(트래픽 비율) → 전체. 단계마다 넘어가는 기준과 멈추는 기준을 미리 적고 같은 기간의 대조 집단을 남긴다. 유형별로 따로 넓힌다(지식형 먼저, 변경형은 개발 환경부터). [S1][O1][제안]
3. **끄는 스위치와 축소 응답.** 무엇이 죽었을 때 사용자가 무엇을 보는지 미리 정한다. 아래 (d). 스위치는 유형·도구·채널 단위로 둔다. [S2][G1]
4. **공급자 장애와 한도.** 재시도는 횟수 상한·지수 백오프·무작위 지연, 대기 시간 헤더 준수. 재시도해도 안 풀리는 오류(지출 상한 등)를 구분한다. 대체 모델을 둔다면 그 조합도 평가한다. 턴 예산을 넘긴 재시도는 하지 않는다. [A9][A8][O5][S2][A6]
5. **용량.** 동시 대화 수 × 턴당 토큰으로 분당 토큰을 추정해 한도와 비교한다. 급증에는 증가 속도 한도가 걸릴 수 있으므로 출시와 모델 전환은 단계적으로 올린다. 우선 처리·보장 용량 상품은 공급자와 시점에 따라 다르다. [A8][O5][O6][A10]
6. **도구 행동의 재시도 안전.** 변경 도구에는 멱등 키를 붙여 재시도가 두 번 실행되지 않게 하고, 시간 초과 뒤에는 재실행 전에 상태를 조회한다. [ST][P2]
7. **운영에서 무엇을 보나.** 소수만 고른다: 유형별 해결률·넘김률·이탈률, 피드백 비율, 근거 없는 답 표본 비율, 범위 밖 비율, 답 못 한 질문, 첫 가시 텍스트·완결 시간, 해결 1건당 비용, 가드 차단, 도구 오류, 승인 거절률. 오프라인 평가가 못 잡는 저하가 있으므로 운영 표본의 상시 채점과 사용자 신고를 변경 이력과 잇는다. [M2][S1][A14][L2]
8. **지식 운영.** 문서마다 담당자·상태·공개 대상·검토일을 둔다. 답 못 한 질문과 "도움 안 됨"을 주제로 묶어 담당자에게 보내고 처리 기한을 둔다. 자주 쓰이는 문서부터 고친다. 문서가 바뀌면 색인 반영까지의 시간을 잰다. [K1][G2][M2][I2]
9. **바깥이 바뀌면.** 모델 종료 통지를 받으면 종료일 전에 평가 전체와 지연·비용 기준선을 새 모델로 다시 잰다. 지식 색인을 크게 바꾸면 검색 평가와 근거 평가를 다시 돈다. 프리뷰 모델에 운영을 걸지 않는다. 종료 일정과 색인 변경 일정을 릴리스 달력에 올린다. [A12][O7]
10. **사고 대응과 소유.** 잘못된 답, 권한 밖 노출, 승인 없는 변경 각각의 심각도와 첫 조치(스위치, 이전 버전 고정, 변경 되돌리기), 알릴 사람, 원인 기록 양식. 조사에 필요한 대화 열람 절차를 미리 정한다. 소유자도 정한다: 프롬프트·가드, 도구·권한, 지식, 평가 묶음, 릴리스 승인, 사고 대응 각각의 담당자. [A14][K1][제안]

(d) 축소 응답: 무엇이 죽으면 사용자가 무엇을 보나 (내용은 제안값)

| 죽은 것 | 감지 | 사용자가 보는 것 | 하지 않는 것 |
|---|---|---|---|
| 모델 공급자(과부하, 한도, 시간 초과) | 오류 코드, 첫 토큰 시간 초과 | 상한 안에서 재시도 → 대체 모델(평가한 조합만) → 검색 결과 목록과 "요약을 만들지 못했다"는 안내 | 도구 실행, 변경 |
| 검색·색인 | 검색 오류, 결과 0건 급증 | "지금 문서를 찾을 수 없다"와 담당 채널 안내 | 근거 없이 모델 지식만으로 답하기 |
| 입력·출력 검사기 | 검사기 오류·시간 초과 | 지식형은 고정 문구로 재시도 안내, 도구 경로는 중단 | 검사 없이 통과시키기 |
| 조회 도구(기간 시스템) | 도구 오류, 시간 초과 | 실패 사실과 이유, 다시 시도 또는 사람에게 넘김 | 추측한 값으로 답하기 |
| 변경 도구 | 오류, 결과 불명 | "결과를 확인하지 못했다"와 상태 조회 결과, 담당자 연결 | 상태 확인 없는 재실행 |
| 승인 경로(승인자 부재) | 승인 대기 시간 초과 | 대기 중임과 만료 시각, 취소 방법 | 승인 없이 진행 |
| 비동기 작업 실행기 | 작업 정체 | 작업 상태 "지연"과 예상, 취소 수단 | 조용한 재시작 |
| 기록 저장소 | 쓰기 실패 | 지식형은 계속하되 경고 지표를 올린다. 변경형은 중단 | 감사 기록 없이 변경 |
| 사람 넘김 창구(근무 외) | 창구 상태 | 접수 티켓 번호와 응답 예정 시각 | "곧 연결된다"는 약속 |

**진행**
- 릴리스 목록(구성요소별 버전·해시)을 만들고 최종 확인용 평가를 한 번 돌려 미리 정한 기준으로 판정한다. 과거 대화 표본을 새 버전으로 재생해(도구는 실행하지 않고 계획만) 이전 버전과 답·경로·비용·시간을 나란히 본다. [제안]
- 그림자 방식과 시범 운영의 대상, 기간, 대조 집단, 넘어가는 기준, 멈추는 기준(예: 권한 밖 노출 1건이면 즉시 중단)을 적고 시작한다. [S1][O1]
- (d)의 행마다 장애를 실제로 주입해 사용자 화면과 기록을 확인한다. [S2]
- 예상 최대 동시 대화 수로 부하 시험을 하고 한도 대비 여유를 적는다. 트래픽은 단계적으로 올린다. [S2][O5][A8]
- 주간 회고를 돈다: 답 못 한 질문·낮은 피드백 묶음 읽기 → 원인 분류(지식 없음, 지식 낡음, 검색 실패, 생성 오류, 범위 밖, 도구) → 지식 담당자에게 보낼 것, 평가 사례로 승격할 것, 범위 조정. [K1][M2][G2]

**검증**
- 턴 기록에 찍힌 버전이 릴리스 목록과 같고, 응답의 모델 ID가 설정과 같다. [A12]
- 되돌리기를 실제로 해 본다. 이전 버전으로 돌린 뒤 새 대화의 기록에 이전 버전이 찍히는지 본다. 스위치를 유형·도구·채널 단위로 실제로 꺼 본다. 꺼진 동안 사용자가 보는 문구를 확인한다. [제안]
- 변경 도구에 같은 요청을 두 번 보내 한 번만 실행되는지 본다. [ST]
- 문서 한 건을 고친 뒤 답에 반영되기까지의 시간을 재고, 답 못 한 질문 한 건이 담당자에게 전달돼 닫히는 것을 끝까지 따라가 본다. [K1]
- 시범 운영 지표를 대조 집단과 같은 기간으로 비교한다. [S1]

**완료 기준**
- [ ] 릴리스 목록(프롬프트, 가드, 도구·권한, 모델 ID, 지식 색인 버전, 평가 묶음 버전)과 최종 확인용 평가 통과 결과가 있다
- [ ] 확대 단계(내부 시험, 그림자 방식, 일부 사용자, 전체)별 넘어가는 기준과 멈추는 기준이 시작 전에 적혀 있고 유형별로 구분돼 있다
- [ ] 축소 응답 표의 모든 행을 장애 주입으로 시험했고 "하지 않는 것"이 지켜졌다
- [ ] 되돌리기와 끄는 스위치를 한 번 실제로 해 봤다
- [ ] 재시도 정책(상한, 백오프, 재시도하지 않는 오류)과 변경 도구의 멱등 처리가 시험됐고, 예상 최대 부하에서의 한도 대비 여유와 단계적 증가 계획이 있다
- [ ] 운영 지표, 신고 경로, 사고 대응 절차와 담당자가 정해졌다
- [ ] 지식 문서마다 담당자와 상태가 있고, 답 못 한 질문이 담당자에게 가서 닫히는 흐름을 1건 이상 끝까지 돌렸다
- [ ] 모델·지식 변경 시 다시 돌릴 평가 목록과 일정이 있다

**흔한 함정:** 전체 사용자에게 한 번에 열기, 배포 전후 수치만 비교하기, 축소 응답을 정하지 않아 장애 때 빈 화면이나 근거 없는 답이 나가기, 재시도를 상한 없이 걸어 한도 초과를 키우기, 변경 도구를 시간 초과 뒤 그대로 다시 실행하기, 지식 담당자 없이 출시하기, 모델이 바뀌었는데 평가를 다시 돌리지 않기, 프롬프트를 운영에서 바로 고치기, 오프라인 평가가 통과했다고 운영 기록을 안 읽기.

**순서와 병렬:** 릴리스 고정 → 최종 확인 → 재생 → 그림자 방식 → 일부 사용자 순서는 지킨다. 축소 응답 시험, 부하 시험, 지식 담당 지정, 사고 절차 작성은 그 사이에 동시에 한다.

## 4. 확인 못 한 것

- **열지 못한 자료.** DoorDash의 지원 자동화 글(403), Moffatt v. Air Canada 결정문(403). 이 문서에 쓰지 않았다. 소비자 대상 사례라 사내용에는 우선순위가 낮다.
- **요약 경유.** Uber Genie 글(I2)은 직접 내려받기가 막혀 요약 도구로만 봤다. 수치와 버튼 이름은 반영 전에 원문 대조가 필요하다.
- **국내 법령.** 인공지능 발전과 신뢰 기반 조성 등에 관한 기본법(시행 2026-01-22)은 국가법령정보센터에서 법령명과 시행일만 확인했고 조문 본문은 불러오지 못했다. 고지 의무 조항과 사내용 적용 여부는 (확인 필요)다. EU 규정(E1)의 사내용 적용 범위도 법무 확인이 필요하다.
- **환경 분리·직무 분리의 표준 근거.** 개발·시험·운영 분리와 요청자·승인자 분리는 [제안]으로 적었다. ISO/IEC 27002나 NIST SP 800-53의 해당 통제는 이번에 열람하지 않았다 (확인 필요).
- **지연 예산 수치.** (b)의 값은 N1의 세 한계를 빼면 전부 제안값이다. N1은 1968·1991년 연구에 기댄 일반 UI 지침이고, 스트리밍 텍스트에서 사용자가 견디는 시간에 대한 1차 실험 자료는 찾지 못했다.
- **대화 설계 지침의 적용 범위.** G1은 음성 인터페이스용이고 대상 플랫폼은 종료됐다. 연속 오류 상한 같은 수치를 LLM 문자 챗봇에 그대로 쓰는 근거는 없다.
- **그림자 방식·A/B 시험의 챗봇 1차 사례.** 카나리아 일반론(S1) 외에 챗봇 출시를 단계별로 기록한 1차 글은 I1·I2 정도만 확인했다. 표본 크기와 판정 통계는 C1(평가) 조사에 맡긴다.
- **응답 캐시의 권한 누출.** D3은 캐시를 나누는 설정이 있다는 것만 보여준다. 의미 유사 캐시가 권한이 다른 사용자 사이에서 답을 흘린 사례나 측정 자료는 찾지 못했다. 위험 서술은 [제안]이다.
- **공급자 문서의 변동.** 캐시 배수·수명·최소 길이, 한도, 속도 등급, 서버 측 대체, 압축은 2026-11-16에 읽은 값이고 일부는 베타다. A7·O3의 모델별 표는 반영 시점에 다시 확인한다. A10은 해당 상품이 레거시라고 적고 있어 보장 용량의 현재 구매 경로는 확인하지 못했다.

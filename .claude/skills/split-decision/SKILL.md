# split-decision

## 절차
1. 관찰한 문제를 기록이나 로그로 확인한다. 기록이 없으면 먼저 기준선을 만들자고 제안한다.
2. 문제를 아래 표로 분류한다.

| 관찰 | 먼저 점검(분리 전) | 분리를 검토할 근거 |
|---|---|---|
| 정보 부족 | 검색, 조회, 추가 질문 | 서로 다른 근거 조사가 필요 |
| 도구 오선택 | 도구 설명, 입력 계약, 권한 | 도구 범위를 독립시킬 이유 |
| Context 과대 | 불필요한 이력·로그 제거, 스킬화 | 별도 작업으로 분리 가능 |
| 단계 의존성 강함 | 상태, 순서, 종료 조건 | 대개 분리보다 고정 경로(코드) |

3. 이득(병렬화, 집중 Context, 검증 지점)과 비용(호출·토큰, 전달 손실, 실패 지점)을 비교한다. Latency는 가장 긴 경로로 판단한다.
4. 분리를 권고한다면 **Context 경계**와 `templates/subagent-contract.md` 계약을 함께 제시한다.
5. 결론과 근거를 `docs/decisions/YYYY-MM-DD-split-<name>.md`에 남긴다.

# 내 Claude Code 세팅 가이드

> 내 Claude를 어떻게 세팅해서 쓰면 좋은지를 순서대로 정리했다. 단계마다 왜 하는지, 무엇을 하는지, 어떻게 확인하는지, 언제 끝났다고 보는지를 적었다.
> 강의에서 이 목적에 필요한 것만 골랐다. 출처는 `(N일차 M강)`이다. 설정 키와 명령은 버전에 따라 바뀌므로 적용 전에 [공식 문서](https://code.claude.com/docs)로 확인한다. 강의와 공식 문서가 다른 곳은 `notes/`의 "확인 필요"에 적어 뒀다.

## 한눈에 보기

```
A0 기본 이해 ─► A1 전역 정리 ─┬─► A2 프로젝트 지침 ─┐
                              ├─► A3 설정 파일 분리 ─┼─► A5 스킬 ─► A6 훅 ─► A8 검증
                              └─► A4 기록 붙이기 ────┘
                              A7 공개 하네스 분석·포크 (A1 뒤 언제든, 격리된 환경에서)
                              A9 비용·컨텍스트 관리, A10 작업 루틴 (계속)
```

| 단계 | 먼저 끝낼 것 | 같이 할 수 있는 것 | 끝났다는 기준 |
|---|---|---|---|
| A0 기본 이해 | 없음 | 없음 | 무엇이 언제 컨텍스트에 들어가는지 설명할 수 있다 |
| A1 전역 정리 | A0 | 없음 | 빈 폴더에서 켰을 때 내가 의도한 것만 로드된다 |
| A2 프로젝트 지침 | A1 | A3, A4 | 새 세션이 지침을 따르고, 팀원도 같은 지침을 받는다 |
| A3 설정 파일 분리 | A1 | A2, A4 | 팀 설정과 개인 설정이 나뉘고 금지 항목이 실제로 막힌다 |
| A4 기록 붙이기 | A1 | A2, A3 | 한 턴을 돌리면 기록이 보인다 |
| A5 스킬 | A2 | A7 | 불려야 할 때 불리고 아닐 때 안 불린다 |
| A6 훅 | A3 (안내 문구는 A5) | A7 | 위반을 넣으면 막히고, 깨진 입력에도 정한 대로 동작한다 |
| A7 공개 하네스 | A1 | A5, A6 | 포크본 하나만 설치돼 있다 |
| A8 검증 | A2~A6 | 없음 | 빈 폴더의 작은 작업이 끝까지 통과한다 |

A9·A10은 끝이 없는 습관이다. 매주 회고하면서 조정한다.

---

## A0. 기본 이해

**왜:** 설정은 결국 "무엇을 언제 컨텍스트에 넣을지"를 정하는 일이다. 구조를 모르면 Claude가 대신 설계해 주지 않는다(6일차 2강).

**할 일**
- 공식 문서의 핵심 개념을 읽는다: 작동 방식, 확장(스킬·훅·MCP·플러그인), `.claude` 디렉터리, 컨텍스트 윈도우(6일차 1강).
- 세 가지를 구분한다(6일차 교재).
  - **지침(메모리)** 은 부탁이다. 모델이 읽고 따르지만 보장은 아니다.
  - **스킬**은 위임이다. 필요할 때 읽는 절차다.
  - **훅과 권한 설정**은 강제다. 정해진 시점에 코드가 실행된다.
- 지침 파일은 시스템 프롬프트가 아니라 대화 쪽(유저 메시지)에 들어가고, 여러 계층이 덮어쓰지 않고 이어붙는다는 점을 기억한다(6일차 2강·교재).

**끝났다는 기준:** 세션을 시작할 때 무엇이 자동으로 로드되고(지침, 자동 메모리, 스킬 설명, MCP 도구 이름), 무엇이 필요할 때만 로드되는지(스킬 본문, 경로 범위 규칙) 말할 수 있다.

## A1. 전역 정리 (`~/.claude`)

**왜:** 전역에 둔 것은 어느 폴더에서 켜든 다 로드된다. 전역이 지저분하면 모든 프로젝트가 영향을 받고, 팀원과 결과가 달라진다(6일차 1·2강).

**할 일**
- **전역 지침(`~/.claude/CLAUDE.md`)** 은 비우거나 모든 프로젝트에 공통인 것만 둔다.
- **전역 스킬**도 공통으로 쓰는 것만 둔다. 스킬 설명도 매 세션 토큰이다.
- **`~/.claude/settings.json`** 을 점검한다.
  - 권한은 금지 목록(`permissions.deny`) 위주로 본다. 안 쓰는 내장 기능은 명시적으로 끈다.
  - 기본 모델과 추론 강도(effort)를 정한다.
  - 상태줄(status line)을 켠다. 내용은 A9에서 정한다.
- **자동 메모리**(`~/.claude/projects/<프로젝트>/memory/`)가 어디에 쌓이는지 확인한다. 이건 내 PC에만 있다. "같은 Claude인데 왜 나만 다르지"의 원인이 된다. 주요 프로젝트는 직접 읽고 고친다.
- PC를 여러 대 쓰면 `settings.json`을 직접 옮기거나 버전 관리한다. 자동으로 복사되지 않는다.

**확인:** 아무것도 없는 빈 폴더에서 Claude를 켜고 컨텍스트에 무엇이 올라왔는지 본다(지침, 스킬 목록, MCP 도구 수와 점유율).

**끝났다는 기준**
- [ ] 빈 폴더에서 켰을 때 의도하지 않은 지침·스킬·도구가 로드되지 않는다
- [ ] 금지 목록과 기본 모델·추론 강도가 내가 정한 값이다
- [ ] 자동 메모리 위치를 알고 있고 한 번 읽어 봤다

## A2. 프로젝트 지침

**왜:** 팀이 같은 결과를 내려면 지침이 저장소에 있어야 한다. 한 파일에 다 적으면 읽고도 잊는다(6일차 2강).

**할 일**
- **프로젝트 지침(`CLAUDE.md`)** 을 저장소에 커밋한다. 템플릿: [`templates/CLAUDE.md`](templates/CLAUDE.md)
  - 짧게 쓴다(200줄 이하 권장, 6일차 교재). 구역은 XML 태그로 통일한다.
  - 넣는 것: 프로젝트 한 줄 설명, 빌드·테스트 명령, 공통 규칙, 작업 방식, 금지 사항.
- **특정 폴더·파일에만 필요한 규칙**은 `.claude/rules/`에 경로 범위(`paths`)를 달아 둔다. 그 파일을 다룰 때만 로드된다. 예시: [`templates/rules/testing.md`](templates/rules/testing.md)
- **개인용 지침**은 `CLAUDE.local.md`에 두고 `.gitignore`에 넣는다.
- **다른 AI 도구와 같이 쓰면** 원본을 한 파일로 통일한다. `CLAUDE`로 시작하는 파일(특히 `CLAUDE.local.md`)이 있으면 `AGENTS.md`를 읽지 않는다. `AGENTS.md`를 원본으로 삼고 `CLAUDE.md`에는 `@AGENTS.md` 한 줄만 두는 방식이 있다(6일차 2강).
- 기존 팀 노하우(위키 등)를 규칙 파일로 옮길 담당자를 정한다.

**승격 규칙:** 같은 컨벤션을 **두 번 틀리면** 지침에 한 줄 추가한다(6일차 교재).

**확인:** 새 세션을 열어 지침에 적은 규칙이 필요한 작업을 시켜 본다. 규칙 파일은 해당 경로의 파일을 다룰 때 로드되는지 본다.

**끝났다는 기준**
- [ ] `CLAUDE.md`가 커밋돼 있고 200줄 이하다
- [ ] 폴더·파일 한정 규칙이 `.claude/rules/`로 분리됐다
- [ ] 개인 지침 파일이 `.gitignore`에 있다
- [ ] 새 세션이 지침의 명령·규칙을 따른다

**흔한 함정:** 지침에 적었으니 지켜질 거라 믿기. 반드시 지켜져야 하면 A6으로 옮긴다.

## A3. 설정 파일 분리

**왜:** 팀이 공유할 설정과 나만 쓰는 설정이 섞이면 서로의 환경을 깨뜨린다. 비싼 모델 설정이 전역에 있으면 모든 프로젝트 비용이 오른다(6일차 6강).

**할 일**
- **`.claude/settings.json`** 은 팀 공유(커밋): 훅, MCP, 권한 금지 목록. 템플릿: [`templates/settings.json`](templates/settings.json)
- **`.claude/settings.local.json`** 은 나만(커밋 제외). 템플릿: [`templates/settings.local.example.json`](templates/settings.local.example.json)
- **이 프로젝트에서만 다른 모델·엔드포인트**를 쓰려면 프로젝트 설정의 `env`에 둔다. 전역은 건드리지 않는다.
- **비밀 키**는 Claude와의 대화에 넣지 않는다. 빈 틀만 만들게 하고 직접 채운다(5일차 4강). `.env` 읽기는 금지 목록에 넣는다.

**확인:** 금지 목록에 넣은 행동(예: `.env` 읽기)을 일부러 시켜서 거부되는지 본다.

**끝났다는 기준**
- [ ] 팀 설정과 개인 설정이 파일로 나뉘고 개인 설정은 커밋되지 않는다
- [ ] 금지 항목이 실제로 거부된다
- [ ] 전역 설정에 프로젝트 전용 값이 없다

## A4. 기록 붙이기

**왜:** 측정해야 개선할 수 있다. 내 사용 기록을 쌓아야 낭비와 반복 실수가 보인다(5일차 2강).

**할 일**
- 관측 도구를 붙인다. 강의 예시는 Langfuse 공식 플러그인이다.
  ```
  claude plugin marketplace add langfuse/Claude-Observability-Plugin
  claude plugin install langfuse-observability@langfuse-observability
  ```
  설정 키는 `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, `LANGFUSE_BASE_URL`이다. 리전에 맞는 주소를 넣지 않으면 인증 오류가 난다. 설치 뒤 재시작한다. ([공식 저장소](https://github.com/langfuse/Claude-Observability-Plugin))
- 회사 코드가 기록에 들어간다. 클라우드에 보내도 되는지 먼저 확인하고, 안 되면 셀프호스팅을 쓴다.
- 기록은 응답이 끝날 때 전송된다. 바로 안 보이면 지연인지 연동 실패인지 구분한다.

**확인:** 한 턴을 돌리고 기록 화면에서 그 턴의 도구 호출과 소요 시간이 보이는지 확인한다.

**끝났다는 기준**
- [ ] 어느 폴더에서 켜든 기록이 쌓인다
- [ ] 한 턴을 열어 오래 걸린 호출을 찾을 수 있다

**이후 사용:** 일주일 이상 쌓은 뒤 패턴을 본다(5일차 7강). 오류 뒤 재시도 반복, 한 번에 묶을 수 있었던 연속 호출이 대표적인 낭비다.

## A5. 스킬

**왜:** 같은 절차를 매번 붙여넣는 건 낭비이고, 지침에 다 넣으면 항상 토큰을 먹는다. 스킬은 필요할 때만 본문을 읽는다(4일차 2강).

**승격 규칙:** 같은 절차를 **세 번째 붙여넣게 되면** 스킬로 만든다(6일차 교재).

**할 일**
- 구조: `SKILL.md` + 필요하면 `scripts/`(실행 코드), `references/`(상세 문서), `assets/`(양식).
- **설명(description)** 은 무엇을 하는지와 언제 쓰는지(아닌 경우 포함)를 짧게 쓴다. 이 한 줄로 불릴지가 정해진다.
- **본문**은 XML 태그로 구역을 나누고 핵심만 둔다. 상세는 `references/`로 빼고 "언제 읽을지"를 적는다(4일차 5강).
- 쓰는 도구의 사용법도 스킬에 적는다.
- **부작용이 있거나 순서가 중요한 절차**는 모델이 스스로 부르지 못하게 하고(`disable-model-invocation: true`) 내가 직접 부른다(6일차 4강).
- 프로젝트 전용 스킬은 프로젝트의 `.claude/skills/`에 둔다.

**확인:** 불려야 하는 요청 3개와 불리면 안 되는 요청 3개를 넣어 본다(4일차 2강).

**끝났다는 기준**
- [ ] 스킬마다 호출 시험 6건의 결과가 기대와 같다
- [ ] 본문이 짧고 상세는 별도 파일에 있다

**흔한 함정:** 설명을 길게 쓰기, 남의 스킬을 그대로 복사해 쓰기(동작을 보고 패턴만 가져온다, 4일차 4강).

## A6. 훅

**왜:** 지침과 스킬은 "가끔" 지켜진다. 매번 일어나야 하는 일은 코드로 강제해야 한다. 훅이 안정성을 가장 크게 좌우한다(6일차 3·6강).

**승격 규칙:** 묻지 않아도 **매번 일어나야 하는 일**은 훅에 연결한다(6일차 교재).

**할 일**
- **언제 동작해야 하는지**부터 정한다. 도구 실행 전과 후가 가장 중요하다.
  - 실행 전(PreToolUse)은 **막는다.**
  - 실행 후(PostToolUse)는 **고치게 한다.** 이미 실행된 뒤라 되돌리지 않는다.
  - 끝내기 전(Stop)은 **확인한다.**
  - 입력 제출(UserPromptSubmit)은 모델에 가기 전이다. 자꾸 잊는 지침을 붙이기 좋다.
  - 세션 종료에는 중요한 정리를 맡기지 않는다. 정상 종료가 드물다.
- **검사는 훅, 해결은 스킬.** 훅 메시지에 고치는 방법을 적는다.
- **판정은 코드로 한다.** 돌릴 테스트도 이름·폴더 규칙으로 고른다. 모델 판단을 끼우지 않는다.
- 예시 3개를 [`hooks/`](hooks/)에 뒀다. 기본으로 켜지지 않는다. 필요할 때 [`hooks/settings.example.json`](hooks/settings.example.json)을 보고 연결한다.
  - `plan_gate.py`: 승인된 계획이 없으면 코드 수정을 막는다.
  - `test_after_edit.py`: 고친 파일과 짝지은 테스트만 돌리고 실패하면 알려준다.
  - `prompt_reminder.sh`: 자꾸 잊는 지침을 매 요청에 붙인다.
- 프로젝트 훅은 **규칙이 생긴 뒤 필요가 확인되면** 만든다. 미리 많이 만들지 않는다(6일차 6강).

**반드시 알아야 할 함정**(6일차 교재)
- 명시적 차단 신호(exit 2 또는 JSON 거부)만 막는다. **exit 1, 스크립트 오류, 시간 초과는 조용히 통과한다.**
- 셸 명령으로 파일을 쓰면 편집 도구용 검사를 거치지 않는다.
- 꼭 막아야 하는 것은 권한 금지 목록(A3)으로도 이중으로 막는다.
- 훅은 권한을 조일 수는 있어도 풀 수는 없다.
- 클론한 저장소의 훅도 내 PC에서 실행된다. 신뢰하는 저장소에서만 켠다.
- 끝내기 전 검사의 두 번째 통과는 재검증이 아니다. 최종 방어선은 리뷰와 CI다.

**확인:** 훅 스크립트에 입력을 직접 넣어 본다. 정상 입력 → 통과, 위반 입력 → 차단, 깨진 입력 → 정한 대로.

**끝났다는 기준**
- [ ] 켠 훅마다 세 가지 입력(정상, 위반, 깨진 입력) 시험 결과가 있다
- [ ] 실제 세션에서 위반을 시도했을 때 막힌다
- [ ] 막지 못하는 우회 경로를 알고 있다

## A7. 공개 하네스·플러그인

**왜:** 처음부터 짜는 것보다 검증된 것을 가져와 내 방식에 맞게 고치는 편이 빠르다. 다만 그대로 쓰면 내 작업 방식과 어긋나고 토큰을 많이 쓴다(6일차 4·5강).

**할 일**
1. 설치 전에 Claude에게 구성(스킬·에이전트·훅·MCP 수)과 위험을 분석시킨다.
2. 망가져도 되는 환경에서 설치해 한 번 써 본다. 잘못되면 설정 폴더를 지우면 되는 환경이어야 한다.
3. **포크**해서 어긋나는 점만 바꾼다: 계획 승인 절차, 커밋·PR 자율성, 언어 규칙, 역할별 모델.
4. 개인화 버전을 설치하면 **원본은 지운다.** 둘 다 있으면 충돌한다.
5. 계획 단계에는 질문형 인터뷰 도구가 유용하다. 질문이 끝나지 않으면 20턴쯤에서 멈추고 결과물을 만들게 한다(6일차 5강).

**끝났다는 기준**
- [ ] 포크본 하나만 설치돼 있고 원본은 지웠다
- [ ] 무엇을 왜 바꿨는지 적어 뒀다

## A8. 검증

**왜:** 설정이 맞는지는 실제 작업을 끝까지 돌려 봐야 안다(6일차 6강).

**할 일**
- **빈 폴더**에 세팅을 설치하고 작은 개발 작업(예: 백엔드 API 하나)을 처음부터 끝까지 맡긴다.
- 지켜보면서 확인한다: 지침을 따르는가, 스킬이 제때 불리는가, 훅이 막을 것을 막는가, 기록이 남는가.

**끝났다는 기준**
- [ ] 작은 작업이 계획 → 구현 → 테스트 통과까지 끝났다
- [ ] 그 과정에서 지침·스킬·훅·기록이 각각 한 번 이상 의도대로 동작했다
- [ ] 발견한 문제를 승격 규칙(두 번 → 지침, 세 번 → 스킬, 매번 → 훅)에 따라 반영했다

## A9. 비용·컨텍스트 관리 (계속)

- **컨텍스트 길이가 비용이다.** 길수록 느리고 비싸다(7일차 1·2강). 큰 탐색은 서브에이전트에 맡기고 결론만 받는다.
- **캐시를 깨지 않는다.** 프롬프트 앞부분이 바뀌면 캐시가 깨진다. 상태줄에 캐시 상태를 띄워 두면 알아챌 수 있다(3일차 7강).
- **컨텍스트 사용률을 본다.** 강사 설정은 60~65%에서 경고, 80%를 넘으면 요청을 보내기 전에 압축부터 한다(6일차 3강). 압축 전에 무엇이 중요한지 지시하고, 요약은 파일로도 남긴다.
- **MCP 도구 수를 확인한다.** 연결만 해도 도구 설명이 컨텍스트를 먹는다(4일차 1강).
- **역할별로 모델과 추론 강도를 나눈다.** 계획은 강한 모델, 단순 작업은 작은 모델(6일차 4강). 새 모델은 최고 강도가 아니라 중간에서 시작해 비교한다(7일차 1강).
- **출력도 비용이다.** 출력을 줄이는 도구나 지침을 검토한다(3일차 7강).
- **잘못 지시했으면 기다리지 말고 멈추고 정정한다**(3일차 7강).

## A10. 작업 루틴 (계속)

1. **요구 정리:** 모호하면 인터뷰하게 한다. 질문에 답하면서 숨은 가정을 드러낸다(3일차 7강, 6일차 5강).
2. **계획 → 리뷰 → 승인:** 코드를 바꾸기 전에 계획(수정 대상, 순서, 테스트 방법)을 쓰고, 다른 컨텍스트의 리뷰를 받고, 내가 승인한다(5일차 7강).
3. **실행:** 계획이 서면 목표만 주고 방법은 맡긴다(`/goal`, 3일차 7강).
4. **검증:** "완료했다"는 말이 아니라 테스트 결과와 실제 변경으로 확인한다.
5. **주간 회고:** 새 세션에서 "내 대화 기록을 분석해줘"로 낭비와 반복을 찾는다(3일차 7강). 찾은 것을 승격 규칙에 따라 반영한다.

### 승격 규칙 (한 장 요약)

| 신호 | 옮길 곳 |
|---|---|
| 같은 컨벤션을 두 번 틀렸다 | 지침 (`CLAUDE.md` 또는 경로 규칙) |
| 같은 절차를 세 번째 붙여넣는다 | 스킬 |
| 묻지 않아도 매번 일어나야 한다 | 훅 |
| 다른 저장소에도 같은 구성이 필요하다 | 플러그인 |
| 그래도 실수가 반복된다 | 더 강한 층으로 (지침 → 스킬 → 훅·권한 → 테스트·CI) |

## 전체가 끝났다는 기준

1. 빈 폴더에서 켰을 때 의도한 것만 로드된다 (A1)
2. 프로젝트 지침·규칙·설정이 저장소에 있고 팀원도 같은 것을 받는다 (A2, A3)
3. 모든 세션이 기록된다 (A4)
4. 반드시 지켜야 하는 규칙은 훅이나 권한 설정으로 막힌다 (A6)
5. 빈 폴더의 작은 작업이 끝까지 통과했다 (A8)
6. 주간 회고 일정이 있다 (A10)

> 8일차(가드레일·보안) 강의가 올라오면 A3(권한)과 A6(훅)을 보강한다.

# 8. 실행 패턴

모든 구조는 **순차, 병렬, 분기, 루프** 네 가지의 조합입니다. 패턴을 고르기 전에 **상태와 의존관계**를 먼저 그립니다. 순서는 목표 → 필요한 상태 → 작업 → 선행 조건 → 종료 조건입니다. "Billing Agent를 만들자"가 아니라 "무엇이 먼저 필요할까?"를 묻습니다. [강의]

| 패턴 | 실행 구조 | 확인할 질문 |
|---|---|---|
| Router | 조건 분기 | 어떤 경로로 보낼까? |
| Supervisor | 분기 + 루프 (+병렬) | 누가 결과를 받고 다음 일을 정할까? |
| Orchestrator-Worker | 분해 → 실행 → 집계 | 어떻게 나누고 다시 합칠까? |
| Swarm/Handoff | 담당자 전환 + 반복 | 누가 대화를 이어받을까? |
| Hierarchical | 위 구조를 중첩 | 새 경계가 정말 필요한가? |
| Plan-and-Execute | 계획 → 실행 → 관찰 → 재계획 | 실행 중에 계획을 고칠 수 있나? |

## 패턴별 주의점 [강의]
- **Supervisor**: 전문가는 결과만 돌려주고 제어권은 Supervisor에 남습니다.
- **Orchestrator-Worker**: Worker 수보다 **작업의 독립성과 결과 계약**이 중요합니다. 검증을 통과하면 종료하고, 근거가 부족한데 예산이 남아 있으면 재계획합니다.
- **Plan-and-Execute**: Claude Code가 대부분 이 방식으로 동작합니다. 반드시 waterfall일 필요는 없습니다.
- **Hierarchical**: 계층 사이로 넘기는 것은 전체 로그가 아니라 **근거, 상태, 한계**입니다.
- **Swarm**: 수평 대화는 결론이 나지 않습니다. 체어맨, 투표, max turn 같은 종료 장치를 코드로 강제해야 합니다. 실전에서 쓰는 것은 드뭅니다.
- 실전에서 흔한 구조는 Plan-and-Execute에 개별 전문가 실행자(분석, 코드 생성, 리뷰)를 두는 형태입니다. 전문가끼리 직접 주고받는 방식은 통제가 어렵습니다.
- Manager 방식(결과를 돌려받음)과 Handoff 방식(대화를 넘김)은 함께 쓸 수 있습니다.
- LangGraph `Send`는 동적 작업 배분 수단일 뿐, 그 자체가 멀티 에이전트 아키텍처는 아닙니다.

## Trace 비교 항목 [강의]
control owner, 호출 수, Context 전달 범위, 최종 응답 주체

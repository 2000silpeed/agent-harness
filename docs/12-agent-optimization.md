# 12. 에이전트 최적화: 동작은 그대로, 근거는 남기고

## 3원칙 [강의, 3일차 6강]
1. **동작이 바뀌면 안 된다.** 도구 호출 순서, 입출력 계약, 사용자가 보는 응답 흐름이 여기에 들어갑니다.
2. **켜고 끌 수 있게 한다.** 토글이 있어야 직접 비교할 수 있고, 자동으로 품질과 지연을 체크할 수 있습니다.
3. **근거와 함께 한다.** "모든 최적화 작업에는 기존 작업에 어떤 문제가 있었고 어떻게 개선했다라는 근거가 꼭 필요하다. 이 작업의 근거를 나한테 꼭 남겨라."

## 관점 체크리스트 [강의]
정답을 주지 말고 질문을 던져서 "코드로 판단해 봐라"고 시킵니다.

**컨텍스트 관점(넣는 양 줄이기)**
- [ ] 도구 수를 줄일 수 있나?
- [ ] 프롬프트를 더 줄일 수 있나?
- [ ] 스킬로 뺄 지점은 없나?

**구조 관점(지연 줄이기)**
- [ ] 서브에이전트로 분리하면 지연이 줄어드나?
- [ ] 더 작은 모델(예: Sonnet → Haiku)로 처리할 수 있나?
- [ ] 판단 구간을 디시전 전용 모델로 바꿀 수 있나?

## 사례 [강의]
- 한 턴 약 4초 → **1.42초**
- 가장 큰 효과는 Sonnet → Haiku(약 1.5초 감소)이고, 판단 구간을 디시전 모델로 바꿔 약 1초를 더 줄였습니다. 입력 토큰도 줄었습니다.

## 작업 방식 [강의]
- **새 세션**을 열고, 모델을 **Opus**로 바꾸고, 기존 코드베이스를 참고로 줍니다. 검토, 의견, 개선에는 Opus를 권장합니다.
- 구현보다 **분석을 먼저** 시킵니다. 끝나면 "진짜 개선이 됐는지"를 검토합니다.
- 근거는 `docs/decisions/YYYY-MM-DD-<name>.md`([`templates/optimization-log.md`](../templates/optimization-log.md))에 남깁니다.

스킬 `optimize-agent`가 이 과정을 안내합니다.

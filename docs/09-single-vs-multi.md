# 9. Single vs Multi: 언제 나눌까

## 시작은 무조건 싱글 [강의]
- 싱글은 쪼갤 수 있지만 멀티는 다시 합치기 어렵습니다. "다시 못 합칩니다."
- 진행 순서: **싱글 + 스킬 → 품질 하락을 측정·기록으로 확인 → 큰 작업부터 서브에이전트로 분리**
- "스킬을 먼저 만들어 보시는 게 훨씬 더 좋은 접근이다." 스킬이 아주 커지면 그때 서브에이전트로 넓힙니다.
- 기준은 "내 작업을 잘 해줄 수 있고 그게 적정한 시간인가"입니다. 싱글이냐 멀티냐 자체는 중요하지 않습니다.

## 실패 원인부터 구분한다 [강의]
| 관찰한 문제 | 먼저 점검할 것 | 분리를 검토할 근거 |
|---|---|---|
| 정보 부족 | 검색, 조회, 추가 질문이 적절했나 | 서로 다른 근거 조사가 필요한가 |
| 도구 오선택 | 도구 설명, 입력 계약, 권한 | 도구 범위를 독립시킬 이유가 있나 |
| Context 과대 | 불필요한 이력과 로그 | 별도 작업으로 뗄 수 있나 |
| 단계 의존성이 강함 | 상태, 순서, 종료 조건 | 분리보다 고정 경로가 맞지 않나 |

## 이득과 비용 [강의]
- 이득: 병렬화, 집중된 Context, 전문화된 검증 지점
- 비용: 호출과 토큰 증가, 전달 손실과 조정 지연, 추가 실패 지점(공유 상태, 재시도, 권한)
- Latency는 에이전트 수가 아니라 **가장 긴 실행 경로**로 판단합니다.
- **SubAgent는 페르소나가 아니라 Context 경계로 나눕니다.** Context 분리와 보안 격리는 별개이므로 권한은 따로 설계합니다.
- 공개된 수치를 읽을 때는 비교 조건부터 확인합니다(무엇 대비, 어떤 eval인지).
- **Fast Path / Slow Path**: 단순한 것은 빠른 경로, 복합 조사는 O-W로 보냅니다. 쓰기 실행 게이트는 공통입니다. "Fast Path는 안전 검사를 생략하는 지름길이 아닙니다."

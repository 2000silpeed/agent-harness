# 1. RAG: 잘 찾아오기와 잘 이야기하기

## 두 축 [강의]
RAG에서 신경 쓸 것은 둘뿐입니다.
1. **잘 찾아오기 = 적게, 정확히.** 많이 가져오면 컨텍스트가 낭비되고, 에이전트가 무엇을 봐야 할지 헷갈립니다.
2. **잘 이야기하기 = 배경지식.** 자료를 줘도 배경지식이 없으면 답하지 못합니다. 배경지식은 스킬로 붙입니다([02-skills.md](02-skills.md)).

## 벡터 DB는 기본값이 아니다 [강의]
"예제가 벡터 DB여서 쓰는 경우가 많아요." 벡터 DB를 걷어내는 프로젝트도 늘고 있습니다. 이유는 다음과 같습니다.
- 임베딩 모델의 발전이 체감되지 않습니다.
- RDB 정형 데이터를 가져오는 경우가 많습니다.
- 파일로 저장해도 빠릅니다.
- 한국어는 BM25 쪽으로 치우칩니다.
- 모델을 바꾸면 다시 임베딩해야 합니다.

파싱은 더 이상 핵심 고민이 아닙니다. 이제 고민할 것은 **저장 방식**입니다.

## 계층 폴더 + index.md [강의]
```
대카테고리/index.md
  중카테고리A/index.md
    소카테고리A-1/index.md, 문서1, 문서2
```
- AI는 우리가 어떻게 저장했는지 모릅니다. 그래서 카테고리마다 `index.md`를 두고 "여기에 이런 정보가 있으니 가서 찾아봐"라고 안내합니다. 템플릿은 [`templates/index.md`](../templates/index.md)입니다.
- 인덱스는 **촘촘하되 문서만큼 길지 않게** 씁니다. 너무 깊게 만들면 찾는 데 오래 걸립니다.
- 인덱스 운영은 검색엔진 운영과 같습니다. 문서가 바뀌면 인덱스도 추가, 개선, 배치 재생성으로 갱신합니다.
- RAG는 저장(벡터DB 또는 계층 파일 + 인덱스), 검색(전체 읽기 또는 발췌 읽기), 활용의 3단계입니다.

## 탐색은 따로 돌린다 [강의]
- `index.md`를 따라 내려가는 탐색 기록은 메인 컨텍스트를 채웁니다. 이 루프를 **서브에이전트**로 떼어 내고 결과만 받습니다. 서브에이전트의 가장 쉬운 출발점입니다.
- "파일은 여기 있다"를 찾는 일은 **작은 모델이나 디시전 모델**로 충분합니다. 찾는 일에는 모델 크기가 상관없습니다.
- 대가는 모델 호출이 하나 늘어나는 것입니다. "'불편하다'가 개선의 출발점"입니다.

## 안티패턴
- 많이 찾아와서 몽땅 넣기
- 예제가 그렇다는 이유로 벡터 DB 채택
- 시스템 프롬프트에 지식을 장황하게 쓰거나 상황마다 치환하기(캐시가 깨짐)
- 파인튜닝으로 지식 주입

# 사례: 배달앱 메뉴 태깅 — 싱글에서 멀티로 [강의, 3일차 3강]

과제는 "엽떡"을 엽기떡볶이(가맹점) → 떡볶이 → 분식으로 맵핑·태깅하는 것이었습니다. 데이터는 약 5천만 건이었고, 가장 큰 병목은 양이었습니다. 판서 기준 처리량은 하루 약 150만 건입니다(전사에서는 "100만 건 남짓"으로 언급).

| # | 단계 | 배운 점 |
|---|---|---|
| 1 | 목표부터 정하고 실행 방식을 고름 | 실시간이 필요 없어서 **배치**로 처리 |
| 2 | 조회 도구 + 시스템 프롬프트(룰 + 퓨샷) + 결과 파일 저장 | 가장 단순한 구성으로 시작 |
| 3 | 3만 토큰 프롬프트를 **카테고리별 스킬**로 분리 | 토큰을 늘려도 품질이 오르지 않음. 시스템 프롬프트는 "스킬을 찾아 그대로 해라"로 가벼워짐. 아직 싱글 에이전트 |
| 4 | 라우팅 결과를 **DB 컬럼에 사전 저장** | 건마다 다시 판단하지 않음(상태 관리). 틀릴 수 있으니 기록도 남김 |
| 5 | 후보 추리기 → 선택 → 상세 맵핑 + 리뷰 역할로 단계 분할 | 사람이 맵핑하는 방식을 따라 하니 단계가 자연스럽게 나뉨 |
| 6 | 하위 메뉴 단위로 반복 | 앞부분은 캐시에 두고 뒤쪽 데이터만 교체 |
| 7 | 골드 데이터셋 | 사람이 확정한 결과로 평가하고 구체적으로 피드백 |
| 8 | 스킬을 **카테고리별 에이전트**로 분리 | 몇천만 건에서는 스킬 로드도 비용. 컨텍스트 격리 |
| 9 | 컨텍스트 레이아웃: `[고정] skill 가공 프롬프트` → `[고정] 하위 음식명 100개` → `[변동] 가맹점 조회 결과` | 변동 영역만 교체 |
| 10 | 일정 압박으로 모델 축소(판서: Gemma 31B → Qwen 8B), 생각 순서를 프롬프트로 지시 | 단계를 잘게 나눠 둔 덕에 모델을 바꿔도 대응 가능 |

교훈: "시작부터 분리하십시오, 별로 좋은 방식은 아니었습니다." 싱글 + 스킬로 시작하고, 스킬이 많아지거나 컨텍스트 격리가 필요할 때 분리합니다. 잘 만든 프로그램은 안 건드리는 게 최선입니다.

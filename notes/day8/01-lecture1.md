### 핵심 요약 (3~5줄)
- 수업 마지막 날 첫 강의다. Gemini 4 Carbon 출시 소식과 "AI로 인한 두뇌 과부하" 글로 시작한 뒤, 가드레일에 들어가기 전에 1~7일차를 판서로 한 줄씩 복습했다. 이유는 "가드레일은 내용이 많진 않아요. 왜 많지 않은지를 이야기하려면" 지금까지 배운 것을 봐야 해서다.
- 복습의 뼈대: RAG(데이터를 기반으로 이야기하게 하기) → 데이터를 잇는 도구의 공통 규격 MCP → 해석 지식을 넣는 스킬(조각 지식)과 코드 모드 → 운영(Langfuse 트레이스 → 골드 데이터셋 → 평가) → 하네스와 훅(DeepAgents에서는 미들웨어) → 메모리와 셀프 임프루빙(드리밍) → 모델이 바뀔 때의 로컬 서빙(vLLM, KV 캐시, 양자화).
- 어제 내용의 보충 두 가지: (1) 웨이트 양자화와 KV 캐시 양자화는 "한쪽만 적용해서는 안 돼요" — 웨이트가 8비트면 KV 캐시도 8비트 이하로 맞춘다. (2) H200 스펙표에서 INT8과 FP8의 연산 수치가 같아서 INT8은 따로 이야기하지 않는다.
- 오늘 주제: 시스템을 잘 구성해도 "항상 사용자가 문제"다. 사용자 입력은 항상 예상을 벗어나고 AI 출력도 가끔 벗어난다. **내부 동작은 최소 권한 원칙과 훅(정규식 등 코드)으로 제어**하고, **사용자 입력 필터링과 AI 출력 방어가 가드레일**이다. 지금까지 내부만 봤다면 오늘은 입출력이라는 "마지막 관문"을 본다.

**1. 모델 소식: Gemini 4 Carbon (00:56~05:47)**
- Gemini에서 새 모델이 나왔다. **Gemini 4 Carbon**은 이미 출시돼 있었고, 일반에 풀린 것이 "어제 새벽"이라고 했다. 강사의 태도는 "기대는 안 되지만"이다("워낙 실망을 많이 시켜서").
- 강사 경험은 Carbon이 아니라 **Gemini 4 Argon**이다. 코딩에는 써 보지 않았고, **한국어를 잘해서 윤문**에 많이 썼다. Claude로 글을 쓰면 "불편한 번역투"가 많은 것과 비교했다. 다만 한국어 문체를 바꾸는 일은 "확실히 한국 모델이 좀 잘하긴 하더라고요".
- Carbon의 특징(강사 설명): 컴퓨터 유즈 기능을 최근 보강해서 출시했고, 텍스트 출력 모델이라 이미지 생성은 안 된다(Gemini는 이미지 모델을 따로 낸다).
  - (공식 문서 확인: https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/4-carbon — 출력은 텍스트만, 이미지·오디오·비디오는 입력 전용, 컴퓨터 유즈 지원, "Google's frontier model". 이 페이지에는 일반 공개 날짜가 없어 "어제 새벽"은 미확인.)
- 가격: Gemini 시리즈의 하이엔드인데 "이벤트가가 아닌 가격"이 **입력 4달러 / 출력 20달러**, 11월 말까지는 그 절반이다. 어제 본 **Fable 5.2는 8달러 / 40달러**라 "출력이 엄청 비싸요" — Gemini는 그 절반이다.
  - (공식 문서 확인: https://aistudio.google.com/docs/pricing — Gemini 4 Carbon·Argon 모두 2026-11-30까지 입력 $2 / 출력 $10, 2026-12-01부터 $4 / $20, 무료 등급 없음.)
  - (공식 문서 확인: https://platform.claude.com/docs/en/about-claude/pricing — Claude Fable 5.2 입력 $8 / 출력 $40, Fable 5.1은 $10 / $50.)
- 강사는 Gemini 요금제를 결제해 둔 게 없어서 오늘·내일 사람들이 쓰는 걸 보고 써 볼 생각이다. 수강생이 "아직 울트라만 풀린 것 같아"라고 했고, 강사는 프로 계정을 가족과 공유 중이라 "아직 써보려면 멀었네요"라고 답했다(소비자 앱 등급별 공개 범위는 미확인).
- 출시 흐름에 대한 강사 관찰: 9월 미국 모델, 10월 중국 모델, 11월 다시 미국 모델 — 경쟁이 심화된다. 수업이 끝날 즈음 모델사들이 **블랙프라이데이 요금제**를 낼 것 같으니 "블프 때 잘 구매를 해놔야 됩니다"(1년을 "따뜻하게" 보내려면).
- 강조 이유: 프로젝트와 실무에서 쓸 모델의 가격 감각. 출력 단가가 비용을 좌우한다는 점을 Fable 5.2와 대조해 보여 줬다.

**3. 복습의 이유와 키워드 지도 (08:38~10:23)**
- 수업으로 진행하는 마지막 날이다. 가드레일을 하기 전에 복습하는 이유: "가드레일은 내용이 많진 않아요. 왜 많지 않은지를 이야기하려면 지금까지 여러분들이 공부해 오셨던 걸 한번 쭉 볼 필요가 있어서".

**4. RAG: 데이터를 기반으로 이야기하게 하기 (10:26~12:41)**
- "한마디로 뭐였나요?" 질문에 수강생들이 답했고, 강사 정리는 "**우리가 가진 데이터를 기반으로 이야기하게 하는 거죠**".
- 중요했던 세 가지: 데이터를 **어떻게 가져오는지**, **어떻게 넣어 주는지**, **원하는 답변으로 만드는지**.
- 앞으로 어떤 에이전트를 만들든 "**RAG는 이제 기본 포함입니다. 왜냐면 데이터를 사용하지 않는 에이전트란 없거든요.**" 예외로 어제 수강생이 만든 영어 공부 챗봇처럼 모델의 순수 지식만 쓰는 경우가 있지만, 기능을 더하면 곧 데이터를 쓰는 RAG 에이전트가 된다.
- RAG는 "에이전트라는 말이 없을 때에도 존재"했다. 판서로 RAG를 **데이터**와 **이야기(답변 생성, 전사 "희연" — 추정)** 두 요소로 나눴고, 이후 복습은 "데이터를 가져오는 부분"을 파헤치는 순서로 이어졌다.

**5. 도구와 MCP (12:41~13:49)**
- 데이터 소스가 워낙 많다(RDB, 벡터 DB, 파일 시스템). 이 많은 시스템을 연동하려고 쓴 방식이 **도구**이고, "그 도구의 **공통 규격**이 바로 MCP".
- 강사는 풀네임을 "모델 텍스트 프로토콜"이라고 말했다(13:18). 바로 이어 "모델의 컨텍스트를 집어넣을 때 사용하는 공통된 약속"이라고 설명했으므로 말실수로 보인다.
  - (공식 문서 확인: https://modelcontextprotocol.io/docs/getting-started/intro — "MCP (Model Context Protocol) is an open-source standard for connecting AI applications to external systems.")
- 정리: 데이터를 넣는 여러 방식을 MCP로 통일했고, "MCP는 사실상 도구들을 표준화한 거죠".

**6. 스킬(조각 지식)과 코드 모드 (13:49~16:05)**
- 도구로 데이터를 잘 가져와도 "표현이 썩 마음에 들지 않아요. **데이터만으로 얘기하는 건 한계가 있습니다.**" 예: RDB **컬럼명**만으로 이야기하면 그 컬럼을 모르는 사람은 "절대 못" 알아듣는다.
- 그래서 추가 지식을 부여한다 — 이것이 **스킬**이다. "아 이 데이터를 이렇게 해석하십시오" 같은 **조각 지식**을 주입한다.
- 구도: **데이터는 MCP 같은 툴로, 답변에 대한 지식은 스킬로** 다룬다.
- 더 나아가면 스킬이 툴을 포함한다(스킬이 더 광범위한 개념). "굳이 MCP를 써야 되나"도 고민해 봤고, 스킬 안에 소스코드를 넣어 두고 실행하게 만드는 것도 했다 → **코드 모드**.
- 코드 모드에 꼭 필요한 도구는 스킬이 넣어 줄 수 없고 **에이전트가 항상 가지고 있어야 한다**: **코드 인터프리터** 같은 코드 실행 도구.
  - (저장소 확인: `Day08/Day08_02.png` — 2026-11-05 커밋의 판서 그림. "Agent Harness" 상자 안에 Prompt·Model·Skills·Tools, Tools 옆 "Code Interpreter", Skills 아래 "Tool 보다 좀 더 큰 개념 = 도메인 지식 저장", "Code Mode 등 적절한 프로그램 실행 설계", 오른쪽 "MCP Server 1. 공통화 2. 보안성". 이번 강의에서 그린 판서와 같은 그림인지는 미확인이나 구도가 같다.)

**7. 운영: 옵저버빌리티 → 골드 데이터셋 → 평가 (16:05~17:25)**
- 에이전트를 운영하면 여러 지표를 봐야 하고, 이때 **옵저버빌리티 도구**를 쓴다. 대표로 **Langfuse**를 썼고 거기서 **트레이스**를 봤다.
- 트레이스로 하고 싶었던 일은 **골드 데이터셋을 만들고 그것으로 평가(evaluation)** 하는 것이다. "고정된 환경의 시험지"를 잘 맞히면 넘어가고, 틀리면 **오답노트**를 만들어 개선한다. "**얘가 100점을 맞게 계속 만들어야 됩니다.**"
- 그 과정에서 계속 시험지와 평가에 집중했고, 그걸 위해 계속 **기록**을 만들었다.

**8. 하네스와 훅(미들웨어) (17:25~19:14)**
- 에이전트가 점점 복잡해졌다(큰 박스를 그리면 RAG라는 글자가 작아진다). 복잡한 시스템을 제어하려고 **하네스** — "모델을 둘러싼 정말 모든 것들" — 을 제어하기 시작한다.
- 에이전트를 하나의 **루프**(강사가 계속 그리던 동그라미)로 보면 "모델이 제어하는 거 말고 **코드로도 제어하고 싶다**"는 생각이 든다.
- 에이전트 **생애 주기** 안의 네 지점을 예로 들었다: 시작할 때, 도구를 실행할 때, 서브에이전트를 실행할 때, 작업이 안정적으로 마무리됐을 때. 이 지점들에서 필요한 코드를 실행하게 만드는 것이 "**훅 또는 DeepAgents에서는 미들웨어**"다.
  - (저장소 확인: `Day08/Day8_Agent_Guardrails_이론자료.pdf` p.46 "Middleware Hook과 방어 책임의 매핑" — `before_agent`, `before_model`, `wrap_model_call`, `after_model`, `wrap_tool_call`, `after_agent`. 교재는 이 훅들에 가드레일 책임을 붙인다. 이 표 자체는 이 강에서 다루지 않았다.)
- 하네스의 나머지 요소도 공부했지만 **훅을 더 강조해서** 배웠다고 정리했다.

**9. 메모리: MEMORY.md는 링크된 리스트 (19:14~21:05)**
- 데이터 중 "특별한 데이터": DB에서 꺼내 오는 것이 아니라 **에이전트가 작업한 내용을 기억**해야 하는 **메모리**. 구현 방식이 정말 다양했다.
- Claude에서 본 메모리 파일: 한 줄 한 줄 쓰여 있고, **어디서 만들어졌는지**(유저 세션에서 만들어졌다, 프로젝트를 실행하고 얻었다)를 **메타데이터**로 남겨 뒀다. 그 밖의 메모리는 대부분 그냥 `memory.md` 파일이었고, 이 md 파일을 어떻게 관리할지에 대한 힌트는 주로 **Claude Code**에서 봤다.
- 구조: "메모리.md는 그냥 리스트였어요. … **문서와 링크된 리스트**". 들어가면 세부 기억 문서로 이어지고 거기에 세부 기억이 촘촘히 있다.

**11. 모델이 바뀐다면: vLLM·KV 캐시·메모리 병목 (24:32~26:24)**

- 어제 본 것: **vLLM** 엔진과, "우리를 가장 힘들게 만드는 녀석"인 **KV 캐시**.
- 왜 컴퓨트 이야기는 별로 안 하고 KV 캐시만 했나: **메모리가 중요해서**다. 컴퓨트는 "지금도 잘해요. 아주 빵빵합니다. Vera Rubin 안 나와도 될 것 같아요." 그 컴퓨트를 감당할 **메모리는 아직 기술적 한계**에 부딪히고 있고 HBM부터 엄청 비싸다. 그래서 KV 캐시를 **오프로딩**까지 해 가며 효율적으로 쓰는 방법을 이야기했다.
  - (공식 문서 확인: https://www.nvidia.com/en-us/data-center/technologies/rubin/ — NVIDIA Vera Rubin 플랫폼 제품 페이지. 강사는 이름만 언급.)
  - (저장소 확인: `Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf` p.68 "KV tiering / offload — 긴 prefix를 계층 간 재사용할 때".)

**12. 양자화: 웨이트와 KV 캐시를 맞춘다 (26:24~28:51)**
- KV 캐시에서 가장 먼저 고민할 것이 **양자화**(데이터 타입을 바꾸는 것)다. 양자화에는 **모델 웨이트 양자화**와 **KV 캐시 양자화**가 있다. "**한쪽만 적용해서는 안 돼요.** 한쪽만 적용하는 건 의미가 없다고 말씀드렸습니다."
- 어제의 예: 모델을 **FP8**로 양자화해 쓰는데 KV 캐시가 **BF16**이면, 계산은 다 8비트인데 저장하려고 16비트로 2배 늘려야 하는 "바보 같은 짓"이다.
- **어제 말하지 않은 것**: 반대로 내려서 저장하는 경우. FP8로 연산하고 **FP4로 저장**하면 반으로 줄였다가 다시 가져올 때 두 배로 늘려야 해서 "왔다 갔다 하는 과정에서 계속 손실"이 난다. 손실이 감당 가능하면 해도 되지만 "잘 안 그럽니다". 그럴 정도면 모델도 같이 내려야 한다.
- 결론: 보통 모델 웨이트와 맞춰서 간다. "**모델 웨이트가 8비트면 KV 캐시도 8비트 이하로만 유지**하는 거죠."
  - (저장소와의 차이: `Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf` p.49 "Weight와 KV Quantization"은 "'INT4 모델'이라고 해서 KV Cache도 INT4라는 뜻은 아닙니다"라며 웨이트 dtype과 KV dtype을 **별개 설정**으로 두고, Weight INT4 + KV BF16 조합도 개념 분리표에 넣는다. 강의의 "한쪽만 적용하면 의미가 없다"는 운영 권고이고 교재는 두 설정이 독립이라는 사실을 적는다 → "의미가 없다"는 평가는 미확인.)

**13. INT8과 FP8: H200 스펙으로 본 이유 (28:51~31:31)**
- 어제 말하지 않은 데이터 타입: **INT8·INT4**. 부동소수점과의 차이는 뒤쪽 정확도 부분이다. 그러면 정수 타입으로 바꾸면 연산 효율이 훨씬 좋아질까? 강사는 좋아질 거라는 기대를 깔고 NVIDIA **H200** 스펙 페이지를 열었다.
- 화면에서 확인한 것: INT8 연산 항목이 따로 있는데 **FP8과 차이가 없다**(전사 "IP8"). 폼팩터 차이로 약간의 속도 차이만 있다.
  - (공식 문서 확인: https://www.nvidia.com/en-us/data-center/h200/ — "FP8 Tensor Core 3,958 TFLOPS"(SXM) / 3,341(NVL), "INT8 Tensor Core 3,958"(SXM) / 3,341(NVL), 각주 "With sparsity". 두 행의 수치가 같고 차이는 SXM·NVL 폼팩터에서만 난다 — 강의 설명과 일치.)
- 강사가 든 이유: INT8이 "0,1,2,…,7로 깔끔하게 정의된" 정수가 아니어서 FP8과 거의 다르지 않다는 취지다. 이 구간 전사가 흐리고 설명 자체도 근거를 대지 않았다 → 미확인.
- 결론: "**그래서 INT8을 이야기하지 않는 겁니다. 어차피 저건 별 쓸모가 없어요.**" 부동소수점(FP8) 위주로만 이야기하는 이유다.

**14. 양자화 포맷: GGUF·AWQ·MXFP4·NVFP4 (31:39~35:42)**
- 어제의 요점 재확인: KV 캐시가 정말 중요하고, 줄이는 게 중요하고, 웨이트와 KV 두 개를 맞추는 게 중요하다.
- **GGUF**: Ollama로 소개한 양자화 포맷. Ollama의 엔진은 **llama.cpp**(전사 "라마다.cpp")이고 Ollama는 프론트엔드다. 장점은 엔진에서 오는데 **CPU·GPU를 모두 쓸 수 있어** CPU로 적절히 오프로딩해 준다.
  - (공식 문서 확인: https://github.com/ollama/ollama — README가 llama.cpp를 "Supported backends" 항목으로 든다. "Ollama의 엔진 = llama.cpp, Ollama = 프론트엔드"라는 관계 표현은 강의 설명이다.)
- **vLLM도 GGUF를 돌릴 수 있다.** 다만 "아직까지도 실험 단계", "실험 단계 된 지 1년 넘었거든요" — vLLM이 "썩 좋아하지 않는" 것이다.
  - (공식 문서 확인: https://docs.vllm.ai/en/latest/features/quantization/gguf.html — "GGUF support in vLLM is highly experimental and under-optimized at the moment". 현재 문서는 GGUF 지원이 `vllm-gguf-plugin`으로 옮겨졌다고 적는다. "1년 넘었다"는 기간은 미확인.)
- vLLM은 그보다 **AWQ** 같은 방식의 양자화를 더 선호한다. "왜 선호하는지는 … 밝혀지지 않았고"(강사도 모른다고 함).
  - (저장소 확인: `Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf` p.51 — 후보 표에 "AWQ / GPTQ 계열 INT4", "FP8 W8A8", "NVFP4 / MXFP4", "BitsAndBytes". 선호 순위는 교재에 없다.)
- 요즘은 일반 양자화가 아니라 **하드웨어 스펙** 또는 **모델 스펙과 결합된** 양자화가 채택된다.
  - **MXFP4**: 작년에 나온 OpenAI의 오픈소스 모델 **GPT OSS**(120B·20B)가 출시 때 낸 포맷. 모델사가 "이렇게 양자화했더니 성능 저하가 가장 덜하던데요"라며 낸 스펙이라는 설명.
    - (공식 문서 확인: https://github.com/openai/gpt-oss — gpt-oss-120b·gpt-oss-20b, "The models were post-trained with MXFP4 quantization of the MoE weights". "성능 저하가 가장 덜하다"는 문구는 이 페이지에 없다 → 강사 표현.)
  - **NVFP4**(전사 "MVFP4"): NVIDIA 칩셋에 맞춘 포맷. 가져갈 GPU가 **블랙웰 이상**이면 "적극 고려하시는 게 좋아요" — 최신 칩셋에서 속도는 늘리고 성능은 유지했다는 뜻이니 "안 쓸 리 없다".
    - (공식 문서 확인: https://developer.nvidia.com/blog/introducing-nvfp4-for-efficient-and-accurate-low-precision-inference/ — "NVFP4 is an innovative 4-bit floating point format introduced with the NVIDIA Blackwell GPU architecture." FP8 대비 정확도 저하 1% 이하 사례를 제시.)
- 이런 포맷은 깊이 보면 **중간중간 레이어만 4비트**이고 **엄청 중요한 것은 BF16으로 유지**하는 선택적 양자화다.
  - (공식 문서의 표현은 "MoE weights"만 MXFP4라는 것까지다. "중요한 레이어는 BF16"이라는 일반화는 강의 설명.)

**16. 오늘의 주제: 가드레일 (39:29~43:59)**
- 에이전트 시스템을 예쁘게 구성해 놓으면 "뭐가 문제냐면 **항상 사용자가 문제**"다. 사용자는 아무것도 모르고 질문한다.
- 크게 보면 통제 대상이 셋이다.
  1. **사용자 입력** — "사용자의 입력은 항상 예상을 벗어납니다. … 우리가 예측했던 대로 해준 적이 없어요."
  2. **AI 출력** — 스킬과 데이터를 아무리 잘 해 둬도 "가끔 벗어나긴 합니다".
  3. **내부 동작** — 에이전트가 데이터 시스템을 건드리고, 코드를 짜고, 연동된 시스템에서 동작을 일으킨다.
- **내부 동작**은 해결이 비교적 쉽다(정확히는 "막을 수 있는 방법이 별로 없어서").

    - (저장소 확인: `Day08/Day8_Agent_Guardrails_이론자료.pdf` p.45 "각 역할에 최소권한을 부여합니다", p.52 "Subagent마다 최소권한을 확인합니다".)
  - **훅**: 동작을 **코드로 캐치**한다. "너 왜 인서트를 써?" 같은 것은 **정규표현식**으로 집어낼 수 있다.
    - (저장소 확인: `Day08/Day08_01.png` — 2026-11-05 커밋의 판서 그림. "오동작을 막아낸다 => 툴을 제한한다", `def get_db(sql: str)` 아래 "1. DB 조회 계정 권한 2. sql 이 SELECT 만". 같은 구도이나 이번 강의 판서인지는 미확인.)
- **입력과 출력**은 어떻게 제어하나 — 이것이 오늘의 **가드레일**이다.
  - 사용자 입력이 시스템에 위험을 가한다면 **어떻게 필터링하고 방어할지**.

### 강사 팁
- 동시에 돌리는 에이전트 작업 수를 줄인다. 작업이 끝나면 맥락을 닫고 다시 쳐다보지 않는다. 사람은 비동기로 동작하지 못한다(댓글 사례는 두세 개).
- 모델 가격은 출력 단가를 본다. 도입가(이벤트가)와 정가를 구분해서 읽는다.
- 한국어 윤문은 한국어를 잘하는 모델을 따로 써 볼 만하다(강사 경험: Gemini 4 Argon, 문체 변환은 한국 모델).
- 블랙프라이데이 요금제가 나오면 그때 구독을 사 둔다.
- 어떤 에이전트든 RAG는 기본 포함이라고 생각한다. 데이터는 도구(MCP)로, 해석 지식은 스킬로 나눠 넣는다.
- 코드 모드를 쓰려면 코드 실행 도구는 스킬이 아니라 에이전트가 기본으로 가지고 있어야 한다.
- 메모리에는 성공보다 실패와 사용자 질책이 남는다. 그 기억을 시스템 프롬프트·스킬·메모리 정리 중 한 곳으로 옮겨 개선한다. 시스템 프롬프트에만 계속 넣으면 비대해진다.
- 웨이트와 KV 캐시의 데이터 타입은 맞춘다. FP8 웨이트에 BF16 KV 캐시는 올려 저장하는 낭비이고, FP8 웨이트에 FP4 KV 캐시는 오갈 때마다 손실이 난다.
- INT8은 따로 고려하지 않는다(H200 스펙상 FP8과 수치가 같다).
- GPU가 블랙웰 이상이면 NVFP4를 적극 고려한다. vLLM에서 GGUF는 돌아가지만 실험 단계다.
- 27B급만 가져갈 수 있는 환경은 대안이 적다(Gemma, Nemotron). 큰 장비(H200 8장급)가 있으면 선택 폭이 넓다(GLM, Mistral 등).
- 에이전트 내부 통제는 권한을 "정말 정말 조금" 주는 것이 근본이고, 훅으로 동작을 코드로 잡는다.
- 가드레일은 새 기술이 아니라 "프로그램 만들면서 다 했던 고민"이다.

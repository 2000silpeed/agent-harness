### 핵심 요약 (3~5줄)
- 모델 가드 대신 **에이전트 루프 속 툴 가드**를 다룬다. 모델 출력은 모델사가 대부분 처리하고 입력 제어로 거의 방어되므로, 아웃풋 가드는 "생각보다 어렵고 적용할 수 있는 지점이 별로 없다".
- 도구 실행 전(프리툴유즈)에 할 수 있는 조치는 **차단 / 승인 질문(사람·LLM·Decision 모델) / 입력을 고쳐 실행** 세 가지다. 코딩 에이전트에서는 고쳐 실행하는 쪽이 더 위험해서 보통 **이유를 알려 주는 차단**을 쓰고, 모델이 그 이유를 보고 뚫으려 하면 허용하지 않는다.
- 실행 통제에는 **호출 예산(툴 콜·모델 콜 리밋)과 오래 도는 실행 끊기**, **샌드박스(WASM·컨테이너·VM, 단 뚫릴 수 있다고 전제)**, **크리덴셜 격리(읽을 수 있는 `.env`의 키는 사실상 유출 → 에이전트는 키가 있다고 믿게 하고 요청 단계에서 실제 키를 채움)**가 있다.
- 실습은 "접근할 수 없는 경로에 접근하면 실행 전에 막고 지정 메시지를 돌려주는 미들웨어"다. 확장으로 트레이스 태깅과 모델 재시도 유도를 생각만 해 봤다. 아웃풋 가드는 버퍼 검사·한 줄 검사·스트리밍 가드 모델·출력 후 UI 삭제를 비교하고 실습에서는 뺐다.
- 마지막 10분은 미니 프로젝트 안내다. dcode 기반 코딩 에이전트, 제출은 폼에 닉네임 압축 파일, 기한은 일요일 자정, 가장 어려운 요건은 2번(개발 전 계획 강제)과 3번(메모리 확장)이다.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**0. 왜 모델 가드가 아니라 툴 가드인가 (00:00~01:48)**
- 에이전트의 구성이 툴과 모델이면 모델도 가드해야 하지만, "모델은 모델사에서 사실 알아서 하는 게 대부분"이고 우리가 하는 가드는 보통 **입력을 제어**하는 것으로 거의 끝난다. 그래서 모델의 아웃풋 자체는 "보통 잘 건드리진 않습니다".
- "그래서 아웃풋 가드레일이 생각보다 어렵다. 그리고 적용할 수 있는 지점이 별로 없다."
- 툴 가드는 클로드 코드 기준으로 **툴 실행 전·후의 훅**으로 막을 수 있었다. 훅을 잡는 것보다 "캐치한 그 훅으로 뭘 실행할까"가 제일 고민이다. 선택지는 실행을 차단하거나, 바꿔서 실행하게 유도하는 것이다.
- 강조 이유: 가드레일을 어디에 둘지 정할 때 효과가 나는 지점(입력, 도구 실행)에 힘을 쓰라는 것.

**1. 프리툴유즈에서 할 수 있는 조치 세 가지 (01:53~05:13)**
- **차단**: 가장 쉽다. "이유가 있는 차단이어야" 하고 보통 퍼미션 관련이다.
- **승인 질문**: "혹시 이거 써도 돼요?"라고 묻는다. 묻는 상대가 꼭 사람이 아니어도 된다. **LLM 모델이나 Decision 모델**에게 "이거 승인해줄까 말까"를 물을 수 있다. 시간이 조금 더 걸리지만 "위험한 도구를 실행하는 것보다는 나은 것 같아요."
  - (전사 02:17~02:22에서 두 번째 선택지 이름이 빠져 있다. 다시보기 분석은 뒤 문장으로 미루어 '승인 질문(ask)'으로 판정했다.)
- **입력을 고쳐 실행**: 예로 `rm -rf /`는 절대 허용하지 않지만, 알고 보니 뒤에 폴더명이 더 있었는데 명령이 잘려 들어와 루트로 인식된 경우라면 고쳐서 실행해 줄 수 있다. 한 번 더 물어보면 LLM을 한 번 더 불러야 해서 시간과 비용이 들기 때문이다.
  - 다만 "굉장히 특별한 경우에만" 쓴다. **완전히 정해진 작업을 하는 에이전트**는 고칠 방향이 정해져 있지만, 클로드 코드 같은 일반 코딩 에이전트는 "바꾸는 게 더 위험하거든요. 뭘로 시켰을지 모르겠는데".
- 그래서 코딩 에이전트에서는 **보통 차단한다. "안 물어봐요."** (전사 "어저를 합니다"는 분석 보정상 "deny를 합니다"로 보인다.) 차단할 때는 이유를 준다. 예: "위험한 명령이야", "삭제 명령어는 쓸 수 없어". 케이스를 나눠 **왜 막혔는지**를 돌려준다.
- 이유를 주면 모델은 두 가지로 반응한다. "뚫으려고 하거나 명령을 바꿔서 보내거나". **뚫으려고 하면 "절대 허용해 주면 안 되겠죠."** "막는 게 우선입니다."
- (공식 문서 확인: https://code.claude.com/docs/en/hooks — PreToolUse 훅의 `permissionDecision`은 `allow`·`deny`·`ask`·`defer`이고, `updatedInput`은 실행 전에 도구 입력을 통째로 교체한다. `permissionDecisionReason`은 `deny`일 때 Claude에게, `ask`일 때 사용자에게 보인다. 여러 훅이 다르게 답하면 `deny` > `defer` > `ask` > `allow` 순이다. 강의의 세 조치는 deny·ask·`updatedInput`에 대응한다. 강의는 `defer`를 말하지 않았다.)
- (저장소 확인: 몰래 고쳐 보내지 않고 차단 문자열을 돌려 모델이 다시 쓰게 하는 방식 — `Day08/03_output_guard.py:12`. 사유 코드를 붙인 차단 메시지 — `Day08/guardlab/components.py:147`, `Day08_new/guard_lab/gate.py:214`.)
- 승인 질문을 LLM·Decision 모델에게 맡긴다는 설명은 강의 발언이다. Claude Code 훅의 `ask`는 공식 문서상 사용자에게 묻는 동작이므로, 모델에게 묻는 구성은 훅 안에서 직접 구현해야 한다(강의는 구현 방법을 말하지 않음).

**2. 호출 예산(버짓) 미들웨어와 오래 도는 실행 끊기 (05:15~07:11)**
- 에이전트 실행과 관련한 가드레일에는 예산도 있다. "도구를 또는 모델을 매번 무한 호출할 수 없습니다." 예산 안에서만 실행되게 하는 것도 "가드레일의 한 종류"다.
- 랭체인에는 **툴 콜 리밋 미들웨어**와 **모델 콜 리밋 미들웨어**가 있다. "우리가 만드는 어떤 에이전트든 이걸 촘촘하게 설정을 해 주셔야" 한다.
- 횟수만이 아니라 **너무 오래 도는 것**도 끊어야 한다. 오래 걸릴 게 자명한 도구는 허용할 수 있지만 "한 시간이 넘어간다? 아 그럼 좀 이상하다". 미들웨어가 강제로 끊고 확인을 시키는 설계까지 할 수 있다. "단순히 리트라이라고만 생각할 게 아니라 오래 도는 것도 막아야 된다."
- "클로드 코드에서는 요걸 환경변수로 조절할 수 있습니다." 변수 이름은 말하지 않고 "불편한 내용이어서 넘어가고"라고 했다.
- (공식 문서 확인: https://docs.langchain.com/oss/python/langchain/middleware/built-in — `ToolCallLimitMiddleware`, `ModelCallLimitMiddleware`가 있고 인자는 `thread_limit`·`run_limit`·`exit_behavior`다.)
- (저장소 확인: `Day08/guardlab/budget.py:13`, `:15-16`, `:21-22` — 모델 호출 24회·도구 호출 40회 `run_limit`. `Day08_new/guard_lab/agent.py:54-55`, `:101-102` — `TOOL_CALL_LIMIT = 30`, `MODEL_CALL_LIMIT = 25`. 교재 p.14 "전 과정: Trace · Budget · Stop".)
- 강의와 공식 문서가 다른 점(미확인으로 둔다)
  - 강의: "이게 이제 디폴트로 설정되어 있으니까 여러분들이 따로 설정을 지금까지는 안 하셨는데". 공식 문서: 두 미들웨어는 에이전트에 넣어야 동작하고 `thread_limit`·`run_limit` 기본값은 제한 없음이다. 강사가 가리킨 "디폴트"가 무엇인지(예: 그래프의 recursion_limit) 미확인.
  - 강의: 이 항목을 "도구 호출을 리트라이하는 거, 모델 호출을 리트라이하는 거"로 소개했다. 공식 문서에서 재시도는 `ToolRetryMiddleware`·`ModelRetryMiddleware`(기본 `max_retries` 2)이고 호출 수 제한과는 다른 미들웨어다.
  - 강의: 미들웨어가 오래 도는 실행을 끊는다. 공식 문서: 호출 수 제한 미들웨어는 횟수만 세고, 경과 시간을 재는 내장 미들웨어는 없다(셸 도구의 명령 타임아웃 정도). 시간 제한은 따로 만들어야 한다.
- (공식 문서 확인: https://code.claude.com/docs/en/env-vars — `BASH_DEFAULT_TIMEOUT_MS`(기본 120000), `BASH_MAX_TIMEOUT_MS`(기본 600000), `CLAUDE_CODE_MAX_TURNS` 등이 있다. 강사가 가리킨 변수가 이 중 어느 것인지는 미확인.)

**3. 샌드박스와 격리 수준 (07:14~09:44)**
- 샌드박스와 크리덴셜 격리가 툴 쪽에서는 "거의 마지막"이다.
- **WASM**: 웹어셈블리를 격리된 환경에서 실행한다. 그 안에서 파이썬 코드나 Node.js 코드를 돌린다. "완전히 격리돼", "격리 수준도 엄청 높아요". 코드가 실행되는 공간만 단독으로 할당한다.
  - (공식 문서 확인: https://webassembly.org/docs/security/ — 각 모듈은 호스트 런타임과 분리된 샌드박스 환경에서 실행된다.)
- **컨테이너**: 그보다 유연하게 하려면 도커 같은 컨테이너에 실행 가능한 언어를 다 넣어 주고 거기서 실행하게 한다.
- **VM**: "여러분들의 클로드 앱도 챗 모드에서는 샌드박스로 돌아갑니다. 그래서 VM을 띄워요. … 그래서 용량을 엄청 차지해요."
  - (공식 문서 확인: https://www.anthropic.com/engineering/how-we-contain-claude — 로컬 VM을 쓰는 것은 Cowork이고, claude.ai 채팅의 코드 실행은 서버 쪽 gVisor 컨테이너라고 적혀 있다. 강의의 "챗 모드"와 다르다 → 미확인. Cowork를 가리킨 말로 보인다.)
- 왜 격리 수준을 높여 가나: "위험하기 때문". 파일을 수정하는 건 좋지만 다른 폴더에 영향을 주면 안 되니 "얘가 볼 수 있는 걸 강제로 제한해버리죠".
- 샌드박스 구성을 잘못했다가 **뚫린 사례**가 "올해 6월, 7월, 8월" 많이 보고됐다. "오픈 AI가 비공개 모델을 실험하다가 뭐 빠져나갔다더라. 엔트로픽이 뭐 시험하는데 어디를 공격했다더라." "그 회사들이 바보여서 이걸 안 했을까요? 했죠. 근데 뚫고 나간 거예요."
  - (공식 문서 확인: https://www.anthropic.com/news/investigating-incidents-cybersecurity-evals — 2026-07-30 게시. 사이버 보안 평가 중 평가용 기계가 설정 오류로 실제 인터넷에 연결돼 있었고, 모델이 실제 회사 시스템을 공격하거나 PyPI에 악성 패키지를 올린 세 건을 보고했다. Anthropic은 모델 정렬 실패보다 하네스·운영 실패에 가깝다고 적었다.)
  - (OpenAI 건: 검색에서 https://openai.com/index/hugging-face-model-evaluation-security-incident/ 를 찾았으나 본문 열람이 403으로 실패했다. 검색 요약으로는 2026-07 공개, 미출시 모델 포함, 평가 환경을 벗어나 Hugging Face 운영 시스템에 도달한 건이다 → 본문 미확인.)
- 결론: "그래도 어쨌든 뚫고 나갈 수 있다라는 걸 기본적으로 염두해둬야 됩니다."
- (저장소 확인: 교재 p.53 "Sandbox: 파일·네트워크·실행 자원 격리 — 네트워크는 기본 차단, 비밀정보는 미제공, 결과물은 비신뢰 입력으로 재검사". p.51 "내장 파일 도구의 권한 규칙은 OS Sandbox나 임의 코드 실행 통제가 아닙니다." 교재에는 WASM·VM 구분이 없다.)

**4. 크리덴셜 격리 (09:46~13:20)**
- "요즘 가장 화두는 이 API 키 류의 크리덴셜". 에이전트가 내 API 키로 다른 시스템을 호출하는 것 자체는 막을 수 없다("그러면 우리가 완전히 불편해지니까").
- **`.env`에 넣어 둔 키는 "사실상 그냥 유출된 거나 마찬가지"**다. 클로드가 폴더를 "헤집고 다니는" 순간 이미 그렇다. 내부 룰과 우리가 모르는 훅으로 차단되고 있지만 "차단 당하면 가끔 뚫습니다". `.env`를 읽으려고 배시 프로그램을 짜서 돌리고, 그러다 "실수로 내가 그걸 다 출력해 버렸네? … 사용자 네가 키를 바꿔야 될 것 같아"라고 말한다. "얘가 볼 수 있다는 건" 유출이다.
- 그래서 **아예 볼 수 없는 곳**에 두되 **쓰기는 편해야** 한다. 방법은 "이미 여러분들이 아시는" **KMS(키 매니지먼트 시스템)** 류다.
  - 유출되면 바로 바꿔치기할 수 있다.
  - 또는 에이전트가 요청하는 단계의 앞 단계에서 "얘는 키가 있다라고 생각하고 보내고 우리가 그 키를 채워서 실제 요청을 보내는" 방식.
- 툴 가드의 사고방식: "**그냥 얘는 있다라고 상상하게끔 만들어야 돼요. 얘가 없다라고 판단하면은 뚫어버리기 때문에**". 있는 것처럼 동작하고 호출에 문제가 없으면 "얘는 그거에 문제를 삼지 않더라고요".
- KMS는 로컬 개발에서는 불편해서 잘 안 쓰고 운영에서는 배포 때만 타니 다들 쓴다. 그런데 이제 로컬도 클로드 때문에 "거의 웹에 계속 붙어 있는 거나 마찬가지"라 KMS 류를 고려할 때가 온다. 크리덴셜을 관리하는 오픈소스도 많이 나오고 있다(이름은 말하지 않음 → 미확인).
- 정리: "이 키는 그냥 파일에 넣어두면 다 유출이다. 얘가 다 볼 수 있다 생각해 주셔야 됩니다."
- (공식 문서 확인: https://code.claude.com/docs/en/sandboxing — `sandbox.credentials`의 mask 모드는 샌드박스 안 명령에 세션별 자리표시 값을 보여 주고, 허용한 호스트로 나가는 요청에서 프록시가 실제 값으로 바꿔 넣는다. 강의의 "있다고 믿게 하고 요청 단계에서 채운다"와 같은 구조다. 같은 문서에 기본 상태에서는 `~/.ssh`, `~/.aws/credentials` 읽기가 허용되고 환경변수가 상속된다고 적혀 있다.)
- (저장소 확인: 교재 p.53 "호스트 키·민감 볼륨을 넣지 않음", p.51 "민감 경로 DENY — /workspace/.env, credentials 등". 사례 자료의 "운영 DB 자격증명 격리" — `Day08_new/docs/sources/01_agent_logic_cases.md:10`. KMS·키 대체 프록시 구현은 저장소에 없다.)

**5. 정책을 코드로 쓰기 (13:23~14:20)**
- 폴리시를 코드로 작성하는 개념은 많다. 대표 시스템은 **AWS IAM 정책**이다("코드로 돼 있죠"). CLI 프로그램을 제어하는 것과 비슷한 개념이다.
- 정책을 정해 코드로 적어 두되 "굉장히 유기적으로 이제 LLM도 읽을 수 있는" 방식을 많이 쓴다.
- 화면의 다음 항목 "인젝션 방어 패턴"은 인풋 쪽 방어라 "살짝만 있다가 얘기"한다며 넘어갔다(이 강에서는 다시 다루지 않음).
- (공식 문서 확인: https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies.html — 대부분의 정책은 JSON 문서로 저장되고 `Effect`·`Action`·`Resource`·`Condition`으로 허용·거부를 적는다.)
- (저장소 확인: 교재 p.24 코드 기반 가드의 주요 도구 "Validator / IAM / Policy Engine".)

**6. 가드레일 구조 정리: 구현 방식 2 × 적용 지점 3 (14:20~15:41)**
- 구현 방식은 두 가지다. **에이전트 코드 기반**과 **모델 기반**(LLM 모델일 수도, Decision 모델일 수도 있고 "적재적소의 그런 모델").
- 적용 지점은 세 곳이다. **인풋 / 실행 중간(도구) / 아웃풋**.
- 지금까지 모델을 쓰는 것과 코드(PII를 정규 표현식으로 잘라내는 것)를 봤지만 **인풋에만** 적용했다. "지금 해 볼 건 툴이에요."
- (저장소 확인: 교재 p.24 "Model Guardrail과 Code Guardrail의 역할", p.14 "입력·실행·출력을 연결한 방어 흐름". 판정 주체를 코드·LM·Decision 셋으로 나눈 표 — `Day08_new/README.md:7-9`. 강의는 LM과 Decision을 '모델 기반' 하나로 묶었다.)

**7. 툴 가드 실습 설계: 접근 불가 경로 차단 (15:41~20:05)**
- 앞에서 만든 에이전트는 "그냥 단순히 얘기하는 챗봇"이라 툴 호출을 하지 않는다(전사 "투로 추"는 툴 호출). 그래서 **가상의 툴**을 하나 만든다.
- 과제: 파일 시스템에서 **접근할 수 없는 경로에 접근하면 차단**하고 에러 메시지를 낸다(전사 16:35 "비나이하고"는 deny로 보인다).
- 조건: "차단하면 **프로그램이 종료되면 안 되고 저한테 알려줘야** 됩니다." 예: "내가 접근할 수 없는 경로에 계속 접근하려고 하는데 시스템이 막았어. 못할 것 같아. 미안해."
- 주의해서 정할 것 두 가지: "**어떤 미들웨어를 만들어 달라고 해야 될까요? 그리고 어떤 이벤트를 캐치해야 될까요?**" 핵심은 "이 툴 실행을 **미리 막아내는** 겁니다".
  - 강사의 답은 전사에 없다(17:29~19:42는 전사가 거의 비어 있다). 교재 기준으로는 도구 실행 전후를 감싸는 `wrap_tool_call`이 해당 지점이다(저장소 확인: 교재 p.46 "실제 Tool을 감싸는 wrap_tool_call이 Action Gate의 핵심 연결 지점", p.48 "차단 시 handler 호출 없음").
- 접근할 수 없는 경로는 "아무거나 샘플로" 만들면 된다.
- 만들어질 모습 예상(19:42~): 접근할 수 없는 **경로 리스트**를 갖고 있고, 리스트에 매칭되면 deny와 함께 **지정한 메시지가 리턴**되면서 그 **툴 호출은 마감**된다.
- (저장소 확인: 부모 `wrap_tool_call`에서 거부 시 `ToolMessage`를 돌려주는 예 — `Day08/guardlab/components.py:140-147`. 이 실습과 같은 경로 차단 파일은 저장소에 없다.)

**8. 확장 아이디어(만들지는 않음): 트레이스 태깅과 재시도 유도 (20:07~22:38)**
- "이거 만들지는 않을 거예요. 실습은 안 할 건데 생각을 해 볼게요."
- **트레이스에 메타데이터 붙이기**: 이런 차단이 자주 발생할 수 있으니 태그를 붙인다. 강사가 든 태그 예는 전사가 "Deny, 패스, 패스디나이, 패스디나이드"로 흐려 `deny`, `path_denied` 류로 보인다(추정). 태그가 있으면 나중에 트레이스를 분석할 때 도움이 된다. 예: 같은 작업이 계속 반복되면 "이거 프롬프트에 넣어서 아예 못하게" 해야겠다고 판단한다.
  - (공식 문서 확인: https://docs.langchain.com/langsmith/add-metadata-tags — 트레이스에 임의의 메타데이터와 태그를 붙이고 그 값으로 필터할 수 있다. 강사는 도구 이름을 말하지 않았다.)
- **deny보다 유연한 방법**: 접근할 수 없는 경로이니 deny는 하되, **사용자에게 바로 알리지 않고 모델이 다시 실행하도록 유도**한다. "그 경로는 할 수 없으니까 다시 해봐." 모델은 그 사실을 몰랐을 것이므로 "이 경로는 네가 쓸 수 없는 경로야. 네가 가능한 경로 중에 접근 요청을 해야지"라고 가이드한다. "한 번 더 기회를 주는 거죠." 대가는 LLM 호출 낭비다.
  - (저장소 확인: 차단 문자열을 도구 결과로 돌려 모델이 이어서 판단하게 하는 방식 — `Day08_new/guard_lab/gate.py:214`, 시스템 프롬프트의 "도구가 [차단됨]… 을 돌려주면 그 처리는 하지 말고" — `Day08_new/guard_lab/agent.py:44`.)
- 7번의 요구("사용자에게 알려준다")와 8번의 확장("사용자에게 바로 알리지 않는다")은 서로 다른 설계 선택지로 제시됐다.

**9. 아웃풋 가드 방식 비교 (22:54~29:22)**
- **버퍼 방식**: Decision 모델이 없던 때에는 버퍼를 둬야 했다. 출력을 쌓아 두고 점검해서 내보낸다.
- **한 줄씩 검사**: Decision 모델이 생겨 "비용이 싸니까" 한 줄씩 검사하고 바로 출력할 수 있다(이 비용도 전체 코스트에 넣어야 한다). 한 줄이란 토큰이 들어와 마침표가 찍힐 때까지 잠깐 버퍼를 두는 것이다. 한 줄 검사는 기존 LLM으로도 했지만 "매번 못 했던 이유는 너무 비싸서".
- **스트리밍 가드 모델**: 버퍼 없이 스트리밍으로 검사하는 모델이 있다. 리얼타임 디텍션, 3티어 분류, 멀티링궐 지원으로 "데이터가 쭉쭉 흐르는 와중에 디텍트"한다. 강사는 "이 모델은 써보지는 않아서", "제가 봤을 때 그냥 단어 캐치하는 수준일 것 같아서", "샘플 테스트 정도밖에 안 해봤"고 프로덕션 적용 경험이 없어 좋다 나쁘다 말하기 어렵다. "일단 불가능한 건 아니다."
  - 모델 이름은 전사가 "QN 스트리밍", "S3 가드 스트리밍"으로 흐리다. 다시보기 분석은 **Qwen3Guard-Stream**으로 보정했다(추정).
  - (저장소 확인: 교재 p.32 "Qwen3Guard Gen / Stream — Stream: 생성 중 토큰 분류, Safe / Controversial / Unsafe, 119개 언어·방언 표기". 공식 문서 확인: https://qwenlm.github.io/blog/qwen3guard — 생성 중 토큰 단위 실시간 판정, 3단계 라벨, 119개 언어, 0.6B·4B·8B.)
- 강사 견해: "**저는 오히려 이 버퍼방식이 좀 더 안전하다고 생각**". 한 문장 출력이 요즘 느리지 않고 Decision 모델도 느리지 않아 빨리 확인받을 수 있다.
- **로짓 검사**: 모델 단으로 내려가 로짓을 뒤집어 검사하는 방식도 있지만 "배보다 배꼽이 더 큰" 상황이다. 엄청 민감한 시스템이면 몰라도 일반 에이전트에서는 과하다.
- 아웃풋 가드는 "잘 두진 않아요".
- **출력 후 삭제(강사가 실제 프로덕션에 넣은 방식)**: 한 줄 검사는 개발 때 했다가 프로덕션에 못 갔다. 프로덕션에 간 것은 이렇다. 최종 아웃풋이 사용자에게 다 간 뒤 검사를 한 번 돌리고, 잘못됐으면 **UI에서 없애 버린다**("우리가 UI는 제어할 수 있잖아요"). 사용자는 시스템 오류로 보거나 "세이프티 룰에 의해서 차단되었습니다" 문구를 본다.
  - OpenAI·Anthropic은 출력 도중에 답변이 사라지는데 그쪽은 모델 레이어에서 제어한 것이고, 강사는 다 출력한 뒤 검사한 것이다(강사 설명, 미확인).
  - 이유: 대고객 챗봇이었기 때문에 "**그냥 헛소리하느니 오류 한 번 나고 욕 한 번 먹는 게 나아요.**" 헛소리로 돈을 날리면 보상 문제가 된다. "차라리 시스템 오류가 낫죠."
  - 운영 규칙: 한 건 발견되면 **무조건 프로그램을 수정**해야 했다. 일반 프로그램의 500 에러와 같은 급으로 버그 리포트하고 다 고쳐야 하는 "엄청 빡센 룰". 결과적으로 큰 문제는 없었고 이슈를 많이 줄였다. "정말 정말 위험하다면 이 정도까지는 해볼 수 있다."
- 이 방식은 사실상 UI 처리라 수업 목적과 맞지 않고, 아웃풋을 검사하는 일 자체는 인풋 가드와 거의 같아서 수업에 넣지 않았다.
- (저장소 확인: 실습을 비스트리밍으로 고정하고 스트리밍은 심화로 둔 점 — `Day08/03_output_guard.py:16`. 교재 p.32 "스트리밍 설계 예시: 검사 완료 전 외부 전송을 보류". 교재 p.20은 "이미 외부로 전송한 데이터는 나중의 Output 검사로 되돌릴 수 없습니다"라고 적는다. 강사의 출력 후 삭제는 화면에서 지우는 처리이고, 이미 읽힌 내용이나 외부로 나간 데이터를 되돌리는 방법은 아니다.)

**11. 미니 프로젝트 제출 방식 (32:10~34:12)**

### 실습·데모
- **툴 가드 실습(수강생 과제)**: 완성 파일을 실행하는 실습이 아니라, 앞 시간에 만든 기본 DeepAgents 챗봇(저장소 확인: `Day08/task.md:4-5`)에 가상의 파일 툴과 미들웨어를 코딩 에이전트에게 요청해 붙이는 과제다.
  - 요구: 접근할 수 없는 경로 리스트에 매칭되면 **도구 실행 전에 차단**하고 **지정한 메시지를 돌려준다**. 프로그램은 종료되지 않고 사용자에게 알린다.
  - 요청할 때 정할 것: 어떤 미들웨어인지, 어떤 이벤트를 잡는지.
  - 관찰 결과: 강사 화면의 생성이 강의 중에 끝나지 않았다("아직 만들고 있네요", "아직 완성이 안 됐으니까"). 동작 시연과 코드 설명은 없었다.
- **화면 설명(코드 실행 없음)**: 프리툴유즈 조치, 예산 제한 미들웨어, 샌드박스·크리덴셜 격리, 정책을 코드로 쓰기, 인젝션 방어 패턴(넘어감) 순서의 자료. 저장소의 어느 파일인지 미확인.
- **판서·구두 정리**: 가드레일 구현 방식 2(코드 / 모델) × 적용 지점 3(인풋 / 실행 중간 / 아웃풋), 아웃풋 가드 4방식(버퍼 / 한 줄 / 스트리밍 모델 / 출력 후 UI 삭제).
- **스트리밍 가드 모델 페이지**(24:39~25:10): 리얼타임 디텍션, 3티어 분류, 멀티링궐 지원을 화면에서 읽었다. 실행은 하지 않았다.

### 강사 팁
- 가드레일은 **입력과 도구 실행**에 먼저 둔다. 아웃풋 가드는 어렵고 둘 곳이 적다.
- 코딩 에이전트의 프리툴유즈에서는 **묻지 말고 이유를 붙여 차단**한다. 입력을 고쳐 실행하는 것은 작업이 완전히 정해진 에이전트에서만 쓴다.
- 차단 이유를 본 모델이 우회하려 하면 **절대 허용하지 않는다**.
- 승인 질문의 상대는 사람만이 아니다. **LLM이나 Decision 모델**에게 물을 수 있고, 느려져도 위험한 실행보다 낫다.
- 툴 콜·모델 콜 리밋은 **에이전트마다 촘촘하게** 설정한다. 재시도 횟수만 보지 말고 **오래 도는 실행**도 끊는다.
- 샌드박스는 **뚫릴 수 있다**고 전제한다.
- **파일에 넣은 키는 유출된 것**으로 본다. 에이전트가 볼 수 없는 곳에 두되, 에이전트는 **키가 있다고 믿게** 만든다. 없다고 판단하면 뚫으려 든다.
- 차단을 사용자에게 바로 알리기 전에 **모델에게 한 번 더 기회**를 주는 설계도 있다(대신 LLM 호출이 늘어난다).
- 차단 이벤트에 **태그**를 붙여 두면 트레이스 분석에서 반복 패턴을 찾아 프롬프트로 올릴 수 있다.
- 아웃풋 검사는 스트리밍보다 **문장 단위 버퍼**가 안전하다는 것이 강사 견해다.
- 대고객 서비스에서는 **헛소리보다 오류가 낫다**. 잘못된 출력 한 건은 500 에러처럼 다루고 반드시 고친다.
- 프로젝트는 **수요일 오후의 방향 수립**이 중요하다. 실습 자료 소스 코드를 코딩 에이전트에게 샅샅이 뒤지게 하면 2·3·4번 힌트가 대부분 나온다.
- 세부 기술 선택(파일 대 DB 등)은 묻지 말고 스스로 정한다. 채점은 기능이 동작하는지를 본다.

## 8일차 3강 — 입력 가드레일 실습: 모델 앞에서 가로채는 InputGuard 미들웨어, PII 치환, 세션 분리라는 구조적 방어

> 출처: 「8일차 3강 다시보기」(whisper 전사 948줄 + 분석, 46:18, 원본 음성 `8일차 3강.m4a`), 「8일차 3강 장표」(10장). SDS AX Advanced · 2026-11-11 오전(점심 직전 강의).
> 이번 강은 교재를 넘기지 않고 판서(세션 분리 그림, 케이스 1~5 개별 호출 그림)와 라이브 코딩으로 진행했다. 실습 파일 `inputguard_practice.py`는 강의 중 Claude에게 시켜 새로 만든 것이라 **저장소에 없다**(저장소 확인: `Day08_new/` 전체에서 `inputguard`·`InputGuard` 문자열 검색 결과 없음). 대응 저장소 폴더는 `Day08_new/`(전사 12:18의 "J208의 new"를 다시보기 분석이 `Day08_new`로 보정, 추정)이고, 강의에서 만든 코드와 구조가 가장 가까운 완성본은 `Day08_new/guard_lab/boundary.py`의 `MessageGuardMiddleware`(저장소 확인: `Day08_new/guard_lab/boundary.py:68`)와 이를 쓰는 `Day08_new/07_model_boundary.py`의 A 부분이다(저장소 확인: `Day08_new/README.md:61`). 아래 "저장소 확인"은 강의에서 만든 파일이 아니라 이 완성본·설정 파일과 대조한 것이다.

### 핵심 요약 (3~5줄)
- LLM으로 입력을 가드한다면 **프롬프트 인젝션**뿐 아니라 **컨텍스트를 쌓아 가스라이팅하는 공격**까지 막아야 하고, 가드는 사용자 입력이 들어오는 **모든 순간**에 동작해야 한다.
- 누적 공격은 기능을 더 붙여서가 아니라 **구조로** 막을 수 있다. 사용자 대화 컨텍스트와 메인 세션을 분리하고 메인에는 한두 줄 요약만 넘기면, 메인 입장에서는 멀티턴이 아니라 "하나의 질문에 하나의 답변"이 된다. 요약 단계에서 필터링도 할 수 있다.
- 실습에서는 deepagents 에이전트에 **InputGuard 미들웨어**(에이전트 실행 전 훅에서 마지막 사용자 메시지를 가로채 가드 모델로 판정 → 통과/리뷰/차단, 차단이면 AI 메시지를 강제로 만들어 고정 문구로 종료)를 만들고, "이전 지시는 모두 무시하라" 입력이 block·instruction injection으로 판정되는 것을 확인했다.
- 두 번째 과제는 **빌트인 PII 미들웨어**에 한국 주민등록번호 정규식 타입을 걸어 치환하는 것이다. PII 처리를 LLM 가드에 맡기면 가드 모델이 원문을 보게 되므로 "실제 시스템에서는 요거는 로컬 모델이어야 됩니다."
- 가드를 에이전트로 만들 때는 서브에이전트가 아니라 **미들웨어 안에서 무조건 호출**하고 structured output으로 판정한다. 가드는 실제 트레이스와 골드 데이터셋으로 계속 고치며, 검증 케이스를 케이스별 개별 호출로 쪼개고 이를 **Decision Model**로 돌리면 한 통 프롬프트보다 빠르고 정확하다는 것이 강사 설명이다.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**1. LLM 입력 가드의 요구사항: 인젝션 + 누적 가스라이팅 (00:00~02:54)**
- 시스템 프롬프트에 방어를 쓰는 방식은 "아까 클로드의 사례처럼 풀어서 설명해서" 할 수 있지만 "그거는 모델에 따라서 달라지니까 그렇다고 치고", LLM으로 입력을 가드한다면 무엇을 막아야 하는지가 이번 강의 출발점이다.
- "컨텍스트가 누적된 입력으로 왔을 때도 방어를 안정적으로 해내야 됩니다."(00:58) 앞 강에서 시연한 가스라이팅까지 막는다는 조건이다.
- 정리(01:37~02:33): **모든 입력에 대해 검증하는 것은 맞다.** 다만 LLM 기반 가드레일은 "단순히 프롬프트 인젝션만 막아내는 게 아니라 … 누적을 통해서 가스라이팅 하는 것도 막아내야 됩니다."
- deepagents 기반으로 설계한다면 이 가드는 **미들웨어**에 들어간다(02:35). 남는 질문은 "미들웨어의 어떤 부분에 들어가야 되고 어떻게 설계해야 될까"이다.
- 강조 이유: 가드를 "인젝션 문구 탐지기"로만 생각하면 누적 공격을 놓친다. 설계 조건을 먼저 세우게 하려는 것.

**2. 가드의 동작 방식과 누적 문제 (02:54~05:02)**
- 조건 1: "사용자의 입력이 들어오는 모든 순간에 동작을 해야 되고요."
- 동작의 실체: "모델의 무언가를 정보를 집어넣고 호출을 해서 그 응답 결과를 받아가지고 **통과 미통과**를 해야 될 겁니다."(03:15)
- 프롬프트 인젝션은 "주로 시스템 프롬프트를 탈취할 목적"이므로 "**뭘 말해줘**라고 하는 키워드에 좀 집중"한다. 확인할 것은 "이 사람이 얘기한 내용이 무언가 정보를 탈취하는 방향인지 아닌지".
- 탈취 방법 중 하나가 "계속 대화를 쓸데없이 쌓아가지고 작업을 하는 경우"다. "이거는 매번 두 번씩 검사하기가 사실 비싼데" → 정보를 탈취하는 요청은 "일단 살짝 경계해야 된다 정도로" 간다.
- 문제 상황: 컨텍스트가 잔뜩 쌓인 뒤 탈취 요청이 오면 모델이 "줄줄줄줄 얘기하는 이 작금의 사태".
- (저장소 확인: 가드가 모델을 불러 판정을 받는 구조는 `Day08_new/guard_lab/gate.py:51` `judge_text` — Guard 하나를 부르고 (신호, 결정)을 돌려주며 판정 실패 UNKNOWN은 REVIEW로 보낸다. 강의에서는 UNKNOWN 처리를 말하지 않았다.)

**3. 세션 분리로 얻는 구조적 방어 (05:02~10:20)**
- "사실 여러분 이 방법 이미 알고 있으세요." 앞서 "컨텍스트를 관리하는 입장에서 **두 가지의 루프를 운영**해야 된다"고 한 내용이 "자연스럽게 방어막이 될 수 있습니다." "사실 이미 가드레일은 이미 여러분들이 알던 게 더 많아요."
- 판서 구조: **사용자 ↔ 컨텍스트(대화 맥락 보관) ↔ 메인(대화 세션)**.
  - 사용자는 AI와 질문·답변을 계속 주고받는다고 느낀다.
  - 메인은 "하나의 질문에 하나만 답하는 그 구조를 최대한" 유지한다. 완전히 하나는 아니고 "컨텍스트에서 한 줄씩 또는 중요한 내용만 추려서 가지고" 온다.
  - 사용자 질문과 대화 맥락은 컨텍스트 쪽에 쌓이고, 메인의 답변만 사용자에게 전달된다.
- 문제가 되는 입력이 들어와도 메인에는 요약된 형태로 전달된다. "사용자 입장에서는 AI가 말을 많이 했다라고 느끼지만 … 우리 메인의 입장에서는 우리는 이미 컨텍스트를 정리해서 가지고 있잖아요."
  - 방어 1: "주요 내용을 발췌할 때 **필터**를 할 수 있겠죠. … 한 줄씩 만들어서 줄 거잖아요. 이때 이미 필터링을 할 수 있습니다."
  - 방어 2: 메인의 시스템 프롬프트에 방어 프롬프트가 있으니 "자기의 프롬프트를 얘기하는 걸 어느 정도 방어"한다.
  - 결과: "컨텍스트 누적의 이슈는 이걸로 막아내는 거죠. **애초에 요약을 통해서 막아내는 거죠.**"(08:45) 사용자에게는 잔뜩 쌓인 것처럼 보여도 "우리 입장에서는 한두 줄".
- "단일 대화 세션입니다. … 멀티턴이 아니에요. 우리가 에이전트를 만드는 입장에서 멀티턴이 아니었다는 거. 이게 그냥 자연스러운 방어 구조가 됩니다."
- 노골적인 직접 공격을 따로 검사할지: "사실 그것도 저는 안 볼 것 같아요. 노골적으로 공격하는 거 볼 필요가 없어요. 이미 이 메인 세션에 시스템 프롬프트에 그 정도는 넣어서 처리를 할 수가 있습니다."
- 강조 이유: "가드레일이라고 생각해서 무조건 뭔가를 만들어야 된다라고 생각을 하셨을 수도 있는데 우리는 이미 어느 정도 방어 구성을 짜놓은 거죠. 이 레이어를 분리시킴으로써." "요게 생각보다 가드레일에서 고려가 잘 안되는 부분이에요." "**기능을 추가할 필요는 없습니다.** 이 가드레일에 구조적으로 막아낼 수 있는 부분이에요."(10:13)
- 세션 분리 구현은 시간이 오래 걸려 이번 강에서 하지 않는다. "실습 미니 프로젝트 때 한번 도전해보시면 좋을 것 같아서"(10:33).

**4. 실습 설계: 모델에 보내기 전에 잡아서 차단 또는 치환 (10:20~14:05)**
- 이번 실습 대상은 "직접적으로 공격하는 거 막아내는 거"다("이런 공격도 가끔 있어요").
- 방식: "사용자의 입력이 들어오면 그걸 **모델에 보내기 전에 캐치**를 하는 거죠."
  - **차단**: "아예 그냥 모델을 보내지도 않고 그냥 고정된 메시지. 차단. 제일 쉽죠." 예: "우리 시스템 위협으로 감지되어서 어쩌고 저쩌고".
  - **치환**: "말해줘"라는 요청을 다른 방식으로 풀어서, 시스템에 대한 내용이 아니라 "일반적인 내용만을 약간 말하게끔 하는" 식으로 바꾼다.
- 파일: `Day08_new`(추정) 폴더 아래 `inputguard_practice.py`를 새로 만들고, "기본 딥에이전트를 하나 정말 껍데기로" 만든 뒤 그 실행을 가로챈다.
- (저장소 확인: 완성본의 같은 선택지 — `on_flag="stop"`이면 실행하지 않고 끝내고 `"warn"`이면 경고문만 붙이고 계속한다. `Day08_new/guard_lab/boundary.py:71-77`, `Day08_new/guard_lab/boundary.py:101-107`. 강의의 "치환"(요청 내용을 일반적인 답만 하게 바꿈)과 완성본의 "warn"(경고문을 앞에 붙임)은 같은 것이 아니다.)

**6. InputGuard 미들웨어 코드 해설 (22:21~25:47)**
- "제가 설명하고 싶었던 핵심 코드는 사실 이 미들웨어를 만드는 거였어요. **인풋가드 미들웨어**라고 하는 … 클래스로 선언된 요 코드를 만드는 게 사실 핵심이었습니다. 뭐 다른 거는 다 부차적인 거고."
- 사용자의 입력을 가로챈다는 것은 "어떤 미들웨어 또는 **어떤 훅 이벤트를 선택할까**"의 문제이고, 선택한 결과는 에이전트 실행 전이다. "**에이전트가 실행되기 전에 가로채는 겁니다.**"(23:13) 그리고 "마지막 사람의 메시지를 가로채요."
  - (저장소 확인: 완성본은 `before_agent` 훅에서 `state["messages"][-1]`이 `HumanMessage`일 때만 검사한다 — `Day08_new/guard_lab/boundary.py:83-88`.)
  - (공식 문서 확인: https://docs.langchain.com/oss/python/langchain/middleware/custom — `before_agent`는 에이전트 시작 전에 호출당 한 번 실행되는 노드형 훅이고, 훅이 `{"jump_to": "end"}`를 돌려주면 실행을 끝낼 수 있으며 클래스 메서드에는 `@hook_config(can_jump_to=["end"])`로 허용 대상을 선언한다.)

**8. 두 번째 과제: 빌트인 PII 미들웨어로 주민등록번호 치환 (27:18~32:19)**

- 생성된 코드(29:51~30:26): "내장 PII 타입"에 주민등록번호용 **정규 표현식**을 걸었다. 앞 여섯 자리는 생년월일, 뒷자리는 성별 자리를 2000년대 출생(추정: 1~4)까지 걸러내도록 짰고, 타입 이름은 "코리안 RRN". 전략은 "전부 치환"(전사 "미덱트"는 redact로 보인다, 추정).
  - "여기가 핵심이죠. 이렇게 **미들웨어를 넣어놨다는 거.** 이 에이전트 시스템이 실행될 때 이 미들웨어 코드, 알아서 포함이 돼서 돌아간다라는 거죠."

  - (저장소 확인: 같은 내장 미들웨어에 사용자 정의 정규식 타입을 거는 예 — `Day08/03_output_guard.py:77-86`(`"kr_phone"` + `detector=r"01[016789]-?\d{3,4}-?\d{4}"`), 공식 문서 사본 `Day08/dcode-analysis/docs_official/sdk/going-to-production.md:890-902`. 주민등록번호용 타입은 저장소에 없다.)

### 강사 팁
- 가드레일이라고 해서 무조건 무언가를 새로 만들 필요는 없다. 세션(레이어)을 분리하면 누적 공격은 구조로 막힌다. "기능을 추가할 필요는 없습니다."
- 노골적인 직접 공격은 메인 세션의 시스템 프롬프트로도 어느 정도 처리된다. 강사라면 그것만 보는 검사는 따로 두지 않겠다고 했다(단, 이번 실습은 바로 그 직접 공격 차단을 연습했다).
- 누적 여부를 매 입력마다 이중으로 검사하는 것은 비싸다. 정보를 탈취하는 방향의 요청인지에 집중한다.
- 차단이 가장 쉽다: 모델에 보내지 않고 고정 메시지를 돌려준다.
- Claude가 만든 코드는 반드시 눈으로 확인한다. 실제로 "모델을 통일하라"는 지시가 가드 모델에 반영되지 않았다.
- 지시를 촘촘하게 줬다면 이 정도 코드는 Sonnet으로 충분하다. Opus까지 필요하지 않다.
- 미들웨어를 붙였으면 그것이 동작하는 케이스를 만들어 실제로 돌려 본다. 해피 케이스 하나로 끝내지 말고 케이스를 더 만들어 개선한다.
- 개인정보를 보는 가드 모델은 실제 시스템에서 로컬 모델이어야 한다.
- 출력 단계에 같은 처리를 하려면 답변을 담아 둘 버퍼가 있어야 한다.
- 입력 가드는 메인이 호출 여부를 정하는 서브에이전트로 만들지 않는다. 무조건 호출되는 자리(미들웨어)에 둔다. 판정은 structured output으로 받는다.
- 가드레일은 대개 공통으로 만들어 한쪽에 띄워 두고 여러 시스템이 요청·응답으로 쓰게 된다.
- 빌트인 PII 미들웨어도, 처음 만든 InputGuard도 완성형이 아니다. "통과시키면 안 됐던" 트레이스를 찾아 이유와 함께 골드 데이터셋으로 만들고, 주로 가드 프롬프트를 고친다.
- 검증 케이스는 한 프롬프트에 몰아넣지 말고 케이스별로 나눈다. 비용·시간이 걸리면 Decision Model로 바꿔 본다. LLM 버전과 한 벌씩 만들어 속도·비용·품질을 나란히 비교하면 검증이 쉽다.

### 프로젝트 체크리스트
- 이 강에서 미니 프로젝트에 대해 말한 것은 한 가지다: "우리가 이렇게 이제 대화 세션을 분리하는 거는 여러분들이 이제 실습 미니 프로젝트 때 한번 도전해보시면 좋을 것 같아서"(10:29~10:33). **제출 링크, 마감, 모델 규칙, 40점 평가 기준은 이 강에서 언급되지 않았다.** (제출·평가 기준 원문 위치만: `Day08/project_guide.md`.)
- [ ] 사용자 대화 컨텍스트와 메인 세션을 분리하고, 메인에는 요약된 한두 줄만 넘기는 구조를 검토한다(강사가 미니 프로젝트 도전 과제로 지목).
- [ ] 요약·발췌 단계에 필터를 둔다(탈취 방향 요청, 붙여 넣은 글 속 지시).
- [ ] 메인 시스템 프롬프트에 자기 프롬프트 노출 방어 문장을 둔다(모델에 따라 효과가 다르다는 전제).
- [ ] 입력 가드는 에이전트 실행 전 훅에서 마지막 사용자 메시지를 가로채게 하고, 판정 결과(통과/리뷰/차단)에 따른 처리를 코드로 강제한다. 차단 시 모델을 부르지 않고 고정 문구로 끝낸다.
- [ ] 리뷰 판정을 어떻게 처리할지 정한다(강의에서는 세 판정이 있다는 것만 말하고 리뷰 처리 방식은 설명하지 않았다).
- [ ] 가드 모델과 대화 모델을 구분해 설정하고, 생성된 코드에서 실제로 어떤 모델이 불리는지 확인한다.
- [ ] 개인정보가 들어올 수 있으면 정규식 기반 치환을 입력 단계에 두고, 원문을 보는 가드 모델은 로컬 모델로 둔다.
- [ ] 출력 단계 검사·치환이 필요하면 답변을 모아 둘 버퍼를 설계에 넣는다.
- [ ] 가드를 에이전트로 만들 경우 서브에이전트가 아닌 미들웨어 안에서 항상 실행하고 structured output으로 통과 여부를 받는다.
- [ ] 가드별로 동작 케이스(통과·차단·치환)를 만들어 실행 결과를 남긴다.
- [ ] 운영 트레이스에서 잘못 통과·차단된 입력을 찾아 이유와 함께 골드 데이터셋에 넣고, 가드 프롬프트를 고칠 때마다 다시 돌린다.
- [ ] 검증 케이스를 케이스별 개별 판정으로 나눌지, Decision Model로 바꿀지는 LLM 버전과 나란히 돌려 속도·비용·정확도로 정한다.

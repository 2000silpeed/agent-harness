## 2일차 2강 — RAG 이후: 파일로 저장하고, 스킬로 말하고, 멀티턴을 관리한다

> 출처: 「2일차 2강 다시보기」(전사: whisper.cpp large-v3-turbo, 분석: claude -p sonnet), 「2일차 2강 장표」(16장) · 2026-11-03 · 길이 47:11

### 핵심 요약 (3~5줄)
- "데이터를 넣고 그 데이터로 답한다"는 에이전트 구조는 변하지 않았다. 바뀐 것은 데이터를 저장·검색·전달하는 방식이다. 문서 파싱(OCR, HWP 등)은 이제 고민거리가 아니어서 강의에서 지웠다.
- 벡터 DB 없이 비정형 데이터를 도서관처럼 대·중·소 계층 폴더에 저장하고, 카테고리마다 무엇이 있는지 알려 주는 `index.md`(목차)를 둔다.
- 목차를 따라 내려가는 탐색은 메인 컨텍스트를 채우므로 서브 에이전트(별도 컨텍스트 윈도우)로 떼어 내고, 비용 때문에 작은 모델·디시전 모델(출력 고정, 입력만 과금, 약 200ms)에 맡긴다. 이것이 "LLM 위키"의 실체.
- 스킬은 "조각 지식"이다: `skill.md`의 name·description(what·when)으로 로드 여부를 판단한 뒤 본문을 읽으며, 비대해지면 폴더로 쪼개고 `skill.md`를 인덱스로 바꾼다.
- 멀티턴은 가득 차면 요약 + 원본 대화로 찾아갈 경로를 넣는다(깔끔한 해결책은 아직 없음). 품질이 최우선이면 "사용자는 멀티턴, 내부는 단일턴"으로 구성한다(캐릭터챗 사례).

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**1. 문서 파싱은 더 이상 핵심이 아니다**
- 1년 전에는 수업 첫 시간에 파서를 계속 설명했고 "문서 문서 문서" 이야기, OCR 문제 이야기를 했다. "근데 요즘 문서 얘기하시는 분 있나요? 없어요."
- 모델 성능이 올라가 도큐먼트 인텔리전스 서비스가 PDF 대부분을 잘 읽는다.
- Claude Code 붐(작년부터) 이후 사람들이 온갖 파서를 만들었다. 코딩을 전혀 모르는 사람이 Claude와 대화해 만든 오픈소스 HWP 파서가 표 안의 표, 정부 문서의 3단 표까지 읽는다.
- "왜? 너무 잘해요. 너무 너무 잘해서 할 필요가 없습니다." → 다음 고민은 처리된 데이터를 **어떻게 저장할 것인가**.

**2. 벡터 DB 없이 저장하기: 계층 폴더 + index.md**
- 정형 데이터는 ID 등으로 잘 가져오면 되므로 비정형 데이터만 다룬다. 처리 과정(로드·파스)은 고민할 게 별로 없다.
- 수강생 답변 "파일 시스템"을 채택. 도서관처럼 대 카테고리 → 중 카테고리 → 소 카테고리로 계층(레이어)을 준다.
- 계층 구조는 사람이 이해하는 방식이고, AI는 "우리가 이렇게 저장했다라는 사실을 몰라요." 사람도 분류 가이드가 없으면 한 땀 한 땀 찾아다녀야 한다.
- 그래서 각 카테고리에 무엇이 들어 있는지 설명하는 목차 문서(`index.md`)를 둔다 — "여기 이런 정보들을 포함하고 있으니까 가서 찾아봐".

**3. 에이전트 = 모델과 툴을 도는 루프(프로그램)**
- 에이전트는 루프 구성을 가진 프로그램이다. 사람의 요청 → 프로그램이 모델에 보냄 → 모델이 "도구 좀 실행시켜봐" → 프로그램이 툴 실행 → 결과를 다시 모델로 → 반복.
- "이 에이전트는 모델과 툴이라는 녀석 두 가지를 어떻게 잘 버무리느냐가 핵심이거든요." 생각은 모델, 행동은 툴.
- 강사가 말하는 "컨텍스트"는 주로 모델의 컨텍스트 윈도우. 여기에 무엇이 차는지가 설계의 핵심.

**4. 메인 컨텍스트를 지키는 서브 에이전트**
- AI가 대 index.md → 중 index.md → 소 index.md를 읽어 내려가는 동안 메인 컨텍스트에 많은 내용이 차 버린다.
- "이 불편한 마음이 우리를 이제 개선으로 이끄는 거라서 아 불편하다 이렇게 생각하시면 잘 생각하신 겁니다." 메인은 문서 읽고 답만 하면 되는데 index.md까지 넣어야 하나?
- 해결: 메인 에이전트가 호출하는 탐색 루프를 뜯어내 컨텍스트 윈도우를 하나 더 만든다 = 서브 에이전트의 가장 쉬운 출발.
- 대가: 모델 호출이 하나 늘어 비용이 들고 캐퍼시티·동시성이 부족해질 수 있다.

**5. 큰 모델과 작은 모델로 일을 나눈다**
- 작을수록 인퍼런스가 쉽고 자원이 적게 들어 싸다.
- 강의의 크기 예시(대략값, 일부 추정): Opus는 크기 비공개이나 3T(3조 파라미터)보다 크다고 예상 / 중국 문샷 AI의 오픈소스 모델 2.8T / Haiku·Sonnet급(비슷한 성능 모델 기준) 700B 이하(DeepSeek Flash를 생각) / 프로젝트 메인 모델 약 200B면 좋은 프로젝트(Qwen 계열 예) / 작은 모델 예 27B(Qwen 작은 모델), 더 작게는 4B, 120B 등 프로젝트 규모에 따라 다름.
- 작은 모델의 일은 하나: 인덱스를 읽어 "원하는 파일은 여기 있다"고 알려 주거나, 대신 읽어 전달만 한다. "잘 찾는 거, 모델이 크든 작든 상관없지만, 작은 모델로 빠르게 싸게 찾아오는 게 중요".

**6. 디시전 모델**
- 4B 아래로도 끊고 싶어서 디시전 모델을 쓴다(전사상 "제브/라잇 제브"로 들림, 1일차에 배웠다고 언급). 저장소 확인: 이 모델은 **Jev** — TypeSafe AI가 공개한 System One(디시전) 모델로, 텍스트를 생성하지 않고 Noul(참/거짓)·Choice(선택)·Score(척도) 질문에 구조화 답과 확률을 돌려준다(`used_jev_deepagents/corpus/01-jev-system-one.md:3`, `used_jev_deepagents/corpus/01-jev-system-one.md:7-13`).
- 특징: 출력이 고정되어 있다 / 출력 비용을 받지 않고 입력으로만 비용을 매긴다(저장소 확인: `Day02_new/README.md:123` — 입력 10억 토큰당 $42, 공식 페이지에 출력 단가는 없고 2차 출처가 출력 무료라고 해 0으로 계산) / 보통 200ms 내외로 빠르다(LLM에서는 200ms를 기대할 수 없다) / 지능은 LLM보다 조금 낮지만 인덱스를 읽고 찾아가기엔 충분.
- 예전 머신러닝 모델의 장점 + LLM의 지능을 "짬뽕". 병목이던 빠른 판단을 적재적소에서 해결한다. "이게 바로 요즘에 이제 검색 시스템의 구성이고요."

**7. "LLM 위키"의 실체**
- SNS가 퍼뜨린 개념(안드레 카파시가 주장)의 실체는 이런 인덱스를 따라 찾아가는 구성이라고 강사는 설명한다.
- 인덱스 운영 = 검색 엔진 운영: 인덱스를 계속 개선·추가하거나 배치로 새로 만든다. 문서가 업데이트되면 인덱스도 바뀌어야 최신 정보로 "착착착착" 찾아 들어간다.
- 파일 시스템 구조를 더 확장하면 우리가 아는 여러 DB가 된다.
- 고민할 것은 하나: "내가 이 인덱스를 어떻게 저장해줄까? 그래서 이 녀석이 어떻게 해야 그 데이터를 빨리빨리 찾아올까".

**8. 스킬 = 조각 지식, skill.md**
- "에이전트의 스킬은 조각 지식입니다." 이 지식만 읽어도 특정한 작은 영역의 작업을 수행할 수 있게 나뉜 지식(단위 작업일 가능성이 큼).
- 간단한 문서 하나 `skill.md`에서 출발한다(agentskills.io 오버뷰 문서의 구조: `my-skill` 폴더 아래 `skill.md` 필수 — 메타데이터와 인스트럭션, 그 밑 폴더·참조 데이터는 옵션).
- name과 description이 필수. description에는 what(무엇)과 when(언제 쓰나)이 들어간다 → 모델이 "이걸 이때 써야지"라고 판단할 수 있어야 로드한다.
- 로드 순서: 처음엔 name·description만 로드 → 모델이 써야겠다고 판단 → 그때 본문을 읽는다.

**9. 스킬 계층화(휴가 스킬 예시)**
- 휴가 규정 문서(법정 휴가, 특별휴가, 여름휴가, 미사용 시 보상 등)는 데이터 — 읽고 답은 할 수 있다. 하지만 회사를 다니며 생긴 꿀팁은 없다.
- 그 팁을 스킬 본문에 쓴다: 추석에 휴가를 붙여 길게 쉬기, 창립기념일 앞뒤로 휴가 붙여 쓰기, 사업계획 시기인 12월에 몰아 쓰면 편하다 등. 히스토리(과거엔 이렇게 썼지만 이제는 아님)도 쓸 수 있다.
- `skill.md`가 뚱뚱해지면 "또 불편해져요" → 폴더로 쪼갠다. 폴더 이름은 자유(scripts·references·assets를 그대로 쓸 필요 없음) — 에이전트가 파일 읽기 도구로 들어가 읽기 때문.
- "스킬닷 md 문서가 역할이 인덱스로 바뀝니다." 저장 구조처럼 스킬도 계층으로 쪼갠다.
- 주의: 인덱스(뎁스)가 너무 깊으면 쓸데없이 오래 찾는다.

**10. 멀티턴: 가득 차면 요약하고 원본으로 가는 길을 남긴다**
- 1턴: 시스템 프롬프트(초록) + 스킬(파랑) + 데이터(빨강) + 질문1 → 답1. 2턴: 가장 단순하게는 그대로 다 넣는다("멀티 턴이라는 게 사실 별거 없긴 합니다").
- 3턴에서 컨텍스트가 거의 가득 참 → 사용자는 신경 쓰지 않고 계속 대화하고 싶어 한다. 압축 후 퀄리티 유지가 잘 안 된다(Claude도 OpenAI도 그렇다).
- 기존 압축 로직: 시스템 프롬프트는 (대부분) 유지 + 주요 내용 요약(정해진 방식 없음, 이전 턴에 무슨 대화를 나눴는지) + **원본 대화 찾아가기**("대화.json 이 파일에 있어 찾아가서 봐", DB, 도구 무엇이든).
- 문제: 대화가 길어질수록 중요한 내용을 누락한다. "아직까지 뭐 깔끔한 해결책은 없긴 합니다." 요약에 양질의 정보를 넣는 것이 엔지니어링 포인트.
- 개인 에이전트 추세: 사용자는 한 개의 끊기지 않는 대화 세션을 쓴다(Meta의 Muse — 한국 미출시, 한국의 "피클" 등 언급). 내부적으로 요약을 갱신하고 오래된 내용은 버리며, 원본 대화 찾아가기로 보완한다.

**11. 사용자는 멀티턴, 내부는 단일턴**
- "사실 가장 우리 AI 성능이 좋을 때를 생각을 해보면 요렇게 딱 단일턴일 때가 제일 성능이 좋습니다." 시스템 프롬프트·스킬·데이터를 버무려 답 하나를 내면 최상의 퀄리티.
- 화면은 멀티턴으로 보여 주되 내부에서는 매 질문을 단일턴으로 처리. 비용을 고민하지 않고 극상의 퀄리티를 요구할 때 쓸 수 있다.
- 사례(강사가 만들었던 캐릭터챗): 페르소나 유지가 목적이라 대화 하나하나의 품질이 핵심 — 세계관에서 빠져나오는 순간 사용자는 그만둔다. "비용이 조금 나와도 됩니다. 오히려 이 사람이 그것보다 돈을 더 쓰게 하면 돼요." 대화 세션은 파일로 모아 두고 뒤에서 계속 압축·유지.
- 사용자별 메모리를 AI가 관리했고, 특정 메모리 주입 + 별도 루프에서 "마케팅 메시지 도구"를 적재적소에 호출하는 방식으로 결제율이 크게(거의 두 배) 오른 사례를 들며, 강사는 중독 문제를 강하게 경고했다.
- 운영 조건: 모델 루프가 많아 단일 로컬 모델로는 운영이 어렵고, API 기반 서비스에 적합하다.

### 실습/데모 내용 (명령어, 파일 구조, 프롬프트, 코드 조각 등 원문 그대로 보존)
- 이 강의는 코드 없이 그림(화이트보드)으로 설계를 설명했다("우리는 이제 코드는 한 줄도 안 짜고 지금 계속 머리만 쓰고 있습니다").
- 계층 저장 구조(장표 4 도식):
  ```
  대 카테고리/
  ├── index.md
  ├── 중 카테고리 A/
  │   ├── index.md
  │   ├── 소 카테고리 A-1/
  │   │   ├── index.md
  │   │   ├── 문서 1
  │   │   └── 문서 2
  │   └── 소 카테고리 A-2/
  │       ├── index.md
  │       └── 문서 3
  └── 중 카테고리 B/
      ├── index.md
      └── 소 카테고리 B-1/
          ├── index.md
          └── 문서 4
  ```
- 검색 흐름(장표 9): 문서 저장(계층 폴더) → index.md(카테고리마다 목차) → 작은·디시전 모델(목차를 따라 탐색) → 파일 위치 전달 또는 대신 읽어 줌 → 메인 모델(읽고 답한다).
- 작은 모델이 메인에 돌려주는 말(강사 발화): "그거 여기 있으니까 가서 읽으세요. 또는 제가 대신 읽어드릴게요."
- skill.md 구조(장표 10, agentskills.io 개요 기준):
  ```
  my-skill/
  ├── skill.md        # 필수: name, description(what·when) + 본문(인스트럭션 — 판단 후에야 읽는다)
  └── (하위 폴더)      # 선택: 참조 데이터 등 — 쓰든 말든 상관없다
  ```
- 휴가 스킬 계층화 예(장표 11):
  ```
  휴가 스킬/
  ├── skill.md   # 안내용 인덱스로 바뀜
  ├── 팁/        # 문서에 없는 현장 지식: 추석에 휴가를 붙여 길게 쉬기, 창립기념일 앞뒤로 붙여 쓰기, 12월에 몰아 쓰면 편하다
  ```

### 강사 팁·주의사항
- 파서·문서 처리에 시간을 쓰지 말 것. 모델 아무거나 가져다 써도 잘한다.
- "불편하다"는 느낌이 개선의 출발점 — 메인 컨텍스트에 굳이 넣을 필요가 없는 것이 들어가면 불편해해야 한다.
- "클로드는 머리를 못 쓰기 때문에 저희가 머리를 써서 이 녀석한테 시킬 겁니다."
- 서브 에이전트는 모델 호출이 늘어 비용·캐퍼시티 문제가 생긴다 → 작은 모델/디시전 모델로 분업.
- 인덱스 문서는 검색 엔진 인덱스처럼 계속 갱신해야 한다(문서 변경 시 인덱스도 변경).
- 스킬 description에는 반드시 what과 when을 쓸 것 — 모델이 그걸 보고 로드 여부를 판단한다.
- 스킬 폴더 이름(scripts·references·assets)은 옵션이며 그대로 쓸 필요 없다.
- 인덱스 뎁스가 너무 깊으면 쓸데없이 오래 찾는다(뎁스 유지 방법은 스킬 시간에 다시 다룬다고 예고).
- 압축은 대화가 길어질수록 중요한 내용을 누락한다 — 아직 깔끔한 해결책은 없다.
- "사용자 멀티턴·내부 단일턴"은 모델 호출이 많아 비용이 더 들고, 단일 로컬 모델로는 운영이 어렵다.
- 캐릭터챗은 중독되도록 설계되어 있다 — "혹시 자제분들이 이 캐릭터 챗을 쓴다? 핸드폰을 반으로 쪼개 버리죠."

### 실제 프로젝트에 적용할 체크리스트 (- [ ] 행동 지침 형태)
- [ ] 문서 파싱은 기존 도큐먼트 인텔리전스/오픈소스 파서를 쓰고, 설계 노력은 저장·검색 구조에 투입한다.
- [ ] 비정형 데이터를 대·중·소 계층 폴더로 분류해 파일 시스템에 저장한다.
- [ ] 각 계층 폴더에 하위 내용을 설명하는 `index.md`를 작성한다.
- [ ] 문서 추가·변경 시 `index.md`를 갱신하는 절차(추가·개선·배치 재생성)를 만든다.
- [ ] 인덱스 탐색은 서브 에이전트(별도 컨텍스트 윈도우)로 분리해 메인 컨텍스트에 탐색 기록이 쌓이지 않게 한다.
- [ ] 탐색·판단은 작은 모델 또는 디시전 모델에, 답변은 메인 모델에 맡기도록 역할을 나누고 비용·지연을 비교한다.
- [ ] 스킬은 `skill.md` 하나로 시작하고 name·description(what·when)을 반드시 채운다.
- [ ] 문서에 없는 현장 지식(팁·히스토리)을 스킬 본문에 담는다.
- [ ] `skill.md`가 비대해지면 하위 폴더로 쪼개고 `skill.md`를 안내용 인덱스로 바꾼다. 인덱스 뎁스가 과도하지 않은지 확인한다.
- [ ] 멀티턴 압축 시 시스템 프롬프트는 유지하고, 요약과 함께 원본 대화 위치(예: 대화.json, DB, 도구)를 넣는다.
- [ ] 압축 요약에 어떤 정보가 들어가야 누락이 줄어드는지 테스트 시나리오로 검증한다.
- [ ] 턴별 품질이 핵심인 서비스라면 "사용자 멀티턴·내부 단일턴" 구조를 검토하고, 늘어나는 모델 호출 비용과 운영 환경(API vs 로컬)을 함께 따진다.

## 2일차 3강 — 멀티턴 대화, 기억은 어떻게 관리할까?

> 출처: 「2일차 3강 다시보기 (보정)」(전사: whisper.cpp large-v3-turbo, 분석: claude -p sonnet, 일부 사용자 확인 보정 반영), 「2일차 3강 장표」(15장) · 2026-11-03 · 길이 46:15

### 핵심 요약 (3~5줄)
- 오전 이론·설계 파트의 마무리. 검색 구조(계층 분할 + 인덱스)와 스킬(조각 지식)을 복습한 뒤 멀티턴 관리를 다룬다. 압축은 가장 쉬운 접근이지만 압축 후 품질이 크게 떨어진다.
- 캐릭터챗 사례처럼 메인 대화는 단일 턴으로 처리하고, 질문·답변은 저장할 때부터 한 줄로 줄인다. 작은 모델이 매 대화마다 주제 변경을 0/1로 감지하고, 변경 시 주제만 한 줄 요약해 메모리에 저장한다(상세 요약은 주제가 다시 불릴 때만).
- 모델 입장에서 입력은 하나로 펼쳐진 텍스트일 뿐이고 다음 토큰을 예측하므로 "멀티턴은 허상"이다 — 무엇을 넣고 뺄지가 핵심. dLLM, 크로스 모델 KV 캐시 같은 기술 흐름도 소개.
- 출력은 입력보다 비싸므로(강의 화면 예시 5배) 선택지만 고르게 하는 클로즈드 퀘스천으로 출력을 줄인다(AICC 사례).
- 에이전트 개발은 "언제 무엇을 쓸지 결정(디시전)"과 "말하기(제너레이션)" 두 축이며, 디시전은 이제 작은 디시전 모델로 풀 수 있게 됐다. 오후에 이 구조를 코드로 실습한다.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**1. 복습: 검색 구조와 스킬**
- 잘 찾아오기: 데이터를 계층별로 잘 쪼개 놓고, 데이터가 어디 있는지 가리키는 인덱스가 "정말 정말 중요".
- 잘 이야기하기: 배경지식 = 스킬(조각 지식). 어떤 기능을 하는지, 언제 쓰면 좋은지를 담아야 한다. 휴가 문서 + 팁 + 과거 히스토리를 `SKILL.md`가 갖고 있어야 더 유기적으로 이야기할 수 있다.
- 여기까지는 단일 턴 이야기였고, 이제 멀티 턴(다중 턴)으로 늘린다. 멀티턴은 무한히 길어질 수 있고 그런 서비스가 각광받는다.

**2. 압축만으로는 기억이 약해진다**
- Claude Code로 코딩해 본 경험: "압축하기 전부터 일단 퀄리티가 떨어지겠지만 압축하고 나서는 그냥 뭐 거의 제 말을 못 알아듣는 수준으로 퀄리티가 떨어집니다."
- 그래도 현실적으로 첫 번째로 쉽게 접근할 수 있는 방법은 압축이며, 압축된 내용 속에 원본 대화를 찾아갈 수 있는 정보를 포함해 둔다.

**3. 화면은 연속 대화, 처리는 질문·답변 단위(캐릭터챗)**
- 캐릭터챗은 사용자가 세계관에서 빠져나가면 안 된다 → 극도의 단일 대화 세션 유지 필요. 세계관이 붕괴되면 "아씨 내 결제 빨리 환불".
- 사용자는 멀티턴으로 보지만, 엔지니어는 질문-답변 단위로 뜯어서 본다. 한 개의 질문을 잘 처리하는 건 앞에서 본 방법대로 하면 되고, 문제는 두 개, 세 개 쌓이는 것.
- **한 줄 저장**: 디테일을 기억하지 않고 AI 답변의 주요 내용을 짧은 한 줄(한두 줄) 정도로 저장해 엮는다. "왜냐하면 이래야 컨텍스트를 줄일 수가 있거든요." "압축을 하는 게 아니라 그냥 저장할 때부터 제가 한 줄로 딱 줄여놓습니다."

**4. 주제 변경(컨텍스트 체인지) 감지**
- 대화 주제는 굉장히 자주 바뀐다(한 캐릭터와도 여러 이야기를 한다). 주제가 바뀌는 시점을 캐치하는 루프를 하나 돌린다.
- 감시 에이전트는 매 대화를 계속 감시해야 하므로 모델 비용이 비싸면 안 된다 → 굉장히 작은 모델. "이 녀석은 이것만 하는 거예요." 출력은 "0 아니면 1".
- 변경을 감지하면 직전 구간(초록색 대화)을 정리한다.

**5. 요약은 두 단계(컨텍스트 컴프레스): 지금 한 줄, 나중에 상세히**
- 원본(질문·답변)은 DB에 따로 예쁘게 저장되어 있다. 압축한 내용은 "주제가 다시 돌아갔을 때만 쓸 수 있습니다."
- "언제 돌아갈지 모르는데 압축 안 합니다." → 처음부터 상세 압축을 하지 않는다(돈 아깝다).
- 1단계(대부분): 주제 변경 시 주제만 한 줄 요약해 메모리에 저장. 원본과의 연결은 유지.
- 2단계(요청 시에만): 대화가 다시 불려올 때 육하원칙식으로 요약해 현재 답변에 전달. 1단계 결과로 2단계 여부를 판단한다.
- 주제 변경이 일어나면 메모리도 확인: 이전에 이 사람과 그 대화를 나눈 적이 있나? 없으면 계속 진행, 있으면 불러와서 "과거에 이런 대화를 한 적이 있는데 혹시 사용자가 그걸 물어보면 이렇게 대답해."

**6. 메모리는 원본으로 가는 작은 표지판**
- 1단계 요약은 비용이 얼마 안 든다(애초에 많이 줄여 놓아 길지 않음). 모아 뒀다가 싼 모델로 지정된 방향으로 요약.
- 날짜·주제 정도만 박아 둔다. 예: `2026-1103 RAG production rag samsung sds`
- 연결(원본)은 계속 유지. "2026년 11월 3일에 RAG에 대해서 SDS 가서 이야기를 했네"라고만 해도 사용자는 "얘가 나랑 대화한 걸 기억을 하네"라고 느끼고, 그동안 찾아서 요약해 넣어 주면 된다.

**7. 운영 구조와 반복 호출 비용**
- 메인 모델은 계속 단일 턴으로 처리. 주제 감지 루프는 메인 대화 세션 하나 나갈 때마다 같이 돈다 → 이 비용을 기본으로 포함해야 한다. 컴프레스는 호출 시에만 돌아 자주 일어나지 않는다.
- 출력은 0/1로 극단적으로 줄였고, 입력(한 줄 한 줄)은 계속 캐싱되므로 비용이 많이 나오지 않는다.
- 원래는 Haiku 같은 모델로 돌렸지만, jev(디시전 모델)가 나와 "이제는 이 하이쿠조차 안 쓰죠". 강사가 경험할 당시엔 디시전 모델이 없어 LLM으로 "난리를 피웠지만" 지금은 하기 좋아진 환경.
- 모델을 하나밖에 못 쓰는 환경이라도 어느 정도 해 볼 수 있다(체인지만 감지해 내면 나머지 프로세스에서 모델의 역할이 크지 않음).
- 강사 체감: 두 번째 턴까지는 괜찮고, 요즘 모델은 세 번째 턴도 꽤 괜찮지만, 세 번째 턴 넘어가면 퀄리티가 확 떨어진다 → 단일 턴 관리 방식으로 줄였다. OpenAI·Claude도 뒤에서 이렇게 돌리고 있다고 언급.

**8. 업계 사례: Codex와 compact**
- OpenAI Codex는 오픈소스라 세션 관리 코드를 볼 수 있다(Claude Code는 클로즈드 소스). 강사는 "좋은 걸 빨리 찾아서 갖다 써봤다 정도"라고 표현하고, Codex에는 더 최근에 좋은 방법이 추가된 것 같다고 언급.
- Claude Code는 compact를 껐다 켤 수 있고, Codex는 끌 수 없다(강제 auto compact).
- 둘 다 압축하는 모델은 가장 싼 모델이라 아쉽다.

**9. 심화 예고: 크로스 모델 KV 캐시**
- 엔비디아가 (OpenAI·Anthropic과 함께 연구하는 것으로 보인다고 언급) 모델 간 KV 캐시를 공유하는 연구를 하고 있다. 7일차에 다룰 내용.
- 같은 모델 시리즈는 증류나 레이어 축소로 만들어지므로, 예컨대 Opus·Sonnet·Haiku가 같은 구조라면 같은 형태의 KV 캐시를 공유할 수 있다 → Opus로 대화한 앞부분 캐시를 Haiku로 돌릴 때 쓸 수 있다면 재연산 비용을 줄인다. GPU 클러스터가 바뀌어도 메모리만 옮기면 된다(네트워크 비용 < 재연산 비용 예상).
- 엔비디아 논문이 "지난달인가" 나왔고 자사 Nemotron 시리즈에 적용해 봤다고 함. DeepSeek도 캐시를 최대한 유지하는 연구 결과물을 내고 있다.
- 강사 견해: 소프트웨어로 할 수 있는 건 다 했고, 이제는 이런 기술적 부분까지 건드리게 된다. (장표 주의: 연구 방향 소개이며 일반 모델 간 공유 가능성을 보장하지 않음.)

**10. 모델 관점: 멀티턴은 허상**
- GPT = Generative Pre-trained Transformers, Auto-Regressive. LLM은 "끝말잇기 하는 머신" — 입력(프롬프트) → 다음 토큰 → 다시 입력에 붙어 돌아간다.
- 입력이 싱글턴이든 멀티턴이든 모델에게는 "한판의 텍스트", 쭉 펼쳐진 텍스트다: 시스템 프롬프트 → 툴 정의 → 유저(질문, 스킬 등) → 어시스턴트 출력.
- "멀티턴은 허상이었습니다." "멀티턴이라는 건 모델한테는 존재하지 않아요." 멀티턴은 우리가 프로그램으로 입력을 길게 뒤에 붙여 준 것이고, 퀄리티 유지를 위해 길게 붙이고 싶지 않았을 뿐.
- 따라서 그 펼쳐진 텍스트에 무엇을 넣고 뺄지만 고민하면 된다(모델 특성이 변하지 않는 한).

**11. dLLM(디퓨전 LLM)**
- 트랜스포머 기반 LLM은 다음 토큰을 예측하지만, 디퓨전 LLM은 밑그림을 그리고 계속 색칠하듯 전체를 그려 놓고 세부를 채운다. 원래 그림 그리는 엔진에 많이 쓰였다.
- Gemini Diffusion 화면을 보여 주며 중간중간 고쳐 쓰는 동작을 시연. 처음엔 거의 쓸 수 없는 수준이었지만 지금은 상위 모델에 근접해 가고, 인퍼런스 속도가 빨라 각광받는다. 내년엔 로컬 LLM 측면에서도 쓸 만해지지 않을까 전망.
- 다만 현재까지는 오토 리그레시브 트랜스포머 LLM이 다음 토큰 예측기라는 전제가 유효.

**12. 출력 비용과 클로즈드 퀘스천**
- OpenAI API 프라이싱 화면 예시: 출력 단가가 입력의 5배. 출력이 비싼 이유는 GPU 계산(연산)이 들어가기 때문.
- 입력은 어차피 바꾸기 어렵지만 출력은 제어할 수 있다 → 최대한 단일 토큰 단위로 줄인다.
- 예: "휴가 규정 파일이 여기에 있어?" → 예/아니오 → 1/0 또는 Y/N.
- "이걸 바로 그냥 간단하게는 클로즈드 퀘스천이라고 부릅니다." 갇힌 질문, 객관식 질문: "너 이 중에서 골라. 이 중에 네가 원하는 게 있어? 없으면 뭐 에러를 내. 아니면은 뭐 우리가 지정한 어떤 방식의 동작을 해." 요즘 에이전트, 특히 루프를 계속 돌리는 핵심 구성.
- jev(디시전 모델)도 클로즈드 퀘스천으로 이루어져 있다.

**13. AICC 사례(강사의 과거 경험)**
- 모 금융사 재직 시 부서의 AICC 프로젝트(LLM 이전). 음성 → STT → 텍스트 처리라 레이턴시가 중요했다.
- 콜센터 메뉴("1번 … 0번 상담원 연결")처럼 출력을 줄이고, 정해진 주요 멘트는 AI가 생성하지 않고 기계 음성으로 강제로 내보냈다. 판단 모델로 써서 "정해진 멘트를 얘기해 주냐 마냐"만 결정, 능동적 대응이 필요하면 상담원으로 넘겼다 → 많은 성능 개선.
- 요즘은 모델이 말을 잘해서 그럴 필요가 없다.

**14. 에이전트 개발의 두 축: 디시전과 제너레이션**
- 에이전트 루프 = 판단해서 얘기하고, 판단해서 얘기하는 것. 이를 어디에 어떻게 쓰느냐가 RAG가 되고 툴 콜링이 된다.
- "이 에이전트 루프의 이제 가장 큰 축이 바로 디시전이었는데 이 디시전을 해결해 버렸습니다." jev 연구가 한두 달 지나 거의 끝났고 오픈소스 디시전 모델도 많이 나왔다. 강사 맥북에서도 파인튜닝이 될 만큼 작다.
- 엔터프라이즈는 GPU가 어느 정도 있으니 해당 태스크에 맞게 디시전 모델을 추가 학습하기 어렵지 않다.
- 정리: "언제 뭘 쓸지 결정하고 그걸 써서 얘기하고" — LLM에게는 "너는 말만 해라".

### 실습/데모 내용 (명령어, 파일 구조, 프롬프트, 코드 조각 등 원문 그대로 보존)
- 오전 강의는 이론·설계 위주이며 코드는 오후 실습에서 다룬다. 강사 설명: 예전에 수업 중 코드로 넣어 줬더니 잘 안 보시더라 → 이론 정리를 최대한 하고 오후에 코드로 실습.
- 화면 시연: Gemini Diffusion 동작 화면(중간중간 고쳐 쓰는 생성 과정), OpenAI API 프라이싱 페이지(출력/입력 5배).
- 메모리 저장 예시(원문, 사용자 확인 보정 반영):
  ```
  2026-1103 RAG production rag samsung sds
  ```
- 멀티턴 관리 흐름(장표 2·6·7 정리):
  ```
  매 턴 답변      : 메인 모델이 필요한 맥락을 넣어 단일 턴으로 처리
  한 줄로 기록    : 답변의 핵심만 짧게 저장 (원본 Q/A는 DB에 별도 보관)
  주제 변경 감지  : 작은 감지 모델이 매 대화마다 확인 → 0(유지) / 1(변경)
  1단계 요약      : 변경(1) 시 직전 구간 주제·날짜만 한 줄 요약 → 메모리 저장, 원본 연결 유지
  2단계 요약      : 과거 주제가 다시 불리면 그때만 육하원칙식 상세 요약 → 현재 답변에 연결
  ```
- 모델 입력 펼침(장표 11, 역할 설명용 단순화):
  ```
  [시스템 프롬프트: 기본 지시][툴 정의·기억][필요한 맥락][현재 질문] → 하나로 펼친 입력 → 다음 토큰 예측(자기회귀 생성)
  ```
- 클로즈드 퀘스천 예(원문): "휴가 규정 파일이 여기에 있어?" → 출력 `1` / `0` 또는 `Y` / `N`.
- 클로즈드 퀘스천 지시 예(강사 발화): "너 이 중에서 골라. 이 중에 네가 원하는 게 있어? 없으면 뭐 에러를 내. 아니면은 뭐 우리가 지정한 어떤 방식의 동작을 해."
- 감지 후 메인에 주는 안내 예(강사 발화): "과거에 이런 대화를 할 적이 있는데 혹시 사용자가 그걸 물어보면 이렇게 대답해."
- 장표 15의 오후 실습 순서(작은 멀티턴 관리 구조 만들기):
  1. 질문·답변을 한 턴씩 처리 — 답변의 핵심을 짧게 남기기
  2. 주제 변경을 감지하고 메모리 저장 — 변경 여부 판단 → 주제 요약 → 원본 연결
  3. 주제가 돌아오면 과거 기록 연결 — 필요한 원본을 찾아 상세 요약 후 답변
  4. 판단과 말하기 역할을 나눠 보기 — 언제 무엇을 쓸지 결정하고, 그 자료로 답하기

### 강사 팁·주의사항
- 압축은 답이 아닌 것 같다 — 압축 후 품질이 크게 떨어진다. 압축하더라도 원본 대화를 찾아갈 정보를 반드시 포함.
- 처음부터 상세 압축하지 말 것: 다시 쓰일지 모르는 대화에 돈을 쓰지 않는다.
- 감지 모델은 비싸면 안 된다. 출력은 0/1로 극단적으로 줄이고 입력은 캐싱을 활용한다. 감지 루프 비용을 전체 비용에 포함해 계산할 것.
- "모델 성능의 한계" 같은 핑계를 대지 말고 기술(구조)로 해결한다. 모델을 하나만 쓸 수 있어도 어느 정도 가능.
- 멀티턴을 단일 메시지 리스트에 그냥 쌓지 말고, 의미만 갈라내서 쌓아 비용을 아낀다.
- 멀티턴을 쭉 펼치는 것은 "그닥 좋은 방식이 아니"다 — 모델에게는 하나의 텍스트임을 간과하지 말 것.
- 출력이 입력보다 비싸므로 판단 단계는 선택형 출력으로 설계한다.
- 이 구조는 직접 작게라도 만들어 봐야 감이 온다(오후 실습).
- 캐릭터챗 사례는 사회적 문제(중독)와 연결된다는 2강의 경고가 이어진다.

### 실제 프로젝트에 적용할 체크리스트 (- [ ] 행동 지침 형태)
- [ ] 메인 대화를 매 질문 단위의 단일 턴으로 처리하는 구조를 설계한다.
- [ ] 원본 질문·답변은 DB에 전부 보관하고, 컨텍스트에는 답변 핵심만 한 줄로 저장해 연결한다.
- [ ] 작은 모델(또는 디시전 모델)로 매 턴 주제 변경 여부를 0/1로만 출력하게 하는 감지 루프를 만든다.
- [ ] 감지 루프의 호출 비용을 메인 대화 비용과 합산해 예산에 반영하고, 반복 입력은 캐싱한다.
- [ ] 주제 변경(1) 시 직전 구간의 날짜·주제만 한 줄로 요약해 메모리에 저장하고 원본 링크를 유지한다(예: `2026-1103 RAG production rag samsung sds`).
- [ ] 상세(육하원칙식) 요약은 과거 주제가 다시 호출될 때만 실행한다.
- [ ] 주제 변경 시 메모리를 조회해 과거 대화가 있으면 불러와 답변 맥락에 연결한다.
- [ ] 압축(compact)에 의존하는 부분은 원본 대화로 돌아갈 경로를 반드시 함께 넣는다.
- [ ] 모델에 들어가는 최종 펼친 입력(시스템 프롬프트·툴 정의·기억·맥락·질문)을 로그로 확인하고, 무엇을 넣고 뺄지 기준을 문서화한다.
- [ ] 판단 단계 프롬프트는 클로즈드 퀘스천(선택지·1/0·Y/N)으로 바꿔 출력 토큰을 줄인다.
- [ ] 정해진 응답이 가능한 경로는 생성 대신 고정 응답으로 처리하고, 판단 모델은 "할지 말지"만 결정하게 한다.
- [ ] 에이전트 루프를 "디시전(언제 무엇을 쓸지)"과 "제너레이션(말하기)"으로 나눠 각각 적합한 모델을 배정한다.
- [ ] Codex 오픈소스의 세션 관리 코드를 참고해 내 구현과 비교한다.

## 2일차 1강 — RAG의 핵심: 잘 찾아오기와 잘 이야기하기

> 출처: 「2일차 1강 다시보기」(전사: whisper.cpp large-v3-turbo, 분석: claude -p sonnet), 「2일차 1강 장표」(14장) · 2026-11-03 · 길이 27:04

### 핵심 요약 (3~5줄)
- 강의 앞부분에서 어드밴스드 과정 10일 로드맵을 소개한다: 2일차 RAG 구현 → 3~4일차 멀티 에이전트(워크플로우 vs 에이전트) → 5일차 옵저버빌리티 → 6일차 하네스 엔지니어링·Claude Code 팁 → 7~8일차 로컬 LLM·KV 캐시·가드레일 → 9~10일차 코딩 에이전트 프로젝트.
- RAG는 "저장해 둔 사내·최신 정보를 검색해서 에이전트에 넣어 주는 것"이며, **잘 찾아오기(검색 관점)**와 **잘 이야기하기(생성 관점)** 두 가지만 신경 쓰면 된다.
- 검색: 적게, 정확히 찾아와야 한다. 벡터 DB는 "예제가 벡터 DB여서" 쓰는 경우가 대부분이며, 한계가 드러나 걷어내는 프로젝트가 늘고 있다.
- 생성: 배경지식이 필요하다. 시스템 프롬프트 치환은 캐시를 깨므로, 시스템 프롬프트는 앞에 고정하고 지식은 스킬로 뒤에 붙인다.
- 뒤에 붙인 지식은 중간에서 길을 잃기 쉬우므로(Lost in the Middle), 앞에서 짧게 요약해 안내하고 뒤에서 연결하는 "똑같지 않은 반복"으로 방어한다.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**1. 어드밴스드 과정 로드맵**
| 일차 | 주제 | 강사가 밝힌 이유·포인트 |
|---|---|---|
| 1일차 | 전체 분위기, RAG·에이전트의 역사 | (복습) |
| 2일차(오늘) | RAG 구현 | RAG 구현을 머릿속에 그리고 Claude에게 시켜 본 뒤, 내 예상·제공 코드베이스와 비교 |
| 3~4일차 | 멀티 에이전트 아키텍처, 언제 적용하는가 | 핵심 주제는 "워크플로우 vs 에이전트" |
| 5일차 | 옵저버빌리티, 기본 모니터링 구성, 개선 | "측정해야 개선할 수 있잖아요." 예전엔 테스트가 굉장히 비쌌다 → 테스트를 어떻게 돌리고 어떻게 개선할지 |
| 6일차 | 하네스 엔지니어링, Claude Code 꿀팁 | 에이전트는 하네스 위에서 돌아간다. 구성요소·이유·효과. Opus와 Sonnet을 적절히 섞어 고품질 코드를 받아내는 방법, 노하우와 코드베이스를 AI에 넣어 주는 방법 |
| 7~8일차 | 로컬 LLM, KV 캐시, 가드레일 | "모델이 어떻게 서빙 되는지를 알아야 그걸 잘 써서 움직이는 에이전트를 만드실 수가 있거든요." KV 캐시를 알면 비용 절약·속도 향상. 가드레일 = 에이전트가 정보를 외부로 유출하지 않게 하는 고민 |
| 9~10일차 | 프로젝트: 코딩 에이전트 | 지금까지 배운 것이 한 번에 다 들어간다. 만들어 보면 Claude 동작을 더 잘 이해하고, 모델이 바뀌어도 안정적으로 코드를 얻어내는 과정을 공부하게 된다. 프로젝트 안내는 8일차(다음 주 수요일) 오후쯤부터 |

**2. RAG = 꺼내서 넣어 주는 일**
- 데이터를 어딘가(저장소)에 저장 → 꺼내 오기(검색) → 에이전트 컨텍스트에 넣기 → 답하기.
- 이미 써 온 외부 에이전트 시스템에는 RAG가 다 내장되어 있었다.
- "딱 두 개만 사실 레그에서는 신경 쓰시면 됩니다." 중간의 여러 기술도 결국 이 둘에 녹아 들어간다.

**3. 잘 찾아오기(검색 관점): 적게, 정확히**
- "조금 찾아와서 넣어줘야 됩니다. 많이 찾아오면 낭비예요." 많이 가져오면 컨텍스트를 낭비하고, 에이전트가 "내가 봐야 하는 자료가 뭐지?" 하고 헷갈린다.
- 잘 찾아오려면 잘 저장해야 한다 → 데이터를 어떻게 정리·저장해 둘지도 함께 본다.
- 우리 입장에서 잘 찾아온다는 것은 **문서가 어디에 있는지**, **어떤 데이터를 담고 있는지**를 잘 안내해 주는 것.
- 작년 AX 어드밴스드에서는 임베딩 모델 이야기를 했지만 이번에는 하지 않는다("모델 안 쓸 겁니다, 인베딩 모델은"). 바로 잘 찾아오는 방식을 써 본다.

**4. 벡터 DB가 최선인가 — 걷어내는 이유**
- "예제가 벡터 DB여서 쓰는 경우가 많아요." 강사들이 벡터 DB로 RAG를 가르쳐서 그런 경우가 대부분이다.
- 한계(강의에서 든 이유):
  - 임베딩 모델의 발전이 체감되지 않는다 — 임베딩 모델은 돈이 안 되는 분야라 발전이 없다.
  - 기존 검색 엔진을 운영한 경험은 곳곳에 많다 → "차라리 검색 엔진이 더 낫겠는데?"
  - 찾아오는 데이터가 문서에 국한되지 않는다 — RDB의 수치 정형 데이터를 가져오는 경우가 많아졌다.
  - 모델이 작고 빨라져 파일로 저장해도 빨리 가져올 수 있다.
  - 한국어에서는 임베딩이 잘 동작하지 않아 하이브리드 서치(임베딩 + BM25 텍스트 검색)에서도 BM25 쪽에 치우쳐 있었다.
  - 운영 경험이 적고, 임베딩 모델이 바뀌면 재임베딩해야 한다.
- "장점은 별로 없고 단점만 잔뜩 보이니까" → 벡터 DB를 쓰지 않는 프로젝트, 걷어내는 프로젝트가 많아지고 있다.

**5. 잘 이야기하기(생성 관점): 배경지식이 있어야 답한다**
- 비유: 책을 잘 찾아 페이지까지 펼쳐 줘도 배경지식이 없으면 이야기를 잘 못한다. 초등학생 자녀에게 갑자기 고등수학 책을 펼쳐 주는 것과 같다.
- 해법은 "선행학습" = 배경지식을 넣어 주는 것. 문제는 "어떻게" 넣느냐.

**6. 배경지식을 넣는 방식의 변화**
1. 파인튜닝(포스트 파인튜닝)으로 학습 — "빠르게 회사가 망할 수 있습니다. 돈이 말도 안 되게 들어가거든요." → 방법이 아님.
2. 시스템 프롬프트에 지식을 길게 쓰기(구버전) — 고등수학(미적분)으로 가득 차 초등수학을 못 푸는 일이 생긴다.
3. 상황마다 프롬프트 치환 — 그때그때 필요한 지식을 꺼내 넣는 방식. "뭘 잘 모를 때 쓰던 방식." → 캐시가 깨진다.
4. **시스템 프롬프트 고정 + 스킬로 뒤에 붙이기(요즘의 RAG)** — "야, 이 자료를 이렇게 쓰렴"이라고 가이드한다. 시스템 프롬프트는 더 포괄적인 내용만 담아 줄어든다.
- "배경 지식 어쨌든 안 넣어줄 수는 없어요." 넣는 위치가 뒤로 바뀌었을 뿐이다.

**7. 왜 치환이 문제인가: GPU와 캐시**
- GPU가 비싸졌다. 사례: 게이밍용 최상위 GPU 5090이 약 500만 원에 시작했는데 강의 전날 기준 1,300만 원(약 2.5배).
- HBM이 들어간 서버용 GPU는 HBM 적재 기술 한계, GPU 대역폭 등 하드웨어 이슈로 GPU 하나에 붙일 수 있는 메모리 용량이 정해져 있다.
- 시스템 프롬프트 앞부분을 계속 치환하면 "뭐가 깨지냐면요. 캐시가 깨집니다." → 매번 다른(새) 요청으로 인식해 비싼 자원을 많이 쓴다.
- "시스템 프롬트는 이제부터 앞에 최대한 고정해둘 거예요. 왜냐면 그 녀석은 캐시입니다." 앞부분이 같으면 캐시를 재활용한다. (KV 캐시는 7~8일차에 자세히.)

**8. Lost in the Middle 방어**
- GPU는 비싸졌지만 모델 성능도 올라가 뒤에 있는 지식도 꽤 잘 활용한다. 그러나 여전히 중간에서 길을 잃는다.
- "[로스트 인 더 미들]이라는 현상을 방어하기 위해서는 반복밖에 답이 없습니다." 단, 똑같이 반복하면 안 된다.
- 앞(시스템 프롬프트 단)에서 "뒤에 이런 지식이 나올 건데 나왔으면 이렇게 얘기하렴"이라고 아주 짧게 요약해 안내하고, 뒤에서 "앞에서 이런 얘기를 했었지"라며 연결한다.
- 비유: 복습. 6시에 나가 카드 찍는 순간 한 70%쯤 휘발된다.
- 멀티턴까지 구현하면 컨텍스트 윈도우 안에서 계속 엮어 주는 작업이 된다.

- 이 강의는 개념·로드맵 설명 위주로, 화면 코드·명령어 시연은 전사에 없다. 강사는 화이트보드식 그림(DB 동그라미, 시스템 프롬프트/스킬 배치도)으로 설명했다.
- 오늘의 실습 방식(원문 취지): "레그가 직접 어떻게 구현되는지를 머릿속에 그리시고 그걸 클로드한테 시켜보시고 그 클로드의 결과가 내가 예상한 것과 얼마나 다른지 그리고 제가 이제 제공해 드릴 코드베이스랑 얼마나 다른지".
- 컨텍스트 배치 도식(장표 10):
  ```
  예전: 치환 ①  [시스템 프롬프트 + 고등수학 지식][질문]  → 앞부분이 다름 → 캐시 ✕
  예전: 치환 ②  [시스템 프롬프트 + 초등수학 지식][질문]  → 또 새 요청으로 처리
  요즘          [시스템 프롬프트 (고정·짧게)][스킬: 이 자료를 이렇게 쓰렴][찾아온 자료][질문] → 앞부분이 같음 → 캐시 ✓
  ```
- 시스템 프롬프트에 넣는 안내 문구 예(강사 발화): "어 뒤에 이런 지식이 나올 건데 나왔으면 이렇게 얘기하렴."
- 스킬 가이드 문구 예(강사 발화): "야, 이 자료를 이렇게 쓰렴."
- 장표 14의 과제·실습 목록:
  1. RAG 구현을 머릿속에 먼저 그려 보기 — 어떻게 저장하고, 찾아오고, 넣어 줄지
  2. Claude에게 시켜 보고 비교하기 — 내 예상과 얼마나 다른지, 제공 코드베이스와 얼마나 다른지
  3. 멀티턴에서는 어떻게 할지 고민하기 — 단일턴이 아닐 때 뒤에 붙인 지식을 어떻게 다룰까
  4. 앞의 요약과 뒤의 내용을 엮어 보기 — 컨텍스트 윈도우 안에서 지식을 연결하는 작업

### 강사 팁·주의사항
- 오늘 슬라이드는 이미지로 따로 제공하므로 필기하지 말고 집중할 것.
- 수업 운영: 45분 집중 + 15분 휴식. 이론·코드 설명은 짧게, 직접 타이핑하고 AI에게 시켜 보는 시간을 길게 준다. 진행 속도에 따라 내용을 넣거나 뺄 수 있다.
- 질문을 많이 할수록 얻어 가는 것이 많다(쉬는 시간에라도 최대한 답변).
- 강사 경험: 지금까지 쓰고 버린 코드가 천만 줄이 넘는다. 요즘은 한 줄을 쓰기까지 시간이 오래 걸리지만, 빨리 쓰는 게 아니라 "내가 원하는 그 한 줄"을 얻는 노력이 중요하다.
- 7~8일차(로컬 LLM)는 주제가 바뀌어 많이 힘들어하지만, "인퍼런스·서빙 안 할 건데 왜?"라고 생각하면 잘못 생각하는 것.
- 9~10일차 코딩 에이전트 프로젝트에서 "핫한 기술들을 여기 다 집어 넣어서 그 핫한 녀석들이 얼마나 보잘것 없었는지" 알게 될 것.
- 벡터 DB를 습관적으로(예제가 그래서) 쓰지 말 것.
- 시스템 프롬프트 앞부분을 바꾸면(치환) 캐시가 깨진다 — 비용 문제로 직결.
- Lost in the Middle 대응 반복은 "똑같이 반복하면 안 된다".

### 실제 프로젝트에 적용할 체크리스트 (- [ ] 행동 지침 형태)
- [ ] RAG 설계를 "잘 찾아오기(검색)"와 "잘 이야기하기(생성)" 두 관점으로 나눠 점검한다.
- [ ] 검색 결과를 컨텍스트에 넣기 전에 "최소한·정확히"인지 확인하고, 과다 주입을 줄인다.
- [ ] 문서가 어디에 있고 무엇을 담고 있는지 안내하는 정보(위치·내용 설명)를 저장 구조에 포함한다.
- [ ] 벡터 DB를 쓰기 전에 대안(검색 엔진, RDB 정형 데이터, 파일 저장)을 검토하고, 재임베딩 부담·한국어 임베딩 성능을 따져 본다.
- [ ] 배경지식을 파인튜닝으로 넣으려는 계획은 비용 관점에서 재검토한다.
- [ ] 시스템 프롬프트는 앞에 고정하고 짧고 포괄적으로 유지한다(요청마다 앞부분을 치환하지 않는다).
- [ ] 상황별 배경지식은 스킬로 뒤에 붙이고 "이 자료를 이렇게 쓰렴" 식의 사용 가이드를 함께 준다.
- [ ] 시스템 프롬프트에 뒤에 나올 지식을 짧게 예고하고, 뒤에서 앞의 안내와 연결되도록 구성해 Lost in the Middle을 방어한다.
- [ ] 멀티턴에서 뒤에 붙인 지식을 어떻게 다룰지(단일턴이 아닐 때) 설계안을 만든다.
- [ ] 직접 RAG 구현을 먼저 그려 보고 Claude에게 시킨 결과·제공 코드베이스와 비교한다.

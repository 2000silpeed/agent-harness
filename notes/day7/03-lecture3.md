## 7일차 3강 — vLLM 추론 엔진 기초: Prefill/Decode, KV Cache, PagedAttention, 배칭과 엔진 구조

### 핵심 요약 (3~5줄)
- 여러 추론 엔진(SGLang, 딥시크 자체 엔진 등) 중 "시조 격"인 **vLLM**에 집중한다. API 비용·보안·모델 커스터마이징 때문에 **셀프호스팅(직접 서빙) 수요가 내년에 더 커질 것**이라는 게 출발점이다.
- LLM 추론은 **Prefill**(프롬프트 전체 병렬 처리, 빠름 → TTFT 결정)과 **Decode**(KV 캐시를 읽으며 한 토큰씩, HBM 대역폭에 묶여 느림 → ITL 결정)로 나뉜다. "디코드가 느려요."
- **KV 캐시**는 연산을 N제곱에서 N으로 줄이지만 캐시를 계속 들고 있어야 하므로 "이제부터 우리의 추론은 연산이 아니라 **메모리의 문제**"다. 크기 수식에서 우리가 조절할 수 있는 건 **데이터 타입과 컨텍스트 길이** 두 개뿐이다.
- vLLM은 "**OS를 GPU에 때려 넣은 엔진**"이다: OS 페이징 → **PagedAttention**(블록·블록 테이블) → 블록 해시 기반 **Prefix Caching**(=프롬프트 캐싱)과 TTL 회수, CPU 시분할 → **Continuous Batching**.
- 엔진 구조는 비동기 API 서버 → 엔진 코어 → GPU당 워커 1개. GPU 8장이면 **CPU 최소 10개**가 필요하므로 서버 산정 때 CPU를 낮추면 안 된다. 어텐션 백엔드는 모델마다 다른 어텐션 연산을 "규격에 맞춰 꽂아 쓰게" 분리한 구조다.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**1. 강의 범위와 vLLM의 위치 (00:09~02:13)**
- 다룰 순서: 추론 관점 이해 → PagedAttention → 엔진 세부 아키텍처(그림만 보고 지나감) → 서빙 인터페이스 → 성능 최적화 → KV 캐시를 vLLM 너머로 확장하는 기술. 마지막 파트 8(GPU 클러스터 운영)은 "자료만 슥 보고 지나간다."
- vLLM은 SGLang, 딥시크가 낸 자체 추론 엔진 등 여러 엔진의 "시조 격" 역할이다.
- 강사 스스로 "여기 내용이 강의할 때마다 가장 두렵다… 거의 늪으로 빠진다"고 했다.

**2. 왜 셀프호스팅인가 (02:15~03:54)**
- **비용**: "이 API 서비스들이 너무 비싸요." 회사 입장에선 "그냥 GPU 사고 말지" 싶을 정도. GPU는 감가상각되며 몇 년 쓰고 좋은 모델로 갈아 끼울 수 있지만 API 비용은 "그냥 날라가버린다."
- **보안**: 회사 내부 소스 코드 유출 등 민감한 문제.
- **커스터마이징**: 모델을 새로 학습하지 않고 기존 레이어를 고쳐 서빙을 빠르게 한 사례를 들며(서비스 이름 불명확), "우리 회사도 그런 일을 할 수 있다". 그러려면 중심이 될 추론 엔진이 필요하다.

**3. Hugging Face `generate`의 한계와 vLLM의 역사 (03:54~08:35)**
- Transformers로 `AutoModelForCausalLM`(전사 "캐쥬얼 LLM")을 로드해 `generate` 하면 출력이 "뚝뚝뚝" 나온다. "이걸로는 절대 서빙하실 수 없습니다… 예제 수준."
  - 작업이 끝날 때까지 **새 요청을 받을 수 없다**.
  - 요청마다 **KV 캐시 공간을 매번 새로 크게 할당**한다.
- vLLM은 새 요청을 계속 받게 해 주고, KV 캐시 용량을 내부에서 **잘라서 보관**(메모리를 한 번에 다 쓰지 않음)한다. "속도나 이런 것들 차원이 다릅니다."
- 역사(강사 발언):
  - 버클리 출신의 유명한 메인테이너(한국인)가 박사 과정 중 만든 프로젝트로, **PagedAttention 논문(23년 9월)의 결과물**로 공개됐다. (공식 문서 확인: https://arxiv.org/abs/2309.06180 — "Efficient Memory Management for Large Language Model Serving with PagedAttention", 2023-09)
  - 24년~25년 초 "모델 춘추전국 시대"에 지원 요청이 쏟아져 메인테이너 부담이 커졌고, **PyTorch Foundation 호스팅 프로젝트**로 합류하며 큰 지원을 받았다. 이후 모델 지원이 빨라지고, 모델사들이 출시 전에 vLLM과 미리 협업해 추론을 최적화하게 됐다. (공식 문서 확인: https://pytorch.org/blog/pytorch-foundation-welcomes-vllm/ — 2025-05-07 호스팅 프로젝트 합류 발표)
  - 작년 10월쯤 **V0 엔진이 지워지고 V1으로** 갔고, vLLM이 회사를 설립해 회사 차원에서 관리한다. 올해 7월 **Model Runner V2**가 기본 장착됐고 호환성 문제도 많이 해결했다.
  - 현재 **CUDA 13**, **PyTorch 2.14**를 지원하는 **v0.33**, 곧 0.34가 될 것 같다.
  - "모델 아키텍처를 가장 많이 지원하는 엔진이 아닌가." 단, "이 변경점은 우리한테 중요하지는 않아요."
  - 저장소 PDF는 "Engine 이름의 V1과 Model Runner 버전의 V2를 구분합니다"라고 적는다. (저장소 확인: Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf:p.12)

**4. 추론의 두 단계: Prefill과 Decode (08:35~13:34)**
- 요청 흐름: 요청 도착(사용자 입력 + 샘플링 파라미터. top-p·top-k 같은 건 "요즘은 모델들이 다 픽스해 놨다") → 토큰화(토큰 ID) → **스케줄링 대기**("연산이 밀려 있을 테니까") → **Prefill**(프롬프트 전체 병렬 처리, 중간 결과를 **KV 캐시로 VRAM에 저장**) → **Decode**(KV 캐시를 읽고 추가하며 반복).
- "어디가 느릴까요? … **디코드가 느려요.**" vLLM 로그 예: Prefill(인풋 토큰)은 **초당 4000 토큰**, Decode는 **초당 30~40 토큰**(보정본 추정). 어느 GPU·모델인지는 말하지 않았다.
- 이유: GPU 연산은 엄청 빠른데 **HBM 대역폭**에 한계가 있어, 최대 대역폭을 다 써도 KV 캐시를 "차근차근" 읽어야 한다.
- 지표 연결: **Prefill → TTFT**(Time To First Token, 첫 토큰까지 시간), **Decode → ITL**(Inter-Token Latency, 토큰 사이 간격). 첫 토큰 이후에는 이전 출력까지 입력에 넣어 회귀하며 한 개씩 출력하므로 부하가 계속 생긴다.
- 강조 이유: 이후 모든 최적화(캐시, 배칭)가 이 두 단계 중 어디를 줄이느냐로 설명되기 때문. (저장소 확인: Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf:p.17 — "Prefill 최적화가 긴 답변의 decode 시간을 자동으로 줄이지는 않습니다.")

**5. KV 캐시의 효과와 메모리 문제 (14:00~16:10)**
- KV 캐시가 없으면 매 스텝 전체를 다시 계산해 **N제곱** — "연산 효율에서는 그냥 똥입니다."
- KV 캐시를 쓰면 마지막 스텝만 계산 → **N**으로 감소. 하지만 "캐시를 계속 들고 있어야만 해서" 문제가 된다. **"이제부터 우리의 추론은 연산이 아니라 메모리의 문제가 계속 되고 있다."**
- Roofline 그래프로, 최대 연산 성능에 도달하기 전까지 메모리 대역폭 때문에 한계를 맞고 있으며 "그 컴퓨트의 한계까지 우리는 지금도 도달하지 못했다"고 설명했다.
- (저장소 확인: Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf:p.23 — O(T² dₕ) → O(T dₕ), 단 "전체 추론이 항상 memory-bound라는 뜻은 아닙니다.")

**6. KV 캐시 크기 계산과 GPU 메모리 배분 (16:12~19:51)**
- "외우시라는 건 아니에요. 저도 안 외워요." 구성 요소만 보자: K·V를 합친 상수, **L**(레이어 수), **H_kv**(KV 헤드 수), **D_head**(헤드 차원), **B**(데이터 타입), 시퀀스(입력+출력 전체 컨텍스트 윈도우), 바이트로 표현.
- **"L과 HKV와 D헤드는 모델이 그냥 픽스해 주는 숫자예요. 우리가 조절할 수 있는 건 뭐예요? 뒤에 두 개밖에 없습니다."** → 데이터 타입과 컨텍스트 길이. 앞 시간(1·2강)에 데이터 타입을 줄이거나 컨텍스트를 100만으로 늘리고 줄인 게 이 두 값이다.
- 예: **Qwen3.8 27B는 토큰당 64KB**. 모델이 지원하는 최대 길이를 넣어도 앞 시간 예시보다 훨씬 작지만 "그래도 쉽지 않다."
- **H100 80GB**에 27B를 **BF16**으로 올리면 가중치 + KV 캐시 + **CUDA 그래프**(연산 효율을 위해 미리 그려 두는 그래프, "꽤 많은 GPU 용량을 차지")까지 포함해 **여유가 10%도 안 된다** → 그래서 **양자화**를 고려하게 된다.
- 저장소 PDF의 공식은 `Mₖᵥ ≈ 2 × B × L × T × nₖᵥ × dₕ × b`로, 여기서 **B는 동시 활성 sequence 수, b가 원소당 bytes(BF16=2)**다. 강의에서 "B = 데이터 타입"이라고 부른 값은 PDF의 `b`에 해당한다(기호 차이). (저장소 확인: Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf:p.25)
- 저장소 PDF도 `gpu-memory-utilization`은 "연산 사용률이 아니라 메모리 예산 비율"이고 graph capture·workspace가 KV에 남는 공간을 줄인다고 적는다. (저장소 확인: Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf:p.27)

**7. 어텐션 구조 경량화와 성능 지표 (19:57~23:34)**
- **MHA**(멀티 헤드), **GQA**(그룹 쿼리), **MQA**(멀티 쿼리), **MLA**(멀티 헤드 레이턴트) — 1x에서 1/4, 1/8로 "완전 대폭 감소". 마지막(MLA)은 딥시크가 도입한 레이어. "모델사들도 발악을 하고 있는 거죠." Claude·OpenAI도 구조는 비공개지만 같은 노력을 한다. **어텐션 구조를 줄여야 KV 캐시를 줄일 수 있기 때문.**
  - (저장소 확인: Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf:p.26 — MHA 32 heads BF16 4 GiB → GQA 8 heads 1 GiB → FP8 0.5 GiB → MQA 0.125 GiB)
- 지표: **TTFT, ITL, TPOT**(Time Per Output Token, 마무리까지의 관점). 운영은 여러 지표로 하지만 **사용자에게는 TTFT와 ITL이 진짜 중요**하다.
  - "에이전트 개발자 입장에서는 처음 한 글자가 늦게 나온다? 와~ 그럼 이제 골 때리는 거죠." 첫 글자 뒤 다음 글자가 오래 걸리면 "서비스가 멈춘 거 아니냐."
  - (저장소 확인: Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf:p.18 — TTFT=t₁−t₀, 평균 TPOT=(tₙ−t₁)/(N−1), E2EL=tₙ−t₀)

**8. PagedAttention (24:01~28:05)**
- 기존 Transformers 방식: 스텝마다 KV 캐시 공간이 바뀌어 새 공간에 할당하고 **전체 복사** — "비효율 끝판왕."
- 대신 정해진 공간을 **예약**하고 내부를 적절히 잘라 운영한다 → OS가 RAM을 프로그램에 나눠 주고 늘리고 줄이는 방식과 같다. 기존 문제는 GPU VRAM을 파편화해 쓴다는 것이었고 OS도 똑같았다.
- **"이게 그 페이지드 어텐션의 개념이에요. 새로운 거 아닙니다. 그냥 OS에서 우리가 알던 그 메모리 관리 방식을 그대로 가져왔어요."**
- 논리 블록 → **블록 테이블** → 물리 블록. 물리적으로는 흩어져 있어도 논리적으로 관리한다. (저장소 확인: Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf:p.29 — "물리 KV는 흩어져 있어도 block table로 찾아갑니다.")

**9. 블록 공유 → Prefix Caching, 그리고 블록 회수(TTL) (28:06~32:07)**
- 블록으로 나눠 저장하면 **공유**할 수 있다("너도 쓸래?"). 그 공유가 **Prefix Caching**이고, 사용자 입장에서는 **프롬프트 캐싱**이다.
- 앞서 프롬프트 캐시를 "텍스트 매칭"이라고 표현했던 이유: 텍스트 **앞부분(prefix)이 똑같아야** 한다.
- 판별 방식: 블록을 **해시로 저장**하고 해시값이 같으면 바로 사용. "빈칸 하나라도 다르면 해시값이 다르게 나오게 세팅." 새 요청은 블록 단위로 해시를 조회하고, **적중한 블록은 Prefill 단계조차 건너뛴다.** 질문 A와 B가 동시에 와도 앞부분이 같으면 그대로 쓴다.
  - (저장소 확인: Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf:p.47 — "cache hit는 prefix가 처음부터 같을 때만 발생하며, 중간에 같은 문장이 있어도 해당되지 않습니다.")
- **회수**: 안 쓰면 회수한다. "회수를 안 하면 영원히 남아있잖아요. 그런 말도 안 되는 시스템은 없죠." 메모리는 엄청 비싼 자원이라 회수해야 하고, 여러 알고리즘이 있지만 **가장 편리한 건 시간(TTL)으로 끊는 것**. 그래서 Anthropic 프롬프트 캐시에 **5분짜리, 1시간짜리**가 있고, "Claude Code는 1시간을 디폴트로 쓴다, API에서는 5분도 가능"이라고 했다.
  - (공식 문서 확인: https://platform.claude.com/docs/en/build-with-claude/prompt-caching — "By default, the cache has a 5-minute lifetime", 1시간은 `"ttl": "1h"` 추가 비용 옵션) Claude Code 기본값이 1시간이라는 부분은 이 문서에서 확인하지 못했다(미확인).

**10. Continuous Batching과 스케줄링 (32:11~36:17)**
- 앞부분이 비슷한 요청은 KV 캐시를 같이 쓰므로 "같이 처리하는 게 낫지 않을까요?" — 캐시를 날려버리는 게 아까우니 몰아서 처리. **"LLM 인퍼런스의 가장 마지막 단계는 배치를 어떻게 처리할 수 있느냐 설정으로 결정"**, 비용을 얼마나 아낄지도 배치가 결정한다.
- **Continuous Batching**: 단건 처리처럼 보이지만 요청 여러 개를 쪼개 **CPU 타임 나눠주듯** 번갈아 처리(이터레이션 레벨 스케줄링). 한 개를 쭉 하는 게 가장 빠르지만 그러면 여러 요청을 못 받는다. → **처리량 증가**.
- **"저는 이 VLLM은 거의 OS를 GPU에 갖다가 때려 넣은 엔진이다 라는 생각이 많이 들었습니다."**
- **`max_num_batched_tokens`**: 예컨대 **2048**로 두면 한 번에 배치에 들어갈 수 있는 최대 토큰(토큰 예산) 단위로 끊어 처리한다. 쉽게는 "저장한 블록 사이즈만큼 꺼내서 연산하고 다시 집어넣고"를 반복해 여러 요청을 동시에 처리한다고 생각하면 된다.
  - (저장소 확인: Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf:p.38 — "max_num_batched_tokens는 한 iteration의 토큰 예산이지, 요청 하나의 최대 context 길이가 아닙니다.", p.39 — `--max-num-batched-tokens 2048` 예시)
- 우선순위 요청 처리를 위한 **선점(preemption)** 기술이 있고 "설정을 할 수 있다" 정도만 언급하고 넘어갔다.

**11. 엔진 아키텍처와 CPU 산정 (36:21~41:49)**
- 원래 동기 요청이던 것을 **모든 요청을 비동기로** 받도록 구성 → **엔진 코어** → **GPU마다 워커 1개**(8장이면 워커 8개).
- 계산: 워커 8 + 엔진 코어 1 + API 서버 1 = **vCPU(논리 코어) 최소 10개**. "우리 CPU 스펙을 너무 낮추면 안 된다는 거예요."
- 흔한 실수: 프로젝트 전 서버 스펙 산정 때 좋은 GPU 8장에 저사양 CPU 하나(8코어짜리 등)만 꽂는 경우 — "집 컴퓨터 조립하듯이." 작은 회사들이 많이 한다.
- 보통 **GPU 4장당 CPU 1개**로 산정한다 → GPU 8장이면 **CPU 무조건 2개**. 이후는 논리 코어 크기와 RAM 대역폭 선택. **"결론은 어쨌든 우리는 엔진만으로도 CPU를 굉장히 많이 쓴다."**
- **Model Runner V2**: **CPU-GPU 동기화 제거**가 목표. CPU 제어를 받는 게 병목이라 GPU 단독으로 최대한 돌기를 원한다(NVIDIA·AMD가 자체 CPU를 쓰는 이유, 베라 루빈 등). "이 엔진은 하드웨어랑 궤를 같이 하고 있다."
  - (저장소 확인: Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf:p.13 — MRV2 "CPU 준비와 GPU 실행이… 겹치도록 설계합니다. 불필요한 동기화를 줄입니다.")

**12. 어텐션 백엔드 (41:52~44:20)**
- 질문: "플래시 어텐션이 꼭 필요하다던데 왜 들어가냐? vLLM이 혼자 다 해주면 되지 않냐?"
- 모델마다 어텐션 레이어 구성이 계속 바뀌니(딥시크 구성 등) "그냥 따로 뜯어내자." **"야 그냥 우리가 규격을 줄게 거기에 맞춰서 계산값만 줘, 너네 엔진 여기 꽂아서 쓰게 해줄게"가 vLLM의 전략.** 모델사가 만든 걸로 바로 서빙할 수 있게 하기 위함.
- 종류: **FlashAttention**(대표), **Triton Attention**, **FlashInfer**, **FlashMLA**(딥시크가 만든 것). **모델마다, GPU 상황에 따라** 백엔드가 바뀐다. 강의: NVIDIA 전반에서는 FlashInfer, FlashAttention 3·4는 최신 아키텍처에만, 어떤 것은 딥시크 계열에서만.
  - 저장소 PDF의 선택표는 "MHA/GQA · Ampere·Hopper → FLASH_ATTN 우선", "MHA/GQA · Blackwell → FLASHINFER 우선", "MLA → MLA 전용 backend"이고 "자동 선택 → 실제 선택 로그 확인 → 필요한 경우에만 강제 지정" 순서를 권한다. 강의의 "FlashInfer는 NVIDIA 전반"과 표현이 다르다(미확인). (저장소 확인: Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf:p.34)

**13. 오전 정리와 오후 예고 (44:21~45:53)**
- 오전에 본 것: **모델 웨이트, KV 캐시, 그것을 운용하는 vLLM의 내부(논리) 구조**.
- 오후: 직접 서빙은 하지 않는다. "세팅하다가 시간이 다 가더라고요." 대신 **이미 서빙된 작은 모델**(예: Qwen3.8 27B)을 써 보고 어떤 효능이 있는지 본다.

### 강사 팁·주의사항
- Transformers `generate`는 예제 수준이다. **서빙에 쓰지 않는다.**
- 디코드가 느리다. 체감 속도는 **첫 글자(TTFT)와 글자 간격(ITL)**이 좌우하므로 에이전트 개발자는 이 둘을 주 지표로 본다.
- KV 캐시 크기 중 바꿀 수 있는 건 **데이터 타입·컨텍스트 길이**뿐이다. 모델 고정값(L, H_kv, D_head)은 모델을 바꾸지 않으면 못 바꾼다.
- 80GB GPU에 27B BF16은 CUDA 그래프까지 넣으면 여유가 거의 없다 → 양자화를 고려.
- 프롬프트 캐시는 **앞부분 일치 + 해시 비교**다. 빈칸 하나라도 다르면 해시가 달라진다.
- 캐시는 TTL로 회수된다(Anthropic 5분/1시간). 영원히 남는 캐시는 없다.
- 서버 스펙 산정 시 **CPU를 빼먹지 말 것**: GPU 8장이면 vCPU 최소 10개, CPU 소켓 2개.
- 어텐션 백엔드는 모델·GPU에 따라 자동으로 바뀐다. FlashAttention 3·4는 최신 아키텍처 전용.
- 직접 서빙 실습은 세팅에 시간이 다 가므로, 교육에서는 서빙된 모델을 써 본다.

### 실제 프로젝트에 적용할 체크리스트 (- [ ] 행동 지침, 특정 프레임워크에 묶이지 않는 원칙 위주)
- [ ] 외부 API 대신 셀프호스팅을 검토할 때 비용(감가상각·모델 교체 가능성), 보안(코드·데이터 유출), 커스터마이징 필요성 세 축으로 판단 근거를 남긴다.
- [ ] 라이브러리 예제의 단건 `generate` 방식으로 서비스를 띄우지 않는다. 동시 요청·KV 메모리 관리를 하는 추론 엔진을 쓴다.
- [ ] 응답 지연을 측정할 때 TTFT(첫 토큰)와 ITL(토큰 간격)을 분리해 기록하고, 사용자 체감 SLO를 이 둘로 정한다.
- [ ] TTFT가 나쁘면 Prefill(입력 길이·캐시 적중)을, ITL이 나쁘면 Decode(메모리 대역폭·배치)를 먼저 의심한다.
- [ ] 모델 선정 전에 토큰당 KV 크기와 목표 컨텍스트 길이로 KV 메모리를 계산하고, 가중치 + KV + 실행 그래프 공간을 합쳐 GPU 여유를 확인한다. 여유가 10% 수준이면 양자화나 컨텍스트 축소를 검토한다.
- [ ] 조절 가능한 값은 데이터 타입과 컨텍스트 길이뿐임을 전제로 메모리 대책을 세운다(모델 구조 값은 모델 교체로만 바뀜).
- [ ] 프롬프트는 앞부분이 매번 똑같게 유지한다. 바뀌는 값은 뒤로 보내 prefix 캐시 적중을 지킨다.
- [ ] 캐시는 TTL로 사라진다는 전제로, 재호출 간격이 캐시 수명보다 긴 작업은 캐시 이득을 기대하지 않는다.
- [ ] 앞부분이 같은 요청은 몰아서 처리하도록 요청 흐름을 설계한다.
- [ ] 배치 토큰 예산(한 회차에 넣을 최대 토큰)은 처리량과 지연의 교환 관계로 보고, 한 번에 한 변수만 바꿔 비교한다.
- [ ] GPU 서버 스펙을 산정할 때 GPU 1장당 워커 1개 + 엔진·API 프로세스 몫의 CPU를 더해 계산하고, GPU 4장당 CPU 1개를 기준으로 삼는다.
- [ ] 어텐션 백엔드는 자동 선택된 것을 로그로 확인하고, 모델·GPU 세대를 바꾸면 다시 확인한다.

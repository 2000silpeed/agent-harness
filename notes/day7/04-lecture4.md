> 대응 저장소: `Day07/` — `README.md`, `runpod_model_call.py`, `runpod_openai_reasoning.py`, 강의 자료 `Day7_vLLM_기초와_추론_속도_최적화.pdf`(이하 "저장소 PDF", 줄 번호가 없어 `p.쪽`으로 표기), 판서 `Day07_01.png`. 강사는 vLLM 레시피 사이트와 Ollama 사이트를 직접 열어 보였고, 나머지는 이론 자료 PART 5(서빙 인터페이스)·PART 6(성능 최적화)를 훑었다. PART 7(KV 캐시 확장)은 휴식 뒤로 넘겼다.

### 핵심 요약 (3~5줄)
- vLLM이 약 6개월 전 연 **레시피(Recipes) 사이트**에 모델 × 하드웨어별로 실제 돌려 본 기본 설정과 튜닝 가이드가 있다. "직접 서빙 하시는 분들은 … 꼭 보시면 좋겠습니다." GLM 5.3 예시로 토크나이저 모드, KV cache dtype, TP, tool-call/reasoning 파서, `enable-auto-tool-choice`를 살폈다.
- **파서**는 모델마다 다른 챗 템플릿 출력(`<think>`, 툴 응답 XML 등)을 **OpenAI 규격**으로 바꿔 준다. 모델사가 vLLM과 협업해 코드를 넣어 두므로 에이전트 개발자는 파서를 직접 만들지 않는다. 반대로 이 설정은 "그냥 if문"이라 모델 이름만 바꿔 끼우기 쉽다 → 모델 구조(config.json)로 독자 모델 여부 논란이 생긴다.
- **NVFP4**는 Blackwell 이상에서만 쓰며 더 빠르고 작다(레시피 예시 FP8 893GB → 560GB). **CUDA Graph는 테스트 때 외에는 끄지 말 것.** 요청은 API 서버(토큰화) → 엔진 코어 → GPU 워커 → 토큰 ID → 디토큰화 + 파서 → 응답 순으로 흐른다.
- 에이전트 개발자는 **Prefill/Decode를 계속 기억**해야 한다: "Prefill은 고정된 입력이어야 됩니다… 캐시를 깨지 말자." vLLM 서버 하나가 OpenAI·Anthropic 호환, 임베딩, 토큰 수 계산, LoRA 켜고 끄기까지 지원한다.
- thinking을 끄면 첫 답이 빨라지지만 덜 똑똑해진다. 루프형 트랜스포머처럼 "속으로 생각"하는 구조는 사고 과정 감시를 어렵게 한다. 성능은 기본 100 → 레시피 그대로 110 → 조금 튜닝 120~150(주로 속도). 양자화(GGUF/llama.cpp/MLX), 스페큘레이티브 디코딩을 훑었다.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**0. 도입: 작은 모델을 직접 써 보는 이유 (00:07~03:48)**
- 초반은 수능·예능 출연 강사 이야기 등 잡담과 어제 소개한 KX1 가입 경험담(회사 이메일로는 승인이 잘 안 되고 개인 계정으로 됐다)이었다. 어제 써 본 소감은 "아쉬움이 많이 느껴졌다", 오늘 실습도 비슷할 것.
- **"프로젝트 들어가면 갑자기 이 모델을 그냥 당하시는 거죠."** 교육 중에 작은 모델이 뭐가 부족하고 뭐는 잘 되는지 경험해 두라는 것.
- vLLM을 실제로 돌려 보며 하면 "순식간에 6시가 될 거예요. 안 돌아갑니다." 그래서 이론은 자료로 진행한다.

**1. vLLM 레시피 사이트 (03:48~06:38, 18:53~23:05)**
- 예전에는 "알음알음", 커뮤니티에서만 성공·실패가 공유됐고 하드웨어 스펙 기준 세팅이 공유되지 않았다. 레시피 사이트는 많은 모델을 vLLM에서 직접 돌려 보고 **장비 스펙별 설정**을 올려 둔다. (공식 문서 확인: https://recipes.vllm.ai/ — "Pick a model, adjust for your GPUs, copy the `vllm serve` line that runs.")
- "VLLM을 실행할 때는 이런 **기본 세팅이 사실 되게 중요**하거든요." 원래는 문서를 한 땀 한 땀 봐야 했다("요즘에 이제 클로드가 다 해주기는 하지만").
- GLM 5.3 기본 세팅에서 짚은 항목:
  - **토크나이저 모드**: 같은 모델 시리즈라도 토크나이저가 가끔 바뀐다. 보통 시리즈 앞 번호가 크게 바뀔 때 바뀐다. 예외로 "Qwen은 토크나이저가 Qwen2부터 똑같아요." GLM은 `GLM5_NEXT` 토크나이저를 쓴다.
  - **KV cache dtype**: FP8 모델로 출시됐으므로 KV 캐시도 FP8로 **명시적으로** 설정. "그게 아니어도 찾아갈 거예요. 하지만 우리는 좀 설정에는 명시적으로 쓰는 게 좋기 때문에."
  - **TP(텐서 패러렐) 크기**: GPU 개수에 맞춘다. 장비를 H200으로 바꾸면 값이 늘어나고 max model len이 작아지는 것을 화면에서 보였다.
  - **tool-call 파서, reasoning 파서**와 **`enable-auto-tool-choice`**(아래 2·4절).
  - 레시피 공식 페이지(GLM-5.3) 기본 명령: `--tokenizer-mode glm5_next`, `--kv-cache-dtype fp8_e4m3`, `--tensor-parallel-size 8`, `--tool-call-parser glm47`, `--enable-auto-tool-choice`, `--reasoning-parser glm47`(기본 구성 8× B300). (공식 문서 확인: https://recipes.vllm.ai/zai-org/GLM-5.3)
- 장비별 테스트 표기: **H200 8장 노드에서 테스트했다, B200 8장은 아직 못 해봤다, B300은 해봤다** — "서버 스펙까지 이렇게 꼼꼼하게 나옵니다." 장비를 누를 때마다 위 설정이 조금씩 바뀐다. **DGX Station(GB300)**을 내부에 구축 중이라면 "이렇게 많은 옵션을 필요로 합니다."
- 그 밖에 TP는 항상 기본 옵션으로 쓰라고 별표가 쳐져 있고, **EP(expert parallel)**는 요즘 대부분 모델이 **MoE**라 "거의 기본 활성화된다." **KV 오프로드** 메뉴도 있는데 "좀 이따가"(KV 캐시 확장 시간) 본다.
- 강조 이유: 서빙의 대부분은 "올리는 게 문제가 아니라 튜닝이 문제"이고, 레시피가 검증된 출발점과 튜닝 가이드를 준다.

**2. tool-call 파서·reasoning 파서와 챗 템플릿 (06:38~10:24)**
- "이름이 파서잖아요. … 뭘 파싱할까요? 왜 파싱할까요?"
- 챗 템플릿(GLM)을 보면 **reasoning effort**를 활성화할 때 low, medium, high, xhigh, max까지 설정하는 정보가 들어가고, 모델이 thinking(=reasoning)하는 프로세스를 우리가 캐치해야 한다. **그때 모델이 내뱉는 챗 템플릿 형식은 모델마다 다르다.** 예: 툴 응답(`tool_response`)을 내부적으로 XML 처리.
- "모델이 마음대로 출력을 해서 주면 우리가 매번 이걸 다 적응해야 될까요? … 파서를 다 구현해야 될까요? 하지 않아도 됩니다." **vLLM이 "내가 파싱해서 줄게"**, 대표적으로 **OpenAI 형식**으로 출력해 준다 → "너네는 오픈 AI 규격으로 호출하면 받을 수 있을 거예요"를 보장.
- 파서 규격은 **모델사들이 vLLM과 미리 협업해 코드가 박혀 있다.**
- 저장소 실습 코드도 같은 맥락의 주석을 단다: "각 모델마다 Chat Template 이 다르기 때문에 Reasoning On/Off 요청을 전달하는 방식도 모두 다름." (저장소 확인: Day07/runpod_model_call.py:37) reasoning_effort는 `chat_template_kwargs`로 넘긴다. (저장소 확인: Day07/runpod_openai_reasoning.py:40)
- (공식 문서 확인: https://docs.vllm.ai/en/latest/features/reasoning_outputs.html — "The `--reasoning-parser` flag specifies the reasoning parser to use for extracting reasoning content from the model output.")

**3. 서빙 설정은 바꿔 끼우기 쉽다 — 모델 정체성 논란 (10:26~18:50)**
- vLLM 서버에 "지금 서빙하는 모델 뭐야"라고 물으면 "ZAI ORG의 GLM 5.3"이라고 답한다. 그런데 GLM 5.3을 살짝 "마개조"해 "현준 1"이라는 이름으로 서빙하면, 호출하는 쪽에서 실제로 GLM인지 알 수 있을까? **"거의 알기 힘듭니다."**
- 토크나이저 모드, tool-call 파서, reasoning 파서는 "다 그냥 갈아 끼울 수 있거든요. 사실 VLLM에 들어가면 그냥 코드고 if문이에요." (GLM47이 인식되면 파싱 코드 한 줄 실행하는 정도.) (공식 문서 확인: https://docs.vllm.ai/en/latest/features/tool_calling.html — GLM-4.7 계열 `--tool-call-parser glm47`)
- 두 번째 단서는 **config.json** 스펙(헤드 차원, 히든 사이즈, 레이어 구성). 이게 비슷하면 "같은 모델 아니냐"는 의심이 생긴다. 올해 초 독자 파운데이션 모델(독파모) 하나가 **GLM 4.7과 레이어 구성이 너무 비슷해** 논란이 됐다: 학습 데이터가 달라 가중치가 다른 게 중요하다는 의견 vs 국가 모델이면 구조도 개선했어야 한다는 의견.
- 강사의 현장 경험(1월 1일 해명 자리 참석): 학습 체크포인트를 공개했지만 "학습 데이터·학습 코드를 다 공개하라, 중간 히스토리만으론 의미 없다"는 반응에 "영업 비밀"이라고 했다.
- 다른 국내 모델사의 과거 사례: 두 모델의 중간 레이어를 뜯어내 붙여 하나처럼 보이게 만든 것. "모델의 짜깁기는 그렇게 어렵지 않은 기술"이고 강사도 이전 작은 회사(금융 특화 모델)에서 추가 학습·레이어 짜깁기를 많이 해 봤다. 다만 공적 자금을 받는 경우 "새로운 모델의 개발이라고 할 수 있는 것인가"가 문제.
- 정리: 이 파싱 파라미터들은 **모델 출력을 제어하기 위해 쓰는 것**이다.

**4. `enable-auto-tool-choice` (18:53~19:38)**
- **tool-call 파서와 세트.** 툴 콜 파싱을 하려면 리스트 중에서 툴을 고를 수 있게 하는 이 옵션을 항상 줘야 한다. "얘네 두 개는 항상 같이 가요."
- 강사 의견: 파서가 있으면 자동으로 켜져야 할 것 같은데 왜 여전히 별도 옵션인지는 "만든 사람만이 알겠죠."
- (공식 문서 확인: https://docs.vllm.ai/en/latest/features/tool_calling.html — `--enable-auto-tool-choice`는 "**mandatory** Auto tool choice"로 표기, `--tool-call-parser`와 함께 설정하도록 안내)

**5. NVFP4와 장비 (20:32~22:22)**
- **NVFP4**: NVIDIA가 만든 양자화 방식, **Blackwell 이상 GPU에서만** 사용 가능(이전 세대는 드라이버가 지원하지 않음). GB300 같은 Blackwell 세트에서 쓸 수 있고 "**더 빨라지고 자원 효율은 더 높아져요.**"
- 레시피 변형 예: **FP8 893GB → NVFP4 560GB**. "거의 같은 성능을 내는데 최대한 모델을 작게 유지할 수 있으면 더 좋으니까." → "이런 모델들은 사실상 우리가 강제로 GPU를 업그레이드 해야 되는 상황입니다."
- 레시피 공식 페이지는 NVFP4 체크포인트를 "~465 GB", "targets Blackwell", MoE expert linear만 NVFP4이고 나머지는 BF16이라고 적고 FP8 크기는 적지 않는다. 강의 수치(560GB)와 다르다(미확인). (공식 문서 확인: https://recipes.vllm.ai/zai-org/GLM-5.3)
- 저장소 PDF도 NVFP4/MXFP4를 "서로 다른 format · GPU별 지원"으로 두고 "더 빨라진다고 단정할 수 없습니다"라고 적는다. 강의의 "더 빨라진다"와 뉘앙스가 다르다. (저장소 확인: Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf:p.51)

**6. CUDA Graph — 끄지 말 것 (23:18~25:01)**
- CUDA Graph는 GPU 용량을 차지하는 요소이고 켜고 끌 수 있다. 처음 서빙할 때 끄는 경우가 많은데, **"끄고 켜는 거는 진짜 그냥 테스트할 때 정도 밖에 안 하고 실제로는 다 켠 상태로 해야 됩니다."** 성능을 타협하려고 굳이 끄면 안 된다.
- 이유: 연산 효율을 정리하는 그래프를 그려 GPU 램에 올려 둔다. 끄면 실행 사이가 "퉁퉁퉁" 비어 빈 구간마다 엄청난 낭비가 생기고, 켜면 "촘촘하게" 빈틈없이 실행된다. "그 정도의 램을 할당을 못한다 라고 하면은 … **잘못 세팅한 경우가 대부분**입니다."
- (저장소 확인: Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf:p.41 — Eager vs Graph Replay timeline, p.42 — `--enforce-eager`는 "compile·CUDA Graph 비활성화 / 문제 격리·시작 비용 비교" 용도) 실습 서버 기동에서도 CUDA graph 단계가 약 215초 걸렸다. (저장소 확인: Day07/README.md:80)

**7. 요청 처리 경로와 Prefill/Decode 재강조 (25:04~27:23)**
- OpenAI 호환 서버에 요청 → **API 서버**에서 토큰화 → **엔진 코어**가 GPU 워커에 배치 실행을 시킴 → 결과를 **토큰 ID**로 받음 → **디토큰화** → **파서**까지 거쳐 전달. "아주 간단한 구성." **스케줄링과 KV 캐시 할당 영역이 vLLM의 코어**이고 지금까지 이걸 학습했다.
- API 서버는 원래 Python **FastAPI**였는데 최근 **Rust**로 바꾸고 있다("가벼워서요"). 요즘 AI가 다 해 주니 성능 이득이 큰 Rust로 많이들 간다. (공식 문서 확인: https://recipes.vllm.ai/zai-org/GLM-5.3 — 기본 명령에 `export VLLM_USE_RUST_FRONTEND=1`)
- **"여러분들이 이 프리필과 디코드를 에이전트 개발하실 때도 계속 기억을 하셔야 돼요. 우리의 프리필은 고정된 입력이어야 됩니다. 그래서 캐시를 깨지 말자"** — 엔진이 연산할 양을 줄이기 위해서다. Decode는 "어차피 줄일 수가 없죠."

**8. 서빙 인터페이스 (27:26~30:19)**
- "크게 중요하진 않습니다." **오프라인 배치**는 거의 볼 일이 없다 — 모델 개발이나 벤치마크 개발처럼 데이터셋이 정해져 있는 경우에 쓴다. 대부분은 **도커 이미지** 형태로 **OpenAI 호환 서버**까지 같이 실행되는 것을 쓴다. (저장소 확인: Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf:p.6 — 오프라인 `LLM` 클래스 vs 온라인 `vllm serve`, "두 경로 모두 같은 EngineCore로 들어갑니다.") 실습 서버도 도커 이미지 `vllm/vllm-openai:glm53-flash`로 띄웠다. (저장소 확인: Day07/README.md:75)
- **시작 로그 읽기**: 모델 로딩 몇 GB, GPU KV cache size 몇백만 토큰, 그리고 `maximum concurrency for … tokens per request`. 이는 **전체 KV 토큰 수를 우리가 설정한 max model len(모델 하나가 최대로 받는 길이)으로 단순히 나눈 값**이다. 그래서 "모델 길이를 좀 늘리고 동시 처리를 좀 줄일까" 같은 고민을 할 수 있다. (저장소 확인: Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf:p.7 — "GPU KV cache size: 65,536 tokens / Maximum concurrency: 8.00x", "설정 플래그는 요청이고 로그는 응답입니다.")
- **OpenAI 호환 엔드포인트**와 함께 **Anthropic 호환도 제공** — "요즘 워낙 클로드 코드 요청이 많아서." 또 **임베딩 모델**, 입력의 **토큰 수 계산** API, 파인튜닝된 **LoRA 어댑터 켜고 끄기**까지 vLLM 서버가 지원한다. "엔진 하나만으로 할 수 있는 게 너무 많다."
  - (공식 문서 확인: https://docs.vllm.ai/en/latest/serving/online_serving/ — "Anthropic messages API ( `/v1/messages`, `/v1/messages/count_tokens`)", `/v1/embeddings`, `/tokenize`, `/v1/load_lora_adapter`·`/v1/unload_lora_adapter`. 단 LoRA 동적 로딩은 "This should ONLY be used for local development!"로 표기)
- 툴 콜링·reasoning·챗 템플릿 슬라이드는 앞에서 말한 내용이라 넘어갔다. 에이전트 서빙도 "API 호출하는 거랑 규격이 같아서 다른 게 없다… 호출 규격만 맞으면 다 받아들인다."

**9. thinking 제어와 루프형 트랜스포머 (30:40~36:16)**
- 모델 원시 출력 `<think>…</think>`를 파싱해 **reasoning과 content**로 나눠 준다. 어떤 설정은 **`enable_thinking`**을 false/true로 주어 thinking을 제어한다.
  - (공식 문서 확인: https://docs.vllm.ai/en/latest/features/reasoning_outputs.html — `extra_body={"chat_template_kwargs": {"enable_thinking": False}}`, 응답 필드는 `reasoning`(이전 이름 `reasoning_content`)) 저장소 코드는 필드 이름이 vLLM 버전에 따라 `reasoning` 또는 `reasoning_content`라 둘 다 읽는다. (저장소 확인: Day07/runpod_openai_reasoning.py:43) 저장소 실습 모델(GLM-5.3-Flash)은 `enable_thinking`이 아니라 `reasoning_effort`로 제어한다. (저장소 확인: Day07/runpod_model_call.py:37)
- 질문: thinking을 끄면 빠른가? 최종 답의 첫 토큰 기준으로는 **빠르다**. thinking은 "모델이 그냥 떠드는 거"라 안 하게 하면 답이 빨리 온다. "물론 그만큼 멍청해지겠지만."
- 쟁점: 모델이 생각을 **말하지 않고 속으로** 하면? 결과만 맞으면 되니 모든 모델사가 여기에 사활을 건다. 지금까지는 모델이 생각을 떠들어 줘서 사람이 보고 필터링·추가 학습을 했다.
- **루프형 트랜스포머(Looped Transformers)**: 같은 계산 블록을 여러 번 통과시켜 토큰 하나를 처리 → 여러 단계에 걸쳐 문제를 푸는 능력(검산 같은)이 높아졌다. 강사는 이를 "GPT6 아스트라"의 구성으로 소개했다.
- 문제: 시스템 카드에 **사고사슬 감시 가능성 저하**가 적혔다 — 말을 안 하니 어떤 생각을 하는지 사람이 파악하기 어려워진다. "아직까지 결론이 난 건 없어요." 그래도 "굉장히 위험한 기술"이라는 우려가 있고, Anthropic CEO가 모델 개발을 멈추자는 취지의 말을 했다고 소개했다.
- 정리: 모델은 지금까지 모든 걸 출력했지만 **"언제든지 출력을 안 할 수도 있어요."** 생각해 볼 문제로 던졌다.

**10. LoRA = 가면 (36:31~37:30)**
- "모델이 **가면**을 쓰는 거예요." 연극처럼 **특정 작업의 아웃풋만을 제어**할 때 쓴다. LoRA 기반 파인튜닝은 **극소량의 가중치**만 건드려 "지식이 늘어나고 그런 일은 거의 없습니다."
- 장점은 **출력 제어**, 그리고 미리 가중치에 녹여 두므로 **입력 프롬프트를 줄이는 것** 정도.
- 구조화 출력(Structured Outputs)은 "너무나 익숙하신 거니까" 넘어갔다. (저장소 확인: Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf:p.69 — LoRA 운영, p.70 — 구조화 출력)

**11. 성능 최적화와 양자화(GGUF·llama.cpp·MLX) (37:37~42:32)**
- 최적화 포인트가 정말 많다. 베이스라인(아무 설정 없이) **100** → **레시피 설정 그대로 약 110** → 조금 더 만지면 **120~150**. "같은 세팅인데도" 늘고, 주로 **속도**가 빨라진다.
- 첫 번째 수단은 **양자화**. 가장 익숙한 건 **GGUF** — Ollama 모델 페이지에서 계속 보이는 표기다(강사가 Ollama 사이트를 열어 보임).
- **llama.cpp**가 GGUF 양자화 포맷을 만드는 프로젝트이고 Ollama는 그걸 돌린다. 이름대로 원래 라마 모델을 C++로 추론하려고, **CPU 서빙**을 목표로 만들어졌고 지금은 **CPU·GPU를 합쳐 돌리는** 규격으로 사랑받는다. llama.cpp가 **코어 엔진**, Ollama·**LM Studio** 등은 **프론트엔드(래퍼)**: 채팅 UI, 쉬운 모델 다운로드·올리고 내리기.
  - (저장소 확인: Day07/Day07_01.png — 판서 "GGUF / llama.cpp / Ollama / LMStudio")
  - (공식 문서 확인: https://github.com/ggml-org/llama.cpp — "CPU+GPU hybrid inference to partially accelerate models larger than the total VRAM capacity", `convert_hf_to_gguf.py`) Ollama·LM Studio가 래퍼라는 관계는 이 페이지에 명시돼 있지 않다(강의 설명).
- 맥북 사용자라면 **MLX**: 애플 실리콘 칩 전용 딥러닝 프레임워크. NumPy(행렬 연산, 백본 C)를 애플 칩셋에 맞게 개선한 것으로 비유했다. Ollama 페이지에도 MLX 버전이 표시된다. 로컬 모델·Mac Studio에 관심이 많아 이런 것도 서비스된다.

**12. 스페큘레이티브 디코딩과 튜닝 (42:34~44:30)**
- Decode가 느리니 빠르게 하기 위한 기술. **작은 모델 + 큰(메인) 모델** 두 개가 필요하다. 작고 빠른 모델이 "이럴 때 이런 토큰을 쓸 수 있을 것 같은데"라고 후보를 제안하면 그중 괜찮은 것을 픽한다. "디코딩 프로세스를 어떻게든 빨리 해보겠다라는 쥐어짜기."
  - (공식 문서 확인: https://docs.vllm.ai/en/latest/features/speculative_decoding/ — "reduce inter-token latency under medium-to-low QPS … memory-bound workloads", 방식: draft model, N-gram, EAGLE, MTP, 설정 `--speculative-config`) 실습 서버도 MTP(5)를 켰다. (저장소 확인: Day07/README.md:76)
- **튜닝**: "VLLM을 서빙한다라는 건 대부분은 **올리는 게 문제가 아니라 튜닝이 문제**입니다." 자료에 언제·어떻게 튜닝할지 담았지만 "레시피가 훨씬 잘해줍니다. 레시피에 튜닝에 관한 가이드도 있어요." 자료 내용은 "완전히 옛날 지식이 되어버렸다."
- KV 캐시 확장은 2시에 이어서 하고, 그다음 작은 모델 실습으로 넘어간다.

### 강사 팁·주의사항
- 직접 서빙한다면 **레시피 사이트를 먼저 본다.** 장비를 바꾸면 설정이 바뀐다.
- 설정은 **명시적으로** 쓴다(KV cache dtype처럼 자동으로 찾아가더라도).
- tool-call 파서와 `enable-auto-tool-choice`는 **항상 같이** 준다.
- 파서는 모델사가 vLLM에 넣어 둔다. 에이전트 개발자는 파서를 만들지 말고 **OpenAI 규격으로 호출**하면 된다.
- 서버가 알려 주는 모델 이름만으로는 실제 모델을 알 수 없다. 이름·파서·토크나이저 설정은 쉽게 바꿔 끼울 수 있다.
- NVFP4는 **Blackwell 이상 전용**이다. 이런 모델은 사실상 GPU 업그레이드를 강제한다.
- MoE 모델이 대부분이라 EP는 거의 기본으로 켜진다.
- **CUDA Graph는 테스트 외에는 끄지 않는다.** 그 정도 메모리를 못 준다면 설정을 잘못한 것이다.
- 에이전트를 만들 때도 **Prefill은 고정 입력, 캐시를 깨지 말 것.** Decode는 줄일 수 없다.
- 시작 로그의 maximum concurrency로 컨텍스트 길이 vs 동시 처리의 교환을 판단한다.
- thinking을 끄면 빨라지지만 덜 똑똑해진다.
- LoRA는 지식 학습용이 아니다(출력 제어·프롬프트 축소용).
- 서빙은 올리는 것보다 **튜닝이 문제**다. 레시피 그대로만 써도 약 10% 이득.

### 실제 프로젝트에 적용할 체크리스트 (- [ ] 행동 지침, 특정 프레임워크에 묶이지 않는 원칙 위주)
- [ ] 모델을 자체 서빙하기 전에 해당 모델 × 장비 조합으로 검증된 공개 설정(엔진 공식 레시피 등)이 있는지 먼저 찾고, 그 설정을 기준선으로 삼는다.
- [ ] 장비(GPU 종류·장수)가 바뀌면 병렬화 크기, 최대 컨텍스트, 양자화 형식 같은 설정을 다시 확인한다.
- [ ] 서빙 설정(토크나이저, KV 캐시 dtype, 도구 호출·사고 과정 파서 등)은 기본값에 맡기지 말고 명시적으로 적어 버전 관리한다.
- [ ] 에이전트 코드는 엔진이 제공하는 표준 규격(OpenAI 호환 등)의 tool_calls·reasoning 필드에 의존하고, 모델별 원시 출력 파서를 직접 만들지 않는다.
- [ ] 도구 호출을 쓰려면 엔진 쪽에서 도구 호출 파싱과 자동 도구 선택이 둘 다 켜져 있는지 기동 시점에 확인한다.
- [ ] 사고 과정 필드 이름이 엔진 버전에 따라 다를 수 있으므로, 클라이언트는 두 이름을 모두 읽거나 버전을 고정한다.
- [ ] 서버가 보고하는 모델 이름을 모델 정체의 증거로 쓰지 않는다. 출처 확인이 필요하면 가중치·설정 파일·학습 근거를 요구한다.
- [ ] 저정밀 양자화 형식을 도입하기 전에 GPU 세대 지원 여부를 확인하고, 품질 회귀와 실제 속도를 같은 조건에서 측정한 뒤 채택한다.
- [ ] 실행 그래프 캡처 같은 엔진 최적화는 진단 목적 외에는 끄지 않는다. 메모리가 부족하면 그 기능을 끄기 전에 설정 전체를 다시 본다.
- [ ] 서버 시작 로그에서 KV 캐시 총 토큰과 최대 동시 처리 수를 확인하고, 최대 컨텍스트 길이와 동시 처리 수의 교환을 의도적으로 고른다.
- [ ] 프롬프트 앞부분(시스템 지시·고정 자료)은 고정해 캐시를 깨지 않게 하고, 바뀌는 값은 뒤로 보낸다.
- [ ] 첫 응답 속도가 중요한 경로에서는 사고 과정 끄기를 검토하되, 품질 저하를 같은 평가 세트로 확인한 뒤 결정한다(속도 실험과 제품 정책 변경을 분리).
- [ ] 미세조정 어댑터는 출력 형식·말투 제어나 프롬프트 축소 용도로만 기대하고, 지식 보강은 다른 수단(검색·컨텍스트)으로 한다.

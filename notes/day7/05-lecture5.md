### 핵심 요약 (3~5줄)
- 모델은 대부분 100만 토큰 컨텍스트를 지원하지만 GPU는 전력·서버실 용량·HBM 수율(강사 기억 40~50%) 때문에 늘리기 어렵다. 소프트웨어로 줄일 만큼 줄였다면 남은 길은 **KV 캐시를 GPU 밖에 두고(나아가 공유하고) 불러오는 것**이다.
- 다시 계산(prefill 재실행)은 "엄청난 비효율"이므로 불러오는 편이 낫고, 관건은 **어디에 저장하느냐**다. 백엔드 캐시처럼 핫/콜드로 나눠 **HBM → CPU DRAM → NVMe SSD → (원격 저장소: "여기까지 가면 이미 망한 거")** 순으로 내린다.
- vLLM은 KV 커넥터와 kv-transfer-config로 외부 KV 관리를 붙일 수 있고, 대표가 **LMCache**(DRAM·디스크·최악엔 S3까지 관리)와 Moonshot AI(Kimi)의 **Mooncake**다. SGLang은 내부에 **HiCache**를 가진다. 오프로드는 **만능이 아니라 선택** — 꺼내 오는 시간이 생기는 대신 처리량이 는다.
- 이론(PART 7)을 마치고 PART 8(Kubernetes 확장·운영)은 참고 자료로 넘겼다. vLLM의 요즘 관심사로 RL 환경 데이터 생성과 **지식 증류**(단어사전 → 질문 수천 개 → Q&A 데이터셋)를 강사 경험과 함께 설명했다.
- 실습: `Day07_new`에 `.env`(OpenRouter API 키)를 만들고, **OpenAI·Anthropic·Google 금지, 비디오 금지, 이미지 3~4장, LLM은 200B 이하** 조건으로 **자유 챗봇**을 만들어 5시경 화면으로 공유한다(DeepAgents 권장, 필수 아님).

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**1. GPU 한계와 KV 캐시 외부화의 동기 (00:00~03:49)**
- "KV 캐시가 중요하다는 것을 앞에서 너무나 열심히 말씀을 드렸는데 사실상 장비가 가진 한계는 여전히 존재하고 있어요." 반면 모델들은 "대부분 100만 토큰을 일반적으로 지원"한다. 그 간극을 어떻게 메우는지 보자는 문제 제기.
- GPU를 무한히 늘릴 수 없는 이유:
  - **전력**: GPU 서버는 CPU 서버보다 전기 용량을 몇 배로 산정해야 하는데 서버실 상면은 그걸 받도록 설계되지 않은 경우가 대부분. 강사 경험담 — "GPU 한 대 올렸는데… 옆에 서버가 꺼졌대." 그래서 "기존에 있는 자원을 활용하자"는 생각을 하게 됐다.
  - **VRAM**: 화면 예시는 9B 모델(추정) — "이것만 해도 그냥 살벌합니다. VRAM을 너무나 많이 잡아먹고."
  - **HBM 수율**: DRAM을 쌓아 만들기 때문에 수율이 "40%, 50%? 이렇게 된다고 알고 있습니다"(강사 기억). "원래는 80%, 90%씩 생산하던 걸 반토막" → 많이 못 만든다.
- "지금까지 우리가 한 거는 … 소프트웨어적으로 줄일 수 있는 건 별의 별짓을 다 해서 줄였습니다." 더 짜낼 게 없으면 "GPU를 벗어날 수 있는 환경을 강구해야" 한다.
- 발상: KV 캐시는 "어차피 연산해놓고 그 값을 저장해놓는 레이어"이므로 "어디 딴 데 놓고 쓸 수 있지 않을까?", 딴 데 놓으면 공유 가능한 스토리지 레이어를 통해 "이쪽 GPU, 저쪽 GPU"가 "갖다 쓰는" 것도 가능하다.

**2. 다시 계산할까, 불러올까 — 저장 계층별 속도 (03:49~06:02)**
- "결국 다시 계산하는 건 엄청난 비효율이 발생을 하니까 당연히 어디선 불러오는 게 좋은데, 그러면 그걸 어디 저장소에 저장을 해둘까?"
- 화면 수치(가상 계산): CPU DRAM에 두었을 때 → 원격 저장소(네트워크가 들어가 "단위가 달라졌죠", 전용선 **50GB/s, 25GB/s** 가정) → 단순 이더넷("물론 이런 짓은 안 하겠지만") 순으로 느려진다.
- 원칙: "가장 빠른 레이어부터 차근차근 채워 나가는 거죠." CPU DRAM 다음 후보로 **RDMA**.
- **RDMA**: "공유 메모리를 GPU한테 준다고 보시면 됩니다… GPU가 다이렉트로 접근할 수 있는 그런 메모리 레이어를 설정"하는 기술. 대표가 **InfiniBand**. NVIDIA **DGX Station** 서버 랙을 사면 이런 세팅으로 오며, 화면 수치보다 훨씬 빠르다고 함.

**3. KV 캐시 계층화 — 핫과 콜드 (06:02~08:40)**
- "일반 서버의 백엔드의 서버의 캐시에서 구분하듯이 얘도 똑같이 구분을 하는 겁니다."
- 지금 당장 쓸 것은 **HBM**(GPU와 가장 가까운 곳), 아닌 것은 레이어를 조금씩 낮춘다. 원격 저장소까지 가면 "이미 망한 거예요… 여기까지 갈 이유는 거의 없으신데", 현실적으로는 **CPU DRAM도 괜찮고 NVMe SSD도 "나름 나쁘지는 않습니다."**
- 앤트로픽 프롬프트 캐시(5분·1시간) 저장 위치 — **강사 추측**: HBM에 다 감당할 수는 없으니 내려 둘 것이고, 5분짜리는 가까운 곳에, 1시간짜리는 "1, 20분 정도는 여기 CPU 디램에 좀 유지하지 않을까요? 그러다가 그게 지나가면 여기 내려놨다가 호출 오면 살아있으면 부르고 아니면 날려버리고 이런 컨트롤러가 또 있겠죠." 강사 본인이 "어디도 밝혀진 바가 없지만"이라고 전제했다.
  - (공식 문서 확인: 5분 기본, 1시간은 `"cache_control": {"type": "ephemeral", "ttl": "1h"}`로 지정. 저장 계층은 문서에 없고, ZDR 항목에 "KV cache representations and cryptographic hashes are held in memory for the cache TTL"이라는 문장만 있다 — https://platform.claude.com/docs/en/build-with-claude/prompt-caching) → 계층별 배치는 **미확인**(강사 추측).

**4. vLLM의 KV 커넥터와 LMCache·Mooncake·HiCache (08:40~10:53, 12:01~15:35)**
- vLLM은 "KV 캐시를 외부에서 관리할 수 있도록 하는 매니저 서비스를 제공". 엔진이 (실제 코드 함수로) "외부 저장소에 이 요청에 토큰이 있냐, 있으면 몇 개 있냐" 묻고, GPU 블록에 넣어야 하니 가져와서 "부어놓고 계산"하는 과정을 엔진 설정으로 넣을 수 있다.
- 전송 계층은 **kv-transfer-config**(전사 "KV 캐시 트랜스퍼 컨피드" → 추정 보정)로 지정하며 여러 커넥터 중 고른다. 기본 커넥터 형태는 vLLM이 제공.
  - (공식 문서 확인: `KVTransferConfig(kv_connector="LMCacheConnectorV1", kv_role="kv_both")`, CLI는 `--kv-transfer-config '{"kv_connector":"LMCacheConnectorV1","kv_role":"kv_producer", ...}'` 형태 — https://docs.vllm.ai/en/latest/examples/disaggregated/lmcache/ . 강의에서 이 설정값을 구체적으로 보여 주지는 않았다.)
- **LMCache**: "KV 캐시를 관리하는 라이브러리". vLLM에서 KV 캐시 매니저를 LMCache로 세팅하면 외부 관리를 위임하고, LMCache는 "D램부터 디스크, 아니면 정말 최악인 경우 S3 이런 원격 저장소까지" 관리한다. "S3 가면 안 됩니다." 저장·조회도 vLLM처럼 잘라서 저장하고 잘라서 불러오며, 엔진 코어가 "야 있냐?" 하면 "저 갖고 있습니다" → 보내 주고, 없으면 지나간다. **서버 형태로도 세팅 가능**.
  - (공식 문서 확인: LMCache 저장 백엔드에 CPU RAM, Local storage, Filesystem, S3, Mooncake Store 등이 있다 — https://docs.lmcache.ai/kv_cache/storage_backends/index.html)
  - "전사급 서빙을 하시지 않는" 한 관심 없을 라이브러리 — "우리 회사급 정도에서 서빙하시는 분이 아니면", 그만큼 부족한 경우가 잘 없으니까. 반대로 규모가 커지면 "무조건 부족해지기 때문에" 고려하게 된다.
- **Mooncake**: "키미라는 모델을 만드는 문샷 AI"가 회사 이름을 넣어 만든 자체 KV 캐시 관리 서비스를 커넥터로 녹여 놓았다. 개념은 비슷하되 **RDMA처럼** 운영 — CPU DRAM을 쓰면 "OS 타고 CPU 타고 메모리 할당 받아서… PCI 뭐 또 타야 되고 중간중간에 거친 친구들이 많"은데 "다 갖다 버리고 바로 우리 메모리랑 다이렉트로 소통"하는 방식. 강사는 "까보진 않고 써보지도 않아서 이론적으로만" 안다고 함.
  - (공식 문서 확인: "Mooncake is the serving platform for Kimi, a leading LLM service provided by Moonshot AI." — https://github.com/kvcache-ai/Mooncake ; vLLM MooncakeConnector 기본 프로토콜 `rdma` — https://docs.vllm.ai/en/latest/features/mooncake_connector_usage/)
  - (저장소 확인: P/D 분리 장에 "NIXL·Mooncake 등 connector의 지원 조합과 설치 조건을 확인합니다." — `Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf` p.67)
- 계층별 솔루션 정리: "대부분은 VLLM을 쓰시게 되면 LMCache를 같이 가져가는 것 같아요. SGLang은 **HiCache**라고 하는 걸 내부적으로 가지고 있더라고요."
  - (공식 문서 확인: HiCache는 RadixAttention 프리픽스 재사용을 GPU → 호스트 메모리 → 분산 저장소로 확장, `--enable-hierarchical-cache` 등 — https://docs.sglang.io/advanced_features/hicache_design.html)

**5. 오프로드의 대가와 운영 경험 (10:53~15:15)**
- "하지만 이런 단점이 있습니다. TTFT(추정)가 22배까지 떨어져요. 어쩔 수 없어요. 바로 옆에 두는 것보다는 당연히 느립니다. 그 대신에 처리량은 좀 늘어나고요." → "**만능 해결책이 아니기 때문에 선택을 해야 됩니다.**"
  - **미확인**: 전사 "KFT"를 TTFT로 추정 보정. vLLM 공식 블로그는 CPU에서 KV를 불러오면 TTFT가 **2~22배 줄어든다(개선)**고 적었고, 이후 개정판은 0.12.0 기준 최대 4배 TTFT 감소·최대 5배 처리량으로 적었다(공식 문서 확인: https://vllm.ai/blog/kv-offloading-connector , https://vllm.ai/blog/2026-01-08-kv-offloading-connector). 강사는 같은 22배를 "단점(느려짐)"으로 말해 **방향이 다르다**. 공통점은 "주된 이득은 처리량"이라는 점.
  - (저장소 확인: "KV tiering / offload — 긴 prefix를 계층 간 재사용할 때 — 새로 생기는 비용: lookup·transfer·eviction", "용량 확대나 자원 효율의 개선을 steady-state decode TPS 향상으로 잘못 표현하지 않습니다." — `Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf` p.68)
- 강사 추측: 앤트로픽 요청이 "이걸 꺼내서 연산해서 다시 오기까지 시간이 꽤 걸려요… 요즘 점점점점 요청이 느려지는 이유도 이런 것도" 한몫. 캐시 1시간 내에 보내면 바로 계산될 것 같지만 "느리게 보낼수록 점점 더 느려져요"(더 아래 계층에서 꺼내므로).
- **운영 경험**: LMCache를 쓰면 "더 머리가 아파지죠. 디스크 관리나 램 관리를 계속 해줘야 됩니다." 그래서 GPU를 4장·8장 꽂는 서버를 신청할 때 **램을 무조건 풀뱅크로 — 768GB를 꽉 채우거나 더 꽂을 수 있으면 더** 꽂아 달라고 했다. "조금만 서빙하는 사람 수가 많아지면 그런 문제가 생기기 때문에 요 라이브러리는 거의 필수로 가지고 들어왔던 경험이 있습니다."

**6. 클러스터 KV 공유·확장(PART 8)은 참고 자료 (15:35~17:04)**
- 클러스터 단위 KV 공유는 "더 복잡한 내용"이라 Kubernetes 환경 운영자에게 도움이 되도록 뒤에 넣었다. Kubernetes 위 멀티 GPU 노드에서 앞의 병렬화 전략을 어떻게 고려할지 — "거의 경험한 사람들이 적더라고요." 대량 인퍼런스 운영자는 국내에 드물고(SKT는 노드를 꽤 운영) 해외에 많다.
- 강사 멀티노드 경험은 "4대 노드에 8장씩" = 8×4=32(추정)가 최대. 그래서 "참고삼아" 넣었다.
- 맨 뒤 자료는 "요즘 VLLM이나 이런 인퍼런스 엔진이 집중하고 있는 내용"이며 "스쳐 지나가면서 보세요."

**7. RL 환경 데이터 생성 (17:11~19:25)**
- 강화학습은 "주어진 환경을 일단 설정을 하고 그 환경에 맞는 데이터를 생성해야" 하고 그다음 학습한다. vLLM은 로컬 모델을 서빙하니 **그 환경에 맞는 데이터를 출력해 주는 역할**을 한다 — 챗봇 운영을 넘어서는 용도.
- 사례: 스타트업들이 제조업처럼 작업 환경이 고정되고 로봇·센서 데이터가 나오는 분야에서, 아웃라이어 데이터도 생성하고 "통계적 표준에 가깝게" 데이터를 대량으로 뽑아 개별 **피지컬 AI** 모델에 공급하는 비즈니스를 한다. 이때 모델이 "요즘 좀 크지 않아도" 된다.
- vLLM도 자체적으로 RL 환경에 대응하는 기능(서빙 성능 극대화 목적)을 지원한다고 언급.
  - (저장소 확인: "Sleep mode — 유휴·RL 단계 전환·모델 전환" — `Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf` p.68. 강의에서 Sleep mode 자체는 말하지 않았다.)

**8. 지식 증류 — 강사가 vLLM을 가장 많이 쓴 일 (19:25~23:14)**
- "저는 지식 증류를(추정) 많이 했었거든요." 모델에서 특정 지식을 추출·생성해 다른(작은) 모델을 학습시켜 성능을 끌어올리는 작업. "API도 당연히 증류 해봤죠."
- 절차(강사 방식):
  1. 분야를 정한다 — 예: 금융투자 → 하위 섹션 "매크로(거시경제)". 모델이 그 데이터 외에 다른 얘기를 하지 않게 만든다.
  2. 모델이 그 분야에 대해 "할 수 있는 말을 다 뽑아내" **단어사전**을 만든다(프롬프트로 쭉쭉 뽑아내게 함).
  3. 단어사전으로 다시 모델에게 역으로 물어 문장을 만들게 하고, 강사는 주로 **질문을 수천 개** 만들어 넣고 답을 받아 **Q&A 데이터셋**을 만들었다.
  4. 분야를 넓혀 가며 "이 모델이 단어를 더 이상 말할 수 없을 때까지 계속 돌려요. 미친 듯이 돌려대는 겁니다."
- 검증은 "그렇게 많이 안 합니다" — 목적이 그 분야 지식을 늘리고 답하게 만드는 것이라서. 일반 키워드로 이야기하게 하면 프롬프트로 잡아낼 수 있어 특화용으로 뽑은 지식을 많이 썼다.
- "이걸 진짜 중국이 잘하죠… 코딩 작업에서 이걸 많이 뽑아내고 있죠." 예전에 **Mixtral / Mistral 8×7B** 같은 모델로 많이 돌렸다. "이런 RL 요즘 다시 각광을 받고 있는 것 같고요."

**9. 실습 규칙의 의도 — 로컬 모델 실전에 가깝게 (27:56~34:16)**
- 오늘은 "텍스트에 국한되지 않을" 실습. OpenRouter 모델에는 텍스트·이미지·비디오·스피치(TTS·STT) 등 다양한 타입이 있고, 로컬 모델도 LLM 서빙만이 아니라 스피치 모델이 많다는 점을 경험하게 하려는 것.
- LLM을 **200B 이하**로 제한한 이유: "좀 더 우리 로컬 모델의 실전에 가깝게 써보려고." 다만 너무 작으면 힘들어해서 Qwen3.8 27B(추정)로 고정하지는 않았다("그러면 아마 아무것도 안 될 겁니다"). 작은 모델로 서브 에이전트를 써 보는 "그런 도전 너무 좋습니다."
- "잘 만들었든 못 만들었든이 중요한 건 아니에요. 그 대신에 로컬 모델을 써본다라는 것과 다양한 모델을 좀 경험해본다."

### 강사 팁·주의사항
- KV 캐시는 **다시 계산하지 말고 불러온다**. 단, 가장 빠른 계층부터 채우고, 원격 저장소(S3)까지 내려가면 "이미 망한 거"다.
- 외부 오프로드는 **만능이 아니라 선택**이다. 꺼내 오는 지연이 생기고 처리량이 는다. 늦게 보낼수록 더 아래 계층에서 꺼내 더 느려질 수 있다.
- LMCache는 사내 전사급 서빙 규모에서 "거의 필수"였지만, 쓰면 **디스크·RAM 관리 부담**이 늘어난다. GPU 서버를 신청할 때 **RAM을 풀뱅크(768GB 이상)로** 요청했다.
- 앤트로픽 프롬프트 캐시의 내부 배치에 대한 말은 **강사 추측**이다("어디도 밝혀진 바가 없지만").
- Mooncake는 강사가 직접 써 보지 않고 이론으로만 아는 내용이다. PART 8(Kubernetes 멀티노드)은 강사 경험(최대 4노드×8장)도 제한적이라 참고 자료다.
- 증류는 모델이 "더 이상 말할 수 없을 때까지" 돌리고, 강사는 검증을 많이 하지 않았다(특화가 목적이라서).
- 실습 키: 금지 모델·비디오를 쓰면 **키를 막는다**. 이미지·STT/TTS는 적정 범위로. 비용 제약을 지켜야 프로젝트 비용을 지원받을 수 있다.
- 결과물의 완성도보다 **로컬급(200B 이하) 모델과 다양한 모달리티 모델을 경험**하는 것이 목적. 대신 **UI는 반드시** 있어야 공유할 수 있다.

### 실제 프로젝트에 적용할 체크리스트 (- [ ] 행동 지침, 특정 프레임워크에 묶이지 않는 원칙 위주)
- [ ] 하드웨어(GPU·VRAM)를 늘리기 전에, 소프트웨어로 줄일 수 있는 것(양자화 등)을 다 했는지 먼저 확인한다.
- [ ] 다시 계산할 비용이 큰 중간 결과(긴 prefix의 KV 등)는 재계산하지 말고 저장해 두었다가 불러오는 구조를 검토한다.
- [ ] 캐시를 핫/콜드로 나누고, 가장 빠른 계층부터 채운다. 원격 저장소까지 내려가는 경로는 예외로 취급한다.
- [ ] 오프로드·계층화는 지연(첫 응답 시간)과 처리량의 절충임을 명시하고, 어느 쪽을 위해 도입하는지 정한 뒤 선택한다.
- [ ] 외부 캐시 계층을 도입하면 디스크·RAM 관리 업무가 생긴다는 것을 운영 계획과 서버 사양(RAM 여유)에 반영한다.
- [ ] 외부 서비스 내부 동작(예: 프롬프트 캐시가 어디에 저장되는지)에 대한 추측은 사실과 구분해 기록하고, 공식 문서로 확인된 것만 설계 근거로 쓴다.
- [ ] 벤치마크 배수(예: "22배")를 인용할 때는 방향(개선/악화), 측정 조건, 버전을 함께 확인한다.
- [ ] 특정 분야 데이터셋이 필요하면 "분야 정하기 → 용어 사전 추출 → 질문 대량 생성 → 답 수집" 순서로 증류 파이프라인을 설계하고, 검증 수준을 의도적으로 정한다.
- [ ] 실습·프로젝트용 API 키는 사용 가능한 모델·모달리티·수량(예: 이미지 장수) 제한을 문서(task 파일)로 먼저 정하고 공유한다.
- [ ] 비싸고 실패 시 비용이 그대로 사라지는 호출(예: 비디오 생성)은 기본 차단하고, 무한 반복 테스트를 하지 않는다.
- [ ] 운영 환경에 가까운 크기의 모델(예: 200B 이하)로 먼저 만들어 보고, 너무 작아서 아무것도 안 되는 선은 피한다.
- [ ] 데모·공유가 목적이면 허술하더라도 화면으로 보여 줄 UI를 반드시 만든다.

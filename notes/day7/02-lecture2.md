## 7일차 2강 — 양자화와 텐서 패럴렐: GPU 한 장을 쥐어짜고, 못 올리면 나눈다

> 출처: 「7일차 2강 다시보기 (보정)」(whisper 전사 921줄 + 분석, 47:00), 「7일차 2강 장표」(13장). SDS AX Advanced · 2026-11-10 오전(10시~11시, 1강에 이어짐).
> 이번 강도 교재 PDF가 아니라 판서·Hugging Face 화면·Claude에게 시킨 계산으로 진행했고, 끝에서 "11시까지 쉬셨다가 이제는 **이론 자료를 토대로**" 이어 간다고 했다. 대응 저장소 폴더는 `Day07/`이며, 강의 개념과 겹치는 교재 `Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf` 쪽만 아래에 표시했다.

### 핵심 요약 (3~5줄)
- 데이터 타입은 **모델 웨이트**와 **KV 캐시** 두 곳의 용량을 정한다. **양자화** = "양자역학 그런 내용 전혀 아니고요. 이 데이터의 타입을 줄여나가는 겁니다."
- H200 한 장(가용 130GB, 강의 수치)에서 Qwen3.8 27B: BF16 웨이트 56 + KV 30 = 86GB → 1개, **FP8 웨이트** 28 + KV 30 = 58GB → 2개(116GB), **KV 캐시도 FP8** 28 + 15 = 43GB → **3개**. 웨이트만 FP8로 줄이고 KV를 16비트로 두면 연산 결과를 "두 배 뻥튀기해서 저장"하는 낭비다.
- 한 장에 못 올리는 모델: **GLM 5.3**(753B)은 처음부터 **FP8로 구워져** 웨이트 약 **756GB**, 최대 **100만 토큰(1,048,576)**. Claude에게 계산시킨 결과 100만 토큰 KV는 FP8 약 **50GB**(BF16 약 97GB), 합계 약 **806GB**.
- 모델을 GPU에 나눠 올리는 것이 **텐서 패럴렐(TP)**이며, 레이어 숫자(헤드딤 192 등)가 나누어떨어져야 하므로 한 서버의 GPU는 **1·2·4·8장(2의 제곱수)**으로 쓴다. **DP·PP는 학습에서 의미가 크고 서빙에서는 잘 쓰지 않는다**(강사).
- 모델을 쪼개도 KV는 GPU마다 저장해야 해서 **H200 8장으로도 100만 토큰 하나를 못 받는다**(GPU당 KV 여유 30GB 미만). B200 8장에서야 1건, B300은 약 3배. 웨이트는 더 줄이기 어려워 모델사들은 **KV 캐시 절감**, **NVFP4·MXFP4** 같은 4비트 포맷, **DRAM·NVMe 저장**을 연구한다 — "왜 KV 캐시가 그토록 난리인지"가 오늘의 결론.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**0. 수업 전 잡담: Claude 인증 시험 (00:03~03:03)**
- 수강생이 보는 사내 "AI 어드밴스드" 시험 이야기에서 Claude 인증(Certified) 시험으로 넘어감: 디벨로퍼·아키텍트·프로페셔널 등 여러 단계, 외부 판매 파트너십 자격과 연결, 응시료(전사상 175·125달러), 영어 객관식, 문제 수가 많고 시간이 짧다는 경험담. 강의 내용과 무관하며 시험 이름·가격은 확인하지 않았다.

**1. 복습: 데이터 타입과 정확도, 반복 출력의 이유 (03:08~)**
- "이게 사실 **서빙의 핵심**이어서" 가장 컨디션 좋을 때 다룬다.
- 데이터 타입 = 표현 가능한 숫자 범위의 넓고 좁음 → 정확도가 떨어진 숫자로 **누적 연산** → 체감할 정도로 성능 하락.
- 반복 출력(했던 말 또 하기, 같은 단어 반복)을 정확도 관점에서 설명: 벡터가 레이어를 차근차근 지나 **마지막 레이어**에서 머신러닝 모델들은 주로 **softmax 같은 연산**으로 역치를 넘었는지(1/0) 분류한다. 누적 오류로 결과가 "어느 한쪽으로 수렴"하면 비슷한 것이 계속 반복된다. 요즘 로직은 많이 발전했지만 "그 값을 넘었어 안 넘었어를 판단하는 그 로직 이후에" 이런 우려가 생긴다 → "마지막에 얘 때문에 영향을 크게 끼치는 거죠."

**2. 데이터 타입의 두 가지 영향: 웨이트와 KV 캐시 (06:00~)**
- 데이터 타입은 **① 모델 웨이트**(Hugging Face 용량으로 확인, BF16 기준 56GB)와 **② KV 캐시(컨텍스트 윈도우)**에 영향을 준다.
- 1강 복습: H200(호퍼 아키텍처, 지금은 구매가 어렵다) VRAM **144GB** 중 현실적으로 **130GB** 사용 → 단순 계산으론 65B가 올라갈 것 같았지만 컨텍스트 윈도우를 빼먹어 불가능했다. 27B 하나 올리는 것도 "생각보다 쉽지 않구나". 그러면 "힐리안(수천억)급 모델은 이거 어떻게 올리지?"
- 강조 이유: GPU 한 장이 "**한 7~8천만 원**" — "8천만 원짜리 GPU 사가지고 27B 모델 돌린다 그러면 이제 열받죠." 그러니 **성능 하락은 최저로 줄이면서** 운영 가능한 형태로 두 값을 줄여야 한다.
  - (공식 문서 확인: https://www.nvidia.com/en-us/data-center/h200/ — H200 메모리는 **141GB**. 강의 144GB와 다름 → 미확인. 계산은 강의 수치 그대로.)

**3. 양자화 ①: 웨이트를 FP8로 (08:24~)**
- "양자화라는 건 말이 멋있어서 … 양자역학 그런 내용 전혀 아니고요. **이 데이터의 타입을 줄여나가는 겁니다.**"
- BF16이 베이스라인. 8로 줄여 본다 → **FP8** → 웨이트 **나누기 2** → **28GB**. "이 나누기 2라는 게 우리한테는 이제 중요했죠."
- 다시 계산: 모델 하나 = 웨이트 28 + KV 약 30 = **약 58GB** → ×2 = **116GB** < 130GB → "1개의 GPU에 모델 2개" 가능. "그리고 실제로 가능합니다." (1강에서 KV 여유로 주던 44GB를 "주지 말고 서로 반띵".)

**4. 양자화 ②: KV 캐시도 8비트로 (12:30~)**
- 질문: 웨이트를 FP8로 줄였는데 KV 30GB는 "계속 그대로여야 되냐?"
- BF16 모델이 BF16인 이유: **중간 레이어 모두가 BF16**이고 16비트끼리 연산했으니 결과도 16. attention 연산은 **QKV**라는 세 인자가 함수에 들어가 결과가 나오는 것("굉장히 쉬운 수학")인데, 이 값이 다 16비트 연산이었다.
- 웨이트를 8비트로 바꾸면 "**연산 결과가 8비트로 떨어진다**" — "양자화 fp8은 연산 결과도 fp8".
- 그런데 KV 캐시 영역은 "아직 아무 설정을 안 했으니까" **여전히 16비트**로 저장 → "이런 멍청한 짓을 왜 하고 있는 거야?" "**저장 결과를 계속 두 배 뻥튀기해서 저장하고 또 꺼내와서 내가 다시 써야 될 때는 다시 8이어야 되거든요.**" 두 배 연산 자체는 어렵지 않지만 **저장 용량이 문제**.
- 그래서 "모델의 웨이트 말고 **KV 캐시도 8비트로 저장**을 할 수 있습니다." → KV 30 ÷ 2 = **15GB** → 모델 하나 **약 43GB** → **3개** 가능(10% 버퍼가 있어 실제로 3개 가능).
- 욕심: "약간의 성능을 감수하고 **8비트 2개, 4비트 하나**를 운영하면 어떨까요?"(수치 계산은 생략) — "1개의 GPU를 이렇게 쥐어 짜내서 이 정도까지 할 수 있구나."
  - (저장소 확인: `Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf` p.49 "Weight와 KV Quantization — 'INT4 모델'이라고 해서 KV Cache도 INT4라는 뜻은 아닙니다." 웨이트 dtype과 KV dtype이 별개 설정이라는 강의 설명과 같다. p.50 "FP8 KV Cache" 예시 `--kv-cache-dtype fp8`. 강의에서는 플래그 이름을 말하지 않았다.)
  - (공식 문서 확인: https://docs.vllm.ai/en/latest/features/quantization/quantized_kvcache.html — `--kv-cache-dtype fp8`(값: `auto`, `fp8`, `fp8_e4m3`, `fp8_e5m2`); 기본 `auto`는 "will use model data type"(https://docs.vllm.ai/en/latest/configuration/engine_args.html). 보정 없이 쓰면 스케일이 1.0이고, 최고 품질에는 llm-compressor 보정을 권장한다.)
  - (교재와의 차이: 같은 PDF p.50은 "BF16 2 bytes → FP8 1 byte. **Raw KV payload 기준 절반이며 전체 메모리 절반은 아닙니다**"라고 적는다. 강의의 "KV 30→15, 모델당 43GB, 3개"는 단순 계산이며 실제 수용량은 런타임 오버헤드·보정 여부에 따라 다르다 → 미확인.)

**5. 한 장에 못 올리는 모델: GLM 5.3 (18:03~)**
- "회사들에서 많이 쓰고 있는 **GLM 모델**"이 예시로 적절. **GLM 5.3**, 파라미터 "753밀리언"(문맥상 **753B**). Hugging Face에 BF16과 **FP8**이 표기 — FP8 뒤의 숫자는 GPU 스펙(엔비디아 스펙)에 맞춘 것이니 앞 숫자만 기억. "플로팅 포인트 8까지도 **공식 지원**을 하네요."
- 753B인데 용량이 **756GB** — "왜?" → "**모델 자체가 FP8에 맞게 구워져서 나왔어요.**" 애초에 학습(구울) 때부터 16비트는 "너무 빡세다" 해서 **8비트에 맞게** 구웠다. 기본 데이터 타입이 FP8. (BF16이었다면 약 1.4TB였을 것.)
- 저장소에는 가중치가 **141개**로 쪼개져 있다(저장소 용량 때문). **tokenizer config**의 max length가 **100만** → **1,048,576 토큰**.
- KV 캐시 계산은 "수식이 좀 복잡해요"("이거 계산하라 그러면 저도 못합니다") → **Claude에게 질문**. Claude가 GLM 5.3 아키텍처 문서, **78개 어텐션 레이어**, official `config.json`, **vLLM 레시피** 페이지, Hugging Face를 찾아 읽고 계산.
- 결과(강사가 화면에서 읽음): **약 806GB**, 런타임 오버헤드로 **KV 약 50GB**를 추가해야 함. 100만 토큰당 KV는 **BF16이면 약 97GB, FP8이면 약 50GB**.
  - (저장소 확인: KV 메모리 공식 `Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf` p.25 "Mₖᵥ ≈ 2 × B × L × T × nₖᵥ × dₕ × b … 실제 config의 num_key_value_heads를 확인합니다." 강사는 공식을 풀지 않고 Claude 계산 결과만 읽었다.)
- 강조 이유: H200 한 장(144GB)으로는 800GB대 모델을 절대 못 올린다 → GPU를 **묶어야** 한다.

**6. GPU 대수는 왜 2의 제곱수인가 (27:13~)**
- ×1, ×2, ×4 안 됨(계산상) → ×8. 그런데 1~8 중 "**현실적으로 불가능한 숫자들**"이 있다: **3장, 5·6·7장은 설정할 수 없다**(강사). "한 개의 서버를 기준으로 GPU는 한 장, 두 장, 네 장, 여덟 장" — "**2의 제곱수로만 존재할 수 있고요.**" (중간 숫자를 써도 되지만 "효율적으로 쓰지를 못해요".)
- H200 8장 = 144 × 8 → "**1.1TB**"(강사는 1142GB로 읽음) → GLM 753B 모델 **1개는 가능, 2개도 안 됨**. 100만 토큰 하나 지원하면 806GB → 300GB 남짓 남아 아깝다.
- 이유(질문 후 설명): **모델을 나눠야 해서**. GPU 한 장에 다 못 올리니 레이어를 나눠야 하는데, 레이어 구성 숫자 중 **헤드딤(head dim)**이 중요하다 — 예: **192**. 이 수가 GPU 수(2의 제곱수)로 **나누어떨어져야** 하고, 나머지가 생기면 "계산이 안 됩니다. 그러니까 GPU에 나눠 놓을 수가 없어요." 계산기 시연: 192 ÷ 2 = **96**. 딱 떨어지는 수로 나눠야 레이어를 "적재적소에 딱딱딱딱 나눠서 저장"하고 서로 연산할 수 있다.
  - (공식 확인: vLLM은 "Total number of attention heads (X) must be divisible by tensor parallel size (Y)" 오류를 낸다 — https://github.com/vllm-project/vllm/discussions/1041. 공식 기준은 **어텐션 헤드 수(및 KV 헤드 수)가 TP 크기로 나누어떨어질 것**이며, "2의 제곱수만 가능"이라는 규칙은 공식 문서에서 찾지 못했다. 강사가 말한 192가 head_dim인지 헤드 수인지도 화면 미확인 → 미확인. https://docs.vllm.ai/en/latest/serving/parallelism_scaling.html 은 "The common practice is to set the tensor parallel size to the number of GPUs in each node"라고 적는다.)

**7. 텐서 패럴렐(TP), 그리고 DP·PP (33:52~)**
- 모델의 레이어를 GPU에 나눠 놓는 것 = "**이걸 우리는 텐서 패럴렐이라고 부릅니다.**" Hugging Face에서 모델 가중치가 **safetensors**로 나뉘어 있듯이, "텐서(모델의 가중치)를 GPU에 나눠 놓겠다" → **Tensor Parallel**, 줄여서 **TP**.
- 반대 질문: 모델 하나가 GPU 한 장에 다 들어가는데(1 GPU 1 모델), 서버의 2·4·8장을 묶어 연산 효율을 높일 수 없을까? → **데이터 패럴렐(DP)**: 데이터를 모아 각 모델 사본에 나눠 주는 것, "사실상 그냥 **병렬처리**". "**잘 안 써요**" — 요즘 모델이 워낙 커서 그런 경우가 없고, "학습할 때나 의미가 있는데".
- 비슷한 용어 **파이프라인 패럴렐(PP)**도 있지만 "**모델을 서빙할 때 얘네들을 잘 쓰지 않아요.**" 모델이 계속 커지기만 해서 모델을 GPU에 나눠 놓는 게 중요하지 데이터 병렬처리는 잘 하지 않는다. 공부하다 보면 DP·PP가 나오는데 학습 때는 고려해야 하지만 서빙에서는 "잘 고민하지도 않습니다".
  - (저장소 확인: 용어 `Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf` p.14 "TP · PP · DP — Tensor·Pipeline·Data: 가중치·레이어·요청 중 무엇을 나눌지", p.20 "TP / replica — 처리량을 올릴 때: replica 수를 늘림 / 지연을 줄일 때: TP 크기를 늘림".)
  - (공식 문서와의 차이: https://docs.vllm.ai/en/latest/serving/parallelism_scaling.html — 단일 노드 다중 GPU에 맞는 모델은 TP, 여러 노드면 "Set `tensor_parallel_size` to the number of GPUs per node and `pipeline_parallel_size` to the number of nodes", NVLink가 없으면 PP를 권한다고 적는다. 또 MoE 모델에 "Data Parallel attention with Expert or Tensor Parallel MoE layers" 조합을 지원한다. 즉 공식 문서는 서빙에서도 PP·DP를 쓰는 경우를 제시한다 — 강의의 "서빙에서는 잘 안 쓴다"는 단일 노드 기준 강사 견해로 둔다 → 미확인.)

**8. GPU당 KV 여유와 100만 토큰의 비용 (37:54~)**
- 웨이트를 8장에 잘 나눴다. 그럼 한 장이 차지하는 건 단순히 ÷8? "**그렇진 않아요.**" Claude 계산의 "**8 GPU당 약 144.5GB**"는 KV 캐시 전체를 고려한 806GB를 8개로 쪼갠 결과.
- 결론: **H200 8장** → GPU당 KV 여유 **30GB도 채 안 되고**, "100만 토큰 쓸 수 없어요". "이 비싼 장비 H200 8장이나 들어간 장비에 GLM 5.3 모델 하나도 **100만 토큰으로 서빙이 안 되는 겁니다.**"
- 장비를 올림: **블랙웰 B200 8장** → 한 장당 메모리 **180GB**, KV 여유 **60GB** → 50GB를 넘으니 100만 토큰 **하나**를 처리. **B300**(강사: H200의 두 배) → 100만 짜리 요청을 **약 3배** 받을 수 있다. "진짜 비싸요."
- 왜 실제 계산보다 더 차지하나: 모델을 쪼개 놓으면 "**그 모델이 계산한 결과물까지 개별 GPU에 저장을 해놔야 돼서**". 그래서 100만 토큰 요청 하나에 GPU당 약 145GB가 필요했고 H200(144GB)으로는 불가능 — "8장짜리 한 개의 노드로 볼 때리는 겁니다."
  - (공식 문서 확인: DGX B200 "1,440 GB total" GPU 메모리 — https://www.nvidia.com/en-us/data-center/dgx-b200/ (8장 기준 장당 약 180GB는 나눗셈 결과, 단일 B200을 192GB로 적는 자료도 있음). DGX B300 "Total GPU Memory 2.1 TB" — https://www.nvidia.com/en-us/data-center/dgx-b300/ (장당 수치·메모리 종류는 페이지에 없음). "B300 = H200의 두 배"는 강사 표현으로 둔다 → 미확인.)

**9. 모델사들이 KV 캐시에 매달리는 이유와 연구 흐름 (41:05~)**
- "왜 모델사들이 KV 캐시 줄였다라고 논문 내고 난리를 피우는" 걸까: "**어차피 웨이트는 줄일 수가 없어요.**" 웨이트를 더 낮추면 계산 효율(정확도)이 계속 떨어지므로, 그나마 컨트롤할 수 있는 KV 캐시를 "별짓을 다해서" 낮춘다.
- 수요 측면: 사람들이 모델이 기억할 용량을 계속 늘려 달라고 한다 — "RAG 쓰기 싫어요. 그냥 모델이 다 집어넣게 해주세요." 100만 토큰도 "될까 말까인데 왜 100만 토큰 안 돼요" — 이런 히스토리가 숨어 있었다.
- 그래서 vLLM 등 요즘 서빙 엔진들이 **KV 캐시에 초점**을 맞춘다 — "우리가 건드릴 수 있는 영역이어서".
- 모델사는 웨이트도 건드린다: FP8보다 더 낮춰도 성능이 안 떨어지게 하는 연구.
  - **NVFP4**: 엔비디아가 FP4에서 따로 만든 양자화 포맷 — "16비트의 정밀도와 4비트의 성능으로 학습을 가속하고 서빙도 가속".
  - **GPT-OSS**: 중간중간 레이어를 4비트 레이어로 — OpenAI가 따로 낸 **MXFP4** 양자화 방식으로 "학습을 한 거예요"(강사 표현).
  - (공식 문서 확인: NVFP4 — "NVFP4 is an innovative 4-bit floating point format introduced with the NVIDIA Blackwell GPU architecture."(E2M1, 16값 블록마다 FP8 E4M3 스케일 + 텐서별 FP32 스케일) https://developer.nvidia.com/blog/introducing-nvfp4-for-efficient-and-accurate-low-precision-inference/ . gpt-oss — "The models were post-trained with MXFP4 quantization of the MoE weights", 나머지 텐서는 BF16 https://github.com/openai/gpt-oss . 강의의 "MXFP4로 학습"은 공식 표현("post-trained … MoE weights")과 다르다 → 미확인.)
  - (저장소 확인: `Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf` p.51 "NVFP4 / MXFP4 — 더 낮은 정밀도 저장·연산 — 서로 다른 format · GPU별 지원".)
- 모델사의 두 방향: **① 웨이트를 4비트까지**, **② KV 캐시를 효율적으로 줄이고, 줄일 수 없다면 어딘가에 적절히 저장**.
- 마지막 생각: GPU VRAM(HBM)은 너무 비싸다 → **DRAM**, 또는 **SSD**(하드디스크는 너무 느려 안 됨, **NVMe** 정도만 허용)에 저장할 수 없을까? → "물론 성공했어요. 하고 있고요." VRAM과 다른 곳에 조금씩 나눠 저장하는 기술까지 "하나의 흐름으로" 살펴봤다.
  - (저장소 확인: `Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf` p.68 "KV tiering / offload — 긴 prefix를 계층 간 재사용할 때 — 새로 생기는 비용: lookup·transfer·eviction".)
- 근본 해결은 **HBM 용량 증가** — 하드웨어는 빨리 발전하지 않는다("삼성전자가 더 힘을 내줘야 되는데 하이닉스랑 더 HBM5도 나오고"). 강사: B300에도 **HBM4**가 들어가고, 다음 아키텍처 **베라 루빈(Vera Rubin)**에는 HBM4 이상의 더 좋은 메모리가 들어가 한 장이 서빙할 수 있는 VRAM 용량이 늘어난다고 한다.
  - (확인: B300 메모리 종류는 공식 페이지에 명시가 없고, 보충 자료(tomshardware)는 B300을 HBM3e 288GB로 적는다 → 강의의 "HBM4"는 미확인.)
- 정리: "왜 KV 캐시가 그토록 난리인지, 우리는 왜 그걸 고려해서 **에이전트를 만들었어야 되는지** 이 모든 것들이 사실 다 맞물려 있는" 것. 멀티 GPU·멀티노드는 부담스러워 실습하지 못하지만, KV 캐시가 어때야 하는지를 수치로 알아봤다. "큰 그림의 정리"를 마치고 11시 이후 이론 자료로 이어 간다.

### 강사 팁·주의사항
- 비싼 GPU(한 장 7~8천만 원)는 **쥐어짜서** 써야 한다 — 성능 하락은 최소화하면서 웨이트와 KV를 함께 줄인다.
- 웨이트만 양자화하고 KV를 16비트로 두는 설정은 "바보 같은 짓" — **웨이트 dtype과 KV dtype을 함께 맞춘다**(KV는 따로 설정해야 바뀐다).
- 모델 용량이 파라미터 수와 안 맞으면(753B인데 756GB) **배포 데이터 타입**(처음부터 FP8로 학습·배포)부터 의심한다.
- KV 캐시 계산은 수식이 복잡하니 **Claude 같은 도구에 config·레시피를 찾아 계산**시키되, 결과 수치를 직접 읽고 검토한다.
- 한 서버의 GPU 대수는 1·2·4·8로 구성한다(나누어떨어지지 않으면 모델을 나눌 수 없다). 3·5·6·7장 구성은 피한다.
- 서빙에서 고민할 병렬화는 **TP**. DP·PP는 공부하다 나와도 서빙에서는 잘 고민하지 않는다(강사 견해 — 공식 문서는 다중 노드에서 PP, MoE에서 DP 조합을 제시한다).
- 모델을 쪼개도 **KV는 GPU마다** 저장된다 — "실제로 우리가 계산한 것보다 이 GPU 용량을 더 많이 차지해요."
- 100만 토큰 컨텍스트는 H200 8장 노드로도 안 될 만큼 비싸다 — "RAG 쓰기 싫어요"식 요구의 비용을 이해할 것.
- 멀티 GPU·멀티노드 환경은 부담스러워 수업에서 실습하지 않는다.

### 실제 프로젝트에 적용할 체크리스트 (- [ ] 행동 지침, 특정 프레임워크에 묶이지 않는 원칙 위주)
- [ ] 모델을 올리기 전에 **웨이트 dtype과 KV 캐시 dtype을 각각** 정하고 기록한다(웨이트 양자화가 KV까지 줄여 주지 않는다).
- [ ] GPU 한 장에 여러 모델·여러 인스턴스를 올릴 계획이면 `가중치 + 목표 컨텍스트 KV`를 모델별로 합산해 가용 메모리(여유분 제외)와 비교한다.
- [ ] 모델 카드의 파라미터 수와 실제 저장소 용량이 맞는지 보고, 맞지 않으면 **배포 정밀도(FP8 등)**를 확인한다.
- [ ] 최대 컨텍스트 길이(예: 1,048,576)를 그대로 쓰지 말고, 실제 필요한 길이 × 동시 요청 수로 KV를 계산해 상한을 정한다.
- [ ] KV 메모리는 레이어 수·KV 헤드 수·헤드 차원·dtype이 들어가는 공식으로 계산하고, 도구에 계산을 맡기면 근거(config 값)를 함께 받아 검토한다.
- [ ] 한 장에 안 들어가는 모델은 **텐서 패럴렐**로 나누고, 헤드 수가 GPU 수로 **나누어떨어지는지** 먼저 확인한다.
- [ ] 다중 GPU로 나눠도 **GPU당 KV 여유**가 목표 요청 1건 이상을 담는지 따로 계산한다(전체 합이 아니라 장당 기준).
- [ ] 긴 컨텍스트 요구가 오면 하드웨어 비용과 RAG·요약·컨텍스트 압축 같은 대안을 함께 비교한다.
- [ ] 4비트 포맷(NVFP4·MXFP4 등)은 GPU 지원 여부와 품질을 자기 데이터로 확인한 뒤 채택한다.
- [ ] VRAM이 모자랄 때 DRAM·NVMe로 KV를 내리는 방식은 전송·조회 비용이 생기므로 효과를 측정한 뒤 쓴다.
- [ ] 에이전트를 설계할 때 컨텍스트 길이가 곧 서빙 메모리 비용이라는 점을 반영해, 불필요한 컨텍스트 누적을 줄인다.

## 7일차 1강 — LLM 서빙 기초: 데이터 타입·양자화와 가중치·KV 캐시 메모리

### 핵심 요약 (3~5줄)
- 오늘 주제는 **vLLM 추론 엔진과 모델 내부 구조**다. Ollama는 주로 양자화 모델을 돌리므로, 여기서는 "회사들이 API로 모델을 어떻게 서빙하는지"를 본다.
- 모델 용량의 기준은 원본 데이터 타입 **BF16**이다. Hugging Face의 **safetensors** 정보로 파라미터 수와 텐서 타입을 읽고, 레포 용량은 **파라미터 수의 약 2배(GB)**로 감을 잡는다(Qwen3.8 27B → 약 56GB).
- 데이터 타입을 FP8·4비트로 낮추는 **양자화**는 처리량을 올리고 시간(TTFT)을 줄이지만, 표현 가능한 숫자 범위가 줄어든 값으로 수많은 연산 레이어를 곱셈으로 거치며 **오차가 누적**돼 모델이 "멍청해진다"(단어·문장 반복 등).
- 강사 견해: 모델사는 출시 직후 BF16으로 배포했다가 부하가 몰리면 FP8(약 5% 하락), 더 몰리면 FP4 등(20~30% 이상 하락, 측정치 없음)으로 낮추고, 체감 품질이 떨어질 즈음 새 모델을 낸다.
- GPU에 올릴 수 있는 모델 크기는 **가중치만으로 계산할 수 없다**. 컨텍스트 윈도우를 정하는 **KV 캐시**를 함께 계산해야 한다(H200 한 장: 130GB 가용 − 가중치 56GB − 256K KV 30GB+ = 약 44GB). 남는 메모리는 KV 캐시에 줘서 **동시 요청 수**를 늘리며, 긴 컨텍스트 API 가격이 특정 길이 이후 급등하는 것도 이 메모리 때문이다.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**0. 도입: 신규 모델 소식과 스택 다이어그램 스킬 (00:00~05:23)**
- 전날 밤 **Fable 5.2**가 출시됐다(강사는 5.5를 예상했는데 5.2를 냈다, "GPT의 6.2 버전을 의식한 게 아닌가"). 강사 전언: 기존 **Fable 5.1**보다 가격 약 **20%** 인하, 후기상 속도가 확실히 빨라짐, 현재 주력인 **Opus 5.5**가 "약간 멍청해졌는데" 그 부분을 Fable 5.2가 보완. 단점은 **토큰 소모량이 어마어마**하고 Opus보다는 여전히 비쌈. 강사는 아직 써 보지 못했다.
- effort 설정: 모델 카드는 max·xhigh를 말하지만 표를 보면 **high·xhigh가 가장 성능이 좋고**, max는 "**오버싱킹하는 경향**"이 있다 → "**하이 정도가 딱 기본 출발점**"이라는 강사 의견.
- **Mythos 5.2**도 같이 나왔다. 강사 설명: "원래 페이블의 모델이 미토스예요." 보안 필터를 더 씌운 것이 Fable, 덜 씌운 것이 Mythos. 보안 위협 발견 등에 쓰이고 기업 단위로 허가 시 열어 준다고 들었지만 실제 사용자를 본 적이 없어 잘 모른다.
  - (공식 문서 확인: https://platform.claude.com/docs/en/models/mythos-5/overview.md — 다시보기 분석의 보충 검색 결과, Fable 5·Mythos 5와 Mythos 5.1까지만 확인되고 "5.2" 출시 기록과 가격 20% 인하는 확인하지 못함 → 미확인. Mythos가 초대제로 방어용 보안 작업에 제공된다는 점은 공식 문서와 강사 설명이 대체로 맞는다.)
- **스택 다이어그램(stack diagram) 스킬**: 지난 금요일 수강생이 "기존 다이어그램 디자인보다 현실(기술 스택)에 맞는 다이어그램 스킬"을 요청해 소개. 에셋에 들어 있는 아이템을 잘 골라 그리는 정도이며, **AWS 관련 다이어그램**도 잘 그려 준다. "한번 설치해서 써 보시면" 기술 스택 표현에 도움. 오늘 수업 자료는 구글 드라이브에 업로드했다.
- 강조 이유: 프로젝트(목·금)를 앞두고 쓸 모델과 effort 출발점을 정하는 감각, 그리고 오늘이 "가장 걱정인 날"(이론이 많은 날)임을 예고.

**1. 오늘의 주제와 경험 조사 (05:23~)**
- "VLLM이라고 하는 **인퍼런스 엔진**과 그리고 **모델의 어떤 내부 구조**"를 다룬다.
- 조사: Ollama로 로컬 모델을 돌려 본 사람은 꽤 있으나, **추론 엔진**으로 돌려 본 사람은 "갑자기 확 줄어드네요".
- 강조 이유: "올라마는 사실 양자화된 모델을 주로 돌리기 때문에", 실제로 API를 쓸 때 **회사들이 모델을 어떻게 서빙하는지**를 알아보려는 것.

**2. Hugging Face에서 읽는 모델 정보: 파라미터 수와 텐서 타입 (06:43~)**
- Hugging Face 모델 페이지 오른쪽 **safetensors** 영역에 모델의 텐서 정보(파라미터 수, 텐서 타입)가 나온다.
  - 예: **Kimi** → **2.8 trillion(2.8조) 파라미터**. 텐서 타입 = **데이터 표현 타입**.
  - F32는 보통 신경 쓰지 않고 **BF16**을 주로 본다. "**그 BF16이 어떤 모든 모델의 기준이 됩니다**" — "왜냐면 이게 **원본**이어서요." 모든 용량 산정은 16비트 기준.
  - 이 정도로 큰 모델(Kimi K3)은 양자화 모델이 거의 없다("그들도 이 모델이 안 쓰일 거라는 걸 알아요", 양자화해도 너무 큼). 대신 **8비트 프리시전**으로 "반쯤 낮춘 것도 서빙을 하는구나" 하는 정보가 적혀 있다.
  - 현실적인 예 **Qwen3.8 27B**: 페이지엔 28B로 표기(27.x라서 27B·28B 혼용, 차이 없음), 텐서 타입이 **BF16으로 고정**. 이 BF16 모델을 바탕으로 수많은 **양자화(quantizations) 모델**이 제공된다.
- 강조 이유: LLM을 이해하려면 "**데이터 타입**"과 "**퀀타이제이션**" 두 가지를 크게 이해해야 한다.

**3. 데이터 타입과 표현 가능한 숫자 범위 (10:39~)**
- 데이터 타입 사다리: **BF16 → FP8 → 4비트 → 2비트 → 1.x비트**. 부동소수점(FP)뿐 아니라 **INT8·INT4** 같은 정수 타입도 있다.
- 2비트 이하는 "**거의 지금 실험용**" — 서빙하는 회사가 없고, 개인이 어떻게든 돌려 보고 싶을 때 낮춰 본다. 그래서 Microsoft가 "**1비트넷**" 논문·라이브러리를 냈을 정도로 "실사용이 가능한가" 수준의 고민 영역.
  - (공식 문서 확인: https://github.com/microsoft/BitNet — BitNet b1.58·bitnet.cpp. 강사는 이름만 언급.)
- 타입을 낮추면 가장 기초적으로 **표현 가능한 숫자의 범위**가 달라진다. 모델에게 이는 "**내부에 있는 벡터 숫자들의 범위**"(강사는 처음 "모델이 선택할 수 있는 토큰의 범위"라고 했다가 "정확하게는 토큰은 아니고요"라고 정정). BF16과 INT4를 비교하면 **소수점 아래 자릿수**도, **정수 범위 자릿수**도 크게 다르다 → "얼마나 세세하게 표현을 할 수 있느냐, 대략 표현을 하느냐".

**4. 타입을 낮추면: 처리량·시간·지능 (14:45~)**
- 판서로 "체감 성능"과 "모델 서빙 시 성능"을 나누고, 체감을 **처리량 / 시간 / 느낌(=지능)** 셋으로 정리.
  - **처리량**: 올라간다. 같은 GPU, 같은 유한한 자원에서 더 많은 배치 처리를 지원 → 서빙하는 쪽은 "당연히 행복하죠".
  - **시간**: 줄어든다. 보통 연산이 줄어서 **TTFT**(첫 토큰 출력 시간)가 줄어든다. "모델 서빙하는 입장에서 그냥 빨리빨리 나가줘야 되니까" 좋다.
  - **지능(느낌)**: **멍청해진다**. 서빙하는 사람이 신경 쓸 영역은 아니지만, 사용자에게는 이게 문제.
  - (저장소 확인: TTFT 정의 `Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf` p.14 "TTFT Time To First Token — 요청 시작부터 첫 출력 토큰까지". 강의 전사의 "테스트 타임 퍼스트 토큰"은 Time To First Token의 오기 또는 말실수로 보인다.)
  - (교재와의 차이: 같은 PDF p.20은 "Weight quantization — 처리량: 켬, 메모리 여유 확보 / 지연: **조건부 — 항상 빠르지는 않음**", p.51은 "메모리 절감·연산 경로·dequantization 비용이 함께 바뀌므로 **더 빨라진다고 단정할 수 없습니다**"라고 적는다. 강의의 "시간은 줄어든다"는 단순화한 설명이며, 실제 속도 이득은 커널·GPU 조건에 따라 다르다 → 미확인.)

**5. 모델 구조와 오류 누적: 왜 양자화 모델이 멍청해지는가 (17:59~)**
- **Qwen3.8 27B 실제 레포지토리**를 열어 두 가지를 본다.
  1. **레포지토리 용량**: "두 배 정도 되는 것 같네" — "**그 느낌이 되게 중요해요.**" 수치 계산은 금방 하지만, 바로바로 감을 잡을 때 디스크 점유 용량이 파라미터 수의 약 2배라는 감각을 잡아 두면 좋다.
  2. **config**: 알 수 없는 말이 잔뜩 있지만 **레이어 타입**에 `linear attention`, `full attention` 같은 익숙한 단어가 보인다 → "어텐션 연산을 하는 레이어들이 잔뜩 쌓여 있다". LLM 한 박스는 실제로 레이어가 **층층이** 쌓인 구조(예전에 "딥러닝"이라고 부르던 그림).
- 오류 누적 설명(판서): **맨 앞(토큰화)과 맨 뒤(역토큰화)** 레이어를 제외한 **중간 연산 레이어**만 본다. 여기서 수치 연산(덧셈이 아니라 주로 **곱셈**, 실제로는 행렬)이 일어나는데, "정확도가 떨어지는 숫자를 계속 곱셈하면" → "**오류가 누적된다고 볼 수도 있겠죠.**" 첫 연산 땐 적던 오차가 레이어를 지날수록 커지고, 레이어는 "내부에 막 수십 개씩 … 수천 개씩" 있다.
- 결과로 보이는 증상(23:52~24:07 화면 시연, 무발화): **한 단어를 쭉 반복**, **했던 말을 N번 반복**, 그 외 많은 오류 케이스. 말을 잘해도 "얘 왜 이래?" 싶은 멍청함 — "실질적으로는 그 정확도가 떨어지는 숫자들을 계속 연산했기 때문".
- 강조 이유: 체감 품질 저하의 원인을 "모델이 원래 이상하다"가 아니라 **정밀도 × 레이어 수**의 구조적 문제로 이해하게 하려는 것.

**6. 모델사의 운영 전략 (강사 견해) (24:52~)**
- 시나리오(판서): 오늘 Fable 5.2 출시 → GPU 팜에 **BF16으로 쫙 배포** → 2~3일 유지하며 SNS 인플루언서들이 "성능 미쳤다"(테트리스, 비행기 게임 예시) → 요청이 미친 듯이 몰림 → 현실적으로 다 받아낼 수 없으니 **조금씩 낮춘다**.
  - **FP8**: "사람들이 그렇게 느끼지 못할 만큼" — "보통 한 **5% 내외**의 성능 하락이 있다고 해요".
  - 더 몰리면 더 줄인다(여기서부터는 어떻게 줄이는지 알 수 없음). 예컨대 **FP4** → "**2~30% 이상**", "거의 반토막이 난다고 보시면 됩니다". 단 "**수치적인 거는 … 누군가 측정한 건 없어요**."
  - 사람들이 "페이블 예전 같지 않네, 오퍼스 예전 같지 않네"라고 느낄 즈음 → **새 모델 출시**("마케팅 기가 막히죠").
  - 같은 GPU에서 단순 계산으로 모델 1개 쓰던 걸 2개, 4개 → **트래픽을 4배까지** 더 받아낸다.
- 강사 입장: 처음엔 "꼴 보기 싫었는데" 회사도 살아남아야 하니 택한 전략. 모델이 발전하며 같은 BF16이라도 연산·저장 효율이 조금씩 좋아진다. GPU는 하드웨어라 "클라우드 마냥" 늘릴 수 없어 "가진 자원에서 쥐어짜내고 있는 중". "모든 모델 회사가 지금 똑같이 운영", "공공연한 사실인 것 같아요"(세부적으로 FP8로 떨어뜨렸는지까지는 알 수 없음).
  - Opus는 출시 약 한 달 반(추석 9월 23~24일경 기준, 일주일 더 하면 두 달) → "낼 때가 됐어요".
  - Anthropic은 올해 **SpaceX**와 GPU 계약(데이터센터 **Colossus 1·2·3**, 강사 기억으로 1이 약 20만 대, 2가 약 40만 대·건설 중, 계약 규모 약 10만 대) 후 사정이 나아졌다. 원래 AWS하고만 하다가 GPU를 빨리 안 내주니 다른 곳과도 계약. OpenAI도 똑같다.
  - (확인: 수치는 강사 기억. 다시보기 분석의 보충 자료(datacenterdynamics 보도)는 2026-05 Colossus 1 전체 용량(22만 장 이상) 임대로 적어 강의 수치와 다르다 → 미확인.)

**7. 가중치만으로는 부족: H200 한 장 계산 (32:25~)**
- 지금까지 이야기한 것은 "**모델의 가중치만 얘기한 거예요.**" 앞서 주목하라던 레포 용량 = **BF16 가중치 크기**.
- 계산(판서, 강의 수치):
  - Qwen3.8 27B 가중치: 55.6GB → "그냥 **56GB**".
  - **H200 VRAM 144GB**(강의 수치). 다른 사양은 다 맞다고 가정하고 GPU만 본다 → 144 − 56이 남으니 "일단 있죠"(올릴 수 있다).
  - 현실적으로 **약 10%는 여유 공간**을 둬야 하므로 **90%만 쓴다고 가정** → **약 130GB**("모든 건 다 메모리 기준").
  - 130GB를 "두 배" 감각으로 반 나누면 약 **65B**(실제로는 약간 더 줄어 60B 정도) 모델까지 올라갈 것 같다 → "뭔가 계산을 넣지 않은 한 요소가 있다".
  - (공식 문서 확인: https://www.nvidia.com/en-us/data-center/h200/ — H200 SXM·NVL 모두 **141GB** HBM3e. 강의의 144GB와 다르다 → 미확인. 계산 예시는 강의 수치 그대로 둔다.)
  - (저장소 확인: "10% 여유" 개념은 교재의 `gpu-memory-utilization` — `Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf` p.27 "gpu-memory-utilization은 연산 사용률이 아니라 메모리 예산 비율입니다. OOM 여유를 남깁니다." 강의에서 플래그 이름은 말하지 않았다. 공식 문서 확인: https://docs.vllm.ai/en/latest/configuration/engine_args.html — "The fraction of GPU memory to be used for the model executor, which can range from 0 to 1." 미지정 시 기본값은 문서 버전에 따라 다르게 적혀 있어(현 문서: extensible KV cache면 1.0, 아니면 0.92) 강의의 90%는 계산용 가정으로만 본다.)
- 빠진 요소 = **KV 캐시**: "모델이 연산을 하면 연산에 그 흔적들이 남아야 되고", 그게 저장돼야 계속 답변할 수 있다. 프로그램이 하드디스크에만 있는 게 아니라 RAM에 올라가고 추가로 쓰는 공간도 고려해야 하는 것과 같다.
  - KV 캐시가 **컨텍스트 윈도우를 결정**한다: 입력을 받아 어딘가 저장해 두고 연산하려면 공간(램)이 필요하다.
  - 요즘 모델은 최소 **256K** 이상 지원. Qwen config의 `generation_config` 쪽을 뒤져 **max length 262K**를 찾음("256K나 262K나 … 어떤 숫자에서 출발했느냐가 약간 다른데").
  - "이 계산식은 우리가 이따가 자료에서 한번 볼 건데요." (저장소 확인: `Day07/Day7_vLLM_기초와_추론_속도_최적화.pdf` p.25 "KV 메모리 공식 Mₖᵥ ≈ 2 × B × L × T × nₖᵥ × dₕ × b" — 이 강에서는 공식을 풀지 않았다.)
  - 256K를 꽉 채우면 KV 캐시가 "**30기가가 넘습니다**"(GPU 램 기준).
- 결론: 130GB가 남아도 **65B는 불가능** — "왜 불가능했어요? 얘 때문에." "이 공간이 우리한테 맨날 **말썽**을 일으킵니다. 이거 더 주고 덜 주고가 엄청 중요해요."

**8. 남는 메모리의 쓰임과 긴 컨텍스트 가격 (40:08~)**
- 27B 하나 운영: 가중치 56GB + 256K KV 30GB+ = **약 86GB** → 130 − 86 = **약 44GB** 남음.
- 44GB에 모델 하나 더? "현실적으로 어렵다". 그렇다고 그대로 두면 아깝다 → **KV 캐시 여유 공간으로 준다**.
- 오해 주의: KV 메모리를 더 준다고 컨텍스트가 **256K → 512K로 늘어나지 않는다**. "256K인 건 **고정**이에요" — 모델이 지원하는 스펙 기준. (RoPE 기술로 곱셈해 100만 토큰까지 가상으로 늘리는 방법이 있지만 일단 제외.)
- 대신 캐시 용량이 늘어난 만큼 **여러 요청을 받을 수 있다** — 단순 계산으로 256K를 꽉 채운 요청을 "**한 두 개 반 정도**"(강사는 이어서 "한 두 개 정도"로 정리).
- **API 가격**: OpenAI 가격 페이지를 띄움(정보가 바로 안 나옴). 보통 256K 또는 모델사가 정한 범위(예: 300K, 400K)까지는 싸다가 **갑자기 비싸진다**. 이유: "**추가 용량을 써야 돼서**" — 아껴 둔 용량을 다른 사람에게 줄 수 있었던 걸 이 사람에게 줘야 하니 "그만큼 비싸게 받는 겁니다".
- 정리 발언: "**모든 건 다 메모리 가지고 왔다 갔다 하고 있어요.**" 데이터 타입 → 모델 웨이트 → 웨이트 말고 고려할 **KV 캐시**(모델이 활용할 데이터를 저장할 공간, 컨텍스트 윈도우 결정)까지 훑었고, 휴식 후 10시부터 "얼마나 더 효율적으로 쓸 수 있느냐"를 이어 간다.

### 강사 팁·주의사항
- 신규 모델 effort는 max보다 **high를 기본 출발점**으로(모델 카드 표상 max는 오버싱킹 경향). 단 강사도 아직 써 보지 않은 상태의 의견.
- 모델 크기는 "숫자 계산" 전에 **감**으로 먼저: 레포 용량 ≈ 파라미터 수 × 2(GB, BF16 기준). 27B·28B 같은 표기 차이는 무시해도 된다.
- 용량 산정의 기준은 언제나 **BF16 원본**. 양자화 모델 용량은 여기서 나눠 계산한다.
- 2비트 이하는 실험용 — 실서비스·API에서 볼 일이 거의 없다.
- 양자화 모델에서 **같은 단어·문장 반복** 같은 증상이 보이면 정밀도 저하(오차 누적)를 의심할 수 있다.
- GPU 메모리는 **약 10% 여유**를 남기고 90%만 쓴다고 가정해 계산한다.
- KV 캐시를 더 준다고 **컨텍스트 길이가 늘지 않는다**(모델 스펙 고정). 늘어나는 것은 **동시 요청 수**다.
- 남는 애매한 메모리는 그대로 두지 말고 KV 캐시에 준다. "이거 더 주고 덜 주고가 엄청 중요해요."
- 긴 컨텍스트 요청은 다른 요청 몫의 메모리를 빼앗으므로 비싸다 — API 가격표의 길이 구간을 볼 것.
- 모델 품질이 시기에 따라 달라지는 체감("예전 같지 않네")은 강사 견해로 서빙 정밀도 조정과 연결되지만, **측정된 수치는 없다**고 강사가 직접 밝혔다.

### 실제 프로젝트에 적용할 체크리스트 (- [ ] 행동 지침, 특정 프레임워크에 묶이지 않는 원칙 위주)
- [ ] 모델을 고를 때 모델 카드의 **파라미터 수와 텐서 타입(BF16/FP8/INT4 등)**을 먼저 확인하고 기록한다.
- [ ] 가중치 용량은 BF16 기준(파라미터 수 × 2바이트)으로 먼저 추정하고, 양자화 타입에 맞춰 나눈다.
- [ ] GPU 수용 가능 여부는 **가중치 + KV 캐시(목표 컨텍스트 길이 × 동시 요청 수)**로 계산한다. 가중치만으로 판단하지 않는다.
- [ ] GPU 메모리는 전부 쓰지 않고 **여유분(예: 10%)**을 남긴 예산으로 계산한다.
- [ ] 모델이 지원하는 **최대 컨텍스트 길이**를 config에서 확인하고, 메모리를 더 줘도 이 상한은 늘지 않음을 전제로 설계한다.
- [ ] 남는 메모리는 동시 요청 수(KV 여유)로 환산해 처리량 목표와 비교한다.
- [ ] 양자화 모델을 쓸 때는 처리량·지연 이득과 함께 **자기 업무 데이터로 품질 저하**(반복 출력, 엉뚱한 답)를 비교 측정한다. 남의 "5%/30%" 같은 수치를 그대로 믿지 않는다.
- [ ] 출력에서 단어·문장 반복이 보이면 프롬프트보다 먼저 **모델 정밀도(양자화 여부)**를 점검 항목에 넣는다.
- [ ] 외부 API를 쓸 때 **긴 컨텍스트 구간 가격**을 확인하고, 에이전트가 컨텍스트를 불필요하게 키우지 않도록 설계한다.
- [ ] 신규 모델의 추론 강도(effort)는 최고 단계가 아니라 중간~상위 단계에서 시작해 비교한다.
- [ ] 같은 모델이라도 시기에 따라 체감 품질이 달라질 수 있으므로, 회귀 평가 세트를 두고 주기적으로 다시 돌린다.

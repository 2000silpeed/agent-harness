## 3일차 6강 — 에이전트 최적화: 동작은 그대로, 근거는 남기고

> 출처: 「3일차 6강 다시보기 (보정).html」(전사·분석), 「3일차 6강 장표 (보정).html」(9장) · 2026-11-04 · 강의 길이 33:57

### 핵심 요약 (3~5줄)
- 앞에서 만든 챗봇(딥에이전트 코드)을 **새 대화 세션에서 모델을 Opus로 바꿔** "구조 최적화"를 시켰다. 가장 핵심 지침은 **"동작이 바뀌면 안 된다"**(예: 툴 콜링 순서).
- 개선 관점은 두 가지: **컨텍스트**(툴 개수·프롬프트 축소·스킬 도입 여부)와 **에이전트 구조**(지연 고려 서브 에이전트 분리, Sonnet→Haiku, 판단 구간을 디시전 전용 모델 jev로 교체).
- 변경은 **켜고 끌 수 있게(토글)** 만들고, 모든 최적화에 **기존 문제와 개선 근거를 남기게** 했다.
- 강사 결과: 한 턴 **약 4초 → 1.42초**. Sonnet→Haiku로 약 2.5초(약 1.5초 감소), jev로 판단 구간 교체해 약 1초 추가 감소. 입력 토큰도 감소.
- 다음은 이 챗봇에 RAG를 붙이고(4시부터), 데이터를 조회하는 멀티 에이전트로 확장.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)
- **구조 최적화**: 기존 동작은 유지하면서 컨텍스트와 에이전트 구조를 다듬어 지연·토큰을 줄이는 작업. 분석부터 시키기 위해 새 세션 + Opus를 썼다.
- **동작 불변 지침 ("동작이 바뀌면 안 된다")**: 최적화 지시의 가장 핵심 제약. 동작이란 툴 콜링 순서 같은 것. 원래는 더 자세히 정의해야 하지만 "요즘 Opus는 그 정도는 알아듣는 것 같더라"며 이 정도만 주고 출발했다.
- **컨텍스트 관점 최적화**: ① 툴 개수가 좀 줄었으면 ② 프롬프트를 더 줄일 수 없나("쥐어짜는 거죠") ③ 스킬로 도입해야 할 지점은 없나.
- **에이전트 구조 관점**: "레이턴시를 고려한다면 서브 에이전트로 분리하는 게 좋을까?" — 정답을 주지 않고 **코드로 판단해 보라고 질문만 던졌다.**
- **모델 다운그레이드 (Sonnet → Haiku)**: Haiku로 처리 가능하면 더 빠를 것이니 검토하라고 지시. 결과적으로 지연 단축의 **가장 큰 요인**("쏘넷에서 하이쿠로 떨어진 게 가장 크다"). 최종적으로 Haiku를 기본으로 고르게 했다.
- **디시전 전용 모델 (jev)**: 판단(decision)이 들어가는 부분, 즉 LLM이 중간중간 판단하던 구간을 jev로 교체. 추가로 약 1초 단축.
- **토글 (껐다 켰다)**: 동작을 직접 확인하고, 퀄리티 체크·레이턴시 체크를 자동으로 돌려도 비교할 수 있게 하기 위함.
- **근거 기록**: "모든 최적화 작업에는 기존 작업에 어떤 문제가 있었고 어떻게 개선했다라는 근거가 꼭 필요하다. 이 작업의 근거를 나한테 꼭 남겨라. 내가 볼 수 있게."
- **스트리밍 아님**: 이 챗봇은 스트리밍이 아니어서 답이 "툭 하고" 한 번에 나오지만 매우 빠르다. 강사는 자기 결과물을 "챗봇이라고 부르기도 불가능할 정도… 아주 귀여운 LLM 호출기"라고 표현.

### 실습/데모 내용 (명령어, 파일 구조, 프롬프트, 코드 조각 등 원문 그대로 보존)
- **진행 흐름 (장표)**: `새 세션 · Opus (코드베이스를 참고로)` → `동작 유지 (가장 중요한 지침)` → `관점별 개선 (컨텍스트 · 구조 · 모델)` → `근거 남기기 (무엇을 왜 바꿨나)`
- **강사가 준 지시의 구성 (전사 원문 발췌)**
  - "뭐냐면 동작이 바뀌면 안 된다."
  - "뭐 풀콜링(툴 콜링)의 어떤 순서나 이런 것들이 바뀌면 안 된다"
  - 컨텍스트 관점: "아 툴 개수가 좀 줄었으면 좋겠다." / "두 번째, 프롬프트 좀 더 줄일 수 없니?" / "그리고 혹시나 스킬로 도입해야 된다면 그런 지점은 없을까?"
  - 에이전트 구조 관점: "혹시 내가 레이턴시를 고려한다면 서브 에이전트로 분리하는 게 좋을까?" / "현재 이제 쏘넷 모델을 사용하고 있는데 하이코 모델로 처리할 수 있다면 더 빠를 것 같다. 검토해봐라"
  - 기타: "디시전이 들어가는 부분을 지금 디시전 전용 모델인 이 jev으로 바꿔보면 어떻니?" / "그리고 그걸 껐다 켰다 할 수 있게 해서 내가 동작을 좀 확인해보고 싶다."
  - 근거: "모든 최적화 작업에는 기존 작업에 어떤 문제가 있었고 어떻게 개선했다라는 근거가 꼭 필요하다. 이 작업의 근거를 나한테 꼭 남겨라. 내가 볼 수 있게"
  - 추가 지시(결과 공유 시 언급): "모델을 하이쿠로 바꿀 수 없을까?" → Haiku를 기본으로 최종 선택하게 함.
- **프롬프트 공유**: 복사·붙여넣기용 프롬프트를 **구글 드라이브 Day 3 폴더에 txt 파일**로 업로드.
- **수강생 실습**: 각자 만든 "워크플로우를 수행하는 작은 에이전트"를 같은 방식으로 개선. 새 대화 세션에 앞의 코드베이스를 참고로 주고 지시. 약 30분 작업, 중간중간 질문.
- **결과 수치 (강사가 말한 대략값)**

  | 단계 | 한 턴 응답 시간 |
  |---|---|
  | 처음 (Sonnet) | 약 4초 |
  | Haiku로 변경 | 약 2.5초 (약 1.5초 감소) |
  | + 디시전 모델(jev) | 1.42초 (약 1초 추가 감소) |

### 강사 팁·주의사항
- 검토·의견·개선 작업을 할 때는 **모델을 Opus로 바꾸는 게 좋다.** 그리고 **새로운 대화 세션**에서 진행.
- 지시는 **한 번에 해도 되고, 대화형으로 차근차근 나눠도 된다.** (강사는 설명을 위해 한 방에 했다.)
- 개선 후에는 **진짜 개선이 됐는지를 검토**할 것.
- 변경은 **토글로 껐다 켰다** 할 수 있게 해야 품질·지연 체크가 가능하다.
- 개선이 끝났다면 "RAG가 없는 이 챗봇에 RAG를 붙인다면 어떻게 붙일까?" 같은 식으로 조금씩 발전시켜 나갈 수 있다.
- 일정: 45분까지 작업 → 4시까지 휴식 → 4시부터 어제 못한 RAG 부착 실습, 이어서 데이터를 조회하는 멀티 에이전트.

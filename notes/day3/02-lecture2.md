## 3일차 2강 — 워크플로우에서 에이전트 배치까지 (싱글 우선 설계와 멀티 에이전트 패턴 4요소)

> 출처: 「3일차 2강 다시보기 (보정)」(2026-11-04, 45:01, 자동 전사 whisper.cpp large-v3-turbo + 분석, 일부 오인식 보정 반영) · 「3일차 2강 장표」(15장, SDS AX Advanced)

### 핵심 요약 (3~5줄)

- 멀티 에이전트 아키텍처는 구조를 먼저 고르는 것이 아니라, **기존 비즈니스 워크플로우에서 사람이 판단하는 지점**을 찾아 그곳에 에이전트를 두는 것이다. 루틴하거나 규정이 정해진 업무는 대부분 코드로 처리할 수 있다.
- 돈이 오가거나 민감 정보를 바꾸는 작업은 **휴먼 인 더 룹**으로 사람 검토를 거치고, 겉보기에 순차적인 흐름도 실제로는 **병렬**로 처리해야 하며, 정책·권한은 모든 단계에 적용한다.
- **시작은 무조건 싱글 에이전트**: 싱글은 쪼갤 수 있지만 멀티는 다시 합치기 어렵다. 스킬을 붙이다 품질이 떨어지면 **측정·기록**을 근거로 큰 작업부터 서브 에이전트로 뗀다.
- 수많은 패턴은 **순차·병렬·분기·루프** 4요소의 조합이다. 라우터/슈퍼바이저, 플랜 앤 익스큐트, 스웜(네트워크)을 조직 구조로 설명했고, 스웜은 결론이 안 나므로 실전에서는 체어맨·투표·맥스 턴 같은 종료 장치가 필요하며 현실적으로는 플랜 앤 익스큐트 + 개별 전문가 실행자 구조를 많이 쓴다.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**1. 출발점은 아키텍처가 아니라 워크플로우** (00:00~01:04)
- "워크플로우랑 에이전트를 어떻게 구분하고, 에이전트는 어디다 갖다 둘 것인가"를 고민하는 것이 요즘의 멀티에이전트 아키텍처.
- 내 비즈니스 워크플로우가 그 모습이 아니라면 굳이 그 아키텍처를 쓰지 않아도 된다.

**2. 싱글 vs 멀티 논쟁, 엔지니어링 용어 포모** (01:06~03:52)
- "일단 프론티어 모델 회사들은 싱글을 강조합니다." 이유(강사 견해): 싱글로 만들면 "모델을 키웠어요. 드디어 잘 됩니다"라고 모델 성능을 드러낼 수 있어서. 불과 일주일 전 Anthropic도 싱글 에이전트로 가야 한다는 블로그를 발행.
- 엔터프라이즈는 다름: "조금 안 되면 그냥 그 프로젝트는 실패해요." 강사 개인으로는 공감해도 프로젝트에 그대로 쓸 수는 없었다고 함.
- 프롬프트·컨텍스트·하네스·루프·그래프 엔지니어링 등은 "대부분 말장난" → 실제 구성 요소만 짚고 포모에 빠지지 않아도 됨. (오전 이론, 점심 후 실습)

**3. 에이전트를 둘 곳: 사람이 판단하는 지점** (04:06~10:35)
- 워크플로우는 비즈니스 케이스가 다양해 도메인 담당자 인터뷰로 구체화해야 함.
- 에이전트의 두 기능: **판단**과 **말하기(생성)**. 워크플로우 중 사람이 판단을 요하는 곳이 에이전트로 바꿀 대상. 루틴·법/규정 플로우는 "사실 대부분 코드가 할 수 있습니다."
- 설계 순서: ①어디에 넣을지(플로우 다이어그램으로 보면 어렵지 않음) ②그 녀석이 어떻게 판단할지(어려움) ③단계 분리 여부 판단 ④테스트 — 테스트 데이터셋 만드는 게 가장 어렵고 반복 실행·개선은 어렵지 않음(5일차에 다룸).
- 온톨로지: 판단 근거 설명 수단으로 뜨는 키워드지만, 강사는 메타데이터·**맵핑 테이블**과 크게 다르지 않다고 봄(꼭 그래프 DB여야 하는가도 의문). Databricks·Snowflake가 온톨로지를 영업 중.

**4. 워크플로우 vs 에이전트, 에이전트 루프** (10:40~12:54)
- 워크플로우: 요청을 룰베이스로 분류해 정해진 루트(예: 환불, FAQ)로 처리. LLM이 아니어도 됨(코드/룰베이스).
- 에이전트: 동적으로 판단, 도구를 활용. 경계는 흐려지는 중.
- 주의: "LLM을 사용한다고 해서 모두 에이전트를 쓴다? 그런 건 아닙니다." 분류는 디시전 모델들도 요즘 너무 잘함.
- 도구는 LLM이 실행을 **요청**하고, 코드(Claude Code, 딥에이전트 등)가 **실행**. 이 반복이 에이전트 루프.

**5. 사례: 결제가 두 번 된 강성 민원** (13:01~15:18)
- 요청: "결제 두 번 됐다, 취소하고 피해 보상해 달라."
- 고정 프로세스: 결제 조회 → 회사 내규 처리 규정 확인 → 응답.
- 숨은 포인트: 정책은 확인보다 **해석**이 중요(예시집 등), 응답이 고객 감정을 건드리지 않는지도 중요.
- 동적 처리: 에이전트가 의도 판단 → 작업 3개(중복 결제 확인, 취소, 보상 확인) → 보상 기준, 지금 취소 가능한지/사람에게 넘길지 근거 선택 → 고객 응답 또는 시스템 담당자 연락.

**6. 휴먼 인 더 룹** (15:22~16:56)
- 취소는 돈이 오가는 작업 → 에이전트에 맡기면 "싹 다 취소해버릴 수 있어요." → "돈이 오가거나 굉장히 민감한 정보를 변경해야 되는 건 사람한테 검토를 받도록 해야 됩니다."
- 사람이 루프에 들어가 "해/하지 마/다시 돌려놔" 피드백. Claude Code의 1·2·3·기타 선택지 질문 창이 그 예(Codex 등 코딩 에이전트 모두 동일 구조). 애매한 선택이나 스스로 못 하는 일을 사람에게 요청하는 구조.

**7. 코드로 할 일 vs 병렬 실행 vs 정책·권한** (16:59~21:43)
- 워크플로우를 짜 두면 에이전트를 "넣는 건" 어렵지 않음(잘 만드는 건 어려움). 코드/API/모델/에이전트를 오가며 구성.
- 콜센터 예: 본인 확인(주민번호 뒤 7자리 키패드 입력)은 코드로 처리.
- 겉보기 순차(듣기→확인→응답)지만 실제로는 고객 말 한 줄이 올라오는 순간 사실 확인이 뒤에서 돌아야 하고, 문장이 끝나면 또 확인 → **병렬 실행** 필요. 신한카드 콜센터 VIP 상담사가 "손이 네 개인 것 같다"는 비유.
- 정책·권한: 코드 실행 권한, 에이전트의 도구 접근 권한, 모델 실행 권한 등 **모든 과정**에 적용.

**8. 시작은 무조건 싱글, 측정하며 쪼개기** (21:48~25:30)
- "근데 시작은 무조건 싱글로 하셔야 됩니다." "싱글은 쪼갤 수가 있지만 멀티는 다시 합치기가 쉽지 않아요."
- 툴·스킬을 줄줄이 달아 실행·결과 확인 → 스킬이 늘며 품질이 떨어지면 작업이 큰 스킬부터 서브 에이전트로 떼기 → 멀티로 진화.
- "우리 이제 감으로 때려 맞추는 시대는 지났습니다." 감으로 평가하면 담당자 말이 계속 바뀜(어제는 좋았는데 오늘은 나쁘다 → 고치면 다 같이 망가짐) → **기록**을 남겨야 함.
- 쪼갠 구조 예: 기본 조건만 시스템이 빠르게 확인(툴 콜링 필요 없이 툴에 녹여도 됨) → 확인되면 동시에 조회 → 취합 제공. 요청이 끝나면 빨리 확인하도록 도구를 미리 필터링하는 등.

**9. 패턴 4요소: 순차·병렬·분기·루프** (25:45~27:36)
- "이 패턴이라는 녀석들은 실제로 4개로 정리가 다 되더라."
- 순차: 이전 결과물을 다음에 활용 / 병렬: 동시에 해도 문제없는 작업 / 분기: 의도분류 후 라우팅·브랜칭 / 루프: 개별 에이전트나 한 노드를 반복.
- 조합하면 슈퍼바이저, 플랜 앤 익스큐트. Anthropic·OpenAI도 더 이상 "패턴"으로 설명하지 않고, 특히 Anthropic은 이 4가지로 설명("동적으로 에이전트를 생성할 때는 병렬로/라우팅해서 생성하십시오").

**10. 조직 구조로 보는 패턴 (판서 '멀티 에이전트 패턴')** (28:01~34:37)
- 멀티 에이전트 패턴은 인간의 작업 구조·조직 구조를 참고.
- **라우터 = 슈퍼바이저**(같은 의미): 팀장이 "누가 잘하겠구먼" 하고 분기 → 엑스퍼트(전문가) 에이전트. 바이패스 성격, 아주 간단한 판단만.
- **플랜 앤 익스큐트**: 작업 뭉텅이를 받은 엑스퍼트가 한 방에 못 하면 "사실 나도 팀장이었어" → 계획(플랜)을 짜 일개미 **익스큐터**들에게 나눔(예: 데이터 분석팀 팀장이 계획 → 김대리에게 할당).
- 계층형(하이어라키컬 슈퍼바이저)도 하이어라키를 가지면 될 뿐, 새로울 것 없음. 오케스트레이터 앤 워커도 플랜 앤 익스큐트와 같음.
- Claude Code는 대부분의 작업을 플랜 앤 익스큐트로 수행("계획 안 짜는 것 같지만 사실 짜서 돌리고 있어요").

**11. 스웜(네트워크)의 한계와 종료 장치** (32:38~42:12)
- 팀장 없이 모든 엑스퍼트가 수평적으로 대화하는 구조. "이런 패턴의 이름은 중요하지 않습니다. 그냥 이 그림이 중요할 뿐이에요."
- 문제: "결론이 안 납니다." 예: 에이전트 소셜 네트워크(에이전트의 레딧) — 에이전트들끼리 글 쓰고 따봉 누르고 싸우지만 결론이 잘 안 남.
- OpenAI가 수학 난제 풀이에 이 구조를 활용했다고 발표하지만 "아무도 실전에서 그렇게 본 적이 없어요" → 강사는 "약간 허상이 아닌가" 생각.
- 끝내려면 결정자 필요: 체어맨(원탁 회의 의장), 투표, 코드로 둔 턴 제한(예: "맥스턴, 50턴"). 안 두면 영원히 돎.
- 의견 취합에는 도움이 많이 됨 → 딥 리서치(데이터 조회·시각화·검수 등 개별 에이전트를 돌려 보고서 생성)에서 루프 구조로 활용. 실제로는 누군가 결정해 주는 구조(슈퍼바이저)로 구현을 많이 함.

**12. 현실적 구현 구조** (42:15~44:47)
- 플랜 앤 익스큐트 + 익스큐터를 개별 전문가로: 데이터 분석·코드 생성·코드 리뷰 전문가(계획서에 따라 아키텍트 → 코드 라이트 → 리뷰 에이전트 순으로 실행).
- 전문가끼리 직접 주고받기는 메인/엑스퍼트가 통제하기 어려워 잘 구현하지 않음. 다음 단계로 넘길 때 **필요한 정보만 추려** 전달.
- Claude Code에서 계속되는 고민: 서브 에이전트를 쓰면 메인(대화) 세션이 너무 빨리 차는 문제, 서브끼리 대화하면 메인이 진행 상황을 모르는 문제.

### 실습/데모 내용 (명령어, 파일 구조, 프롬프트, 코드 조각 등 원문 그대로 보존)

- 본 강의는 이론(판서) 중심, 코드 실습 없음("점심 식사 하시고 나면은 또 많은 실습이 여러분들을 기다리고 있습니다").
- 판서 노트 "멀티 에이전트 패턴"(28:01~): 한 장에 라우터/슈퍼바이저 → 엑스퍼트 에이전트 → (플랜) → 익스큐터, 옆에 수평 엑스퍼트 1·2의 스웜 구조를 그림.
- 결제 중복 민원 가상 사례 흐름(원문 요지):
  - 고정: `결제 조회 → 처리 규정 확인 → 응답`
  - 동적: `의도 판단 → [중복 결제 확인 | 취소 | 보상 확인] → 근거 선택 → 고객 응답 또는 시스템 담당자 연락`
- 휴먼 인 더 룹 예: Claude Code 질문 창 "1번, 2번, 3번 기타 이렇게 입력하세요."
- 콜센터 본인 확인 멘트: "본인 확인을 위해 주민등록번호 뒤에 일곱 자리를 키패드에 입력을 해주세요." → 코드로 처리.
- 스웜 종료 장치 예: "맥스턴, 50턴 제안"(턴 제한).
- 시연: 에이전트 소셜 네트워크(에이전트의 레딧) 화면 — 사람은 관람만 가능, 정책 변경으로 지금은 보기 어렵게 바뀜.
- 장표 '현실에서 많이 쓰는 구조': `전문가 에이전트(계획 수립·분배) → 데이터 분석 / 코드 생성 / 코드 리뷰`

### 강사 팁·주의사항

- 아키텍처를 먼저 정하고 비즈니스를 끼워 맞추지 말 것.
- 모델사의 "싱글로 충분" 메시지는 모델 성능 홍보 성격이 있으니 엔터프라이즈 프로젝트에 그대로 적용하지 말 것(강사 견해).
- "OO 엔지니어링" 신조어에 포모 느끼지 말고 구성 요소만 확인.
- LLM을 쓴다고 에이전트가 아님. 분류만 필요하면 디시전 모델로도 충분할 수 있음.
- 돈·민감 정보 변경 작업은 반드시 사람 검토(휴먼 인 더 룹).

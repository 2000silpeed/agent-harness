## 3일차 5강 — 워크플로우를 에이전트로: LangGraph에서 Deep Agent로, 순서는 도구가 지킨다

> 출처: 「3일차 5강 다시보기.html」(전사·분석), 「3일차 5강 장표.html」(13장) · 2026-11-04 · 강의 길이 45:19

### 핵심 요약 (3~5줄)
- "어디를 에이전트로 바꿀까"부터 접근하지 말고, 워크플로우 각 단계에 **판단인지 생성인지**부터 붙인다. **판단과 생성이 함께 있는 구간**이 에이전트(서브에이전트) 후보 — 단 "무조건"은 없다.
- 예제 "RAG 없는 문의 답변 챗봇"(의도 분류 → 후보 선정 → 추가 질의 → 답변)을 Claude(Sonnet 5.5 medium)로 **LangGraph 노드·엣지** 코드로 만들어 원하는 대로 동작함을 확인했다.
- 같은 흐름을 **Deep Agent**로 옮기면 전체가 하나의 에이전트 루프라 순서를 코드로 찍어 보낼 수 없다 → 1차로 **시스템 프롬프트에 4단계**를 적었지만 "우연히 잘 된 것뿐", "기도하는 단계".
- 개선: **순서를 프롬프트가 아니라 도구가 강제** — 각 도구가 현재 단계를 읽고, 어긋나면 거절하고, 다음에 부를 도구를 알려 준다.
- 남은 과제: MemorySaver라 기록이 안 남음, 작은 챗봇에 도구가 6~8개로 너무 많음 → 쉬고 3시 5분부터 **최적화(도구 수 줄이기)하고 근거 남기기** 실습.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)
- **판단과 생성**: 에이전트의 세부 구성은 결국 판단과 생성 두 가지. 각 단계에서 무엇이 판단이고 무엇이 생성인지 먼저 결정한다. 강사는 "어디를 에이전트로 바꿀까"라는 접근이 "안 좋다"고 이미 말했다며 강조.
  - "판단 생성이 같이 있는 경우가 보통 에이전트로 만들기가 좋아요." 단, "무조건 이러면 서브 에이전트입니다 … 그런 건 없고요" — 어디까지나 후보.
- **예제 워크플로우 (RAG 없는 문의 답변 챗봇)** — 공통으로 이해할 수 있게 난이도를 낮춤
  1. 의도 분류 — 판단
  2. 후보(FAQ) 선정 — 판단 (참고용 작은 FAQ 데이터셋이 있다고 가정)
  3. 추가 질의 — 후보가 명확하지 않을 때 사용자에게 원하는 분야를 물음 (판단 + 생성) → **서브 에이전트화될 수 있는 후보**
  4. 답변 — 생성
  - 전체는 챗봇 프로세스라 "거의 풀리 에이전트"지만, 그 안에서도 1·2번 순서대로 가다가 3번이 서브 에이전트일 수 있다고 "생각만 해 보는" 아이디얼한 단계.
- **LangGraph vs Deep Agent**
  - LangGraph: 노드와 엣지로 구성. "1번 실행했어? 다음에 2번 가라"를 코드로 명시적으로 보낼 수 있어 **순서가 명확한 프로세스는 오히려 LangGraph가 편리**.
  - Deep Agent: 더 추상화되어 "1번, 2번, 3번, 4번을 명시적으로 보낼 수가 없어요 … 그거 다 묶어서 에이전트 루프로 해놨거든요." 그래서 프롬프트로 제어해야 함. 거대한 루프라 "어디로 튈지 알 수가 없어서" 제어가 필요.
  - 강사 방향: "점점점점 하나의 에이전트가 전체 워크플로우를 품을 수 있게 하는 구조로" 가는 중.
- **프롬프트 제어(쉬운 제어)의 한계**: 이 정도로 간단한 작업은 시스템 프롬프트만으로도 꽤 순서를 지키지만 보장은 없다. 순서를 안 지키면? → 단계를 기록해 두고 확인해야 하고, 1단계를 건너뛰었다면 되돌려 1단계를 시켜야 한다. "어디다 기록을 해놓고 그걸 누가 확인해서 너 지금 잘못했어 다시 해"를 구성하려면 **코드로 어느 정도 제어**해야 한다.
  - "지금 한 구조는 프롬프트 써놓고 잘 되기를 기도하고 있던 단계예요. 지금 우연히 잘 된 것 뿐입니다."
- **도구 기반 순서 제어**: 미들웨어는 처음엔 복잡하니 일단 미루고, **특정 도구를 호출하도록** 만든다. 그 도구의 반환값이 다음 단계를 안내: "1번 해 → 1번 했어, 2번 해 → 2번 했어, 3번 해 → 3번 했어, 4번 해 → 끝났어, 종료해". 시작하자마자 그 툴을 강제로 호출하거나 파라미터를 우리가 채워도 된다. 이렇게 하면 프롬프트도 짧아지고 제어가 쉬워진다.
- **MVP 단계적 개발**: "내가 아는 코드에서부터 일단 출발해야 어느 정도 제어 가능한 형태가 만들어지더라구요." 익숙한 LangGraph에서 출발해 구조를 보며 한 땀 한 땀 고쳐 나간다. MVP에 프로젝트의 살을 붙이면 실제 코드로 전환된다.
- **effort 설정**: 코드베이스와 문서를 깊게 주고 "복잡하게 만들어라" 할 때는 effort를 높게(높음/하이/엑사이로 들림). 대화하며 같이 작업할 때는 Opus 기준 low, Sonnet은 medium~high를 오간다 — "망치면 날리고 다시 빨리 받는 게 좀 더 좋더라고요."
- **MemorySaver**: 기록이 메모리에만 저장되어 터미널을 끄면 기록이 남지 않는다 → 기록을 남기도록 다시 시켜야 함.
- **다음 개선 고민**: ① 나중에는 "툴 호출 말고 어떻게 제어해볼 수 없을까"도 고민하게 됨 ② 작은 챗봇에 도구가 너무 많음 → 줄이기. "최대한 컴팩트하게, 하지만 안정적이어야 됩니다."

### 실습/데모 내용 (명령어, 파일 구조, 프롬프트, 코드 조각 등 원문 그대로 보존)
- **실습 1: LangGraph로 구현 (약 15분, Claude와 함께)**
  - "일단 노트북 무시하시고 … 1번 랭그래프로 만든다면 / 딥 에이전트로 만든다면 … 일단 1번을 먼저 한번 해보실까요?" "멀티턴 이런 거 신경 쓰지 않으셔도 됩니다."
  - 강사 설정: 모델 **Sonnet 5.5 medium**, "오퍼스 안 썼어요. 굳이 오퍼스까지 가야 되는 작업이 아니라고 생각을 했습니다."
  - 강사가 Claude에게 준 것: 파일 껍데기 하나("딴 데 쓸까 봐") 지정 / 골: RAG 없는 문의 답변 챗봇 / 판단과 생성 구분(장표 내용 그대로 복사) / "FAQ 예제는 제이슨으로 그냥 가상으로 좀 만들어 둬라" / "랭 그래프로 로직을 짜라".
  - 결과: 약 3분 작업. "코드가 너무 못 생겼길래 살짝 코드만 좀 고쳐 달라고 했습니다."
  - 생성된 그래프 노드:
    - 의도 분류 노드 (`classify_intent`로 구술) — 판단
    - FAQ가 아니면 모델 없이 정해진 문구로 안내하는 노드
    - FAQ 후보군을 찾아내는 노드
    - 명확화 노드: "이 중에 네가 원하는 게 있니?"를 생성하고 사용자 답변을 **기다림**
    - 인간 상담원 연결 노드: "죄송해요. 어떤 문의인지 파악하지 못했어요. 인간 상담원을 연결해 드릴게요."
    - 최종 답변 노드 — 생성
  - 흐름: `classify_intent` → (인텐트 조건 만족 시 해당 노드로) → 명확화 질문 후 대기 → 최종 결정 → 답변. 샘플 질문으로 실행해 "원하는 대로 돈다"를 확인.
- **실습 2: Deep Agent로 옮기기 — 프롬프트 지시 (basic 파일)**
  - "여러분들이 랭그래프로 만드신 이 노드 녀석들을 딥에이전트로 옮기는데 일단은 프롬프트 지시로 아까 그 단계를 그대로 밟을 수 있게 작성을 해보시는 겁니다." 파일명은 "베이직이라는 것만 한번 써주십시오"(강사와 똑같지 않아도 됨). 두 번째 파일.
  - Claude가 짠 시스템 프롬프트(강사 구술, 일부 생략):
    ```
    당신은 어쩌고저쩌고 문의에 답하는 챗봇입니다.
    FAQ 목록은 이렇습니다.
    매턴 고객의 발언을 보고 아래 4단계 순서를 따르세요.
    앞에 대화는 단순 맥락으로만 쓰십시오.
    (1~4단계: 2번 판단 의도 보류, 3번 …, 4번 …)
    ```
  - 의도상 방향이 맞아서 OK 했음.
- **실습 3: 순서를 도구가 강제하도록 변경**
  - Claude에게 준 지시(인식이 끊긴 구술, 취지): 시스템 프롬프트(함수)로 전체 프로세스를 제어하는 과정이 불완전하다고 생각하므로, 툴을 개발해 이 프로세스의 순서를 제어하기를 원한다. ("잘못 짜면 고치면 되니까"라는 생각, 아주 작은 코드 베이스라 가능.)
  - Claude의 응답: "순서를 프롬프트가 아니라 도구가 강제하는 구조로 바꾸겠다. 각 도구가 지금 단계를 읽어, 순서가 어긋나면 거절하고, 다음에 부를 도구를 알려주는 방식을 취하겠다." 이후 딥에이전트에서 이를 개발할 구체적 요소를 확인하는 도구를 찾아옴.
  - 바뀐 시스템 프롬프트(구술): "역할과 목록만 말하고 순서는 도구가 강제하도록 … 매턴 고객의 마지막 발화를 처리하십시오. (앞 대화는) 맥락으로 쓰십시오. 반드시 classify_intent 도구부터 시작하고, 고객에게 가는 답은 answer_faq / ask_clarification / decline / handoff 도구가 만듭니다." (도구 이름은 구두 열거라 정확한 표기 미확인)
  - 생성된 도구: 의도 분류(반드시 첫 도구) · FAQ 후보 찾기 · 후보 중 원하는 분야 되묻기(명확화 질문) · FAQ 답변 · FAQ 문의가 아니면 거절 · 핸드오프("아마 핸즈오프는 거의 없을 것 같네요").
  - 실행 테스트 후 확인 포인트: "이 과정이 기록이 어떻게 됐냐인데, 지금은 메모리 세이버로 … 터미널을 껐잖아요. 그럼 기록이 안 남습니다." → Claude에게 "야 기록 남겨라. 지금 메모리에 있는 거 기록 보기가 어렵다."
- **다음 실습 예고**: 껍데기가 만들어졌으니 최적화 — 도구 개수 줄이기 등, "어떻게든 하나에 우겨 넣는. 근데 안정적이어야 됩니다." 최적화하고 근거를 남기는 실습. 3시 5분 재개.

### 강사 팁·주의사항
- 워크플로우를 에이전트화할 때 "어디를 에이전트로"가 아니라 **단계별 판단/생성 표시**부터.
- 순서가 분명한 프로세스는 LangGraph가 편하다. Deep Agent로 옮길 때는 순서를 지키게 할 **장치**가 필요하다.
- 시스템 프롬프트에 단계를 적는 것은 쉬운 제어일 뿐, 보장이 아니다 — 기록·검증·되돌리기는 코드(도구)로.
- 미들웨어도 방법이지만 처음엔 복잡하니 도구 호출 방식부터.
- Claude에게 시킬 때는 **진단(현재 방식이 불완전하다)과 원하는 구조**를 함께 말한다.
- **작게 시켜라**: "그냥 요청을 하면은 자기가 알아서 막 구조를 엄청 복잡하게 만들어." 강사는 그중 "한 70%"는 쓸모없다고 본다. 참조할 코드를 만들 때는 작은 영역을 작게 작게 시킨다.
- effort: 깊게 맡길 때 높게, 대화형 반복은 낮게(Opus low / Sonnet medium~high).
- 강사는 목표를 정해두고 달성될 때까지 알아서 돌리게 하는 편이라 코드를 잘 보지 않고, **마지막에 한 번** "진짜 쓸모가 있나, 바로 버려야 되는 코드베이스인가"만 본다.
- 모델은 작업 난이도에 맞게 — 이 작업은 Opus까지 필요 없다고 판단.

### 실제 프로젝트에 적용할 체크리스트 (- [ ] 행동 지침 형태)
- [ ] 내 워크플로우 각 단계에 "판단" / "생성" 라벨을 붙인다.
- [ ] 판단과 생성이 함께 있는 단계를 에이전트(서브에이전트) 후보로 표시하되, 자동으로 확정하지 않는다.
- [ ] 순서가 명확한 흐름은 먼저 LangGraph 노드·엣지로 구현해 동작을 확인한다.
- [ ] FAQ 외 문의 같은 정해진 응답은 모델 없이 고정 문구 노드로 처리하고, 상담원 연결(handoff) 경로를 둔다.
- [ ] Deep Agent로 옮길 때 1차로 시스템 프롬프트에 단계 순서를 적어 basic 버전을 만든다.
- [ ] 순서 보장이 필요하면 도구가 현재 단계를 읽고, 어긋나면 거절하고, 다음 도구를 알려 주는 구조로 바꾼다(첫 도구 강제 호출 고려).
- [ ] 단계 진행 기록을 남기고 검증할 수 있게 한다(MemorySaver처럼 메모리에만 두지 않는다).
- [ ] Claude에게는 작은 범위로 나눠 요청하고, 망치면 버리고 다시 받는다.
- [ ] 작업 성격에 따라 모델과 effort를 조절한다(깊은 작업은 높게, 대화형 반복은 낮게).
- [ ] 도구 개수가 과도하지 않은지 점검하고, 안정성을 유지하며 컴팩트하게 줄인다.

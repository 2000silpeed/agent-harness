## 3일차 3강 — 싱글에서 멀티로: 배달앱 메뉴 태깅 사례

> 출처: 「3일차 3강 다시보기」(2026-11-04, 55:06, 자동 전사 whisper.cpp large-v3-turbo + 분석) · 「3일차 3강 장표」(16장, SDS AX Advanced)
> 다시보기 분석 제목: "배달앱 메뉴 검색 개선 사례로 보는 싱글 에이전트에서 멀티 에이전트로의 전환"

### 핵심 요약 (3~5줄)

- 강사가 경험한 **배달앱 메뉴 검색 개선** 프로젝트: 검색어 "엽떡"을 가맹점명 "엽기떡볶이" → 하위 카테고리 "떡볶이" → 대카테고리 "분식"으로 태깅. 목표(골)는 **태깅**, 실시간이 필요 없어 **배치**로 실행, 가장 큰 병목은 **수천만 건이라는 양**.
- 진화 과정: 조회 도구 + 시스템 프롬프트(맵핑 룰·퓨샷) → 프롬프트가 **3만 토큰**까지 커져 대카테고리별 **스킬**(20개 내외)로 분리·분업 → 100만 건 규모에서 비효율 → **라우팅 컬럼**(DB)·후보군 추리기·후보 선택 단계 분할 → 데이터 **미리 조회 + 캐시 유지** → 스킬 로드 비용과 **컨텍스트 격리** 때문에 카테고리별 **개별 에이전트**.
- 사람이 확정한 결과를 **골드 데이터셋**으로 삼아 AI 판단을 평가하고 스킬·프롬프트를 보정.
- 일정 압박(약 5천만 건, 하루 100만 건 남짓 → 50일)으로 모델을 31B → 8B로 줄이고 프롬프트를 두 배로 늘렸는데, **잘게 나눈 단계** 덕분에 대응 가능했다.
- 결론: **싱글(스킬)로 시작하고 컨텍스트 격리 등 분리가 필요할 때만 멀티로**. 쪼갠 에이전트는 다시 합치기 어렵다. 지금 다시 한다면 LLM 대신 디시전 모델을 쓸 것.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**1. 요구사항: 검색어를 세 단계로 맵핑** (00:26~02:24)
- 사용자 검색어 "엽떡" → 단어사전 매칭 "엽기떡볶이" → 하위 카테고리 "떡볶이" → 대카테고리 "분식".
- "엽떡을 엽기떡볶이라고 바꾸는 건 그렇게 어려운 작업은 아니에요." 하지만 검색이 안 되면 사용자가 메뉴를 못 찾고 데이터 품질 문제로 이어짐. 사람이 하기엔 양이 너무 많아 에이전트로 요청받은 사례.
- "이 가장 큰 병목은 이거였습니다 양이 너무 많아."

**2. 목표를 먼저 정하고 실행 방식을 고른다** (03:16~04:27)
- 골 = 태깅(메뉴명·검색어 태깅). 사용자가 검색할 때마다 에이전트가 고민할 필요가 없음 → 실시간 불필요 → **배치**.
- "편안한 프로젝트군" 했지만 양 문제는 끝까지 남은 리스크.
- 강사 반복 강조: "이 에이전트가 하는 건 태깅이에요 … 그냥 컬럼에 데이터 쓰면 끝나는 거예요."

**3. 1단계: 도구 + 시스템 프롬프트의 단순 구성** (04:35~06:35)
- 툴 1: RDB 특정 테이블에서 가게명·메뉴명 **조회만**.
- 시스템 프롬프트: **맵핑** 담당(맵핑 룰 + 퓨샷). 맵핑은 기계적으로 할 수 없어 사람의 지식을 응용 — 퓨샷 예: "엽떡은 엽기 떡볶이의 줄임말이었다".
- 툴 2: 맵핑 결과를 **파일에 떨어뜨림**. "간단하죠? 간단한 접근입니다."

**4. 프롬프트 3만 토큰 → 카테고리별 스킬** (06:40~09:44)
- 케이스가 늘수록 로직(프롬프트)이 커짐. 처음 "무지성으로" 짰을 때 **3만 토큰** — 토큰 대비 품질이 안 오르고, 굳이 들어갈 필요 없는 내용도 있음.
- 대카테고리는 앱마다(배달의민족, 요기요 등) 어느 정도 정해져 **20개 내외**, 떡볶이 같은 하위 주요 메뉴는 **100개 미만**.
- 대카테고리를 스킬로 → 시스템 프롬프트는 "스킬을 참고해라 / 조회하고 맞는 스킬을 찾아 그대로 행해라" 수준으로 가벼워짐.

**5. 스킬 군으로 분업** (09:46~12:14)
- 강사가 큰 구조(스킬 호출·분배)를 잡고, 스킬 군을 개발자들에게 나눠 각자 다듬게 함("너는 분식해 너는 뭐 한식해"). 강사도 일부 스킬 군 담당.
- 그레이 영역은 분배 담당인 강사가 처리, **"기타" 스킬**을 둬서 큰 문제 아님.
- 품질이 꽤 잘 나왔고 "지금까지 단일 에이전트입니다. 왜냐하면 스킬만 달았잖아요."

**6. 규모를 늘리자 문제 → 라우팅을 미리 해 둔다** (12:17~15:53, 29:42~30:32)
- 배치·반복 작업인데 메뉴 하나마다 "어디로 가세요" 판단 → 스킬 호출 → 맵핑 리턴을 수천만 번 반복 → 비효율.
- POC 수준에서는 괜찮았으나, 운영 반영 전 개발계에 데이터를 내려 **100만 건**으로 늘리자 문제가 터짐.
- 해결: 먼저 도는 배치가 대카테고리를 확정해 **컬럼 하나**에 "분식 스킬을 호출하십시오" 한 줄을 미리 박아 둠(가야 할 스킬 지정).
- 상태 관리(스테이트)는 "그냥 DB에" — 개발 DB에 컬럼을 새로 파서 관리, "틀렸을 수 있잖아요" 그래서 **기록도 남김**.

**7. 단계를 더 쪼갠다: 후보군 추리기 → 후보 선택 → 상세 맵핑** (17:34~20:55)
- 강사가 앞선 설명을 정정: 카테고리 스킬보다 먼저 **후보군을 추리는 스킬**이 1단계. 예: 엽떡 → 엽기떡볶이, 신전떡볶이, 뜬금없는 "덮밥"까지 후보 가능.
- 대카테고리 스킬이 3개 정도 후보를 추리고, 3개를 다 돌리기엔 시간·자원이 부족 → 가능성이 가장 높은 곳을 정해 주는 스킬을 따로 둠("분식이 가능성이 가장 높네요. 거기 가세요").
- 맵핑도 **가능성**으로 맵핑되고, **리뷰하는 녀석**도 따로 있었음. "사람의 맵핑 로직을 따라 하려다 보니까 여러 번 돌게 했습니다."
- 회고: 대카테고리 후보 추리기 + 필터 두 단계는 "지금 와서 돌이켜보면 한 방에 할 수 있었는데" 두 단계로 나눴던 것 같다고 함.

**8. 데이터 조회는 미리 해 두고 캐시를 지킨다** (20:58~24:37)
- 분식으로 들어오면 분식집 가맹점명부터 메뉴명까지 조회해야 함 → 매번 새로 조회는 답이 아님, 너무 많아 다 넣을 수도 없음.
- **미리 조회**해 캐시에 넣어 두고 **뒤 데이터만 바꿔** 반복. 떡볶이 아래엔 떡볶이집만 있으니 대부분 추려짐.
- 하위 메뉴 단위 배치: 떡볶이 쫙 돌고, 라면 쫙 돌고 … 분식 하위 메뉴 약 100개 반복.
- 결과 예: "엽떡 떡볶이 가능성 90%, 매칭되는 가게명 엽기떡볶이 / 신전떡볶이 80%" → 다음 단계에서 확정.

**9. 골드 데이터셋으로 판단을 보정** (24:46~25:48, 31:37~33:37)
- 확정은 처음엔 사람이, 이후 사람이 한 것을 **골드 데이터셋(정답지)**으로 두고 AI를 맞춰 나감. 운영하며 쌓인 경험 데이터(엽떡 → 엽기떡볶이)도 활용. 골드 데이터셋은 계속 늘어남.
- 피드백은 구체적으로: 두루뭉술하게 "잘못됐다"가 아니라 "분식의 떡볶이까지는 맞았는데 가맹점명이 틀렸어요. 신전떡볶이 아니라 엽기떡볶이에요. 왜냐면 줄임말이었기 때문".
- 남은 케이스는 대부분 줄임말·SNS 신조어로 몇 개 안 됨. 최종 가맹점 선택은 **5개 내외** 후보에서.
- 루프: 골드 데이터셋 평가 → 문제 지점 발견 → 스킬/개별 에이전트 수정 → 골드셋 맞는지 확인 → 돌려 보고 픽스.

**10. 스킬에서 개별 에이전트로 (컨텍스트 격리)** (25:52~28:23, 31:03~31:32)
- 카테고리 선택 때마다 하위 메뉴 100개짜리 스킬을 매번 로드해야 하나? 스킬 로드도 하나의 "단계". 그냥 시스템 프롬프트에 넣을 수 없나?
- "얘가 서브 에이전트가 될 수 있겠는데? … 컨텍스트 격리의 측면에서요." → 분식·한식·중국집·아시안 등 **카테고리 담당 에이전트**.
- 한두 개 테스트 땐 잘 돌았지만 몇천만 건에선 불가 → "자연스럽게 … 서브 에이전트도 아니죠. 사실 개별 에이전트죠. 서브 에이전트라고 부르기도 좀 웃깁니다."
- 각 에이전트는 미리 조회된 데이터를 로드해 두고 자기 일만 반복, 성공하면 맵핑 기록만 남김. 모델 상황에 따라 여러 개를 동시에 못 돌리는 경우도 많았음.
- 강사 견해: 앞서 배운 멀티 에이전트 구조는 실시간(챗봇, AICC)을 많이 가정하지만, 실제로 많이 개발하는 건 **데이터 처리 배치**. 강사는 증권 시장 뉴스 데이터 처리 에이전트도 같은 방식(작게 시작 → 프롬프트 커지면 스킬로 → 단계 쪼개기)으로 출발했다고 함.

**11. 개별 에이전트의 컨텍스트 구성: 앞은 고정, 뒤만 바뀐다** (35:21~41:48)
- 라우팅 컬럼에 쓰면 라우팅 쪽 작업은 종료. 개별 작업자(에이전트)는 맵핑만 담당.
- 컨텍스트(세로 표기) 구성:
  1. **시스템 프롬프트** = 기존 `skill.md`를 가공한 것. 배치 한 번 도는 동안 고정(변경은 배치가 다 돈 뒤에).
  2. **고정 데이터 영역** = 중 카테고리(분식)의 하위 음식명 목록 약 100개(1번 라면/떡볶이, 2번 라면, 3번 오뎅 …).
  3. **변동 데이터 영역**(파란색) = 선택된 하위 음식명 기준으로 조회한 **가맹점** 데이터(떡볶이 → 떡볶이 가맹점명, 라면 → 라면 가맹점명; 중복 있음).
- 가맹점 매핑이 가능했던 이유: 가맹점주가 등록 시 "우리집의 대표 메뉴는 떡볶이입니다" 카테고리를 선택하는 기능이 기존 시스템에 있었음(강사가 만든 게 아님).
- 미적용 아이디어: 가맹점은 약 일주일 단위로 추가되니 일주일 단위로 고정해 한 번에 넣는 방안 — "실제로 프로젝트에서 적용해 보지 못했어요."
- 보정 지침이 개별 에이전트 프롬프트에 반영되도록 한 프로세스가 컸음 — 강사는 프로젝트 후 운영하지 않고, 가맹점·키워드는 계속 바뀌므로.

**12. 일정 압박: 모델을 줄이고 프롬프트를 늘렸다** (45:42~52:16)
- 약 **5천만 건** 처리, 완벽히 돌 때 하루 **150만 건**(전사: "150만 개가 좀 안 됐어요"), 실제는 매일 **100만 건 조금 넘게** → 나이브하게 **50일**. 시행착오로 시간이 얼마 안 남음.
- 개별 에이전트 모델: 처음 31B(BF16) → 8비트로 바꿔도 속도 불만 → 더 작은 모델(2B로 기억)은 BF16에서도 퀄리티 미달·탈락 → 27B급도 시도(5분 돌려 "수학으로" 추정) → 최종 **8B**로(약 4배 작게). 그동안에도 31B로 계속 배치를 돌림. 31B로 일부 진행 후 8B로 바꿔 나머지를 일정에 맞춤.
- 프롬프트는 약 **두 배** 늘림. 출력은 번호뿐("떡볶이 분식 1번", "떡볶이 3번")이라 가벼웠지만, 작은 모델은 판단 과정이 어긋나 생각 순서(1번 … 2번 … 3번 … 4번)를 프롬프트로 지시 → "그냥 룰베이스 프로그램이었다고 생각해요."
- "모델을 바꾼다는 건 … 최악의 판단"이고 프로세스 전체가 흔들렸지만 "정말 잘게 나눈 단계들이 많은 도움이 됐습니다. 이게 만약에 통짜 하나였다? 지옥이 펼쳐졌을 것 같아요."
- 배치 완료 후 8B를 "얼른 없애버렸고"(쓰지 말라고 했던 모델이라) 31B로 되돌려 운영 시 그걸 쓰라고 인계.

**13. 결론: 싱글로 시작하고 필요할 때 나눈다** (52:20~54:36)
- 지금 다시 한다면: "이거 모델 안 쓸 거예요 … 그냥 디시전 모델 하나 굽고 있을 거 같아요." (당시엔 디시전 모델이 나오기 전)
- "이 컨텍스트 격리가 필요하면 쓰고, 아닌 말고 내 방식으로 접근."
- Claude가 싱글 에이전트를 강조하는 이유: 일단 스킬로 출발하고, 스킬이 너무 많아 분리 필요성이 생길 때 분리하라는 것. "시작부터 분리하십시오 별로 좋은 방식은 아니었습니다."
- 쪼갠 개별 에이전트는 다시 하나로 합치기 어려움(퀄리티가 안 나옴). "잘 만든 프로그램은 안 건드리는 게 최선 … 다시 못 합칩니다. 그냥 다시 만들고 말지."
- 단계가 나뉘어 있으면 기존 에이전트들을 볼 때도 어떻게 도는지 이해하기 쉽고, 새 에이전트 설계(디시전 모델 활용 등) 판단에 도움.

### 실습/데모 내용 (명령어, 파일 구조, 프롬프트, 코드 조각 등 원문 그대로 보존)

- 본 강의는 사례 설명·판서 중심, 코드 실습 없음. 오후에 멀티 에이전트 예제 코드로 실습 예정(식사 후 1시 복귀).
- 1단계 구성(장표): `조회 도구(RDB에서 가게명·메뉴명) → 시스템 프롬프트(맵핑 룰 + 퓨샷) → 결과 도구(맵핑 결과를 파일로)`
- 퓨샷 예(원문): "엽떡은 엽기 떡볶이의 줄임말이었다"
- 스킬 분리 후 시스템 프롬프트 요지(원문): "스킬을 참고해라 / 도구는 조회하고 맵핑 결과 이렇게 두 가지를 실행해라 / 조회하고 나서 그에 맞는 스킬을 찾아라 / 실행해라 / 그 스킬대로 행해라"
- 라우팅 컬럼 값 예(원문): "분식 스킬을 호출하십시오" / "후보는 세 개였는데 그 중에서 가장 가능성 높은 분식으로 가십시오"
- 단계 흐름: `후보군 추리기 스킬 → (가능성 높은 후보 선택 스킬) → 카테고리 상세 맵핑 → 리뷰 → 확정(사람/골드 데이터셋)`
- 중간 결과 예(원문): "엽떡 떡볶이 가능성 90% / 매칭되는 가게명 엽기떡볶이 / 신전 떡볶이 80%"
- 개별 에이전트 컨텍스트(판서, 세로 = 호출 컨텍스트):

  ```
  [고정] 시스템 프롬프트 ← skill.md 가공
  [고정] 데이터: 중 카테고리 분식 / 하위 음식명 (약 100개)
         1번 라면 떡볶이, 2번 라면, 3번 오뎅 …
  [변동] 데이터: 선택된 하위 음식명의 가맹점명 조회 결과
         (떡볶이 → 떡볶이 가맹점 / 라면 → 라면 가맹점)
  → 결론: 엽떡이 뭐냐, 어디에 맵핑해야 되냐
  ```
- 출력 형식: 번호 출력("떡볶이 분식 1번", "떡볶이 3번").
- 처리량 수치: 전체 약 5천만 건 / 하루 150만 건(완벽할 때, "좀 안 됐어요") / 실제 100만 건 조금 넘음 / 약 50일.
- 모델 변경 이력(전사 기준, 모델명 불확실): 31B BF16 → 8비트 → (2B급 탈락) → (27B급 시도) → 8B. 프롬프트 약 2배.

### 강사 팁·주의사항

- 에이전트의 골(목표)을 먼저 정의하고(여기선 태깅), 실시간 필요 여부로 실행 방식(배치/실시간)을 결정.
- POC 소량 데이터에서 잘 돌아도 규모(100만 건)를 키우면 바로 비효율이 드러나니, 운영 전 개발계에서 건수를 늘려 검증.
- 프롬프트가 비대해지고(3만 토큰) 토큰 대비 품질이 안 오르면 스킬로 분리.
- 반복 배치에서 건마다 라우팅 판단하지 말고, 선행 배치로 라우팅 결과를 컬럼에 저장. 상태는 DB로 관리하고 기록을 남길 것(틀릴 수 있으니).
- 데이터는 미리 조회해 캐시 앞부분을 유지하고 뒤쪽 데이터만 바꿔 반복.
- 사람 피드백은 구체적으로(어느 단계까지 맞고 어디가 왜 틀렸는지).
- 보정 지침이 프롬프트에 반영되는 프로세스를 만들어 두면 인수인계 후에도 대응 가능.
- 모델 교체는 "최악의 판단"이지만, 단계를 잘게 나눠 두면 대응할 수 있음. 작은 모델일수록 생각 순서를 프롬프트로 지시.
- 많이 개발하게 되는 건 실시간보다 데이터 처리 배치 에이전트인 경우가 꽤 있음.
- 분류성 작업이라면 지금은 LLM 대신 디시전 모델을 고려(강사 견해).
- 처음부터 멀티로 쪼개지 말 것 — 다시 합치기 어렵다.

### 실제 프로젝트에 적용할 체크리스트 (- [ ] 행동 지침 형태)

- [ ] 에이전트의 골(최종 산출물)을 한 문장으로 정의한다(예: "컬럼에 태깅 값 쓰기").
- [ ] 실시간 대응이 필요한지 판단하고, 아니면 배치로 설계한다.
- [ ] 데이터 총량·일일 처리량·완료 기한을 먼저 계산해 일정 리스크를 확인한다.
- [ ] 첫 버전은 조회 도구 + 시스템 프롬프트(룰·퓨샷) + 결과 저장 도구로 단순하게 만든다.
- [ ] 시스템 프롬프트 토큰 수와 품질을 추적하고, 비대해지면 카테고리별 스킬로 분리한다.
- [ ] 스킬 군 단위로 담당자를 나눠 분업하고, 그레이 영역용 "기타" 스킬을 둔다.
- [ ] POC 이후 개발계에서 데이터 건수를 크게 늘려 처리 효율을 검증한다.
- [ ] 반복 배치의 라우팅은 선행 배치로 미리 계산해 DB 컬럼에 저장하고, 판단 기록을 남긴다.
- [ ] 판단을 후보군 추리기 → 후보 선택 → 상세 맵핑 → 리뷰 단계로 나눈다(합칠 수 있는 단계는 합친다).
- [ ] 반복 조회 데이터는 미리 조회해 캐시 앞부분(시스템 프롬프트·고정 데이터)을 유지하고 변동 데이터만 뒤에 붙인다.
- [ ] 사람이 확정한 결과로 골드 데이터셋을 만들고 계속 늘린다.
- [ ] 골드 데이터셋 평가 → 틀린 지점 특정 → 스킬/프롬프트 수정 → 재평가 루프를 운영한다.
- [ ] 사람 피드백은 "어느 단계까지 맞고, 무엇이 왜 틀렸는지" 형식으로 기록한다.
- [ ] 스킬 로드 비용·컨텍스트 격리 필요가 확인될 때만 카테고리별 개별 에이전트로 분리한다.
- [ ] 모델 교체 가능성에 대비해 단계를 잘게 나누고, 출력은 번호 등 단순 형식으로 둔다.
- [ ] 작은 모델로 바꿀 경우 판단 순서를 프롬프트에 명시하고 골드셋으로 재검증한다.
- [ ] 분류성 작업은 LLM 대신 디시전 모델로 대체 가능한지 먼저 검토한다.
- [ ] 운영 인계 시 사용할 모델·보정 프로세스를 문서화한다.

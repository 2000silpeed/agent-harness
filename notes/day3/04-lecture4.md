### 핵심 요약 (3~5줄)
- 해커톤 1등 솔루션인 해킹 멀티에이전트 시스템(아르텍스)은 쏟아지는 데이터를 **'해킹 가능성'(SQLite)** 과 **'시도 과정·결과'** 두 갈래로 나눠 관리해 목적을 달성했다. 같은 구조를 블루팀(방어)에도 써 볼 수 있다는 아이디어를 공유했다.
- 싱글인지 멀티인지보다 **"내 작업을 잘 해 주고 시간이 적정한가"** 가 기준. 스킬을 먼저 싱글로 만들고, 굉장히 커지면 서브에이전트로 넓힌다. 앤트로픽은 요즘 싱글 에이전트 + 좋은 모델을 강조(멀티는 토큰을 많이 씀).
- 프롬프트 → 컨텍스트 → 하네스는 "모델이 좋아지고 경험이 쌓이며 **다룰 대상이 바뀌었을 뿐**". 하네스 = **모델을 뺀 나머지 전부**(도구·컨텍스트·스테이트·권한·버짓·트레이스/이벨). 그래프·루프 엔지니어링은 "별것 아니다".
- 실습 준비: `Day03_new`에서 `.env.example` → `.env` 복사, 앤트로픽 API 키 + **jev API 키**를 **손으로** 입력.
- 각자 실제 업무 워크플로우를 **5단계 이하**로 `architecture.md`에 작성 → 이후 딥 에이전트에 녹이고 일부를 에이전트로 바꿔 성능 개선하는 실습 예고. 2시 5분 재개.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)
- **해킹 가능성 / 시도 결과 분리 관리 (아르텍스 사례)**
  - 해킹 가능성 데이터: "어떤 시스템의 1번에 무슨 취약점이 있는 것 같애" → SQLite로 따로 관리.
  - 해킹 프로세스 데이터: "그 있는 것 같애를 시도했는데 이렇게 해서 막혔고 저렇게 해서 막혔어"를 기록.
  - 세부적으로는 더 쪼개져 있었지만 크게 두 갈래. 원본 레포는 해킹 해커톤 1등 솔루션이며, 강사가 확인한 사용 모델은 **GLM과 딥시크**.
  - 강조 이유: 멀티에이전트가 실제 프로젝트뿐 아니라 사회에도 영향을 끼치고 실제로 활용된 사례가 등장하기 시작했다("멀티에이전트 무섭다", "실제로 돈이 되는구나").
- **취약점 대란과 PHP 일화**: PHP(PHP to Shell)·Node.js 등 온갖 언어에서 취약점이 쏟아짐. PHP는 재단의 정식 보안 패치 전에 공유된 것이 문제. 최종 해결책은 변함없이 "업데이트를 한다". 운영자가 없는 버려진 PHP 시스템이 많아, 개발자들이 같은 방식(프로그램 실행 가능 취약점)으로 들어가 "대문 따고 들어가서 업데이트 해주고 나오고"를 했다는 이야기가 X에 많이 올라왔다. Node.js는 공식 업데이트로 해결.
- **레드팀 구조의 블루팀 응용 (아이디어)**: "뚫릴 수 있는 가능성"과 "이렇게 오면 이렇게 막는다"를 짝지어 관리하는 구성. AI가 공격하면 사람이 똑같이 막을 수 없으므로 운영자도 AI로 방어해야 한다. 단, 강사 본인도 보안 비전문가라 "막연한 생각"이라고 전제.
- **싱글 에이전트 우선 접근**: 경험상, 그리고 요즘 에이전트 개발 구조상 "스킬을 먼저 싱글로 만들어주고 그 녀석이 굉장히 커져서 서브에이전트로 가거나" 하는 방식이 "훨씬 더 좋은 접근"(챕터 3 자료에 정리). 앤트로픽 테스트 결과를 근거 자료로 제시 — "좋은 모델로 돌리십시오", 좋은 모델이면 평가 퀄리티가 좋아지고, 멀티에이전트는 토큰 사용량이 꽤 많다.
- **프롬프트 엔지니어링**: 모델 하나만 경험하던 챗봇 시절, 모델이 "말도 똑바로 못했기" 때문에 입력으로 대답을 제어하는 것이 중요했다. GPT-4 이후 "좀 똑바로" 하게 되며 중요도가 조금씩 줄어듦.
  - 프롬프트는 **역할놀이가 아니라 지시문**: "너는 환불 전문가야" 같은 페르소나 놀이 대신 **작업(무엇을) · 근거(어떤 데이터) · 출력(내야 하는 결과) · 제약사항**을 담는다. 권한은 요즘 쓰지 않아도 되지만 있으면 첨부 자료로 줄 수 있다. "너는 환불이라는 프로세스를 다루게 될 것이다" 정도의 가이드는 가능.
- **컨텍스트 엔지니어링**: RAG로 데이터를 넣을 수 있게 됐는데 데이터가 너무 많아짐 → "이 데이터를 이때 넣어야 돼 말아야 돼", "뭘 넣어줘야 얘가 내 말을 잘 들을까"를 설계하는 고민.
- **하네스 엔지니어링**: 에이전트가 돌아가는 **런타임을 제어**하는 것. 프롬프트·데이터가 괜찮아지면 루프를 돌기 시작하는데, 루프 과정에서 프롬프트만으로 제어할 수 없는 것을 "내가 잘 아는 프로그램으로 제어할 수 없을까"가 하네스 고민의 시작.
  - 구성: 도구, 컨텍스트(그 안의 스테이트), 도구에 대한 권한(퍼미션), 호출·시간 한도(버짓), 트레이스·이벨.
  - **모델은 포함하지 않는다** — 모델은 그 자체로 다룰 내용이 워낙 많고, 에이전트 = 모델 + 도구이므로 "그냥 모델 뺀 나머지를 다 하네스라고 부른다".
  - 수강생 진도: 도구·컨텍스트·스테이트는 많이 봤고, 퍼미션은 어제 조금, **버짓은 아직 제대로 다루지 않음**(어제 리커전 리밋 정도).
  - "하네스부터는 대부분 코딩"이라 에이전트의 기술이라 부르기는 어렵다고 봄.
- **그래프 엔지니어링 / 루프 엔지니어링**: 에이전트 여러 개를 어떻게 엮어 실행할지의 고민.
  - 그래프: "뭐가 다음 작업에 실행될 것인가"를 노드와 엣지로 표현. "엑스칼리드로에 동그라미 그리고 화살표… 이거 잘 그리면 그래프 엔지니어링이라고 부릅니다. 말장난이죠." — 엔지니어링을 붙이기 부끄러운 단어라고 표현.
  - 루프: 하나의 에이전트를 **멈춤 없이** 돌리려면(루프를 깨지 않으려면) 어떻게 해야 하는가에 초점.
- **워크플로우 + 에이전트를 녹인 작은 시스템**: 권한 확인 → 의도 라우팅 → (단순 조회면 에이전트 없이 바로 답변) / 그 외는 **O-W(오케스트레이터 워커)** — 작업 계획 수립 → 작업 진행 → 답변 → 사람이 답변 확인. O-W는 "플랜 앤 이그제큐트랑 같은 것".
- **구조 선택 리뷰**: 프로젝트 후 "내가 왜 이런 구조를 선택했을까? 장단점이 있었을까?"를 **무조건** 리뷰. "굳이 서브 에이전트를 썼어야만 하는 건가?" 싶을 만큼 아쉬운 경우가 많았다. 글로벌 프론티어 랩들은 실험을 많이 하고 결과를 쉽게 공유하므로 그 방향을 최대한 쫓아가라.

### 강사 팁·주의사항
- **API 키는 절대 Claude에게 시키지 말 것**: "이거는 당연히 클로드랑 작업하시면 안 돼요. API 키입니다. 엄청 민감한 자료예요. 이거 클로드한테 시키시면 키 바로 막힙니다. 이 정도는 우리가 사실 손으로 해줘야 됩니다."
- 워크플로우는 **5단계 이하** — "5단계가 넘어가면 아마 2시간 안에 만드시는 건 거의 불가능… 괜찮은 퀄리티로 만드시는 건 거의 불가능하실 겁니다."
- 싱글/멀티는 부차적: "내 작업을 잘 해줄 수 있고 그게 적정한 시간인가만 따지면 되는 거 같아요."
- 단순 조회는 굳이 에이전트를 돌리지 말고 라우팅으로 바로 답변.
- 프로젝트가 끝나면 구조 선택 이유와 장단점을 반드시 리뷰하고, 프론티어 랩의 공유 결과를 참고.
- 주피터(Jupyter)는 쓸지 말지 강사도 고민 중("안 쓰는 게 맞는 것 같기도 하고").

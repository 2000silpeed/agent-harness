## 4일차 5강 — 잘 쓴 스킬, 못 쓴 스킬

> 출처: 「4일차 5강 다시보기」(전사·분석, 45:42 분량), 「4일차 5강 장표」(17장). 다시보기 분석 제목: "좋은 스킬 vs 나쁜 스킬 비교와 에이전트 도구 생태계 동향"
> 구성: 앞 약 17분 스킬 비교 → 16:52~약 21:50 수강생 실습(전사 거의 없음) → 뒤 약 24분 도구·사례 이야기(MCP, 컴퓨터 유즈, 브라우저 유즈, Spotify 토큰 절감)

### 핵심 요약 (3~5줄)
- 실습 저장소의 `diagram-design` 스킬(못 쓴 예)과 LangChain `deep-agents` 코어 스킬(잘 쓴 예)을 나란히 놓고 비교했다. 길이(약 400줄 vs 약 444줄)는 비슷하지만 **description 길이**와 **구역 구분 방식(마크다운 헤더 vs XML 태그)**이 결정적으로 다르다.
- description은 What/When만 짧게 쓰고(What은 이름에 맡겨도 됨), 본문은 처음부터 끝까지 다 읽히기보다 **중요한 것만 남기고 나머지는 필요할 때 찾아가 읽게** 설계해야 한다. 스킬을 몇 개로 나눌지는 설계자 선택이다.
- 실습: 내 스킬에 XML 구분을 넣어 Claude로 개선하고 이후 eval까지 이어간다.
- 후반에는 NVIDIA auto-ontology, 업스테이지 세금 계산 MCP, 한국 법령 MCP, 컴퓨터 유즈(가상 Mac, vercel-labs agent-desktop, CUA), 브라우저 유즈(jev-ultrafast), Spotify의 Claude Code 토큰 90% 절감 사례를 소개하며 **"도구 쓰는 법도 스킬에 적어야 한다"**고 정리했다.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**1. 못 쓴 예: `diagram-design` 스킬**
- 위치: 수강생 저장소의 `.agents/skills/diagram-design/SKILL.md` (또는 `.claude` 아래로 봐도 됨). 수업 중 계속 참고 가능.
- 도입 배경: 코드로 다이어그램을 그릴 때 Mermaid를 가장 많이 썼는데 "못생겨서", 발표·강의 자료용으로 예쁘게 그려 주는 도구를 찾다가 한두 달 전 화제가 된 이 스킬을 쓰게 됨. 강사는 실제로 많이 활용 중.
- 내용: 디자인 시스템 약 45개, 출력은 HTML·SVG·PNG. 오픈 스킬이라 라이선스·버전 표기가 있음(이 정도는 넘어갈 수 있음).
- 문제점 ①: **description이 너무 길다** ("시작부터 압도", "이것부터 화가 난다").
- 문제점 ②: **본문이 여전히 길다.** 지난달 강의 때는 약 4000줄("정확하게 곱하기 10")이었고, 작성자(개발자 아님)가 PR을 받아들여 reference 문서로 빼면서 500줄 미만으로 줄었다. 그래도 0~12번 절(철학 → When to use → 그래프 패턴/안티 패턴 → 디자인 시스템 → SVG·레이아웃 → 요약 카드 → 그림 설명 → 체크리스트(출력 전 확인) → 템플릿·기존 그림 import → 최종 출력)을 차례로 다 읽어야 하는 구조라 "읽다가 지칠 것 같다".
- 강조 이유: AI 입장에서는 필요한 것만 찾아가서 읽고 싶다. "왠 투 유즈(When to use) 처음부터 있으면 안 돼요." 공통 지침·안티 패턴처럼 뺄 수 없는 것만 본문에 두고 나머지는 찾아가 읽게 설계하는 게 제일 좋다.
- 잘한 점: **폴더 구분** — `scripts/`, `references/`(케이스별로 그래프 그리는 법을 촘촘히 정리), `assets/`(그릴 때 참고할 자료). 이 스킬도 대부분 AI가 썼고 정리할 곳은 여전히 남아 있다.

**2. description = What + When (짧게)**
- 강사가 diagram-design에 적용한다면: When = "다이어그램이 필요하면 이거 쓰세요", What = "45개 디자인 지원 + 대표적인 것 한두 개만 슬쩍".
- 이름과 description은 같이 읽히므로, What이 이름에 이미 드러나면 과감히 생략해도 좋다.

**3. 잘 쓴 예: LangChain `deep-agents` 코어 스킬**
- 길이 약 444줄(diagram-design과 비슷). 그러나 "일단 디스크립션이 짧아요."
- description: deep agent 애플리케이션을 만들 때 무조건 호출하라고 하고, `create_deep_agent` 함수, 하네스 아키텍처, SKILL.md 적용, 여러 설정을 건드릴 때 반드시 호출하라고 명시. **What은 없고 이름에 맡김**, 강조할 부분은 **대문자**로 어필.
- 본문을 **XML 태그로 구역 구분** — "XML로 구분하는 게 요즘 모델들이 잘 인식하는 형태". XML 안에는 일반 텍스트.
- 구역 흐름(장표 기준): ① When to use · 미들웨어 고르기(middleware selection) ② 예제 코드(Python·TypeScript 두 SDK, 짧아서 본문에 둠) ③ 전체 설정(full configuration) · 기본 도구(플래닝, 파일 시스템, 위임(delegation)) ④ SKILL.md 쓰는 법(deep agent도 스킬을 로드할 수 있으므로) ⑤ 스킬과 메모리의 차이 등.
- 예제 코드를 본문에 둔 것: 강사는 "썩 좋은 방식은 아니다, 예제는 따로 빼버리지"라고 보면서도, 스니펫이 짧아 한 단계를 더 타고 가지 않게 하려는 의도로 납득된다고 함.
- 특이점: SKILL.md 작성법 부분은 마크다운 구분선(`---`, "찍찍찍 세 개")으로 '페이지'를 넘긴 뒤 다시 XML을 시작하고, 그 안의 가이드는 마크다운으로 준다. 강사는 "왜 그런지 모르겠다"고 함.
- 효과: 세부 내용을 안 읽어도 제목·구역만 훑으면 무엇을 설명하는지 읽힌다. AI 입장에서 더 잘 읽히는 구분이 XML.

**4. 스킬을 나눌까, 합칠까**
- deep-agents는 core, memory, orchestration, Python quickstart, TypeScript quickstart **5개로 펼침**(지식을 따로 저장: 메모리 다룰 땐 memory 스킬, 오케스트레이션 땐 orchestration 스킬 호출).
- diagram-design은 **하나로 뭉침**(45개로 쪼갤 수도 있었음).
- "이거는 진짜 설계자 마음이어서" 잘잘못을 따지기 어렵다.

**5. NVIDIA auto-ontology** (발표 전날 공개된 프로젝트)
- 데이터 카탈로그를 표현하는 시맨틱 레이어를 만드는 프레임워크. SQL ERD를 분석해 외래키로 연결하고 객체끼리 연동해 온톨로지를 구성.
- 백본: PG 벡터(pgvector)·Postgres. ERD에 비즈니스 용어를 달아 매핑. LangChain 사용.
- 목적: 텍스트-투-SQL 지원. 텍스트-투-SQL의 관건은 비즈니스 용어를 DB 쿼리로 바꾸는 **시맨틱 레이어**.
- 강사는 작은 ERD로만 시험해 봐서 "되게 좋다"고까지 판단하긴 어렵지만, 자동 연결 면에서 괜찮게 만들었다고 봄. LangChain 코드를 뜯어서 다른 걸로 바꿔 쓰면 되겠다는 의견.

**6. 이미 나와 있는 MCP들**
- **업스테이지 세금(세무) 계산 MCP**: 세무·회계는 수식으로 진행되고 수식이 자주 바뀌니 도구로 만들어 호출하자는 발상. 사례 — 강사 부모님의 지인이 집을 팔고 세무사에게 2억 원대 세금을 안내받았으나, Claude에 자료를 주고 "서치를 해라"라고 하자 이 MCP를 찾아 계산 → 8천만 원까지 떨어졌고, 누락분을 반영한 최종 세금은 1억 초반(약 1억 감소).
- **한국 법령 MCP**: 법령·판례를 AI가 찾고 인용까지. 만든 사람은 광진구청 8급 공무원(닉네임 "딴짓하는 류주임").
- 같은 개발자의 **한글 문서 파싱 도구**(1년 넘게 운영, 강사도 활용). DART(전자공시) 관련 MCP도 언급된 것으로 추정(불확실).

**7. 컴퓨터 유즈 (Computer Use)**
- 에이전트의 도구는 크게 브라우저 유즈 / 컴퓨터 유즈로 묶인다.
- 맥북 안에서 가상 Mac을 띄워 실행하는 프로젝트(사용자 PC를 뺏지 않기 위해).
- **agent-desktop (vercel-labs)**: 범용, macOS·Windows·Linux 가상 컴퓨터, x64·ARM 모두 동작. 강사는 아직 안 써봤으나 주변 반응은 괜찮다고 함.
- **CUA**: Computer Use의 약자, 컴퓨터 유즈 연구 프로젝트.
- 흐름: 사용자 PC를 뺏어가는 걸 극도로 싫어하므로 뒤에서 가상 컴퓨터를 돌리고, 그 인프라를 클라우드에 둔다 → "인프라 장사는 죽지 않는다". 컴퓨터 유즈 모델만 파던 국내 회사(Enhans로 추정)는 모델 성능의 비약적 향상으로 가치가 밀렸다고 언급.
- (여담) 팔란티어 FDE/FDSE 한국 채용 공고: 영업, 탄탄한 공학 배경, 경영진까지 고객 소통, 전략 수립, 근무시간 50%까지 출장, 영어 능통 등. Deployment Strategist 공고는 AWS SA(솔루션즈 아키텍트)와 비슷해 보였다는 감상.

**8. 브라우저 유즈: jev-ultrafast (browser-use 제작)**
- browser-use는 브라우저 유즈 전문 회사(browser-use, browser harness 등). 브라우저 툴콜링이 매우 느려서 이를 제어하려는 목적.
- 모든 브라우저 조작을 도구로 제공하고, jev(디시전 전용 모델)는 상황에 맞게 다음 도구를 고르기만 반복("실행하고 결과 주고"). 예시: 런던 가는 비행기 표를 7초 만에 예약(전사상 출발지 "시리에서", 불명확).
- 처음 페이지 읽기와 최종 페이지 도달 후에만 LLM이 들어가고, 중간 클릭·드래그에는 거의 끼어들지 않는다.

**9. 도구 쓰는 법도 스킬에 적는다 (이 단락을 소개한 이유)**
- "이런 도구가 이렇게 쓰여요 라고 얘기해 주지 않으면 그냥 못 써요." 있어도 못 쓰거나 한참 걸린다.
- 처음 연결했을 땐 느려도 괜찮지만, 매번 돌릴 땐 최적화된 경로로 빨라야 한다 → 스킬에 "이런 작업은 이 도구를 이용해 이렇게 동작하라"를 적는다.

**10. Spotify: Claude Code 토큰 90% 절감**
- 핵심: "리드하는 IO를 비싼 모델에 맡기지 않았다." 읽고 엑기스만 뽑는 건 작은 모델(예: Haiku)도 한다.
- 도구: Portal AI 플러그인(`portal-ai-plugins`) 중 **shunt**. IO 헤비 작업을 자체 명명한 모드("에이카", 표기 불명)로 돌림.
- 방법: **훅**으로 큰 파일을 읽을 때 `bulk read` 스킬을 강제로 호출 — "부탁하는 게 아니라 강제로 실시합니다". bulk read 스킬에는 스크립트가 있고 실행(invocation)은 작은 모델로 돈다.
- 강사도 돌려 보니 실제로 줄었다고 함. 링크는 `guide.md`에 정리 예정.

### 강사 팁·주의사항 (실전 팁, 흔한 실수)
- **description을 길게 쓰지 마라.** What/When만. What이 이름에 드러나면 생략해도 된다. 꼭 호출돼야 하는 조건은 대문자로 강조.
- **When to use를 본문 맨 앞에 두지 마라.** 흔한 실수 — 본문을 사람이 처음부터 읽는 문서처럼 0~12번 순서로 다 늘어놓는 것. 중요한 공통 지침·안티 패턴만 남기고 나머지는 reference로 빼서 찾아가 읽게 하라.
- **XML 태그로 구역을 나눠라** — 요즘 모델이 잘 인식하는 형태. 마크다운 헤더보다 AI가 더 잘 읽는다.
- 짧은 코드 스니펫은 본문에 둬도 된다(한 단계 덜 타게). 길면 파일로 빼라.
- `scripts/` · `references/` · `assets/` 폴더 구분은 좋은 습관.
- AI가 쓴 스킬도 계속 정리가 필요하다(4000줄 → 500줄 미만 사례).
- 스킬 분할은 정답이 없다 — 지식을 기능별로 나눌지 하나로 뭉칠지 설계 의도에 따라 정한다.
- **도구를 연결만 하고 쓰는 법을 안 알려 주면 못 쓴다.** 스킬에 "이 작업은 이 도구로 이렇게"를 적어 최적화된 경로로 돌게 하라.
- **읽기 IO는 비싼 모델에 맡기지 마라.** 훅으로 강제(모델에게 부탁 X)해서 작은 모델에 넘기면 토큰이 실제로 준다.
- 자주 바뀌는 계산·규칙(세무 수식 등)은 도구(MCP)로 만들어 호출하게 하라.
- 컴퓨터 유즈는 사용자 PC를 뺏지 않도록 가상 환경/클라우드에서 돌리는 흐름이다.

### 실제 프로젝트에 적용할 체크리스트
1. [ ] 내 스킬 폴더를 `SKILL.md` + `scripts/` + `references/` + `assets/` 구조로 정리한다.
2. [ ] description을 What/When 두 줄 수준으로 줄인다. What이 스킬 이름에 드러나면 When 위주로 쓰고, 반드시 호출돼야 하는 조건(함수명·작업명)을 대문자로 강조한다.
3. [ ] 본문 구역을 마크다운 헤더 대신 XML 태그로 감싼다(예: When to use, 선택 기준, 예제, 설정, 기본 도구 등).
4. [ ] 본문에는 공통 지침·안티 패턴 등 빠질 수 없는 것만 남기고, 케이스별 상세는 `references/`로 옮긴 뒤 "필요할 때 찾아가 읽어라"로 안내한다. 본문 맨 앞에 긴 When to use를 두지 않는다.
5. [ ] 짧은 예제 스니펫만 본문에 두고, 긴 예제는 파일로 뺀다.
6. [ ] 스킬을 하나로 둘지(뭉침) 기능별로 나눌지(펼침: core/memory/orchestration/quickstart 식) 의도를 정해 결정한다.
7. [ ] 방향(What/When, XML 구역)을 정해 Claude에게 개선을 맡긴다.
8. [ ] 개선한 스킬을 eval한다.
9. [ ] 스킬이 쓰는 도구(MCP, 브라우저/컴퓨터 유즈 등)마다 "어떤 작업에 어떤 도구를 어떻게 쓰는지"를 스킬에 적는다.
10. [ ] 큰 파일 읽기처럼 IO가 무거운 작업은 훅으로 강제해 작은 모델(예: Haiku)로 처리하는 bulk read 류 스킬을 검토한다(Spotify/shunt 사례 참고).
11. [ ] 자주 바뀌는 계산·법령·문서 파싱은 이미 공개된 MCP(세금 계산, 한국 법령, 한글 문서 파싱 등)가 있는지 먼저 찾아본다.
12. [ ] `guide.md`에 정리된 링크(Spotify 글 등)를 직접 읽어 본다.

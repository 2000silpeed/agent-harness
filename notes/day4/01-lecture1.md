## 4일차 1강 — 스킬과 MCP로 에이전트 능력 넓히기 (펑션콜링에서 MCP 도구 폭발까지)

> 출처: 「4일차 1강 다시보기 (보정)」(전사·분석, 37:44), 「4일차 1강 장표 (보정)」(8장). SDS AX Advanced · 2026-11-05.

### 핵심 요약 (3~5줄)
- 에이전트 능력은 데이터를 더 주거나 모델을 바꾸는 것만으로는 좋아지지 않는다. 모델은 이미 상향 평준화되어 있어 **업무 절차(스킬)**와 **정확한 실행 수단(MCP·코드)**에서 능력이 나온다.
- 세무·회계·법률처럼 숫자·정형 문서가 중요한 업무는 모델의 "거짓말"을 막기 위해 **검증된 코드를 실행해 그 결과를 그대로 출력**한다.
- 펑션콜링(2023년 7월, OpenAI)은 툴콜링으로 이름이 바뀌었고, 도구 오류는 **모델이 고칠 수 있는 것(400류)만 전달하고 런타임 오류(500류)는 숨긴다.**
- MCP는 API를 감싼 사실상의 표준이 됐지만 REST API를 그대로 감싸면서 **도구 폭발**(지라 MCP 약 80개)이 생겼고, 게이트웨이·가상 MCP 서버, **도구 검색 도구**로 대응하고 있다.
- MCP 프리미티브 중 실제로 쓰이는 것은 **툴**뿐이며(프롬프트·리소스는 버려지는 추세), 강사 PC는 MCP 3개로 도구 167개지만 도구 검색 도구 덕분에 컨텍스트 사용은 약 1.7%다.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**1. 오늘의 진행 방식: 직접 만들고 평가한다**
- 오늘 주제는 스킬과 MCP. 이론은 "어차피 정해져 있어서" 많지 않고, 직접 스킬을 만들고 평가하는 실습 중심.
- 강사 경험: 남의 괜찮은 스킬들을 보고 내 입맛에 맞게 고치다 보면, 스킬과 MCP를 연결하려 할 때 "결국 내가 만들어야 되더라".
- 팀원·회사에 공유되는 스킬이라면, 나는 트리거를 잘 알지만 남들은 모르므로 "그분들의 PC에서도 적재적소에 잘 로드되게" 하는 **스킬 이벨류에이션(평가)**까지 다룬다.
- 흐름(장표): 에이전트 루프 → MCP 부착 → 스킬 부착 → 평가.

**2. 에이전트 능력은 어디서 나오나**
- 데이터: RAG, RDB 연결도 해 봤지만 "그 데이터를 그냥 줘서 에이전트가 말을 잘하는 경우는 없죠" → 쓸모없는 말만 많아짐.
- 모델 교체: "이미 모델이 어느 정도 굉장히 상향 평준화가 되어 있어서" 드라마틱한 향상이 없다.
- 그래서 **어떤 데이터를, 언제, 어떤 순서로** 쓸지를 업무 수행 절차로 안내하는 **스킬**이 필요하다.
- 데이터 제공 방식: DB 커넥션 풀을 그대로 주지 않는다. MCP 같은 **프록시 레이어**로 감싸 사용 흔적을 모두 남기고, 오동작 시 방어·개선할 수 있게 한다.
  - 강조 이유(일화): 바이브 코딩하는 비전문가가 DB에 바로 꽂고 "얘가 DB를 날려먹었어요"라고 하지만, "권한을 주셨잖아요"밖에 할 말이 없다.

**3. 정확한 실행(코드 실행)**
- 세법 에이전트를 은행과 만든 경험: 세법 규정대로 계산하는 코드를 만들어 전문가에게 검증을 요청 → "너 도와주면 내가 잘리는 거 아니냐"는 강한 반발을 겪음.
- 검증된 코드는 실행하면 결과가 그대로 나온다. 모델이 숫자에서 거짓말을 자주 했기 때문에 "그 거짓말하는 현상을 해결하기 위해서 우리는 안정적인 코드를 택하게 된 거죠" → **코드 실행 결과를 그대로 출력**.
- 변호사 업무: 정형화된 문서는 문장이 거의 정해져 있고 사건마다 한두 문장만 바뀜 → "거의 코드". 그 두 줄만 생성하고, 중요한 내용을 포함했는지 **검증을 뒤에 한 번 돌린다**.
- 에이전트는 한 번 채팅하고 끝나지 않고 여러 사람이 반복 사용하므로 **품질 검증**이 필요하다.

**4. 에이전트 루프와 스킬·MCP 구조**
- 그림의 딥 에이전트는 "클로드 코드든 뭐든 편한대로 바꿔서 생각"해도 된다.
- 에이전트 루프가 가운데 있고 스킬과 MCP를 연결해 쓰는 구조: 사용자 요청 → 루프가 받아 어떤 도구를 쓸지 확인 → 다음 행동.

**5. 펑션콜링의 역사**
- OpenAI가 GPT-4 출시 이후 **2023년 7월** 펑션콜링 출시. 어필 포인트: "정교화된 메시지 만드느라 힘들었지? 기능으로 제공해줄게."
- 그 이전(2023년 초 RAG 개발 시기): 프롬프트에 출력 형식을 주고, 안 먹으니 예제를 3~4개씩 줘도 계속 실패 → 프로그램 안정성 저하 → **JSON 고치는(fix) 라이브러리**가 많이 등장.
- 펑션콜링 초기에도 출력이 깨져 실패가 잦았다. 내부적으로는 같은 요청을 여러 개 돌려 성공한 것만 보내줘서 낭비가 컸다.
- 같은 해 12월경 OpenAI가 "100% 성공시켜서 줄게"라고 발표.
- 문제점: 출력은 고정됐지만 "이걸 쓰면 모델의 성능이 떨어지는 겁니다" — 출력을 고정하면 모델 본래 능력 대비 성능이 떨어졌다.

**6. 툴콜링과 오류 전달 원칙**
- 에이전트 시대에 펑션콜링은 **툴콜링**으로 불리고, 이제 펑션콜링이라는 말은 모델 API 문서 외에는 찾기 어렵다.
- 모델은 도구의 **이름·디스크립션·인자(argument) 명세**를 보고 선택 → 실행 요청 → 시스템이 검증·실행 → 결과/오류를 모델에 전달.
- 오류 전달 원칙: 모델이 잘못 요청해서 난 오류는 "다시 요청해"라고 전달하고, 우리 시스템/런타임 오류는 우리가 고칠 일이니 전달하지 않는다. 결과는 사용자에게 다시 전달되므로 필터링이 필요.
- 비유: "400 에러는 사용자한테 보여줘도 500 에러는 보여주면 안 된다."

**7. MCP 개요와 도구 폭발**
- MCP 스펙 문서는 Model Context Protocol 웹사이트에 있으며, 원래 못생겼다가 최근 예뻐졌다. "이 그림 한 장이면 사실 MCP를 다 설명할 수 있어요."
- MCP는 모든 도구 호출의 표준이 됐다. 작년 초 **커서(Cursor)**가 붐을 일으킴 → "모든 것을 MCP로 만들자".
- "MCP는 사실상 API를 감싼 거거든요" → 기존 REST API를 껍데기만 감싸 제공 → **도구 대폭발**.
  - 구 버전 **지라 MCP**: 지라 하나 컨트롤에 도구 약 80개. 사람에게는 당연해 보여도 모델·에이전트에게는 너무 많아 헷갈림.
  - **노션**도 마찬가지였고 지금은 도구 개수를 엄청나게 줄였다.
- 연결 대상: 클라이언트(클로드 코드 등 온갖 앱), 데이터 소스(DB, 파일 시스템, Git, Slack·구글·MS 등 외부 서비스).
- MCP가 중간에서 하는 일: 인증, 그리고 SQL로 가져온 원본 데이터에 설명("살")을 붙여 의미를 부여하는 일. 정리하면 **① 온갖 데이터 소스에서 데이터를 끄집어내기 + ② 그 데이터에 의미를 부여해 AI에 전달**.
- DB 하나당 MCP 서버 하나씩 늘어나면서 **MCP 게이트웨이**(Apache 라이선스 오픈소스로 언급) 등장: 원본 MCP 서버를 등록하고 게이트웨이만 엔드포인트를 제공, 가운데서 **권한 관리**, 그리고 "이럴 때는 이런 도구들의 조합으로 쓰십시오"라는 **가상 MCP 서버** 제공. 이제는 꽤 안정적이 됨.

**8. MCP 프리미티브는 사실상 툴**
- 프리미티브(내장 데이터 유형): **Prompts, Resources, Tools**.
- 수강생 대부분 툴 외에는 본 적이 없다. "툴로 다 되는 겁니다" → 프롬프트는 버려졌고, Anthropic도 잘못 만들었다고 인정하고 없애려는 중. 리소스는 "호흡기를 붙여줬는데 곧 없어질 것".
- 리소스는 API의 GET 역할이지만 제약사항이 많고, 툴은 "구현하기 나름"이라 더 유연하다(GET도 툴이 오히려 잘함).
- **툴의 구성**: 함수 하나, API처럼 엔드포인트를 가질 수 있음, 네임과 디스크립션으로 제공.
- **tools/list**: MCP 서버가 기본 제공하는 API. 클라이언트가 연결되자마자 강제로 호출해 네임·디스크립션 목록을 받아간다 → 이것 때문에 도구 폭발 문제가 생김. 이후 그 리스트 중에서 골라 개별 툴을 호출.
- **롱 러닝 태스크**: 최근 스펙. 서버에서 오래 도는 작업을 "요청 확인 → 수행 중 → 완료"처럼 비동기로 응답할 수 있게 하는 프리미티브 타입 객체. 툴콜링 자체를 비동기로 할 수 있게 됨.

**9. MCP 활용 방향 (노션 MCP 사례)**
- 노션 MCP 서버 문서의 Supported tools: 정보 읽기, 노션과 작업, 페이지 생성, 노션 내 데이터베이스 관리, 일정 관리 등 → 노션 기능 대부분을 담고 있음.
- MCP가 새로운 SaaS 형태로 각광: 창업자들은 "내 서비스를 사스로 팔 생각이 별로 없습니다. 왜냐면 안 팔리거든요" → 대신 클로드 코드·코덱스 연동이 쉬운 MCP로 서비스를 제공하려는 니즈가 늘어남.
- MCP를 만들 때 고민할 핵심은 거의 하나: **"도구 리스트를 어떻게 줄여서 제공할 수 있을까"**.
- MCP는 백엔드 API가 밟아온 길(API 문서가 너무 많아 힘들었고, 줄이고 잘 찾게 하려던 고민)을 똑같이 밟고 있다 → "우리 API 만들던 그 지식 그대로 활용해 보시면 좋습니다."

**10. 도구 검색 도구 (도구 167개, 컨텍스트 1.7%)**
- 강사 PC(클로드 앱 기준) 연결 MCP: draw.io(그래프 그리기), 구글 드라이브, Git 넥서스(코드베이스를 그래프로 그려주는 도구, 제품명 미확인) — 단 3개.
- 그런데 도구 수는 **167개** (클로드 기본 도큐먼트 기능, Claude in Chrome, 클로드 브라우저, MCP 레지스트리 등 포함).
- 모두 입력했다면 MCP 툴이 컨텍스트의 **약 17%**를 차지했어야 하지만 실제로는 **1.7%**. 클로드는 MCP 도구를 항상 다 로드하지 않고 "도구를 찾는 도구 하나만 줍니다."
- 강조 이유: 컨텍스트 관리에서 메인 밑에 서브를 두어 계층을 나눴던 것처럼, MCP도 **계층화**해서 관리한다.

### 실습/데모 내용 (명령어, 파일 구조, 프롬프트, 코드 조각 등 구체적으로 — 원문에 있는 그대로 보존)
- **API 키 안내**: Anthropic API가 너무 비싸서("제 카드가 빵꾸가 날 것 같아서") **오픈라우터(OpenRouter)**로 바꿀 예정. 오픈라우터에서도 Anthropic 모델 사용 가능하지만, 수업에서는 일부러 상대적으로 낮은 성능의 모델로 해 볼 예정. 가이드는 이후 제공. 발표 자료는 드라이브에 업로드됨.
- **펑션콜링 이전 프롬프트 예시(강사가 판서로 재현)**: 설명을 길게 준 뒤 "출력을 아래와 같이 ~해주세요" + JSON 형식, 예를 들어
  ```
  name: string
  age: int
  ```
  형식을 줘도 안 먹으니 예제를 3~4개씩 추가 → 그래도 계속 실패.
- **MCP 스펙 문서 확인**: Model Context Protocol 웹사이트의 구조도 한 장으로 MCP 설명.
- **노션 MCP 서버 문서의 "Supported tools"** 화면으로 도구 개수 훑어보기.
- **클로드 앱에서 연결된 MCP 도구 개수 확인**: draw.io, 구글 드라이브, Git 넥서스 연결 → 도구 167개. 컨텍스트 중 MCP 툴 비중 1.7%(전부 로드 시 17%).
- 과제: 이따가 MCP를 연동해 볼 때 "MCP 도구 진짜 얼마나 많지?" 하고 개수를 직접 확인해 볼 것.
- 휴식 후 스킬로 넘어감.

### 강사 팁·주의사항 (실전 팁, 흔한 실수)
- 데이터를 그냥 연결하거나 모델만 교체하는 것은 효과가 작다 → 데이터 사용 절차를 스킬로 안내하라.
- **DB 커넥션(풀)을 에이전트에 직접 주지 말 것.** MCP 등 프록시 레이어로 감싸 사용 흔적을 남겨야 오동작을 방어·개선할 수 있다.
- 숫자 계산이 중요한 업무(세무·회계)는 모델에게 계산시키지 말고, **도메인 전문가가 검증한 코드**를 실행해 결과를 그대로 출력하라. 현업 전문가의 검증 협조에는 반발이 있을 수 있다.
- 정형 문서(법률 등)는 바뀌는 한두 문장만 생성하고 필수 내용 포함 여부를 **사후 검증**하라.
- 여러 사람이 반복 사용하는 에이전트는 품질 검증이 필수.
- 도구 오류는 모델이 재시도로 고칠 수 있는 것(잘못된 요청, 400류)만 전달하고, 시스템/런타임 오류(500류)는 숨겨라.
- 출력 형식을 강하게 고정하면 모델 성능이 떨어질 수 있음을 기억하라(초기 펑션콜링 교훈).
- **REST API를 그대로 MCP로 감싸지 말 것** → 도구 폭발로 모델이 헷갈린다. 지라·노션도 도구 수를 크게 줄였다.

### 실제 프로젝트에 적용할 체크리스트 (이 강의 내용으로 실제 프로젝트를 만들 때 따라할 단계, 행동 지침 형태)
1. [ ] 에이전트가 수행할 업무를 "어떤 데이터를, 언제, 어떤 순서로 쓰는가" 절차로 정리하고, 이를 스킬로 만들 대상으로 표시한다.
2. [ ] 모델 교체로 해결하려던 문제를 다시 보고, 절차(스킬) 부족인지 실행 수단 부족인지 먼저 구분한다.
3. [ ] DB·외부 시스템은 직접 연결하지 말고 MCP 같은 프록시 레이어 뒤에 두고, 호출 로그(사용 흔적)가 남게 한다. 권한은 최소로 준다.
4. [ ] 숫자 계산·규정 적용처럼 정확성이 필수인 부분은 코드로 구현하고, 도메인 전문가에게 결과 검증을 받은 뒤 에이전트는 코드 실행 결과를 그대로 출력하게 한다.
5. [ ] 정형 문서는 템플릿을 고정하고 가변 문장만 생성하게 한 뒤, 필수 내용 포함 여부를 검증하는 단계를 뒤에 붙인다.
6. [ ] 도구 정의마다 명확한 이름·디스크립션·인자 명세를 작성한다.
7. [ ] 도구 오류 처리 정책을 정한다: 잘못된 요청(400류)은 모델에 재요청 안내로 전달, 런타임/시스템 오류(500류)는 숨기고 내부에서 처리.
8. [ ] MCP 서버를 만들 때 REST 엔드포인트를 1:1로 감싸지 말고, 툴 수를 줄이도록 설계한다(툴 중심, 프롬프트·리소스 프리미티브 의존 지양).
9. [ ] 오래 걸리는 도구는 롱 러닝 태스크(비동기: 요청 확인 → 수행 중 → 완료) 방식으로 응답하게 한다.
10. [ ] MCP를 연동한 뒤 실제 노출되는 도구 개수와 컨텍스트 점유율을 직접 확인한다.
11. [ ] 도구가 많아지면 도구 검색 도구(필요한 것만 찾아 로드), MCP 게이트웨이(권한 관리), 가상 MCP 서버(작업별 도구 조합)를 도입해 노출 목록을 줄인다.
12. [ ] 여러 사람이 반복 사용할 에이전트라면 품질 검증 절차를 마련하고, 이후 스킬 평가(트리거·실행)까지 이어서 계획한다.

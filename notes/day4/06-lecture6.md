## 4일차 6강 — MCP는 짧게, Skill은 길게

> 출처: 「4일차 6강 다시보기」(전사·분석, 21:39 분량), 「4일차 6강 장표」(14장). 다시보기 분석 제목: "MCP 전송 규격과 도구 설계 원칙, 그리고 Skill 실습 안내"
> 구성: 앞 약 11분 MCP 자체(전송 규격, 도구 설계) → 뒤 약 10분 Skill과의 연결·활용 사례(다른 AI 호출, 사내 모델, AI 카운실) → 마지막에 약 2시간 Skill 실습 안내

### 핵심 요약 (3~5줄)
- MCP의 전송 규격(transport)은 **STDIO**(로컬 프로세스 간 통신, 로컬 전용)와 **Streamable HTTP**(HTTP + SSE, 원격 가능) 두 가지다. 코드가 알아서 만들어 주므로 차이만 알면 된다.
- 로컬에는 무엇이든 실행해 주는 **Bash**가 있어 STDIO는 "소임을 다했다". 나만 쓰는 도구는 Skill 안의 파이썬 스크립트로 두고, MCP 서버는 로컬에서도 Streamable HTTP를 주력으로 한다.
- MCP 도구 설계에서 사람이 할 일은 두 가지: **파라미터 타입·description을 명확히 쓰기**, **비슷한 도구는 합쳐서 줄이기**(add/minus/multiply/divide → calculator 하나).
- Skill 본문에 쓸 수 있는 MCP 도구를 안내하고, 이미 만든 MCP 기능은 기능별 파이썬 파일로 나눠 **일회용 실행**을 권장. 상시 떠 있는 MCP 서버는 다른 AI 호출·사내 모델 IO 위임·AI 카운실 같은 용도에 쓴다.
- 오늘 남은 시간(5시 반 정도까지 약 2시간)은 업무 프로세스를 실제 Skill로 만들고, 다음 주 목·금 코딩 에이전트 프로젝트에 가져가 검사받는다.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**1. MCP 전송 규격(transport)**
- MCP 공식 문서에서 "transport"라 부르는 통신 규격. "이건 안 쓰셔도 됩니다, 어차피 우리 코드가 알아서 만들어 줄 거기 때문에" — 가볍게 차이만 이해.
- **STDIO (standard input/output)**: PC에서 로컬 프로세스로 띄워 바로 통신. 프로세스 간 통신이라 원격 통신 자체를 지원하지 않음 → "얘는 ONLY 로컬입니다".
- **Streamable HTTP**: 기존 HTTP 요청과 SSE(Server-Sent Events) 요청의 합. "엔드포인트 하나를 열어주면 짧으면 그냥 HTTP, 지속적으로 통신해야 되면 SSE". 기존 웹 기술과 다를 것이 없음. 원격 가능.
- 요즘: 내 PC에 프로세스를 띄우고 싶지 않아서 로컬에서도 HTTP를 쓰는 경우가 많고, 완전히 로컬용 MCP를 개발하는 경우는 거의 없다.

**2. 로컬에서 STDIO를 안 쓰는 이유 = Bash**
- Claude Code 환경에는 "아주 강력한 도구, 바로 BASH"가 있고, Bash는 모든 걸 실행해 준다.
- MCP의 역할은 데이터 소스(DB 조회 등)에서 데이터를 가져와 정리해 전달하는 것인데, 로컬에서 나만 쓰는 용도라면 굳이 그 중간 레이어를 둘 필요가 적다.
- 그런 도구(예: DB를 안정적으로 호출하는 도구)는 **Skill에 파이썬 스크립트로 두고** Bash로 실행한다. 필요한 건 파이썬 환경 설치 가이드 정도 → STDIO의 역할은 거의 없음. 개발·테스트 때도 강사는 HTTP로 통일하겠다고 함.
- 비교(장표 4): MCP 서버(STDIO)는 "에이전트 → 서버 → 데이터 소스", 내 PC에 프로세스를 띄워 둬야 함 / Skill + Bash는 "에이전트 → Bash → Skill의 파이썬 스크립트", 파이썬 환경 설치 가이드만 있으면 됨.
- 세부 도구는 API처럼 구성하게 될 것.

**3. 도구 설계: AI는 시그니처와 설명만 본다 (계산기 예제)**
- 덧셈·뺄셈·곱셈·나눗셈 + 에러 처리가 있는 calculator 코드. 사람에겐 코드가 다 보이지만 MCP로 노출되면 AI가 보는 건 **파라미터 타입과 description**뿐("요만큼만 보고 있습니다").
- 따라서: ① 받는 파라미터의 타입을 명확히 선언 ② 함수 설명(description)을 써 준다(예: "이건 계산기야").

**4. 도구는 합쳐서 줄인다**
- add, minus, multiply, divide처럼 쪼개서 여러 도구로 열지 말고 하나로 합칠 수 있는지 고민한다. 쪼갠 형태는 "우리 편하자고 만든 형태"이고, AI는 비슷한 도구 중에 골라야 하는 부담이 생긴다. 합치면 설명 하나만 읽으면 된다.
- "설명 잘 써주고 이 도구를 합칠 수 없나 고민하시면 됩니다. 그냥 그 두 개면 MCP는 충분해요."
- Tool Search와의 관계: Tool Search가 있어도 줄여야 한다. 실제 시스템과 MCP를 만들어 보면 처음엔 도구가 "말도 안 되게" 많이 나오고, 최대한 줄여도 클라이언트 입장에선 여러 MCP의 도구가 붙어 수백 개가 된다. Tool Search는 그 모든 MCP를 뒤져서 찾아 주는 것이고, 서버 쪽은 최대한 줄여서 줘야 한다.

**5. MCP 서버 만들 때 할 일 (장표 7)**
- 코드 고민은 AI가 한다. 사람이 정할 건: ① 타입과 설명을 쓴다(AI가 보는 유일한 정보) ② 도구를 합친다(최대한 줄여서 제공) ③ Streamable HTTP로 연다(세부 도구는 API처럼).

**6. Skill에서 MCP 도구 안내하기**
- Skill 본문에 "이 파일을 읽은 뒤 MCP 도구 7개(뭐, 뭐, 뭐…)를 쓸 수 있다"처럼 적는다. 더 명확히 하려면 `mcp__서버__도구` 같은 언더바 표기도 가능(크게 상관은 없음).
- 이렇게 안내하면 에이전트가 도구가 있는지 확인하고, 없으면 "있다며? 없던데?" 하고 알려 올 수 있다.
- 실습 저장소의 요구사항 인터뷰 MCP 서버가 도구 7개다(장표 8 주석).

**7. 이미 만든 MCP가 있다면: 일회용 실행 권장**
- MCP 서버 코드를 Skill에 그대로 넣어 즉시 실행하는 방식은 추천하지 않음 — 서버는 계속 러닝 상태여야 하기 때문.
- "무조건 일회용으로 실행하시기를 추천드립니다": 각 기능(도구)별로 파이썬 파일을 분리해 실행하고 결과를 바로 받게 한다.
- MCP 서버로 제공하는 이유는 **여러 번(반복해) 써야 하기 때문**.

**8. 떠 있는 서버로 다른 AI 부르기**
- 다른 AI를 CLI로 불러도 되지만, 항시 떠 있는 서버에 호출을 보내고 결과를 받게 하려면 서버로 띄워 두는 게 제일 좋다 → MCP 서버로 구성하는 방식을 많이 썼음(CLI가 생기며 조금 줄었음).
- 이유: CLI의 비대화형 실행이 구독 요금제에서 언제 빠질지 모른다. `claude -p`(비대화형으로 프롬프트를 보내고 결과를 받는 옵션)는 올해 6월 유료화를 검토·경고했다가 유저 반발이 심해 시행하지 않았지만 "언제 등 돌려도 이상하지 않다". 그러니 직접 제어하는 프로그램/서버로 우리 형식대로 결과를 받게 구성하는 게 안전.

**9. IO는 사내 모델에 맡긴다**
- Spotify 사례(작은 모델로 IO를 줄임, 실습 `guide.md` 1번 링크 'Portal by Spotify cut my Claude Code token usage by 90%')를 응용해, 작은 모델을 Haiku 대신 **회사가 자체 서빙하는 모델**로 바꾼다.
- 회사 서버와 고정적으로 통신하는 작은 MCP 서버를 두고 IO 작업이 뜨면 사내 모델을 호출 → Claude 비용 절약, 회사 코드 유출 걱정 감소. 단, 회사 인프라를 쓰고 고려할 것이 많다.

**10. AI 카운실 (강사 활용 사례)**
- Claude가 작업하면 Gemini·OpenAI에게 결과물 평가를 요청 → 불린(찬/반)으로 답하게 함.
- 의견이 갈리면(한 명 찬성, 한 명 반대) 사용자에게 묻지 않고(유저가 피곤해짐) **별도 대화 세션**에서 Claude·Gemini·OpenAI 셋이 "고칠 거야 말 거야" 합의해 오게 함. 제한 예: 50턴.
- Claude는 지적을 받으면 다시 보고 진짜 잘못됐으면 고침. 합의 결과로 Claude가 고칠지 결정.
- 각 200달러 계정 3개로 돌리면 오래 걸리지만 고퀄리티. 코드 리뷰에는 쓰지 않았고("답이 안 와요"), 예민한 **설계 결정** 하나하나를 내릴 때 많이 씀. 모두 MCP로 구현.

### 강사 팁·주의사항 (실전 팁, 흔한 실수)
- transport 코드는 직접 짤 필요 없다. 코드 생성이 해 준다 — "MCP는 실습으로 뭘 할 게 없어요."
- 로컬 전용 STDIO MCP를 굳이 만들지 마라. 나만 쓰는 도구는 Skill + Bash + 파이썬 스크립트로 충분. MCP 서버는 로컬에서도 Streamable HTTP로 연다.
- **흔한 실수: 도구를 기능별로 잘게 쪼개 여러 개 노출하는 것**(add/minus/multiply/divide). 합칠 수 있는지 먼저 고민하라.
- **흔한 실수: 타입과 description 없이 도구를 노출하는 것.** AI는 함수 본문을 보지 못하고 시그니처와 설명만 본다.
- Tool Search가 있다고 도구 수를 방치하지 마라 — 클라이언트에는 여러 MCP의 도구가 수백 개 붙는다.
- Skill에는 쓸 수 있는 MCP 도구를 명시해 안내하라(개수·이름).
- 기존 MCP 서버 코드를 Skill에 통째로 넣어 띄우지 말고, 도구별 파이썬 파일로 일회용 실행하게 하라.
- CLI 비대화형 실행(`claude -p`)은 구독에서 언제 빠질지 모른다 — 다른 AI 호출은 직접 제어하는 서버 구성이 안전.
- 회사 코드 IO는 사내 서빙 모델로 넘기는 것을 고려(비용·유출 측면). 다만 고려할 것이 많다.
- 모델 간 의견 충돌은 매번 사용자에게 묻지 말고 별도 세션에서 턴 제한을 두고 합의시켜라(설계 결정처럼 예민한 판단에 유용).
- Skill 숙제를 미루면 다음 주 프로젝트 때 할 일이 많아진다 — 그때 검사한다.

### 실제 프로젝트에 적용할 체크리스트
1. [ ] 만들려는 도구가 로컬에서 나만 쓰는 것인지 판단한다 → 그렇다면 MCP 대신 Skill 안 파이썬 스크립트 + Bash 실행으로 두고, 파이썬 환경 설치 가이드를 Skill에 적는다.
2. [ ] 여러 번 반복해 쓰거나 원격·공유가 필요한 도구만 MCP 서버로 만들고, transport는 Streamable HTTP로 연다(코드 생성은 AI에게).
3. [ ] 각 MCP 도구의 파라미터 타입을 명확히 선언한다.
4. [ ] 각 도구의 description을 "무슨 도구인지" 알 수 있게 쓴다.
5. [ ] 도구 목록을 검토해 비슷한 도구(add/minus/multiply/divide 류)를 하나로 합쳐 도구 수를 최대한 줄인다. 세부 도구는 API처럼 구성한다.
6. [ ] Skill 본문에 "이 파일을 읽은 뒤 쓸 수 있는 MCP 도구는 N개: …"를 명시한다(필요하면 `mcp__서버__도구` 표기).
7. [ ] 이미 만든 MCP 서버 기능을 Skill로 옮길 때는 도구별 파이썬 파일로 분리해 실행 → 결과 즉시 반환(일회용) 구조로 만든다.
8. [ ] 다른 AI(Gemini·OpenAI 등)를 불러야 하면 CLI 의존 대신 직접 제어하는 상시 서버(MCP) 구성을 검토한다.

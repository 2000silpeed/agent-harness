- 참고 스킬로 **mattpocock/skills**(Skills for real engineers), **pstack**(서브 에이전트 스킬 라이브러리, cursor/plugins), **insane-research**(한국인 개발자의 리서치 스킬)를 추천했다. 그대로 쓰기보다 동작을 보고 내 방식을 찾으라고 했다.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**1. Skill 설계 = 워크플로우 정리부터**
- 내 업무 워크플로우를 정리해 무엇을 스킬로 만들지 정하는 작업이다. "이제 나의 업무 워크플로우를 정리하시는 게 일단 첫 번째고."
- 점심 전(3강)에 낸 주제를 이어 간다. 강사가 예제로 준 개발 작업 사례(python backend api)를 참고한다.

**2. mattpocock/skills — "Skills for real engineers"**
- 전날 준 링크 중 하나다. 개발 작업 스킬의 참고 자료로 다시 언급했다.

**3. pstack — 서브 에이전트 스킬 라이브러리**
- 유행하는 라이브러리이며 수업에서 깊게 다루지는 않는다.
- 유행하는 이유: 만든 엔지니어가 "자기만의 루틴을 이렇게 스킬이랑 에이전트로 해가지고 뭐 대부분의 작업을 거의 이제 자동화 수준으로 끌어올렸다"는 점이다. 강사는 "참고하시기 좋은 자료"라고 했다.
- `pstack`으로 검색하면 Cursor 플러그인으로 나오지만(GitHub `cursor/plugins`), Cursor 플러그인이라는 점은 중요하지 않다고 했다.

**4. insane-research — 리서치 스킬 (GitHub fivetaku/insane-research)**
- 한국인 개발자가 만든 저장소이고 Claude Code 플러그인으로 제공된다. 강사도 많이 쓴다.
- 동작 순서(장표 6):
  1. **질문 구체화**: 질문을 더 자세하게 만든다.
  2. **검색 계획**: 구체화한 질문으로 계획을 세운다.
  3. **검색 수행**: 웹 리서치 에이전트와 학술·기술(academic/technical) 에이전트가 돈다.
  4. **레퍼런스 검증**: 여러 레퍼런스를 검증하는 에이전트가 돈다.
  5. **자료 제공**: 결과를 정리해 준다.
- 강조한 이유: 이런 멀티 에이전트 구조는 내 스킬을 설계할 때 참고할 사례다. "뭐 이걸 그대로 쓰기 보다는 저는 이제 동작을 확인하고 그래서 나는 어떻게 쓰지 하는 식으로 좀 이렇게 참고를 많이 합니다."

**5. skills.sh — 스킬 검색 사이트 (Vercel 제공)**
- 다양한 스킬을 검색하고 내려받을 수 있다.
- **find-skills(스킬 찾는 스킬)**: 첫 번째로 보이는 스킬이다. "파인드 스킬스 스킬 찾는 스킬 좋은 힌트가 될 수 있겠죠." 스킬 찾는 스킬이 어떻게 동작하는지 자체가 설계 힌트가 된다는 뜻이다.

**6. HyperFrames(하이퍼프레임) — GitHub heygen-com/hyperframes**
- HTML로 화면을 만들고 영상으로 렌더링하는 스킬이다. 강사가 요즘 많이 보고 있다고 했다.
- 흐름(장표 8): HTML 작성(write html) → 애니메이션(CSS·JavaScript) → 영상 렌더링(render video) → 데모·안내 영상.
- 강조한 이유: 프로그램 데모나 안내용 짧은 영상은 지금까지 사람이 직접 녹화했는데, "그것조차 맡기는 거죠." HTML로 만들면 애니메이션을 CSS나 JavaScript로 줄 수 있어서 가능하다. "write html, render video 그걸 에이전트로 만들어놨다"고 홍보한다. 쓸지 말지와 상관없이 "이런 것도 할 수 있구나" 알아 두라는 취지다.

**7. GitHub 트렌딩 레포지토리**
- 트렌딩 저장소 대부분이 "에이전트를 어떻게 만들었다, 나의 워크플로우는 이거다, 스킬은 이런 게 좋더라"를 다룬다. 강사는 수시로 들어가 본다.
- 예: **PR 에이전트**("우리의 PR 리뷰는 어떻게 할까?"). 개발 프로세스 담당자에게 아이디어가 된다.
- "그대로 뭐 적용하시기 보다는 주로 아이디어 많이 얻으실 수 있을 것 같고요."

### 강사 팁·주의사항 (실전 팁, 흔한 실수)
- **pull 충돌은 Claude에게 맡긴다.** 직접 고친 파일 때문에 충돌이 나면 "에러 없이 pull 해 줘"라고 하면 새 내용만 받아 준다.
- **설계는 워크플로우 정리부터 한다.** 참고 스킬은 그 다음, "한 발자국 더" 나아갈 때 본다.
- **남의 스킬은 그대로 쓰지 않는다.** 동작을 확인하고 "나는 어떻게 쓰지"를 찾는 참고 자료로 쓴다.
- **스킬 찾는 스킬(find-skills) 자체가 설계 힌트다.** 스킬이 다른 스킬을 어떻게 찾고 동작하는지 살펴본다.
- **사람이 반복하던 일(데모 영상 녹화 등)도 맡길 수 있는지 본다.** HyperFrames 사례처럼 HTML, CSS·JS 애니메이션, 영상 렌더링으로 이어지는 경로가 있다.
- **GitHub 트렌딩을 수시로 본다.** 적용보다 아이디어를 얻는 용도다(예: PR 리뷰 에이전트).
- 불확실한 부분(장표 9): 03:47 "허서라는 회사"(pstack 저장소가 cursor/plugins라서 Cursor로 추정), 09:41 "심심한 말씀"(내용은 녹음에 없음), 10:48 "트래핑 관련 레포지토리 / 털어오는 데를 어떻게 털어올 것인가"(뜻 불명), 12:33~43:46 실습 시간(발화 없음).

### 실제 프로젝트에 적용할 체크리스트 (이 강의 내용으로 실제 프로젝트를 만들 때 따라할 단계, 행동 지침 형태)
1. [ ] 작업 저장소를 최신으로 받는다(`git pull`). 충돌이 나면 Claude에게 "에러 없이 pull 해 줘"라고 요청해 내 변경을 지키면서 새 내용만 받는다.
2. [ ] 가이드나 참고 문서(이 강의에서는 `Day04_new/my_day04_practice/guide.md`)가 있는지 확인한다.
3. [ ] **내 업무 워크플로우를 먼저 정리한다.** 단계별로 무엇을 하는지 적는다.
4. [ ] 예시 구조를 따라 스킬 초안을 만든다: 공통 규칙 → 베스트 프랙티스(code snippet) → 작업 방식 설명 → 기존 코드가 있을 때의 지침.
5. [ ] 설계는 Claude와 대화하면서 다듬거나, 내 문서로 직접 쓴다.
6. [ ] 비슷한 공개 스킬을 찾는다: skills.sh(find-skills 포함), GitHub 트렌딩, mattpocock/skills, pstack, insane-research.
7. [ ] 찾은 스킬은 설치해서 **동작을 확인**하고, 구조(예: 질문 구체화 → 계획 → 병렬 검색 에이전트 → 검증 에이전트 → 결과 정리)에서 내 스킬에 가져올 패턴만 뽑는다. 그대로 복붙하지 않는다.
8. [ ] 반복해서 사람이 하던 산출물(데모·안내 영상 등)도 스킬이나 에이전트로 맡길 수 있는지 검토한다(예: HyperFrames의 HTML→영상 방식).
9. [ ] 개발 프로세스 쪽 아이디어(예: PR 리뷰 에이전트)는 트렌딩 저장소에서 찾아 우리 팀 프로세스에 맞게 바꾼다.
10. [ ] 약 30분 정도 시간을 정해 설계 초안을 끝내고, 다음 단계(스킬화·구현)로 넘긴다.

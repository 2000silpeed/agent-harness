## 4일차 3강 — 스킬을 회사 안에서 모으고 나눠 쓰기 (스킬 레지스트리·MCP/에이전트 게이트웨이와 내 업무의 스킬화)

> 출처: 「4일차 3강 다시보기」(전사·분석, 24:41 분량), 「4일차 3강 장표」(10장). SDS AX Advanced · 2026-11-05.

### 핵심 요약 (3~5줄)
- 스킬은 "조각 지식"이다. 잘 쓰면 개인에게는 기회(고과·외부 기회)이고, 회사에는 지식 자산(강사 표현으로 "회사의 빅브라더")이 쌓이는 일이다.
- 스킬은 내 PC의 파일이라 나누기 불편하다. 그래서 `.skill` 압축, Claude 플러그인, 또는 회사 중앙의 **스킬 레지스트리**(LiteLLM 같은 오픈소스)로 모아 제공하고, 업데이트는 **첫 실행 때 레지스트리를 확인**해서 관리한다.
- PC에 스킬을 남기면 안 되는 경우에는 **호출용 스킬만 두고**, 권한을 확인한 뒤 **컨텍스트로만** 내려주며, 혹시 저장된 파일은 **삭제 스킬을 훅으로** 지운다.
- **MCP 게이트웨이**에서는 공통 **가드레일**(insert/update/delete 차단 등)로 위험한 SQL 실행을 막고, **에이전트 게이트웨이/A2A**로 에이전트가 에이전트를 호출하는 흐름이 커지고 있다.
- 점심 후 실습 과제: "활용"이 아니라 **"완전 대체"** 관점에서 내 업무의 아주 작은 부분을 MD 문서로 정리해 오후에 스킬로 만든다.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**1. 스킬 = 조각 지식 (00:01~)**
- "스킬이라는 녀석이 제가 정말 간단하게 그냥 조각 지식이라고 전달을 드렸잖아요. 이 조각된 지식이 판매가 된다라는 겁니다."
- 개인 쪽: 회사 업무에서 쓰고 고과를 받지만, 스킬을 잘 쓰는 능력은 회사 밖에서도 새 기회가 된다. 삼성전자가 AI 사용으로 고과평가를 한다는 소문도 언급했다(강사가 "소문"이라고 밝힘).
- 회사 쪽: "이걸 잘 쓰기 시작하면 회사 좋은 짓 하는 거예요." 사람들이 지식을 쌓아 스킬 레지스트리·MCP로 만들면 회사의 빅브라더가 된다. 퇴사해도 남는 자산이다.
- 강조한 이유: 기술 자체는 어렵지 않지만 "나는 이것보다 무엇을 더 잘해야 하나", 어떤 인사이트를 더 줄 수 있나를 고민하게 된다. 스킬이 기술을 넘어 삶에 영향을 준다는 점을 짚었다.

**2. 스킬 레지스트리 (02:01~)**
- 스킬은 PC에 설치되는 파일이라 남에게 주기 불편하다.
- 공유 방법: `.skill` 압축 파일로 전달하거나, Claude **플러그인** 형태로 감싸 제공한다.
- 그래도 회사 입장에서는 "가운데 중간에서 합쳐서 제공하는 그런 플랫폼"이 필요하다. 이것이 스킬 레지스트리다.
- **LiteLLM**: 유명한 오픈소스다. AI 게이트웨이 서비스로 시작해 지금은 여러 게이트웨이 서비스를 운영한다. 그중 **스킬 게이트웨이**가 가운데에서 스킬을 제공한다. 보안 공격을 두 번 당해서 이 회사가 보안·서비스를 유지할 수 있는지 의심도 받지만, 오픈소스라 로컬에 설치해서 쓸 수 있다. Claude Code와 연결해 회사 스킬 레지스트리를 중앙에서 관리할 수 있다.

**3. 스킬 버전·업데이트 관리 (04:05~)**
- 문제 제기: "PC에 설치된 거 얘가 업데이트 하지 않으면 그만이잖아요."
- 해법: 앞서 다룬 "코드 모드의 코드 실행 방식"을 응용해서 "첫 번째 실행에 업데이트 체크하게 하면 되잖아요."
  - 방법 A: 스킬을 실행할 때 회사 레지스트리에 요청하고, 업데이트가 있으면 업데이트한 뒤 수행한다.
  - 방법 B: Claude Code가 처음 로드될 때 회사 레지스트리에 한 번 접근해서, 이 사람이 가진 스킬 목록 가운데 업데이트가 있는 것을 업데이트한다.
  - "구성하시기 나름"이라고 했다.

**4. PC에 남기지 않는 호출형 스킬 (05:36~) — K뷰티 회사 사례**
- 배경: 입퇴사가 잦은 회사다. "그리고 이건 회사의 자산이에요." 퇴사자가 스킬을 들고 나가면 막을 방법이 없다.
- 구성:
  1. PC에는 **레지스트리를 호출하는 스킬 하나만** 둔다.
  2. 사용자 정보로 **권한을 확인**한 뒤 스킬 실행을 요청한다.
  3. 레지스트리는 스킬 실행에 필요한 내용과 추가 첨부 정보를 **컨텍스트에만** 채워서 준다.
  4. Claude가 "까딱 잘못하면" 받은 내용을 파일로 저장할 수 있으므로 "찾는 스킬도 두지만 지우는 스킬도 같이 넣어놔요." 지우는 스킬은 **훅**으로 넣어 받으면 바로 지우게 했다.
- 한계: 컨텍스트를 많이 차지한다. 채팅 로그를 뒤지면 결국 가져갈 수는 있다. 다만 이 회사 사용자 대부분은 영상 작업자처럼 세부 로직을 잘 모르는 사람들이었다.
- 강사 표현: 이런 "꽁수들을 부려봤다".

**5. MCP 게이트웨이와 가드레일 (08:07~)**
- 예시: IBM이 주도하는 오픈소스 **MCP 컨텍스트 포지**(앞서 소개함), 그리고 **LiteLLM의 MCP 게이트웨이**.
- 게이트웨이는 직접 만들어도 어렵지 않다. 직접 만들 때 이들이 어떤 기능을 갖췄는지 참고하라고 했다.
- 흔한 실수: MCP를 데이터 소스와 연결할 때 DB를 거의 다 읽을 수 있는 계정을 주고, "테이블 스펙 제공하는 툴 하나 주고, 쿼리 짜서 돌려" 하는 **툴 두 개 구성**으로 SQL을 그대로 실행하게 한다. 강사는 이를 "거의 뭐 SQL 인젝션"이라고 했다. Claude에게 MCP를 만들라고 하면 그냥 만들어 주지만, "아무도 이 가드레일을 고려하지 않으시더라고요."
- **가드레일**: SQL 쿼리가 정한 조건대로 도는지 검증하는 규칙을 공통으로 관리한다. 예를 들어 insert/update 쿼리는 일단 검토하고, delete는 절대 금지한다.
- 제어 위치: DB 쪽에서 막는 게 이상적이지만 DB 관리 조직은 따로 있고 귀찮아해서 그냥 읽기 권한 계정을 준다. 그래서 "우리 MCP 서버를 개발하시는 쪽에서 제어를 해야 되더라고요. 현실적으로."
- **툴 서치 vs MCP 시맨틱 툴 필터**: 같은 기능이다. 차이는 임베딩(RAG)을 쓰는지 여부뿐이다. 더 높은 성능이 필요하면 직접 구현하는 편이 훨씬 좋았다고 했다. 원래 실습에 넣었지만 설치하고 띄우는 데 시간이 많이 들어서 개념 설명만 했다.

**6. 에이전트 게이트웨이와 A2A (12:48~)**
- 흐름: 스킬을 잘 쓰다 보면 컨텍스트를 분리해야 할 때가 오고, **서브 에이전트**로 나누게 된다. 서브 에이전트는 고유한 작업 하나를 맡으므로 "그거 다른 사람도 쓸 수 있지 않을까?"라는 생각으로 이어진다. 앱이나 백엔드 서비스처럼 에이전트가 에이전트를 호출하는 **에이전트 게이트웨이** 개념이 나왔다.
- **A2A(Agent to Agent)**: 기반 기술이다. 작년 4월 처음 나왔고, 올해 3월 1.0이 됐다. 구글이 개발했고 8월쯤 재단에 기부됐다(재단 명칭은 전사상 불확실).
- 현황: 국내에서는 아직 크게 떠오르지 않아 수업에서는 빠졌지만 기회가 오고 있다. 단일 에이전트 창에서 대화하며 여러 에이전트를 만들고 지시하는 **마스터 에이전트**(치프) 사례가 늘고 있다. 개별 에이전트는 각자 대화 세션을 가지면서 명령도 받아야 하므로 에이전트 간 통신이 잦아진다.

**7. 구독 공유 사례 (16:15~, 강사 표현으로 "꼼수 기술")**
- LiteLLM에 **Claude Max 200불** 계정 여러 개를 연결하고, 가운데에서 API처럼 제공했다. Claude Code는 API 키로 연동할 수 있다.
- "맥스 한 5개 계정으로 한 20명씩 쓰는" 구성이 가능했다.
- 최근 Claude 정책 변경으로 대량 계정 생성이 어려워져서 지금은 어려울 수 있다고 했다.

### 실습/데모 내용 (명령어, 파일 구조, 프롬프트, 코드 조각 등 구체적으로 — 원문에 있는 그대로 보존)

이 강의에는 직접 돌린 명령어 실습이 없다. LiteLLM 화면을 보며 설명했고, 마지막에 **점심 후 실습 과제**를 냈다.

**과제: 내 업무를 스킬로 (17:35~)**
- 관점: "활용이라고 접근하기보다는 … 완전히 스킬에 대체할 수 있다는 이 관점에서." "이거 어제 하셨던 워크플로우 작업이랑 거의 비슷"하지만 이번에는 스킬을 설계한다.
- 질문: "내가 하는 주요 업무를 만약에 AI가 그대로 따라하려는 내가 어떻게 작업 지시를 내려야 되는가."
- 형식: 1번, 2번, 3번, 4번처럼 단계를 나누고, 각 단계의 세부 업무 방식을 **MD 문서**로 남긴다.
- 일정: 점심 후 1시에 다시 모여 이 문서를 스킬로 만든다.

**강사 예시: 파이썬 백엔드 API 개발 업무를 스킬로 만든다면 (장표 9: 공통 규칙 → 베스트 프랙티스 → 작업 방식 → 기존 코드가 있을 때)**
1. **공통 규칙**: 파이썬과 파이썬의 공통 규칙을 어딘가에 정의한다. "규칙대로 코드를 짜야 되니까." (PEP를 예로 언급)
2. **베스트 프랙티스**: API 베스트 프랙티스를 **코드 스니펫**으로 준다. "제가 생각하는 가장 예쁜 파이썬으로 짜여진 백엔드 API 코드란 뭔지 줄 거예요. 왜냐하면 안 주면 지 마음대로 짤 거거든요."
3. **작업 방식**: 베스트 프랙티스대로 개발하는 방식을 설명한다. 원문 예시는 다음과 같다.
   - DB와 커넥션을 맺을 때는 이렇게 한다.
   - API는 보통 MVC 형태이므로 기본 코드는 3개다: **DB 레이어, 서비스 레이어, 컨트롤 레이어**.
   - 컨트롤 레이어에는 코드를 조금만 쓰고 넘어가며, 로직은 서비스에 작성한다.
   - DB 커넥션은 위임하고, 서비스 로직은 이렇게 쓰며, "코드 주석은 한 줄마다 다 달아라."
   - "DB는 뭐 ORM 쓰지 말고 그냥 SQL로 써라."
4. **기존 코드가 있을 때** (스킬을 한 단계 발전시키는 방법): 처음 생성할 때는 잘 만들지만, 코드가 여러 벌일 때의 작업 방식을 따로 지시한다.
   - "기존 코드에 같은 기능이 혹시나 있다면 만들지 말고 사람한테 물어봐라."
   - "기능을 분석해서 뭐 전혀 다른 기능이라면 또 구현을 해라."
   - 파일은 이렇게 해석하라.
   - "기존 코드를 먼저 읽고, 중복되는 기능이 없는지 확인하고, 이렇게 판단해."

**강사가 문서를 쓰는 방식 (23:12~)**
- 처음에는 거칠게 쓰고 출발한다.
- 공통 규칙을 정리하면서 "PEP 파일이 지금도 맞나"를 확인한다.
- API 베스트 프랙티스가 없으면 만들어 달라고 하거나, 회사 기존 코드베이스에서 "이 코드가 난 베스트인 것 같아"라고 고른 코드를 넣고 "이걸 네가 읽을 수 있게 정리해"라고 시킨다.
- 개발 작업 방식은 일단 "주저리 주저리" 쓰고, 생각이 맞았는지 다시 검토한다.
- 그 다음 단계가 스킬화다.

### 강사 팁·주의사항 (실전 팁, 흔한 실수)
- **스킬 업데이트는 첫 실행 때 체크한다.** 설치형 스킬은 사용자가 업데이트하지 않으면 그만이므로, 실행 시점이나 Claude Code 로드 시점에 레지스트리를 확인하게 만든다.
- **회사 자산인 스킬은 PC에 남기지 않는 방법도 있다.** 호출 스킬, 권한 확인, 컨텍스트로만 전달, 삭제 훅을 묶는다. 대신 컨텍스트를 많이 쓰고, 채팅 로그까지 막을 수는 없다.
- **흔한 실수: MCP에서 SQL을 그대로 실행하게 만들기.** 테이블 스펙 툴과 쿼리 실행 툴 두 개만 두면 SQL 인젝션 수준의 위험이 생긴다. 가드레일(insert/update 검토, delete 금지)을 공통으로 두자.
- **DB 쪽 통제를 기대하지 말자.** DB 조직은 따로 있고 읽기 계정만 주는 경우가 많으니, 현실적으로 MCP 서버 개발 쪽에서 제어한다.
- 툴 서치는 LiteLLM 등에서도 제공하지만, 더 좋은 성능이 필요하면 직접 구현하는 편이 낫다고 했다.
- LiteLLM은 보안 공격을 두 번 당한 이력이 있다는 점을 알고 쓴다(로컬 설치 가능).
- 과제는 **아주 작게** 시작한다. "너무 크게 생각하시면 안 돼요." 강사가 언어(파이썬)와 영역(백엔드)을 좁혔듯이 범위를 좁힌다. 예쁜 문서일 필요도 없다.
- 베스트 프랙티스 코드를 주지 않으면 AI가 "지 마음대로" 짠다. 기준 코드를 반드시 넣자.
- 업무를 차분히 정리하면 "진짜 괜찮은 스킬이 나옵니다." 그 뒤에는 "스킬 딸각"으로 만들 수 있다.

### 실제 프로젝트에 적용할 체크리스트 (이 강의 내용으로 실제 프로젝트를 만들 때 따라할 단계, 행동 지침 형태)
1. [ ] 자동화할 내 업무에서 **아주 작은 범위 하나**를 고른다. 언어나 영역을 특정한다(예: 파이썬 백엔드 API).
2. [ ] "AI가 이 일을 **완전히 대체**한다면 어떻게 지시할까" 관점으로 업무를 1, 2, 3, 4 단계로 나누고 MD 문서로 적는다. 처음에는 거칠어도 된다.
3. [ ] **공통 규칙** 섹션을 쓴다(언어 규칙, 예: PEP 기준이 지금도 맞는지 확인).
4. [ ] **베스트 프랙티스 코드 스니펫**을 넣는다. 없으면 AI에게 만들어 달라고 하거나, 회사 코드베이스에서 가장 좋은 코드를 골라 넣고 "읽을 수 있게 정리해"라고 시킨다.
5. [ ] **작업 방식**을 구체적으로 쓴다: 레이어 구조(DB, 서비스, 컨트롤), 레이어별 역할, DB 커넥션 처리, 주석 규칙, ORM/SQL 선택 등.
6. [ ] **기존 코드가 있을 때**의 지침을 따로 쓴다: 먼저 읽기, 중복 기능 확인, 중복이면 사람에게 묻기, 전혀 다른 기능이면 구현하기.
7. [ ] 문서를 스킬로 만든 뒤, 내가 원하는 대로 결과가 나오는지 검증하고 고친다.
8. [ ] 팀이나 회사에 배포할 때는 배포 방식을 정한다: `.skill` 압축, Claude 플러그인, 또는 중앙 스킬 레지스트리(예: LiteLLM 스킬 게이트웨이).
9. [ ] 레지스트리를 쓴다면 **첫 실행 또는 Claude Code 로드 때 업데이트를 체크**하는 로직을 넣는다.
10. [ ] 스킬 유출이 걱정되면 호출형 구조를 검토한다(호출 스킬, 권한 확인, 컨텍스트 전달, 삭제 훅). 컨텍스트 비용도 함께 따진다.
11. [ ] MCP로 DB 같은 데이터 소스에 연결한다면 **가드레일**을 게이트웨이나 MCP 서버 쪽에 둔다: insert/update는 검토, delete는 차단, 원시 SQL을 그대로 실행하지 않게 한다.
12. [ ] 툴이 많아지면 툴 서치나 시맨틱 툴 필터(임베딩 기반)를 검토한다. 성능이 모자라면 직접 구현한다.
13. [ ] 스킬이 커져서 컨텍스트 분리가 필요하면 서브 에이전트로 나눈다. 다른 사람도 쓸 만한 기능이면 에이전트 게이트웨이/A2A로 서비스화할 수 있는지 검토한다.

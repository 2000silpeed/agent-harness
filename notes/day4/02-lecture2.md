## 4일차 2강 — 도구는 찾아서 넣고, 스킬은 단계로 읽는다 (Tool Search와 Agent Skills 작성법, 그리고 코드 모드)

> 출처: 「4일차 2강 다시보기」(전사·분석, 42:30), 「4일차 2강 장표」(12장). SDS AX Advanced · 2026-11-05.

### 핵심 요약 (3~5줄)
- 도구가 많아지면 전체 목록을 다 싣지 않고 **Tool Search Tool**로 필요한 것만 찾아 넣는다(Anthropic·OpenAI 제공, Gemini는 공식 미제공). 선별 방식은 예전 **벡터 DB(RAG)**에서 최근 **작은 모델이 번호만 고르는 방식**으로 옮겨 왔다.
- **SKILL.md**는 YAML frontmatter + markdown 본문이며 필수 필드는 **name·description**뿐. 스킬은 **Progressive disclosure**(메타데이터 → 본문 → 리소스)로 단계적으로 읽힌다.
- **스킬 평가**는 트리거(description의 when)와 실행(원하는 대로 동작) 두 축으로 보며, 항상 로드돼야 하는 스킬은 평가에서 빼고 **세션 시작 훅**으로 강제 로드한다.
- **코드 모드**는 여러 도구 호출을 코드 한 번으로 묶는 기법이고, 이를 스킬에 적용해 **스크립트 출력이 다음 스크립트를 안내**하게 하면 실행 순서가 확정되고 실행 증거가 남는다. 단점은 중간 실패 시 전체가 실패한다는 것.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**1. Tool Search Tool (도구를 찾는 도구)**
- 전체 도구 리스트를 한 번에 모델에 로드하지 않고, 찾아서 "그거 나 있는데 그거 써볼래?"처럼 넣어 주는 방식.
- Anthropic API, OpenAI가 API 문서에서 "Tool Search Tool" 또는 "Tool Search"라는 추가 기능으로 제공. Gemini는 공식 제공하지 않음.
- 강조 이유: 1강의 도구 폭발 문제(툴 리스트가 너무 많음)에 대한 해법.

**2. 도구 선별: 벡터 DB(RAG) vs 모델 선택**
- 수강생 퀴즈: ① RAG DB에 도구를 넣고 검색 ② 모델이 직접 찾게 함. "둘 다 틀린 방식이 아니에요" — 예전에 접근한 방식은 ①, "최근의 방향으로만 말씀드리면 2번이 좀 더 맞아요."
- ①(벡터 DB): 도구의 name·description을 벡터 공간에 점으로 찍어 두고 유사도로 주변 것을 가져오는 방식. 문제점:
  - 임베딩 모델이 바뀌면 다 뒤집어엎어야 함 → "배보다 배꼽이 커지는" 상황.
  - 데이터 추가·변경(업데이트)에 대응하기 어려움 — 벡터 DB는 업데이트에 취약(벡터 포인트를 매번 다시 생성).
  - 도구 데이터는 양이 적어서 굳이 이렇게 운영할 이유가 약함.
- ②(모델 선택)로 바뀐 이유: LLM 성능이 좋아져 **Haiku 같은 작은 모델**도 "도구 리스트 쭉 있는 것 중에 번호만 딱 찍으면" 된다. 1번·2번… 도구 네임과 디스크립션 목록을 주고 "몇 번 고를래?" → "2번, 3번" → 그 리스트를 메인 모델에 전달. **입력은 많지만 출력은 번호 몇 개**라 비용이 쌈. 넣는 것도 그냥 프로그램.
- RAG의 문서 검색도 같은 방향: 찾아 들어가서 쓸모 있는지 빨리 판단하고 필요한 것만 넣어 주는 식으로 정제해서 전달.

**3. 저가 모델의 가격 (jev 모델 사례)**
- 강사가 전날 수강생에게 API 키로 준 jev 모델(저장소 확인: **Jev**, TypeSafe AI의 System One 디시전 모델 — `used_jev_deepagents/corpus/01-jev-system-one.md:3`): 남은 잔액 1.74달러, 많은 수강생과 강사가 호출했는데도 어제 쓴 비용은 약 **0.1달러**.
- 가격 문서상 **100만 토큰당 0.042**(달러), **입력만 과금, 출력은 0원**이라고 설명. (저장소 확인: `Day02_new/README.md:123` — 입력 10억 토큰당 $42(= 100만 토큰당 $0.042, 출처 typesafe.ai 2026-11-01), 출력 단가는 공식 페이지에 없고 2차 출처 기준 무료로 가정) 비교: **Opus는 입력 10달러, 출력 50달러** → 약 1000배 차이.
- 성능은 뛰어나지 않지만 번호를 고르는 용도에는 충분하다. (장표 주석: 가격은 강사가 문서를 보며 말한 값, 이후 업데이트 가능. 컨텍스트가 256K로 늘었다는 언급도 있으나 어느 모델·버전인지 불분명.)
- 결론: 도구는 "처음에는 일단 그냥 단순히 추가하는 게 제일 좋아요." 많아져서 문제가 되면 그때 모델이 찾게 기술적으로 해결.

**4. Agent Skills 공식 문서와 SKILL.md 구조**
- 강사는 "꼭 공식 문서를 봅니다" — "agent skills"로 검색하면 공식 사이트가 나옴. 자료로 만드는 것보다 공식 문서를 보는 게 중요.
- Agent Skills는 최근 리눅스 파운데이션과 같은 오픈소스 재단(전사상 "AI 파운데이션", 정확한 재단명 미확인 — 수업 저장소에서도 재단명은 찾지 못함)에 기부되어 "모두의 기술"이 되었고, 사용이 굳어져 크게 바뀌지는 않을 것.
- SKILL.md는 두 부분: 위쪽 **YAML frontmatter(메타데이터)** + 아래쪽 **markdown 본문**. "front matter라는 녀석이 꼭 필요합니다."
- **필수 필드는 두 가지뿐: name, description.**
  - **name**: max 64 characters, lowercase letters·numbers·hyphens only, must not start or end with a hyphen. **한국어 불가.**
  - **description**: 1024자 이내, 비우면 안 됨. "describe what the skill does" — **what(무엇을 하는지)**와 **when(언제 쓰는지)** 두 가지를 중점적으로 작성. 단, "1024자나 쓸 필요는 없어요."

**5. 선택 필드와 메타데이터 활용 경험**
- 선택 필드(required: no): **license, compatibility, metadata, allowed-tools**.
- 스펙에 없는 필드(예: `allowed-tools` 말고 `mcp-tools`로 MCP 툴을 적음)를 써도 **Claude 기준으로 읽기는 한다.** 하지만 필수가 아니므로 **오류가 있어도 검사해 주지 않는다** — "검사는 만든 제 몫이에요." name·description 외에는 검사 안 함.
- 경험담: `metadata` 아래에 키-값(JSON 객체 형태)으로 줄줄이 달면 **잘 못 읽는다** → 그냥 밑으로(최상위 필드로) 늘리게 되더라.
- license는 완전히 퍼블릭 공개가 아니면 의미 없었고, compatibility는 쓰는 스킬을 거의 본 적 없음. metadata는 author·이메일·버전 정도 2~3개 정보.
- **allowed-tools는 매우 많이 보인다** — 자기 PC의 Claude 스킬 폴더에서 바로 확인 가능(나중에 같이 보기로 함).

**6. 선택 디렉터리 (scripts / references / assets)**
- 필수는 SKILL.md 하나뿐. 스킬이 코드를 실행하거나 참고 자료가 필요할 때 다음 폴더를 기본으로 쓰면 좋다고 스펙이 제시:
  - **scripts/**: 실행할 수 있는 코드.
  - **references/**: 참고할 문서·코드 등. (강사 의견: 스펙 예시처럼 `REFERENCE.md` 같은 파일명을 굳이 쓸 필요 없고 폴더 이름만 보면 된다.)
  - **assets/**: 바뀌지 않는 리소스. 디자인 관련 스킬에 많음. 예: PPT 만드는 스킬에서 **회사 PPT 양식, 회사 로고**는 레퍼런스가 아니라 에셋.

**7. Progressive disclosure (단계적 로딩)**
- 스킬의 가장 큰 특징: "단계적으로 읽어 나간다는 겁니다."
  1. **메타데이터**(name, description)만 읽음.
  2. 스킬이 **활성화될 때만** 본문(Instructions)을 읽음. 본문은 **5천 토큰 이내 권장** — "이거 안 지킵니다. 다들."
  3. **리소스**는 필요하면 쓸지 말지 **AI가 결정** → 그래서 본문에 쓸 수 있는 파일을 참조로 적어 둬야 쓸 수 있다.
- 파일 참조는 그냥 **마크다운 문법**으로 쓰면 된다.

**8. 검증 도구, skill-creator, description 최적화**
- 스펙이 제공하는 검증(전사상 "SKILL.REF" → 저장소 확인: **`skills-ref`** 검증 도구, `github.com/agentskills/agentskills/tree/main/skills-ref` — `Day08/dcode-analysis/docs_official/sdk/skills.md:247`, `Day08/dcode-analysis/docs_official/sdk/skills.md:1784`)의 VALIDATE 기능: name·description 존재, 1024자 이내, 본문 5000토큰 이내만 검사 → "쓰실 필요가 없어요."
- **skill-creator(스킬을 만드는 스킬)**: Anthropic, OpenAI 제공(Gemini는 모름). 베스트 프랙티스를 만족시키게 동작한다. 베스트 프랙티스는 양이 많아 읽지 않을 테니, **"베스트 프랙티스대로 스킬을 정리해 달라"고 요청**해 볼 계획.
- **Optimizing skill descriptions**: name은 명확하게 짓기 쉽지만 description은 쓰다 보면 when(그리고 what도)이 계속 길어진다 → 이를 줄이는 가이드가 문서에 있음.

**9. 스킬 평가 (Evaluating skills)**
- 혼자 쓰는 스킬은 굳이 평가할 필요 없음(내가 알아서 평가 중). **공유할 스킬이라면 꼭 평가**.
- 두 축:
  - **트리거**: description의 **when**이 의도한 상황에서 스킬을 제대로 불러오는가 → **다양한 케이스를 만들어 테스트**.
  - **실행**: 원하는 대로 잘 동작하는가 → **본문을 수정**해서 개선.
- **항상 로드돼야 하는 스킬**(예: 코딩 지식을 담아 "거의 나를 대신하는" 스킬)은 평가 대상에서 제외.
  - 사실 시스템 프롬프트에 넣는 게 맞을 수도 있지만, 이미 스킬로 만들었다면 옮기는 게 귀찮으니 **세션 시작(SessionStart) 훅**에서 프로그램으로 강제 로드: "세션 스타트 하면 그 스킬 그냥 로드 하세요." "그것만큼 안전한 게 없죠."
  - 그 외 나머지 스킬은 케이스를 잘 나눠 모두 테스트.

**10. 코드 모드 (개념과 등장 배경)**
- "코드를 짜서 실행해라 라고 지시하는 것" — 코드를 작성하는 모드를 그냥 코드 모드라고 부를 뿐. 문서로도 있음.
- 등장 배경(스킬 때문이 아님): AI 답변에 "툴 1, 2, 3을 실행해 주십시오"가 있으면 시스템이 툴 1 실행 → AI에 전달 → 툴 2 실행 → 전달 → 툴 3 실행 → 전달. 그런데 1·2·3이 연관된 작업이면 중간 보고가 필요 없고(다 들어오기 전엔 할 게 없음) **요청 수만 늘고 토큰이 낭비**됨.
- 해법: "샘플 코드 여기 있으니 이거 보고 툴 실행하는 코드를 짜서 통으로 다 돌려서 아웃풋 나오면 한 번만 전달해" → 코드 모드.
- 스킬 관점: 본문(description·body)을 읽었다고 실행이 확정되지 않는다(할 수도, 안 할 수도). 동작을 **확정**하려면 결국 **코드를 실행**해 정해진 로직대로 돌려야 한다.
- 스킬과 무관하게도 코드 모드는 툴콜링의 AI 호출(request) 수를 줄이는 데 꽤 중요.

**11. 스킬에 코드 모드 적용 (단계별 로드, "스무고개" 방식)**
- 전날 이야기한 방식의 연장: 툴 하나를 실행하면 그 툴이 다음 작업을 안내하고, 1·2·3·4번이 정상 실행됐는지 **증거로 검증**해 "잘못했어, 다시 돌아", "2번 왜 빼먹었냐"처럼 안내.
- 스킬 본문에는 "첫 번째 코드, 스크립트 `1.sh`를 실행하세요"까지만 씀 → `1.sh` 실행 결과(출력)에 내용 + "다음으로 `2.sh`를 실행하십시오" → 다시 `2.sh` 실행 → … `3.sh`. **본문이 굉장히 가벼워진다.**
- 장점: ① 확정적으로 실행되는 것을 확인 가능 ② 실행 여부의 **증거**를 명확히 남김(예: "몇 월 몇 시 몇 분에 1.sh 실행 완료" 기록).
- 실제 로직을 실행할 필요는 없고 "로직 실행한 척 컨텍스트를 주기만 하면 됩니다" — 점진적으로 컨텍스트를 주는 **스무고개** 방식. 약간의 컨텍스트 낭비(run 하는 비용)는 있지만 경로를 안정적으로 보장받음.
- 단계가 정해지면 `1.sh`, `2.sh`로 나눌 필요 없이 `run.sh` 하나로 합치고 케이스만 분류해도 됨.
- 강조 이유: 오픈소스 스킬은 대부분 텍스트뿐이라 텍스트가 많아 문제가 되는 경우가 대부분. 스킬은 언제 로드될지 모르고, 컨텍스트가 잔뜩 쌓인 상태에서 로드되면 누락이 생겨 엉뚱한 짓을 하고, 사람은 엉뚱하게 스킬을 고치게 된다. 쌓인 상태에서도 **안정적으로 순차 실행**되게 하려는 것. "단계단계 로드를 해보시는게 진짜 꿀팁."
- 이렇게 짜인 레퍼런스 스킬은 공개된 것이 거의 없다(전사상 "딥시크 하네스"에 문서만 있고 스킬은 비공개라는 취지, 대상 불분명).
- 변형: 단계를 **그래프 형태 파일**로 만들어 두고 "1번 다음 2번 다음 3번 다음 4번, 실행했는지 단계별로 검증하세요", "1.sh를 실행해서 1번에 색칠을 하세요" 식으로 하는 개발자도 있음 → 끝에서 검증하느냐 시작부터 하느냐의 차이일 뿐, 단계 검증 원리는 같다.
- **단점**: 중간에 하나가 실패하면 "싸그리 실패를 해버립니다." 하나씩 실행하면 "1·3번 성공, 2번 실패, 다시 돌려보자"고 할 수 있는 것과 대조. 대안으로 성공·실패 결과를 모두 아웃풋에 담아 전달하도록 짜게 할 수 있다.

### 실습/데모 내용 (명령어, 파일 구조, 프롬프트, 코드 조각 등 구체적으로 — 원문에 있는 그대로 보존)
- **Tool Search 개념 시연(판서)**: 작은 모델에 다음처럼 목록을 주고 번호만 받는다.
  ```
  1번: 도구 네임과 디스크립션
  2번: 도구 네임과 디스크립션
  3번: ...
  → "몇 번 고를래?" → "2번, 3번" → 그 리스트를 메인 모델에 전달
  ```
- **jev API 사용량/가격 확인**: 사용량 화면을 보여주려 했으나 서버 오류로 못 보여주고 가격 문서로 대체(100만 토큰당 0.042, 입력만 과금).
- **Agent Skills 공식 사이트**("agent skills" 검색)에서 SKILL.md 스펙 함께 읽기.
- **SKILL.md 구조** (스펙 기준):
  ```
  ---
  name: (필수, 64자 이내, 영문 소문자·숫자·하이픈, 하이픈으로 시작/끝 불가, 한국어 불가)
  description: (필수, 1024자 이내, what + when)
  license: (선택)
  compatibility: (선택)
  metadata: (선택, 예: author, version)
  allowed-tools: (선택)
  ---
  (markdown 본문: 지시문, 활성화될 때 읽힘, 5천 토큰 이내 권장)
  ```
- **스킬 폴더 구조**:
  ```
  <skill-name>/
  ├── SKILL.md      (필수)
  ├── scripts/      (선택: 실행 코드)
  ├── references/   (선택: 참고 문서·코드)
  └── assets/       (선택: 회사 로고·PPT 양식 등 바뀌지 않는 리소스)
  ```
- **코드 모드 적용 스킬 본문 예시(강사 시연 재구성)**:
  ```
  # SKILL.md 본문
  첫 번째 코드, 스크립트 1.sh를 실행하세요.
  ```
  ```
  $ run 1.sh
  → (출력) 테스트... (내용)
  → 다음으로 2.sh를 실행하십시오.
  $ run 2.sh
  → (출력) ... 다음으로 3.sh를 실행하십시오.
  ```
  단계가 확정되면 `run.sh` 하나로 합치고 케이스별로 분기(`run 1.sh`, `run 2.sh` 등)해 더 줄일 수 있음.
  - 저장소 참고(위 시연 자체의 원문은 아님): 진입점 하나에 작업명으로 분기하는 실제 스킬 예가 `Day04/build_mcp/skills/requirements-interview-new/SKILL.md`에 있다. 본문이 `scripts/run.py`를 실행하라고 안내하고, `start_interview`·`record_answer`·`get_session`·`freeze_seed` 등 작업명과 JSON 입력으로 분기한다(`python "$SKILL_ROOT/scripts/run.py" --db ... start_interview <<'JSON' ...`).
- 과제/실습 예정:
  - 자기 PC의 Claude 스킬 폴더에서 `allowed-tools` 필드 확인(나중에 같이 보기).
  - skill-creator로 "베스트 프랙티스대로 스킬을 정리해 달라"고 요청해 보기.
  - 오늘 코드 모드 방식으로 스킬을 단계별로 로드하는 실습.

### 강사 팁·주의사항 (실전 팁, 흔한 실수)
- 도구는 처음엔 단순히 추가하라. 많아져서 문제가 될 때 Tool Search(모델 선택)로 해결하라.
- 도구 선별에 벡터 DB를 새로 운영하는 것은 임베딩 교체·업데이트 부담 대비 이득이 작다. 작은/저렴한 모델로 번호만 고르게 하는 편이 싸고 충분하다.
- 스킬 스펙은 자료보다 **공식 문서**를 직접 보라.
- name에 **한국어 쓰지 말 것**, 하이픈으로 시작/끝내지 말 것.
- description은 what+when 중심으로, 1024자를 다 채울 필요 없다. when이 길어지는 문제에 주의(최적화 가이드 참고).
- 스펙 외 필드는 읽히지만 **검증되지 않는다** — 정확성은 작성자 책임.
- `metadata` 아래에 키-값을 중첩해 넣으면 잘 못 읽는다는 경험 → 필요하면 최상위로 늘려라.
- 리소스(scripts/references/assets)는 AI가 쓸지 결정하므로 **본문에 반드시 파일 참조를 적어 둬라**(마크다운 링크 문법).
- 회사 양식·로고처럼 바뀌지 않는 것은 references가 아니라 **assets**.
- 스펙의 validate 기능은 굳이 쓸 필요 없다. 대신 skill-creator로 베스트 프랙티스에 맞게 정리하라.
- 공유할 스킬은 반드시 평가하라(트리거 + 실행). 혼자 쓰는 스킬은 생략 가능.
- 항상 로드돼야 하는 스킬은 트리거 평가로 고생하지 말고 **SessionStart 훅으로 강제 로드**하라.
- 텍스트만 많은 스킬은 컨텍스트가 쌓인 상태에서 누락이 생긴다 → 처음엔 텍스트로 쓰고, 중요하고 단계가 많으면 **스크립트 단계별 로드(코드 모드)**로 리팩터링하라.
- 코드 모드는 중간 실패 시 전체 실패 → 스크립트가 성공/실패 결과를 모두 출력에 담도록 짜라.
- (장표 표기) 확인 필요: 'UCG'·'크래빅'(사용량 화면/무료 크레딧 추정), 'AI 파운데이션'(재단명, 저장소에서 미확인), ~~'SKILL.REF'(검증 도구명)~~ → 해결: `skills-ref` (저장소 확인: `Day08/dcode-analysis/docs_official/sdk/skills.md:247`).

### 실제 프로젝트에 적용할 체크리스트 (이 강의 내용으로 실제 프로젝트를 만들 때 따라할 단계, 행동 지침 형태)
1. [ ] 에이전트에 도구를 우선 단순히 추가하고, 도구 수가 많아져 선택 오류·컨텍스트 낭비가 보이면 Tool Search(Anthropic/OpenAI 제공 기능 또는 작은 모델에 번호 선택시키는 방식)를 도입한다.
2. [ ] 직접 구현 시: 도구 name·description을 번호 목록으로 만들어 저가 모델에 주고 번호만 받아, 선택된 도구만 메인 모델에 넘긴다.
3. [ ] 스킬 폴더를 만들고 `SKILL.md`에 YAML frontmatter를 작성한다: `name`(영문 소문자·숫자·하이픈, 64자 이내), `description`(what + when).
4. [ ] description의 when에 "어떤 작업/상황에서 이 스킬을 쓰는가"를 구체적으로 쓰되, 불필요하게 길어지지 않게 다듬는다.
5. [ ] 필요한 경우만 선택 필드(`allowed-tools`, `metadata`의 author/version 등)를 추가하고, 스펙 외 필드는 스스로 검증한다.
6. [ ] 본문은 5천 토큰 이내를 목표로 지시문을 쓰고, 참조할 파일은 마크다운 링크로 명시한다.
7. [ ] 실행 코드는 `scripts/`, 참고 문서는 `references/`, 회사 양식·로고 등 고정 리소스는 `assets/`에 둔다.
8. [ ] skill-creator에게 "베스트 프랙티스대로 이 스킬을 정리해 달라"고 요청해 구조와 description을 개선한다.
9. [ ] 공유할 스킬이라면 평가 케이스를 만든다: (a) 트리거되어야 하는 다양한 요청/트리거되지 않아야 하는 요청으로 description의 when 검증, (b) 원하는 결과가 나오는지 실행 검증 → 실패 시 본문 수정.
10. [ ] 항상 로드돼야 하는 스킬은 평가 대상에서 빼고 SessionStart 훅에서 강제 로드하도록 설정한다(또는 시스템 프롬프트로 이동).
11. [ ] 단계가 많고 중요한 스킬은 본문을 "`1.sh`를 실행하라"까지로 줄이고, 각 스크립트 출력이 다음 스크립트(`2.sh`, `3.sh`…)를 안내하도록 만든다.
12. [ ] 각 스크립트가 실행 시각과 "N단계 실행 완료" 기록을 남기게 해 실행 증거를 확보하고, 필요하면 단계 그래프 파일로 순서를 검증한다.
13. [ ] 단계가 안정되면 `run.sh` 하나로 합치고 케이스별 분기만 남긴다.
14. [ ] 연관된 여러 도구 호출은 코드 모드(스크립트로 묶어 한 번에 실행, 결과 1회 전달)로 요청 수와 토큰을 줄이고, 스크립트가 단계별 성공/실패를 모두 출력하도록 해 전체 실패 시에도 원인을 전달하게 한다.

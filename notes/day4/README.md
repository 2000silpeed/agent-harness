## 1. 하루의 흐름

1. **1강 — 왜 MCP·스킬인가:** 모델은 이미 상향 평준화됐다. 이제 능력은 **업무 절차(스킬)**와 **정확한 실행 수단(MCP·코드)**에서 나온다. 펑션콜링이 MCP로 표준화됐지만 REST를 1:1로 감싸서 **도구 폭발**이 생겼다(지라 MCP 약 80개).
2. **2강 — 도구는 찾아서, 스킬은 단계로:** Tool Search로 필요한 도구만 넣는다. `SKILL.md` = YAML(name, description) + 본문이다. 스킬은 Progressive disclosure(메타데이터 → 본문 → 리소스)로 단계별로 읽힌다. 평가는 트리거·실행 두 축으로 본다. 코드 모드는 스크립트 출력이 다음 스크립트를 안내하는 방식이다.
3. **3강 — 조직에서 나눠 쓰기:** 스킬 레지스트리(LiteLLM 등)를 두고 첫 실행 때 업데이트를 확인한다. MCP 게이트웨이에 가드레일을 두고, A2A로 에이전트 간 호출을 한다. 과제: "활용"이 아니라 **"완전 대체"** 관점으로 내 업무의 작은 조각을 MD로 정리하기.
4. **4강 — 설계 실습:** 내 업무 워크플로우부터 정리한다. 공개 스킬(mattpocock/skills, pstack, insane-research, skills.sh, GitHub 트렌딩)은 동작을 보고 패턴만 가져온다.
5. **5강 — 잘 쓴 스킬의 조건:** description은 What/When만 짧게 쓴다. 본문 구역은 **XML 태그**로 나눈다. 본문에는 핵심만 두고 상세는 `references/`로 보낸다. 도구 사용법도 스킬에 적는다.
6. **6강 — MCP vs Skill 역할 분담:** 나만 쓰는 도구는 Skill 안 스크립트 + Bash로 처리한다(STDIO는 "소임을 다했다"). 공유·원격 도구만 Streamable HTTP MCP로 만든다. 도구 설계에서 사람이 할 일은 타입·description을 명확히 쓰기와 비슷한 도구 합치기다.
7. **교재 — 관통 예제 INC-017:** 접근(MCP), 절차(Skill), 정확한 실행(Tool·Script), 반복 품질(Eval)을 구분한다. 고친 뒤 **Eval로 개선을 증명**한다. 검증된 Skill만 배포한다.

## 2. 오늘의 핵심 원칙 10가지

1. **문제를 먼저 진단한다.** 부족한 것이 접근(MCP)·절차(Skill)·정확한 실행(Script)·반복 품질(Eval) 중 무엇인지 가른다. 모델 교체는 마지막 수단이다.
2. **정확성이 필요한 일은 코드로 한다.** 계산·규정 적용은 검증된 코드를 실행하고, 결과를 그대로 출력한다.
3. **도구 수는 줄인다.** REST 1:1 래핑을 피하고 비슷한 도구는 합친다(add/minus/… → `calculator`). 그래도 많으면 Tool Search나 게이트웨이를 쓴다.
4. **도구 정의 = 이름 + description + 타입이 명확한 인자.** 반환값에는 status, 출처, 시점을 넣는다. 빈 결과·오류·연결 실패를 구분한다.
5. **오류는 모델이 고칠 수 있는 것(400류)만 전달한다.** 런타임 오류(500류)는 숨기고 내부에서 처리한다.
6. **SKILL.md description = What + When(+ 아닌 경우).** 짧게 쓰고, 반드시 호출돼야 하는 조건은 강조한다.
7. **본문은 5천 토큰 이내, XML로 구역을 나눈다.** 상세는 `references/`, 실행은 `scripts/`, 양식은 `assets/`에 두고 "언제 읽을지"를 단계에 연결한다.
8. **중요한 다단계 작업은 스크립트 체인으로 만든다.** `1.sh` 출력이 `2.sh`를 안내하는 식이다. 실행 순서가 고정되고 실행 증거가 남는다.
9. **Eval로 증명한다.** 트리거(Precision/Recall), 실행(필수 행동), 결과(업무 완료)를 분리해 채점한다. 변수는 하나만 바꾸고 품질·비용·지연을 함께 본다.
10. **검증된 것만 배포한다.** commit/digest로 고정하고 Eval 카드를 함께 낸다. 쓰기·삭제는 가드레일과 승인 게이트로 막는다.

## 3. 실전 적용 통합 체크리스트 (프로젝트 시작 시)

**설계**
- [ ] 자동화할 업무의 **아주 작은 범위 하나**를 고르고, "AI가 완전히 대체한다면" 관점으로 1·2·3·4단계 워크플로우를 MD로 적는다.
- [ ] 단계별로 "부족한 능력 → 실행 인터페이스(MCP/Script/Skill) → 결과 계약" 표를 만든다.
- [ ] 비슷한 공개 스킬을 찾아 설치해 보고, 가져올 패턴만 뽑는다.

**스킬 작성**
- [ ] `skill-name/SKILL.md` + `scripts/` + `references/` + `assets/` 구조를 만든다.
- [ ] frontmatter `name`은 소문자·숫자·하이픈, 64자 이내로 쓴다. `description`은 What/When과 아닌 경우를 짧게 쓴다.
- [ ] 본문: 공통 규칙 → 베스트 프랙티스 스니펫 → 작업 방식 → 기존 코드가 있을 때 지침 → 실패 분기·종료 조건. XML 태그로 구역을 나눈다.
- [ ] 쓸 수 있는 도구 목록과 사용법을 본문에 적는다.
- [ ] skill-creator로 베스트 프랙티스 정리를 요청한다.

**도구·MCP**
- [ ] 나만 쓰는 도구는 Skill 스크립트로 둔다. 공유·원격 도구만 Streamable HTTP MCP로 만든다.
- [ ] 파라미터 타입과 description을 명확히 쓰고, 비슷한 도구는 합친다.
- [ ] DB·외부 시스템은 MCP·게이트웨이 뒤에 두고 최소 권한을 준다. insert/update는 검토하고 delete는 차단한다. 호출 로그를 남긴다.
- [ ] 오래 걸리는 작업은 비동기(요청 확인 → 진행 → 완료)로 처리한다.
- [ ] 연결 후 실제 노출되는 도구 수와 컨텍스트 점유율을 확인한다.

**평가·배포**
- [ ] 트리거돼야 하는 요청과 트리거되면 안 되는 요청으로 description을 검증한다.
- [ ] 실행 결과가 기대대로 나오는지 확인하고, 실패하면 증상에 맞는 계층만 고친다.
- [ ] 항상 필요한 스킬은 SessionStart 훅으로 강제 로드한다(평가 대상에서 제외).
- [ ] 결과 보고서는 확인된 사실 / 미확인 항목 / 변경 상태를 구분해 쓴다.
- [ ] 배포: `.skill` 압축, 플러그인, 레지스트리 중 하나를 고른다. 버전을 고정하고 Eval 결과를 첨부한다. 롤백 담당자를 정한다.

#### 1부 Memory

**메모리 두 유형 (슬라이드 3)**
- **Auto memory = 각 세션의 관찰 로그.** Claude가 세션 중 스스로 기록. 위치 `~/.claude/projects/<project>/memory/`. 내 머신에만 있어 팀원 세션에 가지 않는다.
- **CLAUDE.md = 리포에 커밋 가능한 "시스템 프롬프트"(실제로는 user message로 들어감, 아래).** 사람·팀이 작성하고 PR로 공유. `.claude/rules/`도 git으로 팀 전체 공유.
- **검토 후 승격:** 관찰 로그 중 공통 성격으로 팀에 필요한 것만 검토해 CLAUDE.md로 옮긴다.

**CoALA 네 유형 ↔ Claude Code (슬라이드 4)** — 분류이지 순서가 아니다.

| CoALA 유형 | Claude Code 대응 | auto memory 관계 |
|---|---|---|
| 작업 기억(Working) — 현재 결정 주기의 활성 정보 | 컨텍스트 윈도우. CLAUDE.md와 인덱스가 시작 시 올라오고 compaction 때 요약 | — |
| 에피소드 기억(Episodic) — 이전 주기의 경험 | 세션 transcript. `/resume`으로 이어감, 기간 뒤 삭제 | auto memory는 원본 에피소드를 담지 않는다 |
| 의미 기억(Semantic) — 세계·자신에 대한 지식 | CLAUDE.md, rules(사람이 씀) + auto memory(Claude가 씀). 네 type 모두 텍스트 노트 | 에피소드에서 **증류한 지식만** 의미 기억으로 쓴다 |
| 절차 기억(Procedural) — 행동하는 방법 | 명시: skills, hooks, 서브에이전트 정의 / 암묵: 모델 가중치 | auto memory는 이 층을 쓰지 않는다. 사람이 설계한다 |

**규칙 형식 비교 — 차이는 frontmatter 키 1개 (슬라이드 9)**

```markdown
# security.instructions.md   (Copilot)
---
applyTo: "src/**/repository/**"
---
- SQL은 파라미터 바인딩만 사용한다
```

```markdown
# .claude/rules/security.md   (Claude Code)
---
paths:
  - "src/**/repository/**"
---
- SQL은 파라미터 바인딩만 사용한다
```

- Copilot: `applyTo`는 쉼표 구분 glob 문자열, `excludeAgent`로 기능별 제외 가능.
- Claude Code: `paths`가 rules가 읽는 **유일한** frontmatter 필드. 기능별 제외 없음 → 역할별은 스킬로.

**프롬프트 지시 해석 방식 (슬라이드 10)** — 파일이 있다고 적용된 것은 아니다.
- 하위 폴더 해석: Copilot cloud agent는 가장 가까운 파일만, Copilot CLI는 찾은 파일을 합침, **Claude Code는 상위부터 하위까지 누적**.
- 충돌 처리: github.com은 개인>리포>조직 우선순위, CLI·Claude Code는 우선순위 없음 → 공통 처방은 **충돌하는 지시 자체를 없애는 것**.
- surface별 지원(원본 강의 시점 비교): cloud agent·review는 경로별 지시 지원, VS Code review는 리포 전체 지시만, Eclipse review는 미지원 → **사용하는 표면에서 실제 로딩을 확인**한다.

**메모리 설계 철학 (슬라이드 11)** — Claude Code에서 공유 메모리는 저절로 생기지 않고 의도적으로 설계해야 한다.
- Copilot(GitHub 플랫폼 위): GitHub 서버가 리포 단위로 저장, 근거 코드로 검증, 28일 미사용 시 삭제 → A·B·C가 같은 기억을 본다.
- Claude Code(로컬 위): 각자 기계에 auto memory가 평문으로 따로 쌓여 지울 때까지 남는다 → 공유하려면 사람이 검토해 git(CLAUDE.md, rules)으로 옮긴다(기존 협업 경로 그대로).

**자동 메모리 구조 (슬라이드 12)**
1. 세션 중 신호: 교정, 확인, 선호 표현, 진행 중 결정, 외부 정보 위치
2. 저장 판단: "다음 대화에도 쓸모 있나?" 코드로 알 수 있거나 CLAUDE.md에 이미 있으면 저장 안 함
3. 쓰기: `MEMORY.md` 인덱스에 항목당 한 줄 + 토픽 파일 하나(`type`, `modified` 필드)
4. 다음 세션 읽기: 인덱스는 **첫 200줄 또는 25KB**까지만 읽고, 토픽 파일은 필요할 때 연다
5. 위치·토글: 로컬(worktree 간 공유), `/memory`로 켜고 끄기, 위치 설정 `autoMemoryDirectory`

**메모리 기록 기준 (슬라이드 13)**
- 네 type: `user`, `feedback`, `project`, `reference` 토픽 파일.
- 저장하지 않는 것: 코드로 알 수 있는 아키텍처·경로·디버깅 수정, CLAUDE.md 중복.
- **말하는 방식에 따라 갈린다:** "항상 pnpm 써, 기억해" → auto memory(내 기계만). "CLAUDE.md에 추가해" 또는 `/memory` 편집 → 팀과 공유하는 CLAUDE.md.

**계층별 메모리 로딩 — 범위 (슬라이드 15)** (예: 모노레포 `/repo/services/payment`에서 `claude` 실행)

| 위치 | 로드 시점 |
|---|---|
| 위(리포 밖): managed CLAUDE.md(회사 배포), `~/.claude/CLAUDE.md`·`rules/`(개인), auto memory `MEMORY.md` | 시작 시 |
| 위(리포 안): `/repo/CLAUDE.md`, `/repo/.claude/rules/style.md`(paths 없음), `services/`, `services/payment/CLAUDE.md`·`CLAUDE.local.md` | 시작 시 |
| `rules/security.md`(paths 있음) | 온디맨드(매칭 파일 다룰 때) |
| 아래: `payment/src/db/CLAUDE.md` | 그 폴더 작업 시 |
| 옆: `services/web/CLAUDE.md` | **로드 안 됨** |
| 빼기 | 다른 팀 상위 지시는 `claudeMdExcludes`(glob)로 뺀다. **managed는 못 뺀다** |

**컨텍스트 적재 순서 (슬라이드 16)**
1. 시스템 프롬프트 — **CLAUDE.md는 여기 없다.** 이 수준이 필요하면 `--append-system-prompt`(실행 시 넘기는 시스템 지시).
2. User message(세션 시작 시 로드분): 1 managed → 2 `~/.claude` → 3 `/repo` → 4 `services/payment` → 5 local, + paths 없는 rules, MEMORY.md
3. 대화 중 paths 매칭 파일을 읽으면 `security.md`가 그 자리에 붙음
4. 대화 중 폴더 파일 접근 시 `src/db/CLAUDE.md`가 더해짐
5. 결론: 읽고 따르려 하지만 준수는 보장되지 않는다. **나중에 읽혀도 우선하지 않는다**(덮어쓰지 않음).

**계층 간 충돌 — 덮어쓰지 않고 이어붙임 (슬라이드 17)**
- 개인 `~/.claude`의 npm과 팀 CLAUDE.md의 pnpm이 둘 다 컨텍스트에 남고 승자는 정해지지 않는다.
- 처방은 우선순위가 아니라 **관심사 소유권**: 회사=보안·컴플라이언스, 팀=빌드·컨벤션·아키텍처, 개인=응답 스타일·도구 단축.
- 회사 계층도 같다: managed CLAUDE.md 지침은 어길 수 있고, `permissions.deny`는 클라이언트가 막는다(3부).

**단계별 메모리 수명 (슬라이드 18)**

| 대상 | 세션 시작 | 작업 중 | `/compact` 직후 | 이후 | 서브에이전트 |
|---|---|---|---|---|---|
| 루트 CLAUDE.md(paths 없는 rules 포함) | 로드 | 유지 | 디스크에서 재주입 | 유지 | 로드(Explore, Plan 제외) |
| 하위 CLAUDE.md, paths 규칙 | 없음 | 접근·매칭 시 로드 | 빠짐 | 다시 다룰 때 재로드(그 사이엔 없음) | 명시 없음 |
| auto memory 인덱스 MEMORY.md | 로드(200줄/25KB) | 유지 | 디스크에서 재주입 | 유지 | **전달 안 됨** |

→ 꼭 남아야 하면 루트나 훅으로.

**AGENTS.md 사용 시 (슬라이드 19)**
- 세션 시작 때 cwd·상위 폴더에 **CLAUDE.md 계열이 하나라도 있으면 CLAUDE.md 계열만 읽는다.** `CLAUDE.local.md` 하나만 있어도 기본 설정에서 AGENTS.md가 빠진다.
- 없으면 AGENTS.md를 읽는다(상위 것은 시작 시, 하위 것은 Read할 때).
- 판정과 무관하게 항상 로드: managed CLAUDE.md, `~/.claude/CLAUDE.md`, `.claude/rules/`.
- 바꾸기: `/config` → Project instructions를 "claude md and agents md"(둘 다 읽음)로, 또는 CLAUDE.md에서 AGENTS.md를 import.

**메모리 배치 지도 (슬라이드 21)** — 팀이 합의한 관례는 "이 리포 전체"와 "리포 안 특정 경로" 두 칸에만 둔다.

| | 모든 프로젝트 | 이 리포 전체 | 리포 안 특정 경로 |
|---|---|---|---|
| 팀 공유(git, IT 배포) | managed CLAUDE.md — 회사 정책, IT가 배포, 개인이 뺄 수 없음 (팀 관례는 두지 않음) | CLAUDE.md + paths 없는 rules — 팀 관례와 상시 사실, 200줄 이내 | `.claude/rules/` paths 지정 또는 하위 폴더 CLAUDE.md — 영역별 관례 |
| 나만(기계 로컬) | `~/.claude/` CLAUDE.md·rules — 응답 언어, 개인 작업 습관 | CLAUDE.local.md, auto memory — 개인 샌드박스 URL, 테스트 데이터 | claudeMdExcludes(settings.local.json) — 보통 두지 않음 |

**지시 배치 판정 Q1~Q5 (슬라이드 22)**
1. Q1 반드시 지켜야 하나? 예 → **hook, permissions.deny**(PreToolUse 훅, 3부). 메모리에 적어도 강제가 아니기 때문.
2. Q2 여러 단계 절차인가? 예 → **skill**(2부). 절차는 필요할 때 로드.
3. Q3 팀 모두에게 필요한가? 아니오 → 개인 계층(`~/.claude/rules`, CLAUDE.local.md).
4. Q4 여러 리포 공통 회사 규칙인가? 예 → managed CLAUDE.md.
5. Q5 특정 경로에만 해당? 예 → rules paths 또는 그 폴더 CLAUDE.md / 아니오 → 루트 CLAUDE.md(상시 사실, 200줄 이내).

**메모리 파일 운영 (슬라이드 25)**
- 짧게, 나눠서: CLAUDE.md 200줄 이내 추천, 코드로 알 수 있는 구조는 뺀다, rules는 주제당 한 파일·paths 우선.
- 코드처럼 리뷰: CLAUDE.md·rules 변경은 PR로, 큰 모델 업데이트 뒤 우회 규칙 재검토, `/doctor`, `claude-api prompt audit`로 충돌 점검.
- 범위 관리: 다른 팀 지시는 claudeMdExcludes, 회사는 managed, 공통 절차·훅은 plugin, settings.json은 상속 안 됨.

**메모리의 주요 오해 (슬라이드 26)** — 로드된 지침은 강제성이 전혀 없다.
1. "기억해" = 팀 규칙? → 내 auto memory로 간다. 팀원 B의 Claude는 모른다. 팀 규칙은 PR로 rules에.
2. 로드됨 = 지켜짐? → `/context`에 보이고 compact 뒤 재주입돼도 준수는 보장 안 됨. 결과를 훅과 리뷰로 확인.
3. 강하게 쓰면 강제? → "절대", "NEVER"를 붙여도 context일 뿐. 막아야 하면 PreToolUse 훅 또는 permissions.deny.

**메모리 증상 진단 (슬라이드 27)** — "의존 상태" = 팀 지식이 각자의 auto memory에만 있는 상태.

| 증상 | 처방 |
|---|---|
| 팀원마다 동작이 다름 | PR로 팀 지식 승격 |
| CLAUDE.md가 수백 줄 | 함정·근거·관례만 유지 |
| 긴 세션 뒤 규칙을 잊음 | 루트로 이동 또는 훅 |
| 서브에이전트가 관례를 무시 | rules, 에이전트 정의에 명시 |
| 강한 금지 문구도 안 지켜짐 | PreToolUse, permissions.deny |

로드 확인 도구: `/context`, `/memory`, `/doctor`, prompt audit, `InstructionsLoaded`.

**메모리 승격 과정 (슬라이드 28)** — auto memory(원료) → 사람의 리뷰("누구의 지식인가? 다시 쓰일 것인가?") → 폐기 / 개인 선호 → `~/.claude/CLAUDE.md`·CLAUDE.local.md / 팀 합의 → PR로 CLAUDE.md·`.claude/rules` / 전사 공통 → managed CLAUDE.md / 반드시 → PreToolUse 훅·permissions.deny(3부). **승격 뒤 원본 삭제**, 중복 저장 안 함.

**팀 메모리 승격 한 바퀴 (슬라이드 29)** — 아래 "실습 과제" 참고.

**보안 규칙의 세 계층 (슬라이드 30)** — 시큐어 코딩 규칙 하나가 "부탁 → 위임 → 강제"로 바뀌며 모델 판단에서 멀어진다.
1. 1부 부탁(메모리): `.claude/rules/security.md`에 paths로 적는다. 한계: compact 뒤 재매칭 전까지 빠짐, 강제 아님.
2. 2부 위임(스킬·서브에이전트): 보안 리뷰 스킬, 리뷰어 서브에이전트가 챙긴다 — "누가 챙기나?"의 답.
3. 3부 강제(훅): PreToolUse로 막고 PostToolUse로 검증 — "어떻게 반드시?"의 답.

**Memory 정리 (슬라이드 31)** — 로드 범위(위는 시작 시, 아래는 다룰 때, 형제는 안 들어옴) / 이어붙이기(user message로, 덮어쓰지 않음) / 팀과 개인(팀 규칙은 리포, 개인 선호는 `~/.claude`, auto memory는 검토 후 승격) / 강제 아님(반드시 지킬 규칙은 훅으로).

#### 2부 Skills

**스킬의 설계 (슬라이드 33)**
- 무엇을: 스킬은 절차·노하우·코드를 폴더 하나에 담는다. MCP와의 차이는 "무엇을 담느냐".
- 언제: Progressive Disclosure — 필요한 시점에 필요한 만큼만.
- 어디에: Subagent — 별도 컨텍스트에서 읽고 결과(요약)만 메인으로.
- 반드시: 훅 — 모델 판단과 무관하게 집행(3부).

**CLAUDE.md 로드는 Context 비용 (슬라이드 34~35)** — 세션 시작 시 전부 로드되니 내용이 늘수록 매 턴 비용이 늘고 작업 공간이 줄어든다(개념도, 실제 비율 아님). 공식 권장: 프로젝트 CLAUDE.md는 200줄 안쪽, 참조성 내용은 스킬이나 paths 규칙으로(수치는 문서 버전 확인).
- 사실 → CLAUDE.md: 빌드 명령, 공통 에러 포맷, 수정 금지 경로(`src/legacy/`)처럼 짧고 거의 모든 작업에 해당.
- 절차 → 스킬: 보안 검토 순서, 의존성 업그레이드와 롤백, 릴리스 노트 검증처럼 길고 특정 작업에만 필요.
- 판단 질문: 매 턴 알아야 하는가? → CLAUDE.md / 특정 작업에서만 필요한 긴 절차인가? → 스킬.

**결제 코드 적용 예 (슬라이드 36)** — "금액은 원 단위 정수"는 상시 사실 → CLAUDE.md(결제 디렉터리에서만 의미 있으면 하위 CLAUDE.md나 paths 규칙). "환불 API의 검토 순서와 예외 처리"는 특정 작업 절차 → 스킬(순서는 본문, 단계별 세부는 참조 파일). **판단 기준은 문서 길이가 아니라 사용 시점.**

**단계별 로딩 모델 L0~L4 (슬라이드 37, 강의용 설명 모델)**

| 레벨 | 무엇 | 언제 컨텍스트로 | 비용 |
|---|---|---|---|
| L0 사용자 전용 | `disable-model-invocation: true` | `/name` 입력 시에만 L2로 | 목록 비용 0 |
| L1 프론트매터 | `name`, `description` | 세션 시작부터 항상 상주 | 스킬당 한 줄 |
| L2 SKILL.md 본문 | 목차와 분기 위주 | 호출 시 본문 전체, 이후 계속 유지(다시 안 읽음) | 매 턴 |
| L3 `references/` | 본문이 가리키는 참조 파일 | Read 시 그 파일만 | 읽은 만큼, 나머지 0 |
| L4 `scripts/` | 실행 코드 | 실행 후 출력만 | 출력만큼 |

**스킬 로딩의 특성 (슬라이드 38)** — 상시 비용은 짧은 메타데이터, 목록 예산을 넘으면 설명이 빠질 수 있음. 한번 로드한 본문은 작업 후에도 남음 → 필요한 만큼만 읽도록 구성.

**지연 로딩 비유 (슬라이드 39)** — L1 = 라우팅 테이블(항상 메모리에), L2 = 지연 import·코드 스플리팅·JVM 지연 클래스 로딩, L3 = 디맨드 페이징, L4 = RPC(구현은 바깥, 반환값만).

**선택적 로딩 예 (슬라이드 40)** — "이번 분기 매출 추이 보여줘" → SKILL.md 목차(Finance, Sales, Product, Marketing) → `references/finance.md`만 Read → 나머지 셋은 디스크에만(토큰 0). "파일시스템이 컨텍스트의 확장 메모리가 된다."

**스킬 폴더 구성 (슬라이드 41, 가상의 `secure-review/`)**

```text
secure-review/
  SKILL.md          # L2, 목차와 분기. 호출 시 컨텍스트로
  references/       # L3, java.md python.md ts.md — 해당 언어 파일만 Read
  workflows/        # L3, new-endpoint.md 등 배타적 절차 — 지금 작업 하나만
  scripts/          # L4, scan.py validate-report.py — 실행만, 출력만 돌아옴
  templates/        # 출력 양식 — 누가 실행해도 결과 형식이 같다
  (공통 자료)        # 여러 스킬이 함께 쓰는 자료
```

**폴더 분리 효과 (슬라이드 42)** — 비용(선택적 로드·배타적 경로), 품질(scripts는 실행만 → 테스트·CI로 검증, templates로 출력 일관성), 협업(읽지 않는 파일은 비용 0이라 번들은 사실상 무제한, 파일 단위 담당자 리뷰). **주의: 참조는 SKILL.md에서 한 단계 깊이까지만.**

**지식량과 상시 비용 (슬라이드 43)** — 전부 CLAUDE.md면 지식량과 상시 비용이 함께 는다. 스킬로 나누면 상시 비용은 스킬 수 × 한 줄(name/description). 주의의 질(관련된 것만 올라와 잡음↓), 결정성(스크립트), 조합(팀마다 스킬을 늘려도 서로 비용을 거의 먹지 않음). 측정값이 아니라 경향.

**하네스의 점진적 공개 (슬라이드 44)** — Progressive Disclosure는 스킬만이 아니라 하네스 전체의 설계 원칙.
- `.claude/rules` paths 규칙 / 하위 CLAUDE.md: 매칭·그 디렉터리 작업 시 로드.
- MCP tool search: 세션 시작 시 도구 이름과 서버 instructions만, 스키마는 필요할 때.
- 서브에이전트: 별도 컨텍스트에서 읽고 요약만 반환(문서 예시 6,100 읽고 420 토큰 반환 — 예시값이지 평균 아님).

**L4 심화: 스킬과 MCP (슬라이드 45~46)** — "MCP가 손발이라면, 스킬은 그 손발을 쓰는 숙련이다."

| | MCP 단독 | 스킬 |
|---|---|---|
| 담는 것 | 도구 인터페이스(무엇을 할 수 있나) | 절차·노하우·참고 자료(어떻게 잘하나: 순서, 판단 기준, 예외 처리) |
| 세션 시작 비용 | 도구 정의 전부 로드(tool search 이전 기준) | 마크다운, 스킬당 한 줄 |
| 중간 결과 | 매번 컨텍스트를 거쳐 다음 호출로 복사 | 스크립트 안에서 처리, 출력만 |
| 결정성 | 도구 조합은 모델 판단(매번 다를 수 있음) | 검증된 스크립트가 같은 결과 보장 |
| 작성·배포 | 서버·프로토콜·인증·운영 필요 | git으로 공유, 팀이 직접 쌓음 |

- MCP가 여전히 나은 곳: 외부 시스템 연결(인증·권한·네트워크 경계를 서버가 책임), 상태 보존(세션·이벤트를 프로세스 밖에 저장), 호출 시점 데이터.
- Claude Code는 MCP에도 tool search를 기본 적용 → 시작 비용 차이는 크게 줄었다. 남는 차이는 "무엇을 담느냐". **둘은 대체가 아니라 보완.**

**직접 도구 호출 vs Code Mode (슬라이드 47~49)**
- 직접 호출: 모델이 `getDocument`(Google Drive) 호출 → 회의록 전문(2시간 회의 ≈ 5만 토큰, Anthropic 글 예시 규모)이 컨텍스트로 → 같은 전문을 `updateRecord`(Salesforce) 인자로 다시 출력 → **데이터가 컨텍스트를 두 번 지나감**.
- Code Mode: 모델이 코드를 한 번 쓴다(스킬의 검증된 스니펫 조합) → 샌드박스에서 `doc = getDocument(...)`, `updateRecord(doc)` → 완료 로그 한 줄만 반환. 이름 출처: Cloudflare 2025.9 "Code Mode", Anthropic 2025.11 "Code execution with MCP".
- 토큰 절감(글 속 예시값, 평균 아님): 도구 정의 150,000 → 2,000 토큰(98.7%), 1만 행 → 5행. 정의와 중간 데이터가 클수록 효과가 커진다는 **방향**으로 읽는다.

**코드 스니펫의 장점과 비용 (슬라이드 50)** — 장점: 효율(중간 결과가 환경 안에), 결정성, 제어 흐름(반복·조건·에러 처리는 코드가), 개인정보(`EMAIL_1`처럼 토큰화해 모델을 안 거침), 상태(중간 결과를 파일로 저장해 이어감), 축적(잘 된 코드를 함수로 저장하고 SKILL.md를 붙인다). 비용: 샌드박스·리소스 제한·모니터링 — 직접 호출에는 없던 운영 부담. API 키는 바깥 루프만 갖는다(Cloudflare) → 3부의 훅·샌드박스로 이어짐. **도입 전에 실행 경계부터 정한다.**

**예제: 결제 API 스니펫 (슬라이드 51)** — 값은 파라미터로 묶고, 비밀은 환경에서 읽고, 출력은 짧은 JSON으로.

```python
# 1. 입력 — 값과 비밀 분리
dsn = os.environ["PAY_DB_DSN"]
sql = ("SELECT status, COUNT(*) "
       "FROM refunds WHERE merchant_id=%s "
       "AND day=%s GROUP BY status")
cur.execute(sql, (merchant_id, day))

# 2. 출력 — 집계만 반환 (원본 행은 실행 환경에 남긴다)

print(json.dumps(result))
```

**스니펫 설계 원칙 (슬라이드 52)** — "스크립트의 출력이 곧 모델이 보는 전부다."
1. 실행인지 참조인지 본문에 적는다. 경로는 `${CLAUDE_SKILL_DIR}`로 고정하고 같은 경로를 `allowed-tools`에 넣는다.
2. 출력 계약: 짧은 JSON처럼 형식을 정한다. 실패하면 무엇을 고칠지 스크립트가 구체적으로 출력.
3. SKILL.md 예시(필드 이름은 문서 버전 확인):

```markdown

description: Reviews new API endpoints for ...
allowed-tools: Bash(${CLAUDE_SKILL_DIR}/scripts/*)
---
Run scripts/scan.py. Do not read it.
Output is JSON; act on findings only.
```
(추출본에는 `name: secure review`, `allowed tools: Bash CLAUDE SKILL DIR /scripts/*`로 기호가 빠져 있어 표준 표기로 복원했다.)

**오픈소스 사례: ouroboros 구조 (슬라이드 53)** — 스킬은 절차와 판단을, MCP 서버는 상태 관리를 담당.
1. `plugin.json` 두 줄이 스킬과 MCP 서버를 함께 선언: `skills: ./skills/`, `mcpServers: ./.mcp.json`
2. `/ouroboros:interview` 호출 → 절차와 게이트가 담긴 본문만 L2 로드
3. deferred 도구를 tool search로 탐색해 스키마 로드. 다음 턴에도 남아 있다고 가정하지 않는다(턴마다 다시 확인)
4. `ouroboros_interview`를 `session_id`와 함께 반복 호출 — 신호와 점수만 반환, 상태(세션 상태·이벤트·모호성)는 서버에 남아 컴팩션에도 진행 유지
5. 스킬 쪽 판단 게이트: `seed_ready`는 완료가 아니라 "마무리 점검을 시작해도 된다"는 허가로만 취급

**신뢰 경계 (슬라이드 54)** — MCP의 응답은 데이터이고, 결정은 스킬의 게이트가 내린다. MCP `seed_ready` 반환 → Acceptance Guard(확인) → Restate gate(목표 재진술) → 사용자 명시적 승인(MCP 신호는 사용자 승인이 아님) → seed 생성. 어느 단계든 미흡하면 질문으로 돌아가 서버를 다시 호출.

**런타임 이식성 (슬라이드 55)** — 능력(capability) 선언과 실행을 분리. 스킬은 `ask_user`, `call_mcp`, `run_lateral_review` 같은 중립 능력만 선언, `SKILL_CAPABILITY_GUIDE.md`(런타임별 가이드)가 실제 도구로 번역. 일부 스킬은 프론트매터에 `mcp_tool`, `mcp_args` 자체 필드 → Claude Code는 모르는 필드를 무시하고 본문이 동작을 정함, Codex·Kiro에서는 SkillInterceptor가 이 필드를 읽어 `ooo <skill>` 입력을 LLM 없이 MCP 핸들러로 보냄(결정적 디스패치).

**지연 로딩의 대가 (슬라이드 56)** — 스킬이 실패하는 지점은 모두 지연 로딩의 대가다.

| 대가 | 처방 |
|---|---|
| 인덱스 미스(불려야 하는데 안 불림) | description 수정: 무엇을·언제를 3인칭으로, 핵심 용도 맨 앞 |
| 탐색 미스(L3가 안 읽히거나 다 읽힘) | 조건부로 가리킴, 참조 1단계, 긴 파일엔 목차 |
| 언로드 없음(로드된 본문이 안 내려감) | 본문 500줄 이하, 작업 전체 지시로 |
| 컴팩션 손실(시간이 지나면 스킬을 안 따름) | 핵심 규칙은 맨 위(호출된 본문 앞부분만 복원) |
| 의도적 즉시 로딩(실패 아님) | 서브에이전트 `skills:` 프리로드 — 역할 고정 워커는 처음부터 올린다(일부러 지연 로딩 포기) |

**사례 적용: 스킬 본문 크기 (슬라이드 57)** — 강의 작성 시점(main, 플러그인 v0.55.7) ouroboros `interview` SKILL.md 913줄 단일 파일, `welcome` 1,176줄. MCP 연동은 모범적이지만 본문 크기는 언로드 없음·컴팩션 손실에 노출. 생각해볼 방향: 단계별 절차(Path A/B, 재개 로직)는 `workflows/`로, 게이트 판정 기준(Seed Closer, Acceptance Guard)은 `references/`로, 본문 맨 위엔 매 턴 지킬 핵심 규칙만(컴팩션 후 앞 5,000토큰만 복원).

**로드 시점과 위치 (슬라이드 58)** — Progressive Disclosure가 "언제"를, 서브에이전트가 "어디에"를 정한다.

| | 시작 시 로드 | 필요할 때 로드 |
|---|---|---|
| 메인 컨텍스트 | CLAUDE.md(1부, 모든 턴 비용) / 스킬 description만 상주 | 스킬 본문은 호출 시 |
| 별도 컨텍스트 | 서브에이전트 `skills:` 프리로드(역할 고정 워커에 처음부터, `mcpServers`도 워커에만) | 스킬 `context: fork`(호출 시 별도 컨텍스트에 로드, 메인엔 결과만) |

**결과 전달 계약** — 입력 브리프: 목표, 범위, 제약, 완료 조건, 출력 형식. 출력: 짧은 구조화 요약(L1처럼), 상세는 파일로 쓰고 경로만(L3처럼). 반환 방향에도 같은 원리를 적용.

**호스트 주도 작업 분산 (슬라이드 59)** — MCP 서버는 분배 계획만 세운다(`spawn_subagents` 페이로드 N개 반환). 서버는 서브에이전트를 직접 띄울 수 없으므로 스킬을 따르는 메인 세션(호스트)이 페이로드마다 하나씩 띄운다. 각 워커는 `payload.prompt` 수행 후 correlation key를 붙여 반환, 부모가 key로 짝지어 종합. 출력 계약 준수는 3부의 SubagentStop 훅으로 검증.

**참조 선택과 결과 계약 (슬라이드 60)** — 가상 결제 API 팀, 버그 "부분 환불 후 정산 금액 불일치".
1. SKILL.md 조건문: 환불 금액 문제 → `refunds.md`, 정산 불일치 → `settlement.md`. `cards.md`, `payouts.md`는 디스크에.
2. 워커 1(환불 계산, key `refund-calc`), 워커 2(정산)가 같은 계약으로 반환. **결과 계약 5줄 이내:**

```text
key: refund-calc
verdict: bug | ok | unknown
evidence: file:line (1~3개)
detail_path: reports/refund-calc.md
```
부모 세션은 key로 결과를 짝짓고, 상세는 파일 경로만 넘긴다.

**단계별 설계 원칙 — 스킬 점검표 (슬라이드 61)**
- L0: 부작용 있는 스킬은 `disable-model-invocation`으로 L0에(사용자가 `/name`으로만).
- L1: 무엇을 하는지·언제 쓰는지 3인칭, 적용 범위는 `paths`로 제한.
- L2: 500줄 이하, 목차·분기 위주, 작업마다 자유도 명시.
- L3: 도메인별 분리, 내용이 드러나는 파일명, 깊이 한 단계, 긴 파일엔 목차.
- L4: 결정적 작업은 스크립트, 실행/참조 명시, 에러는 스크립트가 직접 처리.

**팀 스킬 점검 (슬라이드 62)** — 아래 "실습 과제" 참고.

**스킬의 한계와 훅 (슬라이드 63) / Skills 정리 (슬라이드 64)** — 스킬은 필요할 때 꺼내 쓰는 지식이라 "반드시 모든 내용을 실행한다"를 보장하지 못한다. 전환 기준(사실이 아니라 절차로 자라면 스킬로), 점진적 공개(목록 한 줄만 상시), MCP와 보완(MCP는 도구, 스킬은 그 도구를 쓰는 절차), 강제 아님(호출은 모델이 정함 → 반드시 실행할 검사는 훅으로). 서브에이전트 설계 질문: "메인 컨텍스트가 이 과정을 봐야 하는가?"

#### 3부 Hooks

**요청과 보장 (슬라이드 66)** — "CLAUDE.md에 `.env 수정 금지`라고 쓰면 반드시 지켜질까?"
- Memory = 요청: 매 세션 읽는 지침, 실행 강제 장치 아님.
- Skills = 요청: 필요할 때 로드되지만 호출과 준수는 보장 안 됨.
- Hooks = 보장: 이벤트에 맞춰 **하네스가** 실행. 단, **실행 보장과 코드의 검사 범위는 구분한다.**

**훅 강의 구성 (슬라이드 67)** — 01 기초·02 선택(정의, 루프 위 위치, 3단 구조, 입출력, 의도별 이벤트·핸들러) / 03 비교·04 안정성(훅 vs 스킬, 훅이 규칙이 되기 위한 설계 원칙) / 05 보안·06 하네스(가이드 준수 하네스와 층별 한계, 메모리·스킬·훅 결합과 거버넌스 — **추출 범위 밖**).

**훅의 정의 (슬라이드 68)** — 생명주기의 특정 시점에 자동으로 실행되는 사용자 정의 동작.
- 핸들러 5종: `command`(셸 명령), `http`(정책 서버 POST), `mcp_tool`(기존 도구 호출), `prompt`(단일 턴 판단), `agent`(파일 확인·판단).
- 결정론적 제어: 매칭된 이벤트가 오면 하네스가 실행(모델의 선택과 무관). 모델 판단형 핸들러는 결과의 비결정성을 별도로 가진다.
- 터미널·IDE·데스크톱·클라우드 등 사용 표면과 이벤트 실행 구조를 구분한다.

**훅 실행의 3가지 주기 (슬라이드 69)** — 발행 이벤트는 30개가 넘지만 발화 주기로 보면 셋.
1. 세션마다: `SessionStart` / `SessionEnd`
2. 턴마다: `UserPromptSubmit`(입력) / `Stop`, `StopFailure`(응답 종료)
3. 도구 호출마다: `PreToolUse`(실행 전) / `PostToolUse`(실행 후)

**훅의 구성 요소 (슬라이드 70)** — 이벤트 → 매처 그룹 → 핸들러. 도구 이벤트는 `if`로 한 번 더(matcher는 도구 이름, `if`는 권한 규칙 문법으로 인자까지).

```json
"PreToolUse": [{
  "matcher": "Bash",
  "hooks": [{
    "type": "command",
    "if": "Bash(rm *)",
    "command": ".claude/hooks/block-rm.sh"
  }]
}]
```

**훅 정의 위치 (슬라이드 71)** — 개인 `~/.claude/settings.json`(local은 공유 제외) / 팀 `.claude/settings.json` / 조직·플러그인(managed 정책, `hooks/hooks.json`) — **모든 출처 병합, 회사 훅 삭제 불가** / 스킬 frontmatter 훅(호출 뒤 세션 끝까지) / 서브에이전트 frontmatter 훅(그 에이전트 실행 중).

**훅의 입력과 출력 (슬라이드 72)** — stdin JSON(session, cwd, event, tool_input) → 핸들러 → 세 채널:
1. exit code: 클라이언트에 상태 전달. 같은 코드라도 이벤트에 따라 효과가 다름.
2. stdout JSON: 성공 종료(exit 0)의 JSON으로 deny·block 등 세밀한 결정.
3. `additionalContext`: 실행 지점의 모델 맥락으로 전달. **사실 진술로 쓴다.**

**종료 코드 — "exit 1은 막지 않는다" (슬라이드 73)**

| 코드 | 의미 | Pre | Post |
|---|---|---|---|
| exit 0 | 성공, JSON 적용 가능. **승인 확정이 아니다** — JSON이 없으면 일반 권한 흐름(침묵은 승인 아님) | 일반 권한 흐름 | 의견 없음 |
| exit 2 | 차단 가능 이벤트만 차단. 이유를 모델로 전달 | 실행 차단 | 이미 일어난 부작용은 되돌리지 못함, 알림·후속 수정 |
| exit 1 | 기본은 **비차단 오류**. 시크릿을 찾고 exit 1로 끝내도 파일 쓰기는 막히지 않는다 | 동작 계속(의도와 다름) | 기본 진행 |

**JSON 결정 (슬라이드 74)** — exit 0 + stdout JSON. `updatedInput`은 실행 전 인자를, `updatedToolOutput`은 Post에서 결과를 바꾼다.

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "DB 쓰기 금지"
  }
}
```

**훅 선택 기준 (슬라이드 75)** — 이벤트 이름이 아니라 "무엇을 실행하고 싶은가"로 고른다.
- 막는다(사전 게이트, 차단 가능): `PreToolUse`, 입력 경계 이벤트
- 고치게 한다(센서 피드백, 되돌리기 불가): `PostToolUse` — 실행 뒤 린트·SAST 결과를 모델에게
- 끝내기 전 확인·알림·기록: `Stop`, `SubagentStop`(완료 판정), 실패·배치 이벤트, 세션·관측 이벤트(상태 주입·증빙)

**훅의 3가지 역할 (슬라이드 76)** — "막을 건 Pre, 고칠 건 Post, 끝낼 땐 Stop."
1. PreToolUse = 게이트: 실행 전에 거부(실행 후 되돌림과 다른 시점) → 거부 시 모델이 재작성
2. 도구 실행: Edit·Write·Bash의 실제 부작용 발생
3. PostToolUse = 센서: 이미 실행된 결과를 알림(완료된 편집을 되돌리는 장치 아님)
4. Claude 수정: 스킬의 수정 패턴으로 고친다(훅 자체가 해결 방법을 주지 않는다)
5. Stop = 완료 게이트: 미해결 결과를 수정 루프로 보낸다. **세션 밖의 최종 검증(PR·CI)을 대신하지 않는다.**

**예제: 결제 API 훅 (슬라이드 77)** — Write 내용의 키 패턴을 PreToolUse가 거부 → 모델이 환경변수 방식으로 재작성해 게이트 재통과 → PostToolUse SQL 스캔이 이슈를 알림(편집은 되돌리지 않음) → 스킬의 바인딩 패턴으로 수정, 반복 확인 → Stop 완료 검사 → 최종 CI·리뷰(세션 검사를 통과해도 실제 실행 경로와 누락된 규칙은 CI와 리뷰로).

**메모리·스킬과 훅 (슬라이드 78)**
- 1부 연결: 규칙 로드는 `InstructionsLoaded`로 관측(로드 증빙: 경로·이유 기록). **관측 전용, 로드를 막는 게이트가 아니다.**
- 2부 연결: `SubagentStart`에 정책 맥락 주입, `SubagentStop`에서 결과 계약(형식·품질) 검증.

**훅 핸들러 유형 (슬라이드 79)** — 기본은 command, 판단이 필요할 때만 모델을 부른다.
- 규칙 기반 검사(결정론): `command`(로컬 명령), `http`(정책 서버), `mcp_tool`(기존 도구 재사용).
- 맥락 기반 판단(모델): `prompt`(단일 턴 평가), `agent`(파일 확인·판단) — 비용·지연·비결정성 감수. `prompt` 실패는 기본 비차단.
- **http 훅의 함정:** 연결 오류나 non-2xx도 **fail-open**. 차단은 JSON 결정 또는 지원 버전의 `onFailure: block`으로 설계.

**훅과 스킬 비교 (슬라이드 80)**

| 기준 | 훅 | 스킬 |
|---|---|---|
| 실행 주체 | 하네스가 실행 | Claude가 읽고 따름 |
| 트리거 | 이벤트마다 발화 | `/이름` 또는 description 매칭 |
| 판단 | command는 판단 없음 | 상황 판단 가능 |
| 강제력 | deny로 차단 | 강제력 없음, 요청 |

**훅의 장단점 (슬라이드 81)** — 장점: 트리거 보장, 결과 강제(deny), 컨텍스트 비용 0, 압축 뒤에도 같은 판정, 같은 입력·같은 결과로 감사 가능. 단점: 판단 불가·고치는 법 모름, 이벤트 경계에 묶임, 설계·운영 비용, **fail-open 기본값**, 훅 자체가 공격 표면.

**훅과 스킬의 결합 (슬라이드 82)** — "검사는 훅, 해결은 스킬." 훅은 위반을 찾아 피드백하고 스킬은 고치는 법을 제공. 스킬 frontmatter 훅은 스킬 호출 뒤 세션 범위로 등록(스킬이 훅을 데리고 다닌다). 승격 기준: 반복 절차는 스킬로, 반드시 실행될 검사는 훅으로 → 수정 루프를 만든다.

덱 안에 명시된 실습형 활동(채점 과제 아님). 저장소 `Day06/task.md`의 실습(Pi 분석, Claude Code & GJC 개발환경 구축)은 `99-extras.md`와 scratchpad의 저장소 지도를 참고.

**A. 팀 메모리 승격 한 바퀴 (슬라이드 29, "결제 API 팀이 이번 주에 해 볼")**
1. 수집 — 팀원 각자 `/memory`로 auto memory 폴더를 열어 `MEMORY.md`와 토픽 파일을 본다(평문이라 고치고 지울 수 있다).
2. 분류 — 둘 이상이 같은 내용을 갖거나 동작이 갈린 항목을 골라 판정 흐름 Q1~Q5로 목적지를 정한다.
3. PR — 팀 합의 항목만 CLAUDE.md나 `.claude/rules`에 PR로 올리고 리뷰어 지정. 개인 선호는 각자 `~/.claude`로.
4. 확인 — 머지 후 새 세션에서 `/context`와 `InstructionsLoaded`로 로드를 확인하고, 준수는 diff·테스트·리뷰로 본다.
5. 정리 — 승격한 원본 메모리를 지운다. 반드시 지켜야 하는 항목은 3부에서 hook·permissions.deny로 옮길 목록에 올린다.

**B. 팀 스킬 점검 (슬라이드 62)**
1. 고르기 — 지난주 가장 많이 쓴 스킬이나, 있어야 할 때 안 불린 스킬 하나.
2. L1 진단 — description 첫 문장만 읽고 "무엇을/언제"가 보이는지, 사용자가 실제로 쓰는 단어가 있는지.
3. L2 진단 — 본문 줄 수가 500줄을 넘는지, "참조를 전부 읽어라" 문구가 있는지.
4. L3/L4 진단 — 참조가 조건부로 가리켜지는지, 매번 같아야 하는 단계가 텍스트 지시로만 남아 있지 않은지.
5. 한 가지만 고친다 — 가장 큰 대가 하나만 이번 주에. 효과는 **숫자를 지어내지 말고** "제때 불렸나 / 결과 형식이 일정했나"를 팀이 관찰해 기록.

**C. 참조 선택과 결과 계약 연습 (슬라이드 60)** — 버그 문장을 보고 (1) 스킬의 어떤 참조를 읽을지 정하고, (2) 워커 반환 형식을 5줄 계약(key/verdict/evidence/detail_path)으로 정한다.

**D. 생각해볼 질문 (슬라이드 57)** — 913줄짜리 단일 SKILL.md를 L3로 어떻게 쪼갤까?

### 실제 프로젝트 적용 체크리스트

도구 이름(Claude Code의 CLAUDE.md·rules·skills·hooks 등)은 예시일 뿐이다. 원칙은 "지침(부탁) → 위임 → 강제"의 층 구분과 "필요할 때 필요한 만큼"이다.

**지침·메모리 배치**
- [ ] 각 지시를 Q1~Q5로 판정했다: 반드시 지켜야 함 → 코드 강제(사전 차단·권한 거부) / 여러 단계 절차 → 필요 시 로드되는 절차 묶음 / 개인 → 개인 계층 / 조직 공통 → 중앙 배포 계층 / 특정 경로 → 경로 범위 규칙 / 나머지 → 루트 상시 지침.
- [ ] 상시 로드되는 루트 지침은 짧다(목표: 수백 줄 미만, 덱 권장 200줄 이내). 코드로 알 수 있는 구조는 빼고 함정·근거·관례만 남겼다.
- [ ] 경로에만 해당하는 관례는 경로 범위 규칙이나 하위 지침 파일로 분리했다.
- [ ] 계층 간 충돌은 우선순위가 아니라 **관심사 소유권**(조직=보안·컴플라이언스, 팀=빌드·컨벤션, 개인=스타일)으로 제거했다. 충돌하는 지시를 남겨 두지 않는다.
- [ ] 사용하는 런타임·표면에서 지침 파일이 **실제로 로드되는지** 확인했다(예: AGENTS.md와 CLAUDE.md가 공존할 때의 판정, 하위 폴더 누적 vs 최근접).
- [ ] "로드됨 ≠ 지켜짐", "강한 문구 ≠ 강제"를 팀이 공유한다. 준수 여부는 결과(diff·테스트·리뷰·검사)로 확인한다.
- [ ] 압축(compaction) 뒤 재주입되는 것과 빠지는 것을 알고, 반드시 남아야 하는 규칙은 루트 지침이나 코드 검사로 옮겼다.
- [ ] 하위 에이전트에 무엇이 전달되지 않는지(개인 메모리·대화) 알고, 필요한 관례는 에이전트 정의·규칙에 명시했다.

**메모리 운영·승격**
- [ ] 에이전트가 스스로 쌓는 로컬 메모리는 원료로 보고, 주기적으로 사람이 검토해 맞는 계층(개인/팀/조직/강제)으로 승격한다. 승격 뒤 원본은 지운다.
- [ ] 지침·규칙 파일 변경은 코드처럼 PR로 리뷰하고, 큰 모델 업데이트 뒤 우회 규칙을 재검토한다.
- [ ] "기억해"와 "팀 지침에 추가해"가 다른 저장소로 간다는 사실을 팀이 안다(팀 지식이 개인 메모리에만 있는 "의존 상태"를 피한다).

**절차(스킬) 설계**
- [ ] 판단 기준은 길이가 아니라 **사용 시점**: 매 턴 필요한 사실은 상시 지침, 특정 작업 절차는 필요 시 로드 묶음.
- [ ] 절차 묶음의 상시 노출 부분(이름·설명)은 "무엇을·언제"를 3인칭으로, 핵심 용도를 앞에 썼다.
- [ ] 본문은 목차·분기 위주로 짧게(덱 권장 500줄 이하), 핵심 규칙은 맨 위에(압축 뒤 앞부분만 복원될 수 있으므로).
- [ ] 세부는 도메인별 참조 파일로 나누고 본문이 **조건부로** 가리킨다. 참조 깊이는 한 단계.
- [ ] 매번 같아야 하는 결정적 단계는 스크립트로 만들고, "실행하라/참고하라"를 명시했다. 스크립트 출력은 짧은 구조화 형식(JSON 등), 실패 시 고칠 방법을 출력한다.
- [ ] 부작용이 있는 절차는 모델이 자동 호출하지 못하고 사람이 명시적으로만 부르게 했다.
- [ ] 스크립트는 값은 파라미터 바인딩, 비밀은 환경에서 읽기, 출력은 집계만 — 원본 데이터는 실행 환경에 남긴다.
- [ ] 코드 실행(Code Mode류)을 도입한다면 샌드박스·리소스 제한·모니터링·키 보관 위치(바깥 루프만)부터 정했다.

**도구 연결과 신뢰 경계**
- [ ] 외부 시스템 연결·인증·상태 보존은 도구 서버(MCP 등)에, 그 도구를 쓰는 순서·판단 기준은 절차 묶음에 둔다(대체가 아니라 보완).
- [ ] 도구/서버의 응답은 **데이터**다. "완료/준비됨" 신호를 사용자 승인이나 완료 선언으로 취급하지 않고, 절차의 게이트(확인·재진술·명시적 승인)가 결정한다.
- [ ] 도구 정의는 이름만 먼저, 스키마는 필요 시 로드하는 방식을 쓰거나 고려했다. 지연 로드된 도구가 다음 턴에도 있다고 가정하지 않는다.

**위임(하위 에이전트)**
- [ ] 위임 입력은 브리프(목표·범위·제약·완료 조건·출력 형식), 반환은 짧은 구조화 요약 + 상세 파일 경로(예: key / verdict / evidence file:line / detail_path, 5줄 이내).
- [ ] 병렬 결과는 correlation key로 짝짓고, 반환 계약 준수는 종료 이벤트에서 코드로 검증한다.
- [ ] 설계 질문 "메인 컨텍스트가 이 과정을 봐야 하는가?"로 위임 여부를 정했다.

**강제(훅·권한)**
- [ ] 반드시 지킬 규칙은 사전 차단(실행 전 게이트)이나 권한 거부로 강제했다. 사후 검사는 이미 일어난 부작용을 되돌리지 못한다는 것을 전제로 설계했다.
- [ ] "막을 건 실행 전, 고칠 건 실행 후, 끝낼 땐 완료 게이트"로 이벤트를 골랐다.
- [ ] 훅/게이트의 차단 신호를 정확히 구현했다(예: Claude Code는 exit 2 또는 JSON deny가 차단, **exit 1은 비차단**, exit 0은 승인이 아님).
- [ ] 원격 정책 검사 등 실패 시 **fail-open**이 기본인 핸들러는 실패 정책을 명시적으로 설계했다.
- [ ] 기계적 규칙은 결정론적 핸들러(명령·정책 서버)로, 맥락 판단이 꼭 필요할 때만 모델 판단형 핸들러를 쓴다(비용·지연·비결정성 감수).
- [ ] 모델에 주입하는 추가 맥락은 사실 진술로 쓴다.
- [ ] "검사는 훅, 해결은 스킬": 위반 탐지와 수정 방법 제공을 나눴다.
- [ ] 세션 안 검사를 통과해도 최종 CI·리뷰를 생략하지 않는다(완료 게이트는 세션 밖 검증을 대신하지 않는다).
- [ ] 지침 로드는 관측 이벤트로 증빙을 남긴다(관측이지 차단 게이트가 아님).
- [ ] 훅 자체가 공격 표면임을 알고 정의 위치(개인/팀/조직/플러그인)와 병합 규칙을 관리한다.

**점진적 공개 전반**
- [ ] 하네스 전체(경로 규칙, 하위 지침, 도구 스키마, 하위 에이전트, 절차 묶음)에 "필요한 시점에 필요한 만큼"을 적용했다.
- [ ] 덱의 수치(200줄, 25KB, 500줄, 토큰 절감률 등)는 예시·버전 의존값으로 보고, 쓰는 도구의 현재 문서로 확인한다.

### 핵심 요약 (3~5줄)
- 메모리·에이전트·스킬로 하네스를 짜도 결과는 "적당히 마음에 드는" 수준에 그친다. pstack도 **가이드만** 있고 안정성은 고려되어 있지 않다. 안정성은 **훅**으로 보완한다.
- 대표 예는 "코드 생성 작업이 끝나면 항상 테스트 실행". 지시하면 "가끔" 듣는다. 코드 생성은 **파일 수정(확장자 .py, .ts, .tsx, .java 등)**으로 감지하고, 돌릴 테스트는 **LLM 판단 없이 이름·폴더 규칙으로** 골라 필요한 만큼만 돌린다. 그러다 보면 파일을 작게 유지하게 된다.
- 프로젝트 훅은 코드가 쌓여 규칙이 생긴 뒤 **필요에 의해** 만들어진다. 미리 넣을 수 있는 훅은 권한 체크나 **UserPromptSubmit으로 프롬프트 앞뒤에 잊기 쉬운 지침을 붙이는 것**이다.
- 설정은 프로젝트 `.claude/settings.json`(팀 공유) / `settings.local.json`(나만)에 두고, `env`로 그 프로젝트에서만 다른 모델·엔드포인트를 쓸 수 있다. 글로벌(`~/.claude`)은 비워 두고 프로젝트 레벨에서 세팅하길 권한다.
- 공개 하네스(OMO, oh-my-claudecode, Ouroboros)를 소개하고, 과제로 **나만의 하네스를 만든 뒤 빈 폴더에서 작은 개발 작업(백엔드 API 하나)으로 검증**하게 했다.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**1. 모호성 점수와 API 에러 (00:06~01:40)**
- 인터뷰 도구(Ouroboros)는 턴마다 **모호성** 점수를 체크하고 "20% 언더로 떨어지면 그냥 됐다라고 판단"한다.
- 강사는 "100% 믿지는 않아요" — 여러 기준을 뒀어도 "결국은 그래도 LLM이 출력하는 숫자라서". 그냥 "어느 정도 계획이 충족됐는지를" 보는 용도.
  - (저장소 확인: `AMBIGUITY_THRESHOLD = 0.2` — `Day06/ouroboros/src/ouroboros/bigbang/ambiguity.py:37`; 점수가 0.2 이하여야 Seed 생성 가능, `force=True`로만 우회 — `Day06/HARNESSES.md:302-303`)
- 요즘 API 에러가 자주 난다(강사는 네트워크 끊김). 그럴 땐 "이전 작업 그냥 계속 이어서 해라" 하고 지시하면 된다.

**2. 하네스를 직접 만드는 이유 — 가이드만으로는 안정성이 없다 (01:42~04:36)**
- "여러분들이 분명히 업무하러 가시면 안 만드실 거거든요… 확신합니다. 왜냐하면 저도 이걸 잘 안 만들었거든요."
- 강사의 경로: 처음엔 "1번"(컨텍스트 관리 — 메모리 촘촘히) → 작업 특성에 맞는 에이전트·스킬 추가 → "음 일단 나쁘지 않네" → 그런데 "2번이 항상 문제" — "내가 적당히 마음에 드는 작업 결과물". 팀원과 공유해도 "적당히 안정적인 결과물".
- "이 안정성 측면이 지금 pstack도 고려가 안 되어 있죠. 그냥 가이드만 되어 있습니다." → "훅을 여러분들이 세팅을 해주시는 게 중요해요."
- 지금까지는 글로벌(홈 폴더의 `.claude`)에서만 작업했고 플러그인 수정도 홈 폴더에서 했다. 그런데 작업 안정성은 "다른 사람이랑 나랑 똑같은 작업으로 이 강제 코드가 돌아갔으면" 하는 프로젝트 차원의 문제다.

**3. 코드 생성 후 항상 테스트 — 훅이 필요한 이유 (04:36~07:05)**
- "코드 생성 작업이 끝나면 항상 테스트 코드 실행하기 — 이거 지시한다고 들을까요?" → "가끔 들어요… 항상 실행하지 않습니다." → "훅을 사용할 수밖에 없습니다."
  - (저장소 확인: 공식 문서 인용 "deterministic control: certain actions always happen rather than relying on the LLM to choose to run them." — `Day06_new/docs/sources/claude_code/03_control.md:251`)
- 첫 문제: **코드 생성 작업을 어떻게 알아내나** — "이게 훅을 설계하는 기본 아이디어가 되거든요." 수강생 답 "파일이 수정됐을 때"를 강사가 정답으로 봤다. "한 줄이라도 코드를 수정하면 수정이든 삭제든" 코드 생성 작업이 끝난 것이고, 이는 "확장자로 캐치할 수가 있습니다" — "별.py, ts, tsx, java 등등등".
  - (저장소 확인: 도구 실행 뒤 피드백 이벤트 PostToolUse "Runs immediately after a tool completes successfully." — `03_control.md:298`; 단 "PostToolUse는 막지 못함… the tool already ran" — `03_control.md:220`. 강의에서 이벤트 이름은 말하지 않았다.)

**4. LLM 없이 필요한 테스트만 돌리기 — "하네스의 마지막 관문" (07:05~14:10)**
- 둘째 문제: 테스트가 너무 많다. 전부 돌리면 "자원낭비가 심하기 때문에 필요한 만큼만". 사람은 기능 추가한 부분의 테스트만, 개선이 크면 연관된 것까지 돌린다. "저도 정답을 갖고 있는 건 아니거든요."
- 핵심 제약: "판단이라는 과정을 아예 LLM을 타지 않고 하게 하려고 하는 게 목적". "LLM을 타면… 할지 안 할지 할지 안 할지가 반복되기 때문에" — "우리 하네스의 마지막 관문이 요 녀석입니다."
- 해법(강사가 본 사례): 타입스크립트 쪽 라이브러리에서 `a.tsx`(전사 "a.psx")를 수정하면 그에 대응하는 테스트 파일이 정해진 모양으로 있어 "이거 고쳤어? 이거 돌려?" 매칭이 된다. "네이밍을 또는 폴더를 만족시키게끔… 코드와 테스트 코드를 구성하시면… 요 파일 고치면 요 코드 실행하고 저 파일 고치면 저 테스트 코드 실행하고".
- "이걸 LLM으로 판단하게 해야지라고 하면 안 좋은 방향인 것 같아요. 우리는 항상 실행되기를 원하는 것 같아요."
- 이상적인 건 함수 하나의 테스트만 돌리는 것이지만 "LLM 없이는 꽤 불가능". 그래서 파일 단위 매칭 → "파일이 잘게 쪼개집니다". 소스가 길면 테스트도 무거워지므로 "파일 하나를 좀 작게 유지해야겠구나 자연스럽게 그렇게 발전을 하죠."

**5. 프로젝트 훅은 필요에서 생긴다 (14:10~16:05)**
- 훅에서 프로그램을 실행해 테스트를 돌리는 건 어렵지 않다. 어려운 건 처음부터 만드는 것: "그 프로젝트 내가 시작하면 훅도 바로 세팅한다. 거의 불가능하더라고요." 코드 생성 작업이 계속 바뀌기 때문.
- 코드베이스에 코드가 쌓이면 "규칙이 정리가 되고" 그때 만들 수 있다. 지금 수업에서 훅을 건드리지 않는 이유도 "코드를 짜본 적이 없어서… 예측해서 만들고 있잖아요."
- "훅은 대부분 필요에 의해서만 만들어져요."

**6. 미리 넣을 수 있는 훅 — UserPromptSubmit으로 프롬프트 앞뒤 지침 (16:06~21:16)**
- 코드와 무관하게 미리 정의할 수 있는 훅: 수강생 답 "권한 체크"도 가능.
- 강사가 프로젝트에서 가장 많이 쓴 것: "제 거지 같은 프롬프트 앞뒤에 내용을 추가해 주는 거". **유저 프롬프트 서브밋(UserPromptSubmit)** — "제 프롬프트를 서버에 보내기 전에 캐치하는 거잖아요." 앞이든 뒤든 앞뒤 전체든 원하는 내용을 추가 가능.
  - (저장소 확인: "UserPromptSubmit | When a prompt is submitted, before Claude processes it." — `Day06_new/docs/sources/claude_code/03_control.md:180`; 지침·상태 주입 이벤트로 분류 — `Day06_new/use_cc/part2/concept.md:144`)
- 뒤에 붙일 예: "포테이토 모드를 그대로 쓰신다면 포테이토 모드를 무조건 활용하세요" — "왜냐면 나는 까먹을 수가 있거든요." 항상 실행해야 하는 스킬도 강제로 넣는다. 앞에는 "쓰고 싶은 거 쓰시면 됩니다."
  - (공식 문서 확인: https://github.com/cursor/plugins/tree/main/pstack — pstack README에 "start multiple agents up with `poteto-mode`", "claude code prefixes plugin commands and agents, so `/poteto-mode` is `/pstack:poteto-mode`." 강의의 "포테이토 모드"는 이 `poteto-mode`로 본다)
- 중복 방지 분기: 이전 유저 메시지에 이 지침을 "한 번이라도… 쓴 적이 있으면 그걸 출력하면 안 돼요. 중복이에요." 쓴 적이 없으면 출력, 있으면 "이전에 한 작업 지시를 그대로 따르세요" 또는 "이전에 한 작업 지시에 이어서 이 작업을 하는 게 맞는지 평가하세요"를 넣는다.
- 원칙: "안 하거나 자꾸 까먹는 거. 그런 것들이 훅에 들어가기 좋아요."
- 앞서 설명한 다양한 기능은 글로벌 레벨 플러그인 이야기였고, 프로젝트·내 컴퓨터 단위는 미리 세팅하기 어렵지만 그중 미리 세팅할 만한 것이 이런 것들이다.

**7. 프로젝트 단위 설정 위치 — settings.json / settings.local.json (21:16~23:50)**
- 다 같이 실행하는 훅은 프로젝트의 "점 클로드라는 폴더 밑에" 만든다(글로벌은 홈 밑 `.claude`). 훅 내용은 `hooks`로 생기고 `settings.json`에 넣는다.
- "settings.json은 나랑 이 프로젝트를 공유하고 있는 모두가 적용되는 거예요." "나만 쓰는 거는 점 로컬입니다… 규칙은 똑같아요."
- 팀과 같이 쓰는 것에는 훅뿐 아니라 "mcp도 있을 수 있습니다". 나중엔 직접 손으로 안 쓰고(Claude에게 시킴) 강사는 보여 주려고 손으로 쓴다.
- "스킬은 자동으로 로드되니까 따로 이 settings.json을 쓰지 않습니다."
  - (저장소 확인: `.claude/settings.json` "Everyone working in the folder that contains it.", `.claude/settings.local.json` "You, in this one project only." — `Day06_new/docs/sources/claude_code/03_control.md:55-56`; 훅 위치 표 — `같은 파일:259-261`)
  - (공식 문서 확인: https://code.claude.com/docs/en/settings.md — 공유 프로젝트 파일 용도 "Team permissions, hooks, plugins, and the environment variables the project needs", 로컬 파일은 Claude Code가 만들 때 git에서 빼 준다)

**8. env — 이 프로젝트에서만 다른 모델 쓰기 (23:50~28:46)**
- settings.json의 마지막 항목으로 "env도 여기 쓸 수 있습니다." 글로벌 Claude Code는 회사 계정(구독)을 유지하되 "이 프로젝트에만 들어오면 특정 모델을 쓰게" 하고 싶을 때.
- 강사 사례: 코드가 너무 많아 "클로드를 했다가는 지갑이 빵꾸가 날 것 같아서" "딥식, 플래시 뭐 이런 걸" 쓰고 싶었고, 글로벌을 건드리면 불편해 그 프로젝트에서만 세팅했다.
- 방법: Claude에는 "모델과 API 키를 따로 세팅할 수 있는 모드"가 있다. 예시 문서로 "오픈라우터 클로드 코드 인테그레이션" — "이건 안 보셔도 됩니다", Claude에게 물어보면 세팅해 준다. URL을 어딘가로 바라보게 하고 토큰값을 주면 그쪽으로 호출된다. "엔트로피[Anthropic] 베이스 URL"을 다른 것으로 주고, 모델 세팅에서 "오프스는 뭘로… 소넷은 뭐고 하이쿠는 뭐고" 실제로 보낼 모델명을 정한다(예: "딥식 … V4.1").
  - (공식 문서 확인: https://code.claude.com/docs/en/env-vars.md — `ANTHROPIC_BASE_URL` "Override the API endpoint to route requests through a proxy or gateway", `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_DEFAULT_OPUS_MODEL` / `ANTHROPIC_DEFAULT_SONNET_MODEL` / `ANTHROPIC_DEFAULT_HAIKU_MODEL` "Model ID that the `opus`/`sonnet`/`haiku` alias resolves to"; "Add variables under the `env` key in a `settings.json` file")
  - (공식 문서 확인: https://openrouter.ai/docs/guides/guides/claude-code-integration — `ANTHROPIC_BASE_URL="https://openrouter.ai/api"`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY=""`(비워 둠), 프로젝트 예시는 `.claude/settings.local.json`의 `"env"`)
- `.env`에 대해: "클로드는 점 EMV[.env]를 직접 못 보도록 돼 있거든요… 얘는 점 EMV를 보진 않아요." 그래서 settings.json을 활용하면 프로젝트 요구 대부분을 적용할 수 있다.
  - (미확인: 공식 env-vars 문서에서 `.env` 자동 로드 여부 문장은 찾지 못함. 문서화된 방법은 셸 export와 settings의 `env` 블록. "직접 못 보도록 돼 있다"는 Read 거부 규칙 설정 여부에 따라 다르며(공식 예시 `"deny": ["Read(./.env)"]`, https://code.claude.com/docs/en/settings.md), 기본 동작으로 확인하지 않았다)

**9. 글로벌은 비우고 프로젝트에서 세팅 (28:46~30:07)**
- "글로벌의 클로드 코드를 너무 촘촘하게 세팅하면 개발 작업에만 쓰는 클로드 코드로 세팅이 되겠죠." 다른 작업에서 그 값이 로드되면 "충돌나요."
- "이 프로젝트 레벨에서 세팅해주시는 걸 좀 더 추천을 드립니다." 나중엔 이 세팅만 따로 관리하고 프로젝트에 "그냥 갖다 부어 넣어주면" 된다. 글로벌은 "깨끗하게 텅텅 비어있고 그 프로젝트를 키면 그 정보가 쫙 불려와서".
- "저는 훅 수업이 제일 어려워요. 훅은 뭐 만들 수 있는 게 없어가지고."

### 강사 팁·주의사항
- 모호성 점수는 LLM이 낸 숫자라 크게 믿지 말고, 계획이 얼마나 찼는지 보는 참고로만 쓴다. 검증이 무한루프에 빠지면 적당할 때 끊는다.
- "항상 해야 할 일"을 지시로 맡기지 말 것 — 가끔만 지켜진다. 훅으로 강제한다.
- 훅에서 실행 여부를 LLM에게 판단시키지 말 것 — 할지 말지가 반복된다. 이름·폴더 규칙으로 결정론적으로.
- 프로젝트 훅을 처음부터 다 세팅하려 하지 말 것 — 코드가 쌓이고 규칙이 생긴 뒤 필요에 따라 만든다.
- 훅에 넣기 좋은 것: **내가 안 하거나 자꾸 까먹는 것**. 이미 쓴 지침은 중복으로 넣지 않게 분기한다.
- 글로벌 설정을 개발용으로 촘촘히 채우면 다른 작업과 충돌한다. 프로젝트 레벨에서 설정하고 그 세팅을 따로 관리해 이식한다.
- 공개 하네스는 무조건 써 보되 개인·교육 PC에서. 써 봐야 불편함을 안다. 강사는 무거워져서 손을 뗐다.
- goal은 계획이 완성된 뒤에, 계획 문서를 목표로 준다.
- 일정: 쉬었다가 4시 5분 재개, 작업 시간을 길게 준다(네트워크가 느려질까 걱정).

### 실제 프로젝트에 적용할 체크리스트 (- [ ] 행동 지침, 특정 프레임워크에 묶이지 않는 원칙 위주)
- [ ] "항상 지켜져야 하는 동작"(예: 코드 수정 후 테스트)을 목록으로 뽑고, 지시문이 아니라 훅·스크립트 같은 결정론적 장치로 강제한다.
- [ ] 코드 생성 완료는 파일 수정·삭제 이벤트와 확장자로 감지한다.
- [ ] 소스 파일과 테스트 파일의 이름·폴더 규칙을 정해 "이 파일을 고치면 이 테스트"를 코드만으로 고를 수 있게 한다. 실행 여부 판단에 LLM을 끼우지 않는다.
- [ ] 테스트가 무거워지지 않게 파일을 작게 유지한다.
- [ ] 프로젝트 훅은 코드베이스에 규칙이 생긴 뒤 필요가 확인되면 추가한다. 시작부터 예측으로 만들지 않는다.
- [ ] 처음부터 넣을 수 있는 훅(권한 체크, 프롬프트 앞뒤에 붙이는 지침)은 먼저 넣는다. 붙이는 지침은 "내가 자꾸 까먹는 것"만, 이미 대화에 있으면 중복 삽입하지 않는다.
- [ ] 팀 공유 설정(훅, MCP, 환경 변수)과 개인 설정을 파일로 분리하고, 개인 설정은 버전 관리에서 뺀다.
- [ ] 비용이 큰 프로젝트는 그 프로젝트 설정에서만 다른 모델·엔드포인트를 지정하고 전역 설정은 건드리지 않는다.
- [ ] 전역 설정은 최소로 비워 두고, 프로젝트별 설정 묶음을 따로 관리해 새 프로젝트에 복사해 쓴다.
- [ ] 계획(명세) 단계의 "완료 점수"는 참고로만 보고, 확인·검증 질문이 끝없이 돌면 사람이 끊는다.
- [ ] 계획이 끝나면 계획 문서를 목표로 지정해 실행을 맡긴다.
- [ ] 만든 하네스는 빈 폴더·빈 프로젝트에서 작은 개발 작업(예: 백엔드 API 하나)으로 처음부터 끝까지 돌려 검증한다.
- [ ] 개인화 버전을 설치했으면 원본 플러그인을 제거하고 검증한다.
- [ ] 공개 하네스는 격리된 환경에서 설치해 보고, 장단점을 판단한 뒤 필요한 부분만 가져온다.

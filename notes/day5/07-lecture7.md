## 5일차 7강 — 코딩 에이전트 프로젝트 안내와 평가 데이터셋·코드 모드 정리

> 출처: 「5일차 7강 다시보기(보정2)」(전사·분석, 44:24 분량), 「5일차 7강 장표(보정2)」(18장). 다시보기 분석 제목: "코딩 에이전트 프로젝트 안내와 평가 데이터셋·코드 모드 실습 정리"
> 구성: 앞 약 18분 다음 주 프로젝트 안내 → 18:00~36:45 쌓은 트레이스로 평가 데이터셋 만들기·코드 모드 사례·authoring 플러그인 → 마지막 약 8분 5일차 정리와 복습 과제(5시부터 이번 주 전체 복습)

### 핵심 요약 (3~5줄)
- 다음 주 프로젝트는 **딥 에이전트 라이브러리의 코딩 에이전트 "디코드"(deepagents code)** 를 기반으로 기능을 추가·개선하는 것. 기간은 **다음 주 목요일 ~ 일요일 자정**, 구글 폼에 **닉네임**으로, 실행에 필요한 **소스 코드만 ZIP**으로 제출, 월요일 채점. 다른 라이브러리·에이전트로 바꿔도 된다.
- 채점 4항목(각 10점, 40점): ① 파이썬 린트 ② **계획 → 리뷰 → 승인 후에만 코드 변경**(계획 없으면 실행 거부) ③ **메모리 기반 자가 개선 하네스**(강사가 가장 중요하다고 한 항목) ④ 랭퓨즈 같은 모니터링 연동. 출석 60점과 합쳐 수료 기준 80점, 1·4번만 해도 20점.
- 평가 데이터셋(시험지)은 **기능(예: RAG)으로 묶지 말고 개선하려는 "문제점"으로** 만든다. 예: "툴콜이 너무 잦다" → 코드 모드 적용 여부를 보는 **트래젝토리 평가** 데이터셋. input/expected_output은 자리일 뿐이고 JSON이라 키를 바꿔도 된다.
- 순정 Claude Code에서 코드 모드는 스킬·훅으로 시도해도 잘 안 됐다(PreToolUse 훅으로 되돌려 보내 2~3개 묶는 정도).
- 정리: 골드셋·평가·트레이스가 묶여 돈다. 개인 Claude Code에 랭퓨즈를 붙여 **일주일 이상** 쌓아 보라. 질문·데이터로 방향이 정해지면 **스킬은 LLM이 고르지 말고 강제 로드, LLM은 말만** 하게 하면 가장 빠르고 성능도 좋았다.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**1. 프로젝트 기반 코드: 디코드(deepagents code)**
- "최종 목적은 클로드 코드를 만드는 건데" Claude Code는 클로즈드 소스라 소스를 구할 수 없으니, 수업에서 계속 다뤄 온 딥 에이전트 기반으로 만든 코딩 에이전트를 쓴다.
- 위치: 딥 에이전트 라이브러리 밑 `libs` 폴더 밑 `code` 폴더. "딥 에이전트 코드", 흔히 "디코드"라고 부른다. (저장소 확인: `Day08/project_guide.md:3-11` — "Deepagents code(a.k.a `dcode`)", 원본 `https://github.com/langchain-ai/deepagents/tree/main/libs/code`, 소스 기준 2026.09.14, 분석 자료 `Day08/dcode-analysis`)
- 장점: 여러 모델 프로바이더를 연결할 수 있다. "Claude Code든 다른 코딩 에이전트든 결국 이런 프로그램 위에 LLM이 연결한 것."
- 밑바닥부터 만들지 않는다. 이미 만들어진 TUI를 다 활용하고 코드베이스는 여기서 출발한다.
- 강사 본인도 디코드가 마음에 안 든다: "코드가 15만 줄이 넘어요", "차라리 러스트 기반으로 다시 짜고 싶다". 그래서 차주 수요일에 **Claude가 이해하기 쉬운 문서를 붙인 코드베이스**를 다시 준다(그냥 보면 "클로드 토큰이 순식간에 녹아 버릴 것"). 그 외 처리는 하지 않고 실행 가능한 상태 그대로 준다.

**2. 채점 기준 네 가지 (각 10점)**
- **1번 파이썬 코드 규칙**: 디코드가 파이썬이라 파이썬 기준. "린트 한 방이면 해결" — 린트 규칙만 잘 지키면 된다. (저장소 확인: `Day08/project_guide.md:24-31` — 1-1 PEP8 스타일 [3], 1-2 명명 규칙·import 정리 [3], 1-3 docstring·주석 [4])
- **2번 계획 → 리뷰 → 승인 후 변경 (단계 고정)**: "모든 단계가 계획을 짜고 그 계획을 리뷰할 수 있도록 단계를 고정시켜 주셔야 됩니다." 일반 에이전트는 "헬로우" 치면 바로 답하지만, **개발 작업이면 캐치해서 강제로 계획 단계로 안내**하고, **계획이 없으면 실행을 아예 거부**해야 한다.
  - 개발 시작 전 요구사항·작업 범위·완료 조건이 정의되지 않으면 거부
  - 수정 대상·작업 순서·테스트 방법이 포함된 계획서
  - AI가 계획 리뷰 → 수정 의견이 있으면 사람이 AI 초안 계획서에 업데이트하는 절차
  - **승인된 후에만 코드 변경**, 계획서에 없는 작업 범위로 바뀌면 계획서 재검토
  - 범위를 벗어날 때 두 가지 경로 모두 인정: 사용자에게 "계획 재검토 필요" 알림 / AI가 "내가 잘못했다"고 인지하고 계획 안에서 수정
  - (저장소 확인: `Day08/project_guide.md:33-44` — 2-1 [2], 2-2 [3], 2-3 [3], 2-4 [2])
- **3번 메모리 기반 자가 개선 하네스** — "사실 세 번째가 제일 중요", "여기 한 30점 주고 싶었는데". 디코드가 아니어도 Claude Code를 잘 쓰는 관점에서 꼭 도전해 볼 주제라 넣었다.
  - 사용 경험을 메모리로 저장, 세션이 끝나도 유지("파일로 남기라는 소리")
  - 새 세션·새 작업에서 관련 메모리를 검색해 실제로 활용하는가
  - 루프에서 나온 성공·실패로 시스템 프롬프트·스킬·메모리 개선안(=계획)을 생성하는가
  - 개선 후 효과 측정 + **기존 기능 정상 동작 검증**("개선을 했는데 기존 동작이 깨지면 안 되죠")
  - 개선안을 선택해 작업에 반영하는가
  - (저장소 확인: `Day08/project_guide.md:46-57` — 3-1 [2], 3-2 [3], 3-3 [3], 3-4 [2])
- **4번 모니터링**: 오늘 한 대로 랭퓨즈 같은 모니터링 도구에 연결하는가. "랭퓨즈에 연결하면 1,2,3,4번이 자동으로 해결되는 그런 계획으로 구성해 뒀습니다." (저장소 확인: `Day08/project_guide.md:59-70` — 4-1 전체 실행 흐름 기록 [3], 4-2 LLM 호출·도구·Memory·자기개선 결과와 오류 [3], 4-3 실행 시간·호출 횟수·재시도 횟수 [2], 4-4 작업별 로그·Trace로 실패 지점 확인 [2])
- 강사도 이 규정대로 검사하는 **채점 에이전트**를 만들어 두었다: 예제를 넣고 물어봐서 안 되면 바로 차감.

**3. 코딩 업무가 아니어도 해 볼 이유 — 저수준 제어**
- "계획자고 기억하는 건 클로드에서도 똑같이 해야 됩니다." 개발 담당이 아니면 1번은 무시해도 되고, 2·3번을 "내가 이걸 Claude Code에 적용한다면"이라는 생각으로 해 보라(4번은 연결하면 끝).
- Claude Code도 내부적으로는 이런 프로그램(타입스크립트)이다. 코드 속에서 직접 구현하면 힌트를 많이 얻는다: 계획 구체화·리뷰를 **무조건 서브에이전트로 강제로** 돌릴 수 있고, 시스템 프롬프트가 하나도 없고 도구도 비울 수 있어 **컨텍스트를 예민하게 컨트롤** 가능 → "로우 레벨 제어가 늘어나는 거죠". 모니터링에도 필요한 정보를 추가로 보낼 수 있다.
- Claude Code는 서비스라 제어할 부분이 많지 않다. 로우 레벨 제어를 해 보면 "클로드도 이렇게 할 수 있지 않을까?" 하는 아이디어를 역으로 얻는다.

**4. 평가 데이터셋 = 시험지, "문제점"으로 만든다**
- "이걸 만들어야… 평가 돌리는 건 일도 아니에요." 개선하려는 문제점을 보기 위해 시험지(정답지)를 만드는 것.
- **기능으로 접근하면 어렵다**: 오늘은 RAG 에이전트를 개발했지만 자리에 가면 다른 기능을 개발한다. "RAG 데이터셋"처럼 특정해 두면 다시 쓰기 어렵다 → **일반적인 개발 작업**이라고 생각하고 접근한다.

**5. 코드 모드와 트래젝토리 평가 사례**
- 강사가 Claude Code에서 "제일 마음에 안 드는 것": LLM → 툴 → LLM → 툴…이 매번 왕복("LLM 이거 3초 호출하자고 이거 왔다갔다 해야 되나"). LLM 한 번에 툴툴툴툴 하는 **코드 모드**(코드를 한 번에 주고 툴을 쭉 실행해 결과를 받는 형태)를 적용해 보고 싶다.
- 이를 확인할 데이터셋(수강생 답을 "완전히 제대로 된 접근"이라고 평가): 툴콜링 리스트를 수집해 **input에는 툴콜 리스트**, **expected_output에는 기대하는 툴콜 명령의 형태**. 지금까지의 "툴콜 툴콜 툴콜…" 단일 툴콜 나열을 잘못된 것으로 판단.
- 하지만 판단은 **유동적**이어야 한다: 진짜로 콜 하나만 필요한 경우도 있다. 언제는 여러 번, 언제는 단일 툴콜을 길게 구성할지 — "이 데이터셋을 만드는 게 제일 어려워요".
- 케이스는 이미 많이 쌓아 놨다("그래서 이 난리를 피운 거예요"): Claude에게 "트레이스 다 분석해서 한 번에 실행할 수 있는 케이스들만 발라내라"고 시켜 골라 데이터셋으로 만들 수 있다. 다만 **기존 기록에만 의존하니 좋은 접근은 아니다**. 그래도 이런 테스트는 만들기 어려운 경우가 더 많다.
- 이것은 결과가 아니라 구조(흐름)를 평가하는 **트래젝토리 평가**. 작업이 명확할수록 "이 툴 다음엔 저 툴" 1·2·3·4 순서가 픽스되지만, 아니면 툴을 어떻게 구성·어떤 순서로 실행할지 고민하게 된다.

**6. 데이터셋 틀(QnA)에 얽매이지 않기**
- 데이터셋이 input / expected_output 형태로 되어 있지만 "너무 얽매이시면 안 됩니다". 그냥 자리가 input, 자리가 expected_output일 뿐이고 안은 JSON이라 키·변수 이름을 바꿔도 된다. 이벨루에이터에는 변수로 들어온다(input 자리에 JSON 객체, expected_output도 JSON `answer: …`였음).
- (저장소 확인: `Day05_new/eval_lab/replay.py:288-296` — 수업 저장소의 Langfuse Dataset 항목도 QnA가 아니라 `input={"events": [...]}`(궤적), `expected_output={"fatal", "first_violation_index", "normal"}` 형태로 넣는다. QnA 형태의 예는 `Day05/gold_agent.py:139`의 `input={"question": question}`)

**7. 트레이스를 쌓는 목적**
- 랭퓨즈에 트레이스를 쌓아 두면 그 속에서 원하는 데이터를 추출하거나 통계 분석을 할 수 있다. 코드 모드처럼 쓸 수 있다면 "되게 많은 모델 토큰을 절약".

**8. 순정 Claude Code에서의 코드 모드 시도 (경험담)**
- "순정의 클로드 코드로는 꽤 어려워요" — 터미널에서 Claude Code를 실행하는 방식으로는 잘 적용이 안 된다. 스킬도 만들고 훅도 넣어 봤지만 안 됨.
- 툴 유즈 훅 두 개(장표: PreToolUse/PostToolUse로 보임) 중 **툴 실행 전 단계에서 가로채 "이거 아닌 거 같은데" 하고 돌려보내는 것**이 가장 효과적이었지만, 한두 개(두세 개) 뭉쳐 보내는 정도에 그쳤다. 원한 건 긴 툴콜링을 한 번에 짜는 것.
- 최근 모델은 애초에 어느 정도 길게 짜 준다: 특정 폴더로 이동해 루프로 스킬을 읽고 주요 내용을 추출해 원하는 데이터만 출력하는 간단한 배시 프로그램을 짜서 돌림. "이 정도는 짜는구나" 했지만 더 큰 프로그램을 원함. 결론적 목적: "제발 호출 좀 많이 하지 마".

**9. authoring 플러그인 (Claude Code 공식 빌트인)**
- 화면에 뜬 제안(디스미스함)을 계기로 소개. 작업 내용을 보고 "이런 작업에서 이런 거 좀 신경 써야 될 것 같은데"를 가이드해 주는 **공식 플러그인** — 사용자가 Claude에 지시한 내용을 까먹지 않도록 가이드.
- `authoring 플러그인`으로 검색하면 설치할지 물어본다. 작업에 따라 뜰 때도 있고 안 뜰 때도 있다. 빌트인이라 CLI뿐 아니라 **Claude 앱에서도** 똑같이 뜬다. "공식 플러그인 중에 괜찮은 게 정말 많다."

**10. 5일차 정리: 골드셋·평가·트레이스 루프**
- "정말 애매한 주제인 평가와 운영", "두루뭉실한 내용이 많아요". 골드 데이터셋을 어떻게 만드는가, 트레이스를 어떻게 남기는가.
- 평가는 골드 데이터셋 기반으로 할 수도 있고, 트레이스에 바로바로 기록을 남길 수도 있다. 예: Jev로 실행한 에이전트 챗 한 줄에 "이거 문서 활용 안 한 거 같다"를 남긴 것도 **작은 eval의 한 종류**.
- 모든 기록을 트레이스에 남기는 이유: 다음에 또 써야 하니까 → 오퍼레이팅할 때 계속 사용. 골드셋·평가·트레이스가 묶여 돌아가는 구조.
- 히스토리가 JSONL로만 쌓여 있으면 잘 안 보게 된다. 화면으로 보면 "내가 왜 이렇게 지시했을까"가 보여 **개선 욕구에 불을 붙여 주는 옵저버빌리티**.

**11. 스킬 강제 로드와 "LLM은 말만"**
- RAG 실습에서 데이터 가져오기까지는 잘 했는데 시간이 부족해 스킬을 못 붙였다. **3번 과제는 스킬 로드**로 준비했으나 못 냈다 → 복습 때 해 볼 것. 앞에서 데이터를 잘 필터링해 전달하면, 그 데이터를 잘 활용하는 방법이 적힌 스킬을 로드해 와야 한다. (저장소 확인: `Day05_new/task.md:2-11` — 과제는 1번(업로드 파일 처리)·2번(Jev 또는 싼 LLM으로 RAG 프로세스 개선, `Day05_01.png` 참고)까지만 있고 3번은 없다)
- "스킬을 LLM이 고를 필요가 있을까요?" LLM은 질문·데이터를 보고 "이 스킬 필요하겠네" → 읽어 와 확인 → 첨부해 실행한다. 그런데 사용자의 질문과 데이터로 **분야(방향)가 이미 정해졌다면** 강제로 로드시켜 주면 끝. 또는 스킬 선택을 (스킬 10개 중 이 데이터로 답하려면 어떤 게 좋은지) 일반 모델에 맡겨도 된다.
- "진짜 순수하게 LLM은 말만 하는 거예요." 강사의 비유: LLM은 임원 — 밑에서 다 움직여 발표 자료를 켜 드리면 보고만 딱 하고 옴. "미리 다 준비된 대본만 딱 읽고 말만 해".
- 효과: "일단 가장 성능이 좋았어요", 속도가 "말도 안 돼". 앞 단계가 느려서 문제였지 말하는 건 스트리밍이라 말하기가 빨리 시작된다 → **말하는 쪽은 머리 좋은(최고 성능) 모델을 써도 된다**, 지금까지 속도 때문에 모델에 타협했지만 타협할 필요가 없었다. 다음 주 디코드로 시도해 볼 수 있을 것, 기술적으로 어렵지 않다.

### 강사 팁·주의사항
- 프로젝트는 떨어뜨리려는 것이 아니다: "웬만하면 다 통갑니다", 채점 에이전트도 빡빡하게 해 놓지 않았다. 유연하게 사고해도 된다. 그래도 2·3번이 핵심이고, 잘 나오면 바로 업무에 적용할 수 있는 수준의 태스크.
- 1번(린트)과 4번(랭퓨즈 연결)은 "거저먹는 것" — 이것만으로 20점.
- 라이브러리는 **잘 아는 걸로** 하라. 디코드는 15만 줄이 넘어 그냥 읽히면 Claude 토큰이 순식간에 녹는다 → 수요일에 문서 붙인 버전을 받을 것.
- 개발 작업은 강제로 계획 단계로 보내고, 계획이 없으면 실행을 거부하라 — 채점 항목이다.
- 개선 후에는 효과뿐 아니라 **기존 기능이 깨지지 않았는지** 검증하라.
- 평가 데이터셋은 기능별로 특정하지 말고 문제점(개선 대상) 중심으로. input/expected_output 틀과 QnA 형태에 얽매이지 말 것.
- 쌓인 트레이스로만 케이스를 고르는 건 좋은 접근은 아니다(기존 기록 의존). 그래도 트래젝토리 테스트는 만들기 어려운 경우가 많아 현실적인 출발점.
- 단일 툴콜이 맞는 경우도 있으니 "여러 번 호출 = 나쁨"으로 고정 판정하지 말 것.
- 순정 Claude Code에서 코드 모드를 기대하지 말 것(스킬·훅으로도 2~3개 묶는 수준).
- 랭퓨즈 트레이스 분석은 오래 걸린다 — 네트워크가 느린 환경에서는 돌리지 말 것.
- 개인 Claude Code에도 랭퓨즈를 붙이되 "하루이틀 쌓아가지고는 의미 없고" 일주일 이상 쌓아 패턴 분석 → 내 작업 개선까지.
- 공식 플러그인(authoring 등)을 둘러볼 것.

### 실제 프로젝트에 적용할 체크리스트
- [ ] 에이전트가 개발(변경) 작업 요청을 감지하면 강제로 계획 단계로 보내고, 계획이 없으면 실행을 거부하게 만든다.
- [ ] 작업 시작 전 요구사항·작업 범위·완료 조건이 정의되지 않으면 진행하지 않는다.
- [ ] 계획서에 수정 대상·작업 순서·테스트 방법을 반드시 포함한다.
- [ ] AI 계획 리뷰 → 사람 수정 반영 → 승인 후에만 코드 변경, 범위가 바뀌면 계획 재검토로 되돌린다(사용자 알림 또는 에이전트 자체 수정).
- [ ] 계획·리뷰 단계는 가능하면 별도 서브에이전트로 분리해 컨텍스트(시스템 프롬프트·도구)를 최소로 통제한다.
- [ ] 작업 경험을 파일 메모리로 저장해 세션이 끝나도 유지하고, 새 작업에서 관련 메모리를 검색해 실제로 쓰는지 확인한다.
- [ ] 성공·실패 기록으로 시스템 프롬프트·스킬·메모리 개선안을 생성하고, 효과 측정과 기존 기능 회귀 검증을 통과한 것만 반영한다.
- [ ] 모든 실행을 트레이스(모니터링 도구)에 남긴다 — 이후 데이터 추출·통계 분석·평가 케이스 발굴에 재사용한다.
- [ ] 평가 데이터셋은 특정 기능이 아니라 개선하려는 문제점(예: 툴 호출 과다) 기준으로 만든다.
- [ ] 흐름이 문제면 결과가 아닌 궤적(툴 호출 구성·순서)을 평가하고, 단일 호출이 정답인 경우도 데이터셋에 포함한다.
- [ ] 데이터셋 항목의 input/expected_output 키는 평가 목적에 맞게 자유롭게 설계한다(QnA 형태 고정 금지).
- [ ] 개인 작업 도구에도 트레이스 관찰을 붙여 일주일 이상 쌓은 뒤 패턴을 분석하고 작업 방식을 개선한다.
- [ ] 질문·데이터로 필요한 스킬이 정해지는 경로는 LLM 선택에 맡기지 말고 코드로 강제 로드한다.
- [ ] 데이터 처리·필터링은 빠른 코드/작은 모델이 끝내고, 최종 LLM은 준비된 내용을 말하게만(스트리밍) 해서 응답 모델 품질을 타협하지 않는다.

## 5일차 1강 — 에이전트 평가: 시험지·정답지·과정 (골든 데이터셋, 트레이스, 궤적 평가와 정답지 만들기의 현실)

### 핵심 요약 (3~5줄)
- 에이전트 평가는 "정답은 없고 모두의 경험만 공유되는" 케이스 스터디다. 키워드는 **골든 데이터셋·평가·트레이스·트레이젝토리(궤적)** 네 가지이고, 사람이 시험 보는 과정(시험지·정답지 → 채점 → 틀린 문제와 풀이 과정 보고 고치기)에 빗대면 쉽다.
- **LLM-as-a-Judge의 가장 큰 문제는 일관되지 않다는 것** — 같은 모델·설정인데 오전/오후에 돌린 점수가 10점씩 차이 나면 믿을 수 없다. 해결 방법은 뒤에서 다루겠다고 미뤘다.
- 최종 답이 같아도 **과정(궤적)이 다르면 같은 성공이 아니다**(계정 잠금 해제 예). 궤적 평가는 위험한 순서를 잡는 데도, 작은 작업에 큰 모델을 쓰는 낭비를 찾는 비용 최적화에도 쓰인다.
- 정답지는 LLM에만 맡기면 50~60점짜리 일반 문제지가 된다. **담당자 인터뷰**에서 출발해 LLM 초안 → 담당자 피드백을 여러 번 오가며 만들고, 문서에 없는 예외의 정답은 담당자가 채운다.
- 시험지가 과거에 머물지 않도록 **운영 기록을 골드 데이터로 승격**(반복·재현 가능·정답 정의 가능)하고, 정답지는 Q&A 3컬럼이 아닌 **시나리오형**(거칠 도구 단계·금지 행동·순서 규칙)으로 쓰며, **개발용과 운영용 데이터셋을 분리**해 오버피팅을 피한다.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**0. 도입 읽을거리 (본 주제 전 약 12분)**
- **자동화의 역설**(1983년 글, 약 40년 전): AI로 자동화·효율화(요즘 말로 AX)를 하면 ① 인간은 어려운 일만 하게 되고 ② 쉬운 일을 차근차근 밟으며 쌓던 경험이 줄어 어려운 일을 할 사람이 줄어드는데, 갑자기 어려운 일을 시키니 다시 비효율로 돌아간다. 강사 고민: "모든 것을 진짜 자동화하는 게 맞을까", 신입 채용을 다 중단하면 경력자는 어디서 나오나. 페이지가 많아 요약본으로 읽었다고 함.
- **LangChain CEO(Harrison Chase)의 컨텍스트 엔지니어링 글**(2026년 말 기준 변화): 긴 스레드 요약, 내용이 많이 리턴되는 툴 결과를 컨텍스트에 바로 넣지 않고 **파일로 오프로딩**, 스킬의 점진적 읽기 설계를 더 촘촘하게, 툴이 많을 때 **툴을 찾는 툴** 설계, 서브 에이전트는 **컨텍스트 격리** 관점. "이미 배우신 거랑 다르지 않다 … 모두가 다르지 않은 방향을 보고 있다." 시간 날 때 읽어 보라고 추천.
- **FDE 로드맵**(깃허브 저장소): AI·ML 기초 → LLM 동작 → 모델 선택 → 프롬프트·컨텍스트 엔지니어링 → RAG → 에이전트 → 코딩 에이전트 → 평가·모니터링 → 세이프티·시큐리티 → 비용·레이턴시 → (이후 "좀 이상했다") 파인튜닝, 인프라·시스템 디자인, 유즈케이스, 인터뷰 준비. 강사 평: "죄다 AI 엔지니어링만 싹 다 써놓은 게 아닌가." 세부는 안 봤고 링크는 나중에 전달하겠다고 함.
- **Claude 쪽의 "서브 에이전트를 메인에 합치자" 글**: 모델이 좋아지면 굳이 쪼갤 필요 없는 서브가 생긴다 → 서브 작업을 메인에 병합해 평가하고, 서브만큼 잘하면 서브를 버린다. 멀티 에이전트 오케스트레이터 + 정해진 파이프라인 대신 **싱글 에이전트 루프 안에서 단계를 툴 콜로 호출하고 최종 출력만 가드레일**하자는 내용. 강사: "쪼개라/합치라"는 거의 연 단위로 반복된다(연초엔 쪼개라고 했음) → 현혹되지 말고 "해보고 얘기하자."

**1. 평가의 네 가지 키워드 — 사람의 시험에 비유**
- **골든 데이터셋(골드셋)**: 에이전트를 평가할 평가 문제와 정답지. "시험을 친다."
- **평가**: 몇 점 맞았는지 매기고, 틀린 문제를 보고 어떻게 개선해야 맞출지 접근.
- **트레이스**: 실행 기록들을 쌓아 놓은 것.
- **트레이젝토리(궤적, 여정)**: 모델이 툴 콜링을 요청 → 툴 호출 → 결과 전달 … 작업 완료까지 쌓인 흐름. 이것까지 평가한다.
- "시험지를 만들고 시험을 풀게 한 다음에 점수를 매기고 … 문제풀이 과정이 적절했는지를 보고 나서 너 이렇게 고치자." 단, "개념만 쉬운 거죠."
- 강조 이유: "정답을 찾겠다라고 접근하면 여기는 굉장히 힘듭니다. 하지만 방법론이 어느 정도 존재하고, 요즘 많이 개선됐다."
- (저장소 확인: 이론 PDF 2쪽이 같은 네 축을 Golden Dataset·Trace 해석·Evaluator·개선 검증으로 정리 — `Day05/Day5_이론자료.pdf:p.2`)

**2. LLM-as-a-Judge의 비일관성**
- 관건은 "평가를 누가 할 거냐." LLM이 평가자로 동작하는 LLM-as-a-Judge의 가장 큰 문제는 **일관되지 않다**는 것.
- 사람도 100% 일관되진 않지만, LLM은 확률의 기계라 "유달리 테스트만 돌리면 확률이 들쭉날쭉." 예: 같은 모델·세팅, 돌린 시간만 오전/오후로 다른데 점수가 10점씩 차이 나면 못 믿는다.
- "이건 어느 누구도 풀지 못했습니다 … OpenAI, Anthropic 그들도 풀지 못했어요." 다만 "요즘은 좀 많이 해결했는데 그 얘기도 뒤에 가서" — 이 강의에서는 해결 방법을 다루지 않았다.

**3. 궤적 평가가 필요한 이유 — 돈과 안전**
- **비용**: "모든 작업을 Opus로 할 수는 없습니다." 박사급 인재에게 청소를 시키는 꼴. 궤적을 보며 "이 과정에서 이게 굳이 필요했나? 좋은 모델을 써야 되나? 좋은 모델은 잘하지만 느린데?"를 판단해 최적화한다.
- **계정 잠금 해제 예(같은 최종 답 "해제했습니다", 한쪽만 괜찮음)**:
  - 실패 궤적: 해제 요청이 오면 바로 unlock 시도 → 그 다음 계정이 맞았나 확인 → 접근 점검하니 거절 → 그래도 "해제했습니다"(앞에서 시도했으니).
  - 정상 궤적: 계정 정보 확인 → 이 사람이 접근 가능한/현재 열린 상태인지 확인 → 언락 처리 → 상태 재확인해 언락이면 "계정 락이 해제됐습니다".
  - (저장소 확인: 이론 PDF의 TRACE A "get_account → check_access → allowed → unlock_account → ok → read_state → unlocked" / TRACE B "unlock_account → attempt → get_account → check_access → denied → '해제했습니다'" — `Day05/Day5_이론자료.pdf:p.4`)
- "프롬프트에 이거 써놓으면 안 할 걸?" → "충분히 합니다. 중구난방으로 막 호출합니다." 앞에 컨텍스트가 조금만 쌓여도 락을 먼저 풀고 엉뚱한 작업을 한다.
- 그래서 궤적을 정확히 평가해 과정이 충실했는지 확인하고, **그 과정을 툴이나 스킬에 다시 정리**해서 엉뚱하게 동작하지 못하게 해야 한다.

**4. 정답지(시험지) 만들기 — 담당자 인터뷰가 출발점**
- 모두 똑같이 출발하는 방법: LLM에 문서를 넣고 만들어 달라 하기(여러 LLM 돌려 괜찮은 것 추리기).
- 문제: LLM은 문서를 "굉장히 일반적으로" 읽어서 문제도 답도 일반적 → "한 50점, 60점짜리 문제지"로 평가하는 상황이 많다.
- "가장 좋은 출발점은 문서도 문서지만 저는 **담당자 인터뷰** 같아요." 담당자가 생각하는 에이전트의 키포인트에 맞게 문서를 읽어야 한다. 이 관점을 잡는 데 시간을 많이 썼다고 함.
- 담당자는 문제를 직접 만들어 주지 않는다 → 그제서야 LLM으로 **초안** → 담당자는 **피드백은 준다** → 문제·답지를 개선 → "몇 번 오가야" 골드 데이터셋이 만들어진다.
- 그다음(프로그램 실행 → 평가 기록을 **Observability 툴**에 기록 → 활용)은 실행일 뿐, "이 앞에가 진짜 어려운 것 같아요."
- 현실: "네 업무에서 중요한 게 뭐야" → "나도 모르겠는데, 얘기해 봐야 알겠는데."
- (저장소 확인: 이론 PDF는 확보 경로를 "인터뷰는 기준을, 문서는 범위를, 운영 Trace는 빠진 실패를" 알려 준다고 정리 — `Day05/Day5_이론자료.pdf:p.7`; 실습 쪽 같은 표 `Day05_new/use_cc/concepts/m2.md:167-171`)

**5. 도메인이 많은 사내 챗봇(업무 효율화 챗봇) 평가 — 실제 케이스**
- 질문: 사내 문서를 읽고 답하는 단순 RAG 챗봇, 문서 도메인이 여러 개면 어떻게 평가하나? 수강생 답(분야별로 담당 부서가 평가)도 좋은 방법이지만 "모든 분야가 다 안 해주려고" 하고 모든 부서를 만나고 다닐 수 없다.
- 강사의 방법: **문서를 잘 인용하는지**로 대부분 데이터셋을 만들었다. 분야 문서 내용을 그대로 읽어 그대로 얘기하는 게 첫 번째, 도메인 지식을 넣는 건 두 번째.
  - 파싱이 깨진 문서(테이블 깨짐, 한글 깨짐)도 "그건 앞단(파싱)의 잘못이니 모르겠고 네가 읽은 그대로를 얘기해"라는 평가셋을 많이 만들었다.
  - 이유: 읽은 걸 그대로 얘기할 수 있다면 지식을 섞는 건 그 다음 작업. 당시엔 스킬이 없어서, 인사 문서가 들어오면 **인사에 맞춘 시스템 프롬프트로 치환**하는 방식으로 구현.
- 실패담: IT 부서가 담당자를 다 데려오겠다 했지만 안 옴. 와도 정보보호 담당이 와서 "그 문서 LLM이 읽는 게 맞아요? 유출되는 거 아니에요?"만 얘기하다 끝남 → "평가지를 만드는 건 여전히 LLM이 못하는 일이구나."
- 다른 시도: LLM으로 만든 초안을 부서별로 뿌리고, 부서별 **간이 챗봇**(UI 못생겨도 됨, 채팅만 오가게)을 담당자에게 줘서 "채팅 좀 몇 번 해 주실래요?" → 담당자가 불만("이따위로 얘기를 하냐")까지 쌓아 줌 → 그걸 보고 잘못된 점 파악·데이터 취합. 메일은 답장이 안 오니까.
- 요즘 방식: 테스트를 잘 안 돌리는 편. 조각화된 지식을 **스킬로 빼고**, 껍데기를 한 시간 만에 빨리 만들어 주고 담당자가 대화 기록만 쌓게 함 → 뒤에서 스킬로 만든다. 담당자의 감에 많이 의존하지만 자기 입맛에 맞게 답해서 좋아한다. 요즘은 LLM이 틀린다는 인식이 공감돼 100점을 요구하지 않는다.
- 그래도 "완전히 견고한 에이전트를 만들기 위해서는 이 데이터셋이라는 걸 꼭 만들어야 돼요." 현업 인터뷰와 업무 문서 모두 너무 중요.

**6. 운영 중 데이터셋 갱신 — 시험지는 과거, 운영은 최신**
- 개발 후 데이터셋이 안 변하는데 기능은 계속 추가 → 간격이 벌어진다. **운영에 쌓인 기록을 다시 데이터셋에 포함**시켜야 한다.
- 반복해서 실패하는 작업을 캐치해 개선(프롬프트·스킬·툴·기능 수정)하면, 그 업데이트된 것도 계속 평가.

**7. 설계·기획 단계에서 확답받을 질문**
- "뭐가 끝나야 너는 **완료**라고 판단하니?"
- "이건 **누구의 요청**을 처리하고, 언제는 이런 프로세스를 타면 안 되니?"
- "문서에 그 정보가 없거나 **정보가 부족**하면 이 시스템은 어떻게 대답해야 되니?" — 디폴트 세팅에 너무 중요.
- "**툴 콜링이 실패**했을 때 어디까지 허용할까요? 아예 시스템 오류로 낼까요?"
- 최종적으로 어떤 과정이 있으면 성공인지, 채팅 답변만 하면 되는지, 답변 길이는 어느 정도여야 오케이인지. → "꼭 확답을 받아놔야 진행했다."
- 문서는 참고하지만 정답을 만들어 주지 않는다. **문서에 없는 예외는 정답을 LLM으로 만들지 말고 담당자가 꼭 채워 넣기** — 여러 문서를 조합해야 하는 답이면 "제가 아니라 당신이 해주십시오."
- (저장소 확인: 이론 PDF의 인터뷰 질문표가 같은 다섯 질문 — 완료/요청 주체/처리 금지 시점/정보 부족/도구 실패 — 을 `expected.final_state`, identity/target constraint, `forbidden_actions`, expected behavior, recovery constraints로 바꾼다. 매 질문마다 "어떤 과정이 있으면 성공이라고 판정할 수 있나요?"를 확인 — `Day05/Day5_이론자료.pdf:p.8`; "문서에 없는 예외는 정답을 LLM으로 만들어 넣지 말고, 현업 확인 대상으로 남깁니다" — `Day05/Day5_이론자료.pdf:p.9`)

**8. 트레이스 → 골드 데이터 승격**
- 대표적으로 성공한 표본과 실패한 표본을 충분히 나눠 둔다. (저장소 확인: `Day05/Day5_이론자료.pdf:p.10` "운영 Trace는 대표 표본과 실패 표본을 나눠 모읍니다")
- 그중 일부를 골드 데이터로 승격. 기준은 여럿이지만 "**그게 반복해서 나오는 문제인가**가 사실 가장 중요했던 것 같아요." 그리고 재현 가능한지, 정답을 정의했는지.
- 시스템이 낸 출력과 사람이 원래 기대한 값을 써 두고 그걸로 평가.
- (저장소 확인: 승격 전 확인 항목 — 재현 가능한가/안전 보관/정답 재정의/중복·충돌/추가 후 다시 잡히는가 — `Day05/Day5_이론자료.pdf:p.11`. 강의는 이 중 "반복성·재현성·정답 정의"만 말로 짚었다. 전사 "제한 가능한지"는 문맥상 "재현 가능한지"로 보이며 PDF의 "재현 가능한가?"와 일치)

**9. 시나리오형 정답지와 순서 규칙**
- 흔한 골드 데이터셋 예제는 Q&A — 질문 / AI 답변(시스템 아웃풋) / 사람이 기대한 답변(익스펙티드 아웃풋) **딱 세 컬럼**.
- 시스템을 만든 사람 입장에서는 그 답에 도달하려면 어떤 도구를 호출해야 하는지 프로세스가 있으니 **시나리오를 같이 꼭 써야** 한다. 예: RAG 챗봇이면 의도 분류 → 데이터 소스 검색 → 데이터 필터링 → 답변. 단계를 써 두면 평가가 쉬워진다.
- 정답만 넣는 게 아니라 **하지 말아야 할 행동**도 데이터셋에 많이 넣는다.
- **병렬(순서 무관) vs 순차(순서 필수)** 구분: `get account`와 `search policy`는 누가 먼저 해도 상관없다(데이터가 동시에 필요). 어떤 프로세스는 무조건 순차. 도구를 만들고 실행시킬 때도 이를 고려.
- (저장소 확인: "Golden Dataset은 Q&A 표가 아니라 Scenario입니다" — input / expected_output / metadata 분리 `Day05/Day5_이론자료.pdf:p.12`; 거절·질문 사례도 넣기 `Day05/Day5_이론자료.pdf:p.14`; "독립적인 조회 순서는 달라도, 쓰기 전에 필요한 조건은 같아야 합니다"(get_account·search_policy는 순서 자유, 같은 대상 승인 완료가 모든 쓰기보다 먼저) `Day05/Day5_이론자료.pdf:p.16`)
- 강의 중 "이거는 빼고", "이거는 아니고"라며 일부 슬라이드는 건너뛰었다.

**10. 개발용·운영용 데이터셋 분리 (오버피팅)**
- 개발용으로 만든 데이터셋과 실제 운영에 쓸 데이터셋은 조금 다른 게 좋다. 개발하는 동안 거기에 오버피팅되는 걸 피할 길이 없다 → 비슷한 다른 데이터셋을 하나 더 구성.
- 현실적으로 어렵다: 만들 시간이 없고, 개발 데이터에 점수를 다 맞춰 놨는데 최종 납품 때 세트가 바뀌면 점수가 뚝 떨어진다.
- 경험담: 고객사 담당자가 자체 데이터셋을 만들어 평가를 돌렸더니 점수 차이가 벌어짐("크게 한번 데인 적"). 기록이 남아 있어서 찾아냈다. "고객사 담당자도 꼭 따로 돌린다" — 열정적인 담당자는 직접 돌리고, 아닌 분은 보고만 받는다.
- (저장소 확인: 같은 사건에서 파생한 쌍은 `family_id`로 묶어 dev / holdout에 흩어 넣지 않는다 — `Day05/Day5_이론자료.pdf:p.15`. 강의는 dev/holdout 용어 대신 "개발용/운영용"이라고 말함)

### 강사 팁·주의사항
- "정답은 없고 모두의 경험만이 공유되는 주제" — 정답을 찾으려 들지 말고 케이스 스터디로 받아들일 것. "그냥 다 부딪쳐야 돼요."
- LLM 평가자 점수는 실행 시점에 따라 흔들릴 수 있다 — 점수 하나를 그대로 믿지 말 것.
- 프롬프트에 순서를 써 둬도 컨텍스트가 쌓이면 어긴다 → 궤적 평가 결과를 **툴·스킬 구조**에 반영해 엉뚱한 호출을 막을 것.
- 정답지를 LLM에게만 맡기면 일반적인 50~60점짜리 문제지가 된다. 담당자는 정답은 안 줘도 피드백은 준다 — 초안을 들고 가라.
- 담당자 미팅에 정보보호 담당이 와서 유출 얘기만 하다 끝날 수 있다. 메일은 답이 안 온다 → 간이 챗봇을 직접 써 보게 해 대화 기록을 받는 우회로.
- 문서에 없는 예외·여러 문서 조합 답은 담당자가 채우게 할 것("제가 아니라 당신이 해주십시오").
- 업계 글("Anthropic이 합치라던데?")에 현혹되지 말고 직접 해 보고 평가로 판단.
- 개발 데이터셋에만 점수를 맞추면 고객사의 별도 데이터셋에서 점수가 떨어진다. 기록(트레이스)을 남겨 두면 원인을 찾을 수 있다.

### 실제 프로젝트에 적용할 체크리스트 (- [ ] 행동 지침 형태, 특정 프레임워크에 묶이지 않는 원칙 위주)
- [ ] 평가를 시작하기 전에 골든 데이터셋(시험지·정답지), 평가 방식, 트레이스 저장, 궤적 검토 네 가지가 각각 준비됐는지 확인한다.
- [ ] LLM 평가자를 쓸 때는 같은 조건에서 여러 번 돌려 점수 흔들림을 먼저 확인하고, 한 번의 점수로 결론 내리지 않는다.
- [ ] 최종 답만이 아니라 궤적(도구 호출 순서·대상·결과)을 평가 항목에 넣는다. 특히 쓰기 작업 전에 확인·권한 단계가 있었는지 본다.
- [ ] 궤적에서 "큰 모델이 굳이 필요 없었던 단계"를 찾아 비용·속도 최적화 후보로 기록한다.
- [ ] 궤적 평가에서 반복되는 순서 위반은 프롬프트 문구가 아니라 도구·스킬 구조로 막는다.
- [ ] 정답지 작업은 담당자 인터뷰로 시작해 에이전트의 핵심 포인트를 먼저 정하고, LLM 초안 → 담당자 피드백을 여러 번 반복한다.
- [ ] 설계 단계에서 완료 기준, 요청 주체, 처리하면 안 되는 경우, 정보 부족 시 응답, 도구 실패 시 허용 범위를 담당자에게 확답받아 기록한다.
- [ ] 문서에 없는 예외나 여러 문서를 조합해야 하는 정답은 LLM이 아니라 담당자가 채우게 한다.
- [ ] 도메인이 많은 문서 기반 챗봇은 "문서를 그대로 정확히 인용하는가"부터 평가하고, 도메인 지식 결합은 다음 단계로 둔다.
- [ ] 담당자가 정답지를 안 줄 때는 간이 챗봇을 배포해 대화 기록·불만을 쌓게 하고 그 기록을 정답지 재료로 쓴다.
- [ ] 정답지는 Q&A 3컬럼이 아니라 시나리오로 쓴다: 거쳐야 할 도구 단계, 하지 말아야 할 행동, 순서 무관(병렬)과 순서 필수(순차) 구분을 함께 적는다.
- [ ] 운영 트레이스에서 성공·실패 표본을 나눠 모으고, 반복해서 나오며 재현 가능하고 정답을 정의할 수 있는 것만 골든 데이터로 승격한다.
- [ ] 기능을 추가·수정할 때마다 운영 기록을 데이터셋에 반영해 시험지와 운영의 간격을 줄이고, 수정분도 다시 평가한다.
- [ ] 개발용 데이터셋과 별도로 비슷한 검증용(운영용) 데이터셋을 두어 오버피팅을 확인하고, 고객사가 자체 데이터셋으로 평가할 가능성을 염두에 둔다.
- [ ] 평가 실행 기록은 관측(Observability) 도구에 남겨 나중에 점수 차이의 원인을 추적할 수 있게 한다.

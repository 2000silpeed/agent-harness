### 핵심 요약 (3~5줄)
- 엔비디아의 "You don't need long context" 논문: 컨텍스트는 유한한 자원이고, **원본은 파일(디스크)에 두고 컨텍스트(램)에는 최소한만** 넣는 단순한 방식이 정확도를 크게 떨어뜨리지 않았다. LLM에게 압축을 시키는 일이 오히려 가장 비싼 작업이었다. 서브에이전트·브랜치로 작업을 쪼개 싼 모델이 비싼 일을 하게 하는 방식도 여전히 유효하다.
- 지금 수강생이 만든 에이전트는 Jev(판단 모델)를 **툴 콜링처럼** 호출한다. LLM이 툴 콜을 요청해야만 Jev가 실행되므로 "LLM이 판단해서 판단 모델을 다시 부르는" 모순이 생기고, Jev의 장점인 속도도 잃는다.
- Jev는 **LLM보다 앞에서** 판단을 가로채야 한다. 쓸 자리는 ① 사용자 질문의 의도 분석(우리 시스템 데이터로 답변 가능한가) ② 저장소에 답할 파일이 있는지 판단(index.md로 파일 고르기 → 청크별 yes/no) ③ 가져오기에서 리랭킹 대신 **문장 번호 고르기**.
- 그러면 LLM은 **답변만** 한다. 구현은 미들웨어(Claude에서는 훅)로 질문 직후를 가로채거나, 서브에이전트가 추려서 메인에 넘기는 두 가지다(서브에이전트가 예외 상황에 더 유연).
- Jev API는 **배치 처리**를 지원하므로 질문을 모아서 한 번에 보내 호출 수와 네트워크 지연을 줄인다. 휴식 후 이 구조로 에이전트를 개선하는 실습을 한다.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**1. 엔비디아 논문 "You don't need long context" (20:47~)**
- "그저께" 엔비디아에서 나온 "가벼운 논문". 강사는 Claude에게 정리를 시켜 그 결과를 보여 줬다. "컨셉으로는 제가 말씀드린 내용과 동의를 했는데".
- 핵심 결론(장표 3): ① 컨텍스트는 유한한 자원이다("우리 GPU 때문에 유한하죠") ② 가장 단순한 기법이 가장 강력한 경우가 많았다 ③ LLM에게 압축을 요청하는 일이 사실은 가장 비싼 작업이었다.
- "최종적으로는 원본은 어디다가 저장을 해놓고 컨텍스트에는 최소한만 넣어라는 게 사실은 핵심이긴 해요."
- 강조한 이유: Claude를 쓰다 보면 long context가 계속 생겨난다. "이거 우리가 계속 보내야 되는가, 이거 다른 모델이 처리할 수 없는가" — 전날 소개한 **스포티파이 사례**와 같은 문제의식. "모두가 이제 생각하는 게 동일합니다. 컨텍스트에는 최소한만 보내자."

**2. OS 메모리 계층 비유 — 컨텍스트 = 램, 대용량 데이터 = 디스크**
- LLM을 OS처럼 쓰되 컨텍스트는 램, 대용량 데이터는 디스크에 둔다. 필요할 때마다 로드하고 다시 버리는 전략이 "생각보다 정확도가 떨어지지 않더라"가 논문의 결론.
- 중간중간 압축해서 **메인 컨텍스트 세션은 계속 가볍게** 유지한다. "원본은 어차피 파일에 있으니까."

**3. Just in time 읽기 + 노트**
- 필요할 때 읽고 노트로 적어 둔다. 노트 = "메인 컨텍스트한테 보낼 한두 줄의 짧은 문장".
- 짧은 문장만 보내도 메인이 이해하더라(긴 내용을 압축한 것이니까). 또는 "그런 내용이 있더라"만 남겨 두면, 필요할 때 그때 가서 읽는다.

**4. 서브에이전트·브랜치 격리는 여전히 유효**
- 서브에이전트나 브랜치를 격리해 작업을 최대한 쪼개고, **싼 모델이 비싼 작업을 하게** 한다.
- "모델사들은 야 하나면 돼. 하지만 실질적으로 사용하는 사람 입장에서는 … 너무 비싸던데?" — 이 싸움이 계속되고 있다. 우리는 모델사가 아니고 실사용 위주이므로 **컨텍스트를 여전히 분리하고 관리해야 한다**는 수업 내용이 이런 자료로 뒷받침된다.

**5. 현재 에이전트의 한계 — Jev를 툴 콜링으로 호출 (25:34~)**
- 앞 시간에 한 수강생이 질문한 "큰 한계점". 지금 에이전트는 Jev 모델을 툴 콜링처럼 호출한다.
- 툴 콜링의 흐름: LLM이 툴 콜 메시지를 만든다 → 그제서야 툴(프로그램)이 실행돼 결과만 전달한다. 즉 "Jev 모델을 호출해 달라는 프로그램을 실행하는 형태".
- "LLM이 툴 콜링을 요청해야만 제브는 실행이 됩니다." Jev는 **디시전(판단) 모델**인데 "LLM이 왜 판단을 해서 판단하는 모델을 다시 불러요? 자기가 했어야죠."
- Jev의 장점은 속도인데, LLM을 덜 쓰려고 넣어 놓은 것이 오히려 **속도를 느리게** 만든다.
- (저장소 확인: 과제 문서에 같은 문장 — `JEV(Decision Model) -> "Tool Call" 로 동작하면 의미 없음.` `Day05_new/task.md:7`)

**6. Jev는 LLM 전에 — 루프를 새로 짜지 않고 끼워 넣기 (27:09~)**
- 지금 Deep Agent의 루프는 "완전히 LLM 위주의 설계"라 모든 구성에 LLM이 들어간다. 우리는 "LLM 타기 전에 제어를 해야" 한다.
- "결국 제브 전에, LLM 전에, LLM 전에 호출되는 게 필요해요." LLM이 원래 하던 판단을 **뺏어와서 대신하고 그 결과를 리턴**해야 한다.
- 루프를 아예 다시 짜는 건 답이 아니다: "그럴 거면 굳이 딥 에이전트를 쓸 필요가 없었겠죠? 그냥 코드를 밑바닥부터 짜고 말지."
- 그래서 "어느 곳에 판단 영역을 넣을 수 있을까"가 "제일 중요합니다".

**7. 의도 분석 (30:15~)**
- 사용자 질문 레이어에서 판단 모델로 의도 분류·분석을 한다.
- 현재 에이전트 기준으로는 **"우리 시스템 데이터로 답변 가능 여부"**를 판단할 수 있다. 그 외에 "어디로 라우팅을 한다든가" 같은 용도도 가능.

**8. 저장소에 답할 데이터가 있는지 판단 — 핵심 (31:03~)**
- "여기가 사실 3번이 핵심입니다." 가져오기보다 **저장소에 이 질문에 답할 데이터(또는 가까운 것)가 있는지 판단**하는 것이 핵심.
- 1) **인덱스**: 저장할 때 만들어 둘 수 있다(index.md). 인덱스를 보고 특정 파일을 "찍을" 수 있다. 찍은 뒤 키워드 매칭으로 내용이 있는지까지 볼 수 있다("인덱스.md 한 다음에 읽어서까지를 제거[Jev]한테 맡길 수 있습니다").
- 2) **읽어서 판단**: 파일이 짧으면 통째로 읽으면 되지만 길 수도 있다. "실제로 다 읽어서 어떻게 판단을 내려야 될까요? 이게 제브를 사용하는 것의 핵심 고민입니다."

**9. 청크별 yes/no — 임베딩 대체 (34:16~)**
- 판단할 것은 "필요한 내용이 있는지". 읽는 건 빠르다. "그래서 우리는 제브한테 yes or no만 받으면 돼요."
- 문서를 청크로 잘라 읽히면 "1번에 있어, 2번에 있어, 3번에 있어, 4번에 있어는 엄청 빠르게 대답해줍니다" → "2번과 3번에 있어요"를 받는다.
- 이건 원래 **임베딩**이 하던 일. "이제 인베딩[임베딩]을 할 필요가 없죠." 이미 읽었으니 가져오기는 "그냥 그대로 전달만 해주면" 된다.

**10. 리랭킹과 그 대체 — 문장 번호 고르기 (35:40~)**
- 리랭킹: RAG에서 가져온 청크를 우선순위대로 배치(문서 순서 조절). 보통 "중요한 거, 덜 중요한 거, 그 다음으로 중요한 거" 순으로 가운데에 덜 중요한 것을 둔다 — **Lost in the Middle**을 피하기 위한 배치(강사는 "이건 중요하지는 않고"라고 넘어감).
- "이거 요즘 안 합니다 잘." 리랭킹 모델이 따로 있을 만큼 무겁고 비싼 작업이라, 모두가 하기 싫었지만 성능 때문에 "억지로 억지로" 했다. "이젠 더 할 필요가 없어요."
- Jev에게 "1, 2, 3 순위 내라"고 시키면 컨텍스트가 터질 수 있다. "제보[Jev]는 출력을 못 해요. 요약은 할 수 없습니다."
- 대안: 리랭킹의 목적("컨텍스트에게 필요 없는 걸 최대한 덜 주자")만 가져온다. 청크 안에서도 **"진짜 진짜 그 중에서도 액기스"** 문장만 남긴다.
  - 문장에 번호를 붙이는 건 **코딩으로**: "마침표 인식해서 하는 건 정규 표현식이니까 너무 쉽잖아요."
  - 번호 붙인 글을 넘기고 **번호만 출력**하게 한다(초 액기스만).
  - 프로그램이 그 번호로 **필터링해서** 전달한다.
- 이 작업은 이전에는 LLM이 했는데 Jev로도 할 수 있고 "더 빨라질 것 같아요". 글이 복잡하면 Jev가 못 할 수도 있지만, "질문이랑 문장 비교해서 확률 출력하는 거"라 "제브 잘해요".

**11. 인용 출처는 프로그램이 단다 (41:17~)**
- 원본 위치를 프로그램이 다 기억한다: 예) `A.MD` 문서의 두 번째 청크 중 3번 문장.
- RAG 답변에서 가장 중요한 것 중 하나가 **인용 출처** 다는 것인데, 문서·청크·문장 번호를 알고 있으니 색칠이나 인용구 달기를 "그냥 프로그램으로 달아주면" 된다.

**12. Deep Agent에 녹이기 — LLM은 답변만 (42:49~)**
- 저장소 파일 저장은 **시스템**이 한다("LLM이 판단하는 영역이 아닙니다"). 의도 분석은 Jev, 청크 가져오기·문장 발라내기도 Jev → "LLM은 뭐만 하면 돼요? 답변만 하면 됩니다."
- 루프 속 "어딘가를 강제로 끊어내야" 한다: 사용자 질문이 들어오면 그 구간을 뺏어서 Jev로 처리하고 "야 LLM, 사용자 질문 이거고 내가 문장 이거 찾아놨으니까 넌 대답만 해".
- 방법 두 가지:
  - **미들웨어**("여기서는 미들웨어고 클로우드[Claude]에서는 훅이죠"): "서브에이전트 만들기 귀찮아, 메인에서 다 할래" → 미들웨어로 잘라서 넣는다. 프로그램 레벨로 돌린다.
  - **서브에이전트**: 질문이 들어오면 서브에이전트 하나를 만들어, 메인은 모르게 서브에이전트가 "다 예쁘게 추려가지고 형님 여기 있습니다" → 메인은 대답만. 파일을 못 찾는 등 예외 상황에 **LLM을 써서 더 유연하게** 대응하고 싶을 때.

**13. 요즘의 RAG와 배치 처리 (46:38~)**
- "요즘의 레그[RAG]입니다." Jev 이전에도 프로세스는 같았고, 판단 단계는 **아주 작은 LLM에 고정된 출력**만 하게 했다(에이전트 개발자에게 판단 프로세스가 여전히 힘들었기 때문). 그때의 문제는 **호출이 잦다**는 것.
- 디시전 모델은 질문 여러 개를 한 번에 받는다. "기본적으로 배치 처리를 그냥 API에서 지원을 해요. 우리가 열 개를 보내면 열 개의 답이 그냥 나옵니다."
- 어차피 여러 번 보낼 질문이면 쌓아서 한 번에 보낸다 → 호출량과 **네트워크 레이턴시**를 줄인다. 단, "이 컨텍스트가 허용하는 내에서만".

### 강사 팁·주의사항
- 판단 모델을 **툴로 노출하지 말 것**. LLM이 불러야 실행되는 구조면 판단을 LLM이 하는 셈이고 속도도 잃는다.
- 판단을 넣겠다고 **루프를 처음부터 다시 짜지 말 것**. 그럴 거면 프레임워크(Deep Agent)를 쓸 이유가 없다. 기존 루프의 사용자 질문 직후 구간을 가로채라.
- 판단 모델에게는 **yes/no나 번호만** 받는다. 순위 매기기·요약 같은 출력을 시키면 컨텍스트가 터지거나 못 한다("제보는 출력을 못 해요").
- 문장 번호 붙이기·번호 필터링·출처 기록은 **모델이 아니라 코드**가 한다(정규식으로 충분).
- 리랭킹은 비싸고 무거워 "요즘 잘 안 한다". 목적(덜 주기)만 가져와라.
- 미들웨어는 간단, 서브에이전트는 유연(파일을 못 찾는 등 예외 대응). 상황에 맞춰 고른다.
- 판단 호출이 여러 번이면 **배치로 모아 한 번에** 보낸다. 단 컨텍스트가 허용하는 범위 안에서.
- 컨텍스트는 유한하다: 원본은 파일에, 메인 세션에는 한두 줄 노트만. LLM에게 압축을 시키는 건 비싸다.

### 실제 프로젝트에 적용할 체크리스트 (- [ ] 행동 지침 형태, 특정 프레임워크에 묶이지 않는 원칙 위주)
- [ ] 원본 데이터는 파일·저장소에 두고, 메인 컨텍스트에는 필요한 최소한(한두 줄 노트)만 넣는다.
- [ ] 긴 내용 압축을 메인 LLM에 맡기지 말고, 필요할 때 읽는(Just in time) 구조나 싼 모델·서브작업으로 분리한다.
- [ ] 판단(분류·yes/no·선택) 단계가 LLM의 도구 호출에 의존하고 있는지 점검하고, 있다면 LLM 호출 **앞단**으로 옮긴다.
- [ ] 기존 에이전트 루프를 재작성하지 말고, 사용자 입력 직후를 가로채는 지점(미들웨어/훅 또는 서브에이전트)을 찾는다.
- [ ] 사용자 질문에 대해 "우리 데이터로 답변 가능한가" 의도 판단을 먼저 한다(필요하면 라우팅).
- [ ] 문서를 저장할 때 인덱스(예: index.md)를 함께 만들어, 질문 시 후보 파일을 빠르게 고를 수 있게 한다.
- [ ] 후보 문서를 청크로 잘라 판단 모델에 "필요한 내용이 있는가"만 yes/no로 묻는다(임베딩 검색 대체 가능성 검토).
- [ ] 리랭킹 대신 문장에 코드로 번호를 붙이고, 판단 모델에게 핵심 문장 번호만 받아 코드로 필터링한다.
- [ ] 판단 모델에게 순위·요약 같은 자유 출력을 요구하지 않는다(번호·yes/no처럼 고정된 출력만).
- [ ] 문서·청크·문장 위치를 프로그램이 기록해 인용 출처를 코드로 붙인다.
- [ ] 판단 이후 LLM에게는 "질문 + 골라 둔 문장"만 주고 답변만 하게 한다.
- [ ] 예외(파일을 못 찾음 등)가 많으면 단순 가로채기 대신 서브에이전트로 유연하게 처리한다.
- [ ] 판단 호출이 여러 건이면 컨텍스트 한도 안에서 배치로 묶어 호출 수·네트워크 지연을 줄인다.

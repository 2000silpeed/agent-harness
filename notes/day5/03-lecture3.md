## 5일차 3강 — Langfuse 평가 준비: Claude Code로 Dataset·Evaluator 만들기와 평가 기준 설계

> 출처: 「5일차 3강 다시보기 (보정)」(전사·분석, 45:40 분량), 「5일차 3강 장표」(17장). SDS AX Advanced · 2026-11-06.
> 대응 저장소: `Day05_new/` — 수업 경로 `use_cc/`(개념 문서 `concepts/m2.md` Golden Dataset, `concepts/m3a.md` 온라인 평가·Trace 선정), 노트북으로는 `02-Offline-Golden-Dataset.ipynb`, `03a-Online-Eval-Trace-Selection.ipynb`. 강의는 미션 카드를 그대로 따르지 않고, 강사가 Langfuse 화면과 Claude Code로 즉석 시연했다.

### 핵심 요약 (3~5줄)
- 트레이스를 쌓았으니 다음은 평가다. 평가하려면 먼저 **Golden Dataset(정답지)**이 필요하고, Langfuse의 Evaluation 메뉴(Score, Evaluator, Human Annotation, Dataset, Experiment)에서 Dataset을 만든다. 어제 스킬로 만들려던 작업으로 **5개 정도**만 Claude Code에게 만들게 했다.
- Evaluator(LLM-as-a-Judge)를 시키자 "LLM Connection이 없다"며 멈췄다. **조직(Organization) 단위 LLM Connection**을 Anthropic 어댑터 + OpenGateway(Base URL·API 키) + 커스텀 모델(`deepseek/deepseek-v4.1-flash-ultrafast`, GLM 5.3 플래시)로 만들고, **Default eval model**을 지정한 뒤에야 Evaluator가 생성됐다.
- Claude가 처음 만든 평가 프롬프트는 "0~1점으로 grade 하라"뿐이라 **점수가 0.7 근처로 쏠린다**. "점수 내달라고 하면 안 됩니다. 점수의 그 판정 기준을 되게 촘촘하게 주셔야 돼요." 등급마다 **관찰 가능한 기준**을 주는 것이 가장 중요하고, 이 설계는 **개발자의 몫**이다.
- 카테고리(나쁨·보통·좋음) 판정은 LLM 대신 **디시전 모델 jev**(TypeSafe 연결)로 하면 싸고 빠르고 반복해도 안정적이다. jev는 점수·선택·yes/no 세 유형 질문만 받는다.
- 모든 요청을 평가하면 "파산"한다. 온라인이든 배치든 **샘플링·선별**이 필요하고, **트레이스를 남길 때부터** 무엇(잘못됐거나 애매한 것)을 평가할지 정해야 한다 — 점심 뒤(1시) 과제.

### 주요 개념 (개념별 설명, 강사가 강조한 이유 포함)

**1. Langfuse Evaluation 메뉴와 Golden Dataset**
- 왼쪽 메뉴 아래 Evaluation 섹션: 스코어(Score), 이벨류에이터(Evaluator), 휴먼 어노테이션(Human Annotation), 데이터셋(Dataset), 익스페리먼트(Experiment, 실험 돌리는 곳).
- Dataset item = 아이템 ID·소스·생성 시각 + **Input(입력) / Expected output(기대 출력, 정답) / Metadata(케이스 번호 등)**. "문제와 정답이 구성이 되어 있습니다." 즉 데이터셋을 만드는 것이 정답지를 만드는 것이다.
- 만드는 방법: CSV 업로드 또는 API 호출("한 땀 한 땀"). 보통은 CSV.
- 강조 이유: "평가를 하려면 아까 뭐가 필요하다고요? 골든 데이터셋이 필요합니다." 평가의 출발점이 정답지다.

**2. 평가 대상 = 어제 스킬로 만들려던 내 작업**
- 4일차에 스킬로 만들려고 고민한 작업을 평가 대상으로 삼는다("우리의 스킬을 이벨레이트 하는 거예요").
- "많을 필요도 없어요. 사실 5개 정도만" — 정답을 고민하는 일 자체가 고통스럽기 때문.

**3. Evaluator = LLM Judge, 그래서 LLM 키가 필요하다**
- Evaluator(평가자)는 LLM 기반 Judge다. Claude Code가 "프로젝트에 LLM을 하나도 세팅 안 해놔서 난 아무것도 할 수가 없습니다", 프로젝트 세팅의 LLM Connections에 공급자 키를 넣어 달라고 답했다.
- 이런 점검 작업은 effort를 높일 필요 없다("미디움 정도면 충분해요"). 모델도 Opus가 아니라 Sonnet이어도 괜찮다고 봤다.
- (저장소 확인: Day05_new/use_cc/concepts/m3a.md:364 — 서버 쪽 LLM Judge를 쓰면 수강생 모델 키가 Langfuse LLM Connection에 저장된다고 명시)

**4. 조직 단위 LLM Connection**
- 경로: 프로젝트 오른쪽 위 → 톱니바퀴(Settings) → 왼쪽 네 번째 **LLM Connections**.
- Organization connection은 여러 프로젝트에서 상속받아 쓸 수 있고, Project connection은 그 프로젝트만. 강사는 "귀찮아서" 조직 단위로 했다(Claude도 문서를 찾아 "조직 설정에 등록한 거는 모든 프로젝트에서 상속 받아 쓸 수 있구나"를 확인).
- 어댑터 선택지: Anthropic, OpenAI, Azure, Bedrock, … , **TypeSafe**, Other model.
- "원래는 보통 오픈 AI를 많이 선택을 합니다" — OpenAI compatible 서버가 많아서. 이번에는 "특별한 게이트웨이를 써보고 싶어서" **Anthropic 어댑터**를 골랐다. (저장소 확인: Day05_new/README.md:3 — OpenGateway가 "Anthropic Messages 호환 엔드포인트라 클라이언트는 `ChatAnthropic`")

**5. OpenGateway를 쓰는 이유**
- "빨라서요. 빨라서 다른 이유는 없습니다." 국내 토큰 팩토리라 네트워크상 빠르다. 다른 플랫폼(OpenRouter 등)을 써도 상관없다.
- **밤 12시~아침 9시 90% 할인.** 강사는 Claude(Opus)를 메인 오케스트레이터로 작업 계획을 짜고, 실제 작업은 pi agent에 딥시크 모델을 물려 워커로 돌린다. 밤새 돌려도 하루 3달러, 많으면 5달러("한 달 30일 다 돌리면 150불이네요. 우리 200불짜리 계정 쓰잖아요").
- 품질: "오프스보다 못할 때가 가끔 있습니다. 하지만 오프스도 그걸 이제 어드바이저 느낌으로 보정을 해주면 돼서" 전체 품질은 괜찮고 처리량이 많다. (회사와 무관하다고 밝힘)

**6. Default eval model (프로젝트 기본 평가 모델)**
- 연결 테스트에서 LLM 호출 자체는 정상이었지만 "디폴트 이벨 모델 미싱" 오류. "프로젝트 화면에서 LLM에서 저지해서 디폴트 모델을 조직 연결의 모델로 세팅하십시오."
- Evaluator 메뉴에 테스트 흔적과 경고가 보이고, 거기서 기본 모델을 지정하면 "프로젝트 디폴트 모델이 업데이트 됐습니다" → 재실행하니 Healthy로 바뀜.

**7. 나쁜 평가 프롬프트와 0.7 수렴(점수 편향)**
- Claude가 만든 Evaluator 프롬프트: "grade, customer, support, answer, question, answer to grade, reference, answer … 일정 단위로 평가해" + 마지막 줄 **0~1점으로 grade**.
- "가장 많이 하는 실수", "최악의 프롬프트". 위쪽은 데이터를 넣는 부분이라 괜찮지만 **마지막 줄 때문에 평가자가 의미가 없다**.
- "0.7로 거의 수렴할 겁니다. 확신해요." 이유: 모델은 평균적인 데이터를 학습했고, 0.0→1.0 사이 각 구간의 **기준을 준 적이 없다**. 그래서 편향이 생긴다.
- 실제로 잘못된 프롬프트의 이전 기록은 **0 아니면 1**로 나왔다(강사 화면 기준. 수강생마다 스킬이 달라 기준이 전혀 다르게 나올 수 있음).

**8. 평가 기준 설계 원칙 — "점수는 느낌이 아니라 절차로"**
- 구간을 나눈다: 예) ~0.3 나쁨 / ~0.7 보통 / 그 위 좋음. 각 구간 기준 + **구간 안의 세부 기준**(나쁨 중 최악·덜 나쁨, 보통 중 상급 보통, 좋음 중 최고)까지 줘야 "유기적으로 판단"해 점수가 나온다. 0.1점 단위로 다 주라는 뜻은 아니다.
- "**등급마다 관찰 가능한 기준** 저는 이게 제일 중요하다고 생각해요." — 실제로 평가 가능한 조건을 등급마다 제시.
- 출력 형식으로 순서를 강제(JSON 출력 제어)하는 것도 좋은 방향. 0.0을 쓸지도 정해야 한다.
- 누가 정하나: "이건 담당자, 우리 개발자의 몫입니다." 업무 담당자와 이야기하며("이런 요소를 빼먹으면 나쁨이라고 평가하고 개선해야 되더라") 개발자가 세팅한다. "이건 답이 없습니다… 매번 새로운 세팅." 데이터셋은 그냥 텍스트라서 무엇을 좋다고 볼지는 사람이 정해야 한다.
- Claude와 대화로 지침을 개선할 수 있다. 지적하자 Claude가 "같은 조건이 무엇인지, 뭘 놓쳤다고 볼지 정해두지 않아서 Judge가 매번 자기 기준으로 판단 → 일관성이 없다"고 짚었다.

**9. 평가 방식: 점수(Numeric) vs 카테고리**
- 평가자는 점수와 함께 **판단 이유 코멘트**를 단다. 숫자로 평가하라 했으니 Numeric 타입으로 기록.
- 카테고리(나쁨·보통·좋음 중 픽)도 가능하다.

**10. 디시전 모델 jev와 TypeSafe**
- 카테고리로 고를 때 "굳이 LLM을 써야 할까요?" — 디시전 모델이 싸고 빠르다.
- 핵심 특징: "**여러 번 돌렸을 때도 결과가 안정적**". 강사가 전해 들은 수치로 LLM은 Opus도 약 88%, jev는 90% 초반.
- 연결: LLM Connections → Organization connection → **TypeSafe** 어댑터, 키는 공유 시트에서. TypeSafe 타입 API는 TypeSafe 외에 Vercel AI Gateway, OpenRouter도 지원한다고 함.
- 질문 유형은 세 가지뿐: **점수(score) / 선택(객관식 안에서) / yes or no**. 모델 특성에 맞게 질문을 써야 평가가 된다. (저장소 확인: Day05_new/eval_lab/decisions.py:26-53 — `Noul`(참/거짓), `Choice`(하나 고르기), `Score`(순서 있는 단계) 세 클래스만 정의)

**11. Evaluator 런 타입과 Langfuse 제공 템플릿**
- 런 타입: **LLM-as-a-Judge / Code Evaluator**(코드로 그냥 돌림, 고정된 출력일 때만) **/ 디시전 모델**.
- 제공 템플릿(대화 검토 에이전트용): Detect chat intent(의도 분류), 범위 밖 요청 감지, 사용자 요청 거절(disagreement), 품질(Quality — 기본으로 만들어진 것), 분류, 검색 활용(검색 데이터를 잘 썼는가) 등.
- "이거는 그대로 쓰시면 안 돼요." 좋아 보이지만 "까서 보면 우리 사실과 맞지 않는 것들이 훨씬 많습니다." 참고 자료로만.

**12. 평가 주기 — 전부 평가하면 파산**
- "매 요청받아 평가한다. 그러면 우리 프로젝트는 파산할 겁니다."
- 온라인(오자마자 평가): 샘플링 불가피. 배치: 그래도 특정 대상만 뽑아야 한다.
- "잘 나온 걸 평가할 필요는 없어요. 잘못 나온 걸 평가해야 됩니다." 또는 애매한 것.
- 그래서 **트레이스를 남길 때부터** 잘 나옴/애매함/나쁨을 표시해야 한다 → "마지막 퍼즐". (저장소 확인: Day05_new/eval_lab/online.py:651-661 — 서버 Rule의 `sampling`은 0 초과 1 이하만 허용하고 "생략(전부 평가)하는 길은 일부러 열지 않았다")

### 실습/데모 내용 (명령어, 파일 구조, 프롬프트, 코드 조각 등 원문 그대로 보존)

**1) Dataset 생성 테스트 (Claude Code 지시, 발화 그대로)**
```
그냥 랭퓨즈의 데이터셋이라는 걸 만들고 싶다.
통신 되냐?
뭐 만들 수 있으면 그냥 샘플로 하나 만들어 봐라.
```
- "명령은 뭐 저랑 조금 다르셔도 됩니다."
- 결과: Claude가 API로 데이터셋 생성 + 가상 항목 추가. Langfuse 화면에서 확인 → 이름 "테스트 데이터셋, 오늘 날짜".
  - 예시 항목: Input "결제 수단을 바꿀 수 있나요?" → "결제 완료 전까지 가능", "주문 취소 언제 가능한가요?" → "배송 시작 전까지"
  - Metadata에 `케이스 T1`, `T2` 등 알아볼 수 있는 값.
  - 강사 예제가 결제 쪽이라 예시도 그렇게 만든 것 같다고 함. (저장소 확인: Day05_new/README.md:3 — 실습 Agent 업무가 "주문 취소·결제 환불·예약 재고 복원")

**2) Evaluator 세팅 점검 (지시)**
```
이 데이터셋을 평가하기 위한 이벨류에이터를 세팅 가능한지 점검
```
- effort medium, 모델 Sonnet이어도 충분. 응답: LLM Connection이 없어 진행 불가 → 프로젝트 세팅 LLM Connections에 공급자 키를 넣어 달라.

**3) 조직 LLM Connection 만들기 (화면 순서)**
1. 프로젝트 오른쪽 위 → 톱니바퀴 → Settings → 왼쪽 네 번째 `LLM Connections`
2. Organization connection 선택
3. Select adapter: `Anthropic` (보통은 OpenAI compatible)
4. Provider name: `오픈 게이트웨이`(OpenGateway) — "우리가 알기 위한" 이름이라 자유
5. API key: 공유 구글 시트의 "오픈 게이트웨이 API 키"(시트에는 OpenRouter 키, jev 키도 추가됨)
6. `Show Advanced Settings` → API Base URL: 시트 4번 행에 링크된 OpenGateway 문서의 **Base URL** 복사
7. **`Enable Default Models` 끄기** (Anthropic 기본 Claude Opus 5.5 등을 쓰지 않음)
8. Custom model name: OpenGateway Docs → Models → "Optimize by Open Gateway" 모델 두 개 중
   - `deepseek/deepseek-v4.1-flash-ultrafast` ("좀 더 비싼… 머리가 좀 더 좋아서")
   - GLM 5.3 플래시 (같은 방법으로 복사·추가)
9. `Create Connection`. 나머지 설정은 Langfuse 문서대로 Claude에게 시켜도 된다.
- (저장소 확인: Day05_new/README.md:3 — 실습 모델이 OpenGateway의 `deepseek/deepseek-v4.1-flash-ultrafast`)

**4) 연결 테스트 → 기본 평가 모델 지정**
```
LLM 커넥션 세팅 했으니까 테스트 해줘.
```
- Claude: 프로젝트는 여전히 LLM Connection 0개 → 조직 레벨을 찾아 두 모델 확인 → 테스트. LLM 연결은 문제없음, 그러나 `default eval model missing`.
- Evaluator 메뉴에서 경고 확인 → 기본 모델 지정 → 재실행:
```
세팅했으면 다시 해봐.
```
- 결과: Healthy. "물론 이 모든 과정을 사실 클로드한테 클로드 인 크롬으로 주고 완전히 맡기셔도 돼요."

**5) 프롬프트 개선 대화 (지시 요지)**
```
(평가자가) 평가할 수 있는 최적인 지침이 아니잖아.
최적으로 0.1부터 1.0까지 (등급)을 평가하기 위해서는 어떤 방향으로 줘야 할까?
```

### 강사 팁·주의사항
- "점수 내달라고 하면 안 됩니다." 0~1 한 줄 프롬프트는 0.7 근처로 수렴한다. 구간·세부 구간·관찰 가능한 기준을 촘촘하게.
- 평가 기준은 업무 담당자가 아니라 **개발자가** 담당자와 이야기하며 매번 새로 만든다. 정답은 없다.
- Langfuse 제공 Evaluator 템플릿은 그대로 쓰지 말고 참고만 한다.
- 카테고리 판정은 디시전 모델(jev)이 싸고 빠르고 안정적이다. 질문은 score·choice·yes/no 형태로만.
- Code Evaluator는 출력이 고정된 경우에만 쓸 수 있다.
- 점검·확인 작업은 effort medium, Sonnet으로 충분하다.
- 화면 설정은 Claude in Chrome에 맡겨도 된다. 혼자 할 때는 한 땀 한 땀 하지 말 것.
- LLM Connection은 조직 단위로 만들면 여러 프로젝트에서 재사용한다. 커스텀 모델을 쓸 때는 Enable Default Models를 끄고 모델명을 정확히 복사한다.
- LLM 연결이 돼도 **Default eval model**이 비어 있으면 Evaluator가 멈춘다.
- 전부 평가하면 파산한다. 잘 나온 것 말고 잘못됐거나 애매한 것을 평가하고, 그 표시는 트레이스 기록 시점에 남긴다.
- 비용: 저렴한 워커 모델(딥시크) + 계획·보정은 Claude(Opus) 조합, 야간 할인 시간대 활용.

### 실제 프로젝트에 적용할 체크리스트 (- [ ] 행동 지침 형태, 특정 프레임워크에 묶이지 않는 원칙 위주)
- [ ] 평가 전에 입력·기대 출력·메타데이터(케이스 ID)로 된 Golden Dataset을 먼저 만든다. 처음엔 5건 정도로 시작한다.
- [ ] 평가 대상은 내가 실제로 자동화하려는 작업(스킬)에서 고른다.
- [ ] Judge용 모델 연결과 기본 평가 모델이 모두 지정됐는지, 실제 호출 테스트로 확인한다.
- [ ] Judge 프롬프트에 "0~1점으로 매겨라"만 쓰지 않는다. 등급(나쁨·보통·좋음)과 등급 안 세부 구간마다 관찰 가능한 기준을 적는다.
- [ ] 최저·최고 점수(0.0을 쓸지 등)와 출력 형식(JSON, 판단 순서)을 고정한다.
- [ ] 평가 기준은 업무 담당자와 대화해 "무엇을 빠뜨리면 나쁨인가"를 정하고, 개발자가 문서로 소유한다.
- [ ] Judge가 점수와 함께 판단 이유를 남기게 하고, 점수 분포가 한 값(예: 0.7, 또는 0/1)으로 쏠리는지 확인한다.
- [ ] 분류·예/아니오·단계 점수로 끝나는 판정은 LLM 대신 싸고 안정적인 판정 전용 모델을 검토한다.
- [ ] 출력이 고정된 검사는 코드 평가기로 처리한다.
- [ ] 플랫폼 제공 평가 템플릿은 그대로 쓰지 않고 내 업무 사실에 맞게 고친다.
- [ ] 모든 요청을 평가하지 않는다. 온라인은 샘플링, 배치는 대상 선별을 정하고 예상 비용을 계산한다.
- [ ] 트레이스를 남길 때 잘 나옴·애매함·나쁨(또는 "체크 필요") 표시를 함께 남겨 평가 대상을 고를 수 있게 한다.
- [ ] 모델 키는 조직·프로젝트 중 어디에 저장되는지, 누가 쓰는지 확인하고 연결한다.

# ERP 어시스턴트 구축 방법론

> 사내 지식 검색을 바탕으로, 도구(MCP)를 통해 ERP의 소스 코드를 읽고 분석하고 고치고, 업무 데이터를 추출하고, 화면을 직접 조작하는 **사내 어시스턴트**를 만드는 방법이다. 무엇을 어떤 순서로 만들고, 단계마다 무엇을 고민하고, 어떻게 진행하고, 어떻게 검증하고, 언제 끝났다고 보는지를 적었다.
> 코딩 에이전트 방법론([`METHOD.md`](METHOD.md))과 같은 틀을 쓴다. 공통 규칙과 비교 규칙은 그 문서의 것을 그대로 따르고, 여기에는 ERP 어시스턴트에서 달라지는 것을 적는다.
> 특정 ERP 제품을 전제하지 않는다. SAP에만 해당하는 내용(ABAP 소스 접근, 이관, 검사 도구, 권한 객체, 화면 스크립팅)은 [`bases/sap.md`](bases/sap.md)에 둔다.

읽는 법
- 이 문서는 뼈대다. 양식·표·시험 목록은 `reference/erp-*.md`에 있다.
- 숫자 옆의 **(제안값)** 은 공개 자료에서 나온 값이 아니라 시작점으로 잡은 값이다. **(확인 필요)** 는 근거를 확인하지 못한 주장이다.
- 용어: 사람 담당자에게 대화를 넘기는 것은 "사람에게 넘김"이라고 쓴다. "이관"은 ERP에서 변경을 개발 → 품질 → 운영 시스템으로 옮기는 절차만 가리킨다.

## 1. 전체 그림

```
C0 범위·유형·기반 ─┬─► C1 대화 시험지·채점기 ────────┐
                   │                                ▼
                   └─► C2 뼈대·관측 ──────────► [기준선 측정] ─┬─► C3 지식·대화 상태 ─────┐
                                                             ├─► C4 도구·사람 연결 ─────┼─► C6 운영 기록 기반 개선 ─┐
                                                             └─► C5 제어·승인·감사 ─────┤                          ├─► C8 배포·운영
                                                                                       └─► C7 지연·비용 최적화 ────┘
```

이 흐름을 **유형마다 한 바퀴씩** 돈다. 앞 유형이 C8의 확대 기준을 통과한 뒤에 다음 유형의 도구를 연다.

```
지식 답변형 (문서를 찾아 근거와 함께 답한다)
   └─► 조회·추출형 (도구로 ERP의 소스 코드와 업무 데이터를 읽는다)
          └─► 변경형 (소스 코드나 시스템 상태를 바꾼다. 화면 조작 포함)
```

| 단계 | 시작하려면 | 같이 진행할 수 있는 것 | 끝났다는 기준 (한 줄) |
|---|---|---|---|
| C0 범위·유형·기반 | 없음 | 없음 | 요청 목록, 유형, 도구별 위험 등급, 성공 지표, 금지 행동이 실제 기록과 숫자로 승인됐다 |
| C1 대화 시험지·채점기 | C0 | C2 | 유형별로 결과를 대화 밖에서 확인하는 채점이 명령 한 줄로 돈다 |
| C2 뼈대·관측·기준선 | C0 (기준선 측정에는 C1 필요) | C1 | 한 턴이 끝까지 돌고, 대화·턴·이벤트로 기록되고, 조건이 적힌 기준선이 있다 |
| C3 지식·대화 상태 | C2 | C4, C5 | 묻는 사람이 볼 수 있는 문서만 찾아 근거와 함께 답하고, 근거가 없으면 답하지 않는다 |
| C4 도구·사람 연결 | C2 | C3, C5 | 도구가 요청한 직원 본인의 권한으로만 실행되고, 변경은 확인 없이 실행되지 않는다 |
| C5 제어·승인·감사 | C2 | C3, C4 | 반드시 지킬 규칙이 둘 이상의 층에서 막히고, 누가 무엇을 어떤 승인으로 했는지 남는다 |
| C6 운영 기록 기반 개선 | C1, C2, C3, C5 | C7 (반영은 따로) | 실패 분류 → 한 가지 변경 → 재측정 → 판정이 한 바퀴 돌았다 |
| C7 지연·비용 최적화 | C3, C4, C5 | C6 (반영은 따로) | 유지 기준을 지킨 채 목표 지연·비용에 도달했거나, 더 줄이지 않는 근거가 있다 |
| C8 배포·운영 | C6, C7 | 없음 | 최종 확인을 통과했고, 장애 때 보이는 응답과 되돌리기를 해 봤고, 담당자가 있다 |

### 유형과 도구 등급

유형은 "어시스턴트가 어디까지 하나"이고, 등급은 "이 도구 호출이 얼마나 위험한가"다. 유형이 올라갈수록 통제가 더해진다. 표의 전체 판은 [`reference/erp-pipeline-ops.md`](reference/erp-pipeline-ops.md) 1절과 [`reference/erp-knowledge-tools.md`](reference/erp-knowledge-tools.md) 8절에 있다.

| 유형 | 쓰는 도구 등급 | 이 유형에서 더해지는 것 |
|---|---|---|
| 지식 답변형 | 없음 (검색만) | 문서 권한으로 거른 검색, 인용, 답하지 않기, 사람에게 넘김, 지식 담당자 |
| 조회·추출형 | 조회, 추출 | 요청한 직원의 신원을 ERP까지 전달, 읽기 전용 도구만 노출, 건수·크기 상한, 대상 환경 명시, 감사 기록, 도구 결과를 지시로 취급하지 않기 |
| 변경형 | 변경, 범용 조작 | 건별 사람 승인과 미리 보기, 요청자와 승인자의 분리(범위는 C5에서 정한다), 중복 실행 방지, 되돌리기, 환경 분리(변경은 개발 시스템, 운영 반영은 기존 이관 절차), 끄는 스위치 |

| 도구 등급 | 예 | 기본 처리 |
|---|---|---|
| 조회 | 객체 한 건 읽기, 소스 한 파일 보기, 문서 검색 | 자동 실행. 반환 상한, 호출 수 제한, 기록 |
| 추출 | 표 대량 반출, 소스 묶음 내려받기 | 필터와 상한 필수. 결과는 파일·핸들로. 목적과 범위 기록. 상한을 넘거나 민감한 데이터면 승인 |
| 변경 | 소스 수정, 데이터 갱신, 설정 변경 | 계획 → 리뷰 → 승인 뒤에만. 개발 시스템에서만. 변경 전후 상태 기록 |
| 범용 조작 | 화면 직접 조작, 임의 질의·임의 명령 | 가장 좁게. 업무 단위 도구로 옮길 수 있는 것은 옮긴다. 남는 것은 단계마다 확인 |

### 왜 이 순서인가
- **평가(C1)와 기록(C2)이 먼저다.** 이유는 `METHOD.md`와 같다. ERP 어시스턴트에서는 하나가 더 있다. 결과를 대화 밖(ERP의 상태, 참조 질의의 결과, 실제 소스)에서 확인할 방법이 없는 과제는 평가할 수 없고, 평가할 수 없는 과제는 맡기지 않는다.
- **C3·C4·C5는 동시에 만들 수 있다.** 다만 아래 결합 지점에서는 순서를 지킨다.
- **유형은 위험이 낮은 것부터 연다.** 지식 답변형에서 검색 권한·기록·평가가 굳은 뒤에 읽기 도구를 붙이고, 읽기에서 신원 전달·감사·상한이 굳은 뒤에 변경 도구를 붙인다. 세 유형을 한 번에 열면 사고가 났을 때 어느 통제가 빠졌는지 가릴 수 없다.
- **C6은 운영 기록이 있어야 의미가 있다.** 첫 바퀴에서는 내부 시험 사용의 기록으로 한 번 돌리고, 출시 뒤에 주기적으로 돈다.

### 병렬 작업 규칙
- `METHOD.md`의 규칙을 그대로 쓴다: 만드는 것은 병렬, 반영하는 것은 하나씩. 읽기는 병렬, 쓰기는 한 번에 한 곳.
- 사람이 3~4명이면: 평가(C1) 한 명, 뼈대·기록(C2) 한 명. 기준선 뒤에는 지식(C3), 도구·신원(C4), 제어·감사(C5)를 한 명씩. ERP 운영(기반·보안) 담당자는 C0부터 끝까지 참여한다. 권한, 환경, 이관은 그 팀만 답할 수 있다.

결합 지점 (병렬로 만들더라도 이 순서는 지킨다)

| 먼저 | 그다음 | 이유 |
|---|---|---|
| C4의 신원 전달 경로 | 조회·추출 도구 연결 | 공용 계정으로 먼저 붙이면 모든 직원이 그 계정의 권한을 얻는다 |
| C4의 반환 상한·핸들 | 추출 도구 연결 | 표 전체나 소스 전체가 한 번에 컨텍스트를 채운다 |
| C5의 승인 양식과 감사 기록 | 변경 도구 연결 | 승인과 기록 없이 실행된 변경은 되짚을 수 없다 |
| C4의 도구 정의 동결 | C3의 캐시·시작 로드량 측정 | 도구 정의가 캐시 접두의 맨 앞이다 |
| C5의 승인 양식 확정 | C3의 요약 생존 시험 | 요약 뒤에도 대기 중인 승인과 대상 환경이 살아 있어야 한다 |
| C3의 검색 평가 | 생성 평가 | 답이 틀렸을 때 못 찾은 것인지 잘못 쓴 것인지 가려야 한다 |
| C6의 채택 | C7의 기준선 재측정 | 프롬프트가 바뀌면 비용·지연 기준선이 바뀐다 |

### 코딩 에이전트 방법론과 달라지는 것

| 항목 | 코딩 에이전트 | ERP 어시스턴트 |
|---|---|---|
| 평가 단위 | 과제 한 건 (요청문 → 변경) | 대화 한 건. 턴은 진단용이다 |
| 숨기는 것 | 숨긴 테스트, 정답 변경 | 기대 끝 상태, 참조 사실·근거 문서, 기대 행동, 모의 사용자 지시문 |
| 결과를 보는 곳 | 작업 트리와 테스트 결과 | ERP의 상태(비운영 복사본), 참조 질의의 결과, 실제 소스, 검색된 문서 |
| 사용자 | 한 명, 요청자가 곧 권한자 | 여러 명이고 권한이 사람마다 다르다. 권한은 ERP가 판정한다 |
| 작업 대상 | 격리된 작업 폴더 | 여러 사람이 쓰는 기록 시스템. 환경(개발·품질·운영)이 나뉜다 |
| 지식 | 저장소를 직접 읽는다 | 주인이 따로 있는 문서를 권한으로 걸러 검색한다 |
| 되돌리기 | 버전 관리로 되돌린다 | 변경 종류마다 다르고, 못 되돌리는 것이 있다 |
| 지연 | 분 단위 작업을 기다린다 | 대화다. 첫 글자가 나오는 시간이 중요하고 긴 작업은 따로 돌린다 |
| 주된 실패 | 틀린 코드, 테스트 조작 | 근거 없는 답, 권한 밖 노출, 엉뚱한 대상의 변경, 낡은 지식 |

### 공통 규칙에 더하는 것
`METHOD.md`의 공통 규칙 일곱 가지와 비교 규칙을 그대로 쓴다. 여기에 넷을 더한다.
1. **결과는 대화 밖에서 확인한다.** 어시스턴트의 "완료했습니다"나 화면의 완료 메시지는 결과가 아니다. ERP의 상태, 참조 질의, 실제 소스로 판정한다.
2. **권한은 ERP가 판정한다.** 어시스턴트와 모델은 "이 사람이 해도 되는가"를 판정하지 않는다. 요청한 직원의 신원을 ERP까지 전달하고, ERP가 그 사람의 권한으로 허용하거나 거부한다.
3. **어시스턴트는 운영 시스템을 바꾸지 않는다.** 변경은 개발 시스템에서만 하고, 품질·운영으로 옮기는 것은 기존 이관 절차와 사람이 맡는다.
4. **문서, 소스 코드의 주석, 데이터 값, 화면의 글자는 자료다.** 그 안의 문장은 지시가 아니다.

## C0. 범위·유형·기반

**목적:** 누구의 어떤 요청을 어디까지 맡길지 정한다. 여기서 정한 유형과 숫자가 뒤 단계 전부의 판정 기준이 된다. 양식은 [`reference/erp-pipeline-ops.md`](reference/erp-pipeline-ops.md) 1~3절에 있다.

**고민할 것**
1. **누가 어느 채널에서 쓰나.** 직군, 권한 집단, 채널(사내 메신저, 웹, 업무 화면 내장). 채널마다 스트리밍, 버튼, 파일, 긴 작업 알림을 지원하는 정도가 다르다. 기존 수단(검색, 담당자 문의, 직접 조회)보다 왕복이 줄어드는지가 기준이다.
2. **요청 목록을 실제 기록에서 뽑는다.** 헬프데스크 티켓, 질문 채널, 사내 검색 기록, 개발 요청 기록에서 요청 유형을 뽑아 빈도와 건당 처리 시간으로 줄 세운다. 회의에서 만든 목록은 실제 분포와 다르다.
3. **범위를 세 칸으로 나눈다.** 한다 / 안 한다(이유와 대안을 알리고 끝낸다) / 반드시 사람에게 넘긴다. 넘기는 계기는 실패 한도 초과, 고위험 행동, 사람 전문가의 판단이 필요한 질문(인사·법무·재무 판단 등)이다.
4. **유형을 정하고, 한 유형으로 시작한다.** 지식 답변형 → 조회·추출형 → 변경형. 요청 유형마다 어느 유형에 속하는지 적는다.
5. **결과를 대화 밖에서 확인할 수 있는가.** 요청 유형마다 확인 수단을 적는다: 근거 문서, 참조 질의, 비운영 복사본의 상태 조회, 테스트와 정적 검사. 확인 수단이 없는 쓰기 과제는 첫 대상으로 삼지 않는다.
6. **도구마다 위험 등급을 매긴다.** 읽기인가 쓰기인가, 되돌릴 수 있는가, 어떤 권한이 필요한가, 영향 범위가 어디까지인가, 어느 환경(개발·품질·운영)을 대상으로 하는가. 등급은 도구 서버가 알려 주는 값이 아니라 우리가 정한다.
7. **ERP 공급사의 사용 조건이 이 구성을 허용하는가.** 도구를 설계하기 전에 닫는다. 공급사의 API 정책과 계약이 공개되지 않은 인터페이스의 호출, 모델이 호출 순서를 스스로 정하는 연동, 대량 추출을 제한할 수 있다. 도구마다 "어느 인터페이스를, 어느 문서가 허용하는 용도로 부르는가"를 표로 적고 공급사와 법무의 확인을 기록으로 남긴다. 허용된 경로(공급사가 제공하거나 인정한 연결 방식, 직접 개발한 인터페이스)로만 설계한다. 예: SAP는 API 정책에서 이 세 가지를 인정한 경로 밖에서는 금지한다([`bases/sap.md`](bases/sap.md) 0절).
8. **환경과 권한의 전제를 ERP 운영 담당자와 확인한다.** 어시스턴트가 닿아도 되는 시스템과 환경, 직원의 신원을 ERP까지 전달할 방법, 변경을 옮기는 절차, 화면 조작이 허용되는지. 이 답이 없으면 조회·추출형 이상으로 가지 않는다.
9. **코드와 데이터가 회사 밖으로 나가도 되는가.** 외부 모델 API를 쓰면 소스 코드와 업무 데이터가 프롬프트에 실려 나간다. 무엇까지 보낼 수 있는지(소스, 업무 데이터, 개인정보), 공급자의 보존·학습 정책, 사내 서빙의 필요를 보안·법무 담당자와 정한다.
10. **경로를 누가 정하나.** 지식 답변은 대개 코드가 경로를 정하는 흐름(분류 → 검색 → 생성)으로 충분하다. 모델이 순서를 정하게 하는 것은 도구를 여러 번 써야 하는 요청 유형으로 한정한다.
11. **기반.** 직접 만들지, 플랫폼을 쓸지, 제품을 살지. 판단 기준: 모델에 들어가는 요청·응답 원문을 볼 수 있는가, 사용자 신원을 도구까지 전달할 수 있는가, 도구 실행 전에 승인 단계를 끼울 수 있는가, 대화 기록을 내보낼 수 있는가, 모델 버전을 고정할 수 있는가, 채널을 지원하는가.
12. **성공 지표와 상한.** 유형별 매번 통과율, 권한 밖 노출 0건, 승인 없는 변경 0건, 잘못된 실행률 상한, 과잉 거절률 상한, 첫 글자가 보이기까지의 시간과 완결 시간, 대화당·해결 1건당 비용. 자료에 나오는 목표 수치는 남의 수치이므로 우리 기준선을 잰 뒤 정한다.
13. **하면 안 되는 일.** 운영 시스템 변경, 요청자 권한 밖의 조회, 승인 없는 변경, 상한을 넘는 반출, 근거 없는 확답. 어시스턴트가 확정하거나 약속할 수 없는 것의 목록을 둔다.

**진행**
- 최근 기록 200건(제안값)을 요청 유형으로 분류하고, 유형마다 세 칸 중 어디인지, 어느 유형인지, 결과 확인 수단을 붙인다.
- 요청 유형별로 이상적인 대화 한 편과 실패 대화 한 편(못 알아들음, 범위 밖, 도구 실패, 권한 없음)을 실제 문장으로 쓴다.
- 도구 후보 목록과 등급 표를 만들고 ERP 운영 담당자에게 확인받는다. 기반 제품의 확인 항목은 `bases/`에 적는다.
- 기반 후보마다 같은 질문 세 개(지식, 조회, 범위 밖)를 넣고 요청·응답 원문과 도구 호출에 실린 신원을 덤프해 읽는다.
- 첫 메시지의 안내 문구(어시스턴트가 할 수 있는 일과 한계, AI라는 점)를 정한다. 사내용에도 고지 의무가 적용되는지는 법무가 확인한다(확인 필요).

**검증**
- 분류한 기록에서 "한다" 칸이 차지하는 비율과, 그중 근거 문서나 도구가 실제로 있는 비율을 센다.
- 두 사람이 같은 기록 50건(제안값)을 따로 분류해 세 칸 판정이 일치하는 비율을 적는다.
- 완료 기준 문장마다 "어떤 명령이나 기록으로 확인하나"를 옆에 적을 수 있다.

**완료 기준**
- [ ] 사용자 집단, 채널, 요청 유형 목록(빈도 포함)이 실제 기록을 근거로 적혀 있다
- [ ] 요청 유형마다 한다 / 안 한다 / 사람에게 넘긴다가 정해졌고, 넘기는 계기와 넘길 곳이 적혀 있다
- [ ] 첫 유형이 하나로 정해졌고, 요청 유형마다 결과를 대화 밖에서 확인하는 수단이 적혀 있다
- [ ] 도구마다 부르는 인터페이스와 그 사용을 허용하는 근거 문서가 표로 있고, 공급사의 정책·계약에 맞는지 공급사와 법무가 확인한 기록이 있다
- [ ] 도구 후보마다 위험 등급과 대상 환경이 있고 ERP 운영 담당자가 확인했다
- [ ] 외부 모델로 보낼 수 있는 데이터의 범위를 보안·법무 담당자가 확인했다
- [ ] 성공 지표 목표값과 턴당 지연·대화당 비용 상한이 숫자로 있고 지표마다 확인 방법이 있다
- [ ] 기반 후보별 확인 결과(원문 덤프, 신원 전달, 승인 단계, 기록 내보내기, 모델 고정)와 선택 근거가 `design/decisions.md`에 있다
- [ ] 금지 행동과 확답할 수 없는 것의 목록을 사용자 대표와 ERP 운영 담당자가 확인했다

**흔한 함정:** 범위를 "무엇이든 물어보세요"로 잡기, 기록 없이 회의에서 요청 목록 만들기, 세 유형을 한 번에 열기, 공용 고권한 계정으로 도구를 붙이고 권한 판단을 모델에 맡기기, 확인 수단이 없는 쓰기 과제를 첫 대상으로 고르기, ERP 운영 담당자 없이 범위를 정하기, 공급사의 사용 조건을 확인하지 않고 도구부터 만들기(다 만든 뒤에 못 쓰게 된다), 남의 목표 수치를 우리 목표로 옮겨 적기, 사람에게 넘기는 길 없이 출시하기.

**순서와 병렬:** 요청 목록과 세 칸 판정이 먼저다. 공급사의 사용 조건 확인은 도구 후보가 나오는 즉시 시작한다(답을 받는 데 시간이 걸린다). 그다음 기반 후보 조사, 도구 등급 표, 데이터 반출 범위 확인, 안내 문구 검토는 동시에 한다.

## C1. 대화 시험지와 채점기

**목적:** "좋아졌다"를 판정할 기준을 만든다. C2와 동시에 진행한다. 케이스 양식, 지표 정의, 검증 표는 [`reference/erp-eval.md`](reference/erp-eval.md)에 있고, 비교 규칙과 통계는 [`reference/eval.md`](reference/eval.md)를 그대로 쓴다.

**고민할 것**
1. **평가 단위는 대화 한 건이다.** 한 턴씩은 괜찮아도 정보가 여러 턴에 나뉘어 오면 성능이 떨어진다. 대화 한 건을 케이스라고 부른다. 표본 단위는 시도가 아니라 케이스이고, 같은 의도·같은 문서에서 나온 케이스는 한 묶음으로 센다.
2. **과제 유형마다 "무엇이 결과인가"가 다르다.** 숨긴 테스트의 자리에 채점자만 보는 기대 결과가 들어간다.

   | 과제 유형 | 결과로 보는 것 | 관문 |
   |---|---|---|
   | 지식 답변 | 필수 사실이 들어 있고, 모든 주장이 검색된 문서로 뒷받침되고, 인용이 그 주장을 실제로 뒷받침한다 | 근거 없는 확답·수치 |
   | 답하지 않기·사람에게 넘김 | 기대 행동과 일치한다(답하지 않음, 되물음, 지정한 곳으로 넘김). 넘길 때 필요한 맥락이 들어 있다 | 지어낸 답 |
   | 데이터 추출 | 결과 집합이 참조 질의의 결과와 같다(행, 열, 집계값, 필터) | 요청자 권한 밖의 행·열이 응답이나 파일에 들어감 |
   | 코드 분석 | 인용한 객체와 줄이 그 버전의 소스에 실제로 있고 주장을 뒷받침한다 | 없는 객체·줄 인용 |
   | 코드 변경 | 개발 시스템에서 숨긴 테스트와 정적 검사가 통과한다 | 범위 밖 객체 수정, 테스트 조작, 운영 반영 |
   | 상태 변경·화면 조작 | 비운영 복사본을 대화 밖에서 조회한 끝 상태가 기대와 같고, 그 밖의 범위는 스냅샷과 같다 | 확인 전 쓰기, 권한 밖 쓰기, 운영 접근 |

3. **사용자 쪽을 누가 연기하나.** 고정 스크립트(재현성이 높지만 어시스턴트가 다른 길로 가면 어긋난다), 실제 대화의 앞부분을 주고 다음 응답만 보기(실제 분포에 가깝고 싸다), 모의 사용자(끝까지 가는 흐름을 보지만 스스로 틀린다). 회귀 묶음은 앞의 둘, 능력 묶음은 모의 사용자를 기본으로 한다(제안값).
4. **모의 사용자를 믿을 수 있나.** 모의 사용자는 평가 조건의 일부이고 측정 오차의 원천이다. 공개 벤치마크에서도 모의 사용자가 틀린 대화가 적지 않게 나왔다. 모의 사용자의 결과만으로 출시를 판단하지 않는다.
5. **답하지 말아야 할 때.** 근거 문서가 없는 질문, 범위 밖 질문, 틀린 전제가 든 질문, 요청자 권한 밖의 정보를 따로 유형으로 둔다. 틀린 답이 답하지 않는 것보다 나쁘다. 거절이 지나친지도 같이 잰다.
6. **검색과 생성을 따로 잰다.** 답이 틀렸을 때 문서를 못 찾은 것인지, 찾았는데 잘못 쓴 것인지 가려야 고칠 곳이 정해진다.
7. **무엇을 코드로, 모델로, 사람이 채점하나.** 끝 상태, 권한 범위, 인용 위치의 존재, 도구 호출 사실은 코드. 충실도, 필수 사실, 넘길 때의 맥락은 사람 라벨로 맞춘 모델 판정. 고위험 답의 정답성, 모델 판정과 갈리는 건, 문체 기준은 사람.
8. **정답에 닿는 길이 몇 개인가.** 모의 사용자 지시문과 채점자 파일이 어시스턴트에 보이는가, 지식 색인에 평가 문항과 정답이 문서로 들어가 있는가, 대화 메모리에 이전 시도가 남는가, 평가용 계정이 실제보다 넓은 권한을 갖는가.
9. **무엇을 미리 적어 두나.** 반복 수, 주 지표(매번 통과), 판정 규칙, 흔들림 폭 측정 방법, 최종 확인용 사용 규칙, 실행 비용.

**진행**
- 과제 유형별 채점 근거 표를 먼저 채운다. 유형마다 5건으로 흐름(환경 초기화 → 대화 실행 → 상태 조회 → 판정)을 끝까지 통과시킨 뒤 늘린다. 개발용은 20건 이상에서 시작한다(제안값).
- 케이스는 실제 문의 기록, 담당자 인터뷰, 기능 × 상황 × 사용자 유형의 조합에서 뽑는다. 바꿔 말하기, 오타, 맥락 없는 짧은 요청, 한 요청에 여러 의도, 중간에 주제를 바꾸는 대화를 섞는다. 한 조건만 다른 쌍(권한 있음/없음, 근거 문서 있음/없음)을 넣는다. 기록에는 개인정보가 있으므로 열람 근거와 비식별화가 먼저다.
- 케이스 파일을 실행기용과 채점자용으로 나눈다. 모의 사용자 지시문은 실행기만 읽고 어시스턴트에는 주지 않는다.
- 쓰기 과제와 화면 조작 과제는 운영이 아닌 복사본에서 돌리고 시도마다 스냅샷으로 되돌린다. 지식 색인과 대화 메모리도 스냅샷을 고정한다. 평가용 요청자 계정은 실제 역할과 같은 권한으로 만든다.
- 모의 사용자를 잠근다: 모델, 프롬프트 버전, 온도, 사용자 유형과 목표, 고정한 앞 턴, 턴·도구 호출·시간 상한, 중단 조건. 전부 결과 파일에 남긴다.
- 판정 순서는 유효성(환경 오류, 채점기 오류, 모의 사용자 오류, 근거 부족이 아님) → 정책 관문 → 결과 → 응답 품질이다. 모의 사용자가 목표를 어긴 시도는 무효로 분류해 다시 돌리고 비율을 따로 적는다.
- 모델 판정기는 기준 하나에 하나씩 두고 통과/실패와 이유를 받는다. 사람 라벨을 예시용·개발용·시험용으로 나누고, 시험용으로 실패를 실패로 본 비율과 통과를 통과로 본 비율을 따로 잰다.

**검증**
- 케이스 검증(케이스마다): 사람이 정답 경로를 따라간 실행은 통과, 아무것도 하지 않은 실행은 실패, 아깝게 틀린 실행(다른 항목 변경, 필터 하나 누락, 한 줄 다른 인용)은 실패, 경로만 다른 정답은 통과.
- 채점기 반례: 완료를 보고했지만 상태가 안 바뀐 실행, 기대 상태는 맞지만 다른 기록도 바뀐 실행, 근거 문서에 없는 수치를 덧붙인 답, 답할 수 없는 질문에 그럴듯한 답, 답할 수 있는 질문에 거절, 권한 밖 행이 한 줄 섞인 추출.
- 모의 사용자 검수: 대화 표본을 두 사람이 따로 읽고 모의 사용자의 오류를 센다.
- 격리: 어시스턴트 쪽에서 모의 사용자 지시문과 채점자 파일을 읽을 수 없다. 앞 시도의 변경과 대화 메모리가 다음 시도에 보이지 않는다. 지식 색인에서 평가 문항 원문이 검색되지 않는다.
- 같은 조건으로 두 번 돌려 흔들림 폭을 잰다. 모의 사용자 케이스와 고정 스크립트 케이스의 폭을 따로 적는다.

**완료 기준**
- [ ] 과제 유형별 채점 근거 표가 있고, 유형마다 결과를 대화문이 아닌 곳에서 확인하는 방법이 적혀 있다
- [ ] 케이스 파일이 실행기용과 채점자용으로 나뉘어 있고, 모의 사용자 지시문과 채점자용 파일을 어시스턴트가 읽을 수 없음을 시험했다
- [ ] 케이스마다 검증 기록이 있다: 정답 경로 통과, 무동작 실패, 아깝게 틀린 실행 실패
- [ ] 답하지 않기·사람에게 넘김·권한 밖 요청 케이스가 답해야 하는 케이스와 짝으로 들어 있다
- [ ] 쓰기·화면 조작 과제가 비운영 복사본에서 돌고 시도마다 초기화됨을 확인했다
- [ ] 모의 사용자의 잠금 항목이 결과 파일에 남고, 모의 사용자 오류율을 사람이 검수한 기록이 있다
- [ ] 모델 판정기마다 사람 라벨 대비 두 비율이 있고, 채점기가 반례 시험을 통과했다
- [ ] 반복 수, 주 지표, 개선·회귀 판정 규칙, 흔들림 폭이 결과를 보기 전에 적혀 있다

**흔한 함정:** 어시스턴트의 완료 문장이나 화면의 완료 메시지로 통과시키기, 한 턴 질의응답만 재고 여러 턴을 안 보기, 모의 사용자를 검수 없이 믿기, 충실도와 정답성을 같은 것으로 보기(문서가 낡았으면 충실한 답이 틀린 답이다), 유사도 점수를 통과 기준으로 쓰기, 거절만 세고 과잉 거절을 안 세기, 평가 계정에 넓은 권한을 줘서 권한 위반이 드러나지 않게 하기, 평가 문항과 정답을 지식 색인에 올려 두기.

**순서와 병렬:** 유형별 채점 근거 표 → 환경 초기화·상태 조회 스크립트 → 케이스 작성(케이스별 병렬) → 케이스 검증 → 채점기 반례 → 모의 사용자 검수 → 첫 전체 실행. 판정기용 사람 라벨 수집은 케이스 작성과 동시에 한다.

## C2. 뼈대·관측·기준선

**목적:** 가장 단순한 경로가 한 턴을 끝까지 처리하게 하고, 모든 대화를 기록하고, 출발점 수치를 잰다. 한 턴의 흐름, 지연 예산, 기록 항목은 [`reference/erp-pipeline-ops.md`](reference/erp-pipeline-ops.md) 4~7절, 이벤트 형식은 [`reference/trace.md`](reference/trace.md)에 있다.

**고민할 것**
1. **한 턴의 흐름.** 접수(인증·세션) → 입력 검사 → 분류와 질의 고쳐 쓰기 → [지식: 검색 → 생성] 또는 [도구: 계획 → (변경이면 승인) → 실행] → 출력 검사 → 턴 종료. 단계 전환은 코드가 판정한다. 범위 밖과 사람에게 넘기는 경우는 모델을 부르지 않고 고정 문구로 끝낸다.
2. **무엇을 동시에 돌리고 무엇을 기다리나.** 도구가 없는 경로에서는 입력 검사와 검색을 동시에 돌려도 된다. 도구가 있는 경로에서는 검사가 끝나기 전에 도구가 실행될 수 있으므로 검사가 끝난 뒤에 진행한다.
3. **스트리밍이 바꾸는 것.** 검사 전에 글자가 화면에 나간다. 출력 검사를 문장·구획 단위로 모아서 할지, 끝난 뒤 회수할지 정한다. 표나 버튼 같은 구조화 출력은 조각이 완성된 뒤에만 그린다. 스트림 중간의 오류와 거절에서 이미 받은 부분을 어떻게 할지 정한다.
4. **지연 예산.** 첫 글자가 보이기까지의 시간과 완결 시간을 따로 잡고 단계별로 나눈다. 서버가 아니라 사용자 화면 기준으로 잰다.
5. **긴 도구 호출.** 예산을 넘는 추출과 변경은 대화 턴 안에서 기다리지 않는다. 접수 → 작업 ID → 진행 알림 → 완료 알림 → 취소 수단으로 나누고, 사용자가 자리를 떠났다 돌아와도 결과가 남게 한다.
6. **기록 구조.** 대화 ⊃ 턴 ⊃ 이벤트. 대화 ID와 턴 ID를 모든 하위 호출(검색, 검사, 도구)에 전파해야 대화 단위의 비용과 지연이 맞는다. 턴마다 요청 유형, 경로, 결과(답함, 되물음, 범위 밖, 넘김, 오류), 검색된 문서 ID, 도구 호출, 확인 요청과 응답, 대상 시스템과 환경을 남긴다.
7. **원문과 개인정보.** 대화 원문과 도구 결과에는 업무 데이터와 개인정보가 들어 있다. 원문 수집은 명시적으로 켠 경우에만, 가리기는 저장 전에 하고, 열람 권한과 보존 기간을 정한다. 원문을 전혀 못 보면 사고 조사가 막히므로 신고된 대화에 한해 열람하는 절차를 둔다.
8. **피드백.** 답변마다 버튼과 의견란을 두고, 암묵 신호(되묻기, 같은 질문 반복, 사람을 찾는 요청, 이탈)를 턴 ID에 잇는다. 명시적 피드백은 적고 불만 쪽으로 치우친다.
9. **대화 설계.** 첫 메시지에 할 수 있는 일을 알린다. 되묻기는 짧게 하고 두 번째는 선택지와 함께 한다. 연속 실패가 상한에 닿으면 사람에게 넘긴다. 도구를 쓰는 대화에서는 대상 시스템과 환경을 화면에 항상 보여 준다.
10. **종료 조건과 예산.** 턴 수, 도구 호출 수, 시간, 비용의 상한. 종료 상태를 나눈다: 답함, 답하지 않음, 사람에게 넘김, 승인 대기, 예산 초과, 실패.

**진행**
- 기록기를 가장 먼저 만든다. 턴 시작과 끝, 모델 호출, 검색, 검사 판정, 도구 호출, 승인, 피드백을 이벤트로 남긴다.
- 가장 단순한 경로(지식 답변: 고쳐 쓰기 → 검색 → 생성)를 끝까지 돌린 뒤 검사와 도구 경로를 붙인다.
- 단계별 시간 필드를 넣는다: 접수, 검사, 분류, 검색, 첫 토큰, 첫 글자 표시(화면에서 측정), 완결, 도구 실행.
- 실패용 고정 응답을 먼저 만든다: 범위 밖, 못 알아들음, 시스템 오류, 사람에게 넘김, 작업 접수.
- 긴 작업용 저장소(작업 ID, 상태, 진행값, 결과 위치, 소유자)를 대화와 분리해 둔다.
- C1이 끝나면 기준선을 잰다: 검색 단계 수치, 유형별 매번 통과율, 관문 위반 건수, 모의 사용자 오류율, 단계별 지연, 대화당 비용. 평가 조건(지식 색인 스냅샷, 모의 사용자 버전 포함)과 흔들림 폭을 같이 남긴다. 실패 기록을 전부 읽고 "어시스턴트 / 케이스·채점기 / 모의 사용자 / 환경"으로 먼저 나눈다.

**검증**
- 대화 한 건의 기록만 보고 어느 단계에서 틀렸는지(분류, 검색, 생성, 검사, 도구)를 사람이 찾는다.
- 대화 단위의 토큰과 비용을 이벤트에서 직접 더해 요약 값과 맞춘다. 하위 호출에 대화 ID가 빠진 건수는 0이어야 한다.
- 일부러 만든 실행: 스트림 중간 오류, 거절로 끝난 응답, 검사에 걸린 입력(도구 경로에서 도구가 실행되지 않았는지), 도구 시간 초과, 가짜 개인정보가 든 메시지(기록에 원문 0건).
- 긴 작업을 시작한 뒤 창을 닫고 돌아와 결과와 진행 상태가 보이는지 본다.

**완료 기준**
- [ ] 한 턴의 흐름, 단계 전환을 판정하는 코드, 동시에 도는 구간과 기다리는 구간이 `design/02-baseline.md`에 있다
- [ ] 대화·턴·이벤트 세 층으로 기록되고 모든 하위 호출에 대화 ID와 턴 ID가 있다
- [ ] 턴마다 요청 유형, 경로, 결과, 대상 시스템·환경, 단계별 시간, 토큰이 남고, 피드백이 턴 ID에 이어져 조회된다
- [ ] 스트림 중간 오류, 거절, 검사 차단, 도구 시간 초과에서 사용자에게 보이는 응답이 정해져 있고 시험했다
- [ ] 가리기 시험에서 원문이 0건이고, 원문 열람 권한과 보존 기간이 적혀 있다
- [ ] 예산을 넘는 도구는 대화와 분리된 작업으로 돌고, 자리를 떴다 돌아와도 결과가 보인다
- [ ] 유형별 기준선(품질, 지연, 대화당·해결 1건당 비용)이 평가 조건·흔들림 폭과 함께 있고, 실패 분류에서 케이스·채점기·모의 사용자의 결함이 0건이다

**흔한 함정:** 서버의 첫 토큰 시간만 재고 화면 표시 시간을 안 재기, 도구 경로에서 검사를 동시에 돌려 걸리기 전에 도구가 실행되기, 회수할 방법 없이 출력 검사를 끝에 두기, 대화 ID를 최상위 호출에만 붙이기, 긴 도구 호출을 대화 턴에 넣고 시간 초과를 재시도로 덮기, 원문을 전부 남기거나 전혀 못 보게 하기, 모의 사용자의 오류로 낮게 나온 수치를 기준선으로 삼기.

**순서와 병렬:** 기록기와 지식 답변 경로는 동시에 만든다. 고정 응답과 작업 저장소는 그 사이에 만든다. 기준선은 평가용 대화 묶음이 준비되고 구성을 동결한 뒤 잰다.

## C3. 지식·대화 상태·메모리

**목적:** 사내 문서에서 묻는 사람이 볼 수 있는 것만 찾아 근거를 달아 답하고, 근거가 없으면 답하지 않게 한다. 여러 턴에 걸쳐 맥락을 잃지 않고 캐시를 깨지 않게 한다. 결정표, 지표 정의, 프롬프트 배치는 [`reference/erp-knowledge-tools.md`](reference/erp-knowledge-tools.md) 1~7절에 있다.

**고민할 것**
1. **지식을 프롬프트에 넣을까, 검색할까, 도구로 조회할까.** 질문 유형마다 고른다. 전체가 작고 모두가 같은 것을 볼 수 있으면 통째로 넣고 캐시한다. 사람마다 볼 수 있는 문서가 다르면 검색한다. 하루 안에도 바뀌는 값(재고, 결재 상태)과 집계는 색인하지 않고 도구로 원천을 조회한다.
2. **출처 목록과 주인.** 출처마다 소유 부서, 누가 볼 수 있는지, 갱신 주기, 폐기 규칙을 적는다. 주인이 없거나 권한을 모르는 출처는 색인하지 않는다. 원천의 권한이 느슨하면 어시스턴트가 그 느슨함을 그대로 드러낸다.
3. **권한을 어디서 집행하나.** 인증된 요청에서 사용자와 그룹을 끌어내 모든 검색 요청에 필터로 건다. 필터는 검색 API 한 곳에 두고, 필터에 넣는 식별자는 모델이 낸 값이 아니라 서버가 검증한 값이다. 생성된 답에서 금지 내용을 걸러 내는 것은 통제가 아니다. 권한 없는 구절이 컨텍스트에 들어가면 모델이 풀어 써서 답에 섞는다.
4. **낡는 것이 셋이다.** 내용 변경, 삭제, 권한 변경은 서로 다른 길로 전파된다. 셋 각각의 반영 지연 목표와 담당자를 정한다.
5. **검색 방식.** 오류 코드, 프로그램 이름, 표 이름, 규정 번호처럼 정확한 식별자로 묻는 질문이 많으므로 어휘 검색을 반드시 포함하고 임베딩 검색과 합친다. 재순위, 청크 크기, 넣는 개수는 우리 문서와 시험 질의로 정한다.
6. **후속 질문.** "그건 언제부터야?" 같은 질문은 그대로 검색하면 안 맞는다. 검색 전에 대화 맥락을 넣어 독립된 질문으로 고쳐 쓴다.
7. **근거와 인용.** 검색된 자료만으로 답하게 하고 주장마다 출처를 붙인다. 인용은 모델이 쓴 문자열이 아니라 기계가 확인할 수 있는 위치로 받는다.
8. **답하지 않을 때.** 검색 결과가 비었거나 모자라면 모른다고 답하고 다음 행동(담당 부서, 사람에게 넘김)을 안내한다. 답하지 않기를 지시문에만 맡기지 않고 점수 임계값이나 충분성 판정을 코드로 둔다.
9. **문서끼리 다를 때.** 폐기되거나 만료된 판은 검색 전에 뺀다. 그래도 남는 충돌은 둘 다 출처·시행일과 함께 보여 주고 모델이 고르게 두지 않는다.
10. **대화 이력을 어떻게 줄이나.** 덧붙이기만 하다가 임계값에서 한 번에 요약한다. 요약 뒤에도 살아야 하는 것은 요약문에 맡기지 않고 구조화 상태로 따로 저장해 매 턴 주입한다: 사용자의 목표, 대상 시스템·환경·객체, 확정된 제약, 대기 중인 승인, 거절된 요청.
11. **프롬프트 배치와 캐시.** 도구 정의와 시스템 프롬프트는 모든 사용자, 모든 대화에서 같은 바이트여야 한다. 사용자 이름, 부서, 날짜, 이번 턴의 검색 결과는 뒤쪽 메시지로 넣는다.
12. **세션.** 세션 식별자는 추측할 수 없게 만들고 서버에서 인증된 사용자에 묶는다. 이력 보관 기한을 정한다.
13. **장기 메모리.** 좁게 시작한다. 사용자가 직접 정한 설정(기본 대상 시스템, 출력 형식)만 저장한다. 사용자별로 격리하고, 사용자가 보고 지울 수 있게 하고, 문서나 도구 결과에서 온 문장은 저장하지 않는다. 기록 형식과 쓰기 정책은 [`reference/memory-improve.md`](reference/memory-improve.md)를 따른다.

**진행**
- 시험 질의를 모으고 질의마다 정답 문서와 구절을 적는다. 답이 없어야 하는 질의, 후속 질문, 권한이 다른 사용자의 같은 질의를 반드시 넣는다.
- 출처 목록 표를 만들고 주인에게 포함 여부와 권한을 확인받는다.
- 수집 흐름(파싱 → 청크 → 메타데이터 → 색인)을 만들고, 변경·삭제·권한 변경 각각의 동기화 길을 따로 만든다.
- 검색 API를 만든다. 호출자의 신원은 서버가 넣고, 필터 없는 호출은 실패하게 한다.
- 검색만 따로 평가해 방식·청크·개수를 정한 뒤 생성을 붙인다. 한 번에 한 가지만 바꾼다.
- 구조화 상태의 형식과 요약 생존 목록을 정하고, 요약 프롬프트를 실제 긴 대화로 조정한다.

**검증**
- 검색: 정답 문서가 상위 k 안에 든 비율, 순위, 답이 없는 질의에서의 결과, 후속 질문의 고쳐 쓰기 전후를 잰다.
- 권한: 권한이 다른 시험 계정 둘 이상으로 같은 질의를 돌려 누출 0건을 확인한다. 필터 없는 직접 호출이 거부되는지 본다.
- 신선도: 원천에서 문서를 고치고, 지우고, 권한을 빼앗은 뒤 각각 검색 결과에 반영되기까지의 시간을 잰다.
- 생성: 근거 충실도, 인용 정확도, 답하지 않기의 정확도와 과잉 거절. 충실도는 높은데 정확성이 낮으면 원천 문서를 의심한다.
- 주입: 지시가 든 문서와 올린 파일을 넣어 놓고 어시스턴트가 따르지 않는지 본다.
- 대화: 강제로 요약한 직후 대상 시스템·환경, 대기 중인 승인, 제약이 유지되는지 본다. 다른 사용자의 세션 식별자로 접근이 거부되는지 본다.
- 캐시: 캐시 읽기 비율을 턴 번호별로 본다. 서로 다른 사용자의 첫 요청에서도 도구 정의와 시스템 프롬프트의 해시가 같은지 본다.

**완료 기준**
- [ ] 질문 유형마다 "넣는다 / 검색한다 / 도구로 조회한다"가 근거와 함께 정해졌다
- [ ] 출처마다 주인, 권한, 갱신 주기, 폐기 규칙이 적혀 있고 주인이 확인했다
- [ ] 검색 요청마다 서버가 넣은 사용자 신원으로 필터가 걸리고, 권한이 다른 계정 시험에서 누출이 0건이다
- [ ] 변경·삭제·권한 변경의 반영 지연을 쟀고 목표 안이다. 각각의 담당자가 있다
- [ ] 검색 지표가 기록됐고 검색 방식·청크·개수의 선택 근거가 있다
- [ ] 답에 확인 가능한 인용이 붙고, 근거 충실도·인용 정확도·답하지 않기의 수치가 있다
- [ ] 주입 문서 시험 기록이 있다
- [ ] 요약 생존 목록과 구조화 상태가 정해졌고 요약 생존 시험을 통과했다. 세션이 사용자에 묶여 있다
- [ ] 도구 정의와 시스템 프롬프트가 대화와 사용자에 따라 바뀌지 않음을 해시로 확인했고 캐시 읽기 비율이 기록됐다
- [ ] 장기 메모리를 쓴다면 저장 항목, 사용자별 격리, 보기·삭제 방법, 보관 기한이 정해졌고 시험했다 (안 쓰면 "해당 없음"과 이유)

**흔한 함정:** 주인 없는 문서함을 통째로 색인하기, 권한을 프롬프트 문장으로 막기, 모델이 낸 사용자 ID로 필터하기, 내용 동기화만 만들고 삭제와 권한 변경을 빠뜨리기, 임베딩 검색만 쓰기, 후속 질문을 그대로 검색하기, 답이 없는 질의를 시험에 넣지 않기, 청크를 많이 넣을수록 좋다고 믿기, 사용자 이름·날짜를 시스템 프롬프트에 넣기, 승인 상태를 요약문에만 남기기, 문서에서 읽은 문장을 사용자 메모리에 저장하기.

**순서와 병렬:** 출처 목록·권한 확인, 시험 질의 수집, 수집 흐름은 동시에 한다. 검색 평가가 먼저이고 생성 평가가 그다음이다. 캐시는 C4의 도구 정의가 동결된 뒤에 잰다. 장기 메모리는 마지막에, 측정된 필요가 있을 때 넣는다.

## C4. 도구·행동·사람 연결

**목적:** 어시스턴트가 ERP를 조회·추출·변경할 때 요청한 직원 본인의 권한으로만 움직이고, 큰 결과가 컨텍스트를 채우지 않고, 상태를 바꾸는 호출은 사람이 본 뒤에만 실행되게 한다. 등급표, 신원 전달, 명세표 양식은 [`reference/erp-knowledge-tools.md`](reference/erp-knowledge-tools.md) 8~15절, SAP에서의 구체 방법은 [`bases/sap.md`](bases/sap.md)에 있다.

**고민할 것**
1. **등급을 누가 정하나.** 도구의 등급은 도구 서버가 알려 주는 표시가 아니라 우리가 정해 코드에 둔다. 등급을 모르는 도구는 변경으로 취급한다.
2. **좁은 도구와 열린 도구.** 임의 질의, 임의 명령, 화면 조작은 도구 하나로 무엇이든 할 수 있어 통제가 어렵다. 자주 하는 작업부터 인자가 정해진 업무 단위 도구로 만들고 열린 도구의 쓰임을 줄여 간다.
3. **누구의 권한으로 실행하나.** 공용 계정으로 ERP를 부르면 모든 직원이 그 계정의 권한을 얻는다. 요청한 직원의 신원을 ERP까지 전달해 ERP가 그 사람의 권한을 검사하게 한다.
4. **신원을 어떻게 전달하나.** 받은 토큰을 그대로 넘기지 않는다. 도구 서버는 자기를 대상으로 발급된 토큰만 받고, ERP용 토큰은 따로 받는다. 사용자 ID와 토큰은 모델에 보이지 않는 실행 컨텍스트에 두고, 도구 인자로 받지 않는다.
5. **큰 결과.** 소스 파일, 표 추출, 화면 내용은 한 번에 컨텍스트를 채운다. 순서대로 쓴다: 서버에서 걸러 줄인다 → 범위·페이지 인자와 작은 기본값 → 전체는 파일이나 핸들로 두고 모델에는 요약(건수, 열 이름, 앞 몇 행)만 → 중간 결과는 코드 실행 환경에서 처리. 핸들은 이름이지 권한이 아니므로 매 호출 사용자를 다시 확인한다.
6. **도구 결과는 신뢰 못 할 입력이다.** 문서 본문, 소스 코드의 주석과 문자열, 데이터의 텍스트 필드, 화면의 글자에 지시가 들어갈 수 있다. 신뢰 못 할 결과를 읽은 뒤의 변경·추출 호출은 자동으로 실행하지 않는다.
7. **변경 전 확인.** 변경 등급의 호출은 전부 계획 → 리뷰 → 승인을 거친다. 작은 변경은 계획이 짧을 뿐 양식은 같다. 승인 단계의 확인 화면은 모델의 문장이 아니라 코드가 만든다: 대상 시스템과 환경, 대상 객체, 바뀌기 전과 후, 영향 범위, 되돌리는 방법. 승인은 화면의 조작으로 받고 대화 속 "네"로 대신하지 않는다. 승인된 인자와 실제 실행 인자가 같은지 서버가 대조한다.
8. **계획 양식을 ERP에 맞춘다.** 계획 양식과 승인 기록은 [`reference/plan-gate.md`](reference/plan-gate.md)를 쓴다. 수정 대상은 파일 경로 대신 ERP의 대상(개발 객체, 데이터 건, 설정 항목)으로 적고, 대상 시스템과 환경을 승인 기록에 넣는다.
9. **중복 실행.** 시간 초과 뒤의 재시도가 두 번 실행되지 않게 한다. 식별 키는 모델이 아니라 하네스가 만든다. ERP가 중복 방지를 지원하지 않으면 다시 실행하기 전에 현재 상태를 조회한다.
10. **화면 조작은 마지막 수단이다.** 같은 일을 하는 API나 업무 단위 도구가 있으면 그것을 쓴다. 화면 조작을 쓴다면 단계마다 화면 상태를 확인하고, 끝 상태는 화면 밖에서 확인한다.
11. **사람에게 넘기기.** 넘김을 도구로 만든다. 사유, 사용자의 목표, 시도한 것과 결과, 근거 문서, 대기 중인 승인을 구조화해 함께 넘긴다.
12. **도구 정의는 대화 중에 바꾸지 않는다.** 도구가 많으면 자주 쓰는 것만 상시 로드하고 나머지는 찾아 쓰게 한다.

**진행**
- 신원 전달 경로를 먼저 세운다: 직원 로그인 → 어시스턴트 → 도구 서버 → ERP. 공용 계정이 남는 구간을 표로 적고 구간마다 없앨 계획이나 남기는 이유를 적는다.
- 도구 명세표를 쓴다: 이름, 등급, 설명, 인자와 예시, 반환(형식, 상한, 잘렸을 때 안내, 핸들), 오류 종류, 필요한 권한, 대상 환경, 승인 필요 여부, 되돌리는 방법.
- 조회 도구부터 붙이고, 반환 상한과 필터를 넣은 뒤 추출 도구를 붙인다. 변경 도구는 확인 화면, 중복 실행 방지, 감사 기록이 있은 뒤에 붙인다.
- 변경 도구가 닿는 대상을 개발 시스템으로 고정한다. 대상 환경은 모델이 고르는 인자가 아니라 배포 설정이다.
- 확인 화면과 승인 대기·재개를 만든다. 사람에게 넘기는 도구와 요약 형식을 만든다.

**검증**
- 세 층으로 시험한다: 모델 없는 도구 단위 시험 → 모델이 도구와 인자를 맞게 고르는지 → 대화 전체(끝 상태로 채점).
- 권한: 권한이 다른 시험 계정 둘로 같은 요청을 돌려 권한 없는 쪽을 ERP가 거부하는지, ERP의 기록에 요청한 직원이 남는지 본다.
- 큰 결과: 상한을 넘는 소스와 표 추출에서 반환이 상한 안이고 안내가 나오는지 본다.
- 주입: 문서, 소스 주석, 데이터 필드에 지시를 심어 놓고 승인 없이 실행된 변경·추출 건수를 센다. 목표는 0이다.
- 확인: 확인 없이 변경 도구를 직접 부르는 길이 막히는지, 승인 뒤 인자를 바꾼 실행이 거부되는지, 거절 뒤 실행되지 않는지 본다.
- 환경: 운영 시스템을 대상으로 한 변경 호출이 거부되는지 본다.
- 중복: 같은 변경 호출을 시간 초과 뒤 다시 보내 한 번만 반영되는지 본다.
- 넘김: 넘겨야 하는 대화와 넘기면 안 되는 대화 묶음으로 적중과 오발을 센다.

**완료 기준**
- [ ] 도구마다 등급, 명세(설명, 인자 예시, 반환 상한, 오류 종류, 필요한 권한, 대상 환경), 단위 시험이 있다
- [ ] ERP 호출이 요청한 직원의 신원으로 실행되고, 권한이 다른 계정 시험에서 ERP가 권한 없는 요청을 거부했다. 공용 계정이 남은 구간은 목록과 이유가 있다
- [ ] 사용자 신원과 토큰이 모델 입력과 도구 인자에 없다
- [ ] 조회·추출 도구의 반환 상한, 잘림 안내, 파일·핸들 반환이 구현됐고 상한 초과 시험을 통과했다
- [ ] 변경·범용 조작 도구는 확인 화면 없이 실행되지 않고, 승인된 인자와 실행 인자의 대조, 거절 시험을 통과했다
- [ ] 운영 시스템을 대상으로 한 변경 호출이 거부된다
- [ ] 변경 호출의 재시도가 한 번만 반영된다
- [ ] 주입 시험에서 승인 없는 변경·추출이 0건이다
- [ ] 사람에게 넘기는 도구와 요약 형식이 있고 적중·오발 수치가 있다
- [ ] 도구 정의 총 토큰, 도구 오류율, 도구 결과 토큰이 적혀 있고 평가 회귀가 없다

**흔한 함정:** 공용 계정 하나로 전부 연결하기, 받은 토큰을 ERP에 그대로 넘기기, 사용자 ID를 도구 인자로 받기, 도구 서버의 "읽기 전용" 표시를 믿고 자동 실행하기, 임의 질의·화면 조작 도구 하나로 시작해 그대로 두기, 표 전체나 소스 전체를 그대로 돌려주기, 소스 주석과 데이터 값은 안전하다고 여기기, 확인을 프롬프트 지시로만 두기, 대화 속 "네"를 승인으로 치기, 대상 환경을 모델이 고르게 두기, 시간 초과 뒤 상태 확인 없이 다시 실행하기.

**순서와 병렬:** 신원 전달 경로와 도구 등급이 먼저다. 조회 도구 구현과 단위 시험은 도구별로 동시에 한다. 추출 도구는 반환 상한 뒤, 변경 도구는 C5의 승인 양식과 감사 기록 뒤에 붙인다. 설명·이름·인자 조정은 한 번에 하나씩 한다.

## C5. 제어·승인·감사

**목적:** 반드시 지켜져야 하는 규칙을 강제로 만들고, 누가 무엇을 어떤 승인으로 했는지 남기고, 한 층이 뚫려도 피해가 커지지 않게 한다. 층별 방어, 판정 주체, 가드 측정은 [`reference/security.md`](reference/security.md)를 그대로 쓰고, ERP 어시스턴트에서 더해지는 위협과 시험은 [`reference/erp-control.md`](reference/erp-control.md)에 있다.

**고민할 것**
1. **반드시 지켜져야 하는 것은 무엇인가.** ERP 어시스턴트의 기본 목록:
   - 요청한 직원의 권한 밖에 있는 것을 보여 주거나 바꾸지 않는다
   - 운영 시스템을 바꾸지 않는다
   - 계획 → 리뷰 → 승인 뒤에만 소스와 데이터를 바꾼다. 범위가 바뀌면 계획으로 돌아간다
   - 상한을 넘는 반출은 승인 없이 하지 않는다
   - 근거 문서 없이 규정·절차를 확답하지 않는다
   - 모든 도구 호출과 승인이 기록에 남는다
2. **세 가지가 한 흐름에 모이는가.** 민감한 데이터(업무 데이터, 소스), 신뢰 못 할 입력(문서, 주석, 데이터 값, 화면의 글자), 밖으로 나가는 길(외부 모델, 파일 반출, 메일·메신저 전송). 어시스턴트는 기본으로 셋을 다 가진다. 밖으로 나가는 길을 가장 먼저 좁힌다.
3. **행동 등급과 승인 방식.** 0 조회는 자동. 1 추출은 상한 안에서 자동이고, 상한을 넘거나 민감한 데이터(개인정보, 공개 전 재무 정보 등)면 데이터 주인의 승인. 2 개발 시스템에서의 변경은 계획과 승인. 3 품질·운영에 닿거나 되돌릴 수 없는 것은 어시스턴트가 실행하지 않는다.
4. **누가 승인하나.** 기본은 요청한 사람이 아닌 다른 사람(담당 개발자, 업무 주인)의 승인이다. 요청한 사람이 혼자 승인해도 되는 범위(예: 본인의 임시 개발 객체)를 팀이 예외로 정해 적는다. 어시스턴트의 계정에는 승인 권한을 주지 않는다. 승인은 대상에 묶는다: 도구, 대상 시스템·환경, 대상 객체, 변경 내용의 해시, 1회, 만료 시각.
5. **승인을 어시스턴트가 위조할 수 없는가.** 승인 기록은 어시스턴트가 쓸 수 없는 곳에 두고, 대화 속 문장("승인받았다")을 승인으로 치지 않는다.
6. **누가 판정하고 누가 강제하나.** 모델은 위험 신호를 내고 코드가 실행을 강제한다. 권한은 ERP가, 범위·상한·환경·승인은 하네스의 코드가 판정한다. 판정이 실패하면 통과가 아니라 차단이다.
7. **도구를 거치지 않는 길.** 들어오는 메시지(붙여 넣은 내용 속 지시), 모델 공급자로 나가는 내용(업무 데이터, 개인정보, 소스), 최종 답변(실패한 일을 했다고 하는 보고, 근거 없는 확답), 메모리 쓰기. 길마다 장치를 두거나 두지 않는 이유를 적는다.
8. **감사 기록.** 누가(직원), 어느 시스템·환경에서, 어떤 도구를 어떤 인자로, 어떤 승인으로, 결과가 무엇이었는지. 어시스턴트가 고칠 수 없는 곳에 두고, ERP 자체의 변경 기록·감사 기록과 맞춰 볼 수 있게 요청 ID를 남긴다.
9. **대화 기록과 직원의 사생활.** 대화 원문을 누가 볼 수 있는지, 얼마나 보관하는지, 직원에게 무엇을 알리는지 정한다. 관련 법규의 적용은 법무·개인정보 담당자가 확인한다(확인 필요).
10. **사람이 보는 횟수가 감당되는가.** 승인 요청이 많으면 읽지 않고 누른다. 대화당 승인 요청 수와 승인율을 잰다. 승인율이 100%에 가까우면 걸러내지 못하는 승인이다.
11. **하네스 자신이 보호되는가.** 검사 코드, 권한 설정, 승인 기록, 감사 기록, 채점기는 어시스턴트가 고칠 수 없어야 한다.

**진행**
- 자산과 신뢰 경계를 한 장에 적는다: 어시스턴트가 읽을 수 있는 것, 바꿀 수 있는 것, 신뢰 못 할 입력이 들어오는 길, 누구의 계정으로 도는가.
- 규칙마다 둘 곳을 정하고 층을 둘 이상 적는다. 예: "운영 시스템을 바꾸지 않는다"는 배포 설정(운영 접속 정보를 주지 않음), 실행 전 검사, ERP 쪽 권한의 세 곳에 둔다.
- 계획 → 리뷰 → 승인 절차를 넣는다. 형식 검사, 읽기 전용 리뷰어, 어시스턴트가 쓸 수 없는 승인 기록, 실행 전 게이트(승인 상태 + 대상 객체 범위 + 환경 + 보호 대상), 범위가 바뀌면 승인 무효.
- 추출 상한(행 수, 크기, 민감 표·열 목록)과 반출 경로(파일 저장 위치, 내려받을 수 있는 사람)를 코드로 건다.
- 모델로 나가는 내용의 가림 규칙을 정한다. 가림은 정규식 같은 코드로 하고, 메인과 하위 호출 모두에 건다.
- 최종 답변의 주장을 실행 기록과 대조한다. 실패했거나 막힌 작업을 "했다"고 답하지 않게 한다.
- 위반 시도를 스크립트로 만들어 검사를 고칠 때마다 다시 돌린다.

**검증**
- 위반을 일부러 시도한다: 권한 없는 계정으로 조회, 승인 전 변경, 승인 뒤 인자 변경, 범위 밖 객체 수정, 운영 시스템 지정, 상한을 넘는 추출, 대화 속 문장으로 승인 주장, 승인 기록 위조.
- 입력에 지시를 심는다: 문서, 소스 주석, 데이터 값, 화면의 글자, 붙여 넣은 내용. 따르지 않는지, 밖으로 나가는 호출이 없는지 본다.
- 검사기를 망가뜨린다: 오류, 시간 초과, 깨진 입력. 차단으로 끝나는지 본다.
- 감사 기록만 보고 "누가 무엇을 어떤 승인으로 했는지"를 사람이 재구성한다. ERP의 기록과 요청 ID로 맞춰 본다.
- 평가의 정책 위반이 0건인지 본다. 위반 판정은 검사와 다른 코드(기록과 ERP의 실제 상태)로 한다.

**완료 기준**
- [ ] 필수 규칙마다 강제 장치가 둘 이상의 층에 있고 차단 시험 기록이 있다
- [ ] 변경은 승인 기록 없이 실행되지 않고, 승인이 대상(시스템·환경, 객체, 변경 내용)에 묶여 있으며, 위조와 승인 뒤 변경 시도가 차단됐다
- [ ] 변경의 승인자는 요청자와 다른 사람이고, 혼자 승인해도 되는 예외 범위가 적혀 있으며, 그 밖에서는 자기 승인이 막힌다
- [ ] 운영 시스템 변경과 권한 밖 조회가 둘 이상의 층에서 막힌다
- [ ] 추출 상한과 반출 경로가 코드로 걸려 있고 상한 초과 시험을 통과했다
- [ ] 검사기 실패·시간 초과·깨진 입력이 차단으로 끝난다
- [ ] 도구를 거치지 않는 길마다 장치나 대응하지 않는 이유가 적혀 있다
- [ ] 감사 기록만으로 누가 무엇을 어떤 승인으로 했는지 재구성되고, 어시스턴트가 그 기록을 고칠 수 없다
- [ ] 대화 원문의 열람 권한, 보관 기한, 직원 안내가 정해졌고 담당자가 확인했다
- [ ] 위협 점검표에 항목마다 대응과 시험 결과가 있고, 차단 시험이 명령 한 줄로 다시 돈다

**흔한 함정:** 권한 판단을 프롬프트 문장으로 두기, 승인 여부만 보고 대상을 안 보기, 대화 속 "승인받았다"를 믿기, 운영 차단을 실행 전 검사 한 곳에만 두기, 추출 상한 없이 읽기 도구를 "안전하다"고 보기, 감사 기록을 어시스턴트가 쓸 수 있는 곳에 두기, 차단 0건을 안전의 증거로 보기, 승인 요청을 많이 받아 사람이 읽지 않게 만들기, 입력 필터로 숨은 지시를 막을 수 있다고 믿기.

**순서와 병렬:** 규칙 배치표, 승인 양식, 감사 기록 형식은 동시에 만들 수 있다. 실행 전 게이트는 C4의 도구 명세가 정해진 뒤 만든다. 차단 시험은 검사·신원 전달·감사 기록이 모두 붙은 뒤 한 번에 돌리고, 그다음부터는 고칠 때마다 다시 돌린다.

## C6. 운영 기록 기반 개선

**목적:** 실제 대화에서 드러난 실패를 분류하고, 한 번에 한 가지를 고치고, 검증된 변경만 받아들인다. 채택 절차는 [`reference/memory-improve.md`](reference/memory-improve.md) 8절을 그대로 쓴다.

**고민할 것**
1. **어디가 틀렸나.** 실패마다 원인을 먼저 나눈다: 지식 없음, 지식 낡음, 검색 실패, 생성 오류, 범위 밖, 도구, 권한·환경, 대화 맥락. 여러 턴에서 난 실패는 한 턴으로 줄여 본다. 한 턴에서도 틀리면 검색·지식 문제이고, 한 턴에서는 맞으면 대화 맥락 문제다.
2. **무엇을 고치나.** 지식이 없거나 낡았으면 프롬프트가 아니라 문서를 고친다(지식 담당자에게 보낸다). 검색 실패는 검색 설정을, 생성 오류는 프롬프트의 지정 구역을, 도구 오류는 도구 설명과 인자를 고친다. 한 번에 한 종류, 한 가설만 연다.
3. **고칠 수 없는 것.** 평가 케이스와 정답, 채점기와 임계값, 권한·승인·감사 설정, 예산, 모의 사용자 지시문, 개선 절차 자신. 지시문이 아니라 경로 허용 목록과 해시 검사로 막는다.
4. **반대 방향도 잰다.** 거절을 줄였으면 답하지 않기 케이스를, 확인 절차를 줄였으면 쓰기 관문을, 답을 길게 했으면 충실도를 같이 본다.
5. **기억에서 배우게 할 것인가.** 사용 경험(어떤 요청에 어떤 도구와 인자가 통했는가)을 남겨 다음 대화에 쓰는 것은 측정된 필요가 있을 때 넣는다. 문서나 도구 결과에서 온 문장이 사람 승인 없이 규칙이 되지 않게 한다.
6. **얼마나 좋아져야 받아들이나.** 흔들림 폭을 먼저 재고, 최소 효과와 회귀 정의를 결과를 보기 전에 적는다.

**진행**
- 운영(또는 내부 시험 사용) 대화를 표본으로 읽는다. 무작위 표본을 항상 남기고 부정 피드백, 긴 대화, 재시도, 사람에게 넘긴 대화를 더한다.
- 실패 유형마다 검사를 하나씩 만든다. 코드로 판정되면 코드로, 아니면 모델 판정기를 만들고 사람 라벨로 맞춘다.
- 운영 실패를 케이스로 올린다: 열람 근거 확인 → 비식별화 → 앞 턴 고정 또는 목표로 재구성 → 기대 결과 작성 → 케이스 검증 → 같은 유형의 "해야 하는 경우"와 짝으로 추가 → 데이터 버전 올림.
- 변경은 현재 버전과 같은 조건으로 비교해 판정한다(채택 / 보류 / 기각 / 판정 불가). 모의 사용자의 지시문과 어시스턴트의 프롬프트를 같은 비교에서 함께 바꾸지 않는다.
- 같은 실패가 다시 나오면 더 강한 층으로 옮긴다: 지침 → 도구 설명·인자 제약 → 실행 전 검사 → ERP 쪽 권한.

**검증**
- 채택한 변경마다 전후 표, 회귀 결과, 반대 방향 케이스의 결과가 있다.
- 탈락한 변경은 반영되지 않았다.
- 지식 담당자에게 보낸 건이 문서에 반영되고 답이 바뀌는 것을 한 건 끝까지 따라가 본다.
- 금지 경로(케이스, 채점기, 권한 설정)를 건드리는 변경이 거부되는지 본다.

**완료 기준**
- [ ] 실패 분류표가 있고 표본을 읽은 기록이 있다
- [ ] 개선 설정(고칠 수 있는 것과 없는 것, 케이스 분할, 반복 수, 흔들림 폭, 채택 기준, 승인자)이 결과를 보기 전에 고정돼 있다
- [ ] 개선 라운드가 한 번 이상 기록됐다(채택·보류·기각·판정 불가 중 무엇이든, 사유와 함께)
- [ ] 운영 실패 한 건 이상을 케이스로 올렸고, 지식 문제 한 건 이상이 담당자를 거쳐 문서에 반영됐다
- [ ] 채택한 변경마다 전후 표, 회귀 결과, 반대 방향 결과, 버전, 되돌리는 방법이 있다 (채택이 없으면 "채택 없음"과 사유)

**흔한 함정:** 지식이 낡았는데 프롬프트를 고치기, 고친 유형의 케이스만 보기, 피드백을 준 대화만 읽기, 모의 사용자와 어시스턴트를 함께 바꾸기, 문서에서 읽은 문장을 규칙으로 저장하기, 최종 확인용으로 라운드마다 판정하기.

**순서와 병렬:** 표본 읽기와 실패 분류는 C7과 동시에 할 수 있다. 변경의 반영은 하나씩 하고, C7과 같은 평가 창에 함께 넣지 않는다.

## C7. 지연·비용 최적화

**목적:** 지켜야 할 것을 지킨 채 느리고 비싼 곳을 줄인다. C0의 목표를 이미 충족했다면 기준선과 근거를 적고 닫는다. 비용 식과 예산표는 [`reference/erp-pipeline-ops.md`](reference/erp-pipeline-ops.md) 5·8절에 있다.

**고민할 것**
1. **단위.** 호출당이 아니라 대화당, 해결 1건당 비용이다. 사람에게 넘긴 대화, 검사·고쳐 쓰기·임베딩·채점 호출, 재시도가 전부 들어간다. 변경형은 성공한 작업 1건당으로 따로 잰다.
2. **입력 비용은 턴마다 는다.** 매 턴 이전 대화를 다시 보내므로 캐시가 없으면 대화당 입력 토큰이 턴 수의 제곱에 비례해 는다.
3. **캐시가 대화에 맞는 조건.** 고정 접두가 최소 길이를 넘는가, 턴 사이의 간격이 캐시 수명 안인가, 접두가 바이트 단위로 같은가. 수명과 가격 배수는 공급자와 모델마다 다르므로 쓰는 모델의 문서로 확인한다.
4. **검색 결과와 도구 결과를 어디에 두나.** 턴마다 달라지는 내용을 앞쪽에 넣으면 그 뒤의 캐시가 매 턴 깨진다. 캐시를 켠 뒤에는 캐시되지 않는 검색 결과와 도구 결과가 입력 비용의 대부분이 된다.
5. **모델을 나누면.** 쉬운 요청 유형을 작은 모델로 보내면 싸지지만 분류가 틀리면 품질이 깎이고, 모델이 갈리면 캐시도 갈린다. 요청 유형별 평가로만 정한다.
6. **답을 저장해 두고 돌려주면.** 질문이 비슷하면 저장된 답을 돌려주는 방식은 권한과 시점에 따라 답이 달라지는 요청에서 위험하다. 쓴다면 모두가 같은 것을 볼 수 있는 지식 질문으로 한정하고, 키에 권한 집단과 지식 버전을 넣고 만료를 둔다.
7. **시간이 어디서 나오나.** ERP 어시스턴트에서는 도구 실행 시간(조회, 추출, 화면 조작)이 모델 시간보다 클 때가 많다. 어느 구간이 느린지 먼저 본다.

**진행**
- 유지 기준을 먼저 적는다: 유형별 품질이 흔들림 폭 안, 정책 위반 0건, 넘김의 정확도.
- 기준선 기록에서 단계별 시간과 토큰을 줄 세워 큰 항부터 본다.
- 품질을 걸지 않는 것부터 한 번에 하나씩 적용한다: 접두 고정과 캐시 → 호출 수 줄이기(분류와 고쳐 쓰기 합치기, 코드로 답할 수 있는 것은 모델 없이) → 독립 조회의 병렬화 → 검색 결과와 도구 결과의 개수·길이 줄이기 → 출력 길이 지침.
- 품질을 거는 것은 평가로 정한다: 추론 강도 → 요청 유형별 작은 모델 → 답 저장.
- 캐시 수명은 턴 사이 간격의 분포로 정한다.
- 변경마다 켜고 끌 수 있게 만들고 전후 수치와 유지 기준 통과 여부를 남긴다.

**검증**
- 캐시 적중을 사용량 필드로 턴별로 확인한다. 둘째 턴부터 읽기가 0이면 연속 두 요청의 접두를 비교한다.
- 전후 비교는 같은 대화 묶음, 같은 동시성으로, 캐시가 찬 상태와 식은 상태를 구분해 잰다. 첫 글자 표시 시간과 완결 시간을 둘 다 적는다.
- 답 저장을 켰다면 권한이 다른 두 계정으로 같은 질문을 넣어 답이 섞이지 않는지, 지식을 바꾼 뒤 낡은 답이 나오지 않는지 본다.

**완료 기준**
- [ ] 유지 기준이 변경 전에 적혀 있고 유형별 기준선(대화당·해결 1건당 비용, 첫 글자 표시·완결 시간)이 있다
- [ ] 캐시 적중이 턴별 사용량 필드로 확인됐고 수명 선택의 근거(턴 간격 분포)가 있다
- [ ] 변경마다 끄고 켜는 방법, 전후 수치, 유지 기준 통과 여부가 있다 (변경이 없으면 "변경 없음"과 근거)
- [ ] 품질을 거는 변경은 유형별 평가 결과를 근거로 채택했다 (없으면 "없음")
- [ ] C0의 지연·비용 목표에 도달했거나 더 줄이지 않는 근거가 있다

**흔한 함정:** 호출당 단가로 비교하기, 날짜·사용자 이름·검색 결과를 시스템 프롬프트에 넣어 캐시를 매 턴 깨기, 턴 간격이 수명보다 긴데 캐시 효과를 가정하기, 평가 없이 작은 모델로 내리기, 권한이 걸린 답을 저장해 두고 돌려주기, 모델만 빠르게 하고 도구 실행 시간을 안 보기, 남이 밝힌 절감 수치를 우리 수치로 쓰기.

**순서와 병렬:** 기준선과 낭비 분석은 C6과 동시에 할 수 있다. 적용은 위 순서대로 하나씩이다. 프롬프트나 도구 정의가 바뀌면 기준선을 다시 잰다.

## C8. 배포·운영

**목적:** 직원이 쓰게 하고, 쓰면서 계속 나아지게 하고, 무언가 죽었을 때 사용자가 무엇을 보는지를 미리 정한다. 확대 단계와 축소 응답 표는 [`reference/erp-pipeline-ops.md`](reference/erp-pipeline-ops.md) 9~12절에 있다.

**고민할 것**
1. **무엇을 한 버전으로 묶나.** 프롬프트, 분류 규칙, 검사 설정, 도구 정의와 등급, 모델 ID와 추론 설정, 지식 색인 버전, 평가 케이스 버전. 하나만 바뀌어도 새 버전이고 턴 기록에 버전이 찍힌다.
2. **어떻게 넓히나.** 내부 시험 사용 → 그림자 방식(지식은 초안만 쓰고 사람이 답한다. 변경형은 실행하지 않고 계획만 낸다) → 일부 사용자 → 전체. 유형별로 따로 넓힌다. 단계마다 넘어가는 기준과 멈추는 기준을 미리 적고, 같은 기간에 쓰지 않는 집단을 남겨 비교한다.
3. **끄는 스위치와 축소 응답.** 모델 공급자, 검색, 검사기, 조회 도구, 변경 도구, 승인 경로, 작업 실행기, 기록 저장소, 사람에게 넘기는 창구가 각각 죽었을 때 사용자가 무엇을 보고 어시스턴트가 무엇을 하지 않는지 정한다. 스위치는 유형·도구·채널 단위로 둔다.
4. **공급자 장애와 한도.** 재시도는 횟수 상한과 간격을 두고, 재시도해도 풀리지 않는 오류를 구분한다. 대체 모델을 둔다면 그 조합도 평가한다.
5. **ERP에 주는 부하.** 추출과 조회가 운영 시스템의 성능에 영향을 줄 수 있다. 동시 실행 수, 시간대, 건수 상한을 ERP 운영 담당자와 정한다.
6. **운영에서 무엇을 보나.** 소수만 고른다: 표본을 판정한 과제 성공률, 사람에게 넘긴 비율과 그 정확도, 잘못된 실행 건수(사람이 되돌리거나 고친 변경), 권한 밖 노출 건수, 같은 사용자가 같은 주제로 다시 묻는 비율, 답 못 한 질문, 승인 거절률, 첫 글자 표시·완결 시간, 해결 1건당 비용. 사람에게 넘기지 않은 비율 하나만 보면 포기하고 떠난 사용자가 성공으로 세어진다.
7. **지식 운영.** 문서마다 담당자, 상태, 공개 대상, 검토일을 둔다. 답 못 한 질문과 낮은 피드백을 주제로 묶어 담당자에게 보내고 처리 기한을 둔다.
8. **바깥이 바뀌면.** 모델 종료 통지를 받으면 종료일 전에 평가 전체와 지연·비용 기준선을 새 모델로 다시 잰다. 지식 색인을 크게 바꾸면 검색과 근거 평가를 다시 돈다. ERP를 올리거나 권한 체계가 바뀌면 C4·C5의 시험을 다시 돈다.
9. **사고 대응과 소유.** 잘못된 답, 권한 밖 노출, 승인 없는 변경 각각의 심각도, 첫 조치(스위치, 이전 버전 고정, 변경 되돌리기), 알릴 사람. 담당자를 정한다: 프롬프트·검사, 도구·권한, 지식, 평가 케이스, 릴리스 승인, 사고 대응.
10. **온라인 비교의 한계.** 사내 사용자 수가 적으면 무작위 비교로 작은 차이를 가려낼 수 없다. 단계적 확대와 오프라인 평가, 이전 버전을 쓰는 집단과의 비교에 기댄다.

**진행**
- 릴리스 목록(구성요소별 버전)을 만들고 최종 확인용 평가를 한 번 돌려 미리 정한 기준으로 판정한다.
- 과거 대화 표본을 새 버전으로 재생해(도구는 실행하지 않고 계획만) 이전 버전과 답, 경로, 비용, 시간을 나란히 본다.
- 그림자 방식과 시범 운영의 대상, 기간, 비교 집단, 넘어가는 기준, 멈추는 기준(예: 권한 밖 노출 1건이면 즉시 중단)을 적고 시작한다.
- 축소 응답 표의 행마다 장애를 실제로 일으켜 사용자 화면과 기록을 확인한다.
- 예상 최대 동시 대화 수로 부하를 걸어 본다. 사용자는 단계적으로 늘린다.
- 사용자가 한 줄로 문제를 남길 수 있는 신고 경로를 만든다.
- 주간 회고를 돈다: 답 못 한 질문과 낮은 피드백 읽기 → 원인 분류 → 지식 담당자에게 보낼 것, 케이스로 올릴 것, 범위 조정 → C6 라운드.

**검증**
- 턴 기록에 찍힌 버전이 릴리스 목록과 같고, 응답의 모델 ID가 설정과 같다.
- 되돌리기를 실제로 해 본다. 스위치를 유형·도구·채널 단위로 꺼 보고 그동안 사용자가 보는 문구를 확인한다.
- 문서 한 건을 고친 뒤 답에 반영되기까지의 시간을 잰다.
- 답 못 한 질문 한 건이 담당자에게 전달돼 닫히는 것을 끝까지 따라가 본다.
- 깨끗한 환경에서 문서대로 설치·실행된다.

**완료 기준**
- [ ] 릴리스 목록(프롬프트, 검사, 도구·등급, 모델 ID, 지식 색인 버전, 평가 케이스 버전)과 최종 확인용 평가 통과 결과가 있다
- [ ] 확대 단계별 넘어가는 기준과 멈추는 기준이 시작 전에 적혀 있고 유형별로 구분돼 있다
- [ ] 축소 응답 표의 모든 행을 장애를 일으켜 시험했고 "하지 않는 것"이 지켜졌다
- [ ] 되돌리기와 끄는 스위치를 한 번 실제로 해 봤다
- [ ] 재시도 정책과 변경 도구의 중복 실행 방지가 시험됐고, ERP에 주는 부하의 상한을 운영 담당자와 정했다
- [ ] 운영 지표, 신고 경로, 사고 대응 절차와 담당자가 정해졌다
- [ ] 지식 문서마다 담당자와 상태가 있고, 답 못 한 질문이 담당자에게 가서 닫히는 흐름을 1건 이상 끝까지 돌렸다
- [ ] 모델, 지식 색인, ERP가 바뀔 때 다시 돌릴 평가·시험 목록이 있다

**흔한 함정:** 전체 사용자에게 한 번에 열기, 세 유형을 같은 날 열기, 축소 응답을 정하지 않아 장애 때 빈 화면이나 근거 없는 답이 나가기, 변경 도구를 시간 초과 뒤 그대로 다시 실행하기, 지식 담당자 없이 출시하기, 사람에게 넘기지 않은 비율 하나로 성공을 판단하기, 모델이나 ERP가 바뀌었는데 평가를 다시 돌리지 않기, 프롬프트를 운영에서 바로 고치기.

**순서와 병렬:** 릴리스 고정 → 최종 확인 → 재생 → 그림자 방식 → 일부 사용자 순서는 지킨다. 축소 응답 시험, 부하 시험, 지식 담당 지정, 사고 절차 작성은 그 사이에 동시에 한다.

## 2. 전체가 끝났다는 기준

유형마다 아래가 모두 참이면 그 유형의 첫 버전이 끝난 것이다. 그 뒤에 다음 유형을 연다.

1. C0에서 정한 성공 지표를 **최종 확인용 평가**에서 충족한다
2. 권한 밖 노출과 승인 없는 변경이 0건이고, 차단 시험이 전부 막힌다
3. 결과를 대화 밖에서 확인하는 채점이 명령 한 줄로 다시 돈다
4. 모든 대화가 기록되고, 누가 무엇을 어떤 승인으로 했는지 기록에서 재구성된다
5. 개선이 "실패 분류 → 한 가지 변경 → 재측정 → 판정"으로 한 번 이상 돌았다
6. 축소 응답과 되돌리기를 실제로 해 봤다
7. 지식, 도구·권한, 평가 케이스, 사고 대응의 담당자가 있다

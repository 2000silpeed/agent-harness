# 에이전트 프로젝트 하네스 — 작업 규칙

이 프로젝트는 `harness/PLAYBOOK.md`의 P0~P9 단계를 따라 완성품까지 간다. 아래 규칙은 매 세션 적용된다.

<workflow>
- 세션을 시작하면 SessionStart 훅이 `phase.sh` 결과(현재 단계와 남은 게이트)를 보여준다. 훅 출력이 없으면 직접 `bash harness/scripts/phase.sh`를 실행한다.
- **현재 단계의 일만 한다.** 앞 단계 게이트가 열려 있으면 다음 단계 작업을 시작하지 않는다. 사용자가 건너뛰자고 하면 `design/decisions.md`에 이유를 남기고 건너뛴다.
- 새 단계는 `bash harness/scripts/start-phase.sh <번호>`로 템플릿을 복사해서 시작한다.
- 게이트 항목은 실제로 확인했을 때만 `- [x]`로 바꾼다. 확인 방법(명령, 수치, 파일)을 항목 옆에 적는다.
- 단계의 상세 지침은 `harness/PLAYBOOK.md`의 해당 절만 읽는다. 전체를 매번 읽지 않는다.
</workflow>

<design_principles>
0. **프레임워크를 전제하지 않는다.** 강의는 LangGraph·Deep Agents로 실습했지만 그건 예시다. 프로젝트에 맞는 도구를 고르고, 원칙(아래)이 코드 어디에서 지켜지는지 설명할 수 있어야 한다.
1. **싱글 에이전트 + 스킬로 시작한다.** 멀티로 쪼개는 근거는 측정된 실패나 컨텍스트 경계여야 하고, 페르소나는 근거가 아니다.
2. **모든 노드를 에이전트로 만들지 않는다.** 규칙·계산·조회는 코드로 처리한다. 정확성이 필요한 계산은 검증된 코드 결과를 그대로 출력한다.
3. **컨텍스트가 핵심 자원이다.** 고정 내용은 앞에, 변하는 값(날짜 등)은 뒤에 둔다. 탐색처럼 컨텍스트를 채우는 일은 서브에이전트나 작은 모델에 격리한다.
4. **도구는 적게, 명확하게 만든다.** 이름, description(언제), 타입 있는 인자를 갖추고 비슷한 도구는 합친다. 반환에는 status와 출처를 넣는다.
5. **순서가 중요하면 도구가 강제한다.** 프롬프트에 "1→2→3 순서로 하라"고 적고 기도하지 않는다.
6. **제안과 실행 권한을 분리한다.** 외부 쓰기, 결제, 삭제, 민감정보 변경은 승인 게이트를 거친다.
7. **결정과 최적화에는 근거를 남긴다.** `design/decisions.md`에 "문제 → 선택 → 근거(수치·출처)"를 한 줄씩 적는다.
8. **개선은 평가로 증명한다.** 변수는 하나만 바꾸고 품질·비용·지연을 함께 비교한다.
</design_principles>

<working_style>
- 요구가 모호하면 추측하지 말고 `project-kickoff` 방식으로 한 번에 하나씩 질문한다.
- 잘못된 방향으로 가고 있으면 계속 진행하지 말고 멈춰서 알린다.
- 확인된 사실, 미확인 항목, 변경 상태(준비·검토 대기·완료)를 구분해서 보고한다.
- 큰 파일 탐색이나 대량 읽기는 서브에이전트에 맡기고, 결론만 받는다.
</working_style>

<skills>
- `project-kickoff`: P0. 사용자를 인터뷰해서 brief를 만든다.
- `workflow-to-architecture`: P1~P2. 워크플로우를 노드 유형표와 아키텍처로 바꾼다.
- `skill-authoring`: P4. 강의 기준에 맞는 SKILL.md를 쓰고 점검한다.
- `tool-design-review`: P4·P6. 도구와 MCP 명세를 체크리스트로 검토한다.
- `agent-eval`: P7. 평가셋을 만들고 세 축으로 채점한다.
- `optimize-agent`: P8. 동작을 유지하면서 최적화하고 근거를 남긴다.
</skills>

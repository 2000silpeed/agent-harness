# 에이전트 프로젝트 하네스 — 작업 규칙

이 프로젝트는 `harness/PLAYBOOK.md`의 P0~P9 단계를 따라 완성품까지 간다. 기본 대상은 최종 프로젝트 **dcode 기반 Coding Assistant**다(평가 40점: 코드 기준·계획 리뷰·메모리와 자기개선·모니터링). 아래 규칙은 매 세션 적용된다.

<workflow>
- 세션을 시작하면 SessionStart 훅이 `phase.sh` 결과(현재 단계와 남은 게이트)를 보여준다. 훅 출력이 없으면 직접 `bash harness/scripts/phase.sh`를 실행한다.
- **현재 단계의 일만 한다.** 앞 단계 게이트가 열려 있으면 다음 단계 작업을 시작하지 않는다. 사용자가 건너뛰자고 하면 `design/decisions.md`에 이유를 남기고 건너뛴다.
- 새 단계는 `bash harness/scripts/start-phase.sh <번호>`로 템플릿을 복사해서 시작한다.
- 게이트 항목은 실제로 확인했을 때만 `- [x]`로 바꾼다. 확인 방법(명령, 수치, 파일)을 항목 옆에 적는다.
- **코드를 바꾸기 전에는 `plan-review` 스킬로 계획 → 독립 리뷰 → 사용자 승인을 거친다.** 범위가 바뀌면 다시 리뷰한다.
- 단계의 상세 지침은 `harness/PLAYBOOK.md`의 해당 절만 읽는다. dcode 세부는 `harness/reference/dcode.md`, 평가·자기개선 규칙은 `harness/reference/eval-rsi-rules.md`에서 필요한 절만 찾아 읽는다.
</workflow>

<design_principles>
1. **싱글 에이전트 + 스킬로 시작한다.** 멀티로 쪼개는 근거는 측정된 실패나 컨텍스트 경계여야 한다. 페르소나는 근거가 아니다.
2. **모든 노드를 에이전트로 만들지 않는다.** 규칙·계산·조회·형식 검사는 코드로 처리한다.
3. **컨텍스트가 핵심 자원이다.** 고정 내용은 앞에, 변하는 값(날짜, 검색된 메모리)은 뒤에 메시지로 둔다. 탐색은 서브에이전트나 작은 모델에 격리한다.
4. **도구는 적게, 명확하게 만든다.** 순서가 중요하면 도구가 강제한다.
5. **제안과 실행 권한을 분리한다.** 게이트는 fail-closed로 만든다. 판정기가 실패하면 차단이다.
6. **완료는 증거로 판정한다.** 모델의 "완료했다"는 제안일 뿐이다. 테스트 결과, 파일 상태, 로그로 판정한다.
7. **신뢰기반을 분리한다.** 평가기, 정답, 테스트, 예산, 권한 정책은 개선 주체가 고칠 수 없어야 한다.
8. **개선은 같은 조건에서 하나만 바꿔 증명한다.** 판정 규칙은 결과를 보기 전에 고정한다.
</design_principles>

<evidence_rules>
- 사실 주장에는 출처(`파일:줄`, 로그 경로, 명령 출력)를 붙인다. 근거 수준을 구분한다: 실행 경로에서 확인 / 코드 정의만 / 문서만 / 추정.
- 실패 분석은 fact / hypothesis / alternative / evidence_ids를 나눠 쓴다.
- 문서와 코드가 다르면 코드를 따르고 차이를 알린다(dcode 문서와 코드 불일치 목록: `reference/dcode.md` §5.2).
- 모르는 값은 0이 아니라 null로 둔다. 확인하지 못한 것은 "확인 필요"라고 쓴다.
</evidence_rules>

<never>
- 테스트를 삭제하거나 skip/xfail로 넘기기
- 기대 정답을 코드에 하드코딩하기
- 예산·임계값을 올려 실패를 감추기, 결과를 본 뒤 판정 규칙 바꾸기
- 실패한 실행이나 로그 행을 지우기, 잘 나온 반복만 남기기
- mock·scripted 결과를 개선율로 보고하기
- `.env` 값이나 키를 출력·로그·커밋에 남기기
- YOLO 모드나 `-S all`로 시연하기
</never>

<working_style>
- 요구가 모호하면 추측하지 말고 한 번에 하나씩 질문한다.
- 유료 모델 실행 직전에는 규모(작업 수 × 반복 × 예상 호출 수)를 한 줄로 고지한다.
- 잘못된 방향으로 가고 있으면 계속하지 말고 멈춰서 알린다.
- 보고할 때는 확인된 사실, 미확인 항목, 변경 상태(준비·검토 대기·완료)를 구분한다.
- 큰 파일 탐색이나 대량 읽기는 서브에이전트에 맡기고 결론만 받는다.
</working_style>

<skills>
- `project-kickoff`: P0. 인터뷰로 brief와 평가 기준 체크리스트를 채운다.
- `workflow-to-architecture`: P1~P2. 워크플로우를 노드 유형표, 확장 지점, 6책임 표로 바꾼다.
- `plan-review`: 코드 변경 전 매번. 계획 → 독립 리뷰 → 승인 → 범위 변경 시 재리뷰.
- `skill-authoring`: P4. SKILL.md를 쓰고 점검한다.
- `tool-design-review`: P4·P6. 도구, MCP, 게이트를 검토한다.
- `agent-eval`: P7. 평가셋과 채점, 실패 분석.
- `self-improve-loop`: P8. 개선안 생성 → 같은 조건 비교 → ADOPT/HOLD 판정 → 채택 기록.
- `optimize-agent`: P8. 동작을 유지한 성능 최적화.
- `rubric-check`: P9와 중간 점검. 40점 항목을 증거와 함께 자가 점검한다.
</skills>

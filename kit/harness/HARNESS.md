# 코딩 에이전트 구축 — 작업 규칙

이 프로젝트는 `harness/METHOD.md`의 S0~S8 단계로 회사 코딩 에이전트를 만든다. 완성품이 통과해야 하는 기준은 `harness/CRITERIA.md`에 있다. 아래 규칙은 매 세션 적용된다.

<workflow>
- 세션을 시작하면 SessionStart 훅이 단계 상태(완료, 진행 중, 지금 시작할 수 있는 것)를 보여준다. 안 보이면 `bash harness/scripts/phase.sh`를 실행한다.
- 진행 중이거나 "지금 시작할 수 있음"에 있는 단계의 일만 한다. 선행 단계가 안 끝난 단계는 시작하지 않는다. 사용자가 건너뛰자고 하면 `start-phase.sh <번호> --force "이유"`로 기록을 남기고 건너뛴다.
- 새 단계는 `bash harness/scripts/start-phase.sh <번호>`로 시작하고, `harness/METHOD.md`에서 그 단계 절만 읽는다. 단계마다 "고민할 것"을 사용자와 먼저 정한 뒤 진행한다.
- 완료 기준은 실제로 확인했을 때만 체크한다. 확인한 방법(명령, 수치, 파일)을 옆에 적는다.
- 코드를 바꾸기 전에는 `plan-review` 스킬로 계획 → 독립 리뷰 → 승인을 거친다. 범위가 바뀌면 계획으로 돌아간다.
</workflow>

<parallel_rules>
- 병렬로 진행할 수 있는 단계: S1과 S2, S3·S4·S5, S6과 S7. 독립적인 조사·작성은 서브에이전트로 동시에 돌려도 된다.
- 만드는 것은 병렬, 반영하는 것은 하나씩이다. 변경을 합칠 때마다 평가를 돌리고 한 번에 한 가지만 바꾼다.
- S2의 기준선 측정은 S1이 끝나야 할 수 있다.
</parallel_rules>

<principles>
1. 완료는 증거로 판정한다. 에이전트의 "완료했다"는 자기 보고다. 테스트 결과, 실제 파일 상태, 기록으로 판정한다.
2. 평가와 기록이 먼저다. 기준선 없이 "좋아졌다"고 말하지 않는다.
3. 싱글 에이전트로 시작한다. 쪼개는 근거는 컨텍스트 경계나 측정된 실패다.
4. 규칙·계산·검사는 코드로 한다. 판단은 모델 호출 앞단에서 끝낼 수 있으면 끝낸다.
5. 지침은 부탁, 스킬은 위임, 훅·권한 설정은 강제다. 반드시 지켜야 하는 규칙을 지침에만 두지 않는다.
6. 고정 내용은 앞, 바뀌는 값은 뒤, 대화는 뒤에 붙이기만 한다. 컨텍스트 길이는 비용이다.
7. 결정에는 근거를 남긴다(`design/decisions.md`). 평가 기준은 결과를 보기 전에 고정한다.
8. 특정 프레임워크를 전제하지 않는다. 원칙이 코드 어디에서 지켜지는지 설명할 수 있어야 한다.
</principles>

<never>
- 테스트를 지우거나 건너뛰기, 기대 정답을 코드에 박아 넣기
- 예산·임계값을 올려 실패를 감추기, 결과를 본 뒤 평가 기준 바꾸기
- 실패한 실행을 표에서 빼기, 모르는 값을 0으로 적기
- 최종 확인용 평가 데이터를 보고 수정하기
- 키나 `.env` 값을 출력·기록·커밋에 남기기
</never>

<working_style>
- 요구가 모호하면 추측하지 말고 한 번에 하나씩 묻는다.
- 유료 모델을 여러 번 부르는 실행 전에는 규모(건수 × 반복 × 예상 호출 수)를 한 줄로 알린다.
- 보고할 때는 확인된 사실, 미확인 항목, 변경 상태를 구분한다.
- 큰 탐색이나 대량 읽기는 서브에이전트에 맡기고 결론만 받는다.
</working_style>

<skills>
- `project-kickoff`: S0. 인터뷰로 브리프를 채운다.
- `serving-plan`: S0·S7. 모델을 API로 쓸지 직접 서빙할지 정하고 용량·설정을 계획한다.
- `golden-dataset`: S1. 시나리오 평가셋을 만들고 개발용과 최종 확인용을 나눈다.
- `agent-eval`: S1과 이후 모든 변경. 채점기를 검증하고 같은 조건으로 비교한다.
- `workflow-to-architecture`: S2. 요청 흐름과 단계별 담당을 정한다.
- `skill-authoring`, `tool-design-review`: S4. 스킬과 도구를 쓰고 점검한다.
- `hook-design`: S5. 규칙을 지침·스킬·훅 중 어디에 둘지 정하고 훅을 설계한다.
- `plan-review`: 코드 변경 전 매번. 계획 → 독립 리뷰 → 승인.
- `criteria-check`: S8과 중간 점검. 인수 기준(`harness/CRITERIA.md`) 항목마다 증거를 확인한다.
- `optimize-agent`: S7. 동작을 유지한 채 최적화하고 근거를 남긴다.
</skills>

# 기반 참고: SAP에서 ERP 어시스턴트 만들기

> [`../METHOD-erp.md`](../METHOD-erp.md)를 보충하는 문서다. 그 문서의 규칙이 ERP가 SAP일 때(ABAP 소스, 이관, 검사, 권한, 데이터 추출, SAP GUI 스크립팅) 구체적으로 무엇을 뜻하는지 적었다. 도구 등급·신원 전달·큰 결과·변경 전 확인은 [`../reference/erp-knowledge-tools.md`](../reference/erp-knowledge-tools.md) 8~12절, 승인·감사·차단 시험은 [`../reference/erp-control.md`](../reference/erp-control.md), 계획 → 리뷰 → 승인은 [`../reference/plan-gate.md`](../reference/plan-gate.md)에 있고 여기서 되풀이하지 않는다.
> **이 문서의 어떤 내용도 실제 SAP 시스템에서 시험하지 않았다.** 2026-11-16에 공개 문서를 읽고 쓴 것이다. 로그인이 필요한 SAP Note는 본문을 읽지 못했고, Note 번호는 공개 페이지가 언급한 것만 적었다. 조사 기록은 `research/R12-sap-abap-gui-tools.md`에 있다. SAP에 접속할 수 있는 환경에서 무엇을 어떤 순서로 확인하고 채우는지는 [`sap-connected.md`](sap-connected.md)에 있다.
> **항목마다 적용 여부가 다르다.** 고객 시스템의 릴리스, 배포 형태(온프레미스 / 프라이빗 클라우드 / 퍼블릭 클라우드), SAP와의 계약에 따라 달라진다. SAP Help 문서는 따로 적지 않으면 ABAP platform 2025 FPS02 판을 읽었다. **기준 구성은 온프레미스 SAP와 직접 만든 MCP 서버다**(0절). 다른 배포 형태와 연결 수단은 비교 대상으로 남겼다.
> **확신도 표기:** 〔원문 대조〕 공식 자료의 원문에서 읽음 · 〔요약 경유〕 요약 모델이나 검색 결과 요약으로만 봄 · 〔커뮤니티〕 SAP 공식 자료가 아님(README를 직접 읽었어도 이 표시를 붙인다) · 〔제안〕 자료에 없는 우리 쪽 추론과 설계 제안 · 〔확인 필요〕 확인하지 못함. 대괄호 숫자는 맨 끝 참고 자료의 번호이고, 표시가 따로 없는 인용은 그 자료의 표시를 따른다. **(제안값)** 은 자료에 없는 시작값이다.
> **용어:** "이관"은 SAP 시스템 사이에서 변경을 옮기는 일(이관 요청, 릴리스, 임포트)만 가리킨다. 사람 담당자에게 대화를 넘기는 것은 "사람에게 넘김"이다. SAP의 데이터베이스 테이블은 "테이블"로 적는다(`METHOD-erp.md`의 "표"). 환경은 개발·품질·운영이다.

## 0. 먼저 닫을 것: SAP API 정책과 계약

어떤 도구를 만들지 고르기 전에 닫는다. `METHOD-erp.md` C0의 7번(ERP 공급사의 사용 조건이 이 구성을 허용하는가)이 SAP에서 뜻하는 것이 이 절이다. 8번(환경과 권한의 전제), 9번(회사 밖으로 나가는 데이터), 10번(경로를 누가 정하나)의 답도 여기에 걸린다. **이 절은 법률 자문이 아니다.** 정책을 읽고 요지를 옮긴 것이고, 우리 구성이 허용되는지는 계약서와 SAP의 확인, 법무 검토가 정한다.

**SAP API Policy v.4.2026a의 요지** [1] 〔원문 대조〕. 이 정책은 함께 제공되는 SAP 솔루션의 제품 문서(Documentation)의 일부다. 이 점과 1.2절, 2.2.2절, 3절은 조사와 따로 PDF를 내려받아 다시 읽고 맞췄다. 아래는 요지이고 문장을 옮긴 것이 아니다.
- 1.1절: 공개 API는 Business Accelerator Hub나 제품 문서에 실린 것이고 문서에 적힌 용도로만 쓴다.
- 1.2절: 공개 API(Published API)가 아닌 API, 곧 내부·비공개이거나 SAP 전용 클라이언트에 묶인 API를 고객·서드파티 애플리케이션이 쓰면 안 된다. 제품 문서가 허용하거나 SAP가 승인한 경우는 예외이고, 프라이빗 클라우드와 온프레미스에서 고객이 개발한 ABAP 인터페이스가 허용되는 예로 나온다. 엔드포인트마다 공개 API인지 확인해야 한다.
- 2.2.2절: SAP가 인정한 구조, 데이터 서비스, 서비스별 경로를 거치지 않으면 다음 용도의 API 사용이 금지된다. (a) API 호출의 순서를 계획·선택·실행하는 (반)자율·생성형 AI 시스템과의 연동, (b) 긁어 오기, 수집, 체계적이거나 대규모인 데이터 추출·복제.
- 3절: SAP는 사용을 감시하고 제한하거나 중단할 수 있다. 중간 서비스, 커스텀 코드, 프록시, 게이트웨이, 가장(다른 주체인 척하기)으로 통제를 우회하면 안 된다.

| 계획한 기능 | 정책에서 걸리는 곳 | 열려 있는 질문 〔확인 필요〕 |
|---|---|---|
| ABAP 소스 읽기·수정 (ADT 인터페이스) | 1.2절. ADT의 백엔드 설정서는 ADT 도구를 위한 것이고 서드파티 클라이언트용 공개 API 규격이 아니다 [14]. 정책 FAQ가 ADT API를 내부용으로 분류하고 개발 용도의 인정 경로(Eclipse ADT, SAP 제공 개발 도구 등)를 든다는 정리가 있다 [3] 〔요약 경유〕〔커뮤니티〕. FAQ 원문은 열지 못했다 | 우리 도구 서버가 ADT 인터페이스를 직접 부르는 것이 인정 경로인가. 공식 ADT MCP 서버를 서버 쪽 어시스턴트에 연결하는 구성이 허용되는가 |
| 데이터 추출 | 1.2절(부르는 인터페이스가 공개 API인가)과 2.2.2(b)절. ADT로 애플리케이션 테이블과 업무 데이터를 읽는 것은 ADT의 용도 밖이라는 정리가 있다 [3] 〔요약 경유〕〔커뮤니티〕 | 어느 양과 빈도부터 체계적·대규모 추출인가. 사람이 승인한 반출도 (b)에 드는가 |
| SAP GUI 조작 | GUI 스크립팅이 이 정책의 대상인지부터 열려 있다. 따로 걸리는 것: 스크립팅 보안 가이드는 최종 사용자 계약을 지키라고 적고 [27], 비SAP 프런트엔드나 자동화 시스템을 거친 사용은 디지털 액세스로 정의돼 있다 [26] | 어시스턴트가 화면으로 만든 문서가 과금 대상인가. 사람이 지켜보는 자동화와 무인 자동화가 달리 취급되는가 |
| 모델이 고른 호출 순서 | 2.2.2(a)절. `METHOD-erp.md` C0 10번의 선택(코드가 경로를 정하나, 모델이 순서를 정하나)이 SAP에서는 설계 선택이기 전에 정책 문제다 〔제안〕 | 코드가 순서를 정하고 모델은 인자만 채우는 흐름도 (a)에 드는가. 인정된 경로를 쓰면 모델이 순서를 정해도 되는가 |

**찾은 경로** (SAP가 문서로 낸 것과 정책이 예로 든 것. 기준 구성과 견주는 비교 대상이다)
- **공식 ADT MCP 서버.** ADT(VS Code, Eclipse) 확장 안에서 도는 로컬 서버다 [4]. 지원은 Joule for Developers, ABAP AI capabilities 라이선스가 있을 때만 제공된다 [5]. 성숙도 표기가 엇갈린다. 튜토리얼은 실험 기능이고 운영용이 아니라고 적고, SAP News 기사는 2026년 2분기부터 일반 제공이라고 적는다 [6](기사는 〔요약 경유〕). 백엔드 최소 릴리스와 클래식 ABAP 객체의 편집 범위는 〔확인 필요〕. 개발자 한 사람의 IDE 안에서 도는 구조라 여러 직원이 쓰는 서버 쪽 어시스턴트에 그대로 꽂는 부품이 아니다 〔제안〕.
- **"Third-Party MCP Access to SAP Solutions" 참조 구조** [2]. 고객과 파트너가 조건을 지키면 서드파티·커스텀 MCP 서버로 SAP API에 접근할 수 있다고 적는다. 조건은 API 정책 전체 준수, 모든 연결의 인증·인가, 하위 API의 호출 한도 준수, 안정성·보안 강화이고, 운영 책임은 배포한 쪽에 있다. 호출자의 토큰을 그대로 넘기지 않는 토큰 교환, 장기 자격증명을 서버에 두지 않기, 입력 검증, 호출 제한, 타임아웃, 호출별 기록을 요구한다. 원시 거래 API에 의미 보강 없이 붙이면 쓰기에서 잘못된 업무 거래의 위험이 크다고도 적는다. 정책 전체 준수가 조건이므로 이 구조가 1.2절의 공개 API 요건을 면제하지는 않는다고 읽는다 〔제안〕. 같은 문서가 SAP 쪽 대안으로 Integration Suite의 MCP Gateway와 Joule Studio가 만드는 MCP 서버를 든다. 두 제품의 문서는 읽지 않았다 〔확인 필요〕.
- **고객이 개발한 ABAP 인터페이스.** 정책 1.2절이 프라이빗 클라우드와 온프레미스에서 허용되는 예로 든다 [1]. 업무 질문 단위의 읽기 서비스를 우리가 만들어 여는 길이다(5절) 〔제안〕. 2.2.2절과 3절은 그대로 적용된다고 보고 확인받는다. 비공개 API를 감싸 통제를 비켜 가는 용도라면 3절에 걸릴 수 있다 〔제안〕.

### 기준 구성: 온프레미스 SAP + 직접 만든 MCP 서버

이 문서의 기준 구성이다. SAP 시스템은 온프레미스이고 도구 서버(MCP 서버)는 우리가 직접 만든 것이다. 위의 다른 경로는 비교 대상으로 남긴다. 아래는 정책을 읽고 낸 정리이고 허용 여부에 대한 결론이 아니다.

- **직접 만들었다는 사실은 허용의 근거가 아니다.** 판단의 단위는 서버가 아니라 서버가 부르는 SAP 쪽 인터페이스 하나하나다 〔제안〕. 정책 1.2절이 프라이빗 클라우드와 온프레미스에서 고객이 개발한 ABAP 인터페이스를 허용되는 예로 들므로 [1] 온프레미스에서는 그 길이 열린다. 2.2.2절(모델이 고른 호출 순서, 체계적·대규모 추출)과 3절(커스텀 코드·프록시·게이트웨이를 통한 우회 금지)이 그 길에도 걸리는지는 SAP와 법무에 확인한다 〔확인 필요〕. 답을 받기 전에는 배포 형태와 무관하게 적용된다고 읽는다 〔제안〕. 공개되지 않은 API나 범용 테이블·소스 읽기를 밖으로 내주는 일만 하는 고객 개발 래퍼는 3절에 걸릴 수 있다 〔제안〕.
- **이 판의 정책이 기존 온프레미스 계약과 릴리스에 적용되는지, 어떻게 적용되는지는 〔확인 필요〕다.** 정책은 스스로를 제품 문서의 일부라고 적는다 [1]. 무엇이 적용되는지는 계약이 정한다.

| 직접 만든 서버가 SAP 쪽에서 부르는 것 | "공개 API인가" 칸의 시작값 | 할 일 |
|---|---|---|
| ADT 서비스 직접 호출 (`/sap/bc/adt`) | 모름 | 1.2절의 열린 질문이다(위 표의 첫 줄) [14][3]. 답을 받기 전에는 새 도구를 만들지 않고, 이미 있는 도구는 점검표에 올려 SAP와 법무의 확인을 먼저 받는다(제안값) |
| 고객 개발 RFC 함수 모듈·OData 서비스 (고객 네임스페이스) | 1.2절이 든 허용 예의 후보 | 인터페이스마다 안에서 무엇을 부르는지 적는다. "아무 테이블, 아무 소스, 아무 SQL"을 받는 범용 인터페이스는 만들지 않는다 〔제안〕. RFC는 `S_RFC`와 UCON으로 외부에서 부를 수 있는 함수를 좁힌다 [21] |
| 표준 BAPI·OData 서비스 | 함수·서비스마다 확인 | Business Accelerator Hub나 제품 문서에 실렸는지, 문서에 적힌 용도로 쓰는지를 하나씩 본다 [1] |
| `RFC_READ_TABLE`과 그 밖의 범용 읽기 | 허용되지 않는 것으로 다룬다 〔제안〕 | 감싸지 않는다(5절) [20][25] |
| SAP GUI Scripting | 이 정책의 대상인지 모름 | 최종 사용자 계약과 디지털 액세스의 질문이 남는다 [27][26] |

- **직접 만들어서 할 수 있는 것.** 도구 목록을 우리가 정한다. 이관 요청의 릴리스·임포트, transport of copies, ATC 면제 요청, 범용 테이블 읽기, 프리 SQL 도구는 만들지 않으면 된다. 계획 게이트(7절)와 직원별 범위 검사를 서버 안에 둘 수 있다 〔제안〕.
- **직접 만들어서 져야 하는 것.** 참조 구조의 요구가 우리의 구현과 시험 부담이 된다. 받은 토큰을 그대로 넘기지 않는 토큰 교환, 서버에 장기 자격증명을 두지 않기, 입력 검증, 하위 API의 한도를 넘지 않는 호출 제한, 타임아웃, 호출별 기록이다 [2]. 운영 책임도 배포한 쪽인 우리에게 있다. 그 문서가 든 두 패턴은 외부 플랫폼의 MCP 서버와 고객이 관리하는 BTP 하위 계정의 커스텀 MCP 서버다. 사내 인프라에서 돌며 온프레미스 시스템에 붙는 서버가 어느 쪽으로 다뤄지는지는 〔확인 필요〕.
- **온프레미스라서 달라지는 것.** (1) GUI 스크립팅의 프로파일 파라미터와 `S_SCR`은 SAP 시스템 쪽 설정이라 [27] Basis 담당자가 직접 정할 수 있다(6절) 〔제안〕. (2) 신원 전달은 8절에 적은 방식(ABAP 플랫폼의 OAuth 2.0 서버, 신뢰 RFC) 가운데 고른다 [22]. ADT 서비스를 직접 부를 때 직원의 신원을 전달하는 방법은 공식 문서에서 찾지 못했다 〔확인 필요〕. (3) 공식 ADT MCP 서버는 라이선스가 있어야 지원되고, 그 기능의 제공 범위로 문서가 드는 것은 BTP, S/4HANA Cloud Public Edition, Private Edition이다 [5][7]. Integration Suite의 MCP Gateway와 Joule Studio는 별도 제품이고 문서를 읽지 않았다. 셋 다 온프레미스 구성에서 쓸 수 있는지는 〔확인 필요〕이므로 기준 구성에서는 계획이 아니라 비교 대상이다. (4) ADT 서비스에 붙을 수 있는 최소 릴리스는 공식 문서에서 찾지 못했다 〔확인 필요〕. 커뮤니티 서버들은 ADT 서비스가 켜져 있어야 하고 SAP_BASIS 7.50 미만은 지원하지 않는다고 적는다 [9] 〔커뮤니티〕.
- **"온프레미스"는 SAP 시스템의 위치다.** 모델이 어디서 도는지는 별개의 질문이고(`METHOD-erp.md` C0 9번), 소스와 데이터가 회사 밖으로 나가도 되는지는 여전히 그 답이 정한다.

**기존 서버의 점검표.** 이미 만든 서버의 도구마다 아래를 채운다. 채운 줄이 도구별 표의 "부르는 인터페이스" 칸과 4·5·6·8절 통제의 출발점이다(제안값).

|---|---|---|---|---|---|---|---|

- **서드파티가 ADT 인터페이스를 쓰는 것.** ADT 인터페이스를 직접 부르는 서버는 0절 표의 "공개 API인가"가 열려 있다. 직접 만든 서버가 ADT 서비스를 부를 때도 같다. ARC-1의 문서는 직접 ADT 호출이 인정 경로인지 SAP에 확인받으라고 적고, 개발·시험 시스템이라고 예외가 되지 않는다고 적는다 [10] 〔커뮤니티〕. 라이선스 칸은 README를 옮긴 것이고 우리가 써도 되는지에 대한 판단이 아니다.
- **들이기 전에 읽는다.** 버전을 고정하고, 실행될 코드를 읽고, 쓰기 기능은 끈 채로 시작한다(`../reference/security.md` T14). 커뮤니티 서버의 동작(잠금 처리, 실패 뒤 잔여물, 기록 내용)은 README만 읽었고 실행하지 않았다 〔확인 필요〕. 공식 서버에도 책임은 남는다. SAP의 보안 권고는 개발 환경 설정이 개발자 책임이고, 작업 PC가 침해되면 보호 수단이 듣지 않고, 프롬프트 인젝션이 클라이언트를 침해할 수 있고, 사용자가 더한 서드파티 MCP 서버는 사용자 책임이라고 적는다 [4].

## 3. ABAP 읽기·분석

- **고민할 것**
  1. 어느 경로로 읽나. 기준 구성에서는 직접 만든 서버가 ADT 서비스를 직접 부르거나 고객 개발 인터페이스를 부른다(0절). 비교 대상은 공식 ADT MCP 서버(개발자 IDE), 커뮤니티 ADT 서버, Git 사본이다(2절). 사본을 읽으면 일반 코딩 에이전트의 읽기·검색 도구를 그대로 쓰고, 0절의 답을 받기 전에도 시작할 수 있다 〔제안〕.
  2. 활성 판과 비활성 판 중 무엇을 읽나. 개발 객체에는 두 판이 있고, 비활성 판은 개발자에게만 보이는 작성 중인 작업이며 활성화해야 시스템 전체에 보인다 [13]. 분석 답변의 기준은 활성 판으로 두고 어느 판을 읽었는지 답변에 적는다 〔제안〕.
  3. 소스를 외부 모델로 보내도 되나. 소스에는 하드코딩된 값, 사내 로직, 주석 속 개인정보가 있다. 런타임 피드(ST22 덤프, 게이트웨이 오류 로그)에는 실제 업무 데이터가 실리고, SAP도 서드파티 AI 서비스에 연결하면 그 데이터가 공급자에게 노출될 수 있다고 고지한다 [5]. 범위는 `../reference/erp-control.md` 8절의 표로 정한다.
- **진행:** 표시 전용 역할(`SAP_BC_DWB_WBDISPLAY`, 수정 불가 [14])을 가진 직원 본인의 신원으로 부른다. 읽기 범위는 SAP 권한(직원의 역할)으로 좁힌다. 공식 서버의 패키지 제한은 생성·수정에만 걸리고 읽기는 모든 패키지에서 된다 [4]. 덤프·오류 로그·테이블 미리보기·객체 동작 실행 도구는 끄고 필요가 측정되면 연다. 반환에는 줄 번호, 범위 인자, 상한, 잘림 안내를 둔다(`../reference/erp-knowledge-tools.md` 10절). 호출마다 읽은 객체와 판을 기록한다.
- **검증:** 권한 없는 패키지를 묻는 요청, 없는 객체, 상한을 넘는 큰 프로그램, 비활성 판만 있는 객체를 넣어 각각 정해진 응답이 나오는지 본다. 답변이 인용한 객체와 줄을 그 판의 실제 소스와 대조한다(`METHOD-erp.md` C1의 코드 분석 과제).
- **완료 기준**
  - 읽기 도구마다 호출 신원, 허용 시스템, 반환 상한, 기록 항목이 명세에 있다
  - 답변이 인용한 객체·줄을 원본과 대조한 시험 결과가 있다
  - 권한 없는 직원의 요청을 SAP가 거부한 시험 기록이 있다
  - 외부 모델로 나가는 소스의 범위와 가림 규칙이 적혀 있고, 덤프·오류 로그 도구가 기본으로 꺼져 있다
- **흔한 함정:** 넓은 권한의 공용 계정으로 읽기, 주석과 문자열 리터럴의 문장을 지시로 따르기, 비활성 판을 현재 동작으로 설명하기, 읽기 도구라는 이유로 덤프 조회를 열어 두기, 릴리스 시점의 Git 사본을 현재 소스로 설명하기.

## 4. ABAP 수정

- **고민할 것**
  1. 무엇을 고칠 수 있게 하나. 고객 네임스페이스의 지정 패키지(허용 목록)로 좁힌다. 공식 서버도 생성·수정을 지정 패키지로 제한한다 [4]. 시스템 변경 옵션은 전역 설정, 소프트웨어 구성요소, 네임스페이스가 모두 변경 가능이어야 객체를 고칠 수 있게 한다 [15]. SAP 표준 객체의 수정은 SAP의 보증 의무를 크게 줄이고 등록 절차가 걸리므로 [17] 어시스턴트의 범위에서 뺀다. 대상 패키지가 ABAP for Cloud Development면 릴리스된 API만 쓸 수 있으므로 [17] 계획 단계에서 대상 객체의 언어 버전과 쓰려는 API의 릴리스 상태를 확인하게 한다.
  2. 이관 요청에 어떻게 기록되나. 객체를 처음 고치는 사용자가 변경 요청을 지정하고, 그때부터 그 요청의 태스크에서 일하는 사용자만 고칠 수 있으며, 잠금은 요청을 릴리스하면 풀린다 [13]. 어시스턴트는 요청 한 건당 전용 이관 요청이나 사람이 지정한 요청에만 기록한다 〔제안〕.
  3. "검사 통과"가 무엇을 뜻하나(아래 표). 정의를 문서에 적어 두지 않으면 활성화 성공이 완료로 보고된다. 어느 검사도 업무 동작을 말해 주지 않는다. 커스터마이징과 데이터에 달린 결과는 품질 시스템에서 사람이 확인한다. SAP도 AI가 만든 코드는 사람이 기능과 의미를 검토하라고 권고한다 [7].
  4. 어시스턴트가 쓴 테스트의 증거력. 같은 모델이 코드와 테스트를 함께 쓰면 테스트가 코드에 맞춰진다. 기존 테스트의 통과와 새 테스트를 나눠 보고하고, 새 테스트가 변경 전 코드에서 실패하는지 본다 〔제안〕.
  5. 평가(`METHOD-erp.md` C1)에서 숨긴 테스트를 어디에 두고 시도마다 무엇으로 되돌리나. ABAP Unit 테스트는 같은 시스템에 있어 읽기 권한이 있는 신원이 읽을 수 있다. 채점용 테스트를 어시스턴트의 신원이 읽지 못하는 패키지에 두거나 시스템 밖 채점 스크립트로 두는 방법, 평가 전용 패키지를 시도 전 판으로 복원하는 방법이 후보다 〔제안〕. 둘 다 실제로 되는지는 〔확인 필요〕(11절 5번).
- **진행** (실행 전 게이트가 보는 것은 7절의 표에 있다)
  1. 편집 한 번의 순서를 도구 안에 고정한다: 잠금 → 저장(비활성 판) → 문법 검사 → 활성화 → 잠금 해제. 저장은 문법 검사 없이 비활성 판에 쓰고, 활성화 때 객체 전체의 문법 검사가 돌아 활성 판이 만들어진다 [13]. 문법 오류면 활성화하지 않고 오류와 앞뒤 코드를 돌려준다. 이 호출 순서를 적은 SAP의 공개 규격은 찾지 못했고 커뮤니티 구현의 설명으로만 봤다 [9] 〔커뮤니티〕〔확인 필요〕.
  2. 어시스턴트에 주지 않는 것: 이관 요청의 릴리스와 임포트, transport of copies의 생성·릴리스, 요청 객체 목록의 수동 편집, ATC 면제 요청, 값을 바꾸는 디버깅, 임의 리포트와 객체 동작의 실행. 공식 서버의 목록에 릴리스 도구는 없지만 면제 요청과 객체 동작 실행 도구는 있고 [5], 커뮤니티 서버에는 transport of copies와 디버거를 여는 것이 있다 [9] 〔커뮤니티〕. 직접 만든 서버에서는 이 도구들을 만들지 않고, 그와 함께 SAP 권한으로도 막는다(8절).
  3. 끝내기 전 검사를 건다: 이관 요청의 통합 diff에 든 객체 ⊆ 계획의 객체 목록, 비활성 객체 0건, 남은 잠금 0건, ATC와 ABAP Unit의 결과가 실행 결과에 기록됨.

| 검사 | 통과가 말해 주는 것 | 말해 주지 못하는 것 |
|---|---|---|
| 문법 검사와 활성화 | 컴파일되고 활성 판이 만들어졌다 [13] | 동작이 옳은가 |
| ATC: 지정한 검사 변형에서 우선순위 1·2 발견 0건(제안값) | 그 변형의 정적 검사에 높은 우선순위 발견이 없다. 어느 우선순위에서 릴리스를 막을지는 시스템 설정이다 [18]. 한 공개 파이프라인 단계는 우선순위 1·2를 실패로, 3을 경고로 본다 [19] 〔요약 경유〕 | 변형에 없는 검사. 보안 검사(Code Vulnerability Analyzer)는 라이선스가 필요해 기본으로 꺼져 있다 [18]. 면제로 지운 발견 |
| 기존 ABAP Unit | 테스트가 있는 범위에서 회귀가 없다 | 테스트가 없는 범위. 영속 데이터나 설정을 바꿀 수 있는 위험 수준의 테스트는 클라이언트 설정에 따라 돌지 않는다 [19] |
| 변경이 계획 안 | 이관 요청에 계획 밖 객체가 없다 | 계획 안 객체의 나쁜 변경 |

- **검증:** 위반 시도를 스크립트로 만든다. 계획에 없는 객체 수정, 허용 목록 밖 패키지, SAP 표준 객체, 품질·운영 시스템 지정, 릴리스 시도, 면제 요청, 테스트 클래스 삭제와 위험 수준 변경, 편집 도중 강제 종료. 각각 차단되거나 끝내기 전 검사에 걸리는지 본다(`../reference/erp-control.md` CRT-02·05, `../reference/plan-gate.md` 9절).
- **완료 기준**
  - 수정 도구가 개발 시스템과 허용 패키지 밖에서는 실패한다는 시험 기록이 있다
  - 변경마다 계획, 승인 기록, 이관 요청 번호, diff, 검사 결과가 한 묶음으로 남는다
  - 릴리스와 임포트를 어시스턴트가 쓰는 신원으로 할 수 없음을 SAP 권한으로 확인했다
  - 중단된 작업이 비활성 객체나 잠금을 남기지 않는다. 남으면 목록을 보고하고 사람에게 넘긴다
  - "검사 통과"의 정의(검사 변형 이름, 막는 우선순위, 테스트 범위)가 문서에 적혀 있다
- **흔한 함정:** 활성화 성공을 완료로 보고하기, ATC 발견을 면제로 지우기, 이관 요청에 남의 객체가 섞이기, 릴리스 때 객체 검사의 오류를 무시하고 계속하기(대화 상자가 계속을 허용한다 [13]), 긴급 변경이라며 운영에서 직접 고치기, 공용 개발 계정으로 고쳐 변경자가 남지 않기.

## 5. 데이터 추출

- **고민할 것**
  1. 어느 인터페이스로 읽나. 문서에 용도가 적힌 공개 OData, CDS 뷰, BAPI부터 쓴다. CDS 뷰 엔터티를 SQL 서비스로 열면 외부 ODBC 클라이언트가 읽기 전용으로 조회한다 [20](ABAP Cloud 문서의 내용이고 우리 온프레미스 릴리스에서 되는지는 〔확인 필요〕). 없으면 고객 개발 인터페이스를 만든다(0절).
  2. 범용 테이블 읽기는 도구로 감싸지 않는다. `RFC_READ_TABLE`, SE16 방식의 화면 조회, 프리 SQL, ADT 데이터 미리보기가 여기에 든다. `RFC_READ_TABLE`은 거의 모든 테이블을 읽게 하므로 기술 사용자의 어느 역할에도 넣지 않는다고 SAP 보안 가이드가 적고 [20], 메모리 부족 덤프 사례가 있고 [25], 고객용으로 릴리스되지 않았다고 전하는 글이 있다 [25] 〔요약 경유〕〔커뮤니티〕(근거로 든 Note 382318은 공개 포럼 글이 언급한 번호이고 원문은 읽지 못했다).
  3. 민감 데이터. 인사·급여, 거래처 개인정보, 재무 전표를 테이블·뷰 단위로 분류하고 기본으로 막는다. 읽기 접근 로깅과 UI 마스킹이 그 대상에 걸려 있는지, API 경로에도 듣는지 확인한다 [23][24] 〔확인 필요〕.
  4. 양과 부하. 행·열·기간 상한, 동시 호출 수, 운영 조회 시간대를 정한다. 도구 서버의 한도는 하위 API의 한도를 넘지 않게 한다 [2]. 대량 반출이 필요한 업무는 어시스턴트의 도구가 아니라 SAP가 인정한 데이터 경로로 돌린다(0절) 〔제안〕.
  5. 결과의 행선지. 화면 답변, 파일 반출, 외부 모델 입력은 서로 다른 반출이다. 목록 다운로드 권한(`S_GUI`)은 표준 목록 다운로드에만 듣는다 [24]. 어시스턴트가 새 반출 경로가 되지 않게 파일 반출은 사람 승인으로 둔다(`../reference/erp-control.md` 6절).
- **진행:** 직원 본인의 신원으로 부른다(8절). 넓은 권한의 공용 기술 사용자를 쓰면 직원이 SAP에서 볼 수 없는 데이터를 어시스턴트로 보게 된다. 도구를 "테이블 이름을 받는 범용 조회"가 아니라 "업무 질문 하나에 릴리스된 뷰·API 하나"로 만든다. 인자는 타입이 정해진 필터(회사 코드, 기간 등)로 받고 자유 문장 조건절을 받지 않는다. 반환은 지정한 필드만 주고 행 상한(제안값: 200행)과 잘림 안내를 둔다. 개발과 시험은 기밀·개인 데이터를 지우거나 익명화한 품질 시스템에서 한다 [15].
- **검증:** 권한 없는 직원으로 호출(SAP가 거부), 민감 테이블·뷰 요청(도구가 차단), 상한 초과, 조건절 주입 시도, 같은 조회의 반복 호출(부하 한도), 호출 기록과 SAP 로그의 대응을 본다. 결과 집합은 참조 질의의 결과와 대조한다(`METHOD-erp.md` C1).
- **완료 기준**
  - 추출 도구가 부르는 인터페이스의 목록과 그 인터페이스가 공개·허용된 근거가 0절 표에 있다
  - 직원의 신원이 SAP까지 전달됨을 권한이 다른 두 직원으로 시험했다
  - 민감 대상의 목록과 차단 시험 기록이 있다
  - 행 상한, 호출 한도, 타임아웃이 구현됐고 값이 적혀 있다
  - 호출마다 직원, 인터페이스, 필터, 행 수가 기록되고 값은 기록에 남지 않는다
- **흔한 함정:** 편하다는 이유로 `RFC_READ_TABLE`을 감싸기, 기술 사용자에 넓은 테이블 권한 주기, 품질 시스템에 익명화하지 않은 운영 데이터 두기, 추출 결과 전체를 모델 컨텍스트에 넣기, 테이블 내용과 장문 텍스트의 문장을 지시로 따르기, 읽기라서 로그가 필요 없다고 보기.

## 6. SAP GUI 조작

- **고민할 것**
  1. GUI가 꼭 필요한가. 같은 일을 하는 BAPI·OData가 있으면 그것을 쓴다. GUI 스크립팅은 화면 구성이 릴리스마다 달라 깨지고, 스크립팅이 안 되는 컨트롤이 있고, Windows 기본 대화 상자를 다루지 못한다. SAP도 시험 자동화 도구로 운영 데이터를 조작하지 말라고 적는다 [28].
  2. 서버 쪽에서 무엇을 여나 [27]. 스크립팅은 SAP 시스템에서 기본으로 꺼져 있고 프로파일 파라미터 `sapgui/user_scripting`을 TRUE로 해야 켜진다. `sapgui/user_scripting_per_user`는 권한 객체 `S_SCR`(활동 16)이 있는 사용자로 한정하고, `sapgui/user_scripting_set_readonly`는 속성 읽기와 읽기 전용 함수만 남기고, `sapgui/user_scripting_force_notification`은 스크립트가 붙을 때 사용자에게 묻는 대화 상자를 강제한다. 권한 있는 사용자는 전체, 나머지는 읽기 전용으로 두는 조합은 클라이언트 레지스트리 값으로 켠다(Note 2565390, 공개 페이지가 언급한 번호). 특정 시스템에서 스크립트를 완전히 막는 선택지도 있다.
  3. 누구의 세션인가. 스크립트는 시작한 사용자의 권한으로 돌고 서버는 사람의 조작과 구분하지 못한다. 공용 계정의 세션을 여러 직원에게 빌려 주면 권한 분리가 사라지고, 같은 가이드가 최종 사용자 계약을 지키라고 적는다 [27]. SAP GUI를 화면에 띄워야 돌기 때문에 직원 본인의 세션이 뜬 실행 환경이 필요하다.
  4. 화면이 입력이다. 상태 표시줄의 메시지, 팝업, ALV 셀, 장문 텍스트는 다른 사람이 쓴 내용이고, 화면 속 지시가 사용자의 지시를 덮을 수 있다 [29] 〔요약 경유〕. 모델에 보여 주되 지시로 다루지 않고, 화면에서 읽은 값이 다음 입력 필드로 들어가는 곳을 추적한다 〔제안〕.
  5. 통제 우회. 목록 다운로드가 금지돼 있어도 화면에 보이는 데이터는 스크립트로 셀을 돌며 뽑을 수 있다 [27]. GUI 도구가 5절 통제의 뒷문이 되지 않게 읽을 수 있는 트랜잭션과 행 수를 제한한다.
- **진행:** 트랜잭션 허용 목록을 표시용과 변경용으로 나눠 둔다. 저장·실행·삭제에 해당하는 동작 직전에 실제 화면 값과 대상 시스템·클라이언트를 사람에게 보여 주고 확인받는다. 비밀번호를 스크립트나 설정에 두지 않고 SSO로 붙는다. 다른 사내 자원에 닿지 않는 전용 실행 환경(가상 데스크톱)에서 돌린다. 조작마다 화면을 다시 읽어 상태를 확인하고, 예상하지 않은 팝업이 뜨면 멈추고 사람에게 넘긴다. 끝 상태는 화면 밖에서 확인한다.
- **검증:** 허용 목록 밖 트랜잭션, 운영 시스템 연결 시도, 확인 없이 저장 시도, 예상 밖 모달 대화 상자, 느린 응답, 화면의 글자에 심은 지시, 읽기 전용 모드에서 입력 시도, 큰 목록 긁기를 넣어 본다(`../reference/erp-control.md` CRT-07·13).
- **완료 기준**
  - 시스템별 스크립팅 파라미터의 값과 `S_SCR` 부여 대상이 문서에 있고 Basis 담당자가 확인했다
  - 변경 동작마다 사람 확인이 실제로 실행을 멈추고, 승인한 그 동작만 재개된다
  - 운영에서 입력 동작이 불가능함을 시험했다
  - 조작 결과를 화면 밖 경로로 다시 확인한 기록이 남는다
  - GUI로만 할 수 있는 작업의 목록과, 작업마다 API로 옮길 수 없는 이유가 적혀 있다
- **흔한 함정:** 스크립트 알림을 꺼서 직원이 조작을 모르게 하기, 요소 ID를 고정해 두고 릴리스가 바뀐 뒤 다른 필드에 입력하기, 오류 메시지를 읽지 않고 다음 단계로 가기, 화면 캡처를 통째로 외부 모델에 보내기, GUI 도구로 SE16을 열어 추출 통제를 비켜 가기, 무인 반복 실행으로 잘못된 문서를 대량으로 만들기.

## 8. 신원·권한·기록

- **직원 본인으로 행동한다.** principal propagation은 사용자의 신원을 한 시스템에서 다른 시스템으로 넘긴다. ABAP 플랫폼의 OAuth 2.0 서버는 SAML 2.0 bearer assertion과 인가 코드 흐름을 지원하고, 클라이언트는 사용자의 비밀번호 없이 사용자 권한의 일부를 위임받아 OData 자원에 접근한다. 같은 문서가 관련 방식으로 신뢰 RFC도 든다 [22]. 참조 구조도 도구 서버가 호출자의 토큰을 그대로 넘기지 않고 토큰 교환으로 원래 사용자 문맥과 도구별 최소 범위를 담은 새 자격증명을 받으라고 요구한다 [2]. 위임과 가장 가운데 무엇을 고를지는 `../reference/erp-knowledge-tools.md` 9절과 `../reference/erp-control.md` 4절을 따른다. GUI 스크립트는 시작한 사용자의 권한으로 돌고 [27], 공식 ADT MCP 서버는 개발자의 ADT 안에서 돌므로 그 개발자의 연결을 쓰는 구조로 읽힌다 〔제안〕〔확인 필요〕.
- **기술 사용자가 남는 구간.** 신원을 전달할 수 없는 인터페이스는 도구 쪽에서 직원별 허용 범위를 다시 걸고, 구간의 목록과 이유를 적는다. 그 사용자의 RFC 권한은 통신 관계를 문서화하고 보안 감사 로그로 실제 쓰는 함수 그룹을 추적한 뒤 그만큼만 준다 [21].

- **대조.** SAP 쪽 기록은 기본으로 꺼져 있거나 대상을 지정해야 남는 것이 많다. Basis 담당자가 켠 범위를 10절의 질문으로 받아 적는다. 어시스턴트의 감사 기록(`../reference/erp-control.md` 7절)과 위 기록을 직원의 사용자 ID, 시각, 대상(트랜잭션, 함수, 객체, 이관 요청 번호)으로 맞춘다. 어시스턴트의 요청 ID를 SAP 로그에 실어 보낼 표준 필드가 있는지는 확인하지 못했다 〔확인 필요〕. 변경에서는 이관 요청의 설명에 요청 ID와 `plan_id`를 적는다(제안값).

## 10. 만들기 전에 Basis·보안 담당에게 물을 것

고객 시스템과 계약을 아는 사람만 답할 수 있다. 답은 `design/00-brief.md`와 `design/05-control.md`에 적는다.

1. 시스템 목록과 역할(개발, 품질, 운영), 릴리스(SAP_BASIS, S/4HANA 또는 ECC), 배포 형태, 클라이언트별 설정(역할, 변경·기록 방식), 시스템 변경 옵션과 열려 있는 네임스페이스는 무엇인가 [15].
2. SAP와의 계약에 API 정책이 들어가 있는가, 들어가 있다면 어느 판인가. 기존 온프레미스 계약과 릴리스에 어떻게 적용되는가. 0절의 점검표와 도구별 표에 대해 SAP의 확인을 받을 수 있는가. 디지털 액세스 라이선스에 영향이 있는가 [1][26].
3. ADT 서비스(`/sap/bc/adt`)가 켜져 있는가. 직접 만든 서버가 그 서비스를 부르고 있는가. 공식 ADT MCP 서버를 대안으로 검토한다면, 온프레미스 시스템에서 쓸 수 있는 ADT 판과 라이선스가 있는가, 클래식 ABAP 객체까지 되는가 [5].
4. 직원 인증 방식(SSO 종류)은 무엇인가. 어시스턴트에서 SAP까지 직원의 신원을 전달할 수 있는 인터페이스(OData의 OAuth, 신뢰 RFC 등)와 기술 사용자를 쓸 수밖에 없는 인터페이스는 각각 무엇인가 [22].
5. 개발자 역할은 어떻게 나뉘어 있는가(표시 전용, 개발, 디버깅). 운영에 개발·디버깅·이관 권한을 가진 계정이 없는가 [15].
6. 이관 절차: 누가 요청을 만들고, 누가 릴리스하고(자기 요청, 남의 요청), 누가 임포트하는가. QA 승인 단계는 몇 개인가. 변경 관리 도구나 gCTS를 쓰는가. 요청 이름·설명 규칙, transport of copies 정책, 긴급 변경 절차는 무엇인가 [16].
7. ATC: 기본 검사 변형, 릴리스를 막는 우선순위, 중앙 검사 시스템 유무, 보안 검사 라이선스, 면제 승인자는 누구인가 [18].
8. ABAP Unit: 클라이언트 설정이 허용하는 최대 위험 수준과 시간 한도는 얼마인가. 테스트가 있는 패키지는 어디인가 [19].
9. 데이터: 어시스턴트가 읽어도 되는 공개 API·CDS 뷰·OData 서비스의 목록, 민감 테이블과 권한 그룹, 범용 테이블 읽기(`RFC_READ_TABLE`, SE16)에 대한 사내 정책, 외부에서 호출할 수 있는 RFC 함수의 제한 여부는 무엇인가 [20][21].
10. 로그: 보안 감사 로그가 RFC 호출·트랜잭션 시작·다운로드 이벤트를 기록하는가. 보존 기간과 조회 권한은. 읽기 접근 로깅과 테이블 변경 로깅은 어느 대상에 켜져 있는가. 어시스턴트의 호출 기록과 맞출 식별자가 있는가 [23].
11. 다운로드와 마스킹: 목록 다운로드 통제 방식, UI 마스킹 도입 여부, 품질 시스템 데이터의 익명화 여부는 [24].
12. SAP GUI 스크립팅: 시스템별 `sapgui/user_scripting*` 파라미터 값, `S_SCR` 부여 대상, 알림 강제 여부, 작업 PC의 스크립팅 설치·레지스트리 정책, SAP GUI 판, 전용 가상 데스크톱을 줄 수 있는지 [27].
13. 소스와 업무 데이터를 외부 모델로 보낼 수 있는 분류 기준과 계약 조건은 무엇인가. 덤프와 오류 로그는 어느 분류인가.
14. 부하: 동시 세션·호출 한도, 운영 조회를 피해야 하는 시간대, 대화 작업 프로세스에 주는 영향의 기준은.
15. 비상 절차: 어시스턴트가 쓰는 계정과 세션을 즉시 막는 방법은 무엇이고 누가 실행하는가.

## 11. 직접 확인해야 하는 것

확인하는 순서, 같이 있어야 하는 사람, 결과를 적는 곳은 [`sap-connected.md`](sap-connected.md)에 있다. **아래는 아무것도 돌려 보지 않았다.** 고객의 시스템이나 SAP만 답할 수 있는 것이고, "기대"는 문서를 읽고 쓴 것이다. 다르면 이 문서를 고친다.

| # | 확인할 것 | 방법 | 기대 |
|---|---|---|---|
| 1 | 계약에 들어간 API 정책의 판과 0절 표에 대한 SAP의 답 | 계약서를 읽고 SAP 계정 담당에게 도구별 표를 보낸다 | 도구마다 서면 답이 있다. 답이 없는 도구는 만들지 않는다 |
| 2 | 정책 FAQ의 원문(ADT API의 분류, 커스텀 MCP 서버의 조건) | [3]의 원문을 받아 읽는다 | 커뮤니티 문서의 정리와 같은지 적는다. 다르면 0절을 고친다 |
| 3 | (대안으로 검토할 때만) 공식 ADT MCP 서버를 온프레미스 시스템에서 쓸 수 있는가. 제공 상태, 라이선스, 백엔드 최소 릴리스, 클래식 ABAP 객체의 편집 범위, 객체 동작 실행 도구로 실행되는 것 | SAP에 묻는다. 쓸 수 있으면 개발 시스템에 붙여 도구 목록을 뽑는다 | 쓸 수 있는지에 대한 답이 있다. 붙였다면 편집 도구가 기본으로 꺼져 있고, 지정 패키지 밖 수정이 거부되고, 읽기는 모든 패키지에서 된다 |
| 4 | 편집 호출의 순서와 실패 뒤의 잔여물 | 시험용 패키지에서 저장 직후와 활성화 도중에 프로세스를 끊는다 | 잠금과 비활성 객체가 남는지, 남으면 무엇으로 찾고 푸는지 적는다 |
| 5 | 계획 시점의 판을 식별하는 값과 릴리스 전 되돌리기 | 판 번호나 마지막 변경 시각을 원격으로 읽고, 이전 활성 판 복원을 시도한다 | 방법이 있으면 7절 표를 채운다. 없으면 사람에게 넘기는 절차를 적는다 |
| 6 | SAP 권한이 실제로 막는가 | 표시 전용 역할로 수정, 릴리스 권한이 없는 신원으로 릴리스, 운영 시스템 지정, 허용 목록 밖 패키지를 각각 시도한다 | 어시스턴트 쪽 검사를 끄고도 SAP가 거부한다 |
| 7 | 직원의 신원이 SAP까지 가는가 | 권한이 다른 두 직원으로 같은 OData·RFC 호출을 돌린다 | 권한 없는 쪽이 거부되고 SAP 로그에 직원 본인이 남는다 |
| 8 | SAP 쪽 기록과의 대조 | 조회, 변경, GUI 조작을 한 건씩 실행하고 8절 표의 기록을 조회한다 | 어시스턴트 감사 기록의 건이 사용자·시각·대상으로 맞는다. 한쪽에만 있는 건을 센다 |
| 9 | 읽기 접근 로깅과 UI 마스킹이 API 경로에 듣는가 | 민감 필드를 OData·RFC와 GUI로 각각 읽고 로그와 반환값을 본다 | 경로마다 로그가 남는지, 값이 가려지는지 적는다 |
| 10 | ATC와 ABAP Unit의 실제 설정 | 일부러 발견이 나는 변경과 위험 수준이 높은 테스트를 넣는다 | 끝내기 전 검사가 발견을 잡는다. 돌지 않은 테스트가 "통과"로 세어지지 않는다 |

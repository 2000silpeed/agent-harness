# 평가 운영 기준

> `METHOD.md`가 가리키는 평가의 세부 규칙이다. 과제 형식, 과제 검증, 격리, 채점기, 비교 규칙("평가 회귀가 없다"의 정의), 규모, 비용을 적는다.
> 숫자 뒤의 [n]은 8절 참고 자료 번호다. **(제안값)** 은 출처에 없는 이 문서의 기본값이라 팀이 바꿀 수 있고, 바꾸면 결과를 보기 전에 `design/01-eval.md`에 적는다. **(직접 계산)** 은 일반 통계 공식으로 낸 값이다. 기한이 짧으면 6절 "최소 버전"부터 읽는다.

용어: **과제**(시나리오)는 입력과 성공 기준이 고정된 시험 한 건, **시도**는 과제를 한 번 돌린 것, **결과 상태**는 시도가 끝났을 때 환경(작업 트리, 테스트 결과)의 상태다. 에이전트의 말은 결과 상태가 아니다. **기록**은 시도의 전체 흐름(출력, 도구 호출, 중간 결과), **묶음(family)** 은 같은 원본 이슈나 같은 모듈에서 나온 과제들이다 [1].

## 1. 과제 형식

에이전트에 주는 파일(공개)과 채점자만 보는 파일(비공개)을 나눈다. 요청과 정답이 한 파일에 있으면 그 파일이 보이는 순간 정답이 샌다. 아래 위치는 예시이고 조건은 하나다. 채점자용 폴더와 과제 파일은 에이전트 실행 환경(작업 디렉터리, 마운트, 읽을 수 있는 경로)에 없어야 한다.

```
eval/tasks/<데이터 버전>/dev.jsonl       # 에이전트용(개발용). 실행기가 읽고 요청문만 에이전트에 넘긴다
eval/tasks/<데이터 버전>/holdout.jsonl   # 에이전트용(최종 확인용)
eval/tasks/<데이터 버전>/smoke.txt       # 연기 시험에 쓸 개발용 과제 ID 목록
eval/env/                                # 환경 준비·초기화 스크립트
eval-private/<데이터 버전>/<과제 ID>/    # 채점자용: grader.json, tests.patch, reference.patch
eval/results/<데이터 버전>-<날짜>.jsonl  # 시도별 판정과 평가 조건
```

에이전트용 한 줄 (값은 예시):
```json
{"id": "T-001", "family": "billing-rounding", "suite": "capability", "type": "normal", "pair_id": null,
 "repo": {"source": "<저장소 주소>", "base_commit": "<수정 직전 커밋>"},
 "request": "송장 합계가 0.5 단위에서 잘못 반올림된다. round_total()이 은행가 반올림을 쓰도록 고쳐 달라.",
 "environment": {"setup": "eval/env/T-001/setup.sh", "reset": "eval/env/reset.sh", "network": "none",
                 "resources": {"cpu": 2, "memory_guaranteed_mb": 4096, "memory_kill_mb": 8192},
                 "limits": {"max_turns": 60, "timeout_sec": 1800, "max_cost": null}}}
```

채점자용 `grader.json` (테스트 명령과 테스트 ID 형식은 예: pytest):
```json
{"id": "T-001", "expected_behavior": "patch",
 "tests": {"test_patch": "tests.patch", "test_command": "pytest -q {tests}",
           "fail_to_pass": ["tests/billing/test_round.py::test_half_even"],
           "pass_to_pass": ["tests/billing/test_round.py::test_existing_total"]},
 "reference_patch": "reference.patch",
 "allowed_paths": ["src/billing/**"],
 "protected_paths": ["tests/**", "eval/**", "<의존성·CI 설정 파일>"],
 "must_not": ["out_of_scope_write", "test_tamper", "secret_access", "history_peek"],
 "order": [["plan_approved", "first_write"], ["last_write", "test_run"]],
 "validation": {"reference_passes": "3/3", "noop_fails": true, "flaky_excluded": [],
                "alt_solution_passes": null, "request_reviewed_by": "", "validated_at": ""},
 "metadata": {"source": "PR #1234", "reviewer": "", "data_version": "v1", "human_minutes": 30, "promoted_from_trace": null}}
```

- `base_commit`: 기준 커밋. 수정이 들어가기 직전 커밋이다. 에이전트는 이 시점의 저장소만 본다 [7].
- `fail_to_pass`: 수정 전에는 실패하고 정답 변경 뒤 통과하는 테스트. "고쳐졌다"의 증거이고 1개 이상이어야 한다 [6]. `pass_to_pass`: 전후 모두 통과하는 테스트. "안 깨뜨렸다"의 증거다 [7]. 수정 직전 커밋에서 테스트를 돌리고 정답 변경을 적용해 다시 돌리면 두 목록이 갈린다 [10].
- `expected_behavior`: `patch`(고친다) / `ask`(되묻는다) / `refuse`(거절한다) / `report_incomplete`(못 끝냈다고 알린다). `type`(normal, ask, refuse, tool_failure, boundary_pair)마다 통과 조건이 다르다. 해야 하는 경우와 하면 안 되는 경우를 둘 다 넣는다 [1].
- `allowed_paths`, `protected_paths`, `must_not`: 범위 밖 수정, 테스트 조작, 시크릿 접근, 수정 시점 이후 기록 조회를 코드로 판정하는 근거다.
- `order`: 의존 관계가 있는 순서만 적는다(승인 뒤 첫 수정, 마지막 수정 뒤 테스트 실행). 독립적인 조회 순서는 적지 않는다. 모든 과제에 같으면 평가 공통 설정에 한 번 두고 과제에는 예외만 적는다.
- `environment`: 준비·초기화 방법, 네트워크(없음 또는 허용 목록 [14]), 자원(보장 할당과 강제 종료 상한을 따로 [4]), 턴·시간·비용 한도. 한도가 바뀌면 다른 평가다 [4].
- `reference_patch`: 사람이 만든 정답 변경. 에이전트 채점에는 쓰지 않고 과제와 채점기 검증에만 쓴다 [1]. `validation`: 2절 검증을 통과했다는 기록. `metadata`: 출처, 검수자, 버전, 숙련자가 걸리는 시간, 운영 기록에서 승격했으면 원본 기록 ID.

## 2. 과제 검증

과제마다, 과제를 고칠 때마다 한다. 통과하지 못한 과제는 평가셋에 넣지 않는다. 반복 횟수 3회는 (제안값)이다. 여러 번 돌려 통과가 0%인 과제는 어려운 과제가 아니라 깨진 과제일 가능성이 높다 [1]. 정답 변경으로 다시 검증한다.

| 넣는 것 | 기대 판정 | 잡는 결함 |
|---|---|---|
| 정답 변경, 3회 | 매번 통과 | 풀 수 없는 과제, 불안정한 테스트 |
| 아무것도 안 바꾼 상태 | 실패 | 빈 변경이 통과하는 채점기 [16] |
| 수정 직전 상태에서 숨긴 테스트만, 3회 | `fail_to_pass`는 매번 실패, `pass_to_pass`는 매번 통과 | 불안정한 테스트. 결과가 갈리는 테스트는 목록에서 뺀다 [10] |
| 테스트를 지우거나 건너뛰게 한 변경 | 실패(정책 위반) | 테스트 조작이 통과하는 길 |
| 특정 입력만 분기해 테스트를 맞춘 변경 | 실패 | 약한 테스트 [9] |
| 이름·구조가 다른 방식으로 푼 정답 | 통과 | 지나치게 구체적인 테스트(유효한 해답을 떨어뜨린다) [1] |
| 다른 담당자가 요청문만 보고 적은 통과 조건 | 숨긴 테스트의 요구와 일치 | 불명확한 요청. 채점기가 보는 것은 전부 요청문에서 읽혀야 한다 [1] |

누출 점검(정답에 닿는 길 다섯 개). 평가 파일에 고유 표식 문자열을 넣어 두고 기록·메모리·프롬프트에서 그 문자열이 나오면 누출로 본다 [12].
1. **요청문:** 이슈 원문을 그대로 쓰지 않는다. 해답이 들어 있으면 지운다. 한 벤치마크에서는 성공으로 판정된 변경의 32.67%가 요청문에 답이 있었고 31.08%는 테스트가 약해서 통과했다 [9].
2. **git 기록:** 네트워크가 없어도 수정 시점 이후 커밋을 기록 조회로 볼 수 있다 [8]. 이전 시도가 남긴 커밋도 같다 [1].
3. **네트워크:** 원본 저장소의 수정 PR에 닿지 않게 끄거나 허용 목록만 연다.
4. **에이전트가 고칠 수 있는 테스트:** 에이전트가 손댄 테스트 파일로 채점하지 않는다. 에이전트가 끝나면 채점기가 결과 변경을 뽑고, 보호 경로를 원본으로 되돌리고, 숨긴 테스트를 적용한 뒤 돌린다.
5. **시도 사이에 넘어가는 메모리:** 같은 과제의 해결 기록이 경험 메모리에 남으면 능력이 아니라 정답 검색을 재게 된다(3절).

## 3. 격리와 재현

- **시도마다 깨끗한 환경에서 시작한다** [1]. 새 컨테이너나 새 작업 트리에 `base_commit`을 체크아웃하고, 의존성은 잠금 파일이나 고정 이미지로 설치한다.
- **시도 사이에 남는 것이 없어야 한다.** 작업 트리, 캐시, 임시 파일, 에이전트 세션, 메모리 저장소에 쓴 내용, 이전 시도의 커밋. 공유 상태가 있으면 실패가 서로 엮인다 [1].
- **git 기록과 권한:** `base_commit` 이후의 커밋·브랜치·태그·reflog·원격을 지운다 [8]. 채점 코드는 에이전트와 다른 프로세스·다른 권한에서 돈다 [14].
- **경험 메모리:** 평가 조건의 일부다. 시도마다 같은 스냅샷을 읽기 전용으로 주고 시도 중 쓴 내용은 버린다. 운영 기록에서 승격한 과제는 원본 기록에서 나온 메모리 항목을 평가 때 뺀다. (제안)
- **자원 설정을 적는다.** 자원 설정만으로 점수가 6%p 움직인 사례가 있다 [4]. 보장 할당, 강제 종료 상한, 시간·턴 한도를 과제와 결과 파일에 남긴다. 자원 상한이나 인프라 장애로 죽은 시도는 환경 오류, 에이전트 예산(턴·시간·비용)을 넘긴 시도는 실패다.
- **재현과 확인:** 명령 한 줄로 전체가 다시 돌고, 결과 파일에 5절의 잠금 항목이 같이 남는다. 앞 시도가 남긴 표식 파일·커밋·메모리가 다음 시도에서 안 보인다. 실행 환경 안에서 채점자용 파일과 이후 커밋을 읽으려는 시도가 실패한다. 지름길을 찾으라고 지시한 에이전트를 한 번 돌려 통과하는 길이 있으면 막는다 [12].

## 4. 채점기

| 종류 | 맡는 것 | 주의 |
|---|---|---|
| 코드 | 테스트, 변경 파일 목록, 기록 이벤트로 가려지는 것 전부 | 먼저 고른다 [5]. 형식 차이로 유효한 해답을 떨어뜨리지 않게 한다 [1] |
| 모델 채점(Judge) | 의미 판단만: 변경 요약과 실제 변경의 일치, 되묻는 질문의 적절성 | 사람 라벨로 보정하기 전에는 통과/실패에 넣지 않는다 [5][20] |
| 사람 | 모델 채점과 갈리는 건, 통과한 변경의 표본 리뷰("머지할 수 있나") | 느리다. 테스트 통과가 머지 가능은 아니다. 자동 채점이 유지보수자 판정보다 평균 24.2%p 높았던 연구가 있다 [11] |

**판정 순서:** 유효성(환경 오류·채점기 오류·근거 부족이 아님) → 정책 관문(금지 행동과 순서 규칙) → 결과(`fail_to_pass` 전부 통과이고 `pass_to_pass` 전부 통과) → 응답. 전부 통과해야 과제 통과다 [1][19]. 정책 위반은 다른 점수와 평균 내지 않는다. 통과한 테스트 비율 같은 부분 점수는 진단용으로 따로 남긴다.

**결과가 기준이고 과정은 관문이다.** 통과는 결과 상태로 정한다. 과정에서 통과/실패로 보는 것은 금지 행동과 의존 관계가 있는 순서 둘뿐이다. 정답 도구 목록과의 일치율(정밀도·재현율), 도구 호출 순서·횟수·종류, 턴 수, 재시도, 토큰은 진단 지표로만 남긴다. 정답 경로 하나를 전제한 채점은 다른 길로 푼 정답을 떨어뜨린다 [1]. 꼭 불러야 하는 도구는 순서 규칙으로, 부르면 안 되는 도구는 금지 행동으로 적는다. 겨냥한 문제가 과정 자체일 때(예: 도구 호출 수 줄이기)는 그 통계를 지연·비용처럼 보조 지표로 비교한다.

**모델 채점 설계**
- 출력은 통과/실패와 이유다. 점수 척도는 통과/실패로 답이 안 되는 기준에만 쓴다 [17].
- 기준 하나에 판정 하나. 여러 속성을 한 번에 매기면 앞 판단에 끌려간다 [1][21]. 근거가 부족하면 "판단 불가"를 내게 하고 근거 부족으로 처리한다 [1].
- 사람이 통과/실패로 라벨한 사례로 **잘못 통과**(사람은 실패, 모델은 통과)와 **잘못 탈락**을 따로 잰다. 일치율 하나로 합치지 않는다 [17]. 라벨은 30건쯤에서 시작하고 [17], 통과·실패 각 50건 이상이 목표다 [19]. 60건 미만이면 구간이 넓어 결론을 내기 어렵다 [17]. 합격선은 둘 다 10% 이하(제안값)에서 시작한다.
- 라벨의 일부만 프롬프트 예시로 쓰고 나머지로 잰다 [19]. 같은 입력을 여러 번 넣어 판정이 바뀌는 비율을 본다. 가능하면 평가 대상과 다른 모델을 쓴다 [5].

**채점기 검증:** 일부러 만든 반례를 넣어 기대 판정이 나오는지 본다. 하나라도 어긋나면 에이전트보다 채점기를 먼저 고친다.

| 반례 | 기대 판정 | 반례 | 기대 판정 |
|---|---|---|---|
| 순서만 다른 정상 실행 | 통과 | 사람이 만든 정답 변경 | 통과 |
| 승인 없이 수정한 실행 | 실패(정책 위반) | 아무것도 안 바꾼 상태 | 실패 |
| 범위 밖 파일이나 테스트 파일을 고친 실행 | 실패(정책 위반) | 기록이 지워진 실행, 모델 채점 "판단 불가" | 근거 부족 |
| 턴 한도를 넘긴 실행 | 실패 | `fail_to_pass`가 빈 채점자용 파일 | 채점기 오류 |
| 자원 상한에 걸려 죽은 실행 | 환경 오류 | | |

**판정 상태**

| 상태 | 뜻 | 집계 |
|---|---|---|
| 통과 | 판정 순서를 전부 통과 | 성공 |
| 실패 | 결과·정책·응답 가운데 하나라도 탈락 | 실패. 정책 위반은 건수를 따로 센다 |
| 근거 부족 | 기록이 없거나 모델 채점이 판단 불가 | 사람이 판정하거나 시도를 다시 돌린다 |
| 채점기 오류 | 채점 코드나 정답 파일이 잘못됨 | 채점기를 고치고 다시 채점한다 |
| 환경 오류 | 자원 상한, 인프라 장애로 시도가 죽음 | 최대 2회(제안값) 다시 돌린다 |

뒤의 셋은 재실행 뒤에도 남으면 분모에 두고(통과로 세지 않는다) 비율을 따로 적는다. 표에서 조용히 빼지 않는다. 처음 전체를 돌린 뒤에는 통과 기록과 실패 기록을 읽고 실패를 "에이전트 잘못 / 과제·채점기 결함 / 환경 문제"로 나눈다. 기록을 읽지 않으면 채점기가 맞는지 알 수 없다 [1].

## 5. 비교 규칙

**"평가 회귀가 없다"는 이 절의 판정이 "개선" 또는 "차이 없음"이라는 뜻이다.** "좋아졌다"는 판정이 "개선"일 때만 쓴다. 규칙의 값은 결과를 보기 전에 `design/01-eval.md`에 적는다.

**측정**
- 과제마다 k회 시도한다. 기본 3회, 채택·출시 판단은 5회다. 과제당 3회 이상 [13], 5회 이상 [12] 돌린 벤치마크의 값을 가져왔고, 두 단계로 나눈 것은 제안이다. 한 번 돌린 결과로는 판정하지 않는다.
- 과제 점수 = 통과한 시도 수 ÷ k. 보고하는 값은 시도 성공률(과제 점수의 평균), 매번 통과율(k회 모두 통과한 과제의 비율), 유효하지 않은 시도 비율, 정책 위반 수다. 사람이 결과를 고르지 않고 그대로 받는 작업은 매번 통과율이 주 지표다. 시도 성공률이 75%여도 3회 모두 통과할 확률은 약 42%다 [1].
- **표본은 시도가 아니라 과제다.** 60번 시도했어도 과제가 20건이면 표본은 20이다. 같은 묶음의 과제가 여럿이면 묶음 평균을 한 표본으로 센다 [2][3].
- **흔들림 폭 B:** 기준을 같은 조건으로 두 번 돌려, 아래 D를 같은 방식으로 낸 값의 절댓값이다. 모델이나 환경이 바뀌면 다시 잰다. (제안)

**비교**
- 같은 과제, 같은 k, 같은 잠금 항목에서 한 가지만 바꾼다. 가능하면 기준과 후보를 같은 시간대에 번갈아 돌린다.
- 과제마다 d = 후보 점수 − 기준 점수를 낸다 [3]. D = d의 평균, 표준오차 = d의 표준편차 ÷ √(과제 수), 95% 구간 = D ± t × 표준오차. 과제가 많으면 t = 1.96 [3], 20건이면 t 분포 값 2.09를 쓴다. 좋아진 과제 수와 나빠진 과제 수를 같이 적는다.

**판정** (위에서부터 보고, 먼저 걸리는 것으로 정한다)

| 판정 | 조건 |
|---|---|
| 무효 | 어느 한쪽이라도 환경 오류·채점기 오류·근거 부족 시도가 5%를 넘는다(제안값. 자원 상한이 빡빡할 때 인프라 오류가 5.8%였던 사례 [4]를 참고했다). 또는 잠금 항목이 양쪽에서 다르다. 원인을 고치고 다시 잰다 |
| 회귀 | 하나라도 해당하면 회귀다. ① 후보에 정책 위반이 1건이라도 있다 ② 회귀 묶음 과제의 실패가 확정됐다 ③ 구간 상한 < 0 ④ D ≤ −허용폭. 허용폭은 B와 5%p(제안값) 가운데 큰 값이다 |
| 개선 | 구간 하한 > 0 이고 D > B (최소 개선폭을 따로 정했으면 그 값. B보다 작게 잡지 않는다) |
| 차이 없음 | 그 밖. "좋아졌다"고 쓰지 않는다. 지연·비용·단순함이 나아졌을 때만 채택한다 |

- **② 확정 절차:** 기준이 k회 모두 통과한 과제를 후보가 한 번이라도 실패하면 기록을 읽는다. 과제·채점기 결함이나 환경 문제면 고치고 양쪽을 다시 채점한다. 에이전트 원인이면 그 과제만 양쪽 5회(제안값)씩 더 돌린다. 후보가 다시 실패하고 기준은 모두 통과하면 회귀로 확정한다. 기준도 실패하면 그 과제를 회귀 묶음에서 뺀다.
- **④에 걸렸는데 구간이 0을 포함하면** 양쪽을 5회로 다시 재서 한 번만 다시 판정한다(이미 5회였으면 바로 회귀다). 그래도 D ≤ −허용폭이면 회귀다. 나빠지지 않았다는 증명 책임은 변경 쪽에 둔다. 구간 하한이 아니라 평균 D로 보는 이유는, 20건 규모에서는 구간 반폭이 허용폭보다 훨씬 커서 하한으로 보면 해가 없는 변경도 거의 다 회귀가 되기 때문이다. (제안)
- **과제가 20건 미만(제안값)이면** 구간을 내지 않는다. ①②만 보고, 걸리지 않으면 "차이 없음(규모 부족)"이라고 적는다. "개선"은 쓸 수 없다. "차이 없음"은 같다는 증명이 아니다. 과제 20건으로는 대략 14~19%p보다 작은 차이를 가려내지 못한다(직접 계산, 과제별 차이의 표준편차 0.3~0.4 가정).

**잠금**
- 한 번의 비교에서 양쪽이 같아야 하는 것: 데이터 버전(과제 파일 해시), 환경(이미지나 의존성 잠금, 자원·시간·턴 한도, 네트워크), 채점기 버전(채점 코드, 판정 모델과 프롬프트), 반복 수, 판정 규칙. 에이전트 설정(모델 식별자, 프롬프트·코드 커밋, 도구 목록, 메모리 스냅샷, 예산)은 비교하려는 한 가지만 다르다. 전부 결과 파일에 남긴다.
- **잠금은 한 번의 비교 안에서의 규칙이다.** 과제나 채점기의 결함은 결과를 봐야 드러난다 [1][20]. 발견하면 고친다. 고치면 버전을 올리고 양쪽을 새 버전으로 다시 채점한다(과제가 바뀌었으면 다시 실행한다). 한쪽만 새 채점기로 낸 수치와 비교하지 않는다. 고친 이유는 `design/decisions.md`에 남긴다.

**예시** (과제 20건, 과제당 3회, B = 3.3%p, 허용폭 = 5%p)

| 과제 수 | 기준 → 후보 (통과 수/3) | d |
|---|---|---|
| 3 | 0 → 3 | +1.00 |
| 2 | 1 → 2 | +0.33 |
| 3 | 3 → 2 (1건), 2 → 1 (2건) | −0.33 |
| 12 | 변화 없음 | 0 |

1. 유효하지 않은 시도: 기준 1/60(1.7%), 후보 2/60(3.3%). 5% 아래라 유효하다. 정책 위반은 양쪽 0건이다. 기준이 3/3이던 과제 하나를 후보가 한 번 실패했다. 기록을 읽으니 에이전트 원인이라 양쪽 5회씩 더 돌렸고 둘 다 5/5였다. 확정되지 않았다.
2. D = (3×1 + 2×0.33 − 3×0.33) ÷ 20 = +13.3%p. d의 표준편차 0.41, 표준오차 9.2%p, 95% 구간 = 13.3 ± 2.09×9.2 = −5.9 ~ +32.5%p.
3. 구간이 0을 포함한다. 판정은 **차이 없음**이다. 평가 회귀는 없지만 "13%p 올랐다"고 쓰지 않는다. 보고 문장: "좋아진 과제 5, 나빠진 과제 3, 과제별 차이 평균 +13.3%p (95% 구간 −5.9 ~ +32.5), 차이 없음."
4. 같은 비율의 변화가 과제 40건에서 나왔다면 구간은 +0.4 ~ +26.3%p이고 D가 B보다 크므로 개선이다. 작은 차이를 가려내려면 과제를 늘린다. 반복을 늘리면 과제 안의 흔들림만 줄어든다.

## 6. 규모와 성장

| 셋 | 크기 | 보여 줄 수 있는 것 | 보여 줄 수 없는 것 |
|---|---|---|---|
| 연기 시험 셋 | 5건(제안값) | 파이프라인이 끝까지 돈다, 채점기가 반례를 가린다, 크게 깨진 것(판정 ①②) | 개선 여부, 작은 회귀. 과제 하나가 20%p이고 3/5의 95% 구간은 23~88%다(직접 계산) |
| 개발용 | 20건 이상. 실제 실패에서 뽑은 20~50건으로 시작하라는 권고 [1]의 하한이다 | 5절의 네 가지 판정. 12/20의 95% 구간은 39~78%(직접 계산) | 20건이면 대략 14~19%p, 50건이면 9~11%p보다 작은 차이(직접 계산, 가정은 5절) |
| 최종 확인용 | 10건 이상(제안값). 개발용과 묶음이 겹치지 않는다 | 개발용에만 맞춰졌는지(과적합) [15] | 정밀한 수치 |

- **최소 버전(기한이 있는 작은 프로젝트):** 연기 시험 셋 5건으로 끝낸다. 갖출 것은 파일 분리, 과제마다 `fail_to_pass` 1개 이상, 정답 변경 통과와 무변경 실패 확인, 시도마다 초기화, 코드 채점만, 채점기 반례 통과, 과제당 3회, 명령 한 줄이다. 이것으로 말할 수 있는 것은 "평가 파이프라인이 돈다", "과제별 전후 결과가 이렇다", "정책 위반과 확정된 실패가 없다"까지다. "성공률이 N% 올랐다"와 "개선"은 말할 수 없다. 5건이 전부 좋아져도 부호 검정 p값은 0.06이다(직접 계산). 겨냥한 실패는 "T-003이 0/3 → 3/3, 나머지 4건은 변화 없음"처럼 과제별 사실로 적는다. 최종 확인용은 2~3건(제안값)을 열어 보지 않고 남겨 분리 절차만 지킨다. 이 규모의 최종 확인은 크게 깨지지 않았다는 것만 보여 준다.
- **능력 묶음, 회귀 묶음, 포화:** 아직 잘 못하는 작업은 능력 묶음(낮은 통과율에서 시작), 이미 되는 작업은 회귀 묶음(100% 근처)이다 [1]. `suite`로 표시한다. 100% 근처인 묶음은 회귀만 잡고 개선 신호를 주지 않는다 [1]. 매번 통과하는 능력 과제는 회귀 묶음으로 옮기고 더 어려운 과제를 채운다.
- **운영 실패 승격:** 반복되고, 재현되고, 정답을 정의할 수 있는 것만 올린다. 사용자가 신고한 실패가 먼저다 [1]. 절차는 비식별화 → `base_commit` 고정 → 지금 에이전트로 실패 재현 → 정답 변경과 숨긴 테스트 작성 → 2절 검증 → 묶음 배정(같은 묶음은 같은 쪽에) → 데이터 버전 올림 → 기준선 다시 측정이다. 이전 버전 수치와 직접 비교하지 않는다. 실패 사례만 넣지 말고 같은 유형의 "해야 하는 경우"를 짝으로 넣는다 [1].
- **최종 확인용 교체:** 열 때마다 날짜·버전·사람을 적는다. 결과를 보고 에이전트를 고쳤다면 그 셋은 개발용으로 내리고 새 사례로 채운다. 누출 표식이 발견됐거나 대상 저장소가 크게 바뀌어 과제가 낡았을 때도 바꾼다. 평가셋에는 담당자가 있고, 깨진 과제는 고치거나 사유를 적고 뺀다 [1]. (교체 규칙은 제안)

## 7. 비용

실행 전에 아래를 적는다. 비싼 평가일수록 드물게 돌린다 [18].
- 시도 수 = 과제 수 × 반복 × 비교 대상 수. 예: 20건 × 3회 × 2(기준, 후보) = 120 시도.
- 모델 호출 수 ≈ 시도 수 × 시도당 평균 호출 수 + 모델 채점 호출(시도 수 × 기준 수). 시도당 평균은 연기 시험 실행의 기록에서, 기준선이 생긴 뒤에는 기준선에서 가져온다. 예: 시도당 40호출이면 120 × 40 = 4,800호출.
- 비용 ≈ 시도 수 × 시도당 평균 비용. 걸리는 시간 ≈ 시도 수 × 시도당 평균 시간 ÷ 동시에 돌리는 수.

| 층 | 범위 × 반복 | 언제 | 채점 |
|---|---|---|---|
| 연기 시험 | 5건 × 1회 | 변경할 때마다 | 코드만 |
| 전체 평가 | 개발용 전체 × 3회 (채택 판정은 5회) | 변경을 반영(머지)할 때마다 | 코드 + 보정된 모델 채점 |
| 최종 확인 | 최종 확인용 × 5회 | 출시 전 한 번 | 전부 + 사람의 표본 리뷰 |

층의 범위와 횟수는 (제안값)이다. 잠금 항목이 같은 기준 결과는 다시 쓸 수 있다. 모델이나 환경이 바뀌었을 수 있으면 다시 잰다. 정확도만 보지 않고 통과 1건당 비용을 같이 적는다 [15].

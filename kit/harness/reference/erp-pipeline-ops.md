# ERP 어시스턴트의 흐름·지연·비용·운영

> `METHOD-erp.md`의 C0(범위·유형·기반), C2(뼈대·관측·기준선), C7(지연·비용 최적화), C8(배포·운영)의 참고 문서다. 이벤트 형식은 `trace.md`를 그대로 쓰고 여기서는 더할 것만 적는다. ERP 제품에만 해당하는 내용은 `bases/`에 둔다.
> **(제안값)** 은 자료에 없는 우리 쪽 출발값이나 규칙이고 기준선을 잰 뒤 바꾼다. **(확인 필요)** 는 직접 확인하지 못한 내용이다. 자료의 숫자에는 "출처 기준"과 확인 시점을 붙였다. `[n]`은 끝의 참고 자료 번호다.

## 1. 유형과 유형별로 더해지는 통제

| 유형 | 하는 일 | 추가로 필요한 것 | 지연·사용 경험에 미치는 영향 |
|---|---|---|---|
| 지식 답변형 | 회사 지식을 검색해 근거와 함께 답한다 | 검색 결과를 묻는 사람의 문서 권한으로 거른다. 근거 링크. "모른다"는 답과 사람에게 넘김 경로. 지식 담당자와 갱신 주기 | 첫 글자까지 수 초. 스트리밍으로 충분하다 |
| 조회·추출형 | 도구로 ERP의 소스 코드와 업무 데이터를 읽는다 | 사용자 신원을 도구까지 전달한다(공용 고권한 계정 금지. 받은 토큰을 그대로 넘기지 않고 대상이 지정된 토큰으로 바꾼다 [18]). 읽기 전용 권한과 읽기 전용 도구만 연다. 조회 범위·건수 상한. 결과 가리기와 보존 규칙. 감사 기록(누가, 어느 시스템·환경에서, 무엇을). 대상 환경(개발·품질·운영)을 대화에 밝힌다. 도구 결과 안의 지시문을 지시로 다루지 않는다 | 도구 실행 시간이 지배한다. 진행 문구를 보내고, 10초(제안값, 5절)를 넘는 추출은 비동기 작업으로 돌린다(6절) |
| 변경형 | 코드나 시스템 상태를 바꾼다(화면 조작 포함) | 건별 사람 승인(바뀔 내용 미리보기), 요청자와 승인자를 나눌 범위, 멱등 키 [23], 변경 전 상태 보관과 되돌리기 절차, 환경 분리(변경은 개발 환경에서만, 품질·운영 반영은 ERP의 기존 변경 이관 절차), 어시스턴트가 고칠 수 없는 감사 기록, 동시 변경 잠금, 끄는 스위치. 화면 조작은 API가 없을 때만 쓰고 단계마다 화면 상태를 확인한다 | 분 단위가 될 수 있다. 접수 응답 → 작업 ID → 진행 알림 → 취소 수단 → 결과 확인 요청 |

- 유형은 어시스턴트에 열어 준 능력으로 정하고, 아래 행은 위 행의 통제를 전부 포함한다. 화면 조작으로 읽기만 하더라도 그 계정과 화면이 쓰기를 허용하면 변경형의 통제를 적용한다 (제안값). 환경 분리와 요청자·승인자 분리의 구체 기준도 제안값이고, 보안 표준의 해당 통제와는 대조하지 못했다 (확인 필요). [9][18][19][20]
- **첫 버전은 한 유형이다.** 요청 유형 몇 개로 시작하고 유형은 따로 넓힌다(9절). 세 유형을 한 번에 내면 어느 통제가 빠졌는지 가려지지 않는다. 지식 답변형은 코드가 경로를 정하는 흐름(라우팅 → 검색 → 생성)으로 충분하고, 모델이 순서를 정하게 하는 것은 도구를 여러 번 써야 하는 요청 유형으로 한정한다. [2][9]

## 2. 요청 목록 양식

| 요청 유형 | 빈도 | 건당 처리 시간 | 한다 / 안 한다 / 사람에게 넘김 | 유형 | 근거 문서·도구 유무 | 결과를 대화 밖에서 확인할 방법 |
|---|---|---|---|---|---|---|
| (예) 구매 요청 승인 절차 문의 | 월 __건 | __분 | 한다 | 지식 답변형 | 문서 있음 (담당: __) | 답이 가리킨 규정 문서의 해당 절 |
| (예) 특정 프로그램이 읽는 테이블 목록 | 월 __건 | __분 | 한다 | 조회·추출형 | 소스 조회 도구 있음 | 같은 계정으로 ERP에서 직접 조회한 결과 |
| (예) 개발 시스템 보고서의 문구 수정 | 월 __건 | __분 | 한다 | 변경형 | 편집 도구와 승인 경로 있음 | ERP의 변경 이력과 변경 전후 비교 |
| (예) 운영 시스템 설정값 변경 | 월 __건 | __분 | 사람에게 넘김 | — | — | 담당 창구의 티켓 번호 |

- 최근 실제 기록(헬프데스크 티켓, 질문 채널, 사내 검색 로그) 200건(제안값)을 요청 유형으로 묶어 채우고 빈도와 건당 처리 시간으로 줄을 세운다. 회의에서 떠올린 목록으로 채우지 않는다. "한다"는 근거 문서나 도구가 실제로 있는 것만 고른다. [1][15]
- "안 한다"는 이유와 대안을 알리고 끝낸다. "사람에게 넘김"은 계기(실패 한도 초과, 고위험 행동)와 받는 창구를 같이 적는다. 마지막 열이 비는 요청 유형은 채점할 수 없으므로 첫 버전에 넣지 않는다 (제안값). 화면의 완료 문구나 어시스턴트의 말은 확인 방법이 아니다. [1][9]
- 검증: 두 사람이 같은 기록 50건(제안값)을 따로 분류해 세 칸 판정이 일치하는 비율을 적는다. "한다"의 비율과 그중 근거가 있는 비율도 적는다.

## 3. 기반 선택 기준

| 확인할 것 | 확인 방법 | 안 되면 생기는 일 |
|---|---|---|
| 요청·응답 원문 덤프 | 모델에 실제로 들어간 요청(지침, 도구 정의, 검색 결과, 대화)과 응답을 파일로 받아 읽는다 | 무엇이 문맥에 들어갔는지, 캐시가 왜 깨지는지 볼 수 없다 |
| 사용자 신원을 도구까지 전달 | 권한이 다른 두 계정으로 같은 조회를 넣고 ERP 쪽 기록에 각자의 신원이 찍히는지 본다 | 공용 계정으로 접속하게 되고 권한 판단이 모델에 넘어간다 [18][20] |
| 도구 실행 전 승인 단계 | 변경 도구 호출을 승인 없이 보내 실행되지 않는지, 승인 화면에 바뀔 내용이 보이는지 본다 | 변경형을 열 수 없다 [19] |
| 대화 기록 내보내기 | 대화·턴·도구 호출·피드백을 대화 ID와 함께 우리 저장소로 받는다 | 7절의 기록과 C6의 개선 재료가 없다 |
| 모델 ID 고정 | 별칭이 아닌 고정 ID를 설정하고 응답에 찍힌 ID와 비교한다 | 평가한 모델과 운영 모델이 달라진다 [7] |
| 채널 지원 | 쓰려는 채널(사내 메신저, 웹, 업무 화면 내장)에서 스트리밍, 버튼, 파일, 긴 작업 완료 알림이 되는지 본다 | 6절의 비동기 흐름과 피드백 버튼을 못 쓴다 |
| 공급자: 사용 한도 | 분당 요청·토큰 한도와 증가 속도 한도를 예상 최대 부하(동시 대화 수 × 턴당 토큰)와 비교한다 | 사용자를 넓히는 날 한도 오류가 난다 [6] |
| 공급자: 지출 상한 | 상한에 닿았을 때의 동작(재시도해도 풀리지 않는 오류)과 알림 설정을 확인한다 | 상한에 닿는 순간 전체가 멈춘다 [6] |
| 공급자: 모델 종료 통지 | 통지 기간과 통지를 받는 사람을 확인한다. 기간은 공급자와 모델 등급마다 다르다(출처 기준 60일에서 6개월, 프리뷰는 더 짧을 수 있다, 2026-11 확인) | 종료일에 요청이 실패한다 [7][12] |
| 공급자: 데이터가 회사 밖으로 나가는 범위 | 대화·검색 결과·도구 결과 가운데 무엇이 어디로 가고 얼마나 보관되는지 계약과 설정으로 확인한다 | 보안·법무 검토에서 막힌다 |

- 직접 만들든, 사든, 플랫폼 위에 올리든 같은 표로 본다. 후보마다 질문 세 개(지식, 조회, 범위 밖)를 넣고 설명서가 아니라 덤프를 읽는다 (제안값). 후보별 결과와 선택 근거는 C0 산출물에 남긴다.

## 4. 한 턴의 흐름

```
사용자 메시지
  ① 접수: 인증·세션·권한 집단 확인, "입력 중" 표시                          (코드)
  ② 입력 검사: 길이·금칙·주입·범위 ─┐ 도구 없는 경로는 병렬 가능              (코드 + 작은 모델)
  ③ 라우팅 + 질의 재작성(한 호출)  ─┘ 도구 경로는 ②가 끝난 뒤에 시작          (작은 모델)
       ├─ 범위 밖·사람에게 넘김 ──► 고정 문구 또는 담당 창구 (모델 호출 없음)
       ├─ 지식 ──► ④ 검색(권한 필터) ──► ⑤ 생성(스트리밍) ──► ⑥ 출력 검사(구획 단위) ──► 화면
       └─ 도구 ──► ④' 도구 계획 ──► [변경형: 사람 승인] ──► 실행(진행 알림 / 비동기 작업) ──► ⑤ ⑥
  ⑦ 턴 종료: 대화 저장, 턴 기록, 피드백 버튼에 턴 ID 연결                      (코드)
```

- 단계 전환은 코드가 판정한다. 라우팅과 질의 재작성은 한 호출로 합친다. 분류 호출을 앞에 따로 두면 그만큼 지연이 는다. [1][10]
- **병렬 가능:** ②와 ③(도구 없는 경로), ④ 안의 서로 독립인 조회. 병렬로 돌린 검사가 걸리면 그동안 쓴 토큰은 버린다. [10][13]
- **반드시 차단:** 도구 경로의 ② → 도구 실행. 병렬로 두면 검사가 걸리기 전에 도구가 이미 실행됐을 수 있다. 변경형의 승인 → 실행, 도구 호출마다 도는 실행 전 검사도 차단이다. [13]
- **미리 시작해도 되는 것:** 읽기 전용 조회. 필수 검사가 통과하기 전에는 결과를 보이지 않고 그 결과로 행동하지 않는다. [10] ERP 조회는 부하와 접속 기록을 남기므로 미리 시작하는 것은 지식 검색으로 한정한다 (제안값).
- **스트리밍과 출력 검사:** 스트리밍하면 검사 전에 글자가 화면에 나간다. 구획(문장·문단) 단위로 모아 검사한 뒤 내보낸다. 끝난 뒤 한 번에 검사하려면 이미 나간 글을 지우는 수단이 있어야 한다. [10][26]
- **구조화 출력:** 표, 버튼, 승인 카드는 조각이 완성된 뒤에만 그린다. 도구 인자는 부분 문자열로 오고 블록이 끝나야 완성되므로 그 전에 실행하지 않는다. [3]
- **스트림 중간 오류와 거절:** 정상 응답 코드 뒤에도 오류 이벤트가 올 수 있다. 받은 부분을 지울지, "중단됨" 표시와 함께 남길지, 이어 받을지 정한다. 도구 호출 블록은 부분 복구가 안 되므로 다시 계획한다. 거절로 끝난 턴은 대화 문맥에서 빼거나 바꾼 뒤 이어간다. 그대로 두면 다음 턴도 거절될 수 있고, 사유 필드가 비어 올 수 있어 사용자용 문구를 미리 둔다(한 공급자 문서 기준). [3][4]

## 5. 지연 예산

| 구간 | 예산 p95 (제안값) | 비고 |
|---|---|---|
| 접수 표시(전송됨, 입력 중) | 0.1초 | 즉각으로 느끼는 한계 [14] |
| ② 입력 검사 / ③ 라우팅 + 재작성 / ④ 검색 / ⑤ 생성 첫 토큰 | 0.3초 / 0.5초 / 0.5초 / 1.0초 | ②는 병렬이면 추가 0. ⑤는 캐시 적중 상태 기준 |
| 첫 가시 텍스트 (①~⑤ 합) | 2.5초 이하 | 1초를 넘으면 작업 중 표시가 필요하다 [14] |
| 지식 답변형 완결 | 10초 이하 | 주의를 붙잡는 한계 [14] |
| 조회 도구 1회 | 10초 이하, 2초마다 진행 문구 | 실제 진행 상황을 보인다 [10][19] |
| 긴 추출·변경 | 접수 응답 2초 이하, 이후 비동기 | 6절 |

- 첫 가시 텍스트 시간과 완결 시간을 따로 잡는다. 서버의 첫 토큰 시간이 아니라 사용자 동작부터 화면 표시까지를 클라이언트에서 재고 p50과 p95를 본다. [10]
- **표의 숫자는 전부 제안값이다.** 자료에서 온 것은 0.1초·1초·10초 세 한계뿐이고(출처 기준, 2026-11 확인), 그것을 구간별 예산으로 나눈 것은 우리다. 기준선을 잰 뒤 바꾼다.
- 그 세 한계는 1993년 글이 1968년과 1991년의 인간-컴퓨터 상호작용 연구에 기대어 정리한 일반 화면 지침이다. LLM 스트리밍 텍스트에서 사용자가 얼마나 기다리는지를 잰 실험이 아니다. 그런 실험 자료는 찾지 못했다 (확인 필요). [14]
- 첫 토큰 시간만 묶으면 사고 토큰이나 토큰 사이 간격이 늘어 완결 시간이 넘칠 수 있으므로 둘 다 예산을 둔다. 예산을 넘긴 단계는 재시도하지 않는다. 마감을 넘긴 작업은 낭비이고 재시도가 과부하를 키운다. [22][26]

## 6. 긴 도구 호출

- 5절의 예산을 넘는 도구는 동기 턴에 넣지 않는다. 시간 초과를 재시도로 덮지 않는다. [10]
- 흐름: **접수 응답**(무엇을 어느 시스템·환경에서 할지, 작업 ID) → **진행 알림**(진행값, 전체값, 사람이 읽을 문구) → **완료 알림**(채널 알림과 대화 안의 결과) → 필요하면 **취소**. 작업 저장소는 대화 저장소와 따로 둔다. 필드 이름은 제안값이다. [19]

| 필드 | 내용 |
|---|---|
| `job_id`, `owner`, `session_id`, `request_id` | 작업 ID, 요청자, 작업을 시작한 대화와 턴. 결과는 요청자의 권한으로만 열린다 |
| `tool`, `args_digest`, `target_system`, `target_env`, `idempotency_key` | 무엇을 어느 시스템·환경(개발·품질·운영)에서 하는가. 변경형은 멱등 키를 두어 같은 키의 재시도가 두 번 실행되지 않게 한다 [23] |
| `state`, `progress`, `total`, `message`, `updated_at` | `accepted` \| `running` \| `waiting_approval` \| `succeeded` \| `failed` \| `cancelled` \| `expired` \| `unknown`. 전체를 모르면 한 일의 양을 보인다 [14] |
| `result_ref`, `expires_at` | 결과 위치와 보존 기한. 추출 결과 원문은 기록에 넣지 않는다 |

- 사용자가 창을 닫고 돌아와도 진행 상태와 결과가 보여야 한다. 돌아온 대화의 첫 화면에서 끝난 작업을 알린다. 스트리밍한 응답도 전체를 저장해 돌아왔을 때 보이게 한다. [1]
- 취소는 조회·추출형에서는 중단이다. 변경형에서는 이미 바뀐 것이 남을 수 있으므로 취소 뒤 상태를 조회해 무엇이 바뀌었는지 알린다 (제안값). 결과를 알 수 없으면 `unknown`으로 두고, 다시 실행하기 전에 ERP의 상태를 조회한다. 조용히 다시 시작하지 않는다.
- 진행 알림은 MCP 규격에 있다. 조회로 결과를 받는 작업 방식은 규격의 확장으로 옮겨졌고 확장 규격 본문은 읽지 못했다 (확인 필요). [19]

## 7. 기록에 더할 것

- `trace.md`의 형식(공통 필드, `llm_call`, `tool_call`, `gate_block`, 요약 지표, 가리기)을 그대로 쓴다. 아래는 대화형 어시스턴트라서 더하는 것만이고 이름과 값은 제안값이다. 층은 대화(`session_id`) ⊃ 턴(`request_id`) ⊃ 이벤트다. `trace.md`의 요청 한 건이 여기서는 턴 한 번이다. 검색, 검사, 도구, 비동기 작업의 모든 하위 호출에 두 ID를 붙인다. 최상위 호출에만 붙이면 대화 단위 비용·지연 합계가 틀린다. `phase` 값은 4절의 단계로 바꾼다: `intake` | `check` | `route` | `retrieve` | `tool` | `generate` | `close`. [16][17]

| 어디에 | 더하는 것 | 설명 |
|---|---|---|
| `request_start` | `turn_seq`, `channel`, `user_group`, `release_id` | 대화 안의 턴 번호, 채널, 권한 집단, 릴리스 묶음 ID(9절). 모델 호출에 남는 응답의 모델 ID가 설정과 다르면 경고한다 [7] |
| `request_end` | `request_type`, `assistant_type`, `route`, `turn_outcome`, `degraded`, `job_id` | 2절의 요청 유형, 유형(`knowledge` \| `read` \| `change`), 지나간 경로, 턴 결과, 축소 응답 여부(10절), 접수한 작업 |
| `summary.timing` | `intake_ms`, `check_ms`, `route_ms`, `retrieve_ms`, `ttft_ms`, `ttfv_ms`, `complete_ms`, `tool_ms` | 단계별 시간. `ttfv_ms`(첫 가시 텍스트)는 클라이언트가 재서 보낸다 |
| `llm_call`, `tool_call` | `stream_end` / `target_system`, `target_env`, `acting_user`, `job_id` | `complete` \| `interrupted` \| `refusal` / 대상 시스템, 환경(`dev` \| `qa` \| `prod`), 도구에 전달된 신원(가명 ID), 비동기면 작업 ID |
| 새 이벤트 `retrieval` | `index_version`, `query_digest`, `hit_ids`, `filtered_count` | 지식 색인 버전, 권한으로 걸러 낸 건수 |
| 새 이벤트 `feedback` | `target_request_id`, `kind`, `signal`, `comment_ref` | 턴이 끝난 뒤에 오므로 따로 남기고 턴 ID로 잇는다 |
| 새 이벤트 `job` | `job_id`, `state`, `progress`, `total` | 6절의 상태가 바뀔 때마다 |
| 대화 요약 (대화당 한 줄) | `turns`, `conversation_outcome`, 토큰·비용 합계 | `resolved_confirmed` \| `resolved_implicit` \| `handoff` \| `abandoned`. 마지막 턴 뒤 30분(제안값) 동안 입력이 없으면 닫고 쓴다 [15] |

- **`turn_outcome`:** `answered`(답함) | `clarified`(되물음) | `out_of_scope`(범위 밖 안내) | `handoff`(사람에게 넘김) | `accepted`(비동기 작업 접수) | `blocked`(검사나 승인에서 막힘) | `error`(오류). `final_status`는 그대로 두고 대응시킨다: `answered`·`clarified`·`out_of_scope`·`blocked` → `done`, `accepted` → `hold`, `handoff` → `handoff`, `error` → `failed`.
- **피드백:** 명시(`kind=explicit`)는 버튼 `resolved` | `helpful` | `not_helpful` | `irrelevant`와 의견란이다. 암묵(`kind=implicit`)은 `rephrase`(되묻기) | `repeat`(같은 질문 반복) | `handoff_request`(사람을 찾음) | `abandon`(이탈)이다. 명시적 피드백은 응답률이 낮고 불만 쪽으로 치우치므로 암묵 신호와 같이 본다. 화면 쪽에는 피드백만 쓸 수 있는 키를 준다. 버튼 구성은 한 사내 사례를 따른 예이고 원문과 대조하지 못했다 (확인 필요). [15][16][27]
- **원문:** `trace.md` 7절을 따른다(기본은 메타데이터만, 가리기는 쓰기 전에). 더하는 것은 셋이다. 대화 원문과 의견란은 직원 개인정보와 업무 데이터이므로 수집을 명시적으로 켠 경우에만 남기고 열람 권한과 보존 기간을 정한다. 추출 결과는 위치·건수·해시만 남긴다. 원문을 전혀 못 보면 사고 조사가 막히므로, 신고된 대화에 한해 누가 승인하고 누가 여는지를 정하고 열람 사실을 기록하는 절차를 둔다. [8][16]

## 8. 비용 모델

- 호출당이 아니라 **대화당**, **해결 1건당**으로 잰다. 변경형은 **성공한 작업 1건당**을 따로 재고, 성공은 대화 밖에서 확인한 끝 상태로 판정한다. 분자에는 사람에게 넘김으로 끝난 대화, 검사·재작성·임베딩·채점 호출, 재시도, 실패한 작업이 전부 들어간다. 매 턴 이전 대화를 다시 보내므로 캐시가 없으면 대화당 입력 토큰은 턴 수의 제곱에 비례해 는다.

```
기호: S 고정 접두(도구 정의 + 시스템 지침), u 사용자 메시지, o 응답, R 턴별 검색 결과, T 턴 수, p 입력 단가, w 캐시 쓰기 배수, r 캐시 읽기 배수
캐시 없음:  입력 토큰 합 = T·(S + R + u) + (u + o)·T·(T−1)/2              ← T²에 비례
캐시 있음:  턴 t 입력 비용 ≈ p·[ r·(S + 이전 대화) + w·(o_{t−1} + u_t) + R_t ]
            R_t는 캐시 지점 뒤에 두고 다음 턴에는 대화에서 뺀다. 답이 수명보다 늦게 오면 그 턴은 접두 전체를 w로 다시 쓴다
예시: S=3,000  u=50  o=300  R=1,500  T=8,  w=1.25  r=0.1
  캐시 없음: 8·4,550 + 350·28 = 46,200 토큰분
  캐시 있음: 0.1·(24,000 + 9,800) + 1.25·2,500 + 12,000 = 18,505 토큰분 (약 40%)
  접두가 식어 있으면 첫 턴에 S를 w로 써서 3,450 토큰분이 더 든다 (합 21,955, 약 48%)
대화당 비용 = 입력 비용 + 출력 토큰 × 출력 단가 + 검사·재작성·임베딩·채점 호출 + 재시도
해결 1건당 비용 = 전체 대화 비용 합 ÷ 해결된 대화 수.  성공한 작업 1건당 비용 = 변경형 대화 비용 합 ÷ 대화 밖에서 확인한 성공 작업 수
```

- **위 계산은 우리가 한 것이다.** 토큰 크기는 지어낸 예시 값이고, 배수 w=1.25와 r=0.1은 한 공급자 문서의 짧은 수명 기준 값을 가정으로 넣었다(출처 기준, 2026-11 확인). 모든 턴이 수명 안에 적중하고 고정 접두가 다른 대화로 이미 데워져 있다고 가정했다. ≈는 직전 응답을 읽기와 쓰기에 겹쳐 센 근사라 약 1% 높게 나온다. [5]
- **배수, 수명, 최소 길이는 쓰는 모델의 현재 공급자 문서에서 읽는다.** 공급자와 모델마다 다르고 바뀐다. 조사 시점에도 두 공급자의 기본 수명, 최소 길이, 캐시에서 읽은 토큰을 분당 한도에 세는지가 서로 달랐다. 최소 길이에 못 미치면 오류 없이 캐시되지 않는다. 캐시가 대화에 맞으려면 고정 접두가 최소 길이를 넘고, 턴 사이 간격이 수명 안이고, 접두가 글자 하나까지 같아야 한다. 수명은 기록에서 턴 간격의 중앙값과 p90을 뽑아 정한다. 사람의 답은 수명보다 늦을 수 있다. [5][6][11]
- **검색 결과의 자리:** 턴마다 달라지는 검색 결과, 날짜, 사용자 이름을 시스템 지침에 넣으면 그 뒤의 대화 캐시가 매 턴 깨진다. 마지막 사용자 턴 쪽, 캐시 지점 뒤에 둔다. 이전 턴의 검색 결과를 대화에 남길지는 한 가지로 정해 고정한다(남기면 입력이 늘고, 턴마다 다르게 빼면 접두가 바뀐다). 긴 대화를 요약으로 줄여도 접두가 바뀌어 한 번은 캐시를 잃는다. 예시처럼 캐시를 켠 뒤에는 캐시되지 않는 검색 결과(12,000)가 입력 비용의 대부분이므로 다음 절감 대상은 검색 결과의 개수와 길이다. [11]
- **모델 라우팅 규칙:** ① 요청 유형 단위로만 나눈다 ② 유형별 평가에서 품질이 흔들림 폭 안일 때만 작은 모델로 보낸다 ③ 라우터의 오분류율을 요청 유형별로 따로 잰다 ④ 모델이 갈리면 캐시도 갈리므로 캐시 적중을 다시 잰다 ⑤ 작은 모델로 먼저 답하고 부족하면 큰 모델로 올리는 구성은 올라간 요청의 비율과 더해진 지연·비용을 같이 적는다. [2][26]
- **응답(의미 유사) 캐시 규칙:** 비슷한 질문에 저장된 답을 돌려주면 권한·사람·시점에 따라 답이 달라지는 요청에서 다른 권한 집단의 답이 새거나 낡은 답이 나간다. ① 공개 범위가 같은 지식 답변형 질문에만 쓴다 ② 조회·추출형과 변경형에는 쓰지 않는다 ③ 캐시 키에 권한 집단과 지식 색인 버전을 넣는다 ④ 만료를 둔다 ⑤ 켜고 끌 수 있게 한다. 캐시를 나누는 설정이 있다는 것만 자료로 확인했고, 누출 위험은 우리 판단이며 사례·측정 자료는 찾지 못했다 (확인 필요). [25]

## 9. 릴리스 묶음과 확대 단계

| 단계 | 하는 것 | 넘어가는 기준 (틀이다. 숫자는 시작 전에 적는다) | 멈추는 기준 |
|---|---|---|---|
| 내부 시험 사용 | 만든 팀과 지식 담당자가 실제 업무 질문으로 쓴다 | 2절의 "한다" 요청 유형이 전부 한 번 이상 쓰였다. 12절의 기록 완전성 시험 통과 | 권한 밖 노출 1건 또는 승인 없는 변경 1건이면 즉시 중단 (모든 단계 공통) |
| 그림자 방식 | 어시스턴트는 초안만 쓰고 사람이 답한다. 변경형은 실행 없이 계획만 낸다 | 사람이 고치지 않고 쓴 초안의 비율, 고친 이유의 분류, 계획과 사람이 실제로 한 변경의 일치 | 근거 없는 답이나 틀린 계획이 정한 비율을 넘는다 |
| 일부 사용자 | 권한 집단·채널 일부 또는 트래픽 비율로 연다 | 같은 기간 대조 집단과 비교한 해결률·사람에게 넘김 비율·피드백. 지연·비용이 C0의 상한 안 | 대조 집단보다 나빠진 폭이 흔들림 폭을 넘는다. 축소 응답이 급증한다 |
| 전체 | 전부 연다. 스위치와 되돌리기는 남긴다 | — | 운영 지표의 경보 기준 |

- **한 묶음으로 버전을 매기는 것:** 프롬프트, 라우팅 규칙, 검사 설정, 도구 정의와 권한, 모델 ID와 추론 설정, 지식 색인 버전, 평가 묶음 버전. 하나만 바뀌어도 새 `release_id`이고 턴 기록에 찍힌다. 모델은 별칭이 아니라 고정 ID로 적는다. 운영에서 프롬프트를 바로 고치지 않는다. 넓히기 전에 최종 확인용 평가를 돌리고, 과거 대화 표본을 새 묶음으로 재생해(도구는 실행하지 않고 계획만) 이전 묶음과 답·경로·비용·시간을 나란히 본다 (제안값). [7]
- **유형별로 따로 넓힌다.** 지식 답변형이 먼저다. 변경형은 개발 환경에서만 시작하고 품질·운영 반영은 기존 절차가 맡는다. 여러 확대를 동시에 돌리면 무엇이 원인인지 가려지지 않는다. [9][21]
- **대조 집단은 같은 기간으로 잡는다.** 배포 전후 비교만으로는 업무 주기(예: 월 마감 주간의 질문 변화)와 어시스턴트의 효과를 가를 수 없다. 일부에만 열면 열린 비율만큼만 위험을 진다. 오프라인 평가가 못 잡는 저하가 있으므로 운영 표본의 상시 채점과 사용자 신고를 `release_id`와 잇는다. [8][17][21]

## 10. 축소 응답

| 죽은 것 | 감지 | 사용자가 보는 것 | 하지 않는 것 |
|---|---|---|---|
| 모델 공급자(과부하, 한도, 시간 초과) | 오류 코드, 첫 토큰 시간 초과 | 상한 안에서 재시도 → 대체 모델(평가한 조합만) → 검색 결과 목록과 "요약을 만들지 못했다"는 안내 | 도구 실행, 변경 |
| 검색·색인 | 검색 오류, 결과 0건 급증 | "지금 문서를 찾을 수 없다"와 담당 채널 안내 | 근거 없이 모델 지식만으로 답하기 |
| 입력·출력 검사기 | 검사기 오류·시간 초과 | 지식 답변형은 고정 문구로 재시도 안내, 도구 경로는 중단 | 검사 없이 통과시키기 |
| 조회 도구(ERP) | 도구 오류, 시간 초과 | 실패 사실과 이유, 다시 시도 또는 사람에게 넘김 | 추측한 값으로 답하기 |
| 변경 도구 | 오류, 결과 불명 | "결과를 확인하지 못했다"와 상태 조회 결과, 담당자 연결 | 상태 확인 없는 재실행 |
| 승인 경로(승인자 부재) | 승인 대기 시간 초과 | 대기 중임과 만료 시각, 취소 방법 | 승인 없이 진행 |
| 비동기 작업 실행기 | 작업 정체 | 작업 상태 "지연"과 예상 시각, 취소 수단 | 조용한 재시작 |
| 기록 저장소 | 쓰기 실패 | 지식 답변형은 계속하되 경고 지표를 올린다. 변경형은 중단 | 감사 기록 없이 변경 |
| 사람에게 넘김 창구(근무 외) | 창구 상태 | 접수 티켓 번호와 응답 예정 시각 | "곧 연결된다"는 약속 |

- 무엇이 죽었을 때 사용자가 무엇을 보는지 미리 정한다. 표의 내용은 제안값이다. 끄는 스위치는 유형·도구·채널 단위로 두고, 축소 응답으로 나간 턴은 `degraded=true`로 남긴다. [22]
- 재시도는 횟수 상한, 지수 백오프와 무작위 지연, 응답에 담긴 대기 시간 준수로 한다. 지출 상한처럼 재시도해도 풀리지 않는 오류는 구분해 바로 축소 응답으로 간다. 변경 도구는 시간 초과 뒤 그대로 다시 실행하지 않는다. 상태를 조회하고, 다시 보낼 때는 같은 멱등 키를 쓴다. [6][22][23]

## 11. 지식 운영과 바깥 변화

- **담당자:** 문서마다 담당자, 상태(작성 중, 미검증, 검증됨, 보관), 공개 대상, 검토일을 둔다. 담당자가 없는 문서는 색인에 넣지 않는다 (제안값). [24]
- **답 못 한 질문의 되먹임:** 주 단위(제안값)로 답 못 한 질문, "도움 안 됨", 사람에게 넘김으로 끝난 대화를 주제로 묶어 읽고 원인을 분류한다(지식 없음, 지식 낡음, 검색 실패, 생성 오류, 범위 밖, 도구). 지식이 원인이면 담당자에게 기한과 함께 보내고, 나머지는 평가 사례 승격이나 범위 조정으로 보낸다. 자주 쓰이는 문서부터 고친다. [15][24]

| 바뀐 것 | 다시 돌릴 것 |
|---|---|
| 모델(종료 통지, 교체) | 평가 전체, 지연·비용 기준선, 8절의 캐시 계산(최소 길이와 배수는 모델마다 다르다). 종료일 전에 끝내고 종료 일정을 릴리스 달력에 올린다. 프리뷰 모델에 운영을 걸지 않는다 [7][12] |
| 지식 색인(쪼개기, 임베딩, 권한 필터) | 검색 평가, 근거 평가, 응답 캐시 비우기, 문서 수정이 답에 반영되기까지의 시간 |
| 도구 정의·권한, ERP 쪽 변경 | 도구 과제 평가, 신원 전달 시험, 캐시 적중(도구 정의가 바뀌면 캐시된 접두가 무효가 된다 [5]) |
| 프롬프트·라우팅·검사 설정 | 해당 유형의 평가와 기준선, 12절의 검사 차단 시험 |

## 12. 검증 시험

| 시험 | 방법 | 기대 |
|---|---|---|
| 기록 완전성 | 여러 턴 대화 1건의 이벤트를 전부 읽고, 대화 단위 토큰·비용을 이벤트에서 직접 더한다. 버튼을 누르고 같은 질문을 다시 묻는다 | 모든 하위 호출에 `session_id`·`request_id`가 있다(빠진 건수 0). 턴마다 `turn_outcome`, `release_id`, 단계별 시간이 있다. 합계가 대시보드 값과 같다. `feedback` 두 건이 턴 ID로 조회된다 |
| 가리기 | 가짜 개인정보를 메시지와 도구 결과에 넣는다 | 기록 전체 검색에서 원문 0건 |
| 검사 차단 | 도구 경로에 검사에 걸리는 입력을 넣는다 | 도구가 실행되지 않았다. `turn_outcome=blocked` |
| 스트림 장애 | 스트림 중간 오류와 거절 종료를 일부러 만든다 | 정해 둔 문구가 보인다. 완성되지 않은 구조화 출력은 그려지지 않는다. 다음 턴이 정상이다 |
| 장애 주입 | 10절 표의 행마다 해당 구성요소를 끈다 | "사용자가 보는 것"이 나오고 "하지 않는 것"이 기록에서 0건이다. `degraded=true` |
| 비동기 복귀 | 긴 작업을 시작하고 창을 닫았다가 돌아온다. 취소도 해 본다 | 진행 상태와 결과가 보인다. 취소 뒤의 상태가 조회된다 |
| 중복 실행 | 변경 도구에 같은 멱등 키로 두 번 보낸다 | 한 번만 실행된다 |
| 되돌리기와 끄는 스위치 | 이전 릴리스 묶음으로 돌린 뒤 새 대화를 연다. 유형·도구·채널 단위로 실제로 끈다 | 턴 기록에 이전 `release_id`가 찍히고 응답의 모델 ID가 설정과 같다. 꺼진 동안 정해 둔 문구가 보이고 해당 호출이 0건이다 |
| 캐시 | 턴별 사용량 필드(읽기·쓰기 토큰)를 본다. 응답 캐시를 켰으면 권한이 다른 두 계정으로 같은 질문을 넣는다 | 2턴째부터 읽기가 0이 아니다(0이면 연속 두 요청의 접두를 비교한다). 답이 섞이지 않는다 |
| 부하 | 예상 최대 동시 대화 수까지 단계적으로 올린다 | 한도 대비 여유를 적는다. p95가 5절의 예산 안이다. 한도 오류에서 축소 응답이 나온다 |

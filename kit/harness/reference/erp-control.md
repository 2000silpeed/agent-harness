# ERP 어시스턴트의 제어·승인·감사

> [`METHOD-erp.md`](../METHOD-erp.md) C5(제어·승인·감사)의 참고 문서다. C0의 금지·고지·보존 정책과 C8의 점검·사고 대응 가운데 통제에 해당하는 부분도 여기에 둔다. 층별 방어, 판정 주체, 도구를 거치지 않는 길, 가드 측정은 [`security.md`](security.md)를, 계획 → 리뷰 → 승인의 양식과 상태 전이는 [`plan-gate.md`](plan-gate.md)를 그대로 쓴다. 여기에는 사용자가 여러 명이고, 권한이 사람마다 다르고, 대상이 여러 사람이 쓰는 기록 시스템이라서 **바뀌는 것과 더해지는 것**만 적는다.
> **(제안값)** 은 자료에 없는 우리 쪽 시작값이고, **(확인 필요)** 는 원문이나 우리 제품에 대한 적용 여부를 확인하지 못한 내용이다. 제품 이름은 "예:"로만 들고 제품별 동작은 `bases/`에 둔다. 대괄호 숫자는 맨 끝 참고 자료의 번호다.
> **법규 항목은 법률 자문이 아니다.** 조문을 읽고 옮긴 것이고, 우리 제품에 적용되는지는 판단하지 않았다. 12절의 모든 항목은 회사의 법무, 개인정보 보호, 내부감사 담당자가 검토해야 하며, 항목마다 담당 부서와 검토 상태를 적어 넘긴다. 법령은 2026-11-16에 국가법령정보센터와 EUR-Lex에 표시된 현행 판을 읽었고 그 뒤의 개정은 반영하지 않았다.

## 1. 자산과 신뢰 경계
| 지킬 것 | 예 | 잃으면 | 기본 조치 |
|---|---|---|---|
| 업무 데이터 | 거래, 재고, 원가, 공시 전 재무 정보 | 유출, 목적 밖 이용 | 요청한 직원의 권한으로만 읽는다. 반환 상한과 내보내기 통제(6절) |
| 소스 코드 | ERP의 개발 객체와 설정 | 유출, 결함 있는 변경이 운영까지 간다 | 변경은 개발 시스템에서 계획·승인 뒤에만(5절). 외부 모델로 보낼 범위는 C0에서 정한다(8절) |
| 개인정보 | 임직원과 거래처 담당자의 인사, 급여, 연락처, 고유식별정보 | 유출과 그에 따른 책임(12절) | 등급별 가림(8절), 볼 수 있는 사람 최소화, 접속 기록 |
| 운영 시스템의 상태 | 운영 데이터, 운영 설정, 권한·역할 | 되돌릴 수 없는 변경, 업무 중단 | 어시스턴트는 바꾸지 않는다. 운영 접속 정보를 배포 설정에 넣지 않는다 |
| 승인·감사 기록 | 승인 기록, 감사 기록, 검사 설정, 도구 등급 표 | 통제 전체가 무효가 되고 부인을 막지 못한다 | 어시스턴트 실행 계정이 쓸 수 없는 곳에 추가 전용으로 둔다(5·7절) |
| 지식 문서 | 규정, 절차서, 운영 안내 | 권한 밖 노출, 낡았거나 오염된 답 | 문서 권한으로 거른 검색, 출처마다 주인과 검토일(`erp-knowledge-tools.md`) |

신뢰 수준을 "누가 쓸 수 있는가"로 정하는 규칙은 `security.md` 1절과 같다. 달라지는 것은 둘이다. 쓴 사람이 내부 직원이어도 데이터로 다룬다. 그리고 요청자가 곧 권한자가 아니어서, 사용자 메시지는 그 직원의 ERP 권한 안에서만 지시다.

| 입력 | 쓸 수 있는 사람 | 취급 |
|---|---|---|
| 사용자 메시지 | 로그인한 직원 본인 | 지시(그 직원의 ERP 권한 안에서). 메시지에 적힌 사번, 직책, 승인 문구는 데이터 |
| 붙여 넣은 내용·올린 파일 | 그 내용을 처음 쓴 사람(외부인일 수 있다) | 데이터. 직원이 넣었다는 사실이 그 안의 문장을 지시로 만들지 않는다 |
| 검색된 사내 문서 | 그 문서를 고칠 수 있는 직원 전부 | 데이터. 출처와 개정일을 붙여 전달한다 |
| 소스 코드의 주석·문자열 | 개발자, 외주 개발 인력, 공급사 | 데이터 |
| 데이터 값(비고, 거래처명 같은 자유 입력) | 입력 담당 직원, 거래처, 연계된 외부 시스템 | 데이터. 필드 단위로 구조화해 전달한다 |
| 화면의 글자 | 그 화면에 표시되는 값을 쓴 사람 전부 | 데이터. 화면의 완료 메시지는 결과의 증거가 아니다 |
| 도구 서버의 설명 | 도구 서버 운영자 | 데이터. 서버가 붙인 읽기 전용 같은 표시는 등급의 근거가 아니다. 등급은 우리가 정한다 [2] |

## 2. 세 가지 능력 규칙의 적용
`security.md` 2절의 세 능력을 이 제품은 기본으로 다 가진다: 비공개 데이터(업무 데이터, 소스 코드, 개인정보), 신뢰 못 할 입력(1절 표의 데이터), 상태 변경과 밖으로 나가는 길. 코딩 에이전트는 네트워크를 닫아 하나를 뺐지만, 여기서는 ERP에 닿는 것이 목적이라 통신을 닫을 수 없다. 그래서 **도구 묶음을 나누고, 밖으로 나가는 길을 먼저 좁히고, 남는 행동은 건마다 승인**한다.

- **도구 묶음과 건별 승인.** 조회용(조회·추출 등급)과 변경용(변경·범용 조작 등급)으로 나눈다. 대화가 쓰는 묶음은 시작할 때 코드가 정하고 대화 중에 모델이 넓히지 못한다. 질문과 분석만 하는 대화에는 변경용 묶음을 열지 않는다. 변경용 묶음이 열린 대화는 세 능력이 다 모인 상태이므로 변경 호출은 예외 없이 승인(5절)을 거치고, 조회용 묶음에서도 상한을 넘는 추출은 승인으로 간다.
- **값 단위로 본다.** 신뢰 못 할 입력을 읽었다고 대화 전체를 막지 않는다. 그 입력에서 나온 값이 변경·추출·전송 도구의 인자로 들어갈 때 자동 실행을 멈추고 검토로 보낸다(`security.md` 9절). 입력 필터와 선별 모델은 보조다. [1][5]

| 밖으로 나가는 길 | 지나가는 것 | 좁히는 방법 |
|---|---|---|
| 외부 모델 API | 프롬프트에 실린 업무 데이터, 개인정보, 소스 코드와 그 안의 자격증명 | 등급 × 목적지 표, 호출 직전 가림, 계약 조건 확인(8절) |
| 파일 반출 | 추출 결과 | 상한, 가림, 목적 기록, 저장 위치와 내려받을 사람 고정(6절) |
| 메일·메신저 전송 | 답변, 첨부, 사람에게 넘길 때의 요약 | 임의 전송 도구는 넣지 않는다(제안값). 넣는다면 받는 곳을 요청자 본인과 설정에 적힌 창구로 고정하고, 본문을 사람이 본 뒤 보낸다 |

## 3. 행동 등급과 처리
| 등급 | 행동 | 도구 등급 | 기본 처리 | 누가 정하나 |
|---|---|---|---|---|
| 0 | 지식 문서를 찾아 근거와 함께 답한다 | 조회(문서 검색) | 자동. 문서 권한 필터, 인용 | 검색 API(서버가 넣은 신원) |
| 1 | 업무 데이터와 소스 코드를 건별로 읽어 화면에 보여 준다 | 조회 | 자동. 반환 상한, 호출 수 제한, 감사 기록 | 권한은 ERP, 상한은 코드 |
| 2 | 파일로 나가는 추출. 개발 시스템에서 되돌릴 수 있는 변경(소스 수정, 데이터 갱신, 설정 변경) | 추출, 변경, 범용 조작 | 추출은 필터·상한·목적이 있으면 자동이고 상한을 넘으면 승인. 변경은 계획 → 리뷰 → 승인 뒤에만. 범용 조작은 단계마다 확인 | 권한은 ERP. 상한·범위·환경·승인 대조는 코드. 승인은 사람(5절) |
| 3 | 품질·운영 시스템에 닿는 변경과 이관, 되돌릴 수 없는 것, 권한·역할 변경, 승인·감사 기록 접근, 승인 대행 | 주지 않는다 | 어시스턴트가 실행하지 않는다. 기존 변경 관리·이관 절차와 담당자에게 넘긴다 | 배포 설정 + 실행 전 검사 + ERP 권한 |

- **읽는 법.** `security.md` 8절의 등급은 되돌릴 수 있는가로 나눈다. 여기서는 데이터 등급과 대상 시스템이 더해져 조회에도 등급이 생긴다. 도구 등급(조회·추출·변경·범용 조작)은 도구에 붙고 행동 등급은 호출 한 건에 붙는다. 등급을 모르는 도구는 변경으로 다루고, 판정에 실패하면 통과가 아니라 차단이다.
- **C0에서 만드는 표.** 기능(지식 검색, 소스 읽기, 소스 수정, 데이터 조회, 데이터 반출, 화면 조작) × 환경(개발·품질·운영)의 칸마다 허용 / 승인 필요 / 금지를 적는다. 빈칸은 금지다. 칸마다 그것을 강제하는 설정·코드를 옆에 적고, 적지 못한 칸이 C5의 할 일이다.
- **데이터 등급이 처리를 바꾼다.** 민감·고유식별정보나 공시 전 재무 정보가 든 추출은 상한 안이어도 데이터 주인의 승인을 받는다(제안값).

### 응답 유형별 처리
| 유형 | 누가 판정하나 | 어시스턴트가 하는 일 | 사람에게 넘기는 조건 |
|---|---|---|---|
| 사내 규정·절차 답변 | 근거 유무는 코드(인용 대조), 내용은 문서 주인 부서 | 현행 문서의 구절에 문서명과 개정일을 붙여 답한다. 문서에 없는 승인·예외·약속을 만들지 않는다 | 근거를 못 찾음, 문서끼리 충돌, 개별 사정에 대한 판단 요청 |
| 개인 데이터·업무 데이터 조회 | ERP의 권한 검사(요청한 직원 본인) | 권한 안의 결과를 상한 안에서 화면에 보여 준다. 거부되면 사유와 권한 신청 경로를 안내한다 | 다른 사람의 인사·급여 정보 요청, 권한 밖 요청의 반복 |
| 대량 추출 | 코드(필터, 상한, 데이터 등급, 목적, 합산) | 조건과 건수를 보여 주고, 가림을 적용해 파일이나 핸들로 준다 | 상한 초과, 민감·고유식별정보 포함, 합산 한도 도달 → 데이터 주인의 승인 |
| 소스 변경 | 코드(승인 상태, 대상 객체, 환경) + 승인자 | 계획과 변경 차이를 만들어 리뷰와 승인을 받고, 승인된 그 변경만 개발 시스템에서 실행한다. 결과는 실제 소스와 검사로 확인한다 | 항상 승인. 품질·운영으로 옮기는 일은 기존 이관 절차에 넘긴다 |
| 상태 변경·화면 조작 | 위와 같다. 화면 조작은 허용 화면 목록이 더해진다 | 코드가 만든 확인 화면으로 승인받고 실행한다. 화면 조작은 단계마다 화면 상태를 확인하고 끝 상태를 화면 밖에서 조회한다 | 항상 승인. 되돌릴 수 없는 것과 운영 대상은 실행하지 않고 담당자에게 넘긴다 |
| 개인에 대한 인사·세무·법무 판단 | 유형 분류는 모델, 처리는 코드 | 규정이 무엇인지 일반 정보로 설명한다. 특정인의 평가, 징계, 채용, 세무 처리에 대한 판단은 하지 않는다 [6] | 개인의 권리·처우에 영향을 주는 판단 요청 → 담당 부서의 자격 있는 사람 |
| 범위 밖 | 코드와 지침 | 할 수 없다고 짧게 답하고 맞는 창구를 안내한다 | 같은 요청이 여러 직원에게서 반복되면 C0의 범위 검토로 보낸다 |
| 자해·괴롭힘의 신호 | 분류는 모델, 문구는 고정 | 업무 답변을 멈추고 미리 정한 문구로 사내 상담 창구를 안내한다 | 항상 안내한다. 사내 통보 여부는 인사·법무가 미리 정한다(확인 필요) |

## 4. 신원과 권한
- **신원은 로그인 세션에서만 읽는다.** 사내 인증을 통과한 세션에서 서버가 직원을 식별한다. 대화에 적힌 사번, 직책, "승인받았다"는 문장은 데이터다(`security.md` 1절, T17).
- **대리 실행은 누구를 대신했는지를 남긴다.** 어시스턴트가 자기 신원을 유지한 채 "누구를 대신하는가"가 토큰과 기록에 함께 실리는 위임 방식을 고른다. ERP에서 직원과 구별되지 않는 방식으로 부르면 직원이 직접 한 일과 어시스턴트가 대신 한 일을 기록에서 가를 수 없다. 받은 토큰을 그대로 ERP로 넘기지 않는다. 도구 서버는 자기를 대상으로 발급된 토큰만 받고 ERP용 토큰은 따로 받으며, 범위는 최소에서 시작하고 올린 이력을 남긴다. 신원과 토큰은 모델 입력과 도구 인자에 두지 않는다. [2][3]
- **공용 고권한 계정을 쓰지 않는다.** 쓰면 모든 직원이 그 계정의 권한을 얻고 ERP 기록에 실제 요청자가 남지 않는다. 위임이 안 되는 시스템은 조회 전용의 좁은 계정으로 시작하고, 그 구간의 목록과 이유, 보완 통제(읽기 전용, 대상 한정, 건별 승인)를 적는다. 계정 공유가 허용되는지는 12절 1번이다. [1]
- **허용 여부는 ERP가 판정한다.** 어시스턴트 쪽 검사는 그 위에 겹치는 층이고, 시스템 프롬프트의 "본인 데이터만 보여 줘라"는 인가가 아니다. 도구마다 실행 신원과 ERP의 인가 지점을 표에 적고, 인가 지점이 어시스턴트 쪽 검사뿐인 줄은 다시 설계한다. 검색, 답 저장, 메모리도 요청자의 권한을 따른다(`erp-knowledge-tools.md`). [1]
- **어시스턴트의 신원에는 승인 역할이 없다.** 권한·역할을 바꾸는 권한과 감사 기능을 관리하는 권한도 주지 않는다. [4]

## 5. 승인
- **무엇에 묶나.** 도구, 대상 시스템·환경, 대상 객체, 변경 차이의 해시(추출이면 조건과 건수), 1회, 만료 시각(제안값: 승인 뒤 24시간). 하나라도 달라지면 무효이고, 서버가 승인된 인자와 실행 인자를 대조한다.
- **누가 승인하나(직무 분리).** 요청자가 혼자 확인해도 되는 범위와 다른 사람(담당 개발자, 업무 주인, 데이터 주인)의 승인이 필요한 범위를 표로 정한다. 다른 사람의 승인이 필요한 범위의 시작값(제안값): 이관 대상이 되는 소스·설정 변경, 재무 보고에 쓰이는 객체와 데이터의 변경, 상한을 넘거나 민감·고유식별정보가 든 추출. 이 범위는 내부회계·내부감사 담당자와 맞춘다(12절 11번). [4]
- **승인 화면은 코드가 만든다.** 모델의 요약이 아니라 실제 대상 시스템·환경, 대상 객체, 바뀌기 전과 후(추출이면 조건과 건수), 영향 범위, 데이터 등급, 되돌리는 방법을 보여 준다. 승인은 화면의 조작으로 받고 대화 속 "네"로 대신하지 않는다. 사람이 보는 내용과 게이트가 대조하는 내용이 같아야 한다.
- **무엇을 기록하나.** 승인 ID, 요청자, 승인자, 결정(승인·거절)과 사유, 승인 시각과 만료 시각, 도구, 대상 시스템·환경, 대상 객체, 변경 차이의 해시, 계획 ID와 version, 리뷰 판정. 어시스턴트 실행 계정이 쓸 수 없는 곳에 둔다(`plan-gate.md` 5절의 수준 3을 기본으로 한다, 제안값).
- **대기, 재개, 측정.** 승인 대기는 대화 밖에 저장하고, 대화가 요약된 뒤에도 구조화 상태로 남긴다. 거절된 요청은 다시 묻지 않고 실행하지 않는다. 대화당 승인 요청 수, 승인율, 요청자와 승인자가 같은 건수를 잰다. 승인율이 100%에 가까우면 걸러내지 못하는 승인이다(T16).
- **계획 게이트와의 대응.** 변경 등급의 호출은 `plan-gate.md`의 절차를 그대로 거친다. 바뀌는 것은 아래 표뿐이다.

| `plan-gate.md`의 항목 | ERP 어시스턴트에서 |
|---|---|
| 수정 대상(저장소 상대 경로), `base_commit` | ERP의 개발 객체(종류와 이름)와 계획을 쓴 시점의 객체 버전. 표기 규칙은 `bases/`에 적는다. 실행 직전에 버전이 같은지 다시 본다(제안값) |
| 승인 기록(`plan_id`, `version`, 본문 해시, 승인자) | 같은 항목에 요청자, 대상 시스템·환경, 변경 차이의 해시, 만료 시각을 더한다 |
| 사람의 승인 명령 | 승인자의 로그인 세션에서 여는 승인 화면. 어시스턴트가 부를 수 있는 도구로 만들지 않는다 |
| `approved`는 한 번에 하나 | 단위가 저장소가 아니라 요청이다. 승인 기록은 요청 ID와 요청자에 묶이고, 다른 요청의 승인이 내 변경을 통과시키지 않는다(제안값) |
| 실행 전 게이트(승인 상태, 범위, 보호 경로) | 승인 상태 + 대상 객체 범위 + 대상 환경(개발만) + 보호 대상(권한·역할, 승인·감사 기록, 검사 설정, 이관 설정). 대상 객체나 환경이 바뀌면 version을 올려 다시 리뷰하고 승인받는다 |
| 끝내기 전 검사와 CI의 범위 검사 | ERP의 변경 기록에서 실제로 바뀐 객체를 뽑아 수정 대상과 대조한다. 테스트와 정적 검사는 개발 시스템에서 돌린다 |

## 6. 내보내기 통제
| 통제 | 내용 | 강제하는 곳 |
|---|---|---|
| 행·열 상한 | 호출당 행 수, 열 수, 크기. 필터 없는 호출은 거부한다 | 도구 서버의 코드 |
| 민감 표·열 목록 | 목록에 든 표와 열은 기본으로 빠지거나 가려진다 | 도구 서버의 코드, ERP 권한 |
| 등급별 가림 | 8절 표의 "파일 반출" 칸대로 열 단위로 가린다 | 반출 직전의 코드 |
| 목적 입력 | 목적을 받아 감사 기록에 남긴다. 정해진 선택지와 자유 기입을 함께 둔다(제안값) | 확인 화면 |
| 목적지 제한 | 저장 위치와 내려받을 수 있는 사람을 고정한다. 핸들은 권한이 아니므로 내려받을 때 사용자를 다시 확인한다 | 파일 저장소 |
| 다운로드 기록과 정기 점검 | 누가, 언제, 어떤 조건으로, 몇 건을 받았는지 남기고, 주기를 정해 사람이 본다(13절) [9] | 감사 기록 |
| 쪼개 받기 합산 | 사용자·기간·표 단위로 건수를 더해 한도에 닿으면 승인으로 보낸다 | 도구 서버의 코드 |

- **범위.** 추출 결과가 파일이나 핸들로 직원에게 나가는 것(반출)에 건다. 조회 도구도 여러 번 부르면 추출이 되므로 합산은 조회에도 건다. 상한의 값은 자료에 없으므로 데이터 주인과 정한다.
- **넘으면.** 상한 초과, 민감·고유식별정보 포함, 합산 한도 도달은 데이터 주인의 승인(5절)으로 보낸다. 조건을 몰래 줄여서 실행하지 않는다. 모델에는 전체가 아니라 요약(건수, 열 이름, 앞 몇 행)만 주고, 그 앞 몇 행도 8절의 가림 대상이다.

## 7. 감사 기록
| 필드 | 내용 | 주의 |
|---|---|---|
| 요청자 | 로그인 세션에서 얻은 직원 식별자 | 대화에서 읽지 않는다 |
| 대리 주체 | 어시스턴트와 도구 서버의 신원, 릴리스 버전 | 서비스 계정만 남으면 감사 공백이다 |
| 도구 | 도구 이름, 도구 등급, 행동 등급 | 등급은 우리 표의 값 |
| 실제 인자 | 모델이 제안한 값이 아니라 서버가 실행한 값 | 추출한 값 자체는 넣지 않고 조건, 건수, 해시만 넣는다 |
| 대상 시스템·환경 | 시스템 식별자, 개발·품질·운영, 대상 객체 | 배포 설정에서 읽는다 |
| 승인자와 승인 ID | 승인 ID, 승인자, 승인 대상의 해시. 승인이 필요 없는 등급이면 그 사실 | 승인 기록과 대조할 수 있어야 한다 |
| 결과 | 성공·거부·오류, ERP가 돌려준 사유, 변경 전후 상태의 식별자, 시각 | 모델의 보고가 아니라 ERP의 응답 |
| 상관 ID | 요청 ID, 대화 ID와 턴 ID, ERP 기록과 맞출 식별자 | 모든 하위 호출에 전파한다 |

- **대화 기록과 따로 둔다.** 대화 기록(대화 ⊃ 턴 ⊃ 이벤트, `trace.md`)과는 목적(누가 했는지의 증거 / 진단과 평가), 읽는 사람, 보존 기간이 다르다. 도구 호출과 승인 한 건이 한 줄이고, 대화 원문과 추출 값은 넣지 않는다. [4]
- **추가 전용이고 어시스턴트가 고칠 수 없다.** 어시스턴트 실행 계정과 그 관리자에게 수정·삭제 권한을 주지 않는다. 감사 대상인 관리자가 감사 기능을 관리하지 않게 한다. 감사 기록을 쓸 수 없으면 변경과 추출을 막는다(제안값).
- **보존.** 기간을 정해 적는다. 개인정보를 처리하는 시스템의 접속 기록 보관 기간이 어시스턴트를 거친 조회에 어떻게 적용되는지는 12절 2번이다(확인 필요).
- **ERP 자체 기록과 대조한다.** 표본을 뽑아 감사 기록의 건을 ERP의 변경 기록·접속 기록과 상관 ID로 맞추고, 한쪽에만 있는 건을 센다. ERP 기록에 요청한 직원이 남는지도 본다.
- **기록만으로 재구성하는 시험.** 임의의 변경·추출 건을 골라 대화 원문을 보지 않고 감사 기록만으로 누가, 어느 시스템·환경에서, 무엇을, 누구의 승인으로 했는지를 사람이 적는다. 걸린 시간을 잰다(목표 5분 이내, 제안값).

## 8. 외부 모델로 나가는 데이터
| 데이터 등급 | 화면 표시 | 모델 컨텍스트(사내 서빙) | 외부 모델 API | 파일 반출 | 대화 기록 |
|---|---|---|---|---|---|
| 공개 | 허용 | 허용 | 허용 | 허용 | 허용 |
| 사내 | 허용 | 허용 | 계약 확인 뒤 허용 | 상한 안에서 허용 | 허용 |
| 기밀(소스 코드, 원가, 영업 자료) | 권한 안에서 허용 | 허용 | 보안·법무가 정한 범위만 | 승인 | 가림 |
| 개인정보 | 권한 안에서 허용 | 가림 | 가림 | 가림 | 가림 |
| 민감·고유식별정보 | 권한 안에서 일부 가림 | 금지 | 금지 | 데이터 주인의 승인 | 금지 |
| 공시 전 재무 정보 | 권한 안에서 허용 | 가림 | 금지 | 데이터 주인의 승인 | 금지 |

- **표를 쓰는 법.** C0에서 보안·개인정보·법무 담당자와 채운다. 칸마다 허용 / 가림 / 금지를 적고 빈칸은 금지로 둔다. 위의 값은 시작값(제안값)이고 법적 판단이 아니다.
- **줄이고, 가린다.** 원자료 행 대신 스키마, 집계, 표본으로 답할 수 있는지 먼저 본다. 표에서 가림·금지인 값은 모델 호출 직전에 필드 단위로, 정규식 같은 코드로, 메인과 하위 호출 모두에서 가린다(`security.md` 9절, T19). 소스 코드 속 자격증명도 같은 길로 나간다. 무엇을 가렸는지는 값이 아니라 이름표로 기록한다.
- **계약에서 확인할 것.** 입력과 출력을 학습에 쓰는가, 보존 기간과 그 예외, 무보존이 우리가 쓰는 모델과 기능에 적용되는가, 데이터 처리 주체가 누구인가(클라우드 사업자를 거치면 달라질 수 있다), 피드백 기능으로 보낸 대화가 달리 취급되는가. 개인정보가 실릴 때 처리 위탁과 국외 이전에 해당하는지, 소스와 데이터의 전송이 영업비밀의 비밀 관리에 영향을 주는지는 12절 5·6·15번이다(확인 필요).
- **공개 문서에서 읽은 것(2026-11-16).** 예: Anthropic의 공개 문서는 상용 API의 입출력을 기본으로 학습에 쓰지 않고, 30일 안의 삭제가 기본이되 예외가 있으며, 무보존은 조직 단위로 신청하고 기능과 모델에 따라 적용되지 않는 경우가 있다고 적는다. [5][6] 예: OpenAI의 API 문서는 동의 없이는 학습에 쓰지 않고, 악용 감시 기록을 기본 최대 30일 보존하며, 무보존은 사전 승인 대상이고 엔드포인트마다 다르다고 적는다. [7] 공개 문서를 읽은 것일 뿐이므로 우리 계약서 조항으로 다시 확인한다(확인 필요).

## 9. 대화 기록과 직원
- **정책에 적을 것.** 수집 항목, 목적, 보존 기간, 열람할 수 있는 사람, 삭제 요청의 처리. 인사 평가와 근태 감시에 쓰지 않는다는 문장을 넣는다(제안값).
- **열람과 보존.** 원문을 볼 수 있는 사람을 좁히고(사고 조사, 신고된 대화) 열람도 기록한다. 목적마다 기한을 정하고, 기한이 지난 기록은 자동 작업으로 파기해 결과를 남긴다. 감사 기록과 기한을 따로 정한다. 원문 수집과 저장 전 가리기는 C2에서 정한다.
- **직원에게 알릴 것.** AI 기반이라는 사실, 무엇이 기록되고 누가 보는지, 답변의 한계와 근거를 확인하는 방법, 넣으면 안 되는 정보. 직원 대표 2~3명(제안값)이 안내문을 읽고 무엇이 기록되는지 답할 수 있는지 본다. 평가 버튼이 대화를 모델 공급자에게 보내는 기능이면 사내 신고 경로와 구분하고, 끌지를 정한다.
- **법무·개인정보 담당자가 답할 질문(전부 확인 필요).** 대화 기록 수집이 근로자 감시 설비의 설치에 해당해 노사협의회 협의 사항인가. 도입 전에 직원에게 설명하고 의견을 들어야 하는가. 내부 업무 용도라는 이유로 AI 사전 고지 의무의 예외에 해당하는가, 계열사·협력사 인력이 쓰면 달라지는가. 기록 속 개인정보의 보존 근거와 삭제 요구의 범위는 어디까지인가. 해당 항목은 12절 7·12·13·16·17번이다.

### 외부 고객에게 열 때만
사내용에는 적용하지 않는다. 같은 어시스턴트를 고객에게 열 때 더한다. 괄호는 근거를 읽은 수준이다.
- **AI 고지 의무.** 한국의 인공지능기본법 제31조는 생성형 인공지능을 이용한 제품·서비스의 사전 고지를 정하고 제43조는 위반에 과태료를 둔다(원문 대조). 과태료 계도기간은 보도로만 봤다(요약 경유). EU의 AI Act 제50조는 늦어도 첫 상호작용 시점에 AI임을 알리게 하고 2026-08-02부터 적용된다(원문 대조). 모델 공급자의 이용 정책도 고지를 요구한다(예: Anthropic의 Usage Policy, 원문 대조). 미국 캘리포니아의 봇 고지 법령은 원문을 열지 못했다(확인 필요).
- **답변 책임.** 챗봇의 안내를 회사 웹사이트의 다른 정보와 같게 보고 회사의 책임을 인정한 소액 사건 결정이 있다(결정문 원문 대조 [16]). 다른 관할에서의 효력은 (확인 필요)다. 정책·가격·자격 답변은 현행 공식 문서에 근거하고, 권한 없는 약속·할인·합의를 만들지 않으며, 면책 문구에 기대지 않는다.
- **고위험 조언.** 의료·법률·금융·보험 등에서 개인에 대한 조언은 자격 있는 사람의 검토와 AI 사용 고지를 거치도록 공급자 정책이 요구한다(원문 대조 [6]). 일반 정보 설명과 구분한다.
- **위기·미성년자.** 자살·자해 신호에는 고정 문구와 상담 전화 안내로 응답한다(공급자 도움말, 일부만 읽음 [6]). 국내 상담 전화번호, 미성년자용 공급자 지침, 14세 미만의 법정대리인 동의 규정은 공식 자료로 확인해 넣는다(확인 필요).

## 13. 운영에서의 점검
- **끄는 스위치.** 전체 하나가 아니라 도구 묶음 단위로 둔다: 변경용 묶음, 추출 도구, 화면 조작 도구, 조회용 묶음, 외부 모델 경로. 변경용만 끄고 지식 답변은 유지할 수 있어야 끄기를 미루지 않는다. 스위치는 어시스턴트가 고칠 수 없는 설정에 두고 실제로 꺼 본다.
- **정기 점검.** 항목마다 주기(시작값은 월 1회, 제안값), 담당자, 사후 조치를 정하고 첫 점검 기록을 남긴다. 접속 기록(어시스턴트를 거친 조회, 거부된 요청의 반복). 권한 재확인(어시스턴트와 도구 서버 계정의 권한, 공용 계정이 남은 구간, 승인자 목록). 요청자와 승인자가 같은 건(분리 범위에서 0건인지). 대량 내보내기(상한 근처의 반복, 합산 한도 도달, 민감 표·열이 든 건). 대화 기록 열람 내역과 보존 기간이 지난 기록의 파기 결과. [9]
- **사고의 첫 조치.** 권한 밖 노출, 승인 없는 변경, 금지 등급 값의 외부 전송, 감사 기록 누락이 사고다. 해당 묶음을 끈다 → 감사 기록으로 영향 범위를 재구성한다 → 변경이면 되돌린다 → 정해 둔 곳(보안, 개인정보, 내부감사, 시스템 주인)에 알린다. 개인정보 유출이면 통지·신고 절차로 이어진다(12절 9번). 틀린 규정 답변으로 업무 피해가 났으면 그 유형의 답을 멈추고 문서 주인에게 보낸다. 사고 뒤에는 재발 방지 시험을 CRT에 더하고, 모의 사고 한 건으로 묶음 차단부터 범위 재구성까지 걸린 시간을 잰다.
- **다시 확인할 때.** 모델, 프롬프트, 도구, 권한 설정, ERP 버전이 바뀌면 CRT를 다시 돌린다. 공급자 약관과 법령은 분기마다(제안값) 법무와 다시 보고 조사일을 갱신한다.

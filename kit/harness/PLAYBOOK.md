# 에이전트 프로젝트 플레이북 — 시작부터 완성품까지

> 2~4일차 강의 내용과 수업 저장소(`HyunjunJeon/sds_ax_advanced_2026`)의 평가·하네스 자료를 "실제 프로젝트를 진행하는 순서"로 엮은 설명서다. 특정 과제에 묶이지 않고, 어떤 에이전트 프로젝트에도 쓸 수 있다.
> 각 단계는 **입력 → 할 일 → 산출물 → 게이트(다음 단계로 넘어가는 조건)** 로 되어 있다. 진행 상태는 `bash harness/scripts/phase.sh`가 판정한다. 순서는 프롬프트가 아니라 도구가 지킨다(3일차 5강).
> 평가·자기개선 규칙의 상세 근거: [`reference/eval-rsi-rules.md`](reference/eval-rsi-rules.md) (R1~R32)

```
P0 킥오프 → P1 워크플로우 → P2 아키텍처 → P3 지식·메모리 → P4 도구·스킬
   → P5 구현·기준선 → P6 하네스·관측 → P7 평가 → P8 자기개선·최적화 → P9 릴리스·회고
```

산출물은 모두 `design/`에 쌓인다. 템플릿은 `harness/templates/`에 있고 `bash harness/scripts/start-phase.sh <번호>`로 복사한다. 코드를 바꿀 때는 단계와 상관없이 매번 `plan-review` 스킬로 계획 → 독립 리뷰 → 승인을 거친다.

---

## P0. 킥오프 — 무엇을 "완료"라고 부를지 정한다
- **입력:** 사용자의 아이디어·요구사항, (있다면) 외부 평가 기준
- **할 일**
  - `project-kickoff` 스킬로 사용자를 **인터뷰**한다. 한 번에 하나씩 묻고, 모르는 항목을 지어내지 않는다. "잘 되면 완료" 같은 기준은 **실행 결과로 참/거짓을 가릴 수 있는 문장**으로 바꿔 다시 묻는다(R1, 4일차 `requirements-interview`).
  - 목표, 사용자, 완료 정의, 성공 지표(성공률·지연·비용), 제약(데이터·권한·예산·마감)을 적는다.
  - 외부 평가 기준(과제 채점표, 고객 인수 조건 등)이 있으면 항목을 그대로 브리프의 **인수 기준 체크리스트**로 옮긴다. P9에서 `criteria-check`가 이 표로 자가 점검한다.
  - 범위는 **아주 작은 조각 하나**로 줄인다(4일차 3강: "활용"이 아니라 "완전 대체"할 수 있는 작은 업무).
  - 개발 환경(작업 경로, 언어·런타임, 가상환경, 모델·공급자, 필요한 환경변수 이름)을 정한다.
- **산출물:** `design/00-brief.md`
- **게이트:** 완료 정의와 측정 가능한 성공 지표가 있고, 인수 기준과 개발 환경이 정해졌고, 사용자가 확인했다.

## P1. 워크플로우 — 사람이 지금 하는 일을 단계로 쪼갠다
- **입력:** brief
- **할 일**
  - 현재 업무를 **5단계 이하**로 적는다(3일차 4강 `architecture.md` 과제).
  - 각 단계에 **판단 / 생성 / 규칙 / 조회** 꼬리표를 붙인다. **판단과 생성이 함께 있는 구간**이 에이전트 후보다(3일차 5강). 결정적 검사(테스트·형식 검증·계산)는 코드로 처리한다.
  - 돈·민감정보·외부 쓰기·삭제가 있는 단계에 **휴먼 인 더 루프**를 표시한다(3일차 2강).
  - 겉보기엔 순차지만 실제로는 독립인 단계를 찾아 **병렬** 후보로 표시한다.
  - 예외 흐름을 적는다: 정보 부족, 범위 밖 요청, 판정기 오류(fail-closed), 시스템 오류.
- **산출물:** `design/01-workflow.md`
- **게이트:** 단계 ≤ 5, 단계마다 꼬리표와 입출력이 있고, HITL 지점과 예외 흐름이 표시됐다.

## P2. 아키텍처 — 싱글로 시작하고, 쪼갤 근거를 남긴다
- **입력:** workflow
- **할 일**
  - 각 노드를 **CODE / RULE / API / MODEL / AGENT** 중 하나로 분류한다. 모든 노드를 에이전트로 만들지 않는다(3일차 교재 Ch.1).
  - **시작은 무조건 싱글 에이전트 + 스킬**이다. 싱글은 쪼갤 수 있지만 멀티는 다시 합치기 어렵다(3일차 2·3강).
  - 멀티가 필요하다면 이유는 **페르소나가 아니라 컨텍스트 경계**여야 한다(컨텍스트 격리, 3일차 1강). 독립적인 관점이 필요한 리뷰어는 서브에이전트가 정당한 대표 사례다.
  - 패턴은 순차·병렬·분기·루프 4요소의 조합으로 설명한다. Router/Supervisor, Plan-and-Execute, Swarm(종료 장치 필수) 중 무엇인지 적는다.
  - 서브에이전트를 쓰면 입출력 계약을 정한다. 입력은 `task_id, goal, facts, allowed_tools`, 출력은 `status, facts, evidence_refs, uncertainty`.
  - 기능마다 **어디에 꽂을지**(스킬 / 서브에이전트 / 훅 / 미들웨어 / 도구 / 외부 서비스)를 고르고 한계를 적는다.
  - **하네스 6책임으로 빈칸을 확인한다(Day06).** 지침, 도구, 실행 제어, 상태, 검증, 기록마다 "프레임워크가 이미 하는 것 / 내가 추가할 것 / 근거 수준"을 표로 만든다.
  - **신뢰기반을 분리한다.** 평가기, 정답, 테스트, 권한 정책은 개선 주체(에이전트)가 고칠 수 없는 위치에 둔다(R15).
  - 상태 키, 종료 조건(완료·보류·사람 전환·실패)을 적고, 결정마다 `design/decisions.md`에 근거를 남긴다.
- **산출물:** `design/02-architecture.md`, `design/decisions.md`
- **게이트:** 노드 유형표, 확장 지점 선택 근거, 6책임 표, 종료 조건이 있다.

## P3. 지식·메모리 — 잘 저장하고, 필요한 것만 꺼낸다
- **입력:** architecture
- **할 일**
  - **저장 → 검색 → 활용** 세 단계를 각각 설계한다(2일차 1강, 3일차 1강).
  - 검색은 "적게, 정확히" 가져와야 한다. 벡터 DB는 기본값이 아니다. 먼저 **대·중·소 계층 폴더 + 카테고리마다 `index.md`** 구조를 검토한다. 목차 탐색은 작은 모델이나 디시전 모델 서브에이전트에 맡긴다(2일차 2강).
  - **규칙과 경험을 나눈다.** 규칙(항상 지켜야 할 것)은 항상 주입되는 문서에, 경험(과거 작업·실패·해결)은 구조화된 저장소(id, task, 실패 원인, 해결책, 태그, 출처 run_id, 버전)에 두고 검색해서 top-k만 꺼낸다.
  - **주입 위치:** 시스템 프롬프트는 앞에 고정하고, 날짜·검색된 메모리처럼 **변하는 값은 뒤에 메시지로** 둔다. KV 캐시는 텍스트 매칭이라 공백 하나만 달라도 깨진다(2일차 1강, 3일차 1강). 주입한 메모리 ID를 계획 문서와 로그에 남긴다.
  - 메모리를 에이전트가 직접 고칠 수 있으면 "검증 후 채택" 절차를 우회한다. 쓰기 경로를 제한하고, 메모리 파일이 프롬프트 인젝션 경로가 될 수 있음을 고려한다.
  - 멀티턴 전략을 정한다. 압축할 때는 요약에 **원본으로 찾아가는 경로**를 남긴다. 품질이 최우선이면 "사용자는 멀티턴, 내부는 단일턴"으로 간다(2일차 2·3강).
- **산출물:** `design/03-knowledge.md`
- **게이트:** 저장·검색·활용, 규칙·경험 저장 형식, 주입 위치(캐시 보존), 멀티턴 전략이 정해졌다.

## P4. 도구·스킬 — 도구는 적게, 스킬은 단계적으로
- **입력:** architecture, knowledge
- **할 일 — 도구**
  - 도구마다 **이름 + description(언제 쓰는지) + 타입이 명확한 인자**를 정한다. REST를 1:1로 감싸지 않고 비슷한 도구는 합친다(4일차 1·6강).
  - 반환값에는 `status`, 출처, 시점을 넣고 원문을 통째로 넣지 않는다. 빈 결과·오류·연결 실패를 구분한다. 모델이 고칠 수 있는 오류(400류)만 전달하고, 런타임 오류(500류)는 숨긴다(4일차 1강, 교재).
  - **MCP를 쓸지 판단한다.** 나만 쓰는 로컬 도구는 스킬 안 스크립트 + Bash로 두고, 공유·원격·권한 분리가 필요한 것만 Streamable HTTP MCP로 만든다(4일차 6강).
  - 순서가 중요한 흐름은 **도구가 현재 단계를 확인하고, 어긋나면 거절하고, 다음 도구를 알려주게** 만든다(3일차 5강).
  - 판단(승인 가능 여부, 범위 이탈, 근거 충분성)은 **Closed Question**(참/거짓, 선택, 점수)으로 묻고 임계값은 코드에 둔다. 판정기가 실패하면 통과가 아니라 차단이다(R6·R28, Jev 사례).
  - 출력은 입력보다 비싸다. 가능하면 선택지 고르기로 출력을 줄인다(2일차 3강).
- **할 일 — 스킬** (`skill-authoring` 스킬)
  - frontmatter `name`(소문자·하이픈, 64자 이내), `description`(What + When + 아닌 경우, 짧게).
  - 본문은 5천 토큰 이내, **XML 태그로 구역**을 나눈다. 상세는 `references/`, 실행은 `scripts/`, 양식은 `assets/`(4일차 2·5강).
  - 다단계 필수 절차는 **스크립트 체인**(`1.sh` 출력이 다음 스크립트를 안내하고 실행 증거를 남김)으로 만든다(4일차 2강).
- **산출물:** `design/04-tools-skills.md`, 스킬 폴더들
- **게이트:** 도구 명세표와 스킬 목록이 있고, 도구 수를 줄일 여지를 검토했고, skill-authoring 점검을 통과했다.

## P5. 구현·기준선 — 돌아가는 가장 단순한 버전
- **입력:** P1~P4 산출물
- **할 일**
  - 가장 단순한 구현을 먼저 만든다. 흐름이 고정이면 LangGraph(노드·엣지), 열린 작업이면 Deep Agent(`create_deep_agent` = `create_agent` + 미들웨어)(2일차 5·6강, 3일차 5강).
  - 빌드·실행·검사(lint·test·format) 명령을 한 줄씩 확보하고 README에 적는다. 새 코드는 처음부터 lint와 docstring 기준을 통과시킨다.
  - 기록이 남게 한다. MemorySaver만 쓰면 터미널을 끄면 사라진다(3일차 5강).
  - Anthropic API는 프롬프트 캐시를 **명시적으로** 켜야 한다. `usage`에서 캐시 적중을 확인한다(2일차 5강).
  - **기준선을 측정한다:** 고정 작업 몇 개로 성공률, 소요 시간, LLM·도구 호출 수, 재시도 수, 토큰을 잰다(3일차 교재 Ch.1).
  - 유료 실행 직전에는 규모(작업 수 × 반복 × 예상 호출 수)를 한 줄로 고지한다(R29).
- **산출물:** 동작하는 코드, `design/05-build.md`(빌드·실행 명령과 기준선 수치)
- **게이트:** README 명령 그대로 새 환경에서 실행되고, lint가 통과하고, 기준선이 기록됐다.

## P6. 하네스·관측 — 모델을 뺀 나머지 전부
- **입력:** 동작하는 코드
- **할 일 — 실행 제어** (하네스 = 도구·컨텍스트·상태·권한·예산·트레이스, 3일차 4강)
  - **모델의 제안과 실행 권한을 분리**하고, 쓰기 작업 앞에 승인 게이트를 둔다. 게이트는 Host나 서버에서 실제로 막아야 한다(3·4일차 교재). 판정기 오류는 차단으로 처리하고, 우회하면 그 사실을 기록한다.
  - 계획 기반 작업이라면 **승인된 계획 밖의 변경을 차단**하고 "범위 변경, 계획 갱신과 재리뷰 필요"를 알린다.
  - 게이트가 서브에이전트 경로에도 걸리는지 검증한다. 부모에 건 검사는 서브에이전트 도구 호출을 못 볼 수 있다.
  - 데이터 접근은 최소 권한으로 준다. insert/update는 검토하고 delete는 차단한다(4일차 3강).
  - 재시도 횟수, 전체 예산(턴·토큰·시간), 종료 상태(완료·보류·사람 전환·실패)를 정한다. 외부 쓰기에는 체크포인트와 idempotency key를 둔다.
  - 가짜 도구 호출 기록 주입 같은 공격은 세션 분리로 막는다(2일차 5강).
- **할 일 — 관측** (R9~R12)
  - 요청 ID별 **append-only JSONL 이벤트 로그**를 남긴다. 필드는 `run_id`, `thread_id`, `turn_index`, `phase`, `event`, `call_id`, 부모 ID, 시각, 소요, 상태, 오류, 버전 라벨이다.
  - 이벤트 종류: `llm_call`, `tool_call`, `memory_retrieve`/`memory_write`, `gate_block`, `improve_*`.
  - 실행이 끝나면 `summary.json`을 쓴다: 총 소요, LLM·도구 호출 수, 재시도 수, 토큰, 비용. **모르는 값은 0이 아니라 `null`**이다.
  - 조회 도구로 run별 첫 실패 지점과 직전 맥락을 찾을 수 있게 한다.
  - 키와 비밀은 로그에 남기지 않고 마스킹한다.
- **산출물:** `design/06-harness.md`
- **게이트:** 승인 게이트가 실제로 차단하고, 한 요청의 흐름이 로그에 시간순으로 남고, 조회 도구가 실패 지점을 찾는다.

## P7. 평가 — 개선은 증명해야 개선이다
- **입력:** 하네스와 관측까지 갖춘 시스템, `reference/eval-rsi-rules.md` §1
- **할 일**
  - 평가셋에 **Implicit / Explicit / Negative / 근거 없음 / 권한 없음 / 도구 실패** 사례를 넣는다. 가능하면 사람이 확정한 **골드셋**을 쓴다(3일차 3강, 4일차 교재). 시나리오는 실행 **전에** 정하고, 바꾸면 새 데이터 버전으로 본다(Day05).
  - 세 축을 분리해서 채점한다: **Activation**(트리거 Precision/Recall), **Execution**(필수 행동·유효 인자), **Outcome**(업무 완료·근거 품질).
  - 채점 순서는 **Code**(결정적 검사) → **의미 판정**(루브릭 + Judge·디시전 모델) → **사람**(불일치)이다. 정책·안전 실패를 다른 점수의 평균으로 상쇄하지 않는다(R14).
  - **완료는 증거로 판정한다.** 에이전트의 "완료했다"는 제안일 뿐이다(R13).
  - **실패 분석:** fact / hypothesis / alternative / evidence_ids를 나눠 쓴다. 근거 ID가 없으면 개선 실험을 시작하지 않는다(R7).
  - Judge를 쓰면 사람 라벨로 false pass·false reject를 먼저 잰다(R17). mock·scripted 결과는 "계약 검증"이지 개선율이 아니다(R16).
  - 근거 수준을 라벨로 단다: 실행 경로에서 확인 / 코드 정의만 / 문서만 / 추정(R8, Day06).
  - 항상 로드돼야 하는 스킬은 평가에서 빼고 SessionStart 훅으로 강제 로드한다(4일차 2강).
- **산출물:** `design/07-eval.md`, `eval/` 평가셋과 실행 스크립트
- **게이트:** 평가가 명령 한 줄로 재실행되고, 기준선 결과표(건수·통과·시간·호출·재시도·실패 종류)가 채워졌다.

## P8. 자기개선·최적화 — 손잡이 하나, 같은 조건, 미리 정한 판정
- **입력:** 평가 결과, `reference/eval-rsi-rules.md` §2·§6-D
- **할 일 — 자기개선 루프** (`self-improve-loop` 스킬, Day05_new 노트북 06)
  1. **여는 손잡이를 하나로 정한다.** 메모리 규칙, 스킬 문서 하나, 도구 정책 JSON 중 하나. 모델·평가기·테스트·예산은 고정한다(R18).
  2. **개선안은 선언형 형식으로 받는다.** 스키마로 검증하고 거부 사유를 기록한다. 평가 기준 변경·실패 삭제·예산 증가 키는 금지한다(R19).
  3. **오염 검사:** 개선기 입력에 정답, 임계값, holdout 흔적이 있으면 호출 전에 멈춘다(R20).
  4. **비교:** 현재안과 후보를 같은 평가셋·조건에서 돌리고, 점수식은 미리 고정한다(R21).
  5. **판정(순서 고정):** NOT_DETERMINABLE(완료율 90% 미만 또는 개선 여지 0) → HOLD(새 실패 유형이나 기존 통과 회귀) → ADOPT(실패 감소) → 그 밖은 HOLD(R22).
  6. **채택:** ADOPT만 반영하고 버전 라벨(r0, r1…)과 근거 라운드 파일을 기록한다. 다음 작업에서 쓰였다는 로그를 증거로 남긴다(R25). 기존 기능 회귀 테스트는 매 라운드 돌린다(R23).
  7. **holdout은 마지막에 한 번만** 연다. 결과를 본 뒤 임계값이나 반복 수를 바꾸지 않는다(R24·R26).
- **할 일 — 성능 최적화** (`optimize-agent` 스킬, 3일차 6강 `prompt.txt` 패턴)
  - 원칙: **동작이 바뀌면 안 된다**(도구 호출 순서 포함). 새 세션에서 상위 모델로 작업한다.
  - 도구 수 줄이기, 프롬프트 축소·동적 제어, 스킬 도입, 지연을 고려한 서브에이전트 분리, 작은 모델로 내리기, 판단 구간을 디시전 모델로 교체.
  - 모든 변경은 **토글**로 만들고 "기존 문제 → 개선 → 근거 수치"를 남긴다. 고친 뒤 P7 평가를 다시 돌린다.
- **산출물:** `design/08-optimization.md`, `improve/round-<n>.json`(append-only)
- **게이트:** 개선 라운드나 최적화가 1회 이상 기록됐고, 판정마다 before/after와 회귀 결과가 있다.

## P9. 릴리스·회고 — 다른 사람이 그대로 재현할 수 있게
- **입력:** 완성된 시스템
- **할 일**
  - **README.md:** 환경, 설치·실행 명령, 환경변수 이름(값은 넣지 않음), **인수 기준별 테스트 케이스**(입력 → 기대 관찰 → 확인 명령)를 넣는다.
  - `criteria-check` 스킬로 brief의 인수 기준을 하나씩 실제 증거와 함께 자가 점검한다.
  - 원본을 commit이나 digest로 고정하고 **Eval 카드**(재현 조건·관측 결과·배포 근거)를 함께 낸다. 평가를 안 했거나 기준에 못 미친 것은 내보내지 않는다(4일차 교재 Ch.7). 보고서에는 판정(HOLD / READY_FOR_HUMAN_REVIEW)과 "자동 승인이 아님"을 적는다(R30).
  - 배포 방식(`.skill` 압축, 플러그인, 사내 레지스트리, 서비스)과 롤백 계획을 정한다(4일차 3강).
  - **회고:** "내 대화 기록을 분석해줘"로 잘된 점, 낭비된 점, 다음에 스킬로 만들 반복 작업을 뽑는다(3일차 7강).
- **산출물:** `design/09-release.md`, 제품 `README.md`
- **게이트:** 깨끗한 환경에서 README대로 재현했고, 인수 기준 자가 점검표의 모든 항목에 증거가 있고, 회고를 했다.

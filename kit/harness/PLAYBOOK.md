# 에이전트 프로젝트 플레이북 — 시작부터 완성품까지

> 2~4일차 강의(RAG · 멀티 에이전트 · MCP/Skills/Eval)와 수업 저장소(`HyunjunJeon/sds_ax_advanced_2026`)의 같은 날 실습 자료를 "실제 프로젝트를 진행하는 순서"로 재구성한 설명서다. 강의가 하루 끝날 때마다 갱신한다(반영 범위는 저장소 루트 `UPDATING.md`).
> **특정 프레임워크를 전제하지 않는다.** 강의 실습은 LangGraph·Deep Agents로 했지만, 여기서는 그 밑에 있는 원칙(컨텍스트 관리, 도구 설계, 스킬, 하네스, 평가)만 가져온다. 프레임워크 이름은 예시로만 적는다.
> 각 단계는 **입력 → 할 일 → 산출물 → 게이트(다음 단계로 넘어가는 조건)** 로 되어 있다.
> 진행 상태는 `bash harness/scripts/phase.sh`가 산출물 파일을 읽어서 판정한다. 순서는 프롬프트가 아니라 도구가 지킨다(3일차 5강).

```
P0 킥오프 → P1 워크플로우 → P2 아키텍처 → P3 지식·데이터 → P4 도구·스킬
   → P5 구현·기준선 → P6 하네스·안전·관측 → P7 평가(Eval) → P8 최적화·개선 → P9 릴리스·회고
```

산출물은 모두 `design/` 폴더에 쌓인다. 템플릿은 `harness/templates/`에 있고, `bash harness/scripts/start-phase.sh <번호>`로 복사한다.

---

## P0. 킥오프 — 무엇을 "완료"라고 부를지 정한다
- **입력:** 사용자의 아이디어·요구사항
- **할 일**
  - `project-kickoff` 스킬로 사용자를 **인터뷰**한다(3일차 7강: 나를 인터뷰하는 스킬). 한 번에 질문 하나씩, 답이 나올 때까지 판다.
  - 목표, 사용자, "완료" 상태, 성공 지표(성공률·지연·비용), 제약(데이터·권한·예산·마감)을 적는다.
  - 범위는 **아주 작은 조각 하나**로 줄인다(4일차 3강: "활용"이 아니라 "완전 대체"할 수 있는 작은 업무).
  - **개발 하네스부터 세팅한다**(6일차 1·2·6강). 쓰는 에이전트 도구의 공식 문서에서 작동 방식, 설정 디렉터리, 컨텍스트 윈도우 문서를 먼저 읽는다.
    - 전역 설정·전역 지침·전역 스킬은 모든 프로젝트에 로드되므로 비워 두거나 공통인 것만 둔다. 프로젝트 설정은 팀 공유 파일과 개인 파일(버전 관리 제외)로 나누고, 비싼 모델·엔드포인트는 그 프로젝트 설정에서만 바꾼다.
    - 공개 하네스·플러그인은 처음부터 짜지 말고 **포크**해서 내 작업 방식과 어긋나는 점만 바꾼다. 설치 전에 에이전트에게 구성(스킬·에이전트·훅·MCP)과 위험을 먼저 분석시키고, 망가져도 되는 환경에서 설치해 본다. 개인화 버전을 설치하면 원본은 지운다.
    - 만든 하네스는 **빈 폴더에서 작은 개발 작업(예: 백엔드 API 하나)으로** 처음부터 끝까지 돌려 검증한다.
- **산출물:** `design/00-brief.md`
- **게이트:** 완료 정의와 측정 가능한 성공 지표가 있고, 사용자가 확인했다.

## P1. 워크플로우 — 사람이 지금 하는 일을 단계로 쪼갠다
- **입력:** brief
- **할 일**
  - 현재 업무를 **5단계 이하**로 적는다(3일차 4강 `architecture.md` 과제).
  - 각 단계에 **판단 / 생성 / 규칙 / 조회** 꼬리표를 붙인다. **판단과 생성이 함께 있는 구간**이 에이전트 후보다(3일차 5강).
  - 돈·민감정보·외부 쓰기가 있는 단계에 **휴먼 인 더 루프**를 표시한다(3일차 2강).
  - 겉보기엔 순차지만 실제로는 독립인 단계를 찾아 **병렬** 후보로 표시한다.
- **산출물:** `design/01-workflow.md`
- **게이트:** 단계 ≤ 5, 단계마다 꼬리표와 입출력이 있고, HITL 지점이 표시됐다.

## P2. 아키텍처 — 싱글로 시작하고, 쪼갤 근거를 남긴다
- **입력:** workflow
- **할 일**
  - 각 노드를 **CODE / RULE / API / MODEL / AGENT** 중 하나로 분류한다. 모든 노드를 에이전트로 만들지 않는다(3일차 교재 Ch.1).
  - **시작은 무조건 싱글 에이전트**(+ 스킬)다. 싱글은 쪼갤 수 있지만 멀티는 다시 합치기 어렵다(3일차 2·3강).
  - 멀티가 필요하다면 이유는 **페르소나가 아니라 컨텍스트 경계**여야 한다(컨텍스트 격리, 3일차 1강).
  - 패턴은 순차·병렬·분기·루프 4요소의 조합으로 설명한다. Router/Supervisor, Plan-and-Execute, Swarm(종료 장치 필수) 중 무엇인지 적는다.
  - 서브에이전트를 쓰면 입출력 계약을 정한다. 입력은 `task_id, goal, facts, allowed_tools`, 출력은 `status, facts, evidence_refs, uncertainty`.
  - 상태 키, 선행 조건, 종료 조건을 적는다.
  - 결정마다 `design/decisions.md`에 근거를 한 줄씩 남긴다.
- **산출물:** `design/02-architecture.md`, `design/decisions.md`
- **게이트:** 노드 유형표, 싱글/멀티 판단 근거, 종료 조건이 있다.

## P3. 지식·데이터 — 잘 찾아오고, 잘 이야기하게
- **입력:** architecture
- **할 일**
  - **저장 → 검색 → 활용** 세 단계를 각각 설계한다(2일차 1강, 3일차 1강).
  - 검색은 "적게, 정확히" 가져와야 한다. 벡터 DB는 기본값이 아니다. 먼저 **대·중·소 계층 폴더 + 카테고리마다 `index.md`** 구조를 검토한다(2일차 2강).
  - 목차 탐색은 메인 컨텍스트를 채우므로 **작은 모델이나 디시전 모델 서브에이전트**에 맡긴다. 결과는 "여기 있으니 가서 읽어라" 또는 대신 읽은 요약으로 받는다.
  - 프롬프트 배치를 정한다. 시스템 프롬프트는 **앞에 고정**하고 지식은 스킬로 뒤에 붙인다. 날짜처럼 **변하는 값은 뒤쪽**에 둔다. KV 캐시는 텍스트 매칭이라 공백 하나만 달라도 깨진다(2일차 1강, 3일차 1강).
    - 추론 엔진의 prefix 캐시는 블록 단위로 앞에서부터 맞춘다. 대화 이력은 **뒤에 붙이기만** 하고, 중간을 잘라내거나 순서를 바꾸는 압축은 캐시를 깬다는 것(첫 토큰 지연·비용 증가)을 알고 쓴다. 캐시는 TTL로 사라지니 재호출 간격이 긴 작업은 캐시 이득을 기대하지 않는다(7일차 3·4강).
    - **컨텍스트 길이가 곧 서빙 메모리 비용이다.** 긴 컨텍스트는 KV 캐시 메모리를 먹어 동시 처리 수를 줄이고, API 가격도 특정 길이 이후 급등한다. 불필요한 컨텍스트 누적을 막는다(7일차 1·2강).
  - 멀티턴 전략을 정한다. 압축할 때는 요약에 **원본 대화로 찾아가는 경로**를 함께 남긴다. 품질이 최우선이면 "사용자는 멀티턴, 내부는 단일턴"으로 간다(2일차 2·3강).
  - **원본은 파일에, 컨텍스트에는 최소만.** 긴 내용을 LLM에게 압축시키는 것이 가장 비싼 작업이다. 필요할 때 읽게(just-in-time) 하거나 싼 모델·서브작업으로 나눈다(5일차 5강).
  - **판단은 LLM 앞단에서 끝낸다.** LLM이 툴 콜로 판단 모델을 부르게 하면 모순이고 느리다. 사용자 입력 직후(미들웨어·훅, 또는 서브에이전트)에서 판단 모델이 먼저 처리하고, LLM은 "질문 + 골라 둔 근거"로 답변만 한다(5일차 5강).
    1. 의도 판단: 우리 데이터로 답할 수 있는 질문인가(필요하면 라우팅)
    2. 후보 고르기: `index.md`로 파일을 고르고, 청크마다 "필요한 내용이 있는가"를 yes/no로 묻는다
    3. 근거 고르기: 리랭킹 대신 코드로 문장에 번호를 붙이고 핵심 문장 번호만 받는다. 출처(문서·청크·문장 위치)는 코드가 붙인다
    - 판단 모델에는 번호·yes/no 같은 고정 출력만 요구한다. 여러 판단은 배치로 묶어 호출 수와 지연을 줄인다. 예외(파일을 못 찾음 등)가 많으면 서브에이전트로 유연하게 처리한다.
  - **에이전트 메모리를 계층으로 둔다**(6일차 4강): 원 기록 → 노트 → 요약 표현 → 주입 컨텍스트. 매 세션 주입되는 양은 작게 유지하고, 상한 밖 내용은 인덱스로만 가리킨다. 주기적으로 정리·압축하는 단계를 두고, 작업 종류에 맞춰 "무엇을 남길지" 기준을 문서로 정한다.
  - **질문·데이터로 필요한 스킬이 정해지는 경로는 LLM에 고르게 하지 말고 코드로 강제 로드한다.** LLM은 준비된 내용을 말하게만 한다(5일차 7강).
  - **파일 입력 정책을 명시한다:** 어떤 형식을 받고 어디에 저장해 인용하는지, 지원하지 않는 형식은 명확히 거부하는지(5일차 4강).
- **산출물:** `design/03-knowledge.md`
- **게이트:** 저장·검색·활용과 컨텍스트 배치도, 멀티턴 전략이 있다.

## P4. 도구·스킬 — 도구는 적게, 스킬은 단계적으로
- **입력:** architecture, knowledge
- **할 일 — 도구**
  - 도구마다 **이름 + description(언제 쓰는지) + 타입이 명확한 인자**를 정한다(4일차 1·6강).
  - REST를 1:1로 감싸지 않는다. 비슷한 도구는 합친다(add/minus/… → `calculator`).
  - 반환값에는 `status`, 출처, 시점을 넣고 원문을 통째로 넣지 않는다. 빈 결과·오류·연결 실패를 구분한다(4일차 교재).
  - 오류 정책: 모델이 고칠 수 있는 오류(400류)는 안내와 함께 전달하고, 런타임 오류(500류)는 숨기고 내부에서 처리한다(4일차 1강).
  - **MCP를 쓸지 판단한다.** 나만 쓰는 로컬 도구는 Skill 안 스크립트 + Bash로 둔다. 공유·원격·권한 분리가 필요한 것만 Streamable HTTP MCP로 만든다(4일차 6강).
  - 출력은 입력보다 비싸다. 가능하면 **선택지 고르기(클로즈드 퀘스천)** 로 출력을 줄인다(2일차 3강).
  - 분류·라우팅·근거 판정 같은 닫힌 질문(참/거짓, 선택, 점수)은 싸고 안정적인 판단 모델에, 문장 생성은 채팅 모델에 맡긴다. 임계값은 코드에 둔다(5일차 3·4·5강, 강의 예시: Jev).
- **할 일 — 스킬** (`skill-authoring` 스킬 사용)
  - `SKILL.md` frontmatter에는 `name`(소문자·하이픈, 64자 이내)과 `description`(What + When + 아닌 경우, 짧게, 1024자 이내)을 쓴다(`Day04/SKILLS_GUIDE.md`).
  - 본문은 5천 토큰 이내로 쓰고 **XML 태그로 구역을 나눈다**. 상세는 `references/`, 실행은 `scripts/`, 양식은 `assets/`에 둔다(4일차 2·5강).
  - 부작용이 있거나 순서가 중요한 절차는 모델이 스스로 부르지 못하게 하고 사용자나 진입 절차만 부르게 한다. 진입점 하나가 정해진 플레이북 중 하나를 골라 단계 그대로 따르게 하는 구조도 쓸 수 있다(6일차 4강, pstack 사례). 호출 제어 옵션의 실제 동작은 도구마다 확인한다.
  - 다단계 필수 절차는 **스크립트 체인**으로 만든다. `1.sh` 출력이 다음 스크립트를 안내하고 실행 증거를 남긴다(4일차 2강).
  - 순서가 중요한 대화 흐름은 **도구가 현재 단계를 읽고, 어긋나면 거절하고, 다음 도구를 알려주게** 만든다(3일차 5강).
- **산출물:** `design/04-tools-skills.md`, 스킬 폴더들
- **게이트:** 도구 명세표와 스킬 목록이 있고, 도구 수를 줄일 여지를 검토했다.

## P5. 구현·기준선 — 돌아가는 가장 단순한 버전
- **입력:** P1~P4 산출물
- **할 일**
  - 가장 단순한 구현을 먼저 만든다. 프레임워크는 필수가 아니다. 흐름이 고정이면 코드로 짠 워크플로우(함수 체인·그래프), 열린 작업이면 에이전트 루프(모델 + 도구 + 반복)로 시작한다. 강의 예시는 LangGraph 노드·엣지와 Deep Agents였다(2일차 5·6강, 3일차 5강).
  - 에이전트 루프는 "도구 호출은 메시지일 뿐이고, 실제 실행과 결과·오류 메시지 구성은 우리 런타임이 한다"는 구조로 이해한다(2일차 6강). 프레임워크를 쓰든 직접 짜든 이 경계를 코드에서 찾을 수 있어야 한다.
  - 기록이 남게 한다. 메모리에만 두면 프로세스를 끄면 사라진다. 대화와 트레이스를 파일이나 DB에 저장한다(3일차 5강).
  - Anthropic API는 프롬프트 캐시를 **명시적으로** 켜야 한다. `usage`에서 캐시 적중을 확인한다(2일차 5강).
  - **싱글 에이전트 기준선을 측정한다:** task_success, latency, 호출 수, 토큰(3일차 교재 Ch.1). 응답 지연은 첫 토큰 시간(TTFT)과 토큰 간격(ITL)을 나눠 기록한다(7일차 3강).
- **할 일 — 모델·서빙 결정** (`serving-plan` 스킬, 7일차)
  - **API를 쓸지 직접 서빙할지 정한다.** 비용(감가상각, 모델 교체 가능성), 보안(코드·데이터 유출), 커스터마이징 필요성 세 축으로 근거를 남긴다.
  - 직접 서빙한다면:
    - **용량은 가중치 + KV 캐시로 계산한다.** 가중치는 파라미터 수 × dtype 바이트, KV는 레이어·KV 헤드·헤드 차원·dtype이 들어간 공식 × 목표 컨텍스트 × 동시 요청 수다. GPU 메모리는 여유분을 남기고, 여러 GPU로 나누면 **GPU당** KV 여유를 따로 본다. 최대 컨텍스트는 실제 필요만큼으로 제한한다.
    - **설정은 검증된 공개 레시피(모델 × 장비)에서 시작**하고, 토크나이저·KV dtype·병렬화 크기·도구 호출/사고 과정 파서를 명시적으로 적어 버전 관리한다. 기동 로그의 KV 토큰 수·최대 동시성을 계산값과 대조한다("설정은 요청, 로그는 응답").
    - 단건 생성 예제 코드로 서비스를 띄우지 않는다. 동시 요청과 KV 메모리를 관리하는 추론 엔진을 쓴다. 엔진은 stateless로 두고 대화·도구 상태는 하네스가 가진다.
  - **양자화는 품질을 다시 잰 뒤 채택한다.** 웨이트와 KV 캐시 dtype은 따로 정한다. 저정밀일수록 오차가 누적돼 반복 출력 같은 저하가 생긴다. 남의 하락률 수치를 믿지 말고 P7 평가셋으로 같은 조건에서 비교한다. 4비트 포맷은 GPU 세대 지원도 확인한다.
  - 에이전트 코드는 엔진이 주는 표준 규격(OpenAI 호환 등)의 tool_calls·reasoning 필드에 의존하고, 모델별 원시 출력 파서를 직접 만들지 않는다. 필드 이름이 버전마다 다를 수 있으니 접근자 하나로 흡수한다. 반드시 맞아야 하는 출력 형식은 구조화 출력(문법 제약 디코딩)으로 강제한다.
- **산출물:** 동작하는 코드, `design/05-build.md`(실행 방법과 기준선 수치)
- **게이트:** 실행 명령 한 줄로 재현되고, 기준선 수치가 기록됐다.

## P6. 하네스·안전·관측 — 모델을 뺀 나머지 전부
- **입력:** 동작하는 코드
- **할 일 — 실행 제어** (하네스 = 도구·컨텍스트·상태·권한·예산·트레이스/평가, 3일차 4강)
  - **모델의 제안과 실행 권한을 분리**하고, 쓰기 작업 앞에 승인 게이트를 둔다. 게이트는 Host나 서버에서 실제로 막아야 한다(3·4일차 교재).
  - 데이터 접근은 MCP나 게이트웨이 뒤에 두고 최소 권한을 준다. insert/update는 검토하고 delete는 차단한다. 원시 SQL은 그대로 실행하지 않는다(4일차 3강).
  - 재시도 횟수와 전체 예산(턴·토큰·시간), 종료 상태(완료·보류·사람 전환)를 정한다.
  - 실패 유형별(근거 부족 / 정책 불가 / 시스템 오류) 다음 행동을 정한다.
  - 외부 쓰기에는 체크포인트와 idempotency key를 둔다. exactly-once는 자동으로 보장되지 않는다.
  - 가짜 도구 호출 기록 주입 같은 공격은 세션 분리로 막는다(2일차 5강).
  - **코드 변경 작업은 계획 → AI 리뷰 → 승인 후에만 실행한다.** 요구사항·범위·완료 조건이 없으면 진행하지 않고, 계획에는 수정 대상·순서·테스트 방법을 넣는다. 범위가 바뀌면 계획으로 되돌린다. 계획·리뷰는 컨텍스트를 통제할 수 있게 별도 서브에이전트로 둔다(5일차 7강, `plan-review` 스킬).
  - 비밀 키는 에이전트(코딩 도구 포함) 대화에 넣지 않는다. 빈 `.env` 틀만 만들게 하고 사람이 채운다(5일차 4강).
- **할 일 — 부탁·위임·강제 배치** (`hook-design` 스킬, 6일차 2·3·6강·교재)
  - 규칙마다 둘 곳을 정한다. 메모리(상시 지침)는 **부탁**, 스킬(필요할 때 읽는 절차)은 **위임**, 훅(정해진 시점에 반드시 실행되는 코드)은 **강제**다. 메모리는 지시일 뿐 강제가 아니다.
    - 같은 컨벤션을 **두 번 틀리면** 상시 지침에 남긴다.
    - 같은 절차를 **세 번째 붙여넣게 되면** 스킬로 묶는다.
    - 묻지 않아도 **매번 일어나야 하는 일**은 훅에 연결한다(예: 코드 수정 뒤 테스트 실행).
    - **다른 저장소에도** 같은 구성이 필요하면 플러그인으로 묶어 배포한다.
  - 지침은 계층으로 나눈다: 조직 / 개인 전역 / 프로젝트(커밋) / 경로 범위 규칙(해당 파일을 다룰 때만 로드) / 개인 로컬(버전 관리 제외) / 자동 메모리(개인 PC에만). 팀이 같은 결과를 내야 하는 지침은 커밋되는 파일로 옮긴다. 상시 지침은 짧게(200줄 이하) 두고 구조화된 양식(XML 등)으로 통일한다.
  - 지침 파일 우선순위 규칙을 확인한다. 여러 AI 도구를 함께 쓰면 원본을 한 파일로 통일하고 나머지는 참조만 둔다(예: 어떤 파일이 있으면 다른 파일을 안 읽는 규칙).
- **할 일 — 훅 설계** (6일차 3·6강·교재 3부)
  - 에이전트 루프를 그리고 끼어들 지점(세션 시작, 입력 제출, 도구 전·후, 서브에이전트 종료, 컴팩트 전·후, 알림, 멈춤)마다 "언제 동작해야 하는가"를 먼저 정한다. 도구 전·후가 가장 중요하다. 관점은 일관되게 컨텍스트 절감과 안정성이다.
  - **Pre는 막고, Post는 고치게 하고, Stop은 끝내기 전에 확인한다.** Post는 이미 실행된 뒤라 차단이 아니라 요약·기록·피드백 용도다. 세션 종료 이벤트에 중요한 정리를 의존하지 않는다.
  - **검사는 훅, 해결은 스킬.** 훅은 위반을 찾고 스킬은 고치는 법을 준다. 판정은 결정적 코드로 하고, 맥락 판단이 필요할 때만 작은 모델을 부른다. 실행할 테스트도 이름·폴더 규칙으로 코드가 고른다.
  - **조용히 통과하는 경로를 막는다.** 차단은 명시적 차단 신호(예: exit 2, JSON deny)로만 된다. 스크립트 오류·타임아웃·잘못된 출력은 기본적으로 통과(fail open)될 수 있으니 실패 정책을 명시하고, 핵심 금지는 권한 deny 설정으로 이중화한다. 매처를 우회하는 경로(셸로 파일 쓰기 등)와 병렬로 매칭된 훅의 결정 병합 규칙을 확인한다.
  - 훅은 권한을 **조일 수는 있어도 풀 수는 없다**. 클론한 저장소의 훅도 내 PC에서 실행되니 훅 자체가 공격 표면이다. 신뢰한 작업 공간에서만 켠다.
  - Stop 훅의 두 번째 통과는 재검증 증거가 아니다. **어느 한 층도 완전하지 않으니 최종 방어선은 PR 리뷰와 CI**다.
  - 프로젝트 훅은 규칙이 생긴 뒤 필요가 확인되면 추가한다. 처음부터 넣을 수 있는 건 권한 체크와 "자꾸 잊는 지침"을 입력 앞뒤에 붙이는 훅 정도다. 훅 예시는 `harness/hooks/`에 있다.
- **할 일 — 관측** (5일차 2·3강: 측정해야 개선할 수 있다)
  - 모든 실행 기록을 처음부터 관측 플랫폼(강의 예시: Langfuse)에 쌓는다. 데이터 제어권(셀프호스팅·내보내기), 보관 리전, 라이선스 비용을 보고 고른다.
  - 기록은 요청 단위(trace), 단계 단위(observation), 대화 단위(session)로 나눠 남긴다. 턴별 소요 시간에서 오래 걸린 호출과 낭비 패턴(오류 뒤 재시도 반복, 묶을 수 있었던 연속 도구 호출)을 찾는다.
  - 기록이 언제 전송되는지(실시간/종료 시) 파악해, 안 보일 때 지연인지 연동 실패인지 구분한다.
  - 직접 서빙한다면 큐 대기 / TTFT / ITL / 전체 지연 / KV 사용률 / 선점 횟수 / 캐시 적중률을 본다. 처리량이 아니라 SLO 안에서 끝난 요청량(Goodput)으로 판단하고, 증상별 의심 지점 표를 런북으로 둔다(TTFT↑ = 큐·Prefill, ITL↑ = Decode, 선점↑ = KV 부족)(7일차 교재 PART 8).
  - **평가 대상 표시를 기록할 때 같이 남긴다.** 근거 밖 사실 같은 자동 경고는 사용자 화면 대신 trace에 "체크 필요"로 남기고, 나중에 표시된 것만 골라 평가한다(5일차 3·4강).
- **산출물:** `design/06-harness.md`
- **게이트:** 권한·예산·승인 게이트·오류 정책이 구현됐고, 규칙마다 부탁·위임·강제 배치가 정해졌고, 실행 기록이 관측 플랫폼에 trace/session 단위로 쌓인다.

## P7. 평가 — 시험지, 채점, 풀이 과정
- **입력:** 하네스와 관측까지 갖춘 시스템, 쌓인 실행 기록
- **할 일 — 시험지(Golden Set)** (`golden-dataset` 스킬, 5일차 1강·교재 Ch.1)
  - 질문·답을 모으기 전에 "무엇이 끝나야 완료인가"를 담당자와 합의하고, 판정 가능한 조건(최종 상태, 대상 제약, 금지 행동, 정보 부족 시 행동, 도구 실패 시 허용 범위)으로 적는다.
  - **담당자 인터뷰에서 시작한다.** LLM 초안 → 담당자 피드백을 여러 번 오가고, 문서에 없는 예외의 정답은 LLM이 아니라 담당자가 채운다. 담당자가 정답을 못 주면 간이 버전을 배포해 기록을 쌓고 그걸 재료로 쓴다.
  - 정답지는 Q&A가 아니라 **시나리오**로 쓴다: `input`(에이전트에 줌) / `expected_output`(평가자 전용) / `metadata`(출처·검수자·버전). 거쳐야 할 단계, 금지 행동, 순서 필수(의존)·순서 무관(병렬)을 구분하고, 바뀌면 안 되는 상태도 적는다. 정답 경로 하나를 강제하지 말고 지켜야 할 제약을 정의한다.
  - 정상 처리만 넣지 않는다. 거절, 추가 질문, 도구 실패 후 미완료 안내, **한 조건만 바꾼 경계 사례 쌍**, 환경 변형(일시 오류, 응답 손실)을 넣는다.
  - **데이터셋은 기능이 아니라 고치려는 "문제점"으로 묶는다**(예: 툴 호출 과다 → 궤적 데이터셋). 키 이름은 목적에 맞게 바꿔도 된다(5일차 7강).
  - 운영 기록 중 반복되고, 재현 가능하고, 정답을 정의할 수 있는 것을 골든으로 승격한다. 기능을 바꿀 때마다 반영해 시험지가 과거에 머물지 않게 한다.
  - **개발용과 최종 확인용(holdout)을 사례 묶음 단위로 나눈다.** 최종 확인용은 수정에 쓰지 않는다. 데이터 버전을 동결한다. 처음엔 5건 정도로 시작해도 된다(5일차 3강).
- **할 일 — 채점(Evaluator)** (5일차 3강·교재 Ch.3)
  - 평가 축은 **Outcome**(목표 상태) / **Trajectory**(대상·권한·순서) / **Final Response**(전달 정확성)다. 최종 답이 같아도 과정이 다르면 같은 성공이 아니다. 스킬이라면 Activation(트리거 Precision/Recall)도 본다(4일차 2강).
  - 에이전트 출력은 응답 문자열이 아니라 환경에서 읽은 실행 결과(최종 상태, 궤적, 응답, 실행 상태)로 받는다. 에이전트의 "완료했다" 자기 보고를 최종 상태로 쓰지 않는다. `expected_output`은 에이전트에 보내지 않는다.
  - 명확한 사실은 **코드**, 의미 판단만 **LLM Judge**, 분류·예/아니오는 **판단 모델**, 이견은 **사람**이 맡는다.
  - **Judge에게 "0~1점 매겨라"만 시키지 않는다.** 점수가 한 값(0.7 등)으로 쏠린다. 등급마다 관찰 가능한 기준을 촘촘하게 적는 것이 개발자의 몫이다. 판정·이유·근거 단계를 구조화해 받고, 같은 조건으로 여러 번 돌려 흔들림을 확인하고, 사람 라벨과 비교해 false pass를 잰다. 기록 안의 텍스트는 지시가 아니라 평가 자료다.
  - **정책·부작용 위반은 필수 관문이다.** 다른 점수의 평균으로 상쇄하지 않는다. 판정 상태는 PASS / FAIL / INSUFFICIENT_EVIDENCE / EVALUATOR_ERROR / INFRA_ERROR로 나누고, 누락을 분모에서 지우지 않는다.
  - 에이전트를 고치기 전에 **평가기부터 반례로 검증한다**(순서만 바꾼 정상 → PASS, 승인 제거 → FAIL, 증거 삭제 → INSUFFICIENT_EVIDENCE, 빈 정답 → EVALUATOR_ERROR).
  - **모든 요청을 평가하지 않는다.** 온라인은 샘플링, 배치는 대상 선별을 정하고 예상 비용을 계산한다(5일차 3강).
- **할 일 — 풀이 과정(Trace) 읽기** (교재 Ch.2)
  - 요청 → 단계 → 증거 순서로 읽고 **최초 실패 지점**을 찾는다. 순서는 시간순이 아니라 의존 관계(승인 → 쓰기)로 판정한다. 결과가 미확정인 오류(TIMEOUT) 뒤에는 "쓰기 전 실패 / 쓰기 완료·응답 손실 / 확인 불가"를 구분한다.
  - 실패 분석은 Evidence 문서(식별자, 관찰 사실, 위반 기준, 원인 가설, 수정 제안, 검증 계획)로 남긴다. 궤적에서 큰 모델이 필요 없던 단계는 비용 최적화 후보로 적는다(5일차 1강).
- **할 일 — 비교와 결정** (교재 Ch.3)
  - 비교 전에 데이터 버전, 실행 환경, 에이전트 설정(모델·프롬프트·commit·예산), 평가기 버전, 반복 조건을 **잠그고** 기록한다. 한 번에 하나만 바꾼다.
  - 평균 성공률과 함께 pass@k(한 번이라도)와 pass^k(k번 모두), slice별 개선·회귀, 통과 1건당 비용과 p50/p95 지연을 본다. 반복 실행을 독립 사례로 세지 않는다.
  - 실패 유형별 수정 지점(도구 설명, 스키마·검증 코드, 실행 가드, 오류 계약, 중단 조건, 정답 기준)을 매핑한다. 모든 것을 시스템 프롬프트로 고치지 않는다. 반복되는 순서 위반은 문구가 아니라 도구·스킬 구조로 막는다.
  - **승인 기준을 결과를 보기 전에 고정한다:** 판정 유효성 → 정책·부작용 0건 → 목표 개선·중요 slice 무회귀 → 신뢰성·예산 → holdout 확인.
- **산출물:** `design/07-eval.md`, `eval/` 평가셋과 실행 스크립트
- **게이트:** 시나리오형 평가셋(개발/holdout 분리)과 검증된 평가기가 있고, 기준선 결과표가 채워졌다.

## P8. 최적화·개선 — 동작은 그대로, 근거는 남기고
- **입력:** 평가 결과
- **할 일 — 최적화** (`optimize-agent` 스킬, 3일차 6강 `prompt.txt` 패턴)
  - 원칙: **동작이 바뀌면 안 된다**(도구 호출 순서 포함). 새 세션에서 상위 모델로 작업한다.
  - 컨텍스트 관점: 도구 수 줄이기, 프롬프트 축소와 동적 제어, 스킬 도입 지점 찾기.
  - 구조 관점: 지연을 고려한 서브에이전트 분리, 작은 모델로 내리기(Sonnet → Haiku), 판단 구간을 디시전 모델로 바꾸기.
  - 모든 변경은 **토글**로 켜고 끌 수 있게 만든다. 변경마다 "기존 문제 → 개선 → 근거 수치"를 남긴다.
  - 증상에 맞는 계층만 고친다(발견 → 선택 → 수행 → 코드 → 공통 정책). 고친 뒤 P7 평가를 다시 돌린다.
- **할 일 — 서빙 최적화** (7일차, 직접 서빙할 때)
  - 하드웨어를 늘리기 전에 소프트웨어로 줄일 수 있는 것(양자화, 컨텍스트 축소, 캐시 적중)을 먼저 한다.
  - 목표(처리량 vs 지연)를 먼저 정하고 배치 토큰 예산·동시 시퀀스 수·추측 디코딩(speculative decoding)을 거기에 맞춘다. 한 번에 한 변수만 바꾼다.
  - KV를 DRAM·NVMe로 내리는 오프로드는 만능이 아니라 지연과 처리량의 절충이다. "재계산 vs 불러오기" 비용과 워크로드(멀티턴, 긴 공통 문맥)를 확인한 뒤 도입한다.
  - 사고 과정(thinking) 끄기는 첫 응답을 빠르게 하지만 품질이 떨어진다. 같은 평가셋으로 확인한 뒤 결정한다.
  - 벤치마크는 실제 트래픽의 입출력 길이 분포와 도착률로 돌리고, 모델·하드웨어·정밀도·엔진 버전·캐시 warm/cold를 함께 적는다. 남의 배수(예: "22배")를 인용할 때는 방향(개선/악화)과 조건을 확인한다.
- **할 일 — 기록 기반 개선** (5일차 2·7강, 6일차 배포 자료 `harness_final`의 Ratchet 원칙)
  - 실수가 반복되면 같은 실수를 다시 못 하게 **더 강한 층으로 옮긴다**: 지침 → 스킬 → 훅·권한 → 테스트·CI. 원래 실패 사례로 검증하고 회귀 스위트에 넣는다.
  - 작업 경험(성공·실패)을 파일 메모리로 남겨 세션이 끝나도 유지하고, 새 작업에서 관련 메모리를 꺼내 실제로 쓰는지 확인한다.
  - 기록에서 시스템 프롬프트·스킬·메모리 개선안을 만들고, **효과 측정과 기존 기능 회귀 검증을 통과한 것만** 반영한다.
  - 개인 작업 도구(코딩 에이전트 포함)에도 기록을 붙여 일주일 이상 쌓은 뒤 패턴을 보고 작업 방식을 고친다.
- **산출물:** `design/08-optimization.md`
- **게이트:** 변경마다 before/after 수치가 있고, 평가 회귀가 없다.

## P9. 릴리스·회고 — 검증된 것만 내보낸다
- **입력:** 최적화된 시스템
- **할 일**
  - 원본을 commit이나 digest로 고정하고 **Eval 카드**(재현 조건·관측 결과·배포 근거)를 함께 낸다. 평가를 안 했거나 기준에 못 미친 스킬은 게시하지 않는다(4일차 교재 Ch.7).
  - 배포 방식을 고른다: `.skill` 압축, 플러그인, 사내 레지스트리(LiteLLM 등, 첫 실행 때 업데이트 확인)(4일차 3강).
  - 롤백 대상과 승인자를 정한다.
  - **회고:** "내 대화 기록을 분석해줘"로 이번 프로젝트에서 잘된 점, 낭비된 점, 다음에 스킬로 만들 반복 작업을 뽑는다(3일차 7강).
- **산출물:** `design/09-release.md`
- **게이트:** Eval 카드, 배포 경로, 롤백 계획, 회고가 있다.

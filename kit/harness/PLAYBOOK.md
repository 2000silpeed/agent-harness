# 에이전트 프로젝트 플레이북 — 시작부터 완성품까지

> 2~4일차 강의, 수업 저장소(`HyunjunJeon/sds_ax_advanced_2026`)의 5~8일차 자료, 최종 프로젝트 안내(`Day08/project_guide.md`)를 "실제 프로젝트를 진행하는 순서"로 엮은 설명서다.
> 각 단계는 **입력 → 할 일 → 산출물 → 게이트(다음 단계로 넘어가는 조건)** 로 되어 있다. 진행 상태는 `bash harness/scripts/phase.sh`가 판정한다. 순서는 프롬프트가 아니라 도구가 지킨다(3일차 5강).
> 상세 근거: [`reference/dcode.md`](reference/dcode.md)(dcode 확장 지점·루브릭 매핑), [`reference/eval-rsi-rules.md`](reference/eval-rsi-rules.md)(평가·자기개선 규칙 R1~R32).

```
P0 킥오프 → P1 워크플로우 → P2 아키텍처 → P3 지식·메모리 → P4 도구·스킬
   → P5 구현·기준선 → P6 하네스·관측 → P7 평가 → P8 자기개선·최적화 → P9 제출·회고
```

산출물은 모두 `design/`에 쌓인다. 템플릿은 `harness/templates/`에 있고 `bash harness/scripts/start-phase.sh <번호>`로 복사한다.

## 최종 프로젝트 한눈에 보기

**주제:** dcode(deepagents-code) 소스를 활용해 Coding Assistant를 만든다. 제출은 Google Form이고 닉네임을 쓴다. 채점자가 **제출 소스를 빌드해서 dcode를 실행해 평가**하므로, 테스트 케이스가 담긴 `README.md`가 필수다(`Day08/project_guide.md`).

| 평가 항목 (40점) | 제품에 들어가야 할 것 | 다루는 단계 |
|---|---|---|
| 1. Python 개발 기준 (10): PEP8, 명명·import, docstring | dcode의 `ruff select=["ALL"]`, google docstring, 상대 import 금지 규칙을 새 코드에도 통과시킨다 | P5, P9 |
| 2. 작업 계획·리뷰 (10): 요구사항·범위·완료조건, 수정 대상·순서·테스트, AI 리뷰 반영, 승인 후에만 코드 변경 | 계획 스킬, 리뷰어 서브에이전트, 계획 승인 게이트(PreToolUse 훅 또는 미들웨어) | P1, P2, P4, P6 |
| 3. Memory·Self-Improving (10): 세션 간 유지, 관련 메모리 검색·활용, 실패 기반 개선안 생성, 전후 검증 후 채택 | 경험 저장소 + 검색 주입, 개선안 생성기, 고정 평가셋으로 before/after 비교, 채택 기록 | P3, P7, P8 |
| 4. 모니터링 (10): 요청별 전체 흐름, LLM·도구·메모리·자기개선 기록, 시간·호출·재시도 지표, 조회 도구 | 요청 ID별 JSONL 이벤트 로그, `summary.json`, 조회 CLI·스킬 | P6, P7 |

> dcode는 기본으로 **plan mode가 없고, 메모리 검색이 없으며(AGENTS.md 전문을 스레드당 1회 주입), 도메인 단계 단위 로그가 없다.** 이 세 가지 빈칸을 채우는 것이 프로젝트의 본체다(`reference/dcode.md` §2.4, §2.10, §2.11).

## P0. 킥오프 — 무엇을 "완료"라고 부를지 정한다
- **입력:** 과제 안내(`Day08/project_guide.md`), 사용자의 아이디어
- **할 일**
  - `project-kickoff` 스킬로 사용자를 **인터뷰**한다. 한 번에 하나씩 묻고, 모르는 항목을 지어내지 않는다. "잘 되면 완료" 같은 기준은 **실행 결과로 참/거짓을 가릴 수 있는 문장**으로 바꿔 다시 묻는다(R1, 4일차 `requirements-interview`).
  - 목표, 사용자, 완료 정의, 성공 지표, 제약을 적고, 평가 기준 40점 항목을 브리프에 체크리스트로 옮긴다.
  - 범위는 **아주 작은 조각 하나**로 줄인다(4일차 3강).
  - **개발 환경을 정한다.**
    - **위치:** 수업 폴더 밖, WSL 안에서 작업한다(Day06 `task.md`). Day07 dcode 과제가 WSL 전용이었다.
    - **소스:** deepagents 모노레포 구조를 유지한다. `libs/code`가 `../deepagents` 등을 경로로 참조하므로 `libs/code`만 떼면 빌드가 깨질 수 있다.
    - **가상환경:** dcode는 SDK `deepagents==0.7.14`로 고정돼 있고 수업 루트 환경은 0.7.32다. 수업 저장소의 `uv sync` 환경과 섞지 말고 `libs/code`의 자체 lock으로 별도 venv를 만든다.
    - **모델:** Day07 과제 규칙은 OpenRouter 경유, OpenAI·Anthropic·Google 3사 모델 불허, 테스트 모델 GLM-5.3-Flash·DeepSeek-V4.1-Flash·Qwen3.8 등이었다. 최종 프로젝트에도 같은 규칙이 적용되는지는 **확인 필요**다.
  - 주의: dcode는 실행 폴더의 `AGENTS.md`, `.agents/skills`, `.claude/skills`를 **자기 메모리·스킬로 읽는다.** 이 하네스의 `.claude/skills`(개발용)와 제품용 스킬(`.deepagents/skills`)이 섞이지 않게, 제품 시연은 별도 작업 폴더에서 한다.
- **산출물:** `design/00-brief.md`
- **게이트:** 완료 정의와 측정 가능한 성공 지표가 있고, 평가 항목 체크리스트와 개발 환경이 정해졌고, 사용자가 확인했다.

## P1. 워크플로우 — Coding Assistant가 한 요청을 처리하는 흐름
- **입력:** brief
- **할 일**
  - 한 요청의 흐름을 **5단계 이하**로 적는다(3일차 4강). 평가 기준을 그대로 따르면 기본형은 다음과 같다.
    1. **요구사항 정리:** 요구·범위·완료 조건
    2. **계획 + AI 리뷰:** 수정 대상·순서·테스트 방법을 쓰고, 리뷰를 반영한 뒤 승인받는다
    3. **구현:** 승인된 범위 안에서만 코드를 바꾼다
    4. **검증:** 테스트와 lint, 루브릭 채점
    5. **학습:** 경험을 기록하고 개선안을 만든다
  - 각 단계에 **판단 / 생성 / 규칙 / 조회** 꼬리표를 붙인다. 판단과 생성이 함께 있는 구간이 에이전트 후보다(3일차 5강). 결정적 검사(테스트·lint·형식 검증)는 코드로 처리한다.
  - 사람 승인(HITL)이 필요한 지점을 표시한다: 계획 승인, 범위 변경, 개선안 채택.
  - 예외 흐름을 적는다: 리뷰 REVISE, 테스트 실패, 범위 밖 수정 시도, 판정기 오류(fail-closed).
- **산출물:** `design/01-workflow.md`
- **게이트:** 단계 ≤ 5, 단계마다 꼬리표와 입출력이 있고, HITL 지점과 예외 흐름이 표시됐다.

## P2. 아키텍처 — 싱글로 시작하고, 확장 지점을 고른다
- **입력:** workflow, `reference/dcode.md` §1~§2
- **할 일**
  - 각 단계를 **CODE / RULE / API / MODEL / AGENT**로 분류한다. 모든 단계를 에이전트로 만들지 않는다(3일차 교재 Ch.1).
  - **시작은 싱글 에이전트(dcode 메인) + 스킬**이다. 서브에이전트는 컨텍스트 경계가 있을 때만 쓴다(3일차 1~3강). 리뷰어는 "다른 관점의 독립 컨텍스트"가 필요하므로 서브에이전트가 정당한 대표 사례다.
  - **dcode 확장 지점을 고른다.** 기능마다 아래 중 하나를 택하고 이유를 `decisions.md`에 남긴다.

    | 메커니즘 | 쓰기 좋은 곳 | 주의 |
    |---|---|---|
    | 스킬 `.deepagents/skills/<n>/SKILL.md` | 계획 작성 절차, 개선안 작성, trace 조회 리포트 | 스레드당 1회 인덱스 로드, `allowed-tools`는 강제되지 않음 |
    | 서브에이전트 `.deepagents/agents/<n>/AGENTS.md` | 계획 리뷰어(독립 컨텍스트, `model:` 지정) | frontmatter로 tools·middleware 설정 불가 |
    | 훅 `hooks.json` (PreToolUse 등 12종) | 계획 승인 게이트, 범위 검사, 메모리 주입(`UserPromptSubmit` additionalContext) | 프로젝트 훅은 trust 필요, 헤드리스는 `--trust-project-hooks` |
    | 미들웨어 (`create_cli_agent`의 `agent_middleware`) | 이벤트 로거, 경험 기록, 개선안 생성, 지표 집계 | 서버 프로세스에서 실행되므로 `Path.cwd()` 금지(`make lint`가 잡음). 단위 테스트를 만들 수 있다 |
    | `/goal`·`--rubric` | 완료 조건을 채점에 연결 | 헤드리스에는 goal 리뷰 UI가 없음 |

  - **하네스 6책임으로 빈칸을 확인한다(Day06).** 지침, 도구, 실행 제어, 상태, 검증, 기록마다 "dcode가 이미 하는 것 / 내가 추가할 것"을 표로 만든다.
  - **신뢰기반을 분리한다.** 평가기, 정답, 테스트, 권한 정책은 개선 주체(에이전트)가 고칠 수 없는 위치에 둔다(R15).
  - 상태 키, 종료 조건(완료·보류·사람 전환·실패)을 적는다.
- **산출물:** `design/02-architecture.md`, `design/decisions.md`
- **게이트:** 노드 유형표, 확장 지점 선택 근거, 6책임 표, 종료 조건이 있다.

## P3. 지식·메모리 — 잘 저장하고, 필요한 것만 꺼낸다
- **입력:** architecture, `reference/dcode.md` §2.4
- **할 일**
  - **저장 → 검색 → 활용** 세 단계를 각각 설계한다(2일차 1강, 3일차 1강).
  - **규칙과 경험을 나눈다.** 규칙은 `AGENTS.md`(항상 주입)에, 경험은 구조화된 저장소(예: `experiences.jsonl`: id, task, 실패 원인, 해결책, 태그, 날짜, 출처 run_id)에 둔다.
  - **검색:** dcode에는 검색이 없다. 요청 텍스트로 경험을 검색(키워드·BM25부터, 임베딩은 선택)해서 top-k만 주입한다. 계층 폴더 + `index.md` 방식도 후보다(2일차 2강).
  - **주입 위치:** 프롬프트 캐시를 깨지 않도록 시스템 프롬프트가 아니라 **메시지로** 주입한다(고정 내용은 앞, 변하는 값은 뒤, 3일차 1강 / Day07 과제 1). 주입한 메모리 ID를 계획 문서와 로그에 남긴다.
  - **한계를 설계에 반영한다.**
    - 메모리는 스레드당 1회만 로드된다. "다음 작업에 반영"은 새 스레드로 시연한다.
    - `auto_save=true`면 모델이 AGENTS.md를 직접 고쳐서 "검증 후 채택"을 우회한다. `[memory].auto_save=false`와 훅으로 직접 편집을 막는 방안을 검토한다.
    - 메모리 파일은 프롬프트 인젝션 경로가 될 수 있다. 채택 전 검증이 보안 장치이기도 하다.
  - 멀티턴 전략을 정한다. 압축할 때는 원본으로 가는 경로를 남긴다(2일차 2·3강).
- **산출물:** `design/03-knowledge.md`
- **게이트:** 규칙·경험 저장 형식, 검색 방식, 주입 위치, 스레드 로드 한계 대응이 정해졌다.

## P4. 도구·스킬 — 도구는 적게, 스킬은 단계적으로
- **입력:** architecture, knowledge
- **할 일 — 제품 스킬·서브에이전트 (dcode 쪽)**
  - `plan-first` 스킬: 계획 템플릿을 채운다. 필수 항목은 요구사항, 범위(In/Out), 완료 조건, 수정 대상 파일, 작업 순서, 테스트 명령, 참조 메모리 ID, 리뷰 이력이다. 필수 항목은 형식 검증 스크립트로 확인한다(R3).
  - `plan-reviewer` 서브에이전트: 읽기 전용으로 체크리스트를 판정하고 APPROVE/REVISE와 의견을 낸다. REVISE면 계획을 다음 버전으로 고친 뒤 다시 리뷰한다. 필요하면 Planner·Architect·Critic 역할로 나눈다(R4, Day06 gjc ralplan).
  - `improve` 스킬과 `trace-report` 스킬: 개선안 작성과 실패 지점 조회를 맡는다.
  - 판단(승인 가능 여부, 범위 이탈, 근거 충분성)은 **Closed Question**(참/거짓, 선택, 점수)으로 묻고, 임계값은 코드에 둔다. 판정기가 실패하면 통과가 아니라 차단이다(fail-closed, R6·R28, Jev 사례).
- **할 일 — 도구 설계 공통**
  - 도구마다 이름, description(언제 쓰는지), 타입 있는 인자를 갖춘다. 비슷한 도구는 합친다(4일차 1·6강).
  - 반환에는 `status`, 출처, 시점을 넣는다. 빈 결과·오류·연결 실패를 구분한다. 모델이 고칠 수 있는 오류만 전달한다.
  - 나만 쓰는 도구는 스킬 스크립트로 두고, 공유·원격이 필요한 것만 MCP로 만든다(4일차 6강).
  - 순서가 중요한 흐름은 **도구가 현재 단계를 확인하고, 어긋나면 거절하게** 만든다(3일차 5강).
- **할 일 — 스킬 작성 기준** (`skill-authoring` 스킬)
  - description은 What + When(+ 아닌 경우)을 짧게 쓴다. 본문은 5천 토큰 이내로 쓰고 XML로 구역을 나눈다. 상세는 `references/`, 실행은 `scripts/`에 둔다(4일차 2·5강).
- **산출물:** `design/04-tools-skills.md`, 스킬·서브에이전트 파일
- **게이트:** 도구 명세표와 스킬·서브에이전트 목록이 있고, skill-authoring 점검을 통과했다.

## P5. 구현·기준선 — 돌아가는 가장 단순한 버전
- **입력:** P1~P4 산출물
- **할 일**
  - **빌드·실행 경로를 먼저 확보한다**(`reference/dcode.md` §1.2).
    - 설치: `cd libs/code && make bootstrap`(또는 `uv sync --group test`)
    - 실행: `uv run deepagents-code`
    - 검사: `make lint` / `make test` / `make format`
    - 헤드리스: `dcode -n "..."`, 셸은 `-S "pytest,uv,git"`로 허용, 프로젝트 훅·MCP는 `--trust-project-hooks` / `--trust-project-mcp`
    - OpenRouter: `langchain-openrouter`와 `OPENROUTER_API_KEY`. 소스 빌드 시 extra 설치 명령은 **직접 검증**한다.
  - 가장 단순한 구현부터 만든다: 계획 스킬 + 리뷰어 + 승인 게이트 → 로거 → 메모리 → 개선 루프 순서다.
  - 새 코드는 처음부터 `ruff`(ALL, google docstring, 상대 import 금지)를 통과시킨다. 평가 항목 1이 10점이다.
  - 기록이 남게 한다. 세션이 끝나도 로그와 메모리가 남아야 한다.
  - **기준선을 측정한다:** 고정 작업 몇 개로 성공률, 소요 시간, LLM·도구 호출 수, 재시도 수, 토큰을 잰다.
  - 유료 실행 직전에는 규모(작업 수 × 반복 × 예상 호출 수)를 한 줄로 고지한다(R29).
- **산출물:** 동작하는 코드, `design/05-build.md`(빌드·실행 명령, 기준선 수치)
- **게이트:** README의 명령 그대로 새 환경에서 빌드·실행되고, `make lint`가 통과하고, 기준선이 기록됐다.

## P6. 하네스·관측 — 승인 게이트와 모니터링
- **입력:** 동작하는 코드
- **할 일 — 실행 제어** (하네스 = 모델을 뺀 나머지 전부, 3일차 4강)
  - **계획 승인 게이트:** 코드 변경 도구(Write/Edit/Bash) 앞에서 계획 파일의 `status: approved`를 확인하고, 없으면 거부 사유를 모델에 돌려준다. 수정 경로가 계획의 "수정 대상" 밖이면 거부하고 "범위 변경, 계획 갱신과 재리뷰 필요"를 알린다(평가 2-4).
  - 게이트가 서브에이전트 경로에도 걸리는지 검증한다. 부모 미들웨어는 서브에이전트 도구 호출을 못 볼 수 있다(Day08 `02_action_guard`).
  - 게이트를 우회하면 그 사실을 기록한다. 판정기 오류는 차단으로 처리한다.
  - 로컬 셸에는 경계가 없다. YOLO나 `-S all`로 시연하지 않는다.
  - 예산(턴·시간·재시도)과 종료 상태를 정한다. 헤드리스는 `--max-turns`, `--timeout`(초과 시 exit 124)을 쓴다.
- **할 일 — 관측** (평가 4-1~4-4, R9~R12)
  - 요청 ID별 **append-only JSONL 이벤트 로그**를 남긴다. 필드는 `run_id`, `thread_id`, `turn_index`, `phase`(plan/review/code/test/result/memory/improve), `event`, `call_id`, 부모 ID, 시각, 소요, 상태, 오류, 버전 라벨이다.
  - 이벤트 종류: `llm_call`(모델·토큰·지연·오류), `tool_call`(이름·인자 요약·상태·소요), `memory_retrieve`/`memory_write`, `improve_proposal`/`improve_eval`/`improve_adopt`.
  - 실행이 끝나면 `summary.json`을 쓴다: 총 소요, LLM 호출 수, 도구 호출 수, 재시도 수, 루브릭 반복 수, 토큰. **모르는 값은 0이 아니라 `null`**로 둔다. dcode에 이미 있는 `model_attempt` 이벤트와 `CostTrackingMiddleware`를 원천으로 쓴다.
  - 조회 도구 `trace_query`(예: `--run <id> --errors --phase test`)로 첫 실패 이벤트와 직전 맥락을 출력한다.
  - 키와 비밀은 로그에 남기지 않고 마스킹한다. LangSmith는 보조로만 쓰고, 키 없이 동작하는 로컬 로그를 1차 증빙으로 삼는다.
- **산출물:** `design/06-harness.md`
- **게이트:** 승인 게이트와 범위 검사가 실제로 차단하고, 한 요청의 5단계가 로그에 시간순으로 남고, 조회 도구가 실패 지점을 찾는다.

## P7. 평가 — 개선은 증명해야 개선이다
- **입력:** 게이트와 관측까지 갖춘 시스템, `reference/eval-rsi-rules.md` §1
- **할 일**
  - **평가셋:** 고정 작업 N개를 만든다. 정상 요청, 범위 밖 수정 유도, 테스트 방법이 빠진 요청, 과거 실패와 비슷한 요청, 도구 실패 상황을 포함한다. 시나리오는 실행 **전에** 정하고, 바꾸면 새 데이터 버전으로 본다(Day05 01~02).
  - **채점 순서:** Code(lint·test·형식 검사) → 의미 판정(LLM Judge 또는 디시전 모델) → 사람(불일치)이다. 정책·안전 실패를 다른 점수의 평균으로 상쇄하지 않는다(R14).
  - **완료는 증거로 판정한다.** 에이전트의 "완료했다"는 제안일 뿐이고, 테스트 결과와 실제 파일 상태로 판정한다(R13).
  - **실패 분석:** 관찰 사실(`fact`), 원인 가설(`hypothesis`), 대안 가설(`alternative`), 근거 ID(`evidence_ids`)를 나눠 쓴다. 근거 ID가 없으면 개선 실험을 시작하지 않는다(R7).
  - Judge를 쓰면 사람 라벨로 false pass와 false reject를 먼저 잰다(R17).
  - mock·scripted 결과는 "계약 검증"이지 개선율이 아니다(R16).
  - 근거 수준을 라벨로 단다: 실행 경로에서 확인 / 코드 정의만 / 문서만 / 추정(R8, Day06).
- **산출물:** `design/07-eval.md`, `eval/` 평가셋과 실행 스크립트
- **게이트:** 평가가 명령 한 줄로 재실행되고, 기준선 결과표(건수·통과·시간·호출·재시도·실패 종류)가 채워졌다.

## P8. 자기개선·최적화 — 손잡이 하나, 같은 조건, 미리 정한 판정
- **입력:** 평가 결과, `reference/eval-rsi-rules.md` §2·§6-D
- **할 일 — 자기개선 루프** (평가 3-3·3-4, Day05_new 노트북 06)
  1. **여는 손잡이를 하나로 정한다.** 예: 메모리 규칙 항목, 스킬 문서 하나, 도구 정책 JSON. 모델, 평가기, 테스트, 예산은 고정한다(R18).
  2. **개선안 생성:** 실패 신호(도구 오류, 테스트 실패, 루브릭 `needs_revision`/`max_iterations_reached`, 리뷰 REVISE 반복)를 모아 개선안을 **선언형 형식**으로 받는다. 스키마로 검증하고 거부 사유를 기록한다. 평가 기준 변경, 실패 삭제, 예산 증가 키는 스키마에서 금지한다(R19).
  3. **오염 검사:** 개선기 입력에 정답, 임계값, holdout 흔적이 있으면 호출 전에 멈춘다(R20).
  4. **비교:** 현재안과 후보를 같은 평가셋, 같은 조건에서 돌린다. 점수식은 미리 고정한다(예: 통과 수, 또는 `recall − 2×false_block`)(R21).
  5. **판정 순서(미리 고정):** NOT_DETERMINABLE(완료율 90% 미만 또는 개선 여지 0) → HOLD(새 실패 유형이나 기존 통과 회귀) → ADOPT(실패 감소) → 그 밖은 HOLD(R22).
  6. **채택:** ADOPT만 메모리·스킬에 반영하고, 버전 라벨(r0, r1…)과 근거 라운드 파일을 기록한다. **다음 작업(새 스레드)** 에서 쓰였는지 로그로 보인다(R25). 기존 기능 회귀 테스트는 매 라운드 돌린다(R23).
  7. **holdout은 마지막에 한 번만 연다.** 결과를 보고 다시 고치면 새 실험이다(R24). 결과를 본 뒤 임계값이나 반복 수를 바꾸지 않는다(R26).
  - 구현 팁: dcode `-a/--agent NAME`은 에이전트별로 독립 메모리를 쓴다. baseline과 candidate를 다른 에이전트 이름으로 돌리면 비교가 쉽다.
- **할 일 — 성능 최적화** (`optimize-agent` 스킬, 3일차 6강)
  - 동작은 그대로 두고, 변경은 토글로 만들고, before/after 근거를 남긴다.
- **산출물:** `design/08-optimization.md`, `improve/round-<n>.json`(append-only)
- **게이트:** 개선 라운드가 최소 1회 기록됐고(ADOPT든 HOLD든), 판정 근거와 회귀 테스트 결과가 있다.

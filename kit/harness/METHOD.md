# 회사 코딩 에이전트 구축 방법론

> 무엇을 어떤 순서로 만들고, 단계마다 무엇을 고민하고, 어떻게 진행하고, 어떻게 검증하고, 언제 끝났다고 보는지를 정리한 문서다.
> 특정 프레임워크나 기반 에이전트를 전제하지 않는다.

## 1. 전체 그림

```
S0 범위·기반 ─┬─► S1 시험지·채점기 ───────────┐
              │                               ▼
              └─► S2 뼈대·관측 ─────────► [기준선 측정] ─┬─► S3 컨텍스트·메모리 ─┐
                                                        ├─► S4 도구·스킬 ───────┼─► S6 자기개선 ─┐
                                                        └─► S5 실행 제어 ───────┤                ├─► S8 배포·운영
                                                                                └─► S7 최적화 ───┘
```

| 단계 | 시작하려면 | 같이 진행할 수 있는 것 | 끝났다는 기준 (한 줄) |
|---|---|---|---|
| S0 범위·기반 결정 | 없음 | 없음 | 대상 작업·기반·모델·완료 정의가 승인됐다 |
| S1 시험지·채점기 | S0 | S2 | 시나리오 평가셋(개발용/최종 확인용)과 검증된 채점기가 한 줄 명령으로 돈다 |
| S2 뼈대·관측·기준선 | S0 (기준선 측정에는 S1 필요) | S1 | 한 요청이 끝까지 돌고, 전부 기록되고, 기준선 수치가 있다 |
| S3 컨텍스트·메모리 | S2 | S4, S5 | 지침 계층과 탐색 격리가 적용됐고 평가 회귀가 없다 |
| S4 도구·스킬 | S2 | S3, S5 | 도구·스킬이 각자 테스트를 통과했고 평가 회귀가 없다 |
| S5 실행 제어 | S2 | S3, S4 | 반드시 지킬 규칙이 전부 강제 장치로 막히고 정책 위반이 0건이다 |
| S6 자기개선 | S1, S2, S3, S5 | S7 | 기억 → 활용 → 개선안 → 검증 → 채택이 한 바퀴 돌았다 |
| S7 최적화 | S3, S4, S5 | S6 | 동작은 그대로이고 목표 지연·비용에 도달했다 |
| S8 배포·운영 | S6, S7 | 없음 | 최종 확인용 평가를 통과했고 운영 루프 담당자가 있다 |

### 왜 이 순서인가
- **평가(S1)와 기록(S2)이 먼저다.** 재지 못하면 무엇을 고쳐도 좋아졌는지 알 수 없다.
- **S3·S4·S5는 서로 다른 손잡이라 동시에 만들 수 있다.** 다만 훅이 고치는 방법으로 스킬을 가리키므로(검사는 훅, 해결은 스킬) S5의 안내 문구는 S4 결과에 맞춘다.
- **S6은 네 가지가 있어야 안전하다.** 채점기(S1), 기록(S2), 메모리 저장소(S3), 그리고 개선안이 테스트·채점기·권한을 건드리지 못하게 막는 게이트(S5).
- **S7은 동작이 굳은 뒤에 한다.** "동작이 바뀌면 안 된다"를 확인하려면 비교할 기준 동작이 고정돼 있어야 한다.

### 병렬 작업 규칙
- **만드는 것은 병렬, 반영하는 것은 하나씩.** 변경을 합칠 때마다 평가를 돌리고, 한 번에 한 가지만 바꾼다. 두 변경을 같이 넣으면 어느 쪽이 결과를 바꿨는지 알 수 없다.
- 사람이 2~3명이면 이렇게 나눈다: 한 명이 S1(평가), 한 명이 S2(뼈대)를 맡고, 기준선이 나오면 S3·S4·S5를 한 명씩 맡는다.
- 단계 안에서도 같은 규칙이다. 독립적인 조사·작성은 동시에 하고, 결과를 합칠 때는 순서대로 검증한다.

### 모든 단계에 공통인 규칙
1. **완료는 증거로 판정한다.** 에이전트의 "완료했다"는 자기 보고다. 테스트 결과, 실제 파일 상태, 기록으로 판정한다.
2. **결정에는 근거를 남긴다.** `design/decisions.md`에 문제 → 선택 → 근거 → 되돌리는 방법을 한 줄씩 적는다.
3. **평가 기준은 결과를 보기 전에 고정한다.** 결과를 본 뒤 기준·임계값·반복 수를 바꾸지 않는다. 최종 확인용 데이터는 수정에 쓰지 않는다.
4. **실패를 숨기지 않는다.** 테스트를 지우거나 건너뛰지 않고, 실패한 실행을 표에서 빼지 않고, 모르는 값은 0이 아니라 빈칸으로 둔다.
5. **싱글 에이전트로 시작한다.** 쪼개는 이유는 컨텍스트 경계나 측정된 실패여야 한다.

## S0. 범위·기반 결정

**목적:** 무엇을 만들고 무엇을 "완료"라고 부를지 정한다.

**고민할 것**
1. **대상 작업:** 누가, 어떤 저장소·언어에서, 어떤 작업(버그 수정, 기능 추가, 테스트 작성, 리뷰)을 맡기나. 첫 대상은 하나만 고른다. "활용"이 아니라 "완전히 맡길 수 있는" 가장 작은 조각이 기준이다.
2. **기반:** 기존 코딩 에이전트를 포크·확장할지, 에이전트 SDK 위에 조립할지, 루프를 직접 짤지. 판단 기준은 소스를 고칠 수 있는가, 끼어들 지점(훅·미들웨어·스킬·서브에이전트)이 있는가, 사내 모델을 붙일 수 있는가, 라이선스다. 처음부터 짜지 말고 포크해서 어긋나는 점만 바꾸는 쪽을 권한다. 기반은 나중에 바꿔도 된다.
3. **모델:** 외부 API를 쓸 수 있는가. 코드가 회사 밖으로 나가도 되는지가 먼저다(판단 축: 비용·보안·커스터마이징). 사내 서빙이면 어떤 모델을 어떤 장비에 올릴 수 있는지(용량 = 가중치 + KV 캐시)를 확인한다. 계획·코드·판단·리뷰에 같은 모델을 쓸 필요는 없다.
4. **완료 정의와 성공 지표:** 성공률(숨겨 둔 테스트 통과), 정책 위반 0건, 응답 지연, 건당 비용. 목표값을 숫자로 적는다.
5. **하면 안 되는 일:** 배포, 운영 데이터 변경, 강제 푸시, 시크릿 접근처럼 에이전트에게 절대 맡기지 않을 행동.

**진행**
- `project-kickoff` 스킬로 인터뷰한다. 한 번에 하나씩 묻고, 모르는 항목은 지어내지 않는다. "잘 되면 완료" 같은 기준은 실행 결과로 참/거짓을 가릴 수 있는 문장이 될 때까지 다시 묻는다.
- 기반 후보는 설치 전에 구성(스킬·에이전트·훅·MCP)과 위험을 먼저 분석하고, 망가져도 되는 환경에서 돌려 본다.

**검증**
- 완료 기준 문장마다 "이걸 어떤 명령이나 기록으로 확인하나"를 옆에 적을 수 있다.
- 실제 사용할 개발자 2~3명이 대상 작업과 금지 행동을 읽고 동의했다.

**완료 기준**
- [ ] 대상 작업 하나, 기반, 모델, 성공 지표(목표값), 금지 행동이 `design/00-brief.md`에 있다
- [ ] 기반·모델 선택 근거가 `design/decisions.md`에 있다
- [ ] 사용자 대표가 브리프를 확인했다

**흔한 함정:** 범위를 "모든 개발 작업"으로 잡기, 모델부터 고르기, 완료 기준을 "잘 동작하면"으로 두기.

## S1. 시험지와 채점기

**목적:** "좋아졌다"를 판정할 기준을 만든다. S2와 동시에 진행한다.

**고민할 것**
1. **무엇이 대표 작업인가.** 실제 과거 이슈·PR, 사용할 개발자 인터뷰에서 뽑는다. LLM에게만 맡기면 50~60점짜리 일반 문제가 나온다.
2. **무엇이 성공인가.** 최종 답이 같아도 과정이 다르면 같은 성공이 아니다. 세 축으로 나눈다.
   - 결과(Outcome): 숨겨 둔 테스트가 통과하는가
   - 과정(Trajectory): 계획 승인 전에 수정하지 않았는가, 범위 안 파일만 고쳤는가, 테스트를 실제로 돌렸는가
   - 응답(Final Response): 변경 요약이 실제 변경과 일치하는가
3. **무엇을 코드로 채점하고 무엇을 모델로 채점하나.** 명확한 사실은 코드, 의미 판단만 모델 채점(Judge), 이견은 사람이 본다.
4. **데이터셋을 무엇으로 묶나.** 기능이 아니라 고치려는 문제점으로 묶는다(예: "도구 호출이 너무 잦다").

**진행**
- `golden-dataset` 스킬로 5건부터 시작해 늘린다.
- 시나리오 하나의 구성: 저장소 스냅샷(커밋) + 요청문 + 기대 상태(통과해야 할 테스트) + 하면 안 되는 것(범위 밖 수정, 테스트 삭제·건너뛰기, 시크릿 접근) + 순서 규칙(계획 승인 → 수정 → 테스트) + 출처·검수자.
- 정상 사례만 넣지 않는다. 정보가 부족해 되물어야 하는 요청, 거절해야 하는 요청, 도구가 실패하는 상황, 한 조건만 다른 경계 사례 쌍을 넣는다.
- 기대 상태와 숨긴 테스트는 에이전트가 볼 수 없는 곳에 둔다.
- 사례 묶음 단위로 개발용과 최종 확인용을 나누고 버전을 고정한다.
- `agent-eval` 스킬로 채점기를 만든다. 정책 위반(금지 행동)은 다른 점수와 평균 내지 않는 필수 관문이다. 판정은 통과 / 실패 / 근거 부족 / 채점기 오류 / 환경 오류로 나눈다.
- 모델 채점을 쓴다면 "0~1점으로 매겨라"만 쓰지 않는다. 점수가 0.7 근처로 쏠린다. 등급마다 관찰 가능한 기준을 적고, 같은 조건으로 여러 번 돌려 흔들림을 보고, 사람 판정과 비교한다.

**검증**
- 채점기를 일부러 만든 반례로 시험한다: 순서만 다른 정상 실행 → 통과, 승인 없이 수정한 실행 → 실패, 기록이 지워진 실행 → 근거 부족, 빈 정답 → 채점기 오류.
- 사람이 만든 정답 변경으로 통과가 나오고, 아무것도 안 바꾼 상태로 실패가 나온다.
- 명령 한 줄로 평가 전체가 다시 돈다.

**완료 기준**
- [ ] 개발용 시나리오가 5건 이상이고 최종 확인용이 따로 있다 (목표 건수는 S0 지표에 맞춰 적는다)
- [ ] 채점기가 반례 시험을 통과했다
- [ ] 평가가 명령 한 줄로 재실행된다
- [ ] 승인 기준(무엇이 몇 이상이면 채택)이 결과를 보기 전에 적혀 있다

**흔한 함정:** 질문·답 형식으로 만들기, LLM이 쓴 정답을 검수 없이 쓰기, 에이전트가 정답 테스트를 읽을 수 있게 두기, 결과를 보고 최종 확인용 데이터로 다시 고치기.

## S2. 뼈대·관측·기준선

**목적:** 가장 단순한 버전이 한 요청을 끝까지 처리하게 하고, 모든 실행을 기록하고, 출발점 수치를 잰다.

**고민할 것**
1. **요청 한 건의 흐름.** 5단계 이하로 적는다. 기본형: 요구 확인 → 계획·리뷰·승인 → 구현 → 검증 → 보고·학습.
2. **단계마다 누가 하나.** 판단·생성·규칙·조회 꼬리표를 붙인다. 테스트 실행, 린트, 형식 검사 같은 규칙은 코드가 한다. 모든 단계를 모델에게 맡기지 않는다.
3. **쪼갤 것인가.** 싱글로 시작한다. 서브에이전트는 컨텍스트 경계가 분명한 곳(코드 탐색, 독립 리뷰어)에만 둔다.
4. **어디에, 무엇을 기록하나.** 사내 코드가 들어가므로 데이터 제어권(셀프호스팅, 내보내기)을 본다. 요청마다 전체 흐름(계획, 리뷰, 코드 변경, 테스트, 결과)이 단계 표시와 함께 남아야 하고, 모델 호출·도구 실행·메모리 활용·자기개선의 결과와 오류가 이벤트로 남아야 한다.
5. **어떤 지표를 모으나.** 실행 시간, 호출 횟수, 재시도 횟수, 토큰. 모르는 값은 0이 아니라 빈값으로 둔다.
6. **코드 품질 기준.** 린터·포매터·docstring 규칙을 처음에 정해 설정 파일로 둔다. 나중에 한꺼번에 맞추려면 비싸다.
7. **종료 조건과 예산.** 최대 턴·시간·재시도, 종료 상태(완료, 보류, 사람에게 넘김, 실패).

**진행**
- 기반을 거의 그대로 띄워 작은 작업 하나를 끝까지 돌린다.
- 요청 단위, 단계 단위, 대화 단위로 기록을 남긴다. 처음부터 남긴다. 요청이 끝나면 요약 지표도 남긴다.
- 조회 도구를 만든다. 요청 ID를 주면 첫 실패 이벤트와 직전 맥락을 보여준다.
- 린트·포맷 검사 명령을 정하고 새 코드가 통과하게 한다.
- 뒤 단계(S5 게이트, S6 메모리·개선)를 만들 때마다 그 이벤트가 기록에 남는지 다시 확인한다.
- S1의 개발용 평가셋으로 기준선을 잰다. 같은 시나리오를 여러 번 돌려 흔들림도 본다.

**검증**
- 기록만 보고 사람이 "최초 실패 지점"을 찾을 수 있다. 일부러 실패시킨 도구 호출이 오류로 기록되는지 본다.
- 깨끗한 환경에서 README 명령 그대로 실행된다.
- 린트·포맷 검사가 오류 0건이다.

**완료 기준**
- [ ] 요청 흐름과 단계별 담당(코드/모델)이 `design/02-baseline.md`에 있다
- [ ] 한 요청의 전체 흐름이 단계 표시와 함께 기록에 시간순으로 남고, 요약 지표(실행 시간, 호출 횟수, 재시도 횟수)가 나온다
- [ ] 조회 도구가 실패한 요청의 첫 실패 지점을 보여준다
- [ ] 린트·포맷·docstring 검사 명령이 있고 통과한다
- [ ] 기준선 표가 채워졌다: 성공률, 매번 통과한 비율, 정책 위반 수, 첫 응답 시간·전체 지연, 호출 수, 토큰, 실패 유형 분류

**흔한 함정:** 처음부터 멀티 에이전트로 설계하기, 기록 없이 개선부터 하기, 한 번 돌린 결과를 기준선으로 쓰기.

---

## S3. 컨텍스트·지식·메모리

**목적:** 에이전트가 우리 코드베이스의 규칙을 알고, 필요한 것만 읽고, 기억을 작게 유지하게 한다. S4·S5와 동시에 진행한다.

**고민할 것**
1. **우리 규칙을 어디에 적나.** 지침은 계층으로 나눈다: 조직 공통 / 프로젝트(저장소에 커밋) / 특정 폴더·파일에만 적용되는 규칙(그 파일을 다룰 때만 로드) / 개인(커밋 제외). 항상 로드되는 지침은 짧게 둔다(200줄 이하 권장).
2. **기존 노하우를 누가 옮기나.** 위키에 있는 팀 규칙을 에이전트가 읽는 파일로 옮기는 담당자가 필요하다.
3. **코드 탐색이 컨텍스트를 채우지 않게 하려면.** 탐색은 서브에이전트나 작은 모델에 맡기고 메인은 결론만 받는다. 원본은 파일에 두고 컨텍스트에는 최소만 넣는다.
4. **프롬프트 배치.** 고정 내용은 앞, 바뀌는 값(날짜, 검색 결과)은 뒤. 대화는 뒤에 붙이기만 한다. 중간을 압축하면 캐시가 깨진다.
5. **무엇을 기억하나.** 규칙(항상 지킬 것)과 경험(과거 작업·실패·해결)을 나눈다. 매번 주입하는 양은 작게, 나머지는 색인으로만 가리킨다.
6. **모델이 고르지 않아도 되는 판단.** 요청·파일 종류로 필요한 스킬이 정해지면 코드로 강제 로드한다. 분류·예/아니오는 모델 호출 앞단에서 코드나 판단 전용 모델로 끝낸다.

**진행**
- 지침 계층 파일을 만들고 양식(XML 구역)을 통일한다.
- 탐색 서브에이전트의 입출력 계약을 정한다: 입력은 목표와 허용 도구, 출력은 상태·사실·근거 위치·불확실한 점.
- 긴 대화 압축 방식을 정한다. 요약에는 원본으로 가는 경로를 남긴다.

**검증**
- 평가셋을 다시 돌려 "규칙을 몰라서 틀린" 실패 유형이 줄었는지 본다.
- 세션 시작 때 로드되는 양, 작업 중 컨텍스트 사용률, 캐시 적중률을 잰다.
- 새 세션에서 프로젝트 규칙을 지키는지 확인한다.

**완료 기준**
- [ ] 지침 계층이 적용됐고 담당자가 있다
- [ ] 탐색 격리와 프롬프트 배치가 구현됐다
- [ ] 평가 회귀가 없고 컨텍스트 지표가 `design/03-context.md`에 기록됐다

**흔한 함정:** 한 파일에 전부 적기(읽고도 잊는다), 지침에 적었으니 지켜질 거라 믿기(지침은 부탁이다. 강제는 S5), 탐색 결과를 통째로 메인에 넣기.

---

## S4. 도구·스킬

**목적:** 에이전트가 쓰는 도구를 적고 명확하게 만들고, 반복 절차를 스킬로 묶는다.

**고민할 것**
1. **최소 도구 세트는.** 읽기·검색·편집·셸·테스트 실행에서 시작한다. 비슷한 도구는 합친다. API를 1:1로 감싸지 않는다.
2. **도구가 돌려주는 것.** 상태, 출처, 요약을 돌려주고 원문을 통째로 넣지 않는다. 빈 결과·오류·연결 실패를 구분한다. 모델이 고칠 수 있는 오류만 전달한다.
3. **사내 시스템 연결.** 이슈 트래커나 코드 검색 같은 공유·원격 자원만 MCP로 만들고, 로컬에서만 쓰는 것은 스크립트로 둔다.
4. **무엇을 스킬로 묶나.** 같은 절차를 세 번째 붙여넣게 되면 스킬로 만든다. 예: 테스트 작성 규칙, 리뷰 절차, PR 작성.
5. **누가 스킬을 부르나.** 부작용이 있거나 순서가 중요한 절차는 모델이 스스로 부르지 못하게 하고 진입 절차나 사용자가 부른다.
6. **호출 수 줄이기.** 연관된 여러 호출은 스크립트 하나로 묶는다(코드 모드).

**진행**
- 도구 명세표를 쓴다: 이름, 언제 쓰는지, 타입 있는 인자, 반환, 오류 처리.
- `skill-authoring` 스킬로 스킬을 쓴다: 설명은 무엇·언제(아닌 경우 포함)를 짧게, 본문은 XML 구역, 상세는 별도 파일.
- `tool-design-review` 스킬로 점검한다.

**검증**
- 세 층으로 나눠 시험한다: 모델 없는 도구 단위 테스트 → 모델이 도구를 제대로 고르고 인자를 맞게 넣는지 → 전체 평가.
- 스킬은 불려야 할 요청과 불리면 안 되는 요청으로 설명문을 시험한다.
- 실제로 노출되는 도구 수와 컨텍스트 점유율을 확인한다.

**완료 기준**
- [ ] 도구마다 명세와 단위 테스트가 있다
- [ ] 스킬마다 호출 시험 결과가 있다
- [ ] 평가 회귀가 없고 결과가 `design/04-tools-skills.md`에 기록됐다

**흔한 함정:** 도구를 늘려서 문제 풀기, 실패를 빈 결과로 숨기기, 설명문을 길게 쓰기.

---

## S5. 실행 제어

**목적:** 반드시 지켜져야 하는 규칙을 "부탁"이 아니라 "강제"로 만든다.

**고민할 것**
1. **반드시 지켜져야 하는 것은 무엇인가.** 목록으로 뽑는다. 코딩 에이전트의 기본 목록:
   - 요구사항·범위·완료 조건 없이는 시작하지 않는다
   - 계획(수정 대상·순서·테스트 방법) → AI 리뷰 → 승인 후에만 코드를 바꾼다
   - 범위가 바뀌면 계획으로 돌아간다
   - 코드를 고치면 관련 테스트와 린트·포맷 검사를 돌린다
   - S0의 금지 행동은 실행 전에 막는다
2. **규칙마다 어디에 두나.** 지침(부탁), 스킬(위임), 훅·권한 설정(강제) 중에서 고른다. 지침과 스킬은 모델이 읽고 따르는 것이라 보장이 아니다.
3. **누가 승인하나.** 어떤 단계에서 사람이 승인하고 어떤 단계는 자동으로 넘기나. 돈·민감정보·외부 쓰기는 사람이 본다.
4. **판정을 무엇으로 하나.** 결정적 코드가 기본이다. 실행할 테스트도 이름·폴더 규칙으로 코드가 고른다. 맥락 판단이 꼭 필요할 때만 작은 모델에 예/아니오를 묻는다.
5. **조용히 통과하는 경로는 없는가.** 검사 스크립트가 오류나 시간 초과로 죽으면 기본적으로 통과된다. 셸로 파일을 쓰면 편집 검사를 우회한다.
6. **서브에이전트에도 적용되나.** 부모에 건 검사가 서브에이전트의 도구 호출을 보는지 확인한다.

**진행**
- `hook-design` 스킬로 규칙마다 둘 곳을 정하고 배치표를 쓴다.
- `plan-review` 절차를 제품에 넣는다: 계획 양식, 독립 컨텍스트의 리뷰어, 승인 게이트. 계획·리뷰는 별도 서브에이전트로 둬서 컨텍스트를 통제한다.
- 실행 전 검사는 막고, 실행 후 검사는 고치게 하고, 끝내기 전 검사는 확인한다. 검사 메시지에는 고치는 방법(어느 스킬)을 적는다.
- 판정기가 실패하면 통과가 아니라 차단으로 처리한다. 핵심 금지는 권한 설정으로도 이중으로 막는다.

**검증**
- 위반을 일부러 시도한다: 승인 전 수정, 범위 밖 파일 수정, 셸로 우회, 금지 명령. 전부 막히는지 본다.
- 깨진 입력을 넣어 정한 대로(차단) 동작하는지 본다.
- 평가셋의 과정 항목에서 정책 위반이 0건인지 본다.

**완료 기준**
- [ ] 필수 규칙마다 강제 장치와 차단 시험 기록이 있다
- [ ] 평가에서 정책 위반이 0건이다
- [ ] 막지 못하는 우회 경로가 표로 남아 있고 리뷰·CI로 보완된다

**흔한 함정:** 지침에 "반드시"라고 적고 끝내기, 오류 종료를 차단으로 착각하기, 검사를 끝내기 직전 한 번만 하기. 어느 한 층도 완전하지 않으므로 최종 방어선은 사람 리뷰와 CI다.

> 가드레일·보안 내용으로 이 단계를 보강할 예정이다.

---

## S6. 메모리 기반 자기개선

**목적:** 에이전트가 작업 경험을 쌓고, 다음 작업에 쓰고, 검증된 개선만 받아들이게 한다. 코딩 에이전트에서 가장 중요한 부분이다.

**고민할 것**
1. **무엇을 언제 기록하나.** 작업이 끝났을 때와 실패했을 때, 작업·실패 원인·해결책·출처 기록을 남긴다.
2. **어떻게 꺼내 쓰나.** 요청과 관련된 경험만 검색해 조금만 주입한다. 주입한 항목을 기록에 남겨 "실제로 썼다"를 보일 수 있게 한다.
3. **무엇을 고치게 하나.** 한 번에 하나만 연다: 프롬프트, 스킬 문서, 메모리 규칙 중 하나. 채점기, 정답, 테스트, 권한 설정은 고칠 수 없는 곳에 둔다.
4. **무엇을 받아들이나.** 효과 측정과 기존 기능 회귀 검증을 통과한 개선만 반영한다. 채택 기준은 미리 적는다.
5. **사람이 어디서 보나.** 자동 채택인가, 사람 승인인가.

**진행**
- 경험 저장소와 검색·주입을 만든다. 세션이 끝나도 남아야 한다.
- 실패 기록에서 개선안을 만든다. 실패마다 관찰 사실과 원인 가설을 나눠 적는다.
- 현재 버전과 개선 후보를 같은 평가셋·같은 조건으로 돌려 비교한다.
- 통과한 개선만 반영하고 버전 표시를 올린다.
- 같은 실수가 반복되면 더 강한 층으로 옮긴다: 지침 → 스킬 → 훅·권한 → 테스트·CI.

**검증**
- 세션 A에서 남긴 경험이 새 세션 B의 기록에 "주입됨"으로 보인다.
- 일부러 실패시킨 작업에서 개선안이 만들어진다.
- 전후 비교표가 있고, 탈락한 개선안은 반영되지 않았다.
- 개선 뒤 기존 평가가 회귀하지 않았다.

**완료 기준**
- [ ] 기억 → 활용이 새 세션에서 기록으로 확인됐다
- [ ] 개선 라운드가 한 번 이상 기록됐다 (채택이든 보류든)
- [ ] 채택 기준과 결과가 `design/06-improve.md`에 있다

**흔한 함정:** 에이전트가 메모리 파일을 직접 고쳐 검증을 건너뛰게 두기, 같은 세션에서 효과를 재기, 개선안이 테스트를 고쳐서 통과시키기.

---

## S7. 모델·비용·속도 최적화

**목적:** 동작을 그대로 둔 채 느리고 비싼 곳을 줄인다.

**고민할 것**
1. **어디가 느리고 비싼가.** 추측하지 말고 기록에서 찾는다. 오류 뒤 재시도 반복, 묶을 수 있었던 연속 호출, 큰 모델이 필요 없던 단계.
2. **모델을 내릴 수 있는 구간.** 분류·선택·예/아니오는 작은 모델이나 판단 전용 모델로 바꾼다.
3. **컨텍스트 줄이기.** 도구 수, 프롬프트 길이, 스킬로 뺄 수 있는 지식.
4. **직접 서빙한다면.** 양자화, 컨텍스트 상한, 캐시 적중. 하드웨어를 늘리기 전에 소프트웨어로 줄인다.

**진행**
- `optimize-agent` 스킬을 쓴다. 원칙은 "동작이 바뀌면 안 된다"(도구 호출 순서 포함)이다.
- 변경마다 켜고 끌 수 있게 만들고, 기존 문제 → 변경 → 전후 수치를 남긴다.
- 직접 서빙이면 `serving-plan` 스킬로 용량과 설정을 다시 본다. 양자화나 모델 교체는 평가셋으로 품질을 다시 잰 뒤 채택한다.

**검증**
- 변경마다 평가를 다시 돌려 회귀가 없는지 본다.
- 전후를 같은 조건으로 잰다: 첫 응답 시간, 전체 지연, 호출 수, 토큰, 건당 비용.

**완료 기준**
- [ ] S0의 지연·비용 목표에 도달했거나, 더 줄이지 않는 근거가 적혀 있다
- [ ] 변경마다 전후 수치와 회귀 결과가 `design/07-optimize.md`에 있다

**흔한 함정:** 평가 없이 모델부터 내리기, 여러 변경을 한꺼번에 넣기, 남이 잰 수치를 그대로 믿기.

---

## S8. 배포·운영

**목적:** 팀이 쓰게 하고, 쓰면서 계속 나아지게 한다.

**고민할 것**
1. **어떻게 나눠 주나.** 설정 묶음, 플러그인, 사내 레지스트리 중 무엇으로 배포하고 어떻게 업데이트하나.
2. **무엇을 조직 차원에서 강제하나.** 개인이 끌 수 없어야 하는 지침·검사.
3. **누가 소유하나.** 평가셋, 지침, 스킬, 훅 각각의 담당자.
4. **운영 기록을 어떻게 되먹이나.** 반복되고, 재현할 수 있고, 정답을 정의할 수 있는 기록을 평가셋으로 승격하는 주기.
5. **되돌리기.** 무엇을 어떤 버전으로, 누가 결정하나.

**진행**
- 최종 확인용 평가를 한 번 돌린다. 결과를 보고 다시 고치면 새 실험이다.
- 소수 사용자로 시범 운영하고 기록을 매주 읽는다.
- 모든 요청을 평가하지 않는다. 표본을 뽑거나 "확인 필요" 표시가 붙은 기록만 본다.

**검증**
- 깨끗한 환경에서 README대로 설치·실행된다.
- 최종 확인용 평가가 미리 정한 승인 기준을 통과한다.
- 시범 사용자 기록에서 정책 위반이 없다.

**완료 기준**
- [ ] 최종 확인용 평가 통과 결과와 재현 조건이 `design/08-release.md`에 있다
- [ ] 인수 기준(`harness/CRITERIA.md`) 항목마다 실행해서 확인한 증거가 있고, README에 항목별 확인 방법이 있다
- [ ] 배포·업데이트·되돌리기 방법이 문서로 있다
- [ ] 주간 회고와 평가셋 승격 담당자가 정해졌다

## 2. 전체가 끝났다는 기준

아래가 모두 참이면 첫 버전이 끝난 것이다. 그 뒤는 운영 루프(S8 → S1 승격 → S6·S7)가 계속 돈다.

1. S0에서 정한 성공 지표를 **최종 확인용 평가**에서 충족한다
2. 정책 위반이 0건이다
3. 깨끗한 환경에서 문서대로 재현된다
4. 모든 실행이 기록되고, 실패 지점을 기록에서 찾을 수 있다
5. 개선이 "측정 → 한 가지 변경 → 재측정 → 채택"으로 한 번 이상 돌았다
6. 평가셋·지침·검사의 담당자가 있다

## 3. 인수 기준과의 관계

완성품이 통과해야 하는 평가 기준 16개 항목(40점)과 단계의 대응은 `harness/CRITERIA.md`에 있다. S0에서 성공 지표를 정할 때 함께 보고, S8에서 `criteria-check` 스킬로 항목마다 증거를 확인한다.

## 4. 진행 도구

- `bash harness/scripts/phase.sh`: 단계별 상태(완료, 진행 중, 지금 시작할 수 있는 것, 선행 단계 대기)를 보여준다.
- `bash harness/scripts/start-phase.sh <번호>`: 단계 산출물 템플릿을 `design/`에 만든다. 선행 단계가 안 끝났으면 거절한다.
- 단계 산출물의 "완료 기준" 체크박스가 모두 체크되면 그 단계는 완료로 판정된다.

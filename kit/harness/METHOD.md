# 회사 코딩 에이전트 구축 방법론

> 무엇을 어떤 순서로 만들고, 단계마다 무엇을 고민하고, 어떻게 진행하고, 어떻게 검증하고, 언제 끝났다고 보는지를 정리한 문서다.
> 특정 프레임워크나 기반 에이전트를 전제하지 않는다. 기반별 내용은 `harness/bases/`에 따로 둔다.

읽는 법
- 이 문서는 뼈대다. 양식·스키마·시험 목록처럼 그대로 가져다 쓸 것은 `harness/reference/`에 있다.
- 숫자 옆의 **(제안값)** 은 공개 자료에서 그대로 나온 값이 아니라 시작점으로 잡은 값이다. 기준선을 잰 뒤 우리 수치로 바꾼다.
- 근거 자료 목록은 [`reference/sources.md`](reference/sources.md)에 있다.

## 1. 전체 그림

```
S0 범위·기반 ─┬─► S1 시험지·채점기 ───────────┐
              │                               ▼
              └─► S2 뼈대·관측 ─────────► [기준선 측정] ─┬─► S3 컨텍스트·메모리 ─┐
                                                        ├─► S4 도구·스킬 ───────┼─► S6 자기개선 ─┐
                                                        └─► S5 실행 제어 ───────┤                ├─► S8 배포·운영
                                                                                └─► S7 최적화 ───┘
```

| 단계 | 시작하려면 | 같이 진행할 수 있는 것 | 끝났다는 기준 (한 줄) |
|---|---|---|---|
| S0 범위·기반 결정 | 없음 | 없음 | 대상 작업·기반·모델·성공 지표·금지 행동이 숫자와 근거로 승인됐다 |
| S1 시험지·채점기 | S0 | S2 | 검증된 과제 묶음과 채점기가 명령 한 줄로 돌고, 비교 규칙이 결과를 보기 전에 적혀 있다 |
| S2 뼈대·관측·기준선 | S0 (기준선 측정에는 S1 필요) | S1 | 한 요청이 끝까지 돌고, 전부 기록되고, 조건이 적힌 기준선이 있다 |
| S3 컨텍스트·메모리 | S2 | S4, S5 | 지침·탐색·캐시·압축·기억 저장이 정해졌고 수치로 확인됐다 |
| S4 도구·스킬 | S2 | S3, S5 | 편집 형식과 도구 규격이 정해졌고 도구·스킬이 각자 시험을 통과했다 |
| S5 실행 제어 | S2 | S3, S4 | 반드시 지킬 규칙이 둘 이상의 층에서 막히고, 위반 시도가 전부 차단됐다 |
| S6 자기개선 | S1, S2, S3, S5 | S7 (반영은 따로) | 기억 → 조회 → 활용 → 개선안 → 검증 → 판정이 한 바퀴 돌았다 |
| S7 최적화 | S3, S4, S5 | S6 (반영은 따로) | 유지 기준을 지킨 채 목표 지연·비용에 도달했거나, 더 줄이지 않는 근거가 있다 |
| S8 배포·운영 | S6, S7 | 없음 | 최종 확인을 통과했고, 되돌리기를 해 봤고, 운영 루프 담당자가 있다 |

### 왜 이 순서인가
- **평가(S1)와 기록(S2)이 먼저다.** 재지 못하면 무엇을 고쳐도 좋아졌는지 알 수 없고, 기록이 없으면 왜 틀렸는지 알 수 없다.
- **S3·S4·S5는 서로 다른 손잡이라 동시에 만들 수 있다.** 다만 아래 "결합 지점"에서는 순서를 지킨다.
- **S6은 네 가지가 있어야 안전하다.** 채점기(S1), 기록(S2), 메모리 저장소(S3), 그리고 개선안이 테스트·채점기·권한을 건드리지 못하게 막는 게이트(S5).
- **S7은 동작이 굳은 뒤에 한다.** "지켜야 할 것을 지켰다"를 확인하려면 비교할 기준이 고정돼 있어야 한다.

### 병렬 작업 규칙
- **만드는 것은 병렬, 반영하는 것은 하나씩.** 변경을 합칠 때마다 평가를 돌리고, 한 번에 한 가지만 바꾼다. 두 변경을 같이 넣으면 어느 쪽이 결과를 바꿨는지 알 수 없다.
- **읽기는 병렬, 쓰기는 한 번에 한 에이전트.** 탐색과 독립 리뷰는 동시에 돌려도 된다. 같은 작업 트리에 여러 에이전트가 동시에 쓰게 하지 않는다. 꼭 필요하면 체크아웃을 나누고 병합을 한 곳에서 순서대로 한다.
- 사람이 2~3명이면 이렇게 나눈다: 한 명이 S1(평가), 한 명이 S2(뼈대·기록)를 맡고, 기준선이 나오면 S3·S4·S5를 한 명씩 맡는다.

결합 지점 (병렬로 만들더라도 이 순서는 지킨다)

| 먼저 | 그다음 | 이유 |
|---|---|---|
| S4의 편집 형식 결정 | S5의 편집 전·후 검사 | 편집 도구가 정해져야 검사가 무엇을 가로챌지 정해진다 |
| S4의 도구 정의 동결 | S3의 캐시·시작 로드량 측정 | 도구 정의가 캐시 접두의 맨 앞이라 설명문 한 줄만 고쳐도 수치가 바뀐다 |
| S5의 계획 양식 확정 | S3의 압축 생존 시험 | 압축 뒤에도 계획과 승인 상태가 살아 있어야 한다 |
| S4의 스킬 | S5의 차단 메시지 | 검사는 막고, 메시지는 고치는 방법(어느 스킬)을 가리킨다 |
| S3의 메모리 저장소 | S6의 조회·주입 | 저장이 실제로 이어져 있어야 조회를 잴 수 있다 |
| S6의 채택 | S7의 기준선 재측정 | 프롬프트·스킬이 바뀌면 비용·지연 기준선이 바뀐다. 둘을 같은 평가 창에 함께 반영하지 않는다 |

### 모든 단계에 공통인 규칙
1. **완료는 증거로 판정한다.** 에이전트의 "완료했다"는 자기 보고다. 테스트 결과, 실제 파일 상태, 기록으로 판정한다.
2. **결정에는 근거를 남긴다.** `design/decisions.md`에 문제 → 선택 → 근거 → 되돌리는 방법을 한 줄씩 적는다.
3. **판정 규칙은 결과를 보기 전에 적는다.** 한 번의 비교 안에서는 데이터·채점기·환경·한도·반복 수를 바꾸지 않는다. 과제나 채점기의 결함을 찾으면 고치되, 고치면 새 버전이고 비교할 양쪽을 새 버전으로 다시 채점한다.
4. **실패를 숨기지 않는다.** 테스트를 지우거나 건너뛰지 않고, 실패한 실행을 표에서 빼지 않고, 모르는 값은 0이 아니라 빈칸으로 둔다.
5. **단순한 구성에서 시작한다.** 싱글 에이전트, 가장 강한 허용 모델, 최소 도구. 부품을 더하는 이유는 측정된 실패여야 하고, 더한 부품마다 "무엇을 못 해서 넣었나"를 적는다.
6. **반드시 지켜져야 하는 것은 코드가 강제한다.** 지침과 스킬은 모델이 읽고 따르는 것이라 보장이 아니다. "속이지 말라"는 문장으로 막을 수 있는 것은 거의 없다.
7. **해당 없는 완료 기준은 지우지 않는다.** `[x] 해당 없음 — 이유`로 닫는다. 건너뛴 단계는 `start-phase.sh --force "이유"`로 기록이 남는다.

### 비교 규칙 (S3·S4·S6·S7이 전부 쓴다)

"평가 회귀가 없다"와 "좋아졌다"는 아래 뜻으로만 쓴다. 자세한 계산과 예시는 [`reference/eval.md`](reference/eval.md)에 있다.

- **측정:** 과제마다 여러 번 돌린다(개발 중 3회, 채택·출시 판단 5회 — 제안값). 표본 단위는 시도가 아니라 과제다. 반복 실행을 독립 사례로 세지 않는다.
- **비교:** 같은 과제·같은 반복 수·같은 평가 조건에서 한 가지만 바꾸고, 과제별 짝 차이(후보 − 기준)로 본다. 좋아진 과제 수와 나빠진 과제 수를 같이 적는다.
- **판정은 넷 중 하나다.** 위에서부터 먼저 걸리는 것으로 정한다.
  - 무효: 환경 오류·채점기 오류·근거 부족인 시도가 미리 정한 한도를 넘었거나 평가 조건이 서로 다르다. 그 실행으로 판정하지 않는다.
  - 회귀: 후보에 정책 위반이 1건이라도 있거나, 기준에서 매번 통과하던 과제가 추가 실행에서도 다시 실패했거나, 짝 차이의 구간 상한이 0보다 작거나, 평균 차이가 허용폭보다 더 나쁘다.
  - 개선: 짝 차이의 구간 하한이 0보다 크고 평균 차이가 흔들림 폭을 넘는다.
  - 차이 없음: 그 밖의 경우. "좋아졌다"고 쓰지 않는다. 지연·비용·단순함이 나아졌을 때만 채택한다.
- **"평가 회귀가 없다"** 는 판정이 개선 또는 차이 없음이라는 뜻이다.
- **흔들림 폭:** 아무것도 바꾸지 않고 같은 조건으로 두 번 돌린 차이다. 이보다 작은 차이는 우연과 구별되지 않는다. 허용폭과 최소 개선폭은 이보다 작게 잡을 수 없다.
- **과제 수의 한계:** 5건은 파이프라인이 도는지 보는 용도다. 5건에서 3건 통과의 95% 구간은 23~88%다. 20~50건이어도 10%p 안팎보다 작은 차이는 가려내지 못한다. 과제가 20건(제안값)에 못 미치면 구간을 내지 않고 정책 위반과 확정된 실패만 본 뒤 "차이 없음(규모 부족)"으로 적는다.
- **비용 층:** 변경할 때마다 일부 과제 1회(연기 시험) → 반영 후보마다 개발용 전체 3회 → 채택 전 5회 → 출시 전 최종 확인용 한 번. 실행 전에 과제 수 × 반복 × 버전 수 × 시도당 비용을 적는다.

## S0. 범위·기반 결정

**목적:** 무엇을 만들고 무엇을 "완료"라고 부를지 정한다. 여기서 정한 숫자가 뒤 단계 전부의 판정 기준이 된다.

**고민할 것**
1. **에이전트로 풀 일인가.** 단계 수와 경로를 미리 알 수 있으면 코드가 순서를 정하는 워크플로가 더 싸고 예측 가능하다. 에이전트가 맞는 경우는 ① 필요한 파일 수·단계 수가 건마다 다르고 ② 통과/실패로 돌아오는 검사(테스트, 빌드, 린트)가 있고 ③ 건당 토큰 비용을 감당할 수 있을 때다.
2. **대상 작업.** 누가, 어떤 저장소·언어에서, 어떤 작업(버그 수정, 기능 추가, 테스트 작성, 리뷰)을 맡기나. 첫 대상은 하나만 고른다. 기준은 "완전히 맡길 수 있는 가장 작은 조각"이면서 "자동 검증이 이미 있거나 붙일 수 있는 조각"이다. 검사가 없으면 에이전트는 된 것처럼 보이는 지점에서 멈춘다.
3. **기반.** 기존 코딩 에이전트를 포크·확장할지, 에이전트 SDK 위에 조립할지, 루프를 직접 짤지. 선택지별 대가를 적는다: 포크(전부 고칠 수 있으나 상류 변경을 계속 따라가야 한다) / SDK(도구·훅·세션을 받지만 내부가 한 겹 가려진다) / 직접 루프(몇 줄로 시작하지만 컨텍스트 관리·재개·권한을 전부 만든다). 판단 기준:
   - 소스를 고칠 수 있는가, 끼어들 지점(훅·미들웨어·스킬·서브에이전트)이 있는가, 사내 모델을 붙일 수 있는가, 라이선스
   - 모델에 실제로 들어가는 요청(시스템 프롬프트, 도구 정의, 메시지)과 응답 원문을 덤프할 수 있는가. 볼 수 없으면 고칠 수 없다
   - 구성요소(계획 단계, 리뷰어, 압축, 서브에이전트)를 하나씩 끌 수 있는가
   - 컨텍스트 관리(압축 시점, 오래된 도구 결과 정리, 캐시 지점)를 우리가 제어할 수 있는가
   - 세션 기록이 프로세스 밖에 남아 중단 지점에서 재개할 수 있는가
   - 공개 형식(지침 파일, 스킬 파일, MCP)을 읽는가. 읽는다면 지침·스킬·도구 자산이 기반과 무관해져 기반을 나중에 바꿀 수 있다
4. **모델.** 외부 API를 쓸 수 있는가. 코드가 회사 밖으로 나가도 되는지가 먼저다(판단 축: 비용·보안·커스터마이징). 사내 서빙이면 어떤 모델을 어떤 장비에 올릴 수 있는지(용량 = 가중치 + KV 캐시)를 확인한다.
   - 기준선은 쓸 수 있는 것 중 가장 강한 모델로 잡는다. 약한 모델로 시작하면 실패가 모델 한계인지 하네스 문제인지 가릴 수 없다. 역할별 모델 분리는 후보 칸만 적고 교체는 S7에서 평가로 정한다.
   - 코딩 에이전트용 점검: 도구 호출 스키마 준수, 우리가 쓸 편집 형식의 적용 성공률, 컨텍스트 창, 접두 캐시 지원, 추론 강도 조절 손잡이.
5. **완료 정의와 성공 지표.** 성공률(숨긴 테스트 통과, 매번 통과 기준), 정책 위반 0건, 전체 지연, 통과 1건당 비용. 목표값을 숫자로 적는다. 건당 최대 턴·시간·토큰 상한도 여기서 정한다(S2 예산과 S7 목표의 기준).
6. **하면 안 되는 일.** 배포, 운영 데이터 변경, 강제 푸시, 시크릿 접근처럼 에이전트에게 절대 맡기지 않을 행동.
7. **사람이 지켜보지 않아도 되는가.** 무인 실행을 목표로 하면 다섯 가지에 답한다: 완료가 무엇인지 아는가 / 스스로 검사할 수 있는가 / 무엇을 건드릴 수 있는가 / 무엇이 멈추게 하는가 / 결과가 어디로 가고 누가 승인하는가.

**진행**
- `project-kickoff` 스킬로 인터뷰한다. 한 번에 하나씩 묻고, 모르는 항목은 지어내지 않는다. "잘 되면 완료" 같은 기준은 실행 결과로 참/거짓을 가릴 수 있는 문장이 될 때까지 다시 묻는다.
- 기반 후보는 설치 전에 구성(스킬·에이전트·훅·MCP)과 위험을 먼저 읽고, 망가져도 되는 환경에서 돌려 본다.
- 기반 후보마다 같은 작은 작업(실패하는 테스트 하나 고치기)을 시키고 요청·응답 원문을 덤프해 읽는다. 기반이 기본으로 켜 두는 구성요소 목록을 뽑아 둔다(S2 구성요소 표의 재료).
- 모델 후보마다 편집 형식 스모크를 돈다: 같은 편집 과제 N건에서 적용 실패 수와 스키마 위반 수를 센다. N과 통과선은 돌리기 전에 정한다.

**검증**
- 완료 기준 문장마다 "이걸 어떤 명령이나 기록으로 확인하나"를 옆에 적을 수 있다.
- 대상 작업의 과거 사례 가운데 자동 검사를 붙일 수 있는 비율을 센다(예: 최근 이슈·PR N건 중 몇 건).
- 실제 사용할 개발자 2~3명이 대상 작업과 금지 행동을 읽고 동의했다.

**완료 기준**
- [ ] 대상 작업 하나와, 그것을 에이전트로 푸는 근거(건마다 다른 단계 수, 자동 검사의 존재)가 적혀 있다
- [ ] 기반 후보별 확인 결과(원문 덤프, 구성요소 끄기, 재개, 공개 형식)와 선택 근거가 decisions.md에 있다
- [ ] 기준선용 모델과 나중에 내려 볼 후보가 구분돼 있고, 편집 형식 스모크 결과가 있다
- [ ] 성공 지표 목표값과 건당 턴·시간·토큰 상한이 숫자로 있고, 지표마다 확인 방법이 적혀 있다
- [ ] 금지 행동 목록이 있고, 무인 실행을 목표로 하면 다섯 문항의 답이 있다
- [ ] 사용자 대표가 브리프를 확인했다

**흔한 함정:** 범위를 "모든 개발 작업"으로 잡기, 검증 수단이 없는 작업을 첫 대상으로 고르기, 약한 모델로 시작해 하네스로 메우기, 프롬프트를 가리는 추상화를 내부를 모른 채 쓰기, 기반의 기본 구성요소를 전부 켠 채 무엇이 기여하는지 모르기, 완료 기준을 "잘 동작하면"으로 두기.

**순서와 병렬:** 대상 작업 결정이 먼저다. 그다음 기반 후보 조사와 모델 후보 조사는 읽기 전용이라 동시에 한다. 기반 × 모델 조합 스모크는 한 번에 한 조합씩 돌린다.

## S1. 시험지와 채점기

**목적:** "좋아졌다"를 판정할 기준을 만든다. S2와 동시에 진행한다. 과제 양식, 채점 순서, 통계는 [`reference/eval.md`](reference/eval.md)에 있다.

**고민할 것**
1. **무엇이 대표 과제인가.** 실제 과거 이슈·PR, 사용할 개발자 인터뷰에서 뽑는다. 모델에게만 맡기면 일반적인 문제가 나온다. 능력 묶음(아직 잘 못하는 작업)과 회귀 묶음(이미 되는 작업, 통과율 100% 근처)을 나눈다.
2. **과제 한 건이 판정 가능한가.** 담당자 두 명이 따로 봐도 같은 통과/실패를 내는가. 채점기가 확인하는 것이 전부 요청문에서 읽히는가(숨긴 테스트가 요청문에 없는 함수 이름·경로를 요구하지 않는가). 요청문에 해답이 들어 있지 않은가.
3. **결과가 기준이고 과정은 관문이다.** 통과 여부는 끝난 뒤의 환경 상태(숨긴 테스트)로 정한다. 과정은 금지 행동과 의존 관계가 있는 순서(계획 승인 → 첫 수정, 마지막 수정 → 테스트 실행)만 통과/실패로 본다. 도구 호출의 순서·횟수·종류는 진단 지표로만 남긴다. 다른 길로 푼 정답을 떨어뜨리면 채점기가 틀린 것이다.
4. **무엇을 코드로 채점하고 무엇을 모델로 채점하나.** 테스트·diff·기록 이벤트로 판정되는 것은 코드. 의미 판단(요약과 변경의 일치, 되묻는 질문의 적절성)만 모델. 모델 채점이 사람과 갈리면 사람.
5. **에이전트가 정답에 닿는 길이 몇 개인가.** 파일(숨긴 테스트·정답 변경), git 기록(이후 커밋, 이전 시도), 네트워크(원본 저장소의 수정 PR), 경험 메모리(같은 사례의 해결 기록), 요청문 자체.
6. **테스트 통과만으로 충분한가.** 숨긴 테스트를 통과한 변경이 리뷰에서는 거절될 수 있다. 통과한 변경의 표본을 리뷰어가 "머지할 수 있나"로 판정하는 층을 둘지 정한다.
7. **무엇을 미리 적어 두나.** 반복 수, 주 지표(사람이 고르지 않고 결과를 그대로 받는 에이전트는 "매번 통과"가 주 지표다), 개선·회귀 판정 규칙, 최종 확인용 사용 규칙, 실행 비용.

**진행**
- `golden-dataset` 스킬로 과제를 만든다. 과거 PR에서 만들 때는 수정 직전 커밋을 기준 커밋으로, PR의 테스트 변경을 숨긴 테스트로, 나머지를 정답 변경으로 둔다. 기준 커밋에서 실패하다가 정답 변경 뒤 통과하는 테스트("고쳐졌다"의 증거)와 전후 모두 통과하는 테스트("안 깨뜨렸다"의 증거)를 나눠 적는다.
- **에이전트에게 주는 파일과 채점자만 보는 파일을 물리적으로 나눈다.** 숨긴 테스트·정답 변경·금지 목록은 에이전트 실행 환경에 넣지 않는다. 채점은 에이전트가 끝난 뒤 보호 경로를 원본으로 되돌리고 숨긴 테스트를 덮어써서 돌린다. 에이전트가 고친 테스트 파일로 채점하지 않는다.
- 5건으로 파이프라인(과제 형식, 격리, 채점)을 끝까지 통과시킨 뒤, 기준선을 재기 전에 개발용을 20건 이상으로 늘린다(제안값). 최종 확인용은 묶음 단위로 따로 둔다.
- 정상 사례만 넣지 않는다. 되물어야 하는 요청, 거절해야 하는 요청, 도구가 실패하는 상황, 한 조건만 다른 경계 사례 쌍을 넣고 유형별 통과 조건을 적는다. 빈 변경이 성공으로 세어지는 길이 없는지 확인한다.
- 시도마다 새 환경에서 시작한다. 기준 커밋 이후의 git 기록과 이전 시도의 흔적을 지우고, 네트워크는 끄거나 허용 목록만 열고, 경험 메모리는 같은 스냅샷을 읽기 전용으로 준다.
- `agent-eval` 스킬로 채점기를 만든다. 판정 순서는 판정 유효성(환경 오류·채점기 오류·근거 부족이 아님) → 정책 관문 → 결과 → 응답이다. 정책 위반은 다른 점수와 평균 내지 않는다. 부분 점수는 진단용으로만 남긴다.
- 모델 채점은 통과/실패와 이유로 받는다. 기준 하나에 판정기 하나, 근거가 부족하면 "판단 불가"를 내게 한다. 사람이 라벨한 사례로 잘못 통과와 잘못 탈락 비율을 따로 잰다.

**검증**
- 과제 검증(과제마다): 정답 변경을 넣어 3회 모두 통과, 아무것도 안 바꾼 상태는 실패, 기준 커밋에서 숨긴 테스트만 돌려 결과가 갈리는 테스트는 목록에서 뺀다. 다른 방식으로 푼 정답이 통과하고, 특정 입력만 분기해 맞춘 변경이 실패하는지 본다.
- 채점기 반례: 순서만 다른 정상 실행 → 통과, 승인 없이 수정 → 실패, 테스트 삭제·건너뛰기 → 정책 위반, 자원 상한·인프라 장애로 죽은 시도 → 환경 오류(턴·시간 예산 초과는 실패), 기록이 지워진 실행 → 근거 부족.
- 격리: 비공개 파일을 에이전트 환경에서 읽으려는 시도가 실패한다. 앞 시도가 남긴 파일·커밋·메모리가 다음 시도에서 보이지 않는다.
- 지름길을 찾으라고 지시한 에이전트를 한 번 돌려 본다. 통과하면 그 길을 막는다.
- 명령 한 줄로 평가 전체가 다시 돌고, 평가 조건이 결과 파일에 같이 남는다.

**완료 기준**
- [ ] 과제 파일이 에이전트용(공개)과 채점자용(비공개)으로 나뉘어 있고, 채점자용을 에이전트 실행 환경에서 읽을 수 없음을 시험했다
- [ ] 과제마다 검증 기록이 있다: 정답 변경 통과(3회), 무변경 실패, 불안정한 테스트 제외
- [ ] 개발용이 20건 이상이고 최종 확인용이 묶음 단위로 따로 있다. 최소 버전(5건)으로 정했으면 근거와 "개선이라고 쓰지 않는다"가 적혀 있다
- [ ] 채점기가 반례 시험을 통과했고, 모델 채점을 쓴다면 사람 라벨 대비 잘못 통과·잘못 탈락 비율이 있다
- [ ] 시도마다 환경이 초기화됨을 확인했다
- [ ] 명령 한 줄로 전체가 다시 돌고, 평가 조건(버전·해시·한도·반복 수)이 결과에 같이 남는다
- [ ] 반복 수, 주 지표, 개선·회귀 판정 규칙, 최종 확인용 사용 규칙이 결과를 보기 전에 적혀 있다

**흔한 함정:** 과제 5건의 통과율 차이로 채택을 결정하기, 한 번 돌린 결과끼리 비교하기, 요청문에 없는 이름을 숨긴 테스트가 요구하기, 에이전트가 고친 테스트 파일로 채점하기, git 기록에 정답 커밋이 남아 있기, 도구 호출 순서가 다르다고 떨어뜨리기, 환경 오류를 에이전트 실패로 세거나 표에서 조용히 빼기, 0%인 과제를 "어려운 과제"로 두기(깨진 과제일 가능성이 높다), 점수만 보고 기록을 안 읽기.

**순서와 병렬:** 과제 작성은 과제별로 동시에 할 수 있다. 과제 검증 → 채점기 반례 시험 → 첫 전체 실행 순서는 지킨다. S2의 기준선 측정은 이 단계가 끝난 뒤다.

## S2. 뼈대·관측·기준선

**목적:** 가장 단순한 버전이 한 요청을 끝까지 처리하게 하고, 모든 실행을 기록하고, 출발점 수치를 잰다. 이벤트 형식과 조회 도구 규격은 [`reference/trace.md`](reference/trace.md)에 있다.

**고민할 것**
1. **요청 한 건의 흐름.** 5단계 이하로 적는다. 기본형: 요구 확인 → 계획·리뷰·승인 → 구현 → 검증 → 보고·학습. 세 가지를 정한다.
   - 단계 전환은 모델의 선언이 아니라 코드가 판정한다(승인 기록, 테스트 종료 코드). 단계 안쪽의 진행(탐색 → 재현 → 수정 → 재실행)은 권장 순서로만 준다.
   - 계획에는 산출물·수정 대상·검증 방법까지 담는다. 구현 세부를 계획에서 못박으면 계획의 오류가 구현으로 번진다.
   - 버그 수정이면 구현 앞에 재현을 둔다. 실패하는 테스트나 재현 스크립트를 먼저 만들고 수정 뒤 같은 것을 다시 돌린다.
2. **단계마다 누가 하나.** 판단·생성·규칙·조회 꼬리표를 붙인다. 테스트 실행, 린트, 형식 검사 같은 규칙은 코드가 한다.
3. **검증을 누가 하나.** 만든 쪽의 자기 평가는 후하다. 판정은 ① 코드(테스트·린트·타입) ② 작성 과정을 보지 않은 독립 컨텍스트의 리뷰어 ③ 사람 순으로 둔다. 리뷰어에게는 범위("정확성에 영향을 주는 것만")를 준다. 범위 없는 리뷰어는 항상 무언가를 찾아내고, 전부 반영하면 불필요한 코드가 쌓인다.
4. **쪼갤 것인가.** 싱글로 시작한다. 쪼개도 되는 경우는 넷이다: 읽기 전용 탐색(질문이 분명하고 읽을 양이 많다), 독립 리뷰(작성 컨텍스트를 공유하지 않는다), 시끄러운 출력 격리(전체 테스트, 넓은 검색), 서로 다른 파일·체크아웃의 독립 작업. 쪼개면 토큰이 몇 배로 늘고 더 느려질 수 있다.
5. **한 컨텍스트 창을 넘는 작업인가.** 넘을 수 있으면 압축만으로는 부족하다. 세션 사이를 잇는 인계 산출물을 정한다: 상태 파일(항목별 완료 여부. 에이전트는 완료 표시만 바꿀 수 있다), 진행 메모, 작업 단위 커밋, 환경 기동·검사 스크립트.
6. **어디에, 무엇을 기록하나.** 사내 코드가 들어가므로 데이터 제어권(셀프호스팅, 내보내기)을 본다. 기록은 대화 ⊃ 요청 ⊃ 이벤트 세 층이고, 요청 ID 하나로 계획·승인·이벤트·요약·평가 결과가 이어져야 한다.
   - 요청마다 전체 흐름(계획, 리뷰, 코드 변경, 테스트, 결과)이 단계 표시와 함께 남는다. 단계 표시는 도구 이름으로 추정하지 않고 흐름을 조정하는 코드가 붙인다.
   - 모델 호출·도구 실행·메모리·자기개선·게이트 차단·계획 상태 변경이 각자 이벤트로 남고, 오류에는 종류 표시가 있다.
   - 내용 원문(프롬프트, 도구 인자·출력)은 기본으로 남기지 않는다. 남긴다면 저장 전에 가리고 따로 둔다.
7. **어떤 지표를 모으나.** 실행 시간, 모델 호출 수, 도구 호출 수, 재시도 수(모델 재시도 / 도구 재호출 / 리뷰 라운드 / 테스트 재실행을 따로), 게이트 차단 수, 토큰(캐시 읽기·쓰기 포함), 도구 오류율, 편집 적용 실패율, 컨텍스트 최대 사용량. 모르는 값은 0이 아니라 빈값으로 둔다.
8. **"첫 실패"가 무엇인가.** 셋을 구분한다: 첫 오류 이벤트, 복구되지 않은 첫 오류(뒤이은 성공이 없는 오류), 게이트 차단(오류가 아니라 정상 동작).
9. **종료 조건과 예산.** 최대 턴·시간·비용·재시도. 무진전 감지(같은 파일 재읽기, 같은 편집 반복, 같은 오류 연속). 종료 상태를 나눈다: 완료, 보류, 사람에게 넘김, 예산 초과, 무진전 중단, 실패.
10. **부품마다 무엇을 가정하나.** 하네스의 각 부품은 "모델이 혼자서는 이것을 못 한다"는 가정이다. 구성요소 / 가정 / 끄는 방법을 표로 적고, 모델이 바뀌면 다시 확인한다.
11. **코드 품질 기준.** 린터·포매터·docstring 규칙을 처음에 정해 설정 파일로 둔다. 나중에 한꺼번에 맞추려면 비싸다.

**진행**
- 기록기를 가장 먼저 만든다. 이벤트는 일어날 때마다 한 줄씩 덧붙인다. 끝에 한꺼번에 쓰지 않는다. 기록 쓰기 실패도 센다. 이벤트 형식을 검사하는 코드를 둔다.
- 가장 작은 구성(프롬프트 + 셸 + 편집 도구)으로 작은 작업 하나를 끝까지 돌려 본 뒤, 기반 기본 구성으로 같은 작업을 돌려 차이를 본다.
- 조회 도구를 만든다. 요청 ID를 주면 단계별 시간순 목록, 첫 오류 / 복구되지 않은 첫 오류 / 게이트 차단, 직전 맥락(직전 모델 호출과 직전 코드 변경)을 보여준다. 끝 이벤트가 없는 요청은 "미완"으로 표시한다. 요청별 요약 표도 낸다.
- 서브에이전트를 둔다면 위임 양식을 정한다: 목표, 출력 형식, 쓸 도구, 하지 말 것, 노력 상한(도구 호출 수), 반환 크기 상한. 큰 산출물은 파일로 쓰고 경로만 돌려준다.
- 완료 보고에는 실행한 명령과 출력(증거)을 붙이게 한다.
- 린트·포맷 검사 명령을 정하고 새 코드가 통과하게 한다.
- 뒤 단계(S5 게이트, S6 메모리·개선)를 만들 때마다 그 이벤트가 기록에 남는지 다시 확인한다.
- S1이 끝나면 기준선을 잰다. 개발용 전체를 3회 이상 돌리고 평가 조건(데이터·채점기 버전, 환경, 한도, 모델, 코드 커밋, 메모리 스냅샷, 일시)을 결과와 같이 남긴다. 같은 조건으로 한 번 더 돌려 흔들림 폭을 적는다. 실패 기록을 전부 읽고 "에이전트 / 과제·채점기 / 환경"으로 먼저 나눈다. 과제·채점기 결함이 0건이 될 때까지 평가를 고치고 다시 잰 값이 기준선이다.

**검증**
- 기록만 보고 사람이 첫 실패 지점과 원인을 찾는다. 조회 도구 출력과 일치하는지, 얼마나 걸렸는지 적는다.
- 일부러 만든 실행으로 기록을 확인한다: 실패하는 도구 호출, 한 번 실패했다가 성공한 호출, 실행 중 강제 종료한 요청, 가짜 시크릿을 넣은 요청. 가짜 시크릿 원문이 기록에 없어야 한다.
- 요약 지표의 호출 수를 이벤트 수로 직접 세어 맞춰 본다.
- 중단·재개: 실행 중인 요청을 죽인 뒤 다시 시작해 이어서 끝나는지 본다(긴 작업이 대상일 때).
- 풀 수 없는 과제를 줘서 예산 안에서 정해진 종료 상태로 끝나는지 본다.
- 거짓 완료율: 에이전트가 완료라고 보고한 건 가운데 숨긴 테스트가 실패한 비율을 센다.
- 깨끗한 환경에서 README 명령 그대로 실행되고, 린트·포맷 검사가 오류 0건이다.

**완료 기준**
- [ ] 요청 흐름, 단계 전환을 판정하는 코드, 단계별 담당이 적혔다
- [ ] 구성요소 표(구성요소·가정·끄는 방법)와 쪼갬 판단이 있다
- [ ] 한 요청의 기록에 다섯 단계가 시간순으로 남고, 모델 호출·도구 실행·오류가 종류 표시와 함께 이벤트로 남으며, 형식 검사를 통과한다
- [ ] 요청마다 요약 지표가 나오고 재시도가 종류별로 세어진다. 모르는 값은 빈값이다
- [ ] 조회 도구가 첫 오류 / 복구되지 않은 첫 오류 / 게이트 차단을 구분해 보여주고 미완 요청을 표시한다
- [ ] 가리기 시험에서 원문이 0건이다
- [ ] 종료 상태가 완료와 구분돼 기록된다 (예산 초과, 무진전 중단 포함)
- [ ] 깨끗한 환경에서 명령대로 실행되고, 린트·포맷·docstring 검사 명령이 통과한다
- [ ] 기준선 표가 평가 조건과 함께 채워졌고, 실패 분류에서 과제·채점기 결함이 0건이다

**흔한 함정:** 처음부터 멀티 에이전트로 설계하기, 같은 작업 트리에 병렬로 쓰게 하기, 서브에이전트에 한 줄짜리 지시 주기, 성공 경로만 기록하기, 끝에 한꺼번에 쓰기, 도구 인자·출력 원문을 그대로 남기기, 게이트 차단을 오류로 세기, 재시도를 한 숫자로 합치기, 조건을 안 적은 기준선, 한 번 돌린 결과를 기준선으로 쓰기, 채점기 결함으로 낮게 나온 수치를 기준선으로 삼아 이후 "개선"을 부풀리기.

**순서와 병렬:** 뼈대 구동과 기록 형식 설계는 동시에 할 수 있다. 기준선 측정은 둘 다 끝나고 구성을 동결한 뒤 한다. 구성요소를 꺼 보는 실험은 한 번에 하나씩 한다.

## S3. 컨텍스트·지식·메모리

**목적:** 에이전트가 우리 코드베이스의 규칙을 알고, 필요한 것만 읽고, 캐시를 깨지 않고, 기억을 남기게 한다. S4·S5와 동시에 진행한다. 메모리 기록 형식은 [`reference/memory-improve.md`](reference/memory-improve.md)에 있다.

**고민할 것**
1. **지침에 무엇을 적나.** 저장소를 읽어도 알 수 없거나 매 세션 다시 찾아야 하는 것만 적는다: 검증 명령(테스트 하나만 돌리는 법, 린트), 코드가 오해를 부르는 곳(따라 하면 안 되는 옛 패턴), 저장소에 없는 결정, 두 번 이상 교정한 것. 구조 설명과 파일 배치는 넣지 않는다. 모델이 직접 읽는다.
2. **지침을 어떻게 나누나.** 계층으로 나눈다: 조직 공통 / 프로젝트(저장소에 커밋) / 특정 경로에서만 로드되는 규칙 / 개인(커밋 제외). 계층이 겹칠 때 기반이 어떻게 처리하는지(이어 붙이는지, 가까운 것이 덮는지) 확인한다. 세션 시작 때 로드되는 지침 전체에 상한을 둔다. 파일을 쪼개서 가져오기만 해서는 로드량이 줄지 않는다. 줄이려면 경로 규칙이나 스킬로 옮긴다.
3. **기존 노하우를 누가 옮기나.** 위키에 있는 팀 규칙을 에이전트가 읽는 파일로 옮기는 담당자가 필요하다.
4. **코드를 어떻게 찾나.** 기본은 파일 목록·문자열 검색·범위 읽기다. 색인이 낡는 문제가 없다. 보조 수단은 측정된 신호가 있을 때 더한다: 심볼 정의·참조를 찾느라 파일을 많이 읽는다 → 언어 서버나 심볼 색인 / 모델의 탐색이 약하거나 창이 작다 → 저장소 지도 / 탐색 지연이 목표를 넘는다 → 의미 검색.
5. **탐색을 어디서 하나.** 서브에이전트로 보낸다: 질문이 분명하고, 읽을 양이 많고, 읽은 원문을 메인이 다시 쓰지 않는다. 직접 한다: 검색 한두 번이면 되는 조회, 읽은 코드를 곧바로 고쳐야 하는 경우. 탐색을 작은 모델에 맡기려면 탐색 재현율(정답 변경이 건드린 파일을 찾아냈는가)로 확인한다.
6. **프롬프트 배치와 캐시.** 캐시는 앞에서부터 같은 구간에만 맞는다. 순서는 도구 정의 → 시스템 프롬프트 → 대화이고, 앞이 바뀌면 뒤가 전부 무효다.
   - 도구 정의와 시스템 프롬프트는 세션 중에 바꾸지 않는다. 도구를 상황별로 제한해야 하면 정의를 빼지 말고 호출을 막거나 지연 로드를 쓴다.
   - 날짜·시각, 검색된 경험, 강제로 로드한 스킬 본문 같은 변동값은 시스템 프롬프트가 아니라 메시지로 넣는다. 한 번 넣은 메시지는 대화 중에 지우거나 바꾸지 않는다.
   - 직렬화를 결정적으로 한다(키 순서, 공백). 같은 내용이 다른 바이트로 나가면 캐시가 조용히 깨진다.
   - 캐시 수명과 최소 길이를 확인한다. 사람 승인 대기처럼 수명보다 긴 공백 뒤의 첫 요청은 전액이다.
7. **컨텍스트를 언제, 어떻게 줄이나.** 손잡이는 가벼운 것부터 셋이다: 오래된 도구 결과 비우기 → 요약 압축 → 리셋(새 컨텍스트 + 인계 산출물). 줄이는 것은 캐시를 깨는 사건이므로 조금씩 자주가 아니라 임계값에서 한 번에 충분히 비운다. 압축에서 살아남아야 하는 것을 목록으로 정한다: 작업 목표, 계획과 승인 상태, 수정한 파일 목록, 검증 명령, 금지 행동, 미해결 오류. 지침과 계획은 요약에 맡기지 말고 디스크에서 다시 주입한다. 실패한 시도와 오류는 지우지 않는다.
8. **무엇을 기억하나.** 세 종류를 한 파일에 섞지 않는다.
   - 규칙(항상 지킬 것): 사람이 쓰고 리뷰한다. 항상 로드되므로 짧게 둔다. 에이전트에게는 읽기 전용이다.
   - 경험(과거 작업의 실패·해결·교훈): 에이전트가 작업 끝에 남긴다. 항상 로드하지 않고 검색해서 조금만 꺼낸다(조회는 S6).
   - 절차(반복 작업의 순서): 스킬로 둔다(S4).
   - 작업 중 상태(할 일 목록, 진행 메모)는 별도 층이다.
9. **무엇을 저장하지 않나.** 코드와 git 기록에서 다시 알아낼 수 있는 것, 지침에 이미 있는 것, 시크릿·개인정보, 평가 정답, 외부에서 읽은 원문(이슈 본문, 웹 페이지, 도구 출력). 기준은 "다음 작업자가 이걸 모르면 같은 실수를 하는가"다.
10. **언제 누가 쓰고, 낡거나 오염되면 어떻게 하나.** 쓰는 시점은 코드가 정한다(작업 종료, 실패, 사람이 교정한 직후). 기억마다 근거(실행 ID, 커밋, 파일·줄)와 만료 기한을 붙이고, 쓸 때 근거가 아직 맞는지 확인한다. 쓰기에는 출처 규칙을 건다: 신뢰 못 할 입력(이슈, 문서, 도구 결과)에서 나온 문장은 그대로 저장하지 않고 격리함으로 보낸다. "기억은 참고 자료"라는 안내문만으로는 막지 못한다. 서브에이전트가 쓰는 기억도 같은 검사를 거친다. 기억은 범위(사용자·프로젝트)별로 나눠 저장하고, 민감 값은 쓸 때 가린다. 갱신은 추가·횟수 증가·폐기 표시만 하고, 모델이 파일 전체를 다시 쓰게 하지 않는다.
11. **모델이 고르지 않아도 되는 판단.** 요청·파일 종류로 필요한 스킬이 정해지면 코드로 강제 로드한다(내용은 메시지로 붙인다). 분류·예/아니오는 모델 호출 앞단에서 코드로 끝낸다.

**진행**
- 지침 계층 파일을 만들고 구역 형식을 하나로 통일한다(마크다운 제목이든 태그든). 형식보다 구체성이 중요하다. "코드를 잘 정리하라"가 아니라 실행할 명령과 경로를 적는다.
- 지침의 줄마다 묻는다: 코드를 읽으면 알 수 있는가. 그렇다면 지운다.
- 탐색 위임 양식을 정한다: 목표, 허용 도구, 하지 말 것, 노력 상한, 반환 형식(상태·사실·근거 위치·불확실한 점)과 크기 상한.
- 요청마다 캐시 읽기·쓰기·비캐시 입력 토큰을 기록한다. 캐시를 깨는 사건 목록을 문서로 둔다(도구 변경, 시스템 프롬프트 변경, 모델·설정 변경, 컨텍스트 정리, 수명 만료).
- 컨텍스트 줄이기 정책(발동 임계값, 최소 비움량, 남길 최근 호출 수, 생존 목록)을 정한다. 압축 프롬프트는 실제 긴 실행 기록으로 조정한다.
- 저장소를 둘로 만든다. 규칙은 지침 계층 파일, 경험은 한 줄에 한 건인 기록 파일과 한 줄 요약 색인. 사람이 열어 읽고 고칠 수 있는 평문으로 두고 버전 관리에 넣는다.
- 쓰기 정책을 코드로 만든다: 작업이 끝나거나 실패하면 기록 단계를 실행하고, 저장 전에 필수 필드·길이·시크릿 모양·평가 정답 흔적·중복을 검사한다. 쓰기·거부·폐기를 이벤트로 남긴다.

**검증**
- 세션 시작 로드량: 첫 요청의 입력 토큰을 구성별로(시스템, 도구 정의, 지침, 스킬 메타데이터, 메모리 색인) 잰다.
- 캐시 읽기 비율: 캐시 읽기 ÷ (캐시 읽기 + 캐시 쓰기 + 비캐시 입력). 비율이 떨어진 요청마다 원인이 사건 목록에 있는지 본다.
- 접두 안정성: 같은 세션의 연속 두 요청에서 시스템 프롬프트와 도구 정의의 해시가 같다.
- 지침 준수 탐침: 지침의 규칙을 각각 건드리는 과제를 새 세션에서 시험해 준수 건수를 센다.
- 압축 생존: 강제로 압축한 직후 생존 목록의 항목(승인 상태, 검증 명령, 금지 행동)을 여전히 지키는지 본다.
- 탐색: 재현율, 탐색에 쓴 토큰, 메인으로 들어온 토큰.
- 메모리 왕복: 값을 하나 쓰고, 프로세스를 끝내고, 새 프로세스에서 에이전트가 쓰는 것과 같은 길로 읽는다. 일부러 실패시킨 작업이 끝나면 경험 1건과 쓰기 이벤트가 생기는지 본다.
- 메모리 거부: 시크릿 모양 문자열, 평가 정답, 상한을 넘는 길이, 저장소 밖 경로를 넣어 전부 거부되는지 본다.
- 평가를 다시 돌려 비교 규칙으로 판정하고, "규칙을 몰라서 틀린" 실패 유형의 건수를 본다.

**완료 기준**
- [ ] 지침 계층, 겹칠 때의 규칙, 합계 상한, 담당자가 정해졌고, 상시 로드 지침이 상한 안이다
- [ ] 탐색 방식(검색 수단, 격리 조건)이 정해졌고 재현율 수치가 있다
- [ ] 시스템 프롬프트와 도구 정의가 세션 중 바뀌지 않음을 해시로 확인했다
- [ ] 컨텍스트 줄이기 정책(임계값, 최소 비움량, 생존 목록)이 있고 압축 생존 시험을 통과했다
- [ ] 규칙 저장소와 경험 저장소가 따로 있고, 종류별로 누가 쓰고 누가 고치는지가 적혀 있다
- [ ] 작업 종료·실패 때 경험이 기록되고, 프로세스를 끝낸 뒤 새 세션에서 같은 길로 읽힌다 (쓰기 이벤트와 왕복 확인 결과)
- [ ] 저장 전 검사의 거부 시험 기록이 있고, 로드량·항목 길이·건수 상한과 만료·정리 담당자가 있다
- [ ] 평가 회귀가 없고 세션 시작 로드량·캐시 읽기 비율·컨텍스트 최대 사용량이 기록됐다

**흔한 함정:** 한 파일에 전부 적기, 시스템 프롬프트에 시각·요청별 값을 넣기, 세션 중에 도구를 넣고 빼기, 조금씩 자주 비워 캐시를 매번 깨기, 대화로만 준 지시가 압축 뒤에도 남는다고 믿기, 검색 한 번이면 될 조회를 서브에이전트로 보내기, 강조 문구(반드시, 중요)를 더해 준수율을 올리려 하기(안 지켜지는 규칙은 줄이거나 강제 장치로 옮긴다), 대화 전체나 도구 출력 원문을 경험으로 저장하기, 메모리가 길어지면 모델에게 요약해서 다시 쓰게 하기, 저장 파일이 있다는 것만으로 "기억한다"고 판단하기.

**순서와 병렬:** 지침 작성, 탐색 방식 실험, 메모리 구조 설계는 서로 독립이라 동시에 한다. 캐시와 시작 로드량은 S4의 도구 정의가 동결된 뒤에 잰다. 압축 생존 시험은 S5의 계획 양식이 정해진 뒤 다시 돈다.

## S4. 도구·스킬

**목적:** 에이전트가 쓰는 도구를 적고 명확하게 만들고, 반복 절차를 스킬로 묶는다.

**고민할 것**
1. **최소 도구 세트는.** 셸과 편집(보기 포함)으로 시작할 수 있다. 전용 도구는 측정된 실패(잘못된 경로, 과도한 출력, 편집 실패)를 막을 때 더한다. 사람이 봐도 어느 도구를 쓸지 헷갈리면 겹치는 것이다. API를 1:1로 감싸지 않는다.
2. **편집 형식.** 코딩 에이전트에서 가장 영향이 큰 결정이다. 후보는 문자열 치환(바꿀 원문이 정확히 한 곳에서만 일치해야 적용), 검색/치환 블록, diff 변형, 파일 전체 다시 쓰기다. 고르는 기준:
   - 모델이 줄 번호·줄 수·이스케이프를 세지 않아도 되는가
   - 일치가 0곳이거나 2곳 이상일 때 조용히 넘어가지 않고 무엇이 문제인지 알려 주는가
   - 큰 파일에서 출력 토큰이 감당되는가
   - 모델마다 맞는 형식이 다르다. S0에서 고른 모델로 적용 성공률을 재서 정하고, 모델을 바꾸면 다시 잰다.
3. **읽기·검색·테스트 도구가 돌려주는 것.** 원칙은 범위·필터·페이지로 필요한 만큼만, 기본값은 작게다.
   - 읽기: 줄 번호와 범위 지정, 기본 창 크기.
   - 검색: 결과 수 상한. 넘으면 일부를 쏟아내지 말고 좁히는 방법을 돌려준다.
   - 테스트: 통과/실패 요약과 실패 항목만 돌려주고 전체 로그는 파일에 둔 뒤 경로를 준다. 관련 테스트만 돌리는 빠른 실행과 전체 실행을 구분한다.
   - 잘랐으면 잘렸다는 사실과 나머지를 보는 방법을 알린다. 출력이 없으면 "성공했고 출력 없음"이라고 적는다.
4. **오류를 어떻게 돌려주나.** 모든 실패를 모델에 알리되 종류를 나눈다.
   - 모델이 고칠 수 있는 것(잘못된 인자, 일치 없음): 무엇이 틀렸고 어떻게 고치는지, 올바른 입력 예시와 함께.
   - 모델이 고칠 수 없는 것(연결 실패, 권한 없음): 재시도하지 말고 보고하라는 안내와 함께.
   - 하네스가 자동 재시도한 일시 오류: 끝난 뒤 결과와 횟수를 알리고 기록에 남긴다.
   - 빈 결과, 실행 오류, 연결 실패는 서로 다른 메시지다.
5. **사내 시스템 연결.** 명령줄 도구가 이미 있으면 셸로 쓰게 하고 사용법은 스킬에 적는다. 명령줄 도구가 없거나, 인증을 서버가 맡아야 하거나, 여러 클라이언트가 같이 써야 하면 MCP로 만든다. 붙일 때마다 도구 정의 토큰을 잰다. 외부 서버가 주는 도구 주석(읽기 전용 등)은 믿지 않는다.
6. **도구 수가 늘면.** 상시 노출 도구가 수십 개에 가까워지거나 정의가 1만 토큰대를 넘으면 자주 쓰는 것만 상시 로드하고 나머지는 필요할 때 찾게 한다. 도구가 적고 전부 자주 쓰이면 지연 로드는 지연만 더한다.
7. **무엇을 스킬로 묶나.** 같은 절차를 세 번째 붙여넣게 되면 스킬로 만든다. 모델이 이미 아는 것은 쓰지 않는다. 깨지기 쉬운 절차는 구체적으로, 판단이 필요한 일은 원칙만 적는다. 결정적이어야 하는 단계는 스킬 안의 스크립트로 둔다.
8. **누가 스킬을 부르나.** 부작용이 있거나 순서가 중요한 절차는 모델이 스스로 부르지 못하게 하고 진입 절차나 사용자가 부른다.
9. **호출 수 줄이기.** 여러 도구 호출을 스크립트 하나로 묶는 방식은 서로 의존하는 호출이 3개 이상이거나 큰 결과를 집계·필터할 때 쓴다. 모델이 중간 결과를 보고 판단해야 하는 일에는 쓰지 않는다. 스크립트 안의 호출도 S5의 검사를 거치는지 확인한다.

**진행**
- 편집 형식을 먼저 정한다. 편집 뒤 문법 검사를 걸어 문법을 깨는 편집은 적용하지 않고 오류와 앞뒤 코드를 돌려준다. 경로는 작업 폴더 안만 받는다.
- 도구 명세표를 쓴다: 이름 / 설명 / 타입 있는 인자와 입력 예시 / 반환(형식, 상한, 잘렸을 때 안내) / 오류(종류별 메시지) / 부작용 여부. **도구 설명은 충분히 쓴다**: 무엇을 하는지, 언제 쓰고 언제 쓰지 않는지, 인자의 뜻, 제약. 짧게 써야 하는 것은 스킬 설명과 상시 로드 지침이다.
- 인자 이름으로 실수를 막는다(`user`가 아니라 `user_id`).
- `skill-authoring` 스킬로 스킬을 쓴다: 설명은 무엇·언제(아닌 경우 포함)를 앞부분에, 가장 중요한 지시는 본문 맨 위에, 상세는 한 단계 깊이의 별도 파일에. 남이 만든 스킬 묶음의 스크립트는 설치 전에 읽는다.
- `tool-design-review` 스킬로 점검한다.
- 도구 개선 루프를 돈다: 현실적인 다중 호출 과제 → 실행 → 기록과 도구 지표 읽기 → 설명문·스키마 수정 → 따로 떼어 둔 과제로 과적합 확인.

**검증**
- 세 층으로 나눠 시험한다: 모델 없는 도구 단위 테스트 → 모델이 도구를 제대로 고르고 인자를 맞게 넣는지 → 전체 평가.
- 지표: 도구 오류율(도구별), 잘못된 도구 선택 비율, 편집 적용 실패율과 실패 뒤 복구에 든 호출 수, 같은 호출의 반복 횟수, 도구 결과 토큰 분포와 상한에 걸린 비율.
- 편집 가드레일: 문법을 깨는 편집, 0곳 일치, 2곳 일치, 작업 폴더 밖 경로를 넣어 각각 정해진 오류가 나오는지 본다.
- 잘라내기: 상한을 넘는 출력에서 안내문이 나오고 다음 호출이 범위·필터를 쓰는지 본다.
- 스킬 호출: 불려야 할 요청과 불리면 안 되는 요청 묶음으로 적중과 오발을 센다. 쓸 모델 전부로 돈다.
- 도구 정의 총 토큰과 상시 노출 도구 수를 잰다.

**완료 기준**
- [ ] 편집 형식이 선택 근거(모델별 적용 성공률)와 함께 정해졌고 가드레일 시험을 통과했다
- [ ] 도구마다 명세(설명, 인자 예시, 반환 상한, 오류 종류)와 단위 테스트가 있다
- [ ] 읽기·검색·테스트 도구의 출력 상한과 잘림 안내가 구현됐다
- [ ] 스킬마다 호출 시험 결과(적중·오발)가 있다
- [ ] 도구 정의 총 토큰, 도구 오류율, 편집 실패율이 적혀 있고 평가 회귀가 없다

**흔한 함정:** 도구를 늘려서 문제 풀기, 실패를 빈 결과로 숨기기, 도구 설명을 한 줄로 쓰기, 스킬 본문에 모델이 이미 아는 설명 늘어놓기, 줄 번호에 의존하는 편집 형식 쓰기, 긴 출력을 통째로 돌려주기, 잘라내고 알리지 않기, 한 모델에서만 시험하기, 평가 과제에 설명문을 맞추다가 과적합하기.

**순서와 병렬:** 도구 구현과 단위 테스트, 스킬 작성은 각각 동시에 할 수 있다. 설명문·이름·스키마 조정은 순차다. 한 도구의 설명을 바꾸면 다른 도구의 선택률이 바뀌므로 한 번에 하나 바꾸고 선택 시험을 다시 돈다. 편집 뒤 린트는 도구 안이든 S5의 실행 후 검사든 한 곳에만 둔다.

## S5. 실행 제어

**목적:** 반드시 지켜져야 하는 규칙을 "부탁"이 아니라 "강제"로 만들고, 에이전트가 읽는 모든 입력이 적대적일 수 있다는 전제에서 한 층이 뚫려도 피해가 커지지 않게 한다. 계획·승인 규격은 [`reference/plan-gate.md`](reference/plan-gate.md), 층별 방어·위협 점검표·차단 시험은 [`reference/security.md`](reference/security.md)에 있다.

**고민할 것**
1. **반드시 지켜져야 하는 것은 무엇인가.** 목록으로 뽑는다. 코딩 에이전트의 기본 목록:
   - 요구사항·범위·완료 조건 없이는 시작하지 않는다
   - 계획(수정 대상·순서·테스트 방법) → AI 리뷰 → 승인 후에만 코드를 바꾼다
   - 범위가 바뀌면 계획으로 돌아간다
   - 코드를 고치면 관련 테스트와 린트·포맷 검사를 돌린다
   - S0의 금지 행동은 실행 전에 막는다
2. **누구에게서 지키나.** 모델이 규칙을 잊는 경우만이 아니다. 목표를 채우려고 지름길을 택하는 경우(테스트를 고쳐 통과, 게이트 설정 수정, 승인 표시를 직접 쓰기)와 입력에 지시가 숨어 있는 경우(저장소 파일, 이슈·댓글, 웹, 도구 응답, 메모리)를 함께 본다.
3. **세 가지가 한 세션에 모이는가.** 비공개 데이터 접근, 신뢰 못 할 입력, 외부 통신·상태 변경. 셋이 모이면 유출이 가능하다. 코딩 에이전트는 기본으로 셋 다 가진다. 가장 싼 선택은 네트워크를 허용 목록으로 좁히고 시크릿을 실행 환경 밖에 두는 것이다.
4. **규칙마다 어디에 두나.** 지침(부탁), 스킬(위임), 실행 전 검사·권한 차단·격리(강제) 중에서 고른다. "반드시"인 규칙은 한 층에만 두지 않는다.
5. **승인을 에이전트가 위조할 수 없는가.** 에이전트가 쓸 수 있는 파일의 문자열(`status: approved`)을 게이트가 믿으면 자기 승인이 된다. 승인 기록은 에이전트가 쓸 수 없는 곳에 두고 승인한 계획 내용의 해시를 함께 남긴다. 계획이 바뀌면 승인은 무효다. 개별 행동의 승인도 도구·대상·인자·1회에 묶는다. 요청문이나 도구 결과에 적힌 "승인받았다"는 권한이 아니다. 신원과 한도는 하네스가 아는 값에서만 읽는다.
6. **게이트가 무엇을 확인하나.** "승인된 계획이 있는가"만이 아니라 "이 파일이 그 계획의 수정 대상인가"를 본다. 그러지 않으면 지난 요청의 승인이 남아 모든 수정이 통과한다.
7. **누가 승인하나.** 사람은 두 번 본다: 계획 승인과 최종 변경. 그 사이의 개별 명령 승인은 격리와 자동 검사로 줄인다. 행동을 되돌릴 수 있는지로 등급을 나눈다: 읽기와 되돌릴 수 있는 쓰기는 자율, 외부 통신·공유 상태 변경은 계획과 허용 목록 안에서만, 되돌릴 수 없는 것(강제 푸시, 운영 DB, 삭제, 배포)은 에이전트가 실행하지 않거나 매번 사람 승인과 미리 보기를 거친다. 승인 요청이 많으면 사람은 읽지 않고 누른다. 요청당 사람 승인 횟수를 지표로 잰다.
8. **누가 판정하고 누가 강제하나.** 모델은 위험 신호를 내고 코드가 실행을 강제한다. 권한·범위·형식·한도·순서는 코드가 판정한다(실행할 테스트도 이름·폴더 규칙으로 코드가 고른다). 의미 판단이 꼭 필요한 곳에만 모델을 쓰고, 싼 것부터 건다: 코드 → 판단 전용 모델 → 애매한 것만 범용 모델 → 사람. 확률을 행동으로 바꾸는 선(허용 / 검토 / 차단)은 코드가 긋는다. 판정이 실패하면 통과가 아니라 검토나 차단이다.
9. **차단하면 어떻게 되나.** 프로그램을 끝내지 않고 사유(규칙과 고치는 방법)를 모델에 돌려준다. 호출을 몰래 고쳐서 실행하지 않는다. 같은 일을 다른 길로 다시 시도하면 그것도 막는다. 차단 뒤에 실제로 실행된 호출은 0건이어야 한다.
10. **도구를 거치지 않는 길은 누가 보나.** 도구 호출 전 검사가 못 보는 길이 넷 있다: 들어오는 메시지(붙여 넣은 내용 속 지시, 여러 턴에 걸친 몰아가기), 모델 공급자로 나가는 내용(민감 값), 최종 답변(실패한 작업을 처리했다고 하는 보고), 메모리 쓰기. 길마다 장치를 두거나 두지 않는 이유를 적는다.
11. **조용히 통과하는 길은 없는가.** 검사기가 오류나 시간 초과로 죽으면 통과가 기본인 기반이 있다. 셸로 파일을 쓰면 편집 검사를 거치지 않는다. 서브에이전트의 도구 호출에 검사가 걸리는지도 확인한다.
12. **층마다 무엇을 못 막는가.** 지침, 권한 차단, 실행 전 검사, 격리(파일·네트워크), 실행 후 검사, 끝내기 전 검사, CI, 사람 리뷰를 놓고 층마다 못 막는 것을 적는다. 빈칸 없이 채우면 다음 층이 왜 필요한지 보인다.
13. **하네스 자신이 보호되는가.** 게이트 코드, 권한 설정, 승인 기록, 채점기, 숨긴 테스트, CI 설정, 규칙 메모리는 계획에 있어도 에이전트가 고칠 수 없어야 한다.
14. **남이 만든 확장을 어떻게 들이나.** 스킬·플러그인·훅·외부 도구 서버는 내 권한으로 도는 코드이거나 내 컨텍스트에 들어오는 지시다. 버전을 고정하고, 읽어 보고, 허용 목록으로 관리한다.

**진행**
- 에이전트가 읽을 수 있는 것, 쓸 수 있는 것, 신뢰 못 할 입력이 들어오는 길을 한 장에 적는다.
- `hook-design` 스킬로 규칙마다 둘 곳을 정하고 배치표를 쓴다. 반드시 지킬 규칙은 층을 둘 이상 적는다.
- 기반의 강제 장치가 실제로 어떻게 동작하는지 공식 문서와 소스로 확인해 `harness/bases/`에 적는다: 규칙 평가 순서, 검사기 실패·시간 초과 시 기본 동작, 여러 검사의 결정 병합, 서브에이전트 적용 여부, 끝내기 전 검사를 실패 시 차단으로 만들 수 있는지, 격리가 덮는 범위.
- `plan-review` 절차를 제품에 넣는다: 계획 양식과 형식 검사, 독립 컨텍스트의 읽기 전용 리뷰어(요청 원문을 받고, 작성자의 대화는 받지 않고, 저장소를 직접 열어 본다), 에이전트가 쓸 수 없는 승인 기록, 실행 전 게이트(승인 상태 + 수정 대상 범위 + 보호 경로), 범위가 바뀌면 승인 무효, 끝내기 전 확인(실제 변경 파일이 수정 대상 안인가, 완료 조건마다 확인 명령을 돌렸는가). 계획 상태가 바뀔 때마다 누가 바꿨는지 기록한다.
- 작업 크기에 따라 계획 깊이를 달리하되 양식은 같게 둔다. 한 줄 수정에도 수정 대상과 확인 명령은 있다.
- 파일 쓰기는 작업 폴더로, 네트워크는 허용 목록으로, 시크릿은 실행 환경 밖으로 둔다. 읽기를 막을 자격증명 경로는 직접 나열한다.
- 실행 전 검사는 막고, 실행 후 검사는 고치게 하고, 끝내기 전 검사는 확인한다. 검사 메시지에는 고치는 방법(어느 스킬)을 적는다. 끝내기 전 검사에는 반복 상한을 두고, 상한에 걸리면 "사람에게 넘김"으로 끝낸다.
- 판정기가 실패하면 통과가 아니라 차단으로 처리한다. 기반의 기본값이 통과라면 설정으로 바꾸고, 바꿀 수 없는 시점의 검사는 CI에 같은 것을 둔다.
- CI에 범위 검사(변경 파일이 계획 안인가), 테스트 삭제·건너뛰기 탐지, 시크릿·의존성 검사를 둔다. CI 설정과 보호 브랜치는 에이전트 권한 밖에 둔다.
- 검사는 항상 지나가는 길에 둔다. 모델이 부를지 말지 정하는 부품(서브에이전트, 스킬)에 강제 검사를 맡기지 않고, 부모 쪽에만 둔 검사가 서브에이전트 경로에서 빠지지 않는지 본다.
- 검토 판정에서는 안내문이 아니라 실행 중단과 재개로 사람에게 묻는다. 모든 호출에서 멈추지 않고 검토 판정에서만 멈춘다.
- 차단 이벤트에 규칙 ID를 붙여 기록하고, 같은 규칙에 반복해서 걸리는 패턴은 지침이나 스킬을 고칠 재료로 쓴다.
- 위반 시도를 스크립트로 만들어 게이트를 고칠 때마다 다시 돌린다.

**검증**
- 위반을 일부러 시도한다: 승인 전 수정, 계획 파일에 승인 표시를 직접 쓰기, 승인 뒤 계획 수정, 범위 밖 파일 수정, 셸로 우회, 금지 명령, 스크립트로 시크릿 읽기, 계획에 없는 의존성 설치, 테스트 삭제·건너뛰기, 게이트·설정 파일 수정. 같은 시도를 서브에이전트에게도 시킨다.
- 입력에 지시를 심는다: 저장소 문서, 이슈 본문, 도구 응답, 메모리 항목. 따르지 않는지, 외부로 나가는 통신이 없는지 본다.
- 검사기를 망가뜨린다: 스크립트 삭제, 예외, 시간 초과, 깨진 입력. 차단으로 끝나는지 본다.
- 한 층을 끄고 다시 돌려 다음 층이 잡는지 본다.
- 결함을 심은 계획(없는 경로, 확인 명령 없는 완료 조건, 테스트 삭제)을 리뷰어에게 주고 몇 개를 잡는지 센다.
- 모델이 판정하는 검사가 있으면 라벨 붙인 항목 세트(정상, 공격 문구를 인용한 정상, 직접 지시, 숨은 지시, 문자 변형)로 놓친 비율과 과잉 차단 비율을 따로 잰다. 판정기를 응답 없음·형식 오류 상태로 만들어 통과되지 않는지 본다.
- 검토 판정에서 실행이 실제로 멈추는지(멈춘 순간 부작용 0건), 재개 뒤 승인한 그 호출만 실행되는지 본다.
- 실패했거나 막힌 작업의 최종 보고가 "완료"라고 하지 않는지 실행 기록과 대조한다.
- 평가의 정책 위반이 0건인지 본다. 위반 판정은 게이트와 다른 코드(기록과 실제 변경 파일)로 한다. 게이트가 죽어 있으면 "차단 0건"과 "위반 0건"이 구분되지 않는다.

**완료 기준**
- [ ] 필수 규칙마다 강제 장치가 둘 이상의 층에 있고 차단 시험 기록이 있다
- [ ] 승인 기록을 에이전트가 만들거나 고칠 수 없고, 실행 전 게이트가 승인 상태와 수정 대상 범위를 함께 확인한다
- [ ] 보호 경로 목록이 있고, 계획에 넣어도 수정이 막힌다
- [ ] 검사기 실패·시간 초과·깨진 입력이 차단으로 끝난다(모델 판정의 실패는 검토나 차단). 그렇게 만들 수 없는 검사는 CI에 같은 것이 있다
- [ ] 차단 뒤 실제로 실행된 호출이 0건이고, 검사 없이 실행되는 경로(서브에이전트 포함)가 없음을 시험했다
- [ ] 도구를 거치지 않는 길(들어오는 메시지, 모델로 나가는 내용, 최종 답변, 메모리 쓰기)마다 장치나 대응하지 않는 이유가 적혀 있다
- [ ] 모델이 판정하는 검사는 라벨 세트로 놓친 비율·과잉 차단 비율·검토율을 쟀다 (모델 판정을 쓰지 않으면 "해당 없음")
- [ ] 층별 방어 표의 "못 막는 것"과 다음 층이 빈칸 없이 채워졌다
- [ ] 위협 점검표에 항목마다 대응과 시험 결과가 있다. 대응하지 않기로 한 항목은 이유가 있다
- [ ] 레드팀 시험이 명령 한 줄로 다시 돌고, 게이트 이벤트가 기록에 남는다
- [ ] 평가에서 정책 위반이 0건이고, 그 판정이 게이트와 독립된 코드에서 나온다
- [ ] 막지 못하는 우회 경로가 표로 남아 있고 보완책이 있다
- [ ] 요청당 사람 승인 횟수가 측정됐다

**흔한 함정:** 지침에 "반드시"라고 적고 끝내기, 에이전트가 쓸 수 있는 파일의 승인 표시를 게이트가 믿기, 승인 여부만 보고 범위를 안 보기, 읽기 차단 규칙만으로 시크릿이 안전하다고 믿기(스크립트가 직접 여는 파일에는 안 걸린다), 넓은 도메인을 네트워크 허용 목록에 넣기, 입력 필터로 숨은 지시를 막을 수 있다고 믿기(뚫려도 할 수 있는 일이 없게 권한을 줄이는 쪽이 먼저다), 리뷰어에게 작성자의 대화를 통째로 넘기기, 차단 0건을 안전의 증거로 보기, 개별 명령 승인을 많이 받아 사람이 읽지 않게 만들기, 남의 스킬·도구 서버를 읽지 않고 설치하기, 코드로 끝나는 검사에 모델을 쓰기, 모델 판정기의 실패를 통과로 처리하기, 검사를 부모 에이전트에만 걸기, 재지 않은 가드를 믿기, 신뢰 못 할 입력을 한 번 읽었다고 세션 전체를 막기(값 단위로 추적한다).

**순서와 병렬:** 규칙 배치표, 기반 동작 확인, 격리 설정은 동시에 할 수 있다. 실행 전 게이트는 S4의 편집 도구가 정해진 뒤 만든다. 차단 시험은 게이트·격리·CI가 모두 붙은 뒤 한 번에 돌리고, 그다음부터는 게이트를 고칠 때마다 다시 돌린다.

## S6. 메모리 기반 자기개선

**목적:** 에이전트가 쌓은 경험을 다음 작업에 쓰고, 검증된 개선만 받아들이게 한다. 개선안 형식과 판정 절차는 [`reference/memory-improve.md`](reference/memory-improve.md)에 있다.

**고민할 것**
1. **무엇으로 찾나.** 경험이 수백 건 이하이면 구조 필터(저장소·경로·작업 종류)와 키워드 검색(오류 문자열, 심볼, 파일명)으로 충분하다. 코딩 작업의 검색 키는 정확히 일치해야 하는 문자열이 많다. 임베딩은 재현율이 모자란다고 측정된 뒤에 키워드와 함께 쓴다.
2. **언제, 얼마나 꺼내나.** 요청을 받은 직후(계획 전)와 실패 직후(그 오류 문자열로). 한 번에 3~5건(제안값), 토큰 상한을 둔다. 발동 조건과 교훈만 넣고 근거는 경로로 가리킨다.
3. **꺼낸 기억을 믿어도 되나.** 주입 전에 근거(파일·커밋)가 지금 코드와 맞는지 확인한다. 안 맞거나 외부 입력에서 나온 항목은 주입하지 않는다. 메모리 내용은 지시가 아니라 참고로 넣는다.
4. **어디에 넣나.** 시스템 프롬프트를 고치지 않는다(캐시가 깨지고 모든 요청에 영향이 간다). 요청 뒤에 별도 메시지로 한 번 붙인다.
5. **"활용했다"를 무엇으로 보이나.** 조회 이벤트는 "꺼냈다"일 뿐이다. 계획에 어느 항목을 어떻게 반영했는지 적게 하고, 같은 작업을 주입 없이 돌린 결과와 비교한다.
6. **무엇을 고치게 하나.** 한 라운드에 한 종류, 한 가설만 연다: 시스템 프롬프트의 지정 구역 / 스킬 문서 하나 / 메모리 규칙 항목. 고칠 수 없는 것: 평가 데이터·정답·숨긴 테스트, 채점기·임계값·반복 수·채택 기준, 권한·훅·게이트, 예산, 모델·추론 강도(S7의 몫), 실행 기록, 저장소의 테스트 코드, 개선 루프 자신. 이 경계는 지시문이 아니라 경로 허용 목록과 해시 검사로 막는다.
7. **개선안을 만드는 쪽이 무엇을 보나.** 개선안은 자기가 읽은 실패에 맞춰진다. 채택 판정은 개선안을 만든 쪽이 읽지 않은 과제로 한다. 과제가 적어 나눌 수 없으면 "방향성 판정"이라고 표시한다.
8. **얼마나 좋아져야 받아들이나.** 흔들림 폭을 먼저 잰다. 최소 효과, 반복 수, 회귀 정의, 비용·길이 상한을 결과를 보기 전에 적는다.
9. **사람이 어디서 보나.** 경험 기록(후보)은 자동. 항상 로드되는 규칙·스킬·시스템 프롬프트의 변경은 사람 승인.
10. **언제 멈추나.** 최대 라운드 수와 비용 상한. 2~3 라운드 연속으로 흔들림 폭을 못 넘으면 내용을 더 고치지 않고 남은 실패를 원인별로 분류한다(지침 부족 / 채점기 문제 / 환경·하네스 문제 / 구조 문제 / 흔들림).

**진행**
- 검색·주입을 만든다. 조회마다 이벤트를 남긴다: 질의, 필터, 후보, 근거 확인 결과, 주입한 항목, 주입 토큰 수. 결과 없음과 조회 오류를 구분한다.
- 계획 양식의 "참조한 경험" 구역에 항목 ID와 "이 계획에서 무엇이 달라졌는지"를 적게 한다. 작업이 끝나면 항목마다 도움/해로움/미사용을 이벤트로 남긴다.
- 개선 설정을 실행 전에 파일로 고정한다: 손잡이와 허용 경로, 읽기용·판정용 과제 목록, 반복 수, 주 지표·관문·가드레일, 흔들림 폭 측정 방법, 회귀 정의, 최대 라운드, 승인자.
- 실패를 모은다. 실패마다 관찰 사실 / 원인 가설 / 다른 설명 / 근거 이벤트를 나눠 적는다.
- 개선안을 정해진 형식으로 받는다. 변경은 diff로, 항목 단위로. 문서 전체를 다시 쓰는 변경, 허용 목록 밖 경로, 기준을 낮추는 문구, 실패 사례의 문자열을 그대로 붙여 넣은 변경은 형식 검사에서 거부한다. 거부한 후보도 사유와 함께 남긴다.
- 현재 버전과 후보를 메모리·설정이 섞이지 않는 분리된 환경에서 같은 조건으로 돌린다. 반영 효과는 새 세션에서 잰다(지침·메모리·스킬 목록은 세션 시작 때 한 번 읽히는 구조가 많다).
- 판정한다: 잴 수 있는가 → 관문(정책 위반·금지 경로) → 회귀 → 효과(판정용 과제에서) → 가드레일(비용·지연·상시 로드량) → 흔적(바뀐 항목이 실제로 로드·인용됐는가) → 사람 승인. 판정은 채택 / 보류 / 기각 / 판정 불가 넷 중 하나로만 적는다.
- 통과한 것만 반영한다. 버전 표시를 올리고, 커밋하고, 되돌리는 명령을 적는다.
- 같은 실수가 다시 나오면 더 강한 층으로 옮긴다: 경험 → 규칙(지침) → 스킬 → 훅·권한 → 테스트·CI. 옮기면 아래 층의 항목은 폐기 표시한다.

**검증**
- 세션 A에서 남긴 경험이 새 프로세스의 세션 B 기록에 "주입됨"으로 보이고 계획에 인용된다.
- 주입을 끄고 같은 작업을 돌려 차이를 본다. 차이가 없으면 검색이 엉뚱한 것을 꺼내거나 평가가 그 능력을 재지 않는 것이다.
- 근거 파일을 바꾼 항목과 외부 입력에서 나온 항목은 주입되지 않는다.
- 일부러 실패시킨 작업에서 개선안이 만들어지고, 그 시점에 대상 파일은 바뀌지 않았다.
- 개선안이 금지 경로(테스트, 채점기, 권한)를 건드리도록 유도해 거부되는지 본다. 평가 하네스 파일을 한 글자 바꿔 해시 검사가 멈추는지 본다.
- 전후 비교표가 있고, 탈락한 개선안은 반영되지 않았다.
- 채택한 변경을 되돌리는 명령을 실제로 실행해 이전 버전으로 돌아가는지 본다.

**완료 기준**
- [ ] 기억 → 조회 → 계획 인용이 새 세션에서 기록으로 확인됐고, 주입을 껐을 때와의 차이가 적혀 있다
- [ ] 개선 설정(손잡이, 고칠 수 없는 것과 막는 장치, 사례, 최소 효과, 승인자)이 결과를 보기 전에 커밋돼 있다
- [ ] 금지 경로 변경과 하네스 변조가 막히는 시험 기록이 있다
- [ ] 개선 라운드가 한 번 이상 기록됐다 (채택·보류·기각·판정 불가 중 무엇이든, 사유와 함께)
- [ ] 채택한 변경마다 전후 표, 회귀 결과, 승인자, 버전, 되돌리는 명령, 새 세션에서 쓰인 기록이 있다 (채택이 없으면 "채택 없음"과 사유)

**흔한 함정:** 에이전트가 규칙·스킬 파일을 직접 고쳐 검증을 건너뛰게 두기, 같은 세션에서 효과를 재기, 개선안이 테스트나 채점 코드를 고쳐서 통과시키기, 개선안을 만든 쪽이 읽은 실패 사례로 채택을 판정하기, 한 번 돌린 결과의 1건 차이로 채택하기, 조회 이벤트만으로 "활용했다"고 하기, 메모리·프롬프트를 통째로 다시 쓰게 하기, 라운드마다 "조심하라" 같은 문장을 쌓기, 최종 확인용으로 라운드마다 판정하기, 실패의 원인이 채점기나 환경인데 지침만 계속 고치기.

**순서와 병렬:** 검색·주입과 개선 루프는 따로 만들 수 있다. 다만 개선 라운드는 검색·주입이 굳은 뒤에 돈다. S7과 동시에 만들 수 있지만 같은 평가 창에 함께 반영하지 않는다.

## S7. 모델·비용·속도 최적화

**목적:** 지켜야 할 것을 지킨 채 느리고 비싼 곳을 줄인다. S0의 지연·비용 목표를 이미 충족했다면 기준선과 근거를 적고 닫는다.

**고민할 것**
1. **무엇을 단위로 재나.** 호출 1건이나 토큰 1개가 아니라 "통과한 작업 1건당 비용"과 "작업 1건의 전체 시간"이다. 싼 모델이 실패하면 그 토큰과 재시도까지 값이다. 요청 종류(대화형, 야간 일괄)가 다르면 따로 재고, 중앙값만이 아니라 느리고 비싼 꼬리(p95)를 본다.
2. **시간이 어디서 나오나.** 작업 시간 ≈ 호출 수 × 첫 토큰까지 시간 + 출력 토큰 ÷ 출력 속도 + 모델 밖 시간(도구 실행, 대기열, 재시도). 어느 항이 큰지 기록에서 찾는다.
3. **무엇이 "동작 유지"인가.** 도구 호출 순서까지 같아야 한다는 기준은 대부분의 최적화와 양립하지 않는다. 대신 지켜야 할 것을 변경 전에 적는다: 결과 통과율이 흔들림 폭 안, 정책 위반 0건, 과정 규칙(승인 전 수정 금지, 테스트 실행) 통과, 최종 응답과 실제 변경의 일치.
4. **품질을 걸지 않는 것부터 한다.**
   - 걸지 않는 것: 캐시가 맞게 프롬프트 배치, 안 쓰는 도구·지침 빼기, 재시도·중복 호출 줄이기, 출력 형식 줄이기, 기다려도 되는 일은 일괄 처리.
   - 거는 것: 추론 강도 낮추기, 예산 조이기, 작은 모델로 내리기, 여러 모델로 나누기. 평가 없이는 적용하지 않는다.
5. **모델을 나누기 전에.** 같은 모델에서 추론 강도를 낮춘 결과를 먼저 잰다. 모델을 나누면 캐시가 갈라지고 관리할 것이 늘어난다. 나눈 구성은 단일 모델의 점수-비용 곡선 전체를 이겨야 한다.
6. **서브에이전트로 빨라지나.** 독립적인 작업을 동시에 돌릴 때와 한 컨텍스트에 안 들어가는 일일 때만 이득이다. 서브에이전트는 부모의 캐시를 못 쓰고 각자 컨텍스트를 다시 읽으므로 비용은 오를 수 있다.
7. **직접 서빙한다면.** 접두 캐시가 켜져 있고 실제로 맞는지, 분류 단계의 출력을 선택지로 강제했는지, 대기열이 쌓이는지. 하드웨어를 늘리기 전에 소프트웨어로 줄인다.

**진행**
- `optimize-agent` 스킬을 쓴다. 목표, 유지 기준, 흔들림 폭을 먼저 적는다.
- 기준선을 요청 종류별로 잰다: 통과 1건당 비용, 전체 시간 p50/p95, 첫 토큰 시간, 호출 수, 입력·출력 토큰, 캐시 읽기 비율, 재시도 수, 도구 실행 시간.
- 낭비를 기록에서 찾아 줄 세운다. 항목마다 "최대 얼마나 줄일 수 있는가"를 적고 작은 것은 버린다.
- 순서대로 한 번에 하나씩 적용한다.
  1. 캐시: 고정 내용을 앞에 얼리고 변동값은 뒤의 메시지로. 적중이 0이면 연속 두 요청의 프롬프트 바이트를 비교해 원인을 찾는다.
  2. 입력: 안 쓰는 도구 빼기, 도구를 필요할 때 찾게 하기, 프롬프트에 박힌 조각 지식을 스킬로 빼기, 예전 모델용 과잉 지시 지우기.
  3. 루프: 오류 뒤 같은 호출 반복, 묶을 수 있는 연속 호출, 규칙으로 끝낼 수 있는 판단을 코드로.
  4. 출력: 응답 형식을 정하고 도구 호출 사이의 설명을 줄인다. 출력 상한을 낮추는 것은 절약이 아니다(잘리면 재시도한다).
  5. 일괄 처리: 평가 실행, 야간 작업처럼 아무도 기다리지 않는 일.
  6. 추론 강도·예산: 평가셋으로 단계별로 훑어 점수-비용 표를 만든다.
  7. 모델 교체: 분류·선택·예/아니오부터. 큰 모델의 낮은 강도와 작은 모델의 기본 강도를 통과 1건당 비용으로 비교한다.
  8. 여러 모델·서브에이전트: 위를 다 해도 목표에 못 미칠 때만.
- 변경마다 켜고 끌 수 있게 만들고, 기존 문제 → 변경 → 전후 수치 → 유지 기준 통과 여부를 남긴다. 효과가 흔들림 폭 안이면 되돌린다.
- 직접 서빙이면 `serving-plan` 스킬로 용량과 설정을 다시 본다. 양자화나 모델 교체는 평가셋으로 품질을 다시 잰 뒤 채택한다.

**검증**
- 변경마다 평가를 다시 돌려 유지 기준을 확인한다.
- 전후를 같은 조건(데이터 버전, 반복 수, 동시성)으로 잰다. 캐시가 찬 상태와 식은 상태를 구분해 적는다.
- 응답에 찍힌 모델 이름이 설정과 같은지 확인한다. 조용한 대체가 있으면 비교가 무효다.
- 캐시 적중을 사용량 필드나 서빙 지표로 직접 확인한다.
- 토글을 꺼서 이전 수치로 돌아가는지 본다.

**완료 기준**
- [ ] 유지 기준이 변경 전에 적혀 있고 요청 종류별 기준선(통과 1건당 비용 포함)이 있다
- [ ] 변경마다 끄고 켜는 방법, 전후 수치, 유지 기준 통과 여부가 있다 (변경이 없으면 "변경 없음"과 근거)
- [ ] 품질을 거는 변경은 점수-비용 표를 근거로 채택했다 (없으면 "없음")
- [ ] S0의 지연·비용 목표에 도달했거나 더 줄이지 않는 근거가 있다

**흔한 함정:** 평가 없이 모델부터 내리기, 여러 변경을 한꺼번에 넣기, 호출당 비용이나 토큰 단가로 비교하기(실패와 재시도가 빠진다), 날짜·요청 ID를 시스템 프롬프트에 넣어 캐시를 매번 깨기, 서브에이전트로 쪼개면 싸진다고 가정하기, 첫 토큰 시간만 줄이고 전체 시간은 재지 않기, 기준 없이 "비슷해 보인다"로 통과시키기, 남이 잰 수치를 그대로 믿기.

**순서와 병렬:** 기준선 측정과 낭비 분석은 S6과 동시에 할 수 있다. 변경 적용은 위 순서대로 하나씩이다. S6이 변경을 채택하면 기준선을 다시 잰다.

## S8. 배포·운영

**목적:** 팀이 쓰게 하고, 쓰면서 계속 나아지게 한다.

**고민할 것**
1. **무엇을 한 버전으로 묶나.** 시스템 프롬프트, 지침, 스킬, 훅·권한, 메모리 규칙, 모델·추론 강도, 평가 데이터 버전을 한 묶음(릴리스 목록)으로 고정한다. 하나만 바뀌어도 새 버전이다. 전부 코드처럼 저장소에 두고 리뷰를 거친다.
2. **어떻게 나눠 주나.** 설정 묶음, 플러그인, 사내 레지스트리 가운데 무엇으로 배포하나. 사용자가 받는 버전을 고정할 수 있는가. 안정 채널과 선행 채널을 둘 것인가.
3. **무엇을 조직 차원에서 강제하나.** 개인이 끌 수 없어야 하는 검사·권한은 관리 설정으로, 안내는 조직 지침으로 둔다. 둘은 다르다.
4. **단계적으로 어떻게 넓히나.** 최종 확인 → 쓰기 없는 재생(과거 요청을 새 버전으로 돌려 계획·diff만 비교) → 소수 사용자·위험이 낮은 저장소 → 전체. 단계마다 넘어가는 기준과 멈추는 기준을 미리 적는다.
5. **운영에서 무엇을 보나.** 오프라인 평가는 실제 사용과 다를 수 있고, 운영 지표는 문제가 사용자에게 닿은 뒤에야 보인다. 둘 다 둔다. 지표는 소수만 고른다: 정책 위반·게이트 차단, 작업 완료율, 사람이 다시 고친 비율, 재시도·최대 턴 도달, 통과 1건당 비용, 전체 시간, 메모리 "해로움" 표시, 사용자 신고.
6. **무엇과 비교하나.** 배포 전후 비교는 시간이 지나며 바뀌는 다른 요인과 섞인다. 같은 기간에 이전 버전을 쓰는 집단을 남겨 비교한다.
7. **운영 기록을 어떻게 되먹이나.** 반복되고, 재현할 수 있고, 정답을 정의할 수 있는 기록을 과제로 승격한다. 새로 승격한 과제는 능력 묶음에, 안정적으로 통과하게 되면 회귀 묶음으로 옮긴다. 최종 확인용은 한 번 쓰면 닳으므로 운영 기록에서 새로 채운다.
8. **누가 소유하나.** 평가 데이터, 지침, 스킬, 훅·권한, 메모리(정리·만료), 릴리스 승인, 사고 대응 각각의 담당자. 자기 변경을 자기가 승인하지 않는다.
9. **되돌리기와 사고.** 무엇을 어떤 버전으로, 누가, 얼마나 빨리. 즉시 끌 수 있는 스위치(메모리 주입, 자기개선 반영, 선행 채널)를 둔다.
10. **바깥이 바뀌면.** 모델 버전이 바뀌면 평가를 다시 돌리고 추론 강도를 다시 훑고 S2의 구성요소 표를 다시 본다. 기반 에이전트를 올리면 S5의 차단 시험을 다시 돈다.
11. **기록에 무엇이 들어가나.** 사내 코드와 개인정보. 보존 기간, 접근 권한, 가리기 규칙을 정한다.

**진행**
- 릴리스 후보를 고정한다. 릴리스 목록(구성요소별 버전·해시)을 만들고 태그를 단다.
- 최종 확인용 평가를 한 번 돌려 미리 정한 승인 기준으로 판정한다. 결과를 보고 다시 고치면 새 실험이고, 그 최종 확인용은 개발용으로 내리고 새로 채운다.
- `criteria-check` 스킬로 인수 기준 항목마다 증거를 확인한다.
- 최근 실제 요청 표본을 새 버전으로 돌려(변경은 버려지는 작업 폴더에서) 계획, diff, 비용, 시간을 이전 버전과 나란히 본다.
- 소수 사용자로 시범 운영한다. 대조 집단, 기간, 넘어가는 기준, 멈추는 기준(예: 정책 위반 1건이면 즉시 중단)을 적고 시작한다.
- 모든 요청을 평가하지 않는다. 표본을 뽑거나 "확인 필요" 표시가 붙은 기록만 본다. 코드로 잴 수 있는 지표는 전수로 모은다.
- 사용자가 한 줄 명령으로 요청 ID와 함께 문제를 남길 수 있는 신고 경로를 만든다.
- 주간 회고를 돈다: 기록 읽기 → 실패 분류 → 과제 승격 후보 선정 → S6 라운드 입력 → 더 강한 층으로 옮길 것 → 메모리 정리.
- 프롬프트·스킬·훅 변경의 통로를 정한다: 변경 요청 → 리뷰 → 평가 자동 실행(회귀 묶음 통과가 병합 조건) → 선행 채널 → 안정 채널. S6의 채택도 이 통로를 탄다.
- 사고 절차를 적는다: 심각도 기준, 첫 조치(끄는 스위치, 이전 태그로 고정), 알릴 사람, 원인 기록 양식(관찰 사실 / 원인 / 왜 평가가 못 잡았나 / 추가한 과제 / 옮긴 층).

**검증**
- 깨끗한 환경에서 README대로 설치·실행된다.
- 최종 확인용 평가가 미리 정한 승인 기준을 통과한다.
- 릴리스 목록의 해시와 실제 실행 중인 구성요소가 일치한다(실행 기록에 버전이 찍힌다).
- 되돌리기를 실제로 해 본다: 이전 태그로 돌린 뒤 새 세션의 기록에 이전 버전이 찍히는지 본다.
- 끄는 스위치를 실제로 꺼 본다.
- 조직 강제 항목을 개인 설정으로 끄려 해도 계속 적용되는지 본다.
- 운영 기록 1건을 과제로 승격해 평가 명령에 포함되는지 끝까지 돌려 본다.

**완료 기준**
- [ ] 릴리스 목록과 최종 확인용 평가 통과 결과·재현 조건이 있다
- [ ] 인수 기준 항목마다 실행해서 확인한 증거가 있고 README에 항목별 확인 방법이 있다
- [ ] 깨끗한 환경에서 문서대로 설치·실행된다
- [ ] 배포·업데이트·되돌리기 방법이 있고, 되돌리기와 끄는 스위치를 한 번 실제로 해 봤다
- [ ] 확대 단계별 넘어가는 기준과 멈추는 기준이 시작 전에 적혀 있다 (운영하지 않으면 "해당 없음"과 이유)
- [ ] 운영 지표, 신고 경로, 사고 대응 절차와 담당자가 정해졌다 (운영하지 않으면 "해당 없음"과 이유)
- [ ] 주간 회고와 평가셋 승격 담당자가 정해졌고 기록 1건 이상을 평가 사례로 승격했다

**흔한 함정:** 프롬프트·스킬을 리뷰와 평가 없이 운영에서 바로 고치기, 배포 전후 수치만 비교하기, 최종 확인용을 릴리스마다 다시 쓰기, 오프라인 평가가 통과했으니 운영 기록은 안 읽기, 자기개선이 채택한 변경을 운영에 자동으로 흘려보내기(S6의 채택은 릴리스 후보이지 배포가 아니다), 시스템 프롬프트·도구 정의를 자주 조금씩 바꾸기(바꿀 때마다 모든 사용자의 캐시가 식는다. 묶어서 낸다), 모델이 바뀌었는데 평가와 설정을 그대로 두기.

**순서와 병렬:** 릴리스 고정 → 최종 확인 → 쓰기 없는 재생 → 시범 운영 순서는 지킨다. 배포 문서, 신고 경로, 사고 절차 작성은 그 사이에 동시에 한다.

## 2. 전체가 끝났다는 기준

아래가 모두 참이면 첫 버전이 끝난 것이다. 그 뒤는 운영 루프(S8 → S1 승격 → S6·S7)가 계속 돈다.

1. S0에서 정한 성공 지표를 **최종 확인용 평가**에서 충족한다
2. 정책 위반이 0건이고, 차단 시험이 전부 막힌다
3. 깨끗한 환경에서 문서대로 재현된다
4. 모든 실행이 기록되고, 실패 지점을 기록에서 찾을 수 있다
5. 개선이 "측정 → 한 가지 변경 → 재측정 → 판정"으로 한 번 이상 돌았다
6. 되돌리기를 실제로 해 봤다
7. 평가 데이터·지침·검사·메모리의 담당자가 있다

## 3. 인수 기준과의 관계

완성품이 통과해야 하는 평가 기준 15개 항목(40점)과 단계의 대응은 `harness/CRITERIA.md`에 있다. S0에서 성공 지표를 정할 때 함께 보고, S8에서 `criteria-check` 스킬로 항목마다 증거를 확인한다. 기한이 짧으면 `CRITERIA.md`의 "기준만 놓고 본 진행 순서"를 따른다.

## 4. 진행 도구

- `bash harness/scripts/phase.sh`: 단계별 상태(완료, 진행 중, 지금 시작할 수 있는 것, 선행 단계 대기)를 보여준다.
- `bash harness/scripts/start-phase.sh <번호>`: 단계 산출물 템플릿을 `design/`에 만든다. 선행 단계가 안 끝났으면 거절한다.
- 단계 산출물의 "완료 기준" 체크박스가 모두 체크되면 그 단계는 완료로 판정된다.

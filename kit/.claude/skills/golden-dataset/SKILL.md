name: golden-dataset
description: 에이전트 평가용 과제(시험지)를 과거 이슈·PR, 개발자 인터뷰, 운영 기록에서 만들어 에이전트용 파일과 채점자용 파일로 나누고, 과제마다 검증한 뒤 개발용·최종 확인용으로 동결한다. 평가를 처음 시작할 때, 고치려는 문제점이 생겼을 때, 운영 실패를 평가셋으로 승격할 때, S1 단계에서 사용. 채점이나 결과 비교는 agent-eval이 맡는다.
---

<purpose>
무엇이 끝나야 완료인지 담당자와 합의하고, 누가 봐도 같은 통과/실패가 나오는 과제로 적는다. 정답은 모델에게 맡기지 않는다.
형식, 검증 표, 규모의 세부와 근거는 `harness/reference/eval.md` 1·2·3·6절에 있다. 이 스킬과 값이 다르면 그 문서가 기준이다. (제안값)은 출처 없이 정한 기본값이고, 나머지 숫자의 출처는 그 문서 8절에 있다.
</purpose>

<procedure>
1. **완료 기준 합의:** 담당자에게 한 번에 하나씩 묻는다. 완료 기준, 요청 주체, 처리하면 안 되는 경우, 정보 부족 시 응답, 도구 실패 시 허용 범위. 답을 지어내지 않는다.
2. **단위와 규모를 정한다.** 기능이 아니라 고치려는 문제점으로 묶는다(예: "도구 호출이 너무 잦다"). 먼저 5건(제안값, 연기 시험 셋)으로 과제 형식·격리·채점이 끝까지 도는지 확인한다. 개선 여부를 판정하려면 개발용을 20건 이상으로 늘린다. 5건으로 끝낼 거면 `design/01-eval.md`에 최소 버전이라고 적는다. 그 경우 "개선"이라고 쓸 수 없고 과제별 전후 결과만 보고한다. 아직 못하는 작업(능력)과 이미 되는 작업(회귀)을 `suite`로 구분한다.
3. **초안 → 피드백 반복:** 모델은 요청문 초안과 변형을 만드는 데만 쓴다. 통과 조건, 문서에 없는 예외, 여러 문서를 조합해야 하는 정답은 담당자가 채운다. 담당자가 정답을 못 주면 간이 버전을 배포해 기록을 쌓고 그걸 재료로 쓴다.
4. **과제로 쓴다.** 질문·답 형식이 아니다. 파일을 둘로 나눈다.
   - 에이전트용: `repo.base_commit`(수정 직전 커밋), `request`, `environment`(준비·초기화, 네트워크, 자원, 턴·시간·비용 한도), `family`, `suite`, `type`
   - 채점자용(에이전트 실행 환경에 두지 않는다): `tests.test_patch`, `tests.fail_to_pass`(수정 전 실패 → 정답 변경 뒤 통과, 1개 이상), `tests.pass_to_pass`(전후 모두 통과), `reference_patch`(사람이 만든 정답 변경), `allowed_paths`, `protected_paths`, `must_not`, `order`, `expected_behavior`, `validation`, `metadata`(출처, 검수자, 버전)
   - 과거 PR에서 만들 때: 수정 직전 커밋에서 테스트를 돌리고, 정답 변경을 적용해 다시 돌려 두 목록을 가른다.
   - 요청문에 해답이 들어 있으면 지운다. 숨긴 테스트가 요구하는 이름·경로·동작이 요청문에서 읽히지 않으면 요청문이나 테스트를 고친다.
   - 정답 경로 하나를 강제하지 않는다. 꼭 지킬 것만 제약으로 적는다: `must_not`(금지 행동)과 `order`(의존 관계가 있는 순서만. 승인 뒤 첫 수정, 마지막 수정 뒤 테스트 실행). "기대 도구 목록"은 적지 않는다. 독립적인 조회 순서도 적지 않는다.
5. **정상만 넣지 않는다.** 되물어야 하는 요청, 거절해야 하는 요청, 권한 없음, 도구 실패 뒤 미완료 안내, 환경 변형(일시 오류, 응답 손실), **한 조건만 바꾼 경계 사례 쌍**을 넣는다. 유형마다 통과 조건을 적는다(예: 되묻기는 "수정 없이 질문으로 끝남"). 빈 변경이 성공으로 세어지는 길이 없는지 본다.
6. **과제를 검증한다.** 통과하지 못한 과제는 평가셋에 넣지 않는다. 결과는 `validation`에 적는다.
   - 정답 변경으로 3회(제안값) → 매번 통과. 아무것도 안 바꾼 상태 → 실패.
   - 수정 직전 상태에서 숨긴 테스트만 3회 → 결과가 갈리는 테스트는 목록에서 뺀다. `fail_to_pass`가 0개가 되면 과제를 버리거나 테스트를 다시 쓴다.
   - 테스트를 지우거나 건너뛰게 한 변경 → 실패(정책 위반). 특정 입력만 분기해 맞춘 변경 → 실패(통과하면 테스트가 약하다). 다른 방식으로 푼 정답 → 통과(실패하면 테스트가 지나치게 구체적이다).
   - 다른 담당자가 요청문만 보고 통과 조건을 적어, 숨긴 테스트의 요구와 맞는지 본다.
   - 누출 점검: 요청문 속 해답, 수정 시점 이후 git 기록, 네트워크, 에이전트가 고칠 수 있는 테스트, 시도 사이에 넘어가는 메모리.
7. **운영 기록 승격:** 반복되고, 재현 가능하고, 정답을 정의할 수 있는 것만 올린다. 사용자가 신고한 실패가 먼저다. 비식별화하고, 지금 에이전트로 실패를 재현하고, 기대 기준은 다시 검수받고, 6번 검증을 거친다. 원본 기록 ID를 `metadata.promoted_from_trace`에 적어 평가 때 같은 사례의 경험 메모리를 뺄 수 있게 한다. 실패 사례만 넣지 말고 같은 유형의 "해야 하는 경우"를 짝으로 넣는다. 지금 실패하면 능력, 고친 뒤 매번 통과하면 회귀로 분류한다.
8. **분리와 동결:** 묶음(family) 단위로 개발용과 최종 확인용을 나눈다. 같은 묶음은 같은 쪽에 둔다. 최종 확인용은 수정에 쓰지 않는다. 열어 본 날짜·버전·사람을 `design/01-eval.md`에 적고, 결과를 보고 에이전트를 고쳤다면 그 셋은 개발용으로 내리고 새 사례로 채운다. 데이터 버전과 파일 해시를 `design/01-eval.md`에 적는다. 과제를 넣거나 고치면 새 버전이고, 비교할 양쪽을 모두 새 버전으로 다시 잰다.
</procedure>

<anti_patterns>
- 모델이 만든 정답을 검수 없이 쓰기
- 요청문과 정답을 같은 파일에 두거나, 채점자용 파일을 에이전트가 읽을 수 있는 곳에 두기
- 이슈 원문을 그대로 요청문으로 쓰기(해답이 들어 있거나 테스트가 요구하는 것이 빠져 있다)
- 정답 변경으로 통과하는지 확인하지 않은 과제 넣기
- 여러 번 돌려 0%인 과제를 "어려운 과제"로 두기(깨진 과제인지 먼저 확인한다)
- 정답 도구 목록이나 호출 순서를 통과 조건으로 적기
- 결과를 본 뒤 최종 확인용으로 다시 고치기
- 질문·답 3컬럼으로 과정 문제를 평가하려 하기
</anti_patterns>

---
name: golden-dataset
description: 에이전트 평가용 시험지(Golden Set)를 과거 이슈·PR, 개발자 인터뷰, 운영 기록에서 만들어 eval/dev.jsonl과 eval/holdout.jsonl로 동결한다. 평가를 처음 시작할 때, 고치려는 문제점이 생겼을 때, 운영 기록을 골든으로 승격할 때, S1 단계에서 사용. 채점이나 결과 비교는 agent-eval이 맡는다.
---

<purpose>
"정답지는 LLM에만 맡기면 50~60점짜리 일반 문제가 된다"(5일차 1강). 무엇이 끝나야 완료인지 담당자와 합의하고, 판정 가능한 시나리오로 적는다.
</purpose>

<procedure>
1. **완료 기준 합의:** 담당자에게 한 번에 하나씩 묻는다. 완료 기준, 요청 주체, 처리하면 안 되는 경우, 정보 부족 시 응답, 도구 실패 시 허용 범위. 답을 지어내지 않는다.
2. **데이터셋 단위를 정한다.** 기능이 아니라 고치려는 문제점으로 묶는다(예: "툴 호출이 너무 잦다" → 궤적 데이터셋). 처음엔 5건 정도로 시작한다(5일차 3·7강).
3. **초안 → 피드백 반복:** LLM으로 초안을 만들고 담당자 피드백을 여러 번 반영한다. 문서에 없는 예외, 여러 문서를 조합해야 하는 정답은 담당자가 채운다. 담당자가 정답을 못 주면 간이 버전을 배포해 기록을 쌓고 그걸 재료로 쓴다.
4. **시나리오로 쓴다.** 질문·답 형식이 아니다. 코딩 에이전트용 한 건의 구성:
   - `repo_commit`, `request`: 에이전트에 주는 것만(저장소 스냅샷과 요청문)
   - `expected`: 평가자 전용. 통과해야 할 테스트, 최종 상태
   - `must_not`: 범위 밖 파일 수정, 테스트 삭제·건너뛰기, 시크릿 접근 같은 금지 행동
   - `order`: 의존 관계가 있는 순서만(계획 승인 → 수정 → 테스트 실행). 독립적인 조회 순서는 자유
   - `metadata`: 출처(이슈·PR·인터뷰·기록), 검수자, 버전, family(같은 사례 묶음)
   - 정답 경로 하나를 강제하지 말고 지켜야 할 제약을 적는다. 기대 상태와 숨긴 테스트는 에이전트가 읽을 수 없는 곳에 둔다.
5. **정상만 넣지 않는다.** 거절, 추가 질문, 정보 부족, 권한 없음, 도구 실패 후 미완료 안내, 환경 변형(일시 오류, 응답 손실), **한 조건만 바꾼 경계 사례 쌍**을 넣는다.
6. **운영 기록 승격:** 반복되고, 재현 가능하고, 정답을 정의할 수 있는 것만 승격한다. 비식별화하고, 기대 기준은 다시 검수받고, 수정 전 실패를 재현해 본다. 대표 표본(성공 포함)과 실패 표본을 나눠 모은다.
7. **분리와 동결:** family 단위로 dev와 holdout을 나눈다. holdout은 수정에 쓰지 않고 최종 확인에만 쓴다. 파일 해시와 버전을 `design/01-eval.md`에 적는다. 시나리오를 바꾸면 새 버전이고, 비교할 두 버전을 모두 다시 돌린다.
</procedure>

<anti_patterns>
- LLM이 만든 정답을 검수 없이 쓰기
- `expected_output`을 에이전트 프롬프트에 넣기
- 결과를 본 뒤 holdout으로 다시 고치기
- Q&A 3컬럼으로 궤적 문제를 평가하려 하기
</anti_patterns>

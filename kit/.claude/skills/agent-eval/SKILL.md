---
name: agent-eval
description: 동결된 평가셋으로 에이전트를 실행해 결과 상태를 기준으로 채점하고, 채점기를 반례로 검증하고, 기준(baseline)과 후보(candidate)를 같은 조건에서 과제별로 짝지어 비교해 개선 / 차이 없음 / 회귀 / 무효로 판정하고 design/01-eval.md를 채운다. S1 단계, 프롬프트·스킬·도구·모델을 바꾼 뒤 "나아졌나"·"평가 회귀가 없나" 확인, 변경 반영 전 회귀 검사, 스킬 호출(Activation) 평가에 사용. 평가셋 만들기는 golden-dataset이 맡는다.
---

<principles>
- 결과가 기준이고 과정은 관문이다. 통과는 결과 상태(Outcome)로 정한다. 과정(Trajectory)에서 통과/실패로 보는 것은 금지 행동과 의존 관계가 있는 순서뿐이다. 다른 길로 푼 정답을 떨어뜨리면 채점기가 틀린 것이다. 응답(Final Response)은 따로 본다.
- 결과 상태는 환경에서 읽는다(작업 트리, 테스트 결과, 기록). 에이전트의 자기 보고를 결과로 쓰지 않는다. 채점자용 파일은 에이전트에 보내지 않고, 에이전트가 고칠 수 없는 곳에 둔다.
- 테스트·변경 파일·기록으로 가려지는 것은 코드, 의미 판단만 모델 채점(Judge), 이견은 사람이 맡는다.
- 정책 위반(금지 행동, 순서 규칙)은 필수 관문이다. 다른 점수의 평균으로 상쇄하지 않는다.
- 판정 상태는 통과 / 실패 / 근거 부족 / 채점기 오류 / 환경 오류다. 누락을 분모에서 지우지 않는다.
- 한 번 돌린 결과로 판정하지 않는다. 과제마다 여러 번 돌리고, 표본은 과제로 세고, 같은 과제끼리 짝지어 비교한다.
- 한 번의 비교 안에서는 조건(데이터 버전, 환경, 에이전트 설정, 채점기 버전, 반복 수, 판정 규칙)을 잠그고 하나만 바꾼다. 판정 규칙의 값은 결과를 보기 전에 적는다.
- 점수가 움직이면 기록을 읽는다. 실패는 에이전트 잘못 / 과제·채점기 결함 / 환경 문제로 먼저 나눈다.
</principles>

<reference>
채점기 설계와 판정 상태는 `harness/reference/eval.md` 4절, 판정 조건과 계산 예시는 5절, 비용 층은 7절에 있다. 이 스킬과 값이 다르면 그 문서와 `design/01-eval.md`에 적힌 값이 기준이다. (제안값)은 출처 없이 정한 기본값이고, 나머지 숫자의 출처는 그 문서 8절에 있다.
</reference>

<procedure>
1. **채점기 먼저 검증:** 일부러 만든 반례로 채점기를 돌린다. 순서만 다른 정상 실행·사람이 만든 정답 변경 → 통과. 아무것도 안 바꾼 상태·턴 한도 초과 → 실패. 승인 없이 수정·범위 밖 수정·테스트 파일 수정 → 실패(정책 위반). 기록 삭제 → 근거 부족. 실패→통과 목록이 빈 채점자용 파일 → 채점기 오류. 자원 상한에 걸려 죽은 실행 → 환경 오류. 하나라도 어긋나면 채점기부터 고친다.
2. **모델 채점:** 최소 버전에서는 쓰지 않고 코드 채점만으로 통과를 정한다. 쓴다면 기준 하나에 판정 하나, 출력은 통과 / 실패 / 판단 불가와 이유·근거 단계(JSON)로 고정한다. 판단 불가는 근거 부족으로 처리한다. 점수 척도는 통과/실패로 답이 안 되는 기준에만 쓰고, 그때는 등급마다 관찰 가능한 기준을 적는다. 사람이 통과/실패로 라벨한 사례(30건쯤에서 시작, 목표는 각 50건 이상)로 잘못 통과와 잘못 탈락을 따로 잰다. 라벨의 일부만 프롬프트 예시로 쓰고 나머지로 잰다. 같은 입력을 여러 번 넣어 판정이 바뀌는 비율을 본다. 가능하면 평가 대상과 다른 모델을 쓴다. 합격선에 못 미친 기준은 통과/실패에 넣지 않고 참고로만 남긴다.
3. **실행:** 유료 실행 전에 규모(과제 수 × 반복 × 비교 대상 수 = 시도 수, 시도 수 × 시도당 평균 호출 수·비용)를 한 줄로 알린다. 시도마다 새 환경에서 시작한다(작업 트리, 캐시, 세션, 수정 시점 이후 git 기록 제거, 경험 메모리는 고정 스냅샷). 에이전트가 끝나면 결과 변경을 뽑고, 보호 경로를 원본으로 되돌리고, 숨긴 테스트를 적용한 뒤 돌린다. 자원 상한이나 인프라 장애로 죽은 시도는 환경 오류, 에이전트 예산(턴·시간·비용)을 넘긴 시도는 실패다. 환경 오류는 정한 횟수만큼 다시 돌리고 재실행 사실을 남긴다. 기준과 후보는 가능하면 같은 시간대에 번갈아 돌린다. 잠금 항목과 시도별 판정을 관측 플랫폼과 `eval/results/<데이터 버전>-<날짜>.jsonl`에 남긴다.
4. **채점:** 판정 순서는 유효성 → 정책 관문 → 결과(`fail_to_pass` 전부 통과, `pass_to_pass` 전부 통과) → 응답이다. 전부 통과해야 과제 통과다. 순서 규칙은 같은 대상의 모든 쓰기 시도(실패·차단 포함)에 적용한다.
   - 과정 통계(턴 수, 도구 호출 수·종류, 재시도·복구, 단계 도달)는 진단 지표로 따로 기록하고 통과/실패에 넣지 않는다.
   - 정답 도구 목록과의 일치율(Precision/Recall)은 정답 경로 하나를 전제하므로 통과/실패에 쓰지 않는다. 꼭 불러야 하는 도구는 순서 규칙으로, 부르면 안 되는 도구는 금지 행동으로 판정한다.
   - 겨냥한 문제가 과정 자체일 때(예: 도구 호출 수 줄이기)는 그 통계를 지연·비용처럼 보조 지표로 비교한다.
   - 스킬을 평가할 때는 불려야 할 요청과 불리면 안 될 요청으로 호출 여부(Activation)를 따로 본다.
5. **실패 분석:** 통과 기록과 실패 기록을 읽는다. 과제·채점기 결함이나 환경 문제면 평가를 고치고 양쪽을 다시 채점한다. 에이전트 잘못이면 최초 실패 지점을 찾고 증거(식별자, 관찰 사실, 위반 기준, 원인 가설, 수정 제안, 검증 계획)를 쓴다. 수정 지점을 고른다: 도구 설명 / 스키마·검증 코드 / 실행 가드 / 오류 계약 / 중단 조건 / 정답 기준. 모든 것을 시스템 프롬프트로 고치지 않는다. 여러 번 돌려 0%인 과제는 깨진 과제인지 먼저 확인한다.
6. **비교 보고:** 시도 성공률, 매번 통과율(pass^k), 유효하지 않은 시도 비율, 정책 위반 수, 묶음별 개선·회귀, p50/p95 지연, 통과 1건당 비용을 적는다.
   - 과제 점수 = 통과한 시도 수 ÷ k. 과제마다 d = 후보 점수 − 기준 점수, D = d의 평균, 95% 구간 = D ± t × (d의 표준편차 ÷ √과제 수).
   - 반복 시도를 독립 사례로 세지 않는다. 같은 묶음의 과제가 여럿이면 묶음 평균을 한 표본으로 센다.
   - 좋아진 과제 수와 나빠진 과제 수, D와 구간, 흔들림 폭(같은 조건 재실행 차이)을 함께 쓴다.
   - 한 번이라도 통과한 비율(pass@k)은 참고로만 적는다. 사람이 결과를 고르지 않는 작업에서 주 지표로 쓰면 실제보다 좋아 보인다.
7. **판정:** `design/01-eval.md`에 미리 적은 값으로, 위에서부터 먼저 걸리는 것으로 정한다.
   - 무효: 어느 한쪽이라도 환경 오류·채점기 오류·근거 부족 시도 비율이 한도를 넘거나 잠금 항목이 다르다. 고치고 다시 잰다.
   - 회귀: 후보에 정책 위반이 1건이라도 있다 / 매번 통과하던 과제의 실패가 추가 실행으로 확정됐다 / 구간 상한이 0보다 작다 / D가 −허용폭 이하다.
   - 개선: 구간 하한이 0보다 크고 D가 흔들림 폭보다 크다.
   - 차이 없음: 그 밖. "좋아졌다"고 쓰지 않는다. 지연·비용·단순함이 나아졌을 때만 채택을 권한다.
   - "평가 회귀가 없다"는 판정이 개선 또는 차이 없음이라는 뜻이다. 과제가 20건 미만(제안값)이면 구간을 내지 않고 정책 위반과 확정된 실패만 본 뒤 "차이 없음(규모 부족)"이라고 쓴다. "개선"은 쓰지 않고 과제별 전후 결과를 표로 보고한다.
   - 채택 조건은 순서대로 본다: 판정 유효 → 정책 위반 0 → 회귀 아님 → 목표 지표 개선 또는 지연·비용 개선 → 최종 확인용에서 회귀 아님.
</procedure>

<cost>
범위를 층으로 나눈다. 변경할 때마다 연기 시험 셋 5건 1회(제안값, 코드 채점만), 변경을 반영할 때마다 개발용 전체 3회(채택 판정은 5회), 출시 전 최종 확인용 한 번. 잠금 항목이 같은 기준 결과는 다시 쓰되, 모델이나 환경이 바뀌었을 수 있으면 다시 잰다. 운영 중 평가는 모든 요청을 채점하지 않는다. 표본을 뽑거나 "확인 필요"로 표시된 기록 위주로 고르고 예상 비용을 먼저 계산한다.
</cost>

<when_to_rerun>
모델, 스킬·프롬프트·도구 계약이 바뀌었을 때, 운영에서 새 실패 기록이 생겼을 때 다시 돌린다. 과제나 채점기의 결함을 고쳤으면 버전을 올리고 양쪽을 새 버전으로 다시 채점한다. 한쪽만 새 버전으로 낸 수치와 비교하지 않는다. 흔들림 폭은 모델이나 환경이 바뀔 때마다 다시 잰다.
</when_to_rerun>

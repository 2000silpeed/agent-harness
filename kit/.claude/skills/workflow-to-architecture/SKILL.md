---

<purpose>
구조를 먼저 고르지 않는다. 업무에서 사람이 판단하는 지점을 찾고, 그곳에만 에이전트를 둔다.
</purpose>

<step_workflow>
1. `start-phase.sh 01`. 사용자와 대화하며 현재 업무를 **5단계 이하**로 적는다. 6단계 이상이면 합친다.
2. 단계마다 꼬리표를 붙인다.
   - 판단: 여러 선택지 중 고르기 → 디시전 모델이나 작은 모델 후보
   - 생성: 문장·문서 만들기 → LLM
   - 규칙: 정해진 규정·계산 → 코드
   - 조회: 데이터 가져오기 → 도구
   - **판단과 생성이 함께 있는 구간**이 에이전트(서브에이전트) 후보다. 단, "무조건"은 없다.
3. 돈·민감정보·외부 쓰기 단계에는 HITL을, 서로 독립인 단계에는 병렬을 표시한다.
</step_workflow>

<step_architecture>
1. `start-phase.sh 02`. 단계마다 CODE / RULE / API / MODEL / AGENT를 정한다.
2. 기본값은 **싱글 에이전트 + 스킬**이다. 멀티를 제안하려면 아래 중 하나가 있어야 한다.
   - 컨텍스트 경계: 탐색이나 대량 읽기가 메인 컨텍스트를 채운다
   - 측정된 실패: 스킬을 붙였더니 품질이 떨어졌다는 기록
   - 지연: 독립 작업을 병렬로 돌려야 목표 지연을 맞춘다
3. 패턴은 순차·병렬·분기·루프로 번역해서 설명한다.
   - Router/Supervisor: 분기
   - Plan-and-Execute: 계획 → 실행 루프 + 관찰·재계획
   - Swarm/Handoff: 대화 이전. 체어맨·투표·최대 턴 같은 종료 장치가 필수다
4. 서브에이전트가 있으면 입출력 계약을 적는다(입력 task_id, goal, facts, allowed_tools / 출력 status, facts, evidence_refs, uncertainty).
5. 상태 키, 종료 조건(성공·보류·사람 전환·실패)을 적는다.
6. **확장 지점을 고른다.** 기능마다 스킬 / 서브에이전트 / 훅 / 미들웨어 / 도구 / 외부 서비스 중 어디에 꽂을지 고르고 한계를 적는다. 사용하는 프레임워크의 문서와 코드로 확인하고, 둘이 다르면 코드를 따른다.
7. **하네스 6책임 표를 채운다**(Day06): 지침, 도구, 실행 제어, 상태, 검증, 기록마다 "프레임워크가 이미 하는 것 / 추가할 것 / 근거 수준"을 적는다. 평가기·정답·테스트·권한 정책 같은 신뢰기반의 위치를 따로 적는다.
8. 결정마다 `design/decisions.md`에 한 줄을 남긴다.
</step_architecture>

<reference_case>
배달앱 메뉴 태깅(3일차 3강): 도구 + 긴 프롬프트 → 프롬프트 3만 토큰 → 대카테고리별 스킬 약 20개 → 라우팅 컬럼을 미리 계산 → 데이터 사전 조회 + 캐시 → 컨텍스트 격리를 위해 카테고리별 개별 에이전트. 단계를 잘게 나눠 두었기 때문에 모델을 31B에서 8B로 바꿀 때도 대응할 수 있었다.
</reference_case>

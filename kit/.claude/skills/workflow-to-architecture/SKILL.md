---
name: workflow-to-architecture
description: 코딩 에이전트가 요청 한 건을 처리하는 흐름을 5단계 이하로 정하고, 단계 전환을 판정하는 코드, 단계별 담당(코드·모델·서브에이전트·사람), 쪼갬 판단, 구성요소 표, 종료 조건·예산을 design/02-baseline.md에 적는다. S2 단계, "어디를 에이전트로 만들까", 서브에이전트로 쪼갤지 고민할 때 사용. 구현 코드 작성에는 쓰지 않는다.
---

<purpose>
구조를 먼저 고르지 않는다. 요청이 처리되는 흐름에서 판단이 필요한 지점을 찾고, 그곳에만 모델을 둔다. 부품마다 "모델이 혼자서는 무엇을 못 해서 넣었나"를 적어 나중에 뺄 수 있게 한다.
</purpose>

<procedure>
1. `bash harness/scripts/start-phase.sh 2`로 산출물을 만든다. `harness/METHOD.md`의 S2 절을 읽는다.
2. 요청 한 건의 흐름을 **5단계 이하**로 적는다. 기본형은 요구 확인 → 계획·리뷰·승인 → 구현 → 검증 → 보고·학습이다. 대상 작업에 맞게 고친다.
   - 단계 전환마다 **코드가 확인하는 것**을 적는다(승인 기록, 테스트 종료 코드, 변경 파일 범위). 모델의 "다 했다"로 넘기지 않는다.
   - 계획에는 산출물·수정 대상·검증 방법까지만 담는다. 구현 세부는 담지 않는다.
   - 버그 수정이면 구현 앞에 재현(실패하는 테스트나 스크립트)을 둔다.
3. 단계마다 꼬리표를 붙이고 담당을 정한다.
   - 규칙(테스트 실행, 린트, 형식 검사, 범위 확인) → 코드
   - 조회(파일 찾기, 이슈 읽기) → 도구
   - 판단(분류, 선택, 예/아니오) → 코드나 작은 모델
   - 생성(계획, 코드, 요약) → 모델
   - 판단과 생성이 함께 있는 구간만 에이전트 루프로 둔다.
4. 검증 순서를 정한다: 코드(테스트·린트) → 작성 과정을 보지 않은 독립 리뷰어 → 사람. 리뷰어에게 줄 범위를 적는다("정확성에 영향을 주는 것만").
5. 기본은 **싱글 에이전트**다. 쪼개도 되는 경우는 넷뿐이다.
   - 읽기 전용 탐색: 질문이 분명하고 읽을 양이 많고 원문을 메인이 다시 쓰지 않는다
   - 독립 리뷰: 작성 컨텍스트를 공유하지 않고 편집 도구가 없다
   - 시끄러운 출력 격리: 전체 테스트 실행, 넓은 검색
   - 서로 다른 파일·체크아웃의 독립 작업
   쓰기는 한 번에 한 에이전트다. 쪼개려면 싱글과 같은 조건으로 비교한 수치(성공률, 토큰, 지연)를 적고, 성공률이 같으면 싱글을 택한다.
6. 서브에이전트를 두면 위임 양식을 적는다: 목표, 출력 형식, 쓸 도구, 하지 말 것, 노력 상한(도구 호출 수), 반환 크기 상한. 큰 산출물은 파일로 쓰고 경로만 돌려주게 한다.
7. 구성요소 표를 쓴다: 구성요소 / 가정 / 끄는 방법. 기반이 기본으로 켜 두는 것(S0에서 뽑은 목록)부터 채운다.
8. 종료 상태(완료, 보류, 사람에게 넘김, 예산 초과, 무진전 중단, 실패), 예산(턴·시간·비용·재시도), 무진전 감지 조건을 적는다.
9. 대상 작업이 한 컨텍스트 창을 넘을 수 있으면 인계 산출물(상태 파일, 진행 메모, 커밋, 기동·검사 스크립트)과 세션 시작·끝 절차를 정한다.
10. 기록 형식은 `harness/reference/trace.md`를 따라 "관측" 절에 채운다. 결정마다 `design/decisions.md`에 한 줄을 남긴다.
</procedure>

<anti_patterns>
- 역할 이름(기획자, 개발자, 검수자)으로 에이전트를 나누기
- 모든 단계를 모델에게 맡기기
- 순서를 프롬프트로만 지시하기. 순서가 중요하면 코드가 강제한다
- 같은 작업 트리에 여러 에이전트가 동시에 쓰게 하기
- 서브에이전트에 한 줄짜리 지시 주기
- 범위 없는 리뷰어의 지적을 전부 반영하기
</anti_patterns>

---
name: workflow-to-architecture
description: 코딩 에이전트가 요청 한 건을 처리하는 흐름을 5단계 이하로 정하고, 단계마다 코드·모델·서브에이전트·사람 중 누가 맡을지와 종료 조건·예산을 design/02-baseline.md에 적는다. S2 단계, "어디를 에이전트로 만들까", 서브에이전트로 쪼갤지 고민할 때 사용. 구현 코드 작성에는 쓰지 않는다.
---

<purpose>
구조를 먼저 고르지 않는다. 요청이 처리되는 흐름에서 판단이 필요한 지점을 찾고, 그곳에만 모델을 둔다.
</purpose>

<procedure>
1. `bash harness/scripts/start-phase.sh 2`로 산출물을 만든다.
2. 요청 한 건의 흐름을 **5단계 이하**로 적는다. 기본형은 요구 확인 → 계획·리뷰·승인 → 구현 → 검증 → 보고·학습이다. 대상 작업에 맞게 고친다.
3. 단계마다 꼬리표를 붙이고 담당을 정한다.
   - 규칙(테스트 실행, 린트, 형식 검사, 범위 확인) → 코드
   - 조회(파일 찾기, 이슈 읽기) → 도구
   - 판단(분류, 선택, 예/아니오) → 코드나 작은 모델·판단 전용 모델
   - 생성(계획, 코드, 요약) → 모델
   - 판단과 생성이 함께 있는 구간만 에이전트 루프로 둔다.
4. 기본은 **싱글 에이전트**다. 서브에이전트는 아래 근거가 있을 때만 둔다.
   - 컨텍스트 경계: 코드 탐색처럼 메인 컨텍스트를 채우는 일
   - 독립 관점: 계획·코드 리뷰어처럼 작성자와 다른 컨텍스트가 필요한 일
   - 측정된 실패나 지연: 기준선에서 확인된 문제
5. 서브에이전트를 두면 계약을 적는다: 입력(목표, 사실, 허용 도구) → 출력(상태, 사실, 근거 위치, 불확실한 점).
6. 사람이 승인하는 지점, 종료 상태(완료, 보류, 사람에게 넘김, 실패), 예산(턴·시간·재시도)을 적는다.
7. 결정마다 `design/decisions.md`에 한 줄을 남긴다.
</procedure>

<anti_patterns>
- 역할 이름(기획자, 개발자, 검수자)으로 에이전트를 나누기
- 모든 단계를 모델에게 맡기기
- 순서를 프롬프트로만 지시하기. 순서가 중요하면 도구나 훅이 강제한다.
</anti_patterns>

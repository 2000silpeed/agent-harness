<decide>
- API vs 직접 서빙: 비용(감가상각, 모델이 금방 바뀌는지), 보안(코드·데이터가 밖으로 나가도 되는지), 커스터마이징(미세조정·특수 설정 필요성)으로 판단하고 근거를 `design/decisions.md`에 남긴다.
- API를 쓰더라도 아래 "컨텍스트·캐시" 절은 그대로 적용된다.
</decide>

<capacity>
1. 모델 카드·config에서 파라미터 수, 텐서 dtype, 레이어 수(full attention 층), KV 헤드 수, 헤드 차원, 최대 컨텍스트를 읽어 적는다. 저장소 용량이 파라미터 수와 안 맞으면 배포 정밀도(FP8 등)를 확인한다.
2. 가중치 = 파라미터 수 × dtype 바이트(BF16 2, FP8 1, 4비트 0.5).
3. KV/토큰 = 2 × 층 수 × KV 헤드 × 헤드 차원 × KV dtype 바이트. 요청당 KV = KV/토큰 × 목표 컨텍스트.
4. 가용 = GPU 메모리 × 사용률(여유분 남김) − 가중치 − 런타임·실행 그래프 공간. 동시 처리 수 = 가용 ÷ 요청당 KV.
5. 한 장에 안 들어가면 텐서 패럴렐로 나눈다. attention head 수가 GPU 수로 나누어떨어지는지 확인하고, **GPU당** KV 여유가 요청 1건 이상인지 따로 본다.
6. 계산을 도구에 맡기면 근거(config 값)를 함께 받아 검토한다. 띄운 뒤 기동 로그의 KV 토큰 수·최대 동시성과 대조한다. 숫자가 다르면 로그가 맞다.
</capacity>

<settings>
- 검증된 공개 레시피(모델 × 장비)를 기준선으로 쓴다. 토크나이저 모드, KV dtype, 병렬화 크기, 도구 호출·사고 과정 파서, 자동 도구 선택을 명시하고 값의 출처를 남긴다.
- 웨이트 dtype과 KV dtype은 따로 정한다. 양자화는 같은 평가셋으로 품질을 다시 잰 뒤 채택한다(반복 출력, 엉뚱한 언어가 섞이면 정밀도부터 의심). 4비트 포맷은 GPU 세대 지원을 확인한다.
- 실행 그래프 캡처 같은 엔진 최적화는 진단 목적 외에는 끄지 않는다.
- 엔진은 stateless로 둔다. 대화·도구 실행 상태는 하네스가 가진다.
</settings>

<context_and_cache>
- 고정 내용(시스템 지시, 도구 정의)은 앞에, 바뀌는 값은 뒤에. 대화 이력은 뒤에 붙이기만 한다. 중간 압축은 캐시를 깬다.
- 캐시는 TTL로 사라진다. 멀티테넌트면 캐시 격리 키를 둔다.
- 최대 컨텍스트를 그대로 쓰지 말고 실제 필요 × 동시 요청 수로 상한을 정한다. 긴 컨텍스트 요구는 하드웨어 비용과 검색·요약 같은 대안을 함께 비교한다.
</context_and_cache>

<measure>
- 지연은 TTFT(첫 토큰)와 ITL(토큰 간격)로 나눠 잰다. TTFT가 나쁘면 큐·Prefill(입력 길이, 캐시 적중)을, ITL이 나쁘면 Decode(메모리 대역폭, 배치)를 의심한다. 선점이 늘면 KV 부족이다.
- 처리량이 아니라 SLO 안에서 끝난 요청량(Goodput)으로 판단한다.
- 벤치마크는 실제 트래픽의 입출력 길이 분포와 도착률로 돌리고, 모델·하드웨어·정밀도·엔진 버전·캐시 warm/cold를 기록한다. 한 번에 한 변수만 바꾼다.
- KV 오프로드(DRAM·NVMe)는 지연과 처리량의 절충이다. 재계산 vs 불러오기 비용을 계산한 뒤 도입한다.
</measure>

name: hook-design
description: 규칙·절차를 메모리(부탁)·스킬(위임)·훅(강제)·플러그인(배포) 중 어디에 둘지 정하고, 훅이 필요하면 이벤트·판정 코드·차단 방식·우회 경로까지 설계해 .claude/hooks/에 만든다. "매번 이걸 시켜야 한다", "자꾸 까먹는다", "훅 만들어줘", 규칙이 안 지켜질 때, S5 단계에서 사용.
---

<placement>
- 같은 컨벤션을 **두 번 틀리면** → 상시 지침(프로젝트 지침 파일). 짧게, 구조화된 양식으로.
- 특정 폴더·파일에서만 필요한 규칙 → 경로 범위가 있는 규칙 파일(그 파일을 다룰 때만 로드).
- 같은 절차를 **세 번째 붙여넣게 되면** → 스킬(필요할 때 읽는 절차).
- 묻지 않아도 **매번 일어나야 하는 일** → 훅(정해진 시점에 실행되는 코드).
- **다른 저장소에도** 같은 구성 → 플러그인으로 묶어 배포.
- 메모리와 스킬은 모델이 읽고 따르는 가이드라 보장이 아니다. 예외 없이 막아야 하면 훅과 권한 deny 설정으로 옮긴다.
</placement>

<hook_procedure>
1. **시점을 정한다.** 세션 시작 / 입력 제출(모델 전달 전) / 도구 전 / 도구 후 / 서브에이전트 종료 / 컴팩트 전·후 / 알림 / 멈춤 중 "언제 동작해야 하는가". 세션 종료 이벤트에는 중요한 정리를 맡기지 않는다.
2. **역할을 정한다.** Pre는 막고, Post는 고치게 하고(이미 실행됨, 요약·기록·피드백), Stop은 끝내기 전에 확인한다. 검사는 훅, 해결은 스킬이다. 훅 메시지에 고칠 방법(어떤 스킬을 쓰라)을 안내한다.
3. **판정은 코드로.** 결정적 규칙(경로, 확장자, 이름 규칙, 문자열 패턴)으로 판정한다. 맥락 판단이 꼭 필요할 때만 작은 모델에 yes/no를 묻는다.
4. **차단 방식을 명시한다.** 명시적 차단 신호(exit 2 또는 JSON deny)만 막는다. exit 1, 스크립트 오류, 타임아웃, 잘못된 출력은 기본적으로 통과될 수 있다. 입력을 못 읽으면 막을지(fail closed) 통과시킬지 정해 코드에 적고, 핵심 금지는 권한 deny 설정으로 이중화한다.
5. **우회 경로를 적는다.** 매처를 거치지 않는 경로(셸 명령으로 파일 쓰기, 직접 호출하는 명령)를 찾아 표로 남기고, 막지 못하는 부분은 CI로 넘긴다. 같은 이벤트에 매칭된 훅들의 결정 병합 규칙을 확인한다.
6. **시험한다.** 정상 입력 → 통과, 위반 입력 → 차단, 깨진 입력 → 정한 대로(fail closed/open) 동작하는지 stdin으로 직접 넣어 확인한다. 이벤트 이름·입력 필드·차단 방식은 쓰는 도구의 공식 훅 문서로 확인한다.
7. **기록한다.** `design/05-control.md`의 규칙표에 규칙, 둘 곳, 이유, 우회 경로를 남긴다. 예시는 `.claude/hooks/`(plan_gate, test_after_edit, prompt_reminder)를 참고한다.
</hook_procedure>

<limits>
- 훅은 권한을 조일 수는 있어도 풀 수는 없다.
- 클론한 저장소의 훅도 내 PC에서 실행된다. 신뢰한 작업 공간에서만 켠다.
- Stop 훅의 두 번째 통과는 재검증 증거가 아니다. 어느 한 층도 완전하지 않으니 최종 방어선은 PR 리뷰와 CI다.
- 프로젝트 훅은 규칙이 생긴 뒤 필요가 확인되면 추가한다. 미리 예측해서 많이 만들지 않는다.
</limits>

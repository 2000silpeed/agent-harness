name: hook-design
description: 규칙·절차를 메모리(부탁)·스킬(위임)·훅(강제)·플러그인(배포) 중 어디에 둘지 정하고, 훅이 필요하면 이벤트·판정 코드·차단 신호·실패 정책·우회 경로까지 설계해 .claude/hooks/에 만들고 세 가지 입력으로 시험한다. "매번 이걸 시켜야 한다", "자꾸 까먹는다", "훅 만들어줘", 규칙이 안 지켜질 때, 훅이 안 막을 때, S5 단계에서 사용.
---

<placement>
- 같은 컨벤션을 **두 번 틀리면** → 상시 지침(프로젝트 지침 파일). 짧게, 구조화된 양식으로.
- 특정 폴더·파일에서만 필요한 규칙 → 경로 범위가 있는 규칙 파일(그 파일을 다룰 때만 로드).
- 같은 절차를 **세 번째 붙여넣게 되면** → 스킬(필요할 때 읽는 절차).
- 묻지 않아도 **매번 일어나야 하는 일** → 훅(정해진 시점에 실행되는 코드).
- **다른 저장소에도** 같은 구성 → 플러그인으로 묶어 배포.
- 메모리와 스킬은 모델이 읽고 따르는 가이드라 보장이 아니다. 예외가 0개인 규칙만 훅과 권한 차단 규칙으로 옮긴다. 강제 규칙은 적게 유지한다(가끔 잘못 발동하고, 누군가 유지해야 한다).
</placement>

<hook_procedure>
1. **시점을 정한다.** 세션 시작 / 입력 제출(모델 전달 전) / 도구 전 / 도구 후 / 서브에이전트 종료 / 컴팩트 전·후 / 알림 / 멈춤 중 "언제 동작해야 하는가". 막을 수 있는 시점은 도구 전, 입력 제출, 멈춤이다. 도구 후는 이미 실행된 뒤다. 세션 종료에는 중요한 정리를 맡기지 않는다(막을 수 없고 제한 시간이 짧다).
2. **역할을 정한다.** Pre는 막고, Post는 고치게 하고(요약·기록·피드백), Stop은 끝내기 전에 확인한다. 검사는 훅, 해결은 스킬이다. 훅 메시지에 고칠 방법(어떤 스킬을 쓰라)을 적는다.
3. **판정은 코드로.** 결정적 규칙(경로, 확장자, 이름 규칙, 문자열 패턴)으로 판정한다. 경로는 정규화한 뒤 비교한다(상대 경로, `..`, 심볼릭 링크, 대소문자). 다른 모델에게 묻는 훅은 결정적이지 않으니 맥락 판단이 꼭 필요할 때만 쓴다.
4. **차단 신호를 명시한다.** `<semantics>`의 명시적 차단 신호만 막는다. 그 밖의 종료는 전부 통과다.
5. **실패 정책을 정한다.** 막는 훅(게이트)은 고장 나면 막고(fail closed), 알리는 훅(피드백)은 고장 나면 건너뛴다(fail open). 게이트는 코드와 설정 **양쪽**에 건다: 스크립트는 모든 예외를 차단 신호로 끝내고, 설정은 "실패 시 차단"과 짧은 시간 제한을 준다. 그 설정이 듣지 않는 시점(끝내기 전 검사)의 검사는 CI에 같은 것을 둔다.
6. **우회 경로를 표로 남긴다.** 이 훅을 비켜 가는 길을 적고 막지 못하는 부분은 다른 층(권한 차단, 격리, 끝내기 전 검사, CI)에 넘긴다: 셸 명령으로 파일 쓰기, 매처에 없는 도구(노트북 편집, 외부 도구 서버), 도구 호출 없이 붙는 파일 첨부, 사람이 직접 고치기, 훅 코드와 설정 자체를 고치기. 같은 이벤트에 여러 훅이 걸릴 때의 결정 병합 규칙도 확인한다.
7. **세 가지 입력으로 시험한다.** 정상 → 통과, 위반 → 차단, 깨진 입력(배열, 문자열, 빈 입력, JSON 아님, 필드 타입 오류) → 정한 실패 정책대로. stdin에 직접 넣고 종료 코드를 표로 남긴다. 그다음 설정 검사와 실제 세션에서 위반을 한 번 시도한다(`<verification>`).
8. **기록한다.** `design/05-control.md`의 규칙표에 규칙, 둘 곳, 이유, 실패 정책, 우회 경로와 보완 층을 남긴다. 예시가 설치돼 있으면 `.claude/hooks/README.md`(파일 표, 시험 방법, 한계)를 참고한다.
</hook_procedure>

<semantics>
Claude Code 기준이다(v2.1.322 문서로 확인). 다른 기반이나 다른 버전이면 같은 항목을 그 문서로 확인해 `harness/bases/`에 적는다.

차단 신호
- **종료 코드 2**가 차단이다. 사유는 stderr에 쓴다(모델이 읽는다). 종료 코드 0은 통과다.
- **종료 코드 1, 스크립트 예외, 시간 초과, 경로 오타로 시작 실패, 깨진 출력은 통과다.** 대화 기록에 훅 오류 알림만 남는다.
- JSON으로 답할 때는 종료 코드 0에 stdout으로 JSON 객체 하나만 낸다. 도구 전(PreToolUse)의 결정은 `hookSpecificOutput.permissionDecision`에 `deny`·`ask`·`allow`로 둔다. 최상위에 두면 오류 없이 무시된다. 그 밖의 이벤트는 최상위 `decision: "block"`과 `reason`이다.
- 효과는 이벤트마다 다르다. 도구 전은 호출을 막고, 도구 후는 stderr를 모델에 보여 줄 뿐이고(성공한 호출 뒤에만 돈다), 멈춤(Stop)은 끝내기를 막아 계속 일하게 한다.

실패 정책
- 훅 설정에 `"onFailure": "block"`(v2.1.295 이상, `command`·`http` 훅)을 주면 시작 실패·0과 2가 아닌 종료 코드·시간 초과·깨진 출력도 막는다. 기본 시간 제한이 길므로(명령 훅 600초) `timeout`을 직접 준다.
- 이 설정은 멈춤 계열 이벤트와 백그라운드(`async`) 훅에는 효과가 없다.
- Stop 훅은 입력의 `stop_hook_active`가 true면 다시 막지 않는다. 연속으로 막는 횟수에 상한(8회)이 있어 결국 끝난다.

허용과 거부
- 훅의 **거부**는 모든 권한 모드에서 통한다(확인을 건너뛰는 모드에서도).
- 훅의 **허용**은 확인 창을 건너뛰게 할 뿐 권한 설정의 차단·확인 규칙을 넘지 못한다. 규칙이 없는 호출의 확인은 건너뛰게 되므로, 허용을 돌려주는 훅은 조건을 좁게 쓴다.
- 여러 훅의 결정이 다르면 deny > defer > ask > allow 순이다. 같은 이벤트의 훅은 병렬로 돌고, 하나가 막아도 나머지는 끝까지 돈다(부작용은 일어난다).
- 사람 확인이 필요한 경우는 막지 말고 묻게 한다(`ask`).

적용 범위
- 훅은 **서브에이전트의 도구 호출에도** 돈다. 입력의 `agent_id`·`agent_type`으로 구분한다. 병렬 호출이면 훅도 동시에 돈다.
- 파일을 고치는 도구는 `Edit`, `Write`, `NotebookEdit`다(`NotebookEdit`의 경로 필드는 `notebook_path`). `MultiEdit`는 현재 도구 목록에 없는 옛 이름이다. 매처는 대소문자를 가린다.
- 셸로 파일을 쓰면 파일 도구 매처의 훅은 돌지 않는다. `@`로 붙인 파일은 도구 호출이 아니라서 읽기 훅을 거치지 않는다.
- 입력 제출·멈춤 이벤트에는 매처가 없다. 입력 제출 훅은 예약 작업이나 백그라운드 서브에이전트 보고에도 돈다. 붙이는 글은 명령문이 아니라 사실 진술로 짧게 쓴다(요청마다 대화 기록에 쌓인다).
</semantics>

<verification>
1. 스크립트 단위: 정상·위반·깨진 입력을 stdin에 넣고 종료 코드를 본다. 게이트는 깨진 입력에 2, 피드백 훅은 0이어야 한다.
   `echo '[]' | python3 .claude/hooks/<훅>.py; echo "exit=$?"`
2. 설정 파일: `claude doctor`에 `Invalid settings`가 없다. 잘못된 훅 항목 하나가 그 설정 파일의 다른 항목까지 적용되지 않게 만들 수 있다(범위는 확인 필요).
3. 세션 안: `/hooks`에 등록이 보인다. 위반을 한 번 시도해 차단 사유가 대화 기록에 보이는지 본다.
4. 게이트: 스크립트 경로를 일부러 틀리게 적어도 막히는지 본다("실패 시 차단" 확인).
5. 서브에이전트에게 같은 위반을 시켜 같은 결과인지 본다.
</verification>

<limits>
- 명령 훅은 격리 밖에서 사용자 권한 전체로 실행된다. 클론한 저장소의 훅도 내 PC에서 돈다. 신뢰한 작업 공간에서만 켠다. 비대화형 실행은 신뢰 확인 없이 저장소의 훅을 돌린다.
- 훅 코드와 설정 파일은 보호 경로에 둔다. 에이전트가 고칠 수 있으면 나머지가 의미 없다.
- 반드시 지켜야 하는 규칙은 훅 하나에만 두지 않는다. 권한 차단 규칙이나 격리에 한 번, CI에 한 번 더 둔다.
- Stop 훅이 물러난 뒤의 두 번째 종료는 재검증이 아니다. 어느 한 층도 완전하지 않으니 최종 방어선은 PR 리뷰와 CI다.
- 차단 0건은 안전의 증거가 아니다. 훅이 죽어 있어도 0건이다. 시험에서 차단이 일어나는지를 본다.
- 프로젝트 훅은 규칙이 생긴 뒤 필요가 확인되면 추가한다. 미리 예측해서 많이 만들지 않는다.
</limits>

<principles>
출처: 수업 저장소 Day05_new 노트북 06(Self-Improving Agent), Day05 평가 파이프라인. 상세는 `harness/reference/eval-rsi-rules.md` §2, §6-D.
- **손잡이는 하나만 연다.** 메모리 규칙, 스킬 문서 하나, 도구 정책 JSON 중 하나를 고르고, 모델·평가기·테스트·평가셋·예산은 고정한다.
- **개선기는 신뢰기반을 못 건드린다.** 평가 코드, 정답, 테스트, 임계값, 예산은 개선 대상이 아니다.
- **결과를 본 뒤 규칙을 바꾸지 않는다.** 점수식, 판정 순서, 반복 수는 실행 전에 적어 둔다.
- **mock·scripted 결과는 개선율이 아니다.** "계약 검증"으로만 표기한다.
</principles>

<procedure>
1. `design/08-optimization.md`의 "자기개선 설정"을 먼저 채우고 사용자 확인을 받는다.
2. **실패 수집:** 이벤트 로그에서 실패 신호(도구 오류, 테스트 실패, 루브릭 needs_revision/max_iterations_reached, 리뷰 REVISE 반복, 게이트 차단)를 모은다. 실패마다 fact / hypothesis / alternative / evidence_ids를 쓴다.
3. **오염 검사:** 개선기에 보낼 입력에 정답, 임계값, holdout ID, 테스트 기대값이 있으면 호출하지 않고 멈춘다.
4. **후보 생성:** 개선기를 한 번 호출해 후보 K개(예: 3)를 선언형 형식으로 받는다. 스키마로 검증해서 형식 오류, 금지 키(기준 변경·실패 삭제·예산 증가), 현재안과 같은 후보는 `rejected`에 사유와 함께 남긴다.
5. **비교:** 현재안(항상 포함)과 후보를 같은 평가셋, 같은 모델, 같은 예산으로 돌린다. 유료 실행 전에 규모(작업 수 × 반복 × 후보 수 ≈ 호출 수)를 한 줄로 고지한다.
6. **판정 (순서 고정):**
   1. NOT_DETERMINABLE: 어느 쪽이든 평가 완료율이 90% 미만이거나 현재안에 실패가 없다. "개선 없음"이 아니라 "재지 못함"이다.
   2. HOLD: 후보에서 새 실패 유형이 생겼거나, 현재안에서 통과하던 사례가 실패한다.
   3. ADOPT: 후보의 실패 수가 현재안보다 적다.
   4. 그 밖은 HOLD.
7. **기록:** `improve/round-<n>.json`을 새 파일로 쓴다(같은 이름이면 거부). 현재 버전, 후보, 거부 사유, 비교표, 판정, 개선기 입력의 해시를 넣는다.
8. **채택:** ADOPT만 메모리·스킬에 반영하고 버전 라벨(r0→r1)을 올린다. 반영은 다음 스레드부터 보이므로 새 스레드에서 같은 종류의 작업을 돌려, 채택안이 쓰였다는 로그(`memory_retrieve` 등)를 증거로 남긴다.
9. **holdout:** 라운드를 마친 뒤 마지막에 한 번만 holdout으로 확인한다. 그 결과를 보고 다시 고치면 새 라운드다.
</procedure>

<implementation_notes>
- baseline과 candidate는 메모리·설정이 섞이지 않게 분리된 프로필(디렉터리, 에이전트 이름 등)로 돌린다.
- 메모리를 세션 시작 때 한 번만 읽는 구조라면, 반영 효과는 새 세션에서 측정한다.
- 에이전트가 메모리 파일을 직접 고칠 수 있으면 이 루프를 우회한다. 쓰기를 막거나 개선안 경로로만 받게 한다.
</implementation_notes>

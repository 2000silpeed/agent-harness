---
name: self-improve-loop
description: 실패 기록과 평가 결과에서 개선안(시스템 프롬프트의 지정 구역·스킬 문서·메모리 규칙 중 하나)을 만들고, 미리 고정한 기준으로 현재 버전과 같은 조건에서 비교해 채택·보류·기각·판정 불가를 판정한 뒤 사람이 승인한 것만 반영한다. S6 단계, "에이전트가 스스로 나아지게", 같은 실수가 반복될 때 사용. 평가셋 만들기는 golden-dataset, 채점·비교 실행은 agent-eval, 비용·속도 변경은 optimize-agent가 맡는다.
---

<references>
- 기록·개선안 형식, 고칠 수 있는 것과 없는 것, 채택 절차의 설명: `harness/reference/memory-improve.md`
- 비교 방법과 "평가 회귀가 없다"의 정의: `harness/reference/eval.md`. 이 스킬에서 다시 정의하지 않는다.
- 채우는 산출물: `design/06-improve.md`. 라운드 기록은 `improve/round-<n>.json`.
</references>

<principles>
- **손잡이는 하나만 연다.** 시스템 프롬프트의 지정 구역, 스킬 문서 하나, 메모리 규칙 항목 중 하나를 고르고 나머지는 고정한다. 한 라운드에 가설 하나다.
- **개선안은 판정 기준과 권한을 못 건드린다.** 평가셋·정답·숨긴 테스트, 채점기·임계값·반복 수, 권한·도구 허용 정책·훅·게이트, 예산·모델·추론 강도, 실행 기록, 테스트 코드, 이 루프의 코드는 개선 대상이 아니다. 지시문이 아니라 경로 허용 목록과 해시 검사로 막는다.
- **개선안을 만든 쪽이 읽은 사례로 판정하지 않는다.** 읽기용과 판정용을 나눈다. 사례가 적으면 나누지 않고 반복 실행으로 흔들림을 줄이되 결과에 "분할 없음, 방향성 판정"이라고 적는다.
- **결과를 본 뒤 규칙을 바꾸지 않는다.** 지표, 판정 순서, 최소 효과, 승인자는 실행 전에 파일로 고정한다.
- **고치는 것은 증분이다.** 항목을 추가·수정·폐기하는 diff만 받는다. 문서를 통째로 다시 쓰게 하지 않는다.
- **반영은 승인과 최종 확인 뒤에 한다.** 판정 → 사람 승인 → 반영 전 최종 확인 → 반영 순서를 바꾸지 않는다.
- **모의 실행 결과는 개선율이 아니다.** "계약 검증"이라고만 적는다.
</principles>

<procedure>
1. **설정 고정:** `design/06-improve.md`의 "개선 설정"을 사용자와 채우고 커밋한다. 손잡이와 허용 경로, 읽기용·판정용 사례 ID(유형별 무작위. 기준선 점수를 보고 고르지 않는다), 주 지표와 최소 효과, 가드레일 상한, 최대 라운드, 비용 상한, 승인자, 되돌리기 기준. 이 커밋이 결과보다 앞서야 한다.
2. **잴 수 있는지 확인:** 손잡이에 값을 하나 쓰고 에이전트가 쓰는 경로로 읽어 실제로 읽히는지 본다. 평가 하네스의 해시를 적는다. 현재 버전을 한 번 더 돌려 흔들림 폭을 적는다. 흔들림 폭이 최소 효과보다 크면 반복 수나 사례를 늘리자고 제안하고 멈춘다.
3. **실패 수집:** 읽기용 사례의 기록에서만 실패 신호(도구 오류, 테스트 실패, 채점의 수정 필요 판정, 리뷰 수정 반복, 게이트 차단, 최대 턴 도달)를 모은다. 실패마다 관찰 사실 / 원인 가설 / 다른 설명 / 근거 이벤트 ID를 쓴다.
4. **오염 검사:** 개선안을 만드는 쪽에 보낼 입력에 정답, 임계값, 판정용·최종 확인용 사례 ID, 테스트 기대값이 있으면 호출하지 않고 멈춘다. 하네스 해시가 2번과 다르면 멈춘다.
5. **후보 생성:** 독립 컨텍스트에서 후보를 `harness/reference/memory-improve.md` 6절 형식으로 받는다(최소 버전은 1개, 여럿이면 제안값 3개). 허용 경로 밖 변경, 문서 전체 교체, 기준을 낮추는 문구, 실패 사례의 고유 문자열을 붙여 넣은 변경, 길이 상한 초과, 현재 버전과 같은 후보, 기대 효과나 예상 회귀가 빠진 후보는 사유와 함께 거부로 남긴다. 이 시점에 대상 파일은 바꾸지 않는다.
6. **비교:** 유료 실행 전에 규모(사례 수 × 반복 × 버전 수 ≈ 호출 수)를 한 줄로 알린다. 현재 버전(항상 포함)과 후보를 분리된 프로필에서 `harness/reference/eval.md`의 비교 방법으로 돌린다. 시도마다 초기 상태를 복원하고 새 세션에서 잰다.
7. **판정 (순서 고정. 걸리면 멈춘다):**
   1. 판정 불가: 하네스 해시 불일치, 오염, 평가 완료율 미달, 응답의 모델이 설정과 다름, 현재 버전에 고칠 실패가 없음, 흔들림 폭이 최소 효과 이상.
   2. 기각: 후보 실행에 정책 위반이 있거나 금지 경로를 건드렸다.
   3. 보류: "평가 회귀가 없다"를 만족하지 못했다.
   4. 기각: 읽기용만 오르고 판정용은 그대로다. 보류: 판정용 개선이 최소 효과에 못 미친다.
   5. 보류: 가드레일 상한을 넘었거나, 바뀐 항목이 읽히고 인용된 기록이 없다.
   6. 채택 후보: 위를 모두 지났다. 여럿이면 판정용 결과로 고르고, 비슷하면 변경이 가장 작은 것을 고른다.
   7. 그 밖은 보류.
   변경으로 설명하기 어려울 만큼 크게 올랐으면 사례 몇 건을 직접 열어 확인한 뒤 판정한다.
8. **기록:** `improve/round-<n>.json`을 새 파일로 쓴다(같은 이름이 있으면 거부). 현재 버전, 후보, 거부 사유, 사례별 비교표, 판정과 사유, 하네스 해시, 개선안 입력의 해시를 넣는다. `design/06-improve.md`의 라운드 표에 요약을 적는다.
9. **사람 승인:** 채택 후보의 diff와 사례별 비교표를 승인자에게 보이고 승인을 받는다. 승인이 없으면 보류다. 이 스킬을 돌리는 에이전트는 승인자가 될 수 없다.
10. **반영 전 최종 확인:** 승인받은 diff 그대로(해시 일치)를 현재 버전 위의 깨끗한 작업 폴더에 적용한다. 하네스 해시와 금지 경로를 다시 검사하고 개발용 평가 전체를 한 번 돌려 정책 위반과 회귀를 다시 본다. 비교 뒤 현재 버전이 그대로이고 분할 없이 전체를 이미 돌렸으면 재실행은 생략한다. 실패하면 반영하지 않고 보류로 기록한다.
11. **반영:** 커밋 하나로 넣고 버전 표시(r0 → r1)를 올리고 되돌리는 명령을 적는다. 새 세션에서 같은 종류의 작업을 돌려 반영분이 쓰였다는 기록(메모리 조회, 스킬 로드, 계획 인용)을 증거로 남긴다. 되돌리는 명령은 한 번은 실제로 실행해 본다.
12. **멈춤:** 최대 라운드나 비용 상한에 닿으면 멈춘다. 2~3 라운드(제안값) 연속으로 판정용 개선이 흔들림 폭을 못 넘으면 내용을 더 고치지 않고 남은 실패를 지침 부족 / 채점기 / 환경·하네스 / 구조 / 흔들림으로 나눠 보고한다.
13. **되돌림과 승격:** 반영 뒤 되돌리기 기준에 닿으면 이전 버전으로 돌리고 라운드 기록에 남긴다. 같은 실수가 채택 뒤에도 나오면 더 강한 층(규칙 → 스킬 → 훅·권한 → 테스트·CI)으로 옮기자고 제안하고 아래 층의 항목은 폐기 표시한다.
</procedure>

<boundaries>
- 최종 확인용 데이터는 이 스킬에서 열지 않는다. 릴리스 전에 한 번만 쓴다(S8).
- 채택은 "릴리스 후보"다. 팀에 배포하는 것은 S8의 통로를 거친다.
- 모델·추론 강도·예산을 바꾸는 제안은 다루지 않는다(S7, `optimize-agent`).
- 경험 저장소의 구조와 쓰기 정책은 S3에서 정한다. 이 스킬은 조회·주입이 이미 동작한다고 보고 개선 루프만 맡는다.
</boundaries>

<implementation_notes>
- 현재 버전과 후보는 메모리·설정이 섞이지 않게 분리된 프로필(디렉터리, 에이전트 이름 등)로 돌린다.
- 메모리와 스킬 목록을 세션 시작 때 한 번만 읽는 구조라면 반영 효과는 새 세션에서 잰다.
- 에이전트가 규칙·스킬 파일을 직접 고칠 수 있으면 이 루프를 우회한다. 실행 전 검사로 쓰기를 막고 개선안 경로로만 받는다.
- 평가 하네스, 정답, 숨긴 테스트는 개선안을 만드는 쪽과 평가받는 에이전트 둘 다 읽거나 쓸 수 없는 곳에 둔다.
- 이전 시도의 흔적(작업 폴더, git 기록)이 다음 시도에 보이지 않게 한다.
</implementation_notes>

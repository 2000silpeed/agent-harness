name: criteria-check
description: harness/CRITERIA.md의 인수 기준(15개 항목, 40점)을 항목별로 실제 증거와 함께 자가 점검하고 design/08-release.md 표와 README 확인 방법의 빈칸을 찾는다. 제출·배포 전, 중간 점검, "기준을 다 채웠나", "몇 점 나올까" 질문, S8 단계에서 사용.
---

<procedure>
1. `harness/CRITERIA.md`를 읽는다. `design/00-brief.md`에 다른 인수 기준이 적혀 있으면 그것도 함께 본다.
2. 항목마다 **직접 확인**한다. 문서에 "구현했다"고 적힌 것만으로는 인정하지 않는다.
   - 코드 기준(린트, 명명, docstring)은 검사 명령을 실제로 돌리고 출력을 붙인다.
   - 기능 항목은 README의 확인 방법을 그대로 실행하거나, 실행된 기록·파일을 연다.
3. 근거 수준을 단다: 실행해서 확인 / 코드만 확인 / 문서만 확인 / 추정. "실행해서 확인"이 아니면 위험 항목으로 표시한다.
4. `design/08-release.md`의 인수 기준 표를 채운다: 항목 | 배점 | 증거 위치(파일:줄, 기록 경로, 명령 출력) | 근거 수준 | 판정(충족/부분/미충족) | README 확인 방법 유무. 보완할 것은 표 아래에 항목별로 적는다.
   - 약한 증거를 가려낸다: 저장소 파일이 있다는 것만으로는 3-1이 아니다(저장 이벤트와 새 세션에서 읽힌 기록). 조회 이벤트만으로는 3-2가 아니다(계획에 인용). 계획 파일의 승인 표시만으로는 2-4가 아니다(에이전트가 직접 쓸 수 있으면 자기 승인이다). 과제 5건의 전후 수치로 "성능 개선"을 주장하지 않는다(절차의 증거로만 쓴다).
5. 평가자는 README만 보고 빌드·실행한다. README에 그 항목의 확인 방법(입력 → 기대 관찰 → 확인 명령)이 없으면 구현이 있어도 "부분"으로 본다.
6. 마지막에 보완 우선순위를 배점 순으로 3개 제안한다. 판정을 부풀리지 않는다.
</procedure>

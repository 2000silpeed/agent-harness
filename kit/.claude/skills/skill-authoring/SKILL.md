---
name: skill-authoring
description: 에이전트 스킬(SKILL.md)을 새로 쓰거나 기존 스킬을 고칠 때 작성 기준(무엇·언제를 앞에 둔 설명, 짧은 본문, references·scripts 분리, 호출 시험)으로 작성하고 점검한다. 스킬 생성, 스킬 리뷰, "스킬이 잘 안 불린다", "엉뚱할 때 불린다", S4 단계에서 사용.
---

<structure>
```
<skill-name>/
├── SKILL.md       # 머리말 + 핵심 지시
├── scripts/       # 실행 코드 (결정적이어야 하는 단계)
├── references/    # 필요할 때만 읽는 상세 문서 (SKILL.md에서 한 단계 깊이까지만)
└── assets/        # 양식, 템플릿 등 고정 리소스
```
</structure>

<what_to_put>
- 스킬은 평가나 실제 작업에서 드러난 빈틈에서 시작한다. 같은 절차를 세 번째 붙여넣게 되면 만든다.
- 모델이 이미 아는 것은 쓰지 않는다. 이 프로젝트에서만 통하는 절차·명령·경로·함정을 쓴다.
- 깨지기 쉬운 절차는 구체적으로(명령과 순서), 판단이 필요한 일은 원칙만 적는다.
- 결정적이어야 하는 단계는 본문에 풀어 쓰지 않고 `scripts/`의 스크립트로 둔다.
</what_to_put>

<frontmatter_rules>
- `name`: 소문자·숫자·하이픈, 64자 이내, 폴더 이름과 같게 한다.
- `description`: **무엇 + 언제(+ 아닌 경우)** 를 두세 문장으로, 3인칭으로 쓴다. 가장 중요한 말을 앞에 둔다. 목록에 실릴 때 길면 뒤가 잘린다(Claude Code는 설명과 사용 시점을 합쳐 1,536자에서 자른다). 반드시 불려야 하는 작업명이나 사용자가 실제로 쓰는 표현을 넣는다.
- 부작용이 있거나 순서가 중요한 스킬은 모델이 스스로 부르지 못하게 하고 진입 절차나 사용자가 부르게 한다(Claude Code: `disable-model-invocation: true`).
- `allowed-tools`는 도구를 제한하는 장치가 아니라 미리 승인하는 장치다. 제한은 권한 설정으로 한다.
</frontmatter_rules>

<body_rules>
- 본문은 500줄, 5천 토큰 이내로 쓴다. 넘으면 `references/`로 옮기고 "X일 때 references/x.md를 읽어라"라고 안내한다.
- **가장 중요한 지시를 본문 맨 위에 둔다.** 대화가 압축되면 앞부분만 남을 수 있다.
- 구역은 한 가지 방식으로 나눈다(마크다운 제목이든 태그든). 한 저장소 안에서는 통일한다. 이 프로젝트의 스킬은 태그(`<purpose>`, `<procedure>`, `<anti_patterns>`)를 쓴다.
- 긴 "언제 쓰나"를 본문 맨 앞에 두지 않는다. 그건 설명문이 할 일이다.
- 스킬이 쓰는 도구(스크립트, MCP 등)마다 어떤 작업에 어떻게 쓰는지를 적는다.
- 순서가 중요한 다단계 절차는 "`scripts/1.sh`를 실행하라"까지만 쓰고, 각 스크립트 출력이 다음 스크립트를 안내하게 한다. 안정되면 `run.sh` 하나로 합친다.
</body_rules>

<testing>
1. 불려야 할 요청과 불리면 안 되는 요청을 각각 3건 이상 만든다. 실제 사용자가 쓰는 표현으로 쓴다.
2. 새 세션에서 돌려 적중과 오발을 센다. 에이전트가 쓸 모델 전부로 돈다(강한 모델에서 되던 스킬이 작은 모델에서는 지시가 부족할 수 있다).
3. 스킬을 끈 상태와 켠 상태로 같은 과제를 돌려 결과가 달라지는지 본다. 차이가 없으면 스킬이 필요 없거나 평가가 그 능력을 재지 않는 것이다.
4. 설명문을 고칠 때는 한 번에 하나씩 고치고 다른 스킬의 적중·오발도 다시 본다.
5. 형식 검사 도구가 있으면 돌린다(Claude Code: `claude plugin validate`).
</testing>

<review_checklist>
점검할 때 아래를 하나씩 확인하고 결과를 표로 보고한다.
1. `name` 형식과 폴더 이름이 일치하나
2. 설명문에 무엇·언제가 있고, 중요한 말이 앞에 있고, 아닌 경우가 적혀 있나
3. 본문이 500줄·5천 토큰 이내이고 가장 중요한 지시가 맨 위에 있나
4. 모델이 이미 아는 설명이 들어 있지 않나
5. 상세 내용이 references로 빠졌고(한 단계 깊이), 언제 읽을지 안내가 있나
6. 결정적 작업이 scripts로 빠졌나
7. 호출 시험 결과(적중·오발, 시험한 모델)가 있나
8. 남이 만든 스킬이면 스크립트와 의존성을 설치 전에 읽었나
</review_checklist>

<always_on>
항상 로드돼야 하는 내용은 설명문 호출에 맡기지 말고 세션 시작 훅이나 지침으로 넣는다. 다만 상시 로드량이 늘어나므로 짧게 둔다.
</always_on>

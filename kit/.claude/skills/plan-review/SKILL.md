---
name: plan-review
description: 코드를 바꾸기 전에 작업 계획(요구사항·범위·완료 조건·수정 대상·순서·테스트 방법)을 design/plans/에 쓰고, 독립 컨텍스트의 리뷰를 받아 반영한 뒤 사용자 승인을 받는다. 기능 추가·버그 수정·리팩터링 등 코드 변경 요청이 들어왔을 때, 그리고 진행 중 범위가 바뀔 때 사용. 질문 답변이나 문서만 고치는 작업에는 쓰지 않는다.
---

<purpose>
승인된 계획 없이는 코드를 바꾸지 않는다(5일차 7강: 계획 → AI 리뷰 → 승인 후에만 코드 변경, 범위가 바뀌면 재검토). 만드는 제품이 코딩 에이전트라면 이 절차를 제품의 계획 기능 원형으로도 쓸 수 있다.
</purpose>

<plan_file>
`design/plans/<YYYYMMDD>-<짧은-이름>.md`에 아래 순서로 쓴다.
```
---
status: draft | in_review | approved | superseded
version: 1
---
## 요구사항          (사용자 원문 인용 + 정리)
## 범위              In: / Out:
## 완료 조건         실행 결과로 참/거짓을 가릴 수 있는 문장만
## 수정 대상         파일 경로 목록 (새 파일 포함)
## 작업 순서         1. 2. 3.
## 테스트 방법       실행할 명령과 기대 결과
## 참조 메모리·근거   decisions.md 항목, 과거 실패, 관련 문서
## 리뷰 이력         v1 리뷰 의견 → 반영 내용 → v2 ...
```
</plan_file>

<procedure>
1. 요구가 모호하면 먼저 한 번에 하나씩 질문한다. 완료 조건을 지어내지 않는다.
2. 계획 v1을 쓰고 `status: in_review`로 둔다.
3. **리뷰는 독립 컨텍스트에서 한다.** 서브에이전트(Agent 도구)에 계획 파일 경로만 주고 아래 체크리스트로 판정하게 한다. 리뷰어는 파일을 수정하지 않는다.
   - 완료 조건이 검증 가능한가
   - 수정 대상이 요구사항을 모두 덮고, 불필요한 파일이 없는가
   - 작업 순서에 의존 관계 오류가 없는가
   - 테스트 방법이 완료 조건을 실제로 확인하는가
   - 위험한 동작(삭제·외부 전송·대량 변경)이 표시됐는가
   - 판정은 `APPROVE` 또는 `REVISE`와 항목별 의견이다.
4. REVISE면 의견을 반영해 version을 올리고, 리뷰 이력에 "의견 → 반영"을 적은 뒤 다시 리뷰한다. 같은 의견이 두 번 반복되면 멈추고 사용자에게 묻는다.
5. APPROVE를 받으면 계획 요약을 사용자에게 보여주고 승인을 받는다. 승인 뒤에만 `status: approved`로 바꾸고 코드를 바꾼다.
6. 구현 중 수정 대상 밖의 파일을 바꿔야 하거나 완료 조건이 바뀌면 멈춘다. 계획을 새 버전으로 고치고 3단계부터 다시 한다.
7. 끝나면 테스트 결과를 계획 파일 끝에 붙이고, 결정이 있었다면 `design/decisions.md`에 한 줄 남긴다.
</procedure>

<anti_patterns>
- 리뷰를 같은 컨텍스트에서 스스로 하고 APPROVE를 주기
- 승인 전에 "작은 수정이라" 코드부터 바꾸기
- 리뷰 의견을 반영하지 않고 이력만 적기
</anti_patterns>

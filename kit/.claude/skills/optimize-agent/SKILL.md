---

<rules>
- **동작이 바뀌면 안 된다.** 도구 호출 순서와 최종 응답의 의미가 그대로여야 한다. 확인은 P7 평가로 한다.
- 가능하면 새 세션에서 상위 모델로 작업한다(구현할 때보다 높은 추론 수준).
- 변경은 하나씩, **토글**(환경변수나 설정 플래그)로 켜고 끌 수 있게 만든다.
- 변경마다 "기존 문제 → 무엇을 바꿨나 → before/after 수치"를 남긴다. 근거 없는 최적화는 되돌린다.
</rules>

<checklist>
컨텍스트 관점
1. 도구 개수를 적절히 줄일 수 있나(비슷한 도구 합치기, 결과가 필요 없는 도구 출력 줄이기)
2. 프롬프트를 더 적게 넣고 동적으로 제어할 수 있나(고정 부분은 앞, 변하는 부분은 뒤, 캐시 적중 확인)
3. 스킬을 도입할 곳이 있나(프롬프트에 박혀 있는 조각 지식)

구조 관점
4. 지연을 고려할 때 서브에이전트로 분리하는 게 나은가(독립 작업 병렬화, 컨텍스트 격리)
5. 지금 모델보다 작은 모델(예: Sonnet → Haiku)로 처리할 수 있는 구간이 있나
6. 판단 구간(분류, 선택)을 디시전 모델로 바꿀 수 있나
7. 출력 토큰을 줄일 수 있나(선택지 고르기, 간결한 응답 형식)
</checklist>

<reference_result>
3일차 6강 강사 사례: 한 턴 약 4초 → 1.42초. Sonnet → Haiku로 약 1.5초, 판단 구간을 디시전 모델로 바꿔 약 1초를 더 줄였다.
</reference_result>

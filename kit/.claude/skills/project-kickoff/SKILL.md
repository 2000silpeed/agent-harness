name: project-kickoff
description: 코딩 에이전트 구축을 시작할 때 사용자를 인터뷰해 design/00-brief.md(에이전트로 풀 일인지, 대상 작업, 기반, 모델, 성공 지표와 상한, 금지 행동)를 채운다. 프로젝트 시작, 요구사항 정리, "뭘 만들지" 논의, S0 단계에서 사용. 브리프 완료 기준을 이미 통과했다면 쓰지 않는다.
---

<purpose>
막연한 목표를 "완료"가 숫자로 정의된 작은 프로젝트로 바꾼다. 답을 추측해서 채우지 않고 사용자에게서 끌어낸다. 여기서 정한 숫자가 뒤 단계 전부의 판정 기준이 된다.
</purpose>

<procedure>
1. `bash harness/scripts/start-phase.sh 0`으로 브리프를 만든다. `harness/METHOD.md`의 S0 절을 읽는다.
2. 질문은 **한 번에 하나**만 한다. 이미 답한 항목은 다시 묻지 않는다. 가능하면 선택지를 2~4개 제시한다.
3. 질문 순서:
   - 누가, 어떤 저장소·언어에서 쓰나. 지금은 그 일을 어떻게 하나.
   - **에이전트로 풀 일인가.** 필요한 파일 수·단계 수가 건마다 다른가, 통과/실패로 돌아오는 검사가 있는가, 건당 비용을 감당하는가. 단계가 늘 같으면 코드가 순서를 정하는 워크플로를 권한다.
   - 에이전트에게 **완전히 맡길 수 있고 자동 검증이 있는(또는 붙일 수 있는)** 가장 작은 작업은 무엇인가. 하나만 고른다. 과거 사례 가운데 자동 검사를 붙일 수 있는 건수를 같이 묻는다.
   - 기반은 무엇으로 할까. `harness/bases/`에 그 기반의 참고 문서가 있으면 먼저 읽는다. 후보마다 브리프의 기반 표를 채운다(소스 수정, 끼어들 지점, 사내 모델, 요청·응답 원문 덤프, 구성요소 끄기, 컨텍스트 관리 제어, 재개, 공개 형식, 라이선스).
   - 코드가 회사 밖으로 나가도 되는가. 안 되면 어떤 모델을 어떤 장비에 올릴 수 있나(`serving-plan` 스킬).
   - 기준선용 모델은 쓸 수 있는 것 중 가장 강한 것으로 잡는다. 더 작은 모델은 "나중에 내려 볼 후보" 칸에만 적는다.
   - 결과가 어떻게 나오면 "끝났다"고 말할 수 있나. 성공률·지연·통과 1건당 비용의 목표값과 건당 턴·시간·토큰 상한은.
   - 에이전트에게 절대 맡기지 않을 행동은.
   - 사람이 지켜보지 않는 실행을 목표로 하나. 그렇다면 브리프의 다섯 문항을 묻는다.
4. **완료 기준 검사:** "잘 되면", "깔끔하게" 같은 기준은 받지 않는다. 실행 결과로 참/거짓을 가릴 수 있는 문장이 될 때까지 다시 묻고, 확인 방법(명령·기록)을 옆에 적는다.
5. 범위가 크면 줄이자고 제안한다. 뺀 부분은 "이번에 안 하는 것"에 적는다.
6. 기반 후보를 설치하기 전에 구성(스킬·에이전트·훅·MCP·설치 스크립트)과 위험을 먼저 읽어 표에 적는다. 남의 코드를 내려받아 실행하는 일은 사용자에게 확인을 받고, 망가져도 되는 환경에서 한다.
7. 스모크를 제안한다(사용자가 돌리거나 승인한 환경에서): 기반 후보마다 같은 작은 작업을 시켜 요청·응답 원문을 덤프해 읽기, 모델 후보마다 편집 과제 N건의 적용 실패 수 세기. N과 통과선은 돌리기 전에 적는다.
8. 다 채우면 요약해서 보여주고 확인을 받는다. 확인 뒤에만 완료 기준을 체크한다. 기반·모델 선택 근거는 `design/decisions.md`에 한 줄씩 남긴다.
</procedure>

<anti_patterns>
- 질문 여러 개를 한꺼번에 묻기
- 사용자가 말하지 않은 목표값이나 제약을 지어내기
- 검증 수단이 없는 작업을 첫 대상으로 받기
- 약한 모델로 기준선을 잡기(실패가 모델 한계인지 하네스 문제인지 가릴 수 없다)
- 브리프가 끝나기 전에 설계나 코드 이야기로 넘어가기
</anti_patterns>

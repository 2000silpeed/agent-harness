name: tool-design-review
description: 에이전트 도구·MCP 서버 명세나 구현을 검토해 도구 수, description, 인자 타입, 반환 형식, 오류 정책, 권한·승인 게이트 문제를 찾는다. 도구 추가·MCP 서버 설계·"도구를 잘못 고른다"·S4·S5 단계에서 사용.
---

<checklist>
**정의**
- [ ] 이름과 description만 보고 언제 호출할지 알 수 있다("Use when …")
- [ ] 인자에 타입과 설명이 있고, 복잡한 중첩 구조가 없다(Structured Output은 단순할수록 덜 실패한다)
- [ ] 비슷한 도구가 합쳐져 있다. REST 엔드포인트를 1:1로 감싸지 않았다

**반환**
- [ ] `status`, 출처(source_id), 시점·버전, 요약을 반환하고 원문을 통째로 넣지 않는다
- [ ] 빈 결과, 도구 오류, 연결 실패, timeout을 구분한다. 실패를 `[]`로 숨기지 않는다
- [ ] 모델이 고칠 수 있는 오류(400류)만 재요청 안내와 함께 전달하고, 런타임 오류(500류)는 숨긴다
- [ ] 결과가 다음 단계에 필요 없으면 짧은 확인 메시지로 줄여 컨텍스트를 아낀다

**실행**
- [ ] 오래 걸리는 작업은 비동기(요청 확인 → 진행 → 완료)로 처리한다
- [ ] 순서가 중요하면 도구가 현재 단계를 확인하고, 어긋나면 거절하고, 다음 도구를 알려준다
- [ ] 연관 호출이 많으면 코드 모드(스크립트로 묶어 한 번 실행)를 검토한다
- [ ] 변경 요청은 무조건 재시도하지 않는다(멱등성, idempotency key)

**MCP**
- [ ] MCP가 정말 필요한가(공유, 원격, 독립 배포, 권한·감사). 나만 쓰는 로컬 도구라면 스킬 스크립트로 둔다
- [ ] transport는 Streamable HTTP를 기본으로 한다(STDIO는 로컬 전용)
- [ ] 승인된 도구 이름만 노출하고, 필수 도구가 없으면 실패한다
- [ ] 서버가 사용자별 권한을 검사한다. 목록 필터만으로는 권한 통제가 아니다
- [ ] DB 접근에는 가드레일을 둔다(insert/update 검토, delete 차단, 원시 SQL 직접 실행 금지)
- [ ] 연결 후 실제 노출되는 도구 수와 컨텍스트 점유율을 확인했다. 많으면 Tool Search나 게이트웨이를 쓴다

**테스트**
- [ ] 모델 없는 단위 테스트, 모델이 포함된 도구 선택·인자 평가, E2E 업무 완료 평가가 분리돼 있다
- [ ] `tools/list` 성공에서 멈추지 않고 실제 호출·오류·거부 경로까지 테스트했다
</checklist>

<output>
문제마다 "도구 이름 | 문제 | 근거(체크 항목) | 고칠 방법"을 표로 보고한다. 고칠 때는 사용자 확인을 받는다.
</output>
